    MIB Operations Language SCOS-2000 Solar Orbiter Synthetic parameters

    Synthetic parameters and the OL language¶

    A synthetic parameter is a monitoring parameter whose value is computed by SCOS-2000 on the ground instead of being extracted from a telemetry packet. Older ESA control systems called them derived parameters.1 A synthetic parameter can convert an attitude quaternion into angles, combine two redundant units into one "in use" value, or decide whether another parameter is meaningful at all. Once computed, it is treated like any other telemetry parameter. It can be displayed, calibrated, limit checked and used inside other synthetic parameters.5

    In the MIB, a synthetic parameter is a PCF record whose nature field PCF_NATUR is not R. Most synthetic parameters also have a text file, named after the parameter, that holds its definition in the SCOS-2000 Operations Language (OL).614 This page describes the kinds of synthetic parameter and how each is evaluated, what the available sources say about the OL, and what the real definitions in the Solar Orbiter MIB release MIB__20250916M25925PFMS001_SOL look like. Every Solar Orbiter number comes from this wiki's own SQL queries on that release.42

    The kinds of synthetic parameter¶

    PCF_NATUR (field 11 of the PCF, Char(1), mandatory) gives the nature of every monitoring parameter. Five of its six values describe computed or constant parameters:

    Dynamic OL synthetic parameters (D)¶

    A dynamic OL synthetic parameter is defined by an OL text. Its life cycle has four properties that matter in practice:1

    • Local and lazy. It is evaluated in the process that needs it, and only if some server or user application needs it, for example a TM Desktop display or the validity of another displayed parameter.
    • Change driven. When needed, it is re-evaluated every time a sample of a contributing dynamic parameter is received and its value or validity has changed.
    • Not stored. Computed values are not archived. In retrieval mode the parameter is recomputed in the same way as in real time.
    • Editable on line. After import the OL definition can be changed on line. The change is local unless it is broadcast, in which case all processes use it until the next database import.

    The ICD adds a warning about super-commutated inputs: a synthetic parameter that uses one is recomputed once per sample of that input, which can be very costly.2

    SPEL synthetic parameters (P)¶

    SPEL parameters behave exactly like dynamic OL parameters, but their definitions use the Synthetic Parameters Expression Language and live in the directory named by the IMPT_SPEL_DIR configuration variable. The ICD notes that, for the time being, SPEL is supported only by the SCOS-2000 delivery for EGSE systems, not by the standard deliveries.62 The SPEL syntax is not described in the available sources.

    Hard-coded synthetic parameters (H)¶

    A hard-coded synthetic parameter is a C++ routine, either written directly or produced by the OL compiler from a dynamic OL definition, and linked into the relevant library. It is used exactly like a dynamic OL parameter. The ICD weighs the choice: hard-coded parameters need much less processing power and are not limited by the OL syntax, but their definition can neither be seen nor changed on line.2 A 2003 ESA presentation lists the same three flavours, "OL-synthetic", "Compiled OL" and "Hard-coded (C++)", next to the item "Re-calculated for retrieved data".22

    Saved synthetic parameters (S)¶

    A saved synthetic parameter has no expression of its own. PCF_RELATED names a dynamic OL or hard-coded synthetic parameter, and a central process, the Synthetic Parameters Packet Generator (SPPG), evaluates that definition systematically whenever a changed sample of a contributing parameter arrives.72 The values are written, in raw or engineering form as computed and with their validity flags, into SCOS-2000 TM packets of their own, the synthetic packets.2

    Two configuration files drive the SPPG. sppg.apid.ctrl lists the synthetic packets (by SCOS-2000 packet ID) that the SPPG generates. sppg.map gives, for each synthetic packet, the packet ID of the TM packet whose arrival triggers its generation, and optionally the domain of that packet. Each line holds tab-separated fields, and several triggering packets may feed the same synthetic packet. The triggering packet must contribute, directly or indirectly, to one of the saved parameters, otherwise the SPPG never registers for it.23

    Each saved parameter needs a PLF entry giving its position in the synthetic packet, without overlaps. The slot is always 13 octets long, and PCF_PTC must be 13.38

    Slot sizes from the ICD.3 The ICD gives the three sizes but not their order inside the slot, nor the coding of the value-type octet. The diagram uses the order of the ICD's sentence.

    Solar Orbiter. The 2025 release has two saved synthetic parameters, NTTSS030 and NTTSS031 ("Last C_Lock DST-1" and "DST-2"). Their PCF_RELATED names the dynamic parameters NTTSX030 and NTTSX031, and both use PTC 13. Their PLF entries put them at octets 0 and 13 of SPID 66838, a packet of type (251,2) from APID 1966 described as "Saved Synthetics". The 13-octet step is exactly the ICD slot size, and both PCF records give PCF_WIDTH = 104 bits, the same 13 octets.44 The related dynamic parameters return an absolute time (PTC 9, PFC 17) and are discussed in the OL section below.

    Static user defined constants (C)¶

    A static user defined constant (UDC) is a parameter whose value comes from PCF_PARVAL. The ICD says that SCOS-2000 handles static UDCs as synthetic parameters with a constant value. The value can be changed, locally or globally, with the OL editor of the Telemetry Query Display. Dynamic UDCs, in contrast, have nature R and live in an internally generated "constants TM packet".16 In OL expressions both kinds are read through the .raw view (the value entered) or the .eng view (the calibrated value, only if the UDC is calibrated), for example C1000.raw.17 Solar Orbiter defines no parameter of nature C.42

    How SCOS-2000 evaluates synthetic parameters¶

    Cascades. A synthetic parameter is potentially recomputed whenever any contributing sample arrives. If C uses B and B uses A, a new sample for A triggers A, then B, then C. The ICD stresses that this differs from earlier control systems, where a derived parameter was computed when a given source packet arrived. Up to release 3.1 this meant that circular dependencies had to be avoided. Later releases compute each parameter at most once per update cycle triggered by a new source packet.4

    Validity. SCOS-2000 derives the validity of a synthetic value from the current validity of the values used to compute it. An explicit criterion in PCF_VALID/PCF_VALPAR can restrict it further. The overall validity is the logical AND of both.49 The SCOS-2000 EGSE manual shows validity as a bit set with named conditions, among them VAL_DIVIDE_BY_ZERO and VAL_OL_PARSE ("An error occurred parsing OL expression").32

    Calibration. A synthetic parameter can be calibrated. SCOS-2000 then treats the computed value as the raw value, whatever its meaning.4 The ICD's definitions say the same from the other side: for a synthetic parameter, the raw value is the output of its OL or hard-coded routine.12 The PCF field PCF_SPTYPE (E engineering, R raw) records which view the expression returns. It is not imported, and serves the off-line consistency checker to catch synthetics that return an engineering value and are wrongly calibrated again.10

    Types. A valid PTC and PFC must be given even for synthetic parameters, matching the format of the computed value, otherwise the importer rejects the parameter.8

    Where synthetics may be used. Because synthetic parameters are processed by the telemetry model, they are allowed wherever the ICD restricts a reference to "TM model" parameters: validity parameters, calibration and limit applicability parameters, verification and pre-transmission validation expressions, CDF_TMID, and displays.918

    Update policy seen from a test procedure. In the SCOS-2000 EGSE, a test procedure that subscribes to a parameter in the default UPDATE mode is notified when a TM packet updates it or when a contributing parameter is updated: for a synthetic parameter one of its source parameters, and for any parameter its validity, limit applicability or calibration selection parameter.34 For the variant running on the Herschel/Planck Central Checkout System (TOPE/CCS), the manual states that the policy for synthetic parameters is the same, and lists the status consistency (SCC) state among the triggers.33

    Definition files¶

    The ICD's interface overview says that dynamic synthetic definitions are stored as separate files, one per parameter, next to the ASCII tables.14 The rules are:

    • The file name is the parameter name (PCF_NAME), without extension.15
    • Dynamic OL files go into the directory given by the IMPT_EXPR_DIR configuration variable, SPEL files into IMPT_SPEL_DIR.12 Issue 5.1 gives the typical location /home/sops1/data/ASCII/SYNTHETIC.21
    • A file may have any number of lines. The importer reads it and verifies the content.1
    • In a multi-domain installation each domain has its own files, and the General Domain holds a "multi-domain database" whose only content is the multi-domain synthetic parameters.1415

    Projects that consumed MIBs treated the folder differently. The HCSS MIB Clarification and Tailoring Note accepted synthetic definitions in a subdirectory called synthetic for its final interface, where only constants (PCF_NATUR = C) were to be ignored. Its software version 0.2 ignored the folder and considered only parameters of nature R, and a check that would raise an error on invalid synthetic definitions was still "to be implemented".3937 The Alcatel note on MIB processing by the Herschel/Planck system database (HPSDB) requires the "derived parameter expression files" to be delivered with the MIB files.40 On the documentation side, the Herschel/Planck Operations Interface Requirements Document asks each instrument user manual to define every synthetic parameter by its purpose, its nature (dynamic, hard-coded or saved, with reference to ICD issue 5.1), its PCF_NAME, its input parameters from housekeeping or diagnostic packets, its algorithm and its validity condition.38 See Mission tailoring.

    The Solar Orbiter release follows the ICD layout: its archive contains a directory synthetic with 1,582 files, one per parameter of nature D, each named after its parameter. This wiki's SQLite copy holds them in the table synthetic(NAME, SOURCE). Every D parameter has a file, and every file belongs to a D parameter.43

    The Operations Language¶

    What the sources say¶

    The ICD says that the syntax of dynamic OL synthetic parameters is documented in the "SCOS-2000 Synthetic Parameters SUM" (RD-9, SUM-0019).1 Its reference list also includes a "SCOS-2000 Operations Language ADD" (RD-2, ADD-0007).13 Neither document is in this wiki's library. The ICD gives only scattered facts:

    • Synthetic parameter expressions are written in OL, and the importer verifies them.1
    • Parameters have a .raw and an .eng view (shown for UDCs as C1000.raw and C1000.eng).17 From release 2.3 the OL "only supports one view" to return a parameter's source value, whatever the parameter's nature, which is why a UDC may no longer be tied to both the static and the dynamic view.16
    • Issue 5.1 adds that another synthetic parameter is referred to through its .syn view; issue 7.0 no longer mentions this view.365 No Solar Orbiter file uses .syn.45
    • The OL recognises the kind of a component from its first characters, so no parameter name may begin with VAR, GVAR or $.11
    • SCOS-2000 has an OL compiler that turns a dynamic OL definition into C++.2

    The 2003 ESA presentation adds that SCOS-2000 uses the public-domain tools Flex and Bison for OL parsing.23

    The SCOS II OL: design intent¶

    A paper by ESOC and Computer Resources International describes the Operations Language of SCOS II, the control system generation that ESOC was developing for Huygens, Artemis and Envisat.24 The paper carries the NASA report number N95-17533 and plans its "release 1" for the first quarter of 1995.30 Its design goals explain much of what SCOS-2000 synthetic definitions look like:

    • Why a language. Calibrations cover most derivation needs, but some values must be computed by combining parameters algorithmically. In the Multi-Spacecraft Support System (MSSS) an operations engineer specified such algorithms on paper and a software engineer coded them; in SCOS I the operations engineer wrote them directly in FORTRAN with a few added constructs. In both cases the code was compiled and linked into the control system, an algorithm error was found only when it crashed at run time, and changes took a long time.25
    • Kinds of knowledge. The paper separates declarative knowledge (calibration curves, parameter structures, entered through forms) from expressive knowledge (derived parameters, command validation conditions) and procedural knowledge (operations procedures), the last two written in OL.26
    • Layers. An interaction layer (user interface), a logical layer centred on the OL, and a physical layer that provides the control-system services, linked by an explicit object-oriented data model.26
    • Interpreted and strongly typed. OL scripts are interpreted, but the data model is part of the type system, so misuse of an object is detected when the database is prepared rather than at execution. A script is a declaration part plus a statement list, and can be as small as a single Boolean expression.27
    • Default attributes. Each class may have a default attribute. For a parameter it is the engineering value, so the expression P112 means P112.eng.value. A parameter also offers a delta service to reach historical samples.28
    • Validity propagates. A value computed from non-valid values is itself non-valid.29
    • Parsing once. Scripts are part of the database configuration, so their parse trees are built at preparation time with lex and yacc and are used directly by the interpreter.2829
    • Kept simple. The authors describe the language as deliberately "kept simple and stupid", with the intelligent behaviour left to the physical layer objects.31

    The paper's own example computes a derived parameter P117: if the limit status of P112 is above limits, P117 takes the upper limit of P112, otherwise the engineering value of P112.27 Its Figure-2 writes this with := for assignment and an if … then … else … endif; block.28 Its table of constructs lists assignment, wait, function invocation, goto-label, if-then-else, select-case, while-do, repeat-until, for-in-list-do and for-to-step-next statements; value reference, function invocation, Boolean, numeric, string, time, list, set, matrix, vector and map expressions; and mathematical, statistical and bit-manipulation functions, object creation and object copy.28

    Inference

    The available sources do not state how far the SCOS-2000 OL follows the SCOS II OL. The shared name, the := assignment and the if … then … else … endif; block of the paper's example (both found in the Solar Orbiter files), and the .raw/.eng views, suggest a common lineage, but the SCOS-2000 grammar may differ in detail. The syntax summary below is therefore derived from what the real Solar Orbiter files contain, not from a specification.

    Inference

    The meanings below are this wiki's reading of the files, not documented semantics. := assigns, == compares, return(x) ends the evaluation with result x, and a file that ends with a bare expression (as NYGSX001 or NPWSX054 do) seems to return the value of that expression. land/lor and and/or both appear as logical operators. Names that begin with VAR_ are local variables, while GVAR_ variables keep their values between evaluations (the files say so in comments). .time gives the time stamp of a sample, and OPMCS_utc2obt and OPMCS_timeoffset look like mission-supplied functions. $NAME is described in a comment as a "static reference" that returns the previous value of the saved synthetic. No file uses loops, select/case, delta or wait.

    Worked example 1: attitude quaternion to roll, pitch and yaw¶

    The parameters NACSXN12, NACSXN13 and NACSXN14 ("GFE Attitude roll-angle", "pitch-angle" and "yaw-angle") are dynamic OL parameters of type PTC 5, PFC 2 (64-bit real). Their inputs are four telemetry parameters, NCAD4N12 to NCAD4N15, described as GFE_EST_QUAT_V-X, _V-Y, _V-Z and GFE_EST_QUAT-SC, also 64-bit reals. The PLF places the four at octets 17, 25, 33 and 41 of SPID 29501, a (3,25) housekeeping packet "AOCS Dynamics SASM/WSM" from APID 178, and in other AOCS packets.46 Browse them in the explorer: NACSXN12, NACSXN13, NACSXN14, NCAD4N15.

    Write \(q_1, q_2, q_3\) for the vector part (NCAD4N12, NCAD4N13, NCAD4N14) and \(q_4\) for the scalar part (NCAD4N15). The roll file reads (real file content, indentation normalised):46

    VAR_x := 1.0 - 2.0 * (NCAD4N12.raw * NCAD4N12.raw + NCAD4N13.raw * NCAD4N13.raw);
VAR_y := 2.0 * (NCAD4N15.raw * NCAD4N12.raw + NCAD4N13.raw * NCAD4N14.raw);

if VAR_x > 0 then
return(arctan(VAR_y/VAR_x)*180/3.1415926);
else
    if VAR_x < 0 and VAR_y < 0 then
    return((arctan(VAR_y/VAR_x)-3.1415926)*180/3.1415926);
    else
    return((arctan(VAR_y/VAR_x)+3.1415926)*180/3.1415926);
    endif;
endif;

    Line by line:

    1. VAR_x is \(x = 1 - 2(q_1^2 + q_2^2)\). The .raw view is used; the quaternion components have no calibration (empty PCF_CURTX), so the raw value is the decoded real number itself.1246
    2. VAR_y is \(y = 2(q_4 q_1 + q_2 q_3)\).
    3. If \(x > 0\), the roll angle is \(\arctan(y/x)\), converted to degrees with \(\pi \approx 3.1415926\).
    4. Otherwise the result is moved into the correct quadrant: subtract \(\pi\) when \(x < 0\) and \(y < 0\), add \(\pi\) in all other cases. Together the branches emulate the two-argument arctangent, giving a roll angle between −180° and +180°.

    The yaw file has the same shape with \(x = 1 - 2(q_2^2 + q_3^2)\) and \(y = 2(q_4 q_3 + q_1 q_2)\). The pitch file computes \(s = 2(q_4 q_2 - q_3 q_1)\) and returns \(\arcsin(s)\) in degrees when \(|s| < 1\), and \(-90\) or \(+90\) otherwise:46

    \[ \phi = \operatorname{atan2}\bigl(2(q_4 q_1 + q_2 q_3),\ 1 - 2(q_1^2 + q_2^2)\bigr),\quad \theta = \arcsin\bigl(2(q_4 q_2 - q_3 q_1)\bigr),\quad \psi = \operatorname{atan2}\bigl(2(q_4 q_3 + q_1 q_2),\ 1 - 2(q_2^2 + q_3^2)\bigr) \]

    Inference

    These are the textbook formulas for roll, pitch and yaw (a Z-Y-X, or 3-2-1, Euler sequence) of a unit quaternion whose scalar part is the fourth component. The MIB states neither the rotation convention nor the frames involved. Three details of the files are worth a reviewer's attention:

    • The clamp in the pitch file protects arcsin against rounding just outside \([-1, 1]\).
    • The roll and yaw files divide by VAR_x before testing it. When \(x = 0\) exactly, the division is by zero. The EGSE manual's validity flags include VAL_DIVIDE_BY_ZERO, which suggests that such a sample would be marked invalid rather than crash the evaluation.32
    • In all three pitch files (NACSXN13, NACSXNE3, NACSXWP3) the inner if is closed by elseif; instead of endif;. Since the importer verifies OL content, the parser apparently accepts this, but the available sources do not document elseif.

    The same three formulas are repeated for the "GSE Attitude" (NACSXNE2–NACSXNE4) and "AGP Dem." (NACSXWP2–NACSXWP4) angles, with other quaternion inputs.46

    Worked example 2: consistency of instantiated monitoring reports¶

    Almost two thirds of Solar Orbiter's synthetic parameters, 995 of 1,582, are consistency checks with descriptions such as PID11_S001_CONSISTENCY or PID11_F001_CONSISTENCY. Each is an 18-line file of the same shape:47

    ###########################################################
# This synthetic calculates the consistency of the
# instantiated service 12 packet for SMON 1 of PID 11
#
# In case the order in which the monitors are reported
# in the generic service 12 packet, this synthetic
# will flag the incorrectly parsed monitors as invalid.
#
# Returns 1 if the parsed and intended monitoring IDs match
#         0 otherwise
#
###########################################################

if (NXAS001A.raw == 1) then
   return (1);
else
   return (0);
endif;

    This is the real file NXAS001R. It belongs to an ingenious use of the MIB. A PUS service 12 monitoring list report carries a list of monitoring definitions, and the file's own comment warns that the monitors may not be reported in the expected order. Solar Orbiter's MIB nevertheless describes these reports as fixed packets, several SPIDs per subsystem ("#1", "#2", "#3", told apart by the monitor IDs in PI1 and PI2), with a fixed slot per expected monitor. SPID 65909, "AOCS - Monitoring List Report #1", has the parameter NXAS001A "PID11_S001_ID" at octet 19, followed by NXAS001B "Monitored Par", NXAS001C "Validity Par" and so on up to NXAS001Q at octet 65.47

    The synthetic parameter answers one question: does slot 1 really contain monitor 1? Every other field of the slot then uses it as its validity parameter. NXAS001B to NXAS001G and the event identifiers have PCF_VALID = NXAS001R, and the limit values NXAS001I and NXAS001L are in turn valid only when the "Limit Check" field NXAS001G is 1.47 If the spacecraft reports the monitors in a different order, the misplaced values are shown as invalid instead of being attributed to the wrong monitor. The same pattern covers the private "Functional Monitoring Status Report" packets of type (142,11) (NXAF001D and similar).

    flowchart LR
    A["NXAS001A<br/>monitor ID in slot 1<br/>(octet 19 of SPID 65909)"] --> R{"NXAS001R<br/>OL: A.raw == 1 ?"}
    R -- "1: valid" --> F["NXAS001B … NXAS001Q<br/>PCF_VALID = NXAS001R<br/>(or via NXAS001G / NXAS001N)"]
    R -- "0" --> X["all fields of slot 1<br/>flagged invalid"]

    Relationships from the PCF and PLF records of SPID 65909.47

    The scale is large: the 995 consistency parameters serve as validity parameter for 9,289 PCF records. Including other synthetics, 1,024 distinct synthetic parameters validate 9,756 parameters, which is almost half of the 20,692 PCF records that have a validity parameter at all.48 How the generic packet reaches SPID 65909 is a separate piece of Solar Orbiter tailoring, the dup table and APID-specific identification rules. It is explained on Mission tailoring of the MIB.

    Worked example 3: state across evaluations with global variables¶

    Most OL definitions are pure functions of their inputs. Nine Solar Orbiter files keep state between evaluations with GVAR_ variables. NPWSX054 "IFX_BDR1_Conv1_IIN_AVG" computes what its header calls the "rolling average of In-use PCDU BDR Converter Input Current", over up to 200 samples. Here is the real code, without its header and some other comment lines:49

    VAR_dummyA := NPWD4768; #Changes every packet, needed for OL to update
VAR_dummyB := NPWT4768; #Changes every packet, needed for OL to update
VAR_nmax := 200; # Rolling average window size
# PCDU-A in use
if NCSD0PC4.raw == 2 then
VAR_curr := NPWD4752;
else
#Else PCDU-B in-use
if NCSD0PD4.raw == 2 then
VAR_curr := NPWT4752;
else
VAR_curr := 0; # No PCDU in use....?
endif;
endif;
GVAR_NPWx4752cnt := GVAR_NPWx4752cnt + 1;
if GVAR_NPWx4752cnt > VAR_nmax then
GVAR_NPWx4752cnt := VAR_nmax;
endif;
GVAR_NPWx4752avg := GVAR_NPWx4752avg * (GVAR_NPWx4752cnt - 1)/GVAR_NPWx4752cnt + VAR_curr/GVAR_NPWx4752cnt;
GVAR_NPWx4752avg;
    1. The first two assignments read counters that change in every packet, NPWD4768 and NPWT4768. The comments explain why: referencing them makes them contributing parameters, so the definition is re-evaluated for every packet even when the current itself is unchanged. This is the change-driven evaluation rule of the ICD put to work.1
    2. The two if blocks pick the current of whichever PCDU (A or B) is in use, according to the status parameters NCSD0PC4 "PCDU A SCV Status.scvOp" and NCSD0PD4 (the same for PCDU B).
    3. GVAR_NPWx4752cnt counts samples up to the window size of 200.
    4. The average is updated recursively: \(\bar{x}_n = \bar{x}_{n-1}\,(n-1)/n + x_n/n\). Once the counter saturates at 200, this becomes an exponential moving average with weight 1/200.
    5. The last line is a bare expression, the global average, which the file uses as its result.

    NPWSX054 itself is declared as a 32-bit real (PTC 5, PFC 1). Its input currents NPWD4752 and NPWT4752 are 12-bit unsigned integers (PTC 3, PFC 8) with the unit A.4919

    Inference

    The files do not say how GVAR_ variables are initialised or whether they are shared between processes. A dynamic parameter is evaluated locally in each process that needs it and again in retrieval,1 so a rolling average kept in global variables probably depends on how long the displaying process has been running and on the retrieval start point. A related file, NSMXS009 "SSMM M0 Cont Error", tracks the growth rate of a memory error counter with OPMCS_utc2obt(NSM00798.time); in its first branch it returns GVAR_Ok, while every other line uses GVAR_SSMM_M0_Ok, and the same branch resets GVAR_SSMM_M0_Gradient although the rest of the file reads GVAR_SSMM_M0_LastGradient. Both look like slips.

    Statistics of the Solar Orbiter synthetic folder¶

    Size. The 1,582 files hold 762,460 characters, 482 on average and 3,995 at most. 45 files are empty and 22 more contain only the comment # empty script: spare parameters such as NCXSS028 "SPARE SEC OL 22" and test parameters NMCSX988–NMCSX999 "TEST Synth-…". 1,254 files contain comments.51

    Shape. 361 non-empty definitions fit on a single line, typically a validity helper such as NAHS0000 "Volt valid cond logic": if(NAHD0000.eng == "Standby") then return(0); else return(1);endif;. 996 files have exactly 18 lines, and 995 of them are the consistency checks of example 2.51

    Inputs. Ignoring the 67 files without code, a definition references between 1 and 140 other parameters, 1,180 of them exactly one. The largest, NPWSX103 and NPWSX104 "PCDU A/B LCL Power (all)", each reference 140 parameters.51

    Types and categories. 1,097 synthetics are Booleans (PTC 1, PFC 0). Next come 1-bit enumerations (PTC 2, PFC 1: 182), 32-bit reals (PTC 5, PFC 1: 96), 32-bit unsigned integers (PTC 3, PFC 14: 75) and 6-octet CUC relative times (PTC 10, PFC 17: 37).19 By category, 1,346 are numerical (17 calibrated), 210 are status parameters with a textual calibration, and 26 are text. Only 6 set PCF_SPTYPE, all to R.51

    Change since 2020¶

    The April 2020 release had 390 synthetic files: 354 for D parameters and 36 for H parameters. All 36 H files are empty, consistent with their definitions living in compiled C++, and 79 files are empty in total.532 By 2025 the H nature has disappeared, and at least some former H parameters are now OL: NCDS0AA1 "PS1 Expected DL Time" was hard-coded in 2020 and is defined by OPMCS_timeoffset(NCXSS001); in 2025.5350

    Inference

    The move from compiled to interpreted definitions, and the quadrupling of OL files, fits the ICD's trade-off: OL definitions can be read and changed on line, at the price of more processing.2 The releases do not record the reason. Note also that other control systems that read SCOS-2000 MIBs may support different synthetic languages: Terma lists "Different synthetic (derived parameter) languages" among the extensions of its CCS5/TSC products.41

    The SWA instrument database, published separately, defines no synthetic parameter: all 2,885 of its PCF records have nature R.54

    SQL used

    Run against solo-2025-09-16.sqlite (and solo-2020-04-16.sqlite, swa-idb.sqlite). The operator and construct counts were computed by a small Python script that reads synthetic.SOURCE, strips # comments and string literals, and counts regular-expression matches; it never executes the definitions.

    -- natures and files
SELECT PCF_NATUR, count(*) FROM pcf GROUP BY 1;
SELECT count(*), sum(length(SOURCE)), avg(length(SOURCE)), max(length(SOURCE)),
       sum(length(SOURCE) = 0) FROM synthetic;
SELECT p.PCF_NATUR, count(*) FROM synthetic s LEFT JOIN pcf p ON p.PCF_NAME = s.NAME GROUP BY 1;
SELECT count(*) FROM pcf p WHERE PCF_NATUR = 'D'
   AND NOT EXISTS (SELECT 1 FROM synthetic s WHERE s.NAME = p.PCF_NAME);      -- 0

-- saved synthetics
SELECT PCF_NAME, PCF_DESCR, PCF_RELATED, PCF_PTC, PCF_WIDTH FROM pcf WHERE PCF_NATUR = 'S';
SELECT l.PLF_NAME, l.PLF_SPID, l.PLF_OFFBY, p.PID_TYPE, p.PID_STYPE, p.PID_APID, p.PID_DESCR
  FROM plf l JOIN pid p ON p.PID_SPID = l.PLF_SPID WHERE l.PLF_NAME IN ('NTTSS030', 'NTTSS031');

-- example 1
SELECT SOURCE FROM synthetic WHERE NAME IN ('NACSXN12', 'NACSXN13', 'NACSXN14');
SELECT PCF_NAME, PCF_DESCR, PCF_PTC, PCF_PFC FROM pcf WHERE PCF_NAME LIKE 'NCAD4N1_';
SELECT PLF_NAME, PLF_SPID, PLF_OFFBY FROM plf WHERE PLF_NAME LIKE 'NCAD4N1_';

-- example 2
SELECT count(*) FROM synthetic s JOIN pcf p ON p.PCF_NAME = s.NAME
 WHERE p.PCF_DESCR LIKE '%CONSISTENCY%';                                       -- 995
SELECT PCF_NAME, PCF_DESCR, PCF_VALID, PCF_VALPAR FROM pcf WHERE PCF_NAME LIKE 'NXAS001%';
SELECT count(*), count(DISTINCT PCF_VALID) FROM pcf
 WHERE PCF_VALID IN (SELECT NAME FROM synthetic);                              -- 9756, 1024

-- uses (repeat for ocf.OCF_NAME, ocp.OCP_RLCHK, cur.CUR_RLCHK, cve.COL2, ptv.PTV_PARNAM, dpc.COL2)
SELECT count(*), count(DISTINCT OCP_RLCHK) FROM ocp WHERE OCP_RLCHK IN (SELECT NAME FROM synthetic);

-- types and categories
SELECT PCF_PTC, PCF_PFC, count(*) FROM pcf WHERE PCF_NATUR = 'D' GROUP BY 1, 2 ORDER BY 3 DESC;
SELECT PCF_CATEG, PCF_CURTX <> '', count(*) FROM pcf WHERE PCF_NATUR = 'D' GROUP BY 1, 2;

 WHERE p.PCF_NATUR = 'H' AND length(s.SOURCE) > 0;                             -- 0
