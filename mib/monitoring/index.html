    MIB Monitoring SCOS-2000 Solar Orbiter Telemetry

    Monitoring in the MIB: parameters and packets¶

    The SCOS-2000 Mission Information Base (MIB) is split into a static part, usually called the database, and a dynamic part, the packet archive.1 The static part tells the control system everything it needs to turn downlinked telemetry packets into named, typed and validated parameter samples. On the monitoring side, nine ASCII tables do this work. The PCF defines every monitoring parameter. PID, PIC and TPCF tell the telemetry packetiser how to recognise an incoming packet and which processing keys to give it. PLF and VPD describe where parameter values sit inside fixed and variable packets. GRP, GRPA and GRPK group parameters and packets.4 Calibration and limit checking hang off the PCF and have their own pages: Calibration in the MIB and Monitoring checks.

    This page follows the Database Import ICD issue 7.0 (EGOS-MCS-S2K-ICD-0001, 2017-08-11). The library copy comes from the Solar Orbiter MOC document server, where the file name begins with "MOC-applicable MIB".7 Every Solar Orbiter number below comes from this wiki's own SQL queries on the public release MIB__20250916M25925PFMS001_SOL (database version 25925PFM, comment 20250916-CSW3.1.2_MAS7.33).53 You can browse every object mentioned here in the MIB explorer.

    The monitoring tables at a glance¶

    Each table is a tab-separated ASCII file named after the table in lower case (for example pcf.dat), with one record per line. An empty optional field still carries its separator.2 Fields marked with * in the ICD form the table key. Fields marked M are mandatory. An optional field left empty takes the import default given in the ICD.3

    From packet to parameter sample¶

    The processing chain explains why the tables look the way they do. The SCOS-2000 telemetry packetiser receives a telemetry source packet. It reads the APID from its fixed place in the packet header, and the PUS service type and subtype from a position set by configuration variables. If the PIC says that this type/subtype needs more identification data, it extracts up to two further fields (PI1, PI2) from the packet data field. It then looks up the PID table with the full key and files and distributes a SCOS-2000 packet under the processing keys found there: the SPID for fixed packets and the TPSD for variable packets.28 PLF (fixed) or VPD (variable) definitions then govern parameter extraction.28

    flowchart LR
    A[TM source packet] --> B["Read APID<br/>(fixed header position)"]
    B --> C["Read type / subtype<br/>(position set by MISCconfig)"]
    C --> D{"PIC record for<br/>type/subtype/APID<br/>or type/subtype?"}
    D -- yes --> E["Extract PI1 / PI2<br/>(PIC offsets, widths)"]
    D -- no --> F["PI1 = PI2 = 0"]
    E --> G["PID lookup:<br/>TYPE, STYPE, APID, PI1, PI2"]
    F --> G
    G --> H["SCOS-2000 packet<br/>filed with SPID (+TPSD)"]
    H --> I["PLF: fixed layout<br/>(per SPID)"]
    H --> J["VPD: variable layout<br/>(per TPSD)"]
    I --> K["PCF: decode PTC/PFC,<br/>validity, calibration,<br/>checks, displays"]
    J --> L["Variable Packets Display<br/>(limited processing)"]

    Flow drawn from the packetiser description in the ICD.2832 The SCOS-2000 packet body holds the complete TM source packet. For missions that use the standard packetiser, PLF offsets therefore count from the first octet of the source packet header, and VPD processing starts PID_DFHSIZE octets later.34

    Two design constraints for the on-board software

    The ICD warns that the packetiser assumes two things. First, the type and subtype fields, when present, sit at the same position in every packet the spacecraft generates. Second, every packet with a given type/subtype carries its additional identification fields at the same position and with the same width.28 The ICD flags both as constraints that the on-board design must respect.

    PCF: monitoring parameter characteristics¶

    The PCF holds one record per monitoring parameter. The word "monitoring parameter" covers three things: telemetry parameters extracted from packets, user defined constants and synthetic parameters computed on the ground.8 Fields 20 to 23 are optional, for backward compatibility, and the importer accepts PCF records with 19 to 23 fields.8 The Solar Orbiter pcf.dat has 23 fields in every record.54

    Type and width: PTC, PFC and PCF_WIDTH¶

    The PTC/PFC pair is the parameter's encoding. SCOS-2000 uses it to decode values of parameters whose nature is R or C.11 The meaning of each pair is listed in Appendix A of the ICD, which follows the nomenclature of the Packet Utilisation Standard (PUS). The MIB parameter types page covers it in full, and PUS parameter types gives the PUS side. Values are always handled in three forms. The encoded value is the bits in the packet. The raw value is the decoded number before calibration. The engineering value is the result of calibration. Raw and encoded values only coincide for unsigned integers; a 16-bit signed raw value of −1, for example, is encoded as 0xFFFF.1

    PCF_WIDTH matters only for variable packets. It gives the slot width when it differs from the length implied by PTC/PFC, for example when padding bits byte-align the next field; padding bits always precede the value. For a deduced parameter (PTC 11), a width means "extract from a fixed-width slot"; no width means "use the length of the actual type, padded as defined for that type".1236 Only seven Solar Orbiter parameters set it. Five are deduced parameters of the on-board monitoring reports, each with a 64- or 32-bit slot. Two are saved synthetic parameters with a 104-bit (13-octet) slot.55 Thirteen octets is exactly the size the ICD prescribes for a saved synthetic parameter: 8 octets of value, 1 octet of value type and 4 octets of validity flags.23

    Validity: PCF_VALID, PCF_VALPAR and expiry¶

    A parameter value is only meaningful in some on-board states. A heater current means nothing while the heater's power line is off. The MIB expresses this with a validity criterion: the parameter is valid when the parameter named in PCF_VALID has the raw value PCF_VALPAR (default 1). SCOS-2000 also requires the validity parameter itself to be valid. The validity parameter must have an integer raw representation and must be processed by the telemetry model (it appears in the PLF or it is synthetic). Circular validity chains are not allowed.13 For a synthetic parameter, the overall validity is the logical AND of the validity derived from its inputs and its own explicit criterion.13

    A second mechanism needs no MIB entry. When no instance of a periodic packet arrives within its generation interval (PID_INTER) plus a globally configured margin, every parameter in it is flagged invalid ("expired"). The ICD notes that this removes the need to encode in validity criteria all the on-board conditions under which a packet is generated.8 Behind the single word "invalid" sits a bit set of reasons. The SCOS-2000 EGSE test language, for example, exposes flags such as VAL_STATE_OFF (state validity evaluates to 0), VAL_EXPIRED (packet not arrived), VAL_CALIBRATION (calibration failed) and VAL_UNKNOWN_STATE (state parameter invalid).51

    In the Solar Orbiter MIB, 20,692 parameters have a validity parameter, drawn from 2,933 distinct validity parameters, all of them integer types (PTC 1 to 4). The most used validity parameters are the …SCV Status.scvTm enumerations of the two PCDU and two RIU sides: NCSD0PC3 (PCDU A, 1,369 dependants), NCSD0PD3 (PCDU B, 1,357), NCSD0PE3 (RIU A, 1,210) and NCSD0PF3 (RIU B, 1,210). Their textual calibration CCDT0065TM maps 0, 1 and 2 to NOT_APPLICABLE, OFF and ON. Dependent parameters therefore use PCF_VALPAR = 2, which means "valid when ON". Of the 20,692 records, 9,775 use the value 1, 8,216 use 2 and 2,436 leave the field empty and inherit the default 1. The remaining 265 use 0 (243 records), 80 (12), 32 (8) or 64 (2).55 No Solar Orbiter PID record sets PID_INTER, so, as far as the MIB is concerned, no packet is declared periodic for expiry purposes.5930

    Category and nature¶

    PCF_CATEG tells SCOS-2000 which family of calibration applies. N covers numerical parameters, with or without a numerical, polynomial or logarithmic calibration, and all non-numerical types except character strings. S (status) is for parameters with a textual calibration. T (text) is for character strings (PTC 8).15 Solar Orbiter has 100,087 N, 26,538 S and 120 T parameters. The 120 T parameters match its 120 PTC 8 parameters exactly.55

    Synthetic parameters behave like telemetry parameters once computed. They can be displayed, calibrated (the computed source value is treated as the raw value) and limit checked.24 Dynamic OL parameters are recomputed whenever a contributing sample changes in value or validity, also during retrieval. Saved synthetic parameters are computed by the Synthetic Parameters Packet Generator (SPPG) and written into synthetic packets, so retrieval shows exactly what was computed in real time. The price is that only the values present when a triggering packet arrives are stored.23 The synthetic parameters page covers the languages and the 1,582 Solar Orbiter definition files. Solar Orbiter's two saved synthetic parameters are NTTSS030 and NTTSS031 ("Last C_Lock DST-½"). They save the synthetic parameters NTTSX030 and NTTSX031, use PTC 13 and have the 104-bit width noted above. Their PLF entries place them at octets 0 and 13 of SPID 66838 "Saved Synthetics" (type 251, subtype 2, APID 1966), one 13-octet slot each.5561

    User defined constants (UDCs) come in two kinds. A static UDC has PCF_NATUR = C and a database default in PCF_PARVAL, which can only be changed through the OL editor. A dynamic UDC has PCF_NATUR = R and a PLF entry in an internally generated "constants TM packet", whose values operators set through TM SPACON or the parameter injection interface.25 Solar Orbiter uses only dynamic UDCs. Its constants packet is SPID 66830 "Dynamic UDCs" (APID 1966, type 160, subtype 3). Among its 13 parameters are NCFZ0001 "TC Link Time Out", NDSZX003 "DST Uplink Path" and NPWZ0000 "PCDU_MODEL".56 The last one selects calibration curves at run time; see conditional calibration. The same pattern serves the MISC packet, which carries selected configuration variables as pseudo-telemetry. Those variables must be 32-bit signed integers (PTC 4, PFC 14), IEEE doubles (PTC 5, PFC 2) or character strings (PTC 8).26 Solar Orbiter's MISC packet is SPID 66832 "MISC_PACKET: Config variables packet MISCdynamic server" (APID 1966, type 160, subtype 5), with 21 parameters. Two of them use types outside that list: NYG01921 "TCO_DEFAULT_ENCOD_SCHEME" is PTC 5, PFC 1 (IEEE single) and NYG01923 "CMD VC ID" is PTC 4, PFC 12 (16-bit signed).56

    Calibration, checks and display fields¶

    PCF_CURTX names the single calibration of a parameter. It must match a TXF_NUMBR for status parameters, or a CAF_NUMBR, MCF_IDENT or LGF_IDENT for numerical ones. It is mandatory for status parameters. It must be empty for text, string (PTC 7, 8) and time (PTC 9, 10) parameters, and for parameters calibrated through the CUR table.17 In Solar Orbiter, 30,936 parameters name a calibration: 26,533 textual, 3,433 numerical and 970 polynomial. Another 907 parameters use conditional selection through CUR.57 PCF_INTER is a leftover. The ICD states that SCOS-2000 ignores it and takes extrapolation behaviour from the calibration curve.18 The calibration page gives the details.

    PCF_USCON = Y enables status consistency checking. The number of such parameters has a hard upper limit, set by the size of the packet that holds the snapshot of all status consistency checks; the PCF_USCON description says that from release 4.1 it can be changed with the configuration variable MAX_SCC_MESSAGE_LENGTH.19 The OCP rules elsewhere in the same ICD say it cannot be changed by configuration; see monitoring checks. Solar Orbiter flags 15 parameters, all with one OCP check of type C (monitoring checks).55

    PCF_UNIT and PCF_DECIM are pure display attributes. Solar Orbiter gives a unit to 5,124 parameters. Where PCF_DECIM is set, the most common values are 3 (23,081 parameters) and 2 (13,434).55

    Time parameters, archiving and byte order¶

    For absolute times, PCF_CORR = Y converts the on-board time to UTC with the time correlation of the clock named by PCF_OBTID. With N, the value is extracted unchanged and the clock's time format defines the epoch, or TCO_ESA_EPOCH when no clock is given.21 See time correlation in SCOS-2000 and CCSDS time codes. Solar Orbiter sets N for all 47 relative-time parameters, as the ICD requires, and for 3 absolute-time parameters. It never sets PCF_OBTID, so the mission default clock applies.55

    PCF_DARC = 1 asks the parameter archive (DARC) to record the parameter. Solar Orbiter sets it on 49,330 parameters.5522 PCF_ENDIAN = L declares a little-endian parameter. Exactly one Solar Orbiter parameter uses it: NYG02201 "GS Packet Size", a 32-bit unsigned integer.55

    Recognising packets: PID, PIC and TPCF¶

    PID: packet identification¶

    The PID maps packet identification values to SCOS-2000 packet IDs. The SPID identifies the structure of a fixed packet, as defined in the PLF. The TPSD identifies the structure of a variable packet, as defined in the VPD. One telemetry packet can be processed both ways.29

    # Field Type M / default Meaning
    1* PID_TYPE Number(3) M PUS service type, 0–255; 0 means no data field header
    2* PID_STYPE Number(3) M PUS service subtype, 0–255; 0 as above
    3* PID_APID Number(5) M APID: 0–2047 for spacecraft packets, 2048–65535 for packets generated by SCOS-2000 applications or other domains such as SCOEs
    4* PID_PI1_VAL Number(10) 0 value of the first additional identification field (for example a structure ID), 0 to 2^31−1
    5* PID_PI2_VAL Number(10) 0 value of the second additional identification field (for example a function ID)
    6* PID_SPID Number(10) M SCOS-2000 packet ID, 1 to 2^32−1 (0 not allowed); up to S2K-R5 it also chose the history file
    7 PID_DESCR Char(64) description; also the message text of the event raised when PID_EVENT is set
    8 PID_UNIT Char(8) on-board subsystem (future filtering)
    9 PID_TPSD Number(10) -1 structure ID for the Variable Packets Display; −1 if the packet is not in the VPD
    10 PID_DFHSIZE Number(2) M octets from the start of the source packet to where VPD processing begins (0–99), typically primary header plus data field header
    11 PID_TIME Char(1) N Y if the packet carries a generation time field
    12 PID_INTER Number(8) generation interval of a periodic packet in ms, used for expiry; empty for non-periodic packets
    13 PID_VALID Char(1) Y which of several records with the same key is valid
    14 PID_CHECK Number(1) 0 1 to check the Packet Error Control CRC, 0 not to
    15 PID_EVENT Char(1) N raise a SCOS-2000 event on reception: N none, I info, W warning, A alarm
    16 PID_EVID Char(17) event number; the full event ID becomes TPKT_OBE::nnnn; 1–9999 suggested

    Field definitions from ICD §3.3.2.4.1.30

    The ICD attaches rules to the PID that protect the archive. These rules matter for anyone who maintains a MIB over a long mission:31

    • The packetiser key is the first five fields. Associating several keys with one SPID is deprecated from release 5.0: each distinct packet must have its own SPID.
    • Packets identified by APID alone, without a data field header, get 0 in all other key fields.
    • Once mission telemetry is being archived, the mapping from identification fields to SPID must not change. PID entries whose SPIDs exist in the archive must not be deleted, or advanced retrieval services such as the GDDS break. The TPSD of archived packets must not change either.
    • Internally generated packets (UDC, MISC, synthetic and system control packets) should also have PID entries, with a type/subtype/APID combination that no other source uses, plus a TPCF entry for the mnemonic.

    PIC: where the extra identification fields are¶

    Many PUS packets share a type/subtype and differ only in the first field of their data. A housekeeping report TM(3,25) carries a structure ID; an event report TM(5,x) carries an event ID. The PIC tells the packetiser, for each type/subtype (and optionally APID), where the extra identification fields are. Offsets count in octets from the start of the source packet. Widths count in bits. An offset of −1 means "no such field".32

    # Field Type M / default Meaning
    1* PIC_TYPE Number(3) M service type
    2* PIC_STYPE Number(3) M service subtype
    3 PIC_PI1_OFF Number(5) M octet offset of PI1 from the start of the source packet, or −1
    4 PIC_PI1_WID Number(3) M width of PI1 in bits
    5 PIC_PI2_OFF Number(5) M octet offset of PI2, or −1
    6 PIC_PI2_WID Number(3) M width of PI2 in bits
    7* PIC_APID Number(5) 99999 APID the record applies to; empty means all APIDs

    Precedence: a record matching type/subtype/APID wins. Otherwise a record matching type/subtype applies. Otherwise PI1 and PI2 are taken as 0. The packetiser reads the PIC directly; it is not imported into the run-time database.32 The Herschel ground segment added a sanity rule: a PID entry must not carry a non-zero PI1 when the matching PIC says PI1 is not used.41

    On Solar Orbiter every telemetry packet except the standard spacecraft time packet has a data field header. The primary header is 6 octets and the data field header 10 octets, so source data starts at octet 16.42434445 This matches PID_DFHSIZE = 16 on 11,138 of the 11,150 PID records.59 The diagram shows the first 17 octets of a Solar Orbiter housekeeping report, the part the packetiser needs.

    Inference

    The positions of type and subtype inside the 10-octet data field header (octets 7 and 8 from the packet start) follow from the field order printed in SOL.S.ASTR.TN.00079 §4.2.2.1 (spares, PUS version, service type, subtype, spacecraft time), assuming the spares and the version share the first octet. The TN also defines an 8-bit destination ID in the TM data field header (§13.3), and the time field is CUC with 4 coarse and 2 fine octets. One octet each for version/spares, type, subtype and destination ID plus 6 time octets gives the 10 octets, but the order of the destination ID and the time is not stated in the text.4546 The figure with exact offsets was not available as text. The positions are a SCOS-2000 configuration item (MISCconfig), not part of the MIB.28

    The Solar Orbiter PIC shows the pattern clearly:60

    Type/subtype PI1 offset / width PI2 offset / width What PI1 is (from the packet definitions)
    (3,25), (3,26) 16 / 8 −1 1-octet SID of the housekeeping or diagnostic report48
    (5,1) to (5,4), all APIDs 16 / 16 −1 event ID

    183 of the 256 PIC records declare no extra fields at all.60

    TPCF: packet characteristics¶

    The TPCF holds one record per SPID with the packet mnemonic, shown on displays to identify where a value came from (None when missing), and TPCF_SIZE. TPCF_SIZE is not imported. It exists for missions that generate history-file configuration and should then hold the full SCOS-2000 packet size: the source packet plus the SCOS-2000 packet header of 64 octets (header versions 0 to 3) or 76 octets (version 4), or 0 for truly variable packets.33 Solar Orbiter has a TPCF record for every PID SPID. 2,325 of them have size 0 and 8,825 give a non-zero size, from 6 to 4,136 octets. 7,484 of the non-zero sizes are below 64 octets, the size of the SCOS-2000 packet header alone, so the mission does not fill this field according to the ICD guideline (it is not imported, so this has no run-time effect).5933

    Other features of the Solar Orbiter PID table:59

    • PID_TIME = Y for 11,141 records. The 9 exceptions are the 3 transfer-frame pseudo-packets and the 6 ground-station packets described below.
    • PID_DFHSIZE is 16 except for 12 records. Six have 0: the three transfer-frame pseudo-packets (APID 1, type 0) and the three MATIS packets of type 166. Six have 6, that is the primary header only: the time report SPID 9999 and five internal packets of types 160 and 161. The time report is keyed as type 9, subtype 2 on APID 0, the APID that Solar Orbiter reserves for its time packet, which has no data field header.43 The TM-TC ICD itself calls this packet "TM (9,2)" while stating that it has no data field header.46 The Database Import ICD's general rule would key a packet without data field header with type and subtype 0;31 how the Solar Orbiter packetiser reconciles the two is not stated in the available sources.
    • PID_CHECK = 1 (verify the packet error control) appears on only 6 records: the three "complete transfer frame" pseudo-packets CTFBAD, CTFIDLE, CTFGOOD (APID 1, type 0) and three MATIS packets. Every spacecraft packet has PID_CHECK = 0.

They are ground-station packets LMS_NNO, LMS_CEB and LMS_MLG, each at low and high frequency, on APIDs 2048–2065, with parameter descriptions such as "LMS_NNO WSDS1 Temp", "WSDS1 Wind Speed" and "FEC1 AZ act Pos". Their parameters are named NYN…, NYC… and NYM… rather than the reserved NNOiiii-style names.
    • Eighteen SCOS-internal and ground-generated packets share APID 1966 and use the private types 160 to 166 and 251. Examples are "Dynamic UDCs" (160,3), the MISC packet (160,5), "TC Spacon Packet" (160,6), the mini-transfer-frame packets (161,3–5), "Bad Telemetry Packets" (162,1), the time correlation packets (164,1–3), the three MATIS status packets (166,1–3) and "Saved Synthetics" (251,2). APID 1966 lies inside the range 0–2047 that the ICD assigns to spacecraft packets; the ICD only asks that internal packets use a type/subtype/APID combination that no other source produces.3031
    • 2,063 records have a TPSD. In every one of them the TPSD equals the SPID (for example 14173), and 2,063 distinct TPSDs are defined in the VPD.

    The APID itself has structure on Solar Orbiter: 7 bits of process ID and 4 bits of packet category.43 APID 178 of YCA2Z011 is binary 0001011 0010, process ID 11 and category 2 (simple arithmetic on the rule; the APID allocation itself is in Annex 8 of the TN). See the APID 178 explorer page.

    Fixed packets: the PLF¶

    The PLF describes packets whose layout is fixed, identified by SPID. A parameter can appear in many packets. Overlapping entries (two parameters from the same bits) and gaps are both allowed, but a parameter may have only one record per packet. A super-commutated parameter is therefore described by one record with a repetition count.35 All standard monitoring displays (alphanumeric, graphic, scrolling) extract values through the PLF.35

    # Field Type M / default Meaning
    1* PLF_NAME Char(8) M parameter (PCF_NAME)
    2* PLF_SPID Number(10) M packet (PID_SPID)
    3 PLF_OFFBY Number(5) M octet offset of the first occurrence, from the end of the SCOS-2000 header, which is the first octet of the source packet with the standard packetiser
    4 PLF_OFFBI Number(1) M bit (0–7) of the first bit within that octet; bit 0 is the leftmost, most significant bit
    5 PLF_NBOCC Number(4) 1 number of occurrences (1–9999); 1 for normal parameters
    6 PLF_LGOCC Number(5) 0 bits between the starts of two consecutive occurrences (0–32767)
    7 PLF_TIME Number(9) 0 time offset of the first occurrence from the packet time, in ms (±4,080,000)
    8 PLF_TDOCC Number(9) 1 time between consecutive occurrences in ms (1–4,080,000)

    Field definitions from ICD §3.3.2.5.1.35 The Herschel clarification note confirms that bit 0 is the most significant bit, and that offsets coincide with the source packet start only with the generic packetiser.40 The value length is not in the PLF: it follows from PTC/PFC.12 PLF_TIME and PLF_TDOCC time-stamp each sample. Graphic displays use them to plot super-commutated values, and scrolling displays and printouts use them to show times.35

    The ICD's housekeeping note explains why these offsets have to be static. SCOS-2000 time-stamps each sample from the packet time plus the fixed MIB offset, so the offsets must be known in advance and be the same in every instance of the packet. Likewise, the collection interval of a periodic packet is fixed in the database; SCOS-2000 does not update it when a ST[03] command changes it on board.39 New ST[03] housekeeping structures must also be defined in the MIB before the spacecraft starts sending them; ESA missions usually generate the ST[03] definition commands from the database.39

    In the Solar Orbiter MIB the PLF holds 400,792 records for 107,792 distinct parameters in 9,056 packets. 725 records are super-commutated, and 91 have a non-zero PLF_TIME.61

    Example: bit-level layout in an IMU housekeeping packet¶

    Octets 65 to 70 of YCA2Z011 (SPID 29534, TM(3,25), APID 178, SID 11) hold status bits and two 12-bit temperatures of gyro IMU11 (real PLF data).62

    Three PLF features show here. Single-bit flags are located by PLF_OFFBI alone (NMUD1104…NMUD1111 at bits 0–7 of octet 66). A 12-bit value starts in the middle of an octet (PLF_OFFBI = 4). The same bits are also exposed as whole 8- and 16-bit raw words (NMU0Z000: PTC 3, PFC 4 at octet 65; NMU0Z002: PTC 3, PFC 12 at octet 67), which is allowed because overlaps are legal.3562

    Example: super-commutation at 8 Hz¶

    YCA2Z229 (SPID 29540, TM(3,26) "AOCS OCM 8Hz Diag", APID 184, SID 229) carries 16 samples of an AOCS state block. Every block parameter has PLF_NBOCC = 16, PLF_LGOCC = 744 bits (93 octets), PLF_TIME = −1875 ms and PLF_TDOCC = 125 ms. The n-th sample (n = 0…15) of a parameter first located at octet o therefore sits at bit \(8o + 744n\) and is time-stamped \(t_{pkt} - 1875 + 125n\) ms. The last sample carries the packet time itself, and the first is 1.875 s older (real PLF data; the formula restates the ICD field definitions).6235

    The block adds up to 744 bits, exactly the PLF_LGOCC step, so consecutive samples are packed with no gap. Before the block sit the SID (NCD030C1, octet 16, 8 bits) and an enable flag (NCA3Z03A, octet 17).62 The largest repetition count in the Solar Orbiter MIB is 2,046: NIH0XCPI "Data from CPIO file", a 2-octet string repeated every 16 bits from octet 20 of SPID 56333 "SSMM XF Engineering Files".61 The ICD warns that a synthetic parameter fed by a super-commutated parameter is recomputed for every sample, which can be costly, and that saved synthetic parameters cannot be super-commutated.23

    Variable packets: the VPD¶

    Some PUS reports have no fixed layout. A repeat counter N precedes N groups, or a parameter ID decides how the following value is interpreted. The VPD describes such packets, element by element, for packets whose PID gives a TPSD. It has no relation to the PLF or the display tables.36 Each element starts where the previous one ended, shifted by VPD_OFFSET bits: a positive offset makes a gap, a negative one an overlap.36 The table must be sorted by VPD_TPSD and VPD_POS.36

    # Field Type M / default Meaning
    1* VPD_TPSD Number(10) M structure ID (PID_TPSD)
    2* VPD_POS Number(4) M ordinal position of the element
    3 VPD_NAME Char(8) M parameter (PCF_NAME)
    4 VPD_GRPSIZE Number(3) 0 for a repeat counter (or a dummy fixed-repeat element): number of following elements in the repeated group; nesting is allowed
    5 VPD_FIXREP Number(3) 0 0 no repeat; > 0 fixed number of repetitions (the counter element is then a dummy, defined in the PCF but absent from the packet); −1 repeat to end of packet (future extension)
    6 VPD_CHOICE Char(1) N Y: the value is a TPSD that defines the rest of the packet; must be the last element of its structure (choice is not supported by the VPD application)
    7 VPD_PIDREF Char(1) N Y: the value is an on-board parameter ID, looked up in PCF_PID to name a following deduced value
    8 VPD_DISDESC Char(16) column header text on displays
    9 VPD_WIDTH Number(2) M 0 hides the value; > 0 displays it in full
    10 VPD_JUSTIFY Char(1) L L, R or C justification
    11 VPD_NEWLINE Char(1) N Y starts a new line; not allowed inside repeated groups
    12 VPD_DCHAR Number(1) 0 0 value only, 1 name and value, 2 name, PCF_DESCR and value
    13 VPD_FORM Char(1) N B, O, D, H or N (normal: engineering value if a single calibration exists)
    14 VPD_OFFSET Number(6) 0 bits between the end of the previous element and this one (−32768…32767)

    Field definitions from ICD §3.3.2.5.2.36

    Limitations of variable packets

    Appendix C of the ICD states that values extracted from variable packets do not take part in full telemetry processing: no validity, no monitoring checks, no validation or verification checks and no synthetic parameter evaluation. Their parameters and time references are only known once the packet is opened. The ICD therefore advises against delivering regular housekeeping in variable packets.38 Only parameters of packets defined in the VPD are shown in the full mode of the Packets History Display.34

    Solar Orbiter defines 2,063 variable structures in 19,863 VPD rows. 711 rows are repeat counters (VPD_GRPSIZE > 0) and 1,449 rows carry parameter IDs (VPD_PIDREF = Y). No row uses VPD_FIXREP or VPD_CHOICE. 404 rows have a non-zero offset, 389 of them negative (overlaps).63

    Example: the out-of-limit list report TM(12,11)¶

    The on-board monitoring report TM(12,11) on APID 163 (SPID and TPSD 14173, "Parameters Out-of-limit List Report") is a textbook variable packet. A 2-octet counter N is followed by N repetitions of eight fields, whose value fields take their type from the monitored parameter (real VPD data).6450

    POS VPD_NAME Description PTC/PFC VPD attributes
    1 NCD0C0B1 OBCHP_Nb Mon in 12,11 3/12 (16-bit unsigned) GRPSIZE = 8: repeat the next 8 elements N times
    2 NCD0C094 OBCHP_S12_Mon_ID ¾ (8-bit)
    3 NCD0C095 OBCHP_Monitored Par ID 2/32 (32-bit enumerated) PIDREF = Y
    4 NCD0C0B4 OBCHP_S12_Bit Mask 3/14 (32-bit)
    5 NCD0C0B5 OBCHP_S12_Par value 11/0 deduced, PCF_WIDTH = 64, PCF_RELATED = NCD0C095
    6 NCD0C0B6 OBCHP_S12_Crossed Limit 11/0 deduced, width 64, related NCD0C095
    7 NCD0C0B7 OBCHP_S12_Prev Status 2/8
    8 NCD0C0C8 OBCHP_S12_Curr Status 2/8
    9 NCD0C0B9 OBCHP_S12_Trans time 9/17 (CUC, 4 + 2 octets)

    The VPD reproduces the structure printed in the Solar Orbiter TM-TC and Packet Structure ICD. The document gives the counter as 2 octets, the monitoring ID as 1, the parameter ID as 4, the mask as 4, parameter value and limit crossed as 8 octets each ("deduced"), the two statuses as 1 octet each and the transition time as 6 octets.50 The deduced value fields show how PCF_RELATED, PCF_WIDTH and VPD_PIDREF work together. NCD0C095 delivers an on-board parameter ID, which SCOS-2000 matches against PCF_PID to find the monitored parameter and its type. The following 64-bit slots are decoded with that type.1412 The same nine-element structure is reused for the TM(12,12) check transition report (TPSD 14171), with counter NCAB0021 "Nb of PMONs in TM(12,12)".64 The monitoring checks page compares these on-board reports with ground checking. The ECSS-E-ST-70-31C data model describes the same idea in neutral terms: arrays with a repetition-number format, and deduced structures selected by conditions.52
