    MIB tooling and open-source libraries¶

    The SCOS-2000 Mission Information Base (MIB) is exchanged as plain ASCII tables, but nobody maintains 100,000 parameters in a text editor. Around the interface defined by the Database Import ICD has grown a family of tools: off-line databases and editors that produce the tables, importers and ingestion programs that check and load them, translators that feed other control systems, and, more recently, open-source software: a complete mission control framework (Yamcs) that can load a MIB through a plug-in, and small libraries that read MIBs and the packets they describe. This page surveys the tools documented in this wiki's library, the open-source packages published on PyPI and GitHub, and ends with the scripts that build this site. For how these tools fit into the wider preparation of operations data, see Operations preparation.

    What the ICD expects of tools¶

    The ICD sets the division of labour. It places no constraint on how the ASCII files are produced, and expects that a relational database such as MS Access will usually be used.1 The off-line database is responsible for consistency. The SCOS-2000 importer checks only the most dangerous problems, and from release 4.0 an off-line database consistency checker is delivered with the main SCOS-2000 releases.2

    The importer's own behaviour is precise:34

    • Every field is checked against its declared type and length. A field that is too long is truncated with a warning. A mandatory field left null is set to 0 or the empty string, with a warning.
    • Relational integrity is checked. A record that refers to something missing, such as an unknown parameter, is not imported.
    • Command and sequence parameter values are checked against their format. Invalid values become 0, the empty string or 1970.001.00.00.00 for absolute times.
    • All messages go to a log file that is overwritten at each import (/home/sops1/Import.log).
    • Import options are a full import (optionally per domain) and a "check only" run that reports without changing any data. From release 5.0, sequences and displays are converted to XML files in the FARC instead (see Display definitions).

    The ICD also warns that the import default of a field is not the same thing as the default an off-line editor may propose.5 And it gives one example of logic that belongs in the off-line "TM/TC database manager", not in SCOS-2000: for housekeeping packets defined on board with PUS service 3, ESA missions typically define the packet in the database first and generate the service 3 commands from it automatically.6

    ESOC's MS-Access database editor and the HIFI evaluation¶

    In April 2000, an ESA presentation of SCOS-2000 to the FIRST/Planck projects listed the elements on offer: SCOS-2000, a router and a Tcl/Tk procedure automation tool reused from PROBA, and, as additional elements, "Database Editors" based on MS Access from INTEGRAL.7

    Requirements. HIFI wrote down what an instrument team needed from such an editor (SRON-U/HIFI-SP-2000-2, August 2000). The MIB, "a set of more than 30 ASCII files", configures SCOS-2000 and must evolve with the instrument during integration.8 The requirements group into five areas:9

    Area Requirements (summary)
    Data content All data needed to configure SCOS-2000; one table per SCOS-2000 file.
    User interface A datasheet per table with ICD field names and tip texts; complete records visible without scrolling; forms that follow the MIB structure (PCF with checks and calibrations, CPC with range sets and de-calibrations, PID with VPD and PLF, CCF with CDF, PTV and verification, CSF with its sub-tables, packet headers, parameter sets, and display layouts); pull-down menus for foreign keys.
    Data checking Unique keys enforced; update cascades so keys can be edited; no unintended delete cascades; validation rules for enumerated fields; mandatory fields enforced; ICD defaults used and never exported blank; a configurable whole-data-set checker; counters maintained or regenerated.
    Groups of data Data organised per instrument subsystem, enterable by subsystem engineers without SCOS-2000 knowledge, reportable per subsystem, and swappable when a subsystem model (QM, FM) changes.
    Tools Import, append, export and delete sets of SCOS-2000 files; an intuitive entry tool for parameter value sets.

    Its §3.4 names four groups of tables (parameter data, packet data, parameter sets and operator data), while the table of its Annex A uses five: Operator (the six display tables), Packet, Packet header, Parameter and Parameter set.910

    Evaluation. HIFI's evaluation report (SRON-U/HIFI/RP/2001-1 issue 2, April 2001) assessed version 2.0 of the "SCOS-2000 Database Editing Subsystem", which the report also calls the "Integral MS Access editor", and includes the replies of the editor's author.11 The key findings:

    Project databases: HPSDB and the satellite database¶

    For Herschel/Planck, the Operations Interface Requirements Document required a single common Satellite Database, delivered as Oracle data files with field-level change records.17 The Herschel/Planck System Database (HPSDB), documented by Alcatel Alenia Space, loaded instrument and CCS MIB files and regenerated SCOS-2000 and CCS "bridge files". Its object model, naming, default values and per-field processing rules are summarised on Mission tailoring.18 Two of its design choices show what an engineering database adds to the bare ICD. Every item carries a 64-character mnemonic, a 256-character long description and configuration data (user, date, reason, source, validation dates), none of which SCOS-2000 can import. And an 8-bit category flag per item selects which users (AIT, operations, software, flight dynamics) see it when bridge files are generated.19

    ESA's SCOS-2000 based EGSE (EMCS, user manual issue 4.0 of 2004) worked the other way round. ESA had started an Oracle-based repository for its space system model, but it was not available, so users populated mission data directly in the ASCII files. SCOS-2000 loaded them into its internal MIB database, and the mergeDATA and setSCOSdata facilities merged data sets and switched between them.2021

    Ingestion into a science ground segment: HCSS¶

    The Herschel Common Science System read MIBs with its own ingestion software, whose interface and checks are defined by the HCSS MIB Clarification and Tailoring Note.22 In practice (SPIRE, 2007), ingestmib reads the directory named by the property hcss.mib.datadir, runs semantic checks, writes mibchecker.log, and stores the MIB definitions in a Versant object database under a user label. Afterwards cusgui loads the labelled MIB for the Common Uplink System.23 The checks it performs are listed on Mission tailoring.

    SRDB Translator: from SCOS-2000 to ECHO¶

    An undated paper by Intecs and Thales Alenia Space Italia describes the SRDB Translator, which imports a Satellite Reference Database (SRDB) in SCOS-2000 MIB form into ECHO, the TAS-I central checkout (EGSE) system. The motivation is that SCOS-2000 had become the standard for ESA mission control and often for EGSE, so the SRDB is "almost always" based on the SCOS-2000 run-time database, while unit tests and AIV at TAS-I used ECHO and its own database.24 The paper carries no date. Its most recent reference is ICD issue 6.1 of February 2006,37 and the copy in the library is hosted on the same ESA Indico event (number 109) as the Terma paper cited below, which is headed "SESP 2010".38

    Analysis. The two databases cover similar entities (parameters, calibrations, checks, packets, commands, verification), both built on PUS, but a one-to-one table mapping is "almost inapplicable". For every item the authors distinguish data present in both, data present only in the SRDB (adopted by extending ECHO, or ignored) and data that only ECHO needs (supplied separately).25 Two of their conversion tables:26

    Topic SCOS-2000 ECHO Rule
    Verification checks vs telecommands separate entities with a mapping table checks as a detail table of each TC duplicated for every linked TC
    Verification stage any stage of the execution profile not applicable stage not imported
    Verification window start time and interval in s maximum time from TC emission in ms (start + interval) × 1000
    Expected value raw or engineering engineering only raw checks discarded
    Numerical curve identifier Char(10) integer 1–9999 mapping algorithm; original name kept in the description
    Radix of raw values decimal, octal, hex decimal only converted
    Points per curve unlimited 2 to 1,000 others not imported or truncated
    Polynomial curve boundaries not held mandatory ECHO relaxed
    Logarithmic curves supported not handled ECHO extended
    Curves per parameter unlimited 4 extended to 99

    Implementation. The translator is a utility of the ECHO Database Manager (MTGP) on MS SQL Server, compliant with SCOS-2000 ICD issue 6.1. In a first step it loads the SCOS-2000 tables unchanged into dedicated tables. In a second step stored procedures transform them into ECHO tables, either directly or as a file for later import, and it can merge the result with EGSE-local objects. A log lists the outcome per object.27

    Use and limits. It was first built for Galileo GIOVE-B (an SRDB delivered as a single MS Access 2000 file), extended for Sentinel-1, and used for BepiColombo on-board computer and SSMM databases of about 10,000 records each.28 Because the first step expects exactly the columns of its ICD issue, BepiColombo databases made to an earlier ICD issue had to be adjusted to add the missing columns before import, and every project's customisations require new analysis. The authors call for a standard XML-based exchange language.2930 CCSDS defines such a language, XTCE; the paper does not mention it.

    Terma CCS5, SCS5 and TSC¶

    Terma's checkout and control products read SCOS-2000 MIBs natively. A 2010 paper explains the choice: building a new monitoring and control system from scratch was attractive only if users kept their test language and database interfaces. The MIB interface, it says, "while not perfectly normalized, and not always perfectly designed, is nevertheless well known, relatively well described, and well understood".31

    The 2024 presentation and the data sheet list the MIB-related features:3234

    • the SCOS-2000 MIB data model "6.9+…7.2" (data sheet: "ICD 6.9 extended"), with unlimited field lengths;
    • variable packets and parameters supported globally, deduced parameters in TM and TC, configurable length fields, both endianities, VPD_CHOICE and dynamic housekeeping definitions;
    • different synthetic (derived parameter) languages;
    • dropping and loading several databases without restart, with a clean separation of data from different suppliers (platform, payloads, instruments, EGSE), and an online MIB browser with search, filter and patch features;33
    • all tables accessible from the TOPE procedure language; TC sequence tables not supported (TOPE or command stack files are used instead).

    Dynamic housekeeping definitions (DYNHK)¶

    The "dynamic housekeeping definitions" in that list are described in a Terma B.V. paper by P. Kazmirchuk, "Managing Telemetry Definitions on the Fly". The paper shows what a checkout system can do with a MIB at run time.46 An on-board data pool can hold tens or even hundreds of thousands of parameters. During integration, engineers use telecommands of PUS service 3 to make the on-board computer generate new housekeeping or diagnostic packets that no one defined in advance. A central checkout system (CCS) identifies packets only through its reference database, so without help these packets arrive as unknown. Until then, engineers had to write static TM definitions by hand.47 DYNHK closes that gap. It watches the uplinked service 3 requests and writes the matching MIB rows itself.

    What CCS5 provides. CCS5 uses the MIB as its reference-database format and TOPE, a Tcl-based language, for automated procedures. The paper says both are backward compatible with SCOS-2000. When a test session starts, CCS5 loads the MIB tables into memory. TOPE can then read every table and write some tables and columns. CCS5 can also merge several MIBs, for example from different equipment suppliers, and adds a field "Source" that records which MIB each row came from.49

    The PUS requests it reads. The paper uses the PUS-A names (its reference is ECSS-E-70-41A): TC(3,1) and TC(3,2) define a new housekeeping or diagnostic report, TC(3,3) and TC(3,4) clear definitions, TC(3,5) enables generation, and TM(3,25) and TM(3,26) are the reports. PUS-C keeps these subtype numbers, under names such as "create a housekeeping parameter report structure" for TC[3,1].100 The application data of TC(3,1) and TC(3,2) carries the structure identifier (SID), a collection interval in units of the default housekeeping scheduling rate, and the list of on-board parameter IDs with their counters. The SID, together with the APID and the subtype, identifies a TM packet definition uniquely. The requests therefore carry enough information to build the definition.48

    The component is a TOPE script running on the CCS server console. Its authors had to change the core C++ modules so that TM packets can be defined without disturbing ongoing monitoring and control, generate MIB rows from PUS request parameters, and distribute the new definitions to all workstations in time.49 A redefinition of a SID that already exists disables the old definition, adds one with a new SPID and logs a message. As a result, SPID and TPSD values are never reused within a session.50

    Mapping to the MIB tables. CCS5 identifies TM packets in the same steps as SCOS-2000: APID, then service type and subtype, then the PIC entry that locates the extra identification fields PI1 and PI2, then the PID entry that yields the SPID, and finally the PLF and/or VPD rows that list the parameters.52 (See Monitoring in the MIB for the full procedure.) DYNHK writes VPD rather than PLF rows. The service 3 request lists parameter IDs but no offsets, and VPD normally packs parameters back to back, which matches the request. VPD also allows variable-length strings, and CCS5 archives every VPD sample of a packet, so retrieval does not depend on when the packet was (re)defined.52

    PID field Value written by DynHkMonitor
    PID_TYPE 3
    PID_STYPE 25 (housekeeping) or 26 (diagnostic)
    PID_APID from a configured mapping of TC APID to TM APID
    PID_PI1_VAL, PID_PI2_VAL derived from the SID, as the PIC entry dictates
    PID_SPID allocated from a configurable offset clear of the static definitions, incremented for each new request
    PID_DESCR generated text, for example "Dyn HK" followed by the SID
    PID_TPSD equal to the SPID
    PID_DFHSIZE derived from PIC: the start reference for variable parameters
    PID_TIME Y (on-board time assumed in the packet header)
    PID_INTER computed from the collection interval
    PID_CHECK 1 (packet error control assumed present)
    other fields blank, so the ICD defaults apply
    PID_VALID set to false when TC(3,3) or TC(3,4) clears the SID

    Fields from the paper's "PID Table" section.54

    In the simple case every parameter is sampled once. Each one gets a VPD row with VPD_TPSD = PID_TPSD, VPD_POS = 1 to NPAR, and VPD_NAME = the PCF name whose PCF_PID equals the on-board parameter ID in the request. When the request's NFA indicator is 1, super-commutated parameters follow. DYNHK then adds a group-repeater row with VPD_NAME "REPEATER", VPD_GRPSIZE = NPAR2 (parameters in the group) and VPD_FIXREP = NREP (samples).55

    Three gaps between the PUS request and the MIB need configuration. The collection interval comes in scheduling-rate units, but CCS5 needs milliseconds to expire stale parameters, so a setting schedulingRate supplies the conversion. The TM APID cannot be derived from the TC APID, so a mapping is configured. And because the MIB ICD does not refer to the SID directly, PIC rows for the new packets must exist beforehand. CCS5 uses them to split the SID into PI1 and PI2 (or use it as PI1 alone) and to compute PID_DFHSIZE.5253

    Persistence. The added rows live only in memory and are lost when the MIB is reloaded. They carry the Source value "DYNHK", so they can be saved as separate MIB files and merged into the next session. Whether that is wise depends on whether the on-board software keeps its dynamic definitions over a reboot, for example in EEPROM, so both saving and reloading are optional.51 The paper ends by noting that PUS-C (2016) has standardised many service 3 subservices that the implementation then handled under mission-specific numbers.56

    Inference: date of the paper

    The paper carries no date. It calls ECSS-E-ST-70-41C (2016) "published last year" and cites ICD issue 6.9 (2010), which suggests 2017. It is hosted on ESA Indico event 180, which also hosts a paper by F. Trifin and A. Walsh whose header names the Workshop on Simulation and EGSE for Space Programmes (SESP), 28–30 March 2017, at ESA-ESTEC.565758 That the Kazmirchuk paper was presented at SESP 2017 is this wiki's inference from the shared event; the paper itself does not say so.

    The Solar Orbiter MIB for comparison. The public 2025 Solar Orbiter MIB takes the static route that DYNHK is meant to complement. It defines 288 TM(3,25) and 89 TM(3,26) packets on 76 APIDs. All 377 are fixed packets (PID_TPSD = −1, so their parameters are located through PLF), with PID_DFHSIZE 16, PID_TIME Y and PID_CHECK 0. Their PIC entries place PI1, the SID, at octet 16 with a width of 8 bits. On the command side the MIB holds 82 TC(3,1) and 77 TC(3,2) definitions. Thirteen are generic commands whose SID is an editable element: twelve "Define New … Parameter Report" commands, six per subtype, and the instrument command ZIT00301 "Def New HK Par. Rep.". The other 146 are predefined report definitions such as "Define HK: AOCS Dynamics FAST", each with a fixed SID that equals the PI1 value of a TM(3,25) or TM(3,26) packet already in PID. Example: command ZCA2Z05B (APID 188) fixes SID 77, and SPID 29530 "AOCS Dynamics FAST" is TM(3,25) with PI1 = 77 on APID 180.64

    Inference

    A DYNHK-style tool on this MIB would need its SPID offset above the existing range (the PID table's SPIDs run from 101 to 1,000,006) and could reuse the existing PIC rows for (3,25) and (3,26). In ICD terms, PID_CHECK 0 means that the packetiser does not check the packet error control field, either because the packet has none or because the check is disabled. The paper's choice of 1 enables the CRC check. Which of the two applies to Solar Orbiter housekeeping packets is not stated in the available sources.59

    Yamcs and the yamcs-scos2k MIB loader¶

    Yamcs is an open-source mission control framework. Its server manual (release 5.14.1-SNAPSHOT, copyright 2026) is published by Space Applications Services NV/SA, Belgium, with Aerospace Applications North America in Houston.69 GitHub shows the yamcs/yamcs repository under the AGPL-3.0 licence.92 Yamcs follows a traditional monitoring and control model. Parameters arrive in groups, usually binary packets, and are checked against limits that can depend on context. Commands consist of a name and arguments, are gated by transmission constraints and significance, and pass through verification stages.70 The server is a single Java process. Data links connect to the target system, preprocessors and postprocessors handle packet details that the database does not describe (such as checksums), and processors apply the Mission Database (MDB) to turn packets into parameters and commands into packets.71

    The Mission Database and its loaders¶

    The MDB uses terminology "very close" to XTCE: space systems, containers, parameters, commands and algorithms, with space systems named by UNIX-like paths such as /BogusSAT/SC001.72 Yamcs builds the MDB at start-up from a configurable loader tree in the instance configuration. Each loader fills one space system and can have sub-loaders for its children, and loaders of different types can be mixed as long as their content maps onto Yamcs' internal, XTCE-based model. The result is cached on disk.76 The manual documents three built-in loaders:747576

    Loader type Input Notes
    xtce XTCE XML file(s) (file or fileset) tolerant reader: unknown tags ignored, and it "strives to be backward compatible" with XTCE 1.0 and 1.1; the unsupported XTCE features are listed on the XTCE page
    sheet Excel 97-2003 .xls workbook (.xlsx not supported) sheets General, ChangeLog, DataTypes, Parameters, DerivedParameters, LocalParameters, Containers, Algorithms, Alarms, Commands, CommandOptions, CommandVerification and Calibration; format versions 5.3 to 7.1
    emptyNode none creates an empty space-system node to hang sub-loaders on

    Two details matter for anyone coming from the MIB. First, in Yamcs a calibrator works in opposite directions for the two kinds of type: raw to engineering for parameters, engineering to raw for arguments. A parameter's calibration cannot simply be reused for a command argument, just as the MIB keeps CAF and CCA separate.73 Second, the MDB is normally read-only. Since version 5.8.8, sub-trees can be declared writable, so that parameters and parameter types can be added at run time and persisted in XTCE form.72 A note at the end of the same chapter still says that Yamcs "does not persist TM/TC definitions" and has no import function. The manual does not reconcile the two statements.76

    Inference: the variable-length options

    Two sources explain the two vblParamLengthBytes options. The ICD says that from SCOS-2000 R4.0 the PUS length field in front of variable-length octet and character strings in commands can be switched on or off by configuration.62 The Yamcs manual says that for command arguments only it accepts a length tag of 0 bits, which XTCE forbids, "for compatibility with other systems (e.g. SCOS-2k)".77 SCOS-2000 itself does not decode variable-length strings in telemetry,62 so the TM option serves packets that SCOS-2000 would need special processing for. A default of 0 bytes in the loader therefore matches a SCOS-2000 configuration without the length prefix. The example values 7 and 8 for the type and subtype offsets match the PUS TM layout: a 6-octet primary header followed by one secondary-header octet before the service type.

    SCOSpy¶

    SCOSpy decodes the SCOS-2000 packet header, the internal header that SCOS-2000 puts in front of each stored TM or TC packet in its archive (see Mission archives), not the CCSDS header. From a hexadecimal string, SCOS(packet) returns the common packet header, a TM or TC packet header and the data. According to the README:40

    • Common header fields include CTree, AccessF, SimFlag, FilingTime, CreationTime, CreateID, SCID, GSID, PSize, PType, Version, FilingFlag, DistFlag, TSPolicy, TQ, StreamID, SeqCounter, SPID and MissionID.
    • TM packet header fields: TPSD, RouteID, PUSAPID, PUSSSC, PUSService, PUSSubService.
    • TC packet header fields include UplinkTime, ExecTime, LUTime, RequestID, the PUS APID, sequence count, service, subservice and acknowledgement flags, and source host and type.
    • The event packet header is not implemented. Only packet types 1 (TM) and 2 (TC) are supported.
    • Lookup tables are built in for BepiColombo (mission ID 816, spacecraft IDs 816 and 817). The README shows how to add JUICE (ID 844) by extending two dictionaries.

    The presence of SPID and TPSD in the TM header is what ties archived packets to the MIB: they are the processing keys from the PID table (see Monitoring in the MIB).

    mib-generator¶

    mib-generator builds SCOS-2000 MIB databases from C header files. Its README describes "basic abilities" for parsing C syntax, interpreting declarations that follow an expected structure of TM and TC packets, and creating the corresponding MIB. It names neither a mission nor the tables it writes, and refers to separate online documentation.40 That documentation ("MIB Generator, Release 0.1", Josef Vácha, 15 September 2023) fills in the detail. It describes the tool as a set of Python scripts, run mainly from the terminal as mib-gen (with a PySide6 GUI, mib-gen-gui), that assumes one specific formatting of the input C files, and as "under active development".8284

    Inputs. Four C files are expected:83

    File Expected content
    TM .h structure of the TM packets, their entries and calibrations
    TM .c the list of TM packet types: an apidNum array mapping APID names to numbers, and a tmProperties array giving each packet type its APID, service type and subtype
    TC .h structure of the commands and of the TC packet headers, decalibrations and verifications
    TcTm .h definitions shared by TM and TC, such as common identifier structures and enums

    Annotations. The generator evaluates #define macros and enum constants into one dictionary, then reads C comments of the form /*{ … }*/ as json5 dictionaries. A comment in front of a struct declares a packet: pack_type links it to the type, subtype and APID in the .c file, spid and text_id give its SPID and MIB name, and base_par_index with prefix names its parameters. In the documentation's example, prefix "LWT" and base index 59200 give the third entry the name LWT59202. Comments on the fields mark the SID (sid, with const_value), the SCOS type (type, for example CUCTIME4_3), a variable-packet role (vpd: fixed, count or data) and a calibration (cal). Bit-field widths such as uint8_t compression:5 are honoured, and nested structs are expanded in place.85 Calibrations are declared in comments keyed mcf (polynomial coefficients), lgf (logarithmic), text_cal or an annotated enum (textual) and num_cal (point pairs). Commands use service and sub, cdf: count|data for repeated groups, min/max for range checks, default, const_value for fixed areas, enum for a decalibration, and cvs for verification stages. Stages are declared in stand-alone comments (cvs_def, cvs_type, cvs_interval, default), and the sample code notes that CVS_SOURCE is always R (report-based) and the start time 0.86

    Outputs. The construction classes documented in the API chapters produce rows for 25 tables:87

    Object MIB tables
    TM packet pid, pic, tpcf, pcf, plf, cur, vpd
    TC header tcp, pcpc, pcdf
    TC command ccf, cpc, cdf, prf, prv, cvp
    Calibrations caf/cap, mcf, lgf, txf/txp
    Decalibrations paf/pas
    Verifications cvs

    Before saving the tables as .dat files, the generation package checks every value against the type, length, uniqueness and mandatory flags recorded per column in its longdata module. Repeated rows in unique columns are deleted with a warning. One further check, mnemon_check, enforces unique, non-empty mnemonics in description fields, following "additional mib specifications by OHB Italia", the only user organisation the documentation names.89 A dedicated filter reduces the packet list to one PIC row per type and subtype, and warns when packets of the same type and subtype declare their identification fields at different positions.90 This is the constraint that the ICD itself places on PIC: all packets of one type and subtype must carry their extra identification fields at the same position and with the same length.60 Two simplifications are documented: only one calibration per parameter (through PCF_CURTX, not several CUR rows), and fixed repetitions in VPD, which need a counter, get an extra "virtual" PCF entry that no packet contains.88 Optionally, a .docx document lists the entries of every TM and TC packet in a layout that follows a usual ICD.89

    Inference

    Generating the MIB from the on-board software's own C structures is the reverse of the "database first" approach that the ICD describes for ESA missions,6 and suits small projects whose flight software is the single source of truth. The documented table set has no monitoring checks (ocf/ocp), no version record (vdf), no sequences and no displays, so those would have to come from elsewhere. The documentation states no ICD issue.

    tools/srcgrep.py Lists the source registry and searches the extracted text of each library document, printing PDF page indexes (counted from the form feeds of pdftotext) for citations.
    tools/check_page.py Lints a wiki page: front matter keys, registered source slugs, relative links to planned or known pages, footnote definitions, bit-field JSON, balanced code fences and length.
    tools/build_explorer.py Reads a directory of MIB ASCII tables (plus the synthetic folder and the extra Solar Orbiter tables) and writes the JSON data of the MIB explorer: indexes of parameters, packets, commands, sequences and calibrations, detail records bucketed by an FNV hash, verification stages, and optionally a diff against an older release.
    tools/mib_columns.json Column order for all 53 tables: 36 in pyscos2000 order with ICD 7.0 names, 17 from the ICD 7.0 text, plus the list of name differences above.
    tools/pyscos2000_schema_icd72.json The introspected pyscos2000 schema.
    tools/build_pages.py Generates the data-driven pages: the library pages, the reference catalogue, the MIB table reference pages, the sources-and-copies page, the glossary and its abbreviation tooltips, and the field descriptions used by the explorer.
    tools/build_nav.py Writes the explicit navigation into mkdocs.yml, taking page titles from the front matter.
    tools/plan.json The page plan of the wiki.

    The read-only SQLite copies of the Solar Orbiter MIBs used for every query on these pages name each table after its .dat file. They use the pyscos2000 column names where available and COL1…COLn in file order for the other tables, and hold the synthetic definitions in a table synthetic(NAME, SOURCE).45 The script that produced the SQLite files is not among the repository's tools.

    Choosing a tool¶

    Need Tool in the sources
    Edit a mission MIB with forms and referential integrity an off-line relational database or editor (ESOC's MS-Access editor in the 2000s; mission databases such as HPSDB)
    Check a MIB before import the SCOS-2000 importer's "check only" option and the off-line consistency checker; in Python, pyscos2000's checkers
    Load a MIB into a non-SCOS checkout system the SRDB Translator (ECHO), Terma CCS5/TSC
    Recognise housekeeping packets defined on board during a test Terma CCS5 DYNHK
    Run an open-source control system on a MIB Yamcs with the yamcs-scos2k loader (no delta, event or status-consistency checks, no command stacks)
    Read a MIB in Python pyscos2000 (ICD 7.2 schemas); SpacePyLibrary (nine tables, ICD 6.9)
    Decode PUS packets with a MIB scospus
    Decode archived SCOS-2000 packet headers SCOSpy
    Create a MIB from flight-software C headers mib-generator
    Parse EDDS XML deliveries edds_process
    Decode CCSDS packets from an XTCE file Yamcs, OpenC3 COSMOS, Space Packet Parser
    Decode or build CCSDS/PUS packets described in code CCSDSPy, spacepackets
    Browse the public Solar Orbiter MIB this site's MIB explorer
