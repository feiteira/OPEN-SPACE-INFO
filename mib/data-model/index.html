    MIB data model: how the tables relate¶

    The MIB is a relational database spread over 53 tab-separated files. No file declares its relationships. Instead, the Database Import ICD says, in the description of each field, which field of which other table its value must match. This page collects those statements into one model. It lists the key of every table, draws the references as entity-relationship diagrams for each area (monitoring, packets, displays, commanding, verification and sequences, parameter sets), walks the main join paths with real records from the Solar Orbiter MIB, and reports how well that MIB respects the model.

    Appendix B of the ICD contains six relationship figures: monitoring, display, command, command sequence, parameter set, and command and sequence parameter tables.1 In the 7.0 PDF they are images only. The extracted text of issue 5.1 still carries the field labels of the same figures.2 The diagrams on this page are therefore rebuilt from the field definitions of issue 7.0, cross-checked against the 5.1 figure labels, and then tested against the data.

    Modelling principles¶

    Normalised tables. All tables are normalised: each field holds a single item, never a variable-length list. Many-to-many relationships are resolved through mapping tables.3 For example, a parameter can appear in many packets and a packet holds many parameters, so plf sits between pcf and pid. Likewise, cvp sits between commands and verification stages, and psm between commands or sequences and parameter sets.45

    Keys. In the ICD's field tables, an asterisk after the field number (1*) marks a key field. A table may contain only one record for each combination of key values.6 The key is therefore the natural primary key of the file. Key fields are always mandatory.7

    Names and identifiers. References use the referenced item's name (an alphanumeric ID, typically up to 8 characters) or identifier (a number).8 There are no surrogate keys. Renaming a parameter in the off-line database means rewriting every row that mentions it.

    Integrity at import. The importer checks relational integrity. A record that refers to something missing, such as an unknown parameter, is not imported and a warning is logged.9 A reference error does not stop the import. The offending row is simply missing from the run-time database, and only the import log records why.

    Cardinality as stated by the ICD. The overview sections spell out the cardinalities of the main relationships:45

    Relationship Cardinality stated in the ICD
    Parameter → validity parameter (PCF_VALID) many-to-1. One validity parameter can serve many parameters.
    Parameter ↔ calibrations via cur many-to-many
    Parameter → numerical curve (caf) / textual calibration (txf) many-to-1. Curves are shareable. Each has 1 or more points.
    Parameter → monitoring check set (ocf) 1-to-1. One set holds up to 16 checks.
    Check → applicability parameter (OCP_RLCHK) Each check may reference 1 parameter. One parameter can serve many checks.
    Parameter ↔ TM packets via plf / vpd many-to-many
    Parameter ↔ groups (grpa), parameter ↔ displays (dpc, gpc, spc) many-to-many, possibly with repetitions
    Command → PTV expressions (ptv) 1-to-many. Expressions are ANDed and not shared between commands.
    Command ↔ verification stages via cvp many-to-many. Each stage has 1 or more ANDed cve expressions.
    Command ↔ parameter sets via psm many-to-many
    Command ↔ command parameters via cdf many-to-many. cdf gives each parameter's position.
    Command parameter → cca / paf / prf many-to-1. Each is shareable and has 1 or more points or entries.
    Sequence → elements (css) → element parameters (sdf) 1-to-many, and 1-to-many
    Sequence → formal parameters (csp) 1-to-many
    Packet header (tcp) ↔ header parameters (pcpc) via pcdf many-to-many
    Packet header (tcp) → commands (ccf) 1-to-many. Each command references exactly one header.

    Raw and engineering columns in cap and ccs

    In the monitoring curve table cap, CAP_XVALS holds the raw value. In the command curve table ccs the columns are swapped: the ICD remarks that the engineering values are in CCS_XVALS, and CCS_YVALS holds the raw value.15 Both tables are therefore keyed on the raw value (CAP_XVALS, CCS_YVALS). The Solar Orbiter data agrees: in curve CAHP0000TC the CCS_XVALS are reals such as −0.5 and the CCS_YVALS are integers such as −1024, matching CCA_ENGFMT = R and CCA_RAWFMT = I.66 Command curves must also map raw and engineering values one to one, because they are used in both directions.16

    Validity and related parameters. PCF_VALID names a parameter whose raw value is compared with PCF_VALPAR to decide whether this parameter is valid. The validity parameter must be an integer parameter that the TM model processes, and circular validity chains are forbidden.26 PCF_RELATED has two uses. For a saved synthetic parameter it names the synthetic parameter whose value is stored. For a parameter of type deduced (PTC 11) it names the parameter that carries the on-board parameter ID used to interpret it.27

    Calibration. A parameter has either one calibration or several.2829

    • One calibration: PCF_CURTX holds its name. The target table depends on PCF_CATEG. With category S (status) the name must be a TXF_NUMBR. With category N (numerical) it must be a CAF_NUMBR, an MCF_IDENT or an LGF_IDENT. The field carries no indication of which of the three it is.
    • Several calibrations: PCF_CURTX stays empty and cur lists the candidates. For each parameter, the cur rows are evaluated in increasing CUR_POS. The first whose applicability expression CUR_RLCHK = CUR_VALPAR holds selects the calibration named in CUR_SELECT.

    PCF_CURTX must be empty for text parameters, for string and time parameters (PTC 7, 8, 9 and 10), and for every parameter that appears in cur.28 The calibration tables themselves are described on Calibration in the MIB.

    Monitoring checks. ocf holds one record per checked parameter, keyed by the parameter's own name. It contains the number of checks and whether limits are expressed in raw or engineering form. ocp holds the individual checks, up to 16 per parameter. Each check may carry an applicability expression OCP_RLCHK = OCP_VALPAR. That expression is ignored for status-consistency checks (OCP_TYPE = C).430 See Monitoring checks.

    Two numbers identify every SCOS-2000 TM packet:3132

    • the SPID (SCOS-2000 Packet ID), which keys the fixed layout in plf and the characteristics in tpcf;
    • the TPSD (Telemetry Packet Structure Definition), which keys the variable layout in vpd. It is −1 for packets that have no variable definition.

    Identification. The packetiser recognises an incoming source packet in three steps:3118

    1. It reads the APID, type and subtype at fixed, MISCconfig-defined positions.
    2. It looks up pic, first for the type/subtype/APID combination and then for the type/subtype alone. The APID-specific lookup exists from issue 6.5, through PIC_APID.19 The pic record says where up to two further identification fields (PI1, PI2) sit and how wide they are.
    3. It looks up pid with APID, type, subtype, PI1 and PI2 to obtain the SPID and TPSD.

    The pic→pid relationship is therefore a lookup rule, not a stored foreign key. A packet type with no pic entry is looked up with PI1 = PI2 = 0.3318

    Layout. plf places a parameter at PLF_OFFBY bytes plus PLF_OFFBI bits. For the SCOS-2000 packetiser, the reference is the start of the source packet header.3435 vpd lists the parameters of a variable structure in VPD_POS order, with repeat counters (VPD_GRPSIZE, VPD_FIXREP) and parameter-ID fields (VPD_PIDREF).36 The data model allows a packet to be both fixed and variable.31 In the Solar Orbiter release none is (see integrity).

    Groups. grp defines a named group of type PA (parameters) or PK (packets). grpa and grpk list the members. Groups exist so that their members can be enabled or inhibited together.37

    A command definition is built in three layers:544

    1. The packet header. CCF_PKTID selects a header layout in tcp, whose elements are listed bit by bit in pcdf. Each element is either a fixed area (F, with a value in PCDF_VALUE) or a named header parameter from pcpc. A named parameter takes its value from the command (A APID, T type, S subtype, K acknowledgement flags) or from the command subsystem (P, for example packet length and sequence count).45
    2. The application data field. cdf lists the command's elements in bit order. Each element is a fixed area (A), an editable parameter (E) or a fixed, non-editable parameter (F), and parameter elements name a cpc parameter. Only editable parameters can be given values in sequences (sdf). Elements are encoded with no gaps, so padding must be defined explicitly.46
    3. The parameter definitions. cpc gives each parameter's type (PTC/PFC; see parameter types), display format, and optional references. A numerical (de-)calibration goes to cca/ccs, a textual one to paf/pas, and a range check to prf/prv. CPC_CATEG decides which references are allowed. C requires CPC_CCAREF. T requires CPC_PAFREF. A, P and N forbid both.49

    ptv attaches static pre-transmission validation expressions (parameter = value) to a command. These are ANDed and never shared.5 CDF_TMID names a monitoring parameter whose current value becomes a dynamic default. The PTC/PFC of that parameter must equal those of the command parameter.50 dst (optional, mainly for EGSE) maps an APID to a routing string such as NCTRS or EGSE.TC.0x8800. APIDs not listed go to NCTRS.51 The single Solar Orbiter dst record routes APID 1372 to EGSE.TC.0x8800.66 More on these tables: Commanding in the MIB.

    TC packet headers: tcp, pcpc, pcdf¶

    The real Solar Orbiter header layout NOM_TC ("NOM_DH_TC_Packet_Header") is used by 5,318 of the 5,454 commands. Its 13 pcdf records describe this 80-bit structure. The values and bit positions below are real, taken from the pcdf table:66

    The field names above are the PCDF_DESC texts, and the codes are the PCDF_TYPE values. The first seven fields (bits 0 to 47) follow the CCSDS Space Packet primary header. The last six (bits 48 to 79) form the PUS TC data field header (see PUS packet structures). The other three Solar Orbiter headers are HPC1_TC (125 commands, 7 pcdf records covering only the 48-bit primary header), NOS2KHDR ("NIS Throw Events", 6 commands) and NO_HDR ("TCP Header for CF/CS", 5 commands). The last two have no pcdf records at all.66

    The "Source ID" element changed between releases. In the 2020 release it was a fixed area (F, value 0) with no header parameter. In 2025 it has type O and the new header parameter DFH_SRC ("Source ID") in pcpc.6625

    Inference

    ICD 7.0 lists the PCDF_TYPE values F, A, T, S, K and P.45 The O used for "Source ID" is not among them. It is presumably a Solar Orbiter or newer SCOS-2000 extension, for example a value supplied by the ground. How SCOS-2000 populates it is not stated in the available sources.

    Verification. A verification stage (cvs) is defined once and shared. It has a stage type, which is acceptance A, start S, progress 0–9 or completion C. It also has a source: report-based R (PUS service 1 reports) or parameter-based V, plus a time window.52 cvp links stages to commands (CVP_TYPE = C). The option S for sequences is defined, but the ICD states that SCOS-2000 supports verification for commands only, and a command may have at most one stage of each CVS_TYPE. cve holds the parameter/value expressions of parameter-based stages only.5354 An expression with CVE_INTER = C is an echo check. In that case CVE_VAL names a command parameter (CDF_PNAME), not a value.55 See Command verification.

    Sequences. A sequence (csf) holds numbered elements (css) without gaps. Each element is a command (CSS_TYPE = C, a ccf name) or a nested sequence (S, a csf name). Comments (T) and formal-parameter elements (F, P) are defined in the ICD but marked as unsupported or future.56 The CSS_ELEMID description still says that a command element must not contain group repeaters, while the cdf section allows them from R4.2 when all repeated values are fixed in the database.5646 Solar Orbiter uses this: 2,467 command elements (234 distinct commands) contain a group repeater.66 Each element's parameter values are in sdf. A row there is keyed to the element by sequence name and entry number. For a command element, SDF_POS is the parameter's bit offset (CDF_BIT). For a nested sequence, it is the formal parameter number (CSP_FPNUM). With group repeaters, SDF_POS is the offset after expansion and SDF_REPPOS gives the original CDF_BIT.57 csp declares the sequence's formal parameters. An sdf value can refer to one of them (SDF_VTYPE = F). See Command sequences and parameter sets.

    A parameter set (pst) is a named collection of command or sequence parameters. A parameter value set (psv) is a named combination of values for those parameters, and its values are in pvs. psm attaches sets to commands and sequences. A command or sequence may name a default value set (CCF_DEFSET, CSF_DEFSET), and a sequence element may take its values from a set (SDF_VALSET).585960 The membership table cps is not used by SCOS-2000.61 In cps and pvs, the parameter is identified the same way as in sdf. That is CDF_PNAME plus CDF_BIT for commands, or CSP_FPNAME plus CSP_FPNUM for sequences.6162 Solar Orbiter defines no parameter sets: all five tables are empty.66

    Polymorphic references¶

    Several fields point to one of several tables, and a type flag in the same or another record tells which. A generic schema tool cannot enforce these references. They are also the usual source of import warnings:

    • PCF_CURTX and CUR_SELECT share one namespace across caf, mcf, lgf and txf, disambiguated by PCF_CATEG (and, for N, by whichever table actually contains the name).2829 In 2001 the HIFI editor evaluation reported the rule then used, with numeric IDs: check caf first, then mcf, and keep the two number ranges disjoint.65
    • CVP_TASK and PSM_NAME hold a command or a sequence name, with CVP_TYPE or PSM_TYPE saying which.5363
    • CSS_ELEMID holds a command, a sequence or a formal parameter, according to CSS_TYPE.56
    • SDF_POS/SDF_PNAME, CPS_PAR/CPS_BIT and PVS_PNAME/PVS_BIT hold a command parameter (name plus bit offset) or a sequence formal parameter (name plus number).576162
    • CPC_DEFVAL and CSP_DEFVAL normally hold a value. For "Command ID" parameters (CATEG = A) they hold a command name, and for "Parameter ID" parameters (P) a parameter name.64
    • CVE_VAL normally holds a value, but a command parameter name when CVE_INTER = C.55

    Walking the main join paths with real data¶

    The examples below come from the 2025-09-16 Solar Orbiter MIB. The names link to the MIB explorer.66

    Packet → PID → PLF → PCF → calibration¶

    The housekeeping packet TM(3,25) - SID 103 - Analog HK VLDA arrives with APID 1092, type 3 and subtype 25.

    1. pic for type 3 / subtype 25 (no APID given) says that PI1 is 8 bits wide at byte offset 16. There is no PI2 (offset −1).
    2. pid for (3, 25, 1092, PI1 = 103, PI2 = 0) gives SPID 59203, TPSD −1 (fixed layout) and PID_DFHSIZE = 16. The ICD declares PID_DFHSIZE irrelevant for fixed packets.20
    3. tpcf for SPID 59203 gives the mnemonic YIT59203 and TPCF_SIZE = 39. That size field is not imported and serves only mission-specific tools.47
    4. plf for SPID 59203 places 12 parameters, at byte offsets 16, 17, 19, …, 37. All are 16-bit unsigned integers (PTC 3, PFC 12), except the 8-bit SID field at offset 16.
    5. pcf for NIT0E028 ("V_Pix") gives category N and PCF_CURTX = CIT01053TM. The parameter NIT83001 ("HK_SID", PTC 2 PFC 8) is category S with PCF_CURTX = CITT1120TM.
    6. Calibration. CIT01053TM is not in caf. It is in mcf (poly/CIT01053TM, "Vpix_Abs_Bias"), a polynomial with coefficients 0 and 0.001033884, so eng = 0.001033884 × raw. CITT1120TM is in txf (txt/CITT1120TM, 18 aliases). Its txp maps raw 103 to HK_SID_103.

    The SID field (NIT83001) is placed by plf at byte 16, exactly where pic tells the packetiser to read PI1. The identification field and the parameter that displays it are one and the same bits, defined twice: once as an identification rule and once as a parameter.

    SQL used 
    SELECT * FROM pic WHERE PIC_TYPE='3' AND PIC_STYPE='25';
SELECT * FROM pid WHERE PID_SPID='59203';
SELECT * FROM tpcf WHERE TPCF_SPID='59203';
SELECT l.PLF_NAME, c.PCF_DESCR, c.PCF_PTC, c.PCF_PFC, l.PLF_OFFBY, l.PLF_OFFBI,
       c.PCF_CATEG, c.PCF_CURTX
  FROM plf l JOIN pcf c ON c.PCF_NAME = l.PLF_NAME
 WHERE l.PLF_SPID='59203' ORDER BY CAST(PLF_OFFBY AS int);
SELECT * FROM caf WHERE CAF_NUMBR='CIT01053TM';     -- no row
SELECT * FROM mcf WHERE MCF_IDENT IN ('CIT01053TM','CIT01063TM','CIT01064TM');
SELECT * FROM txp WHERE TXP_NUMBR='CITT1120TM';

    Parameter → CUR → CAF/CAP, and parameter → OCF → OCP¶

    The parameter NCFT2X70 ("BattDischarge_I1 (PCDUA)", PTC 3 / PFC 12, unit A) shows the two remaining monitoring paths. It is carried in SPID 30552, "SYS Safe Mode ULGA", at byte 182.66

    1. pcf gives category N and an empty PCF_CURTX, because the parameter has several calibrations.
    2. cur has two rows. Position 1 selects the numerical curve CPWP4752TM when NPWZ0000 = 10. Position 2 selects CPWP9752TM when NPWZ0000 = 11.
    3. The applicability parameter NPWZ0000 ("PCDU_MODEL", PTC 2 / PFC 8) is a dynamic user-defined constant: PCF_NATUR = R, located in SPID 66830 "Dynamic UDCs". Its textual calibration AYMODELE labels raw 10 as EM and raw 11 as FM.
    4. caf/cap. Both curves have two points. CPWP4752TM maps raw 0 and 4095 to −8.8449 and 29.8655. CPWP9752TM maps them to −8.9764 and 28.93.
    5. ocf for NCFT2X70 declares 2 checks (OCF_NBOOL) on calibrated values (OCF_INTER = C, real limits OCF_CODIN = R). An out-of-limit state needs 2 consecutive violating samples (OCF_NBCHCK).
    6. ocp holds the two checks: position 1 is a soft limit (S) from −8.9764 to 0.14, position 2 a hard limit (H) from −8.9764 to 0.15. Neither has an applicability parameter.

    The calibration of this parameter therefore depends on a value that operators set on the ground through TM SPACON (see the MIB). The field semantics are those of the ICD.292324

    SQL used 
    SELECT * FROM cur WHERE CUR_PNAME='NCFT2X70';
SELECT PCF_NAME, PCF_DESCR, PCF_PTC, PCF_PFC, PCF_CATEG, PCF_CURTX, PCF_NATUR FROM pcf
 WHERE PCF_NAME IN ('NCFT2X70','NPWZ0000');
SELECT PLF_NAME, PLF_SPID, PLF_OFFBY FROM plf WHERE PLF_NAME IN ('NCFT2X70','NPWZ0000');
SELECT * FROM txp WHERE TXP_NUMBR='AYMODELE' AND TXP_FROM IN ('10','11');
SELECT * FROM cap WHERE CAP_NUMBR IN ('CPWP4752TM','CPWP9752TM');
SELECT * FROM ocf WHERE OCF_NAME='NCFT2X70';
SELECT * FROM ocp WHERE OCP_NAME='NCFT2X70';

    Command → CCF → CDF → CPC → PRF, and CVP → CVS¶

    The command ZCD00382 ("Define HK Para Rpt Collection Interval", TC(3,130), APID 172) walks the commanding chain:

    1. ccf gives CCF_PKTID = NOM_TC, so the header is the 80-bit layout shown above.
    2. cdf has two elements, both editable (E) and both taking their default from the parameter definition (CDF_INTER = D): PCD03011 (8 bits at bit 0) and PCD03012 (16 bits at bit 8).
    3. cpc gives PCD03011 ("HK SID") the type PTC 3 / PFC 4, an 8-bit unsigned integer, with range set VCD00353. PCD03012 ("generation period report") gets PTC 3 / PFC 12, 16 bits, with range set VCD00187.
    4. prf/prv. VCD00353 allows 1 to 192 and VCD00187 allows 1 to 65535. Their descriptions read "Integer between 1 and 19" and "Integer between 1 and 65". Both are exactly 24 characters long, the Char(24) limit of PRF_DESCR, so they appear to be the real ranges cut off at that limit (84 prf descriptions are exactly 24 characters).6622
    5. cvp attaches stages 14001 and 14007. In cvs, 14001 is acceptance (A) and 14007 is completion (C). Both are report-based (R), open 0 s after release and use a 20 s interval. Report-based stages have no cve rows.
    SQL used 
    SELECT * FROM cdf WHERE CDF_CNAME='ZCD00382';
SELECT CPC_NAME, CPC_DESCR, CPC_PTC, CPC_PFC, CPC_CATEG, CPC_PRFREF FROM cpc  -- CPC_PNAME is CPC_NAME in the SQLite copy
 WHERE CPC_NAME IN (SELECT CDF_PNAME FROM cdf WHERE CDF_CNAME='ZCD00382');
SELECT * FROM prv WHERE PRV_NUMBR IN ('VCD00353','VCD00187');
SELECT * FROM cvp WHERE COL1='ZCD00382';        -- cvp/cvs are stored as COL1..COLn
SELECT * FROM cvs WHERE COL1 IN ('14001','14007');
SELECT * FROM pcdf WHERE PCDF_TCNAME='NOM_TC';

    Sequence → CSF → CSS → SDF / CSP¶

    The sequence AACC309A ("STR A time update v06") has one formal parameter and two elements:

    css entry Element Release sdf rows (SDF_POS, SDF_PNAME, SDF_VTYPE, SDF_VALUE)
    1 command ZST15401 "STR1 Select ASP Channel", TC(154,1) A (relative to sequence start), 00.00.00 8, PST05054, F (formal parameter), XC309A01
    2 command ZCD00982 "Start Time Synchronisation to User", TC(9,130) R, 00.00.01, with CSS_MANDISP = Y 0, PCD09821, E (engineering), STAR_TRACKER_A; and 8, PCD09822, R (raw), 0

    The formal parameter XC309A01 ("ASP CHANNEL") is declared in csp with PTC 2 / PFC 8 and category T (textual calibration). When the sequence is loaded, the operator's value for XC309A01 flows into the PST05054 parameter of the first command.66 In the release column, CSS_RELTYPE = A counts CSS_RELTIME from the start of the sequence, and R counts it from the release of the previous command. For a command that needs its own manual dispatch (CSS_MANDISP = Y, as both elements here do), R counts from that command's dispatch time instead.48 More on release timing: Command sequences.

    SQL used 
    SELECT * FROM csf WHERE CSF_NAME='AACC309A';
SELECT CSS_ENTRY, CSS_TYPE, CSS_ELEMID, CSS_RELTYPE, CSS_RELTIME, CSS_MANDISP FROM css WHERE CSS_SQNAME='AACC309A';
SELECT * FROM sdf WHERE SDF_SQNAME='AACC309A';
SELECT CSP_FPNAME, CSP_FPNUM, CSP_DESCR, CSP_PTC, CSP_PFC, CSP_CATEG FROM csp WHERE CSP_SQNAME='AACC309A';

    By the ICD's import rule, the three orphan rows (one plf row and two cvp rows) would simply not be imported.9 The references agree with the model everywhere else, including the subtle SDF_REPPOS rule for commands with repeated groups.57

    This wiki also tested the key of every populated table against the 2025 data. All keys are unique except in two tables:66

    • txp. Calibration CYCT0002TM contains the row raw 1 → "Active" twice, so the key TXP_NUMBR + TXP_FROM is duplicated once. The 2020 release has no such duplicate.25
    • ccs. The key CCS_NUMBR + CCS_YVALS (raw) is unique, which confirms the reading of the columns above. On the engineering side, curve CPWP8010TM maps engineering 0 to both raw 0 and raw 430. This conflicts with the ICD's requirement that command curves be one to one.16

    The pid key, which includes PID_SPID, is unique. The packetiser's lookup key (the first five fields) is not: the three ground-frame packets 1000002, 1000003 and 1000006 ("Bad", "Idle" and "Good complete transfer frame") all use type 0, subtype 0, APID 1, PI1 0, PI2 0, and all three have PID_VALID = Y. The ICD allows several records with one lookup key, but only one may be valid, and at import only the last one with Y stays valid.1221

    SELECT count(*), sum(PLF_SPID IN (SELECT PID_SPID FROM pid)),
       sum(PLF_NAME IN (SELECT PCF_NAME FROM pcf)) FROM plf;

       sum(PCF_CURTX IN (SELECT TXF_NUMBR FROM txf)), sum(PCF_CURTX IN (SELECT MCF_IDENT FROM mcf))
  FROM pcf;
SELECT count(*) FROM pcf WHERE PCF_NAME IN (SELECT CUR_PNAME FROM cur) AND PCF_CURTX<>'';  -- 0
SELECT * FROM cvp WHERE COL1 NOT IN (SELECT CCF_CNAME FROM ccf);
SELECT COL3, count(*), sum(COL1 IN (SELECT COL1 FROM cve)) FROM cvs GROUP BY 1;
-- sdf -> cdf (temporary indexed copy, because the database is opened read-only)
CREATE TEMP TABLE tcdf AS SELECT CDF_CNAME, CDF_PNAME, CDF_BIT FROM cdf;
CREATE INDEX temp.i1 ON tcdf(CDF_CNAME, CDF_PNAME, CDF_BIT);

                            AND d.CDF_PNAME=s.SDF_PNAME AND d.CDF_BIT=s.SDF_POS))
  FROM sdf s WHERE s.SDF_ELEMID IN (SELECT CCF_CNAME FROM ccf);
