    Monitoring checks: limits and out-of-limits¶

    Calibration turns a telemetry sample into an engineering value. Monitoring checks decide whether that value is acceptable. In the SCOS-2000 MIB, two tables define every check the ground applies. The OCF holds one record per checked parameter. The OCP holds the checks themselves: soft and hard limits, expected statuses, deltas between samples, status consistency with commanding, and event triggers. Each check can be guarded by an applicability condition.16 When a valid sample violates an applicable check often enough, SCOS-2000 declares the parameter out of limits (OOL). It then shows the parameter on the OOL display. OOL records also end up in the packet archive, from which the EDDS delivers them to users.1923

    Spacecraft can also check their own parameters, with the PUS on-board monitoring service ST[12]. The last section compares the two and shows how the Solar Orbiter MIB decodes the on-board reports. All Solar Orbiter numbers come from this wiki's SQL queries on release MIB__20250916M25925PFMS001_SOL.40 Parameters and calibrations used here are introduced on Monitoring in the MIB and Calibration in the MIB.

    OCF: one record per checked parameter¶

    The OCF holds at most one record per parameter. It says how many checks the parameter has, how many consecutive violations make it OOL, and in which representation the limits are written.4

    # Field Type M Meaning
    1* OCF_NAME Char(8) M checked parameter (PCF_NAME)
    2 OCF_NBCHCK Number(2) M number of consecutive valid samples violating a check that are needed to declare the parameter OOL
    3 OCF_NBOOL Number(2) M number of OCP records for this parameter, 1 to 16
    4 OCF_INTER Char(1) M U uncalibrated: limits are raw values; C calibrated: limits are engineering values (only for calibrated parameters)
    5 OCF_CODIN Char(1) M format of the limit values: R real, I integer, A ASCII

    Field definitions from ICD §3.3.2.3.1.4 OCF_CODIN must match the representation chosen by OCF_INTER:4

    OCF_CODIN Allowed when
    R real raw values of real parameters (OCF_INTER = U, PTC 5), or engineering values of parameters with a real numerical curve, a polynomial or a logarithmic calibration
    I integer raw values of integer parameters (OCF_INTER = U, PTC < 5), or engineering values of integer-valued numerical curves
    A ASCII engineering values of status parameters (PCF_CATEG = S, OCF_INTER = C), compared with alias texts

    If the parameter is also used in a command verification expression, OCF_CODIN must be compatible with CVE_INTER.4

    A configuration coupling

    SCOS-2000's Behaviour Limit Checker can skip consecutive samples of periodic parameters whose value and validity are unchanged. If this optimisation is on (BEHV_ENABLE_OPTIMIZATION = 1), the configuration variable MVC_MAX_CONST_NUMBR must exceed the largest OCF_NBCHCK in the MIB.5

    OCP: the checks¶

    The OCP holds one record per check. SCOS-2000 applies the checks of a parameter in the order of the table, which must be sorted by OCP_NAME and OCP_POS.68

    # Field Type M / default Meaning
    1* OCP_NAME Char(8) M checked parameter (OCF_NAME)
    2* OCP_POS Number(2) M order of the check; soft/hard pairs ordered soft first
    3 OCP_TYPE Char(1) M S soft limit check; H "hard limit or soft status check" (wording of ICD 6.7 to 7.0); D delta check; C status consistency (needs PCF_USCON = Y); E event generation only, no OOL
    4 OCP_LVALU Char(14) low limit (numerical S, H, E checks; mandatory); or one expected status value (status parameters, S/H; mandatory); or minimum delta (D; optional, positive or empty)
    5 OCP_HVALU Char(14) high limit (numerical S, H, E; mandatory); or maximum delta (D; optional, positive or empty); irrelevant for status parameters and C
    6 OCP_RLCHK Char(8) applicability parameter; not used for C
    7 OCP_VALPAR Number(5) 1 raw value of OCP_RLCHK that makes the check applicable; not used for C

    Field definitions from ICD §3.3.2.3.2.8 Like validity and calibration-selection parameters, an applicability parameter must have an integer raw representation and be processed by the telemetry model (extracted through the PLF, or synthetic). SCOS-2000 also requires the applicability parameter to be valid.8

    Inference

    ICD issues 6.7, 6.9 and 7.0 all describe OCP_TYPE = H as "Hard limit or soft status check".813 Issue 5.1 simply has S soft OOL and H hard OOL,14 and the 7.0 rules say status checks, like limit checks, "can be associated to a check severity (Soft or Hard)".6 This wiki therefore reads S and H as soft and hard severity for both limit and status checks. The "soft status" wording looks like an editorial slip. In the Solar Orbiter MIB, status checks use both letters: 1,360 S and 696 H records.41

    The five kinds of check¶

    Limit checks (soft and hard)¶

    A limit check compares the valid value with a low/high pair. Limit checks are always given in pairs: a low limit alone is not possible. They apply only to numerical parameters (PCF_CATEG = N).7 Each check has a severity, soft (S) or hard (H). A soft/hard pair must share the same applicability condition (or have none) and follow each other in the order soft, then hard. Soft and hard checks may use the same low or high value. Either severity can also stand alone: a soft check does not need a hard partner.7

    A value exactly equal to a limit is not out of limits.7 The Herschel clarification note puts it the other way round: OOL is raised only if the value is below the low limit or above the high limit, for both soft and hard limits.15 A parameter that violates several checks at once, such as a soft and a hard one, is displayed according to the more critical violation.7

    Status checks¶

    A status check compares a status parameter's value with a set of allowed values. Each allowed value takes one OCP record, with the value in OCP_LVALU. With OCF_CODIN = A the values are alias texts, which requires OCF_INTER = C.84 All records with the same applicability condition and the same type form one set of allowed values. Several sets, under different applicability conditions, let the expected status depend on the configuration.7

    Delta checks¶

    A delta check compares the difference between the current valid value and the last valid value with a minimum and maximum. OCP_LVALU is the minimum delta and OCP_HVALU the maximum. Either may be left empty to skip that side. Both must be positive, because the check applies to positive and negative deltas alike.87 Delta checks are allowed on numerical representations: PCF_CATEG = N, or the raw value of any parameter with PTC < 6.7 The ICD's compatibility note lists delta checks among the options introduced in recent issues. Issue 5.1 had no D type.214

    Status consistency checks¶

    A status consistency check (SCC) compares a parameter, typically a status affected by commanding, with a reference value that SCOS-2000 maintains from the predicted or detected effect of commands.6 Several rules apply:739

    • The parameter needs PCF_USCON = Y.
    • The applicability condition is forced to true.
    • C checks (and E checks) must precede all other checks of the same parameter.
    • The CVE table, besides defining verification, identifies the parameters that a command affects. Their SCC is disabled during that command's verification window. For such parameters, the verification value (CVE_INTER) must use the same raw or engineering representation as the OOL checks (OCF_INTER).
    • CVE_CHECK says what a CVE record does for SCC. With B (the default), the record verifies the command and drives the SCC: its CVE_VAL becomes the new expected value of the parameter at the end of the verification stage window. With S, the record only disables the SCC during the window, and it must be combined with at least one B record of the same stage.9
    • The number of SCC parameters has a hard ceiling, set by the size of the SCOS-2000 packet that holds the snapshot of all SCC states. The ICD contradicts itself on whether the ceiling can be configured. The PCF_USCON description says it can be modified from release 4.1 through MAX_SCC_MESSAGE_LENGTH; the OCP rules say it "cannot be modified by configuration".37

    The operator can reset SCC states from TM SPACON.20 The EGSE test language reports SCC states as SCC_UNINIT, SCC_INIT, SCC_DISABLE and SCC_OFF.16 ECSS-E-ST-70-31C defines the same idea in neutral terms. The reference is either the last uplinked value of a command argument, with the check suspended during the command's execution window, or an expression for autonomous on-board changes.33

    Event checks¶

    An E check is not a monitoring check in the usual sense. When the parameter leaves the given range (and the check is applicable), SCOS-2000 generates an event with the full ID BEHV::<OCP_NAME>. Such events can trigger configured actions such as sending an e-mail, setting a configuration variable or running a script. A parameter that triggers an E check does not appear on the OOL display.6 This differs from the packet-level PID_EVENT mechanism, which raises an event when a packet arrives (PID fields).10

    How SCOS-2000 selects and applies checks¶

    For each new valid sample, SCOS-2000 runs through the parameter's OCP records in table order:7

    1. A check is applicable when it has no applicability parameter, or when its applicability parameter is valid and equals OCP_VALPAR. For C checks applicability is always true.
    2. The search stops at the first applicable check or soft/hard pair. Later sets are ignored, including after C or E checks. A global configuration variable, BEHV_STOP_FIRST_SET, can make SCOS-2000 apply all applicable checks instead, but only for the whole system, not per parameter.
    3. The selected checks are evaluated. A violation that persists for OCF_NBCHCK consecutive valid samples declares the parameter OOL.4

    Inference

    C and E checks must come first, and the search stops at the first applicable check, which for C is always the case. Read together, the two rules imply that a parameter with a status consistency check gets no further limit or status checks unless the global all-applicable option is set. The ICD does not spell this consequence out.

    flowchart TD

    Inference

    The state diagram is this wiki's reading of the ICD. The ICD defines when a parameter becomes OOL (OCF_NBCHCK consecutive valid violating samples) and that the more critical violation is displayed. It does not state whether a return to nominal also needs OCF_NBCHCK samples, or what happens to the counter on invalid samples. The TDRS output, which includes a state VIOL for "not in limits, but its number of violations is not equal to the maximum number of violations", suggests the intermediate "violating" state exists in the implementation.22 PUS ST[12], by contrast, applies its repetition number in both directions (below).

    What the operator and the archive see¶

    Displays and logs. The OOL display lists the telemetry parameters that are currently out of limits. The message display (event logger) scrolls SCOS-2000 log messages.19 Parameters carry an OOL state next to their value and validity. The SCOS-2000 EGSE test language, for example, returns an OOL state of NOMINAL, WARNING, ALARM or SCC for a parameter.16 It also lets a test procedure subscribe to a parameter so that it is notified when a limit applicability parameter or a calibration selection parameter changes, not only the value.17 Limit values, like calibration points and OL expressions, can be changed on line.20

    Packets and files. The Herschel/Planck EGSE configuration of SCOS-2000 stores OOL event packets under a system SPID, OOL_PACKET_APID, default 3000.18 Herschel's science ground segment pulled OOL data out of SCOS-2000 as "Out-of-Limits files" (ORF). A file retriever asks SCOS-2000 for a time period and receives the name of the written file, and an ingestor links each OOL packet to the observation building block closest in time. In routine phase the same ingestor read OOL files from the MOC's Data Disposition System, recognised by the extensions .OOL or .TLM.21 See Herschel/Planck ground segment.

    Retrieval services. The TDRS complete result file gives an OOL code for every sample.22 The EDDS delivers OOL records from the packet archive (PARC) with a typed state model. EDDS stream clients store them in OolRecording_… files.23

    Source OOL vocabulary
    EGSE test language (getoolstate) NOMINAL, WARNING, ALARM, SCC
    TDRS result file (OOL column) NOM, L low, LL low-low, H high, HH high-high, SCC_UNIT (SCC initialised), SCC_F (SCC failure), UDEF, delta codes (MIN_D_LOW, MIN_D_HIGH, MAX_D_LOW, D_EQUAL and a second MIN_D_HIGH described as the high limit for positive deltas), VIOL
    EDDS OOL record (OOLRecordType) LIMIT, STATE, STATUS_CONSISTENCY, SOFT_HARD_LIMIT, LIMIT_MO, DELTA
    EDDS OOLParameterState NOMINAL, WARNING, OUT_OF_LIMITS, SCC, SCC_DISABLE, SCC_OFF, SCC_UNINIT, VIOLATION, NO_VALUE
    EDDS limit / status / delta / SCC states LIMIT_HIGH, LIMIT_HIGH_HIGH, LIMIT_LOW, LIMIT_LOW_LOW, LIMIT_WITHIN_RANGE; STATUS_ALLOWED, STATUS_UNEXPECTED; DELTA_ALLOWED, DELTA_EQUAL, MAX_DELTA_HIGH, MAX_DELTA_LOW, MIN_DELTA_HIGH, MIN_DELTA_LOW; B_SCC_ENABLE, B_SCC_DISABLE, B_SCC_FAIL, B_SCC_OFF, B_SCC_UNINIT

    Vocabularies as printed in the sources.162223 An EDDS OOL record also carries the value, the lower and upper limits, the allowed values, the SCC reference value, the delta and last values, and hard and soft violation counts.23

    Inference

    The sources do not give a mapping from MIB check types to these vocabularies. A natural reading: a soft limit violation shows as WARNING / L or H / LIMIT_LOW or LIMIT_HIGH; a hard violation as ALARM (EGSE) or OUT_OF_LIMITS (EDDS) / LL or HH / LIMIT_LOW_LOW or LIMIT_HIGH_HIGH; a status check failure as STATUS_UNEXPECTED; an SCC failure as SCC / SCC_F / B_SCC_FAIL. Treat this as a hypothesis to verify against real EDDS output.

    Counts from both releases.4046

    More detail on the 2025 release:4041

    • Representation. 2,029 parameters are checked on raw integers (U/I) and 110 on raw reals (U/R). 1,558 are checked on calibrated reals (C/R), 8 on calibrated integers (C/I) and 1,633 on alias texts (C/A).
    • Number of checks. 3,649 parameters have one OCP record, 1,453 have two, 185 three, 31 four, 1 five, 17 six, and 2 have fifteen.
    • Persistence. 3,989 parameters go OOL on the first violating sample (OCF_NBCHCK = 1), 1,116 need 2 samples and 203 need 3. A handful need 4, 5, 8, 10, 14, 15 or 24.
    • Pairs. Among numerical limit sets, 1,534 are soft/hard pairs. 1,921 are hard checks alone and 202 soft checks alone. Every pair is ordered soft before hard, and no limit set has its low limit above its high limit.
    • Applicability. 859 OCP records use 180 distinct applicability parameters. The most frequent is NSM00002 "Current SSMM Mode act" (120 records), followed by the heater status parameters NPWSX053 "EUI OU DEC HEATER Sts" (54) and NPWSX051 "SPICE CE DEC HEATER Sts" (42).
    • Synthetic parameters. 242 of the checked parameters are dynamic OL synthetic parameters (PCF_NATUR = D).

    Example: soft and hard limits on an IMU temperature¶

    NMUD1113 "IMU11 SIA temperature" has OCF_NBCHCK = 1, OCF_NBOOL = 2, OCF_INTER = C and OCF_CODIN = R: two checks on calibrated real values, OOL at the first violation. Its OCP records (real MIB data):42

    OCP_POS Type Low High Applicability
    1 S soft −16 48 NCSD0P43 = 2 (IMUA Gyr1 SCV status ON)
    2 H hard −18 54 NCSD0P43 = 2

    The applicability parameter is the same one that makes the parameter valid (PCF_VALID = NCSD0P43, PCF_VALPAR = 2). Combined with the 11-point calibration curve CMUT0013TM (calibration page), these illustrative raw values give:

    Raw (12-bit) Engineering (degC) Outcome
    400 (0x190) invalid (below the curve, CAF_INTER = F) not checked: only valid values are checked
    850 (0x352) 54.898 hard OOL (above 54)
    1000 (0x3E8) 48.047 soft OOL (above 48, below 54)
    1100 (0x44C) 44.343 nominal
    2850 (0xB22) −13.837 nominal
    2900 (0xB54) −16.032 soft OOL (below −16)
    3150 (0xC4E) −34.426 hard OOL (below −18)

    The outcomes apply the ICD rules to real MIB definitions; the raw values are illustrative.742 Its neighbour NMUD1112 "IMU11 ORG temperature" uses the same curve, the same validity criterion and the same high limits (48 and 54), but its low limits are 2 (soft) and 1 (hard), and both checks are conditioned on NCSD0P73 ("IMUA Gyr4 SCV Stat.Tm") while its validity uses NCSD0P43.42 This may be deliberate or a copy slip; the MIB does not say.

    Example: limits that depend on a heater¶

    NRU02712 "ANP_1_1_12 SPICE CE" (16-bit raw, calibrated through the 51-point curve COMB000000 to DegC, OCF_NBCHCK = 2) has six checks. The heater status NPWSX051 "SPICE CE DEC HEATER Sts" (0 NOMINAL OFF, 1 NOMINAL ON, 2 INCORRECT CONF) selects one of three soft/hard pairs (real MIB data):43

    OCP_POS Type Low High Applies when NPWSX051 =
    1 S −44.5 −38.5 0 (NOMINAL OFF)
    2 H −47.5 −35.5 0
    3 S −44.5 57 1 (NOMINAL ON)
    4 H −47.5 60 1
    5 S −44.5 −38.5 2 (INCORRECT CONF)
    6 H −47.5 −35.5 2

    With the heater off, or incorrectly configured, the nominal band is −44.5 to −38.5 degC and the hard band −47.5 to −35.5 degC. With the heater on, the high limits rise to 57 and 60 degC. Under the standard "stop at first applicable set" rule, only the pair whose condition is true is evaluated, and two consecutive violating samples are needed.7 The parameter is located in three packets, YCF1Z079, YCF2Z003 and YCS2X188, all TM(3,25).43 The same pattern exists for other SPICE and EUI temperatures with six checks, keyed on NPWSX051 or on NPWSX053 "EUI OU DEC HEATER Sts" (for example NRU02730, NTCD50D6, NTCD50L6).41

    Example: a 15-value status check¶

    NCDT09N0 "OMMA_State" (32-bit enumerated, alias set CCDT0098TM with 16 states) has OCF_INTER = C, OCF_CODIN = A, and fifteen S records listing allowed texts: OFF, POWER_ON, POWER_OFF, FILLING, CHECKING, PREOPERATIONAL, OPERATIONAL, INIT, SYNCHRONISING, NOT_SYNC, ABORT_FILLING, ABORT_CHECKING, POWER_ON_END, POWER_OFF_END, INIT_END. The only state of the alias set that is missing is FAILED (raw 8). In effect, the soft status check flags that single state. NCDT09X0 (OMMB) is defined the same way (real MIB data).44

    Example: delta checks on error counters¶

    All 105 delta checks in the Solar Orbiter MIB belong to 105 different NIU… counters, such as NIU01008 "TC_Bad", NIU0100A "TM_Bad", NIU0101C "SpWwriteErr" and NIU0202C "EUV_HSL_CommandsBad". Every one has OCF_NBCHCK = 1, OCF_INTER = U, OCF_CODIN = I, a single D check and no other check. In 102 of them the minimum and maximum delta are both 0. The other three, NIU0700B "FSI_HSL_Timeout", NIU0800B "Lya_HSL_Timeout" and NIU0900B "EUV_HSL_Timeout" (16-bit unsigned), have both thresholds set to 2048 (real MIB data).44

    Inference

    With a maximum delta of 0, any change of the counter between two valid samples exceeds the maximum, so each new error raises an OOL. The minimum delta of 0 can never be undercut by an absolute difference. For the three timeout parameters with both thresholds at 2048, any delta other than exactly 2048 lies below the minimum or above the maximum. The ICD does not say whether a delta exactly equal to a threshold counts as a violation. EDDS and TDRS both have a separate "delta equal" state (DELTA_EQUAL, D_EQUAL),2322 which suggests the implementation distinguishes it. Why these three checks use 2048 is not stated in the available sources.

    Example: status consistency checks¶

    All 15 SCC parameters are counters of numerical category (13 unsigned integers and 2 enumerated parameters), each with one C check, OCF_INTER = U and OCF_CODIN = I; five use OCF_NBCHCK = 3 and ten use 1. Examples are NCDT02A0 "OBCHP_TTRMA_VC0_NB_Err" (OCF_NBCHCK = 3), NCDT07K0 "OBCHP_Nb_Reject_TcBuff", NDSD0046 "DST-A WD Reset Counter" and NSM01800 "PS0 Stored PKT counter". None of them appears in the CVE table, so no command verification disables their SCC (real MIB data).44

    Inference

    The ICD documents one way to set the SCC reference value: the CVE_VAL of a CVE_CHECK = B record at the end of a verification window. Because no CVE record names these counters, their reference value can only come from SCOS-2000's internal handling (for example initialisation from the first sample, or an operator reset in TM SPACON). The check then works like a latching "the counter has changed" alarm. The ICD does not describe how the reference value is initialised.

    Data-quality observations¶

    The following points come from simple consistency queries. They are reported as observations, not as errors of the mission's MIB:41

    • NCDX9308 has an OCF record with OCF_NBOOL = 2 but no OCP records. The ICD requires the count to match the OCP table.4
    • 349 status parameters (PCF_CATEG = S) carry raw integer limit pairs (OCF_INTER = U, OCF_CODIN = I, OCP_HVALU filled). For example, NCDX9000 "E_SCV_OBC_TTR_CPDU_A" has a soft pair 2…2 and a hard pair 1…2. The ICD restricts limit checks to PCF_CATEG = N and calls OCP_HVALU irrelevant for status parameters.78 How SCOS-2000 treats these records is not stated in the available sources.

    Ground checks and on-board monitoring (PUS ST[12])¶

    Ground checks run in the control centre on every valid sample that reaches it. On-board monitoring runs on the spacecraft itself, and its events can trigger on-board reactions. The PUS-C standard defines it as ST[12]. Its parameter monitoring subservice checks on-board parameters against definitions loaded by the ground, reports check transitions to the ground and raises events when conditions are violated. Those events can be caught on board, for example by the event-action service ST[19].24

    ST[12] parameter monitoring in brief¶

    • Check types. Limit checks and expected-value checks are mandatory; delta checks are optional. A limit check succeeds when low ≤ value ≤ high. An expected-value check masks the value and compares it with the expected value. A delta check compares the difference between consecutive values with two thresholds; its definition includes the number of consecutive deltas that are averaged.2526
    • Definitions. Each parameter monitoring definition (PMON) contains its own ID, the monitored parameter, an optional check validity condition, an optional definition-specific monitoring interval and a check definition. The check definition holds a repetition number, the check type, the limits or expected value and mask, and an optional event ID for each kind of violation. Several definitions may watch the same parameter, one with warning limits and one with danger limits, for example.2426
    • Check validity condition. A validity parameter, a bit mask and an expected value. The condition is true when (validity parameter AND mask) equals the expected value.26
    • Statuses. For a limit check the checking status is "unchecked", "invalid", "within limits", "below low limit" or "above high limit". A new status is established only after "repetition number" consecutive checks agree, in either direction.2728
    • Reporting. Each status change is recorded in a check transition list, reported in TM[12,12] check transition reports when a declared maximum number of transitions is reached or at the maximum transition reporting delay after the first recorded transition. TC[12,10] requests a TM[12,11] out-of-limits report.3031

    Solar Orbiter's on-board monitoring and how the MIB decodes it¶

    Solar Orbiter implements its own tailoring of service 12.34 Each monitoring entry added with TC(12,5) contains a monitoring ID, the parameter ID, a validity parameter ID (0 means "always check"; the validity parameter is a Boolean), a monitoring interval in application cycles, a repetition count Rep (1–255, the number of successive samples needed both to declare a parameter out of limits and to declare it back within limits), an enable status, and either a limit definition (low limit with EID, high limit with EID) or an expected-value definition (mask, expected value, EID).35 The checking statuses are coded 0 (within limits or expected value), 1 unchecked, 2 invalid, 3 unselected (not used), 4 unexpected value or below low limit, and 5 above high limit. The maximum reporting delay is counted in 8 Hz cycles, and 0 disables transition reports.3836

    The reports reach the ground as variable packets. The MIB defines TM(12,9) monitoring list, TM(12,11) out-of-limit list and TM(12,12) check transition reports as variable packets for the six APIDs 163, 179, 195, 211, 227 and 259, each with its own TPSD, plus one more TM(12,12) on APID 1075. The TM(12,11) of APID 163 is TPSD 14173.45 Its VPD layout is drawn here (real MIB definitions; field sizes also printed in the Solar Orbiter TM-TC and Packet Structure ICD):4538

    The status fields use the alias set CCDT0011TX (0 VALID, 1 UNCHECKED, 2 INVALID, 4 BELOW_LOW, 5 ABOVE_HIGH, 6 OUT_OF_LIMIT). That set matches the codes of the TM-TC and Packet Structure ICD and adds a value 6 that the ICD does not list.4538 The Database Import ICD notes that all service 12 reports are variable packets. Their values therefore do not take part in validity, monitoring checks or synthetic parameters on the ground. The ICD recommends variable packets only for special reports that need no such cross-processing with other telemetry.1112 The MIB also contains fixed-layout TM(12,9) definitions on APIDs 1986 to 1990 ("AOCS", "PAYLOAD", "PLATFORM", "SYSTEM" and "THERMAL" monitoring list reports, numbered #1 to #3). They are distinguished by two 8-bit identification fields: PI1 at octet 19 and PI2 at an APID-specific offset (octet 883 for AOCS, 2083 for PAYLOAD, 2755 for PLATFORM, 2227 for SYSTEM and 2179 for THERMAL). The PLF names what sits there: the monitoring-ID fields of fixed entry slots. In SPID 65909 (AOCS #1), for example, octet 19 holds NXAS001A "PID11_S001_ID" and octet 883 holds NXAS041A "PID11_S041_ID". The three AOCS reports have PI1/PI2 values 1/41, 122/142 and 220/242. Two SYSTEM definitions (SPIDs 65917 and 65954) share PI1 = 1 and differ only in PI2 (255 and 253).45 This matches the TM-TC ICD, where the monitoring status, the maximum reporting delay and the count N precede the first monitoring ID of the report.37

    Inference

    The fixed (12,9) definitions look like a way to decode the expected content of the on-board monitoring list, split over several report packets, with the full PLF machinery rather than the VPD. The monitoring IDs of two entry slots then tell the packets apart. The source documents do not explain these definitions.

    The neutral data model of ECSS-E-ST-70-31C covers both worlds. A limit check carries domain-specific limit sets (AIV, Operations, Software), each selected by a validity condition expression, with upper and lower danger and warning limits and a corrective activity for each. Delta checks have maximum and minimum thresholds, expected-state checks have lists of values, and status consistency checks have a command argument or expression as reference.3233

    Inference

    ECSS-E-ST-70-31C warning and danger limits correspond naturally to SCOS-2000 soft and hard limits, and its "first true validity condition applies" matches the SCOS-2000 "first applicable set" rule. Neither document states this correspondence.
