    Mission tailoring of the MIB¶

    The SCOS-2000 Database Import ICD defines a generic Mission Information Base (MIB): 53 tab-separated tables that any mission can fill (51 in the summary of its §3.2, plus the two printout tables PPF and PPC defined in §3.3.2.7.7–3.3.2.7.8).13 No real project uses it untouched. Projects narrow it, by forbidding options, shortening identifiers and fixing naming rules, so that databases from many suppliers can be merged. They also widen it with extra files for information the ICD has no place for. This page collects the tailoring documents in this wiki's library, most of them from the Herschel/Planck programme, and then examines the extra tables of the public Solar Orbiter MIB.

    What the ICD itself allows¶

    The ICD leaves three doors open on purpose:

    • Any off-line database. The ICD imposes no constraint on how the ASCII files are produced. Typically a relational database is used, "e.g. MS ACCESS" in issue 7.0, and "ORACLE, MS ACCESS" in issue 5.1.25
    • Extra fields at the end. Fields that a mission needs and that the ICD does not define "have to be added at the end of the table". Their length is limited only by the importing computer.6
    • Another separator. A mission may replace the tab separator, provided the importer is adjusted.6

    The ICD also makes the off-line system responsible for consistency. The importer catches only the most dangerous problems, and an off-line consistency checker is delivered from release 4.0.7 Everything else, such as names, numbering ranges and which optional features are used, is left to the mission. That is the space that tailoring documents fill.

    The Herschel/Planck tailoring stack¶

    On Herschel and Planck, the five instrument teams (HIFI, PACS and SPIRE; HFI and LFI) worked with instrument EGSEs based on SCOS-2000. Their MIBs then had to flow into Alcatel's Herschel/Planck System Database (HPSDB) and the Central Checkout System (CCS), and, for Herschel, into the Herschel Common Science System (HCSS).     The project requirement: one common satellite database¶

    The Herschel/Planck Operations Interface Requirements Document (OIRD) sets the frame. The prime contractor and the instrument developers deliver a Satellite Database (SDB) that defines all telemetry, telecommands, command sequences and software parameters, the instrument parts being provided by the principal investigators. It must be a single common database for system engineering, AIV and operations, comply with the SCOS-2000 Import ICD issue 5.1 (the OIRD's AD-8),4 be internally consistent and consistent with the flight dynamics database and on-board software, contain no irrelevant data and no duplications, and record every update down to field level.1213 Deliveries are scheduled from version 0 (instrument AVM) to a pre-launch update one month before launch, as Oracle data files, each with a configuration control file and the on-board software versions it matches.13 For naming, the OIRD defers to the project naming convention H-P-1-ASPI-SP-0141.14

    The packet rules: the PS-ICD narrows the parameter types¶

    Before any MIB rule, the Packet Structure ICD (SCI-PT-ICD-07527, issue 6.0 of January 2008) fixes what may appear in a packet at all: the space and ground segments support "all and only" the structures and services it defines, and packets may use only the parameter types of its Appendix 6.6768 That appendix is a subset of what the SCOS-2000 import ICD accepts, so every packet field described in a Herschel/Planck MIB had to use a PTC/PFC pair from this list (field meanings as on MIB parameter types):6869

    PTC Type PFC allowed by the PS-ICD Restriction compared with the MIB
    1 Boolean 0 -
    2 Enumerated 1 to 8, 12, 16, 32 bits Other widths up to 32 bits excluded
    3, 4 Unsigned, signed integer 0 to 14 (4 to 15 bits, 2, 3 or 4 octets) No 48- or 64-bit integers
    5 Real 1 (IEEE single), 2 (IEEE double) MIL-STD-1750A formats excluded; PFC 3 was removed in issue 6.0
    6 Bit string 1, 2, 4, 8 bits Other widths excluded
    7 Octet string 0 (variable) or n octets Not editable by the operator when used in a TC
    8 Character string 0 or n characters On board only for the PROM software version identifier (allowed since issue 6.draftA); free for SCOE/EGSE
    9 Absolute time 17 (CUC, 4 octets coarse, 2 fine) Only one time format
    10 Relative time - Not used
    11 Deduced 0 Used for OBCP parameters in TM(18,13)

    The right-hand column is this wiki's comparison with the MIB ICD; the PS-ICD values are from Appendix 6 and its change record.6869707174 The PS-ICD also reserves the APIDs 2016 to 2046 for SCOE and EGSE messages and 2047 for idle packets, and gives every instrument a base APID whose four low bits separate packet categories and prime from redundant units (HIFI: 1024 prime, 1025 redundant, 1026/1027 non-essential HK, 1028-1031 science).7273 By this wiki's reading, a MIB built for these rules therefore has many pid rows per instrument that differ only in the low bits of PID_APID; the PS-ICD does not discuss the MIB.

    The PS-ICD type set against a later mission (real data, Solar Orbiter 2025)

    Applied to the Solar Orbiter MIB of 16 September 2025, the Herschel/Planck type set would accept 124 203 of the 126 745 monitoring parameters. The other 2 542 use enumerations of other widths (250, for example 224 of 18 bits), bit strings of 3, 5, 6, 7, 11 or more bits (124), absolute times other than PFC 17 (2 119, of which 2 116 are PTC 9 PFC 15), relative times (47) and PTC 13 (2). All its reals are IEEE (PFC 1 or 2), and 120 parameters are character strings, among them software version strings such as NIC0A000 (FSW_VERSION_STR). Of the 7 155 command parameters, 40 fall outside the set (4 enumerated, 35 absolute time, 1 relative time).116

    Inference

    This is a comparison, not a judgement: Solar Orbiter has its own packet rules, and its choice of other PFC values is not an error. The comparison only shows how much narrower the Herschel/Planck packet rules were than the import ICD, and therefore than what a generic MIB tool must support.

    Alcatel faxes of 2003: identifier limits and reserved ranges¶

    The Herschel Planck project office of Alcatel Space Industries (Cannes) sent two faxes to the five instrument teams, copied to ESTEC and ESOC, under the subject "SCOS – Limitation to naming convention". Their stated aim is to support a "smooth transition" from instrument-level to module-level testing.1518

    H-P-ASP-LT-2607, 27 January 2003 sets five requirements:1617

    # Requirement Justification given
    1 Calibration curve identifiers limited to Number(3) the ICD (issue 5.1) allows Number(4); the naming convention defines a curve identifier at theoretical element level as "IDIN03F"
    2 Range set identifiers limited to Number(3) same reasoning
    3 Command verification stage identifiers limited to Number(4) the ICD allows Number(5); the convention defines "IDIN04F"
    4 Dynamic UDCs allocated in fixed ranges of the single "constant packet" in the PLF the constant packet is unique, so allocations would overlap at integration
    5 The SPID of the constant packet must support 1,024 octets every level produces the same archive format, at the cost of disk space at instrument level

    The UDC allocation of requirement 4 partitions the constant packet as follows:17

    Range Herschel Planck
    0000–0099 System System
    0100–0199 SVM SVM
    0200–0299 PLM PLM
    0300–0399 HIFI HFI
    0400–0499 PACS LFI
    0500–0599 HIFI (sic; SPIRE expected) not used ("Sorbtion cooler ?")
    0600–1023 spare, allocated by ASP spare, allocated by ASP

    A typo in the source

    The fax's text layer really assigns 0500–0599 on Herschel to "HIFI" a second time (PDF p. 2).17 Since HIFI already holds 0300–0399 and SPIRE is the only Herschel instrument without a range, the second entry probably means SPIRE. This is this wiki's reading; no corrected version of the fax is in the library.

    H-P-ASP-LT-2905, 27 March 2003 adds two requirements to those of the January fax. This fax is a scan without a text layer; its content here is summarised from the manual reading recorded in this wiki's library entry, which this review re-checked against the scanned page images. It numbers its requirements 5 and 6, so both faxes have a requirement 5.18

    • Requirement 5: in the pid table, PID_SPID must equal PID_TPSD. The justification is "only to facilitate the mapping" between the Herschel/Planck System Database (HPSDB) and the SCOS "bridge" files: different SCOS packets will no longer be able to address the same variable packet structure definition.18
    • Requirement 6: in the pcf table, the field printed "PCF-WIDTH" "shall not be set to 'Null'". The justification (where the field is printed "PCF_WIDFT") is that it is "(indirectly) redundant with VPD_OFFSET" and that HPSDB will only support VPD_OFFSET.18

    Inference

    The scan does say "shall not be set to 'Null'"; the manual reading did not invert it. The rule nevertheless sits oddly with its own justification and with the HPSDB processing note of 2006, which ignores PCF_WIDTH on input, forces it to null on output and says only VPD_OFFSET is used.45 Either the fax itself contains a slip (a rule that the field "shall be set to Null" would match its justification), or the project reversed the rule between 2003 and 2006. The available sources do not say which.

    SPIRE's MIB naming convention¶

    SPIRE's technical note SPIRE-RAL-NOT-001155 (issue 1.2, 11 March 2002) applies the project naming convention to the SPIRE MIB, including the parameters of the SPIRE EGSE and test equipment, which are not delivered with the instrument. It calls the MIB the "Mission Implementation Base".19

    Item ICD fields Pattern Convention ref.
    Command CCF_CNAME, CDF_CNAME, PTV_CNAME SCiiippp 4580
    Command parameter CPC_PNAME, CDF_PNAME SPiiippp 5130
    Command numerical / textual calibration CCA_NUMBR, CCS_NUMBR / PAF_NUMBR, PAS_NUMBR tttnnnrrr (alternative sss) 5370
    Monitor packet PID_SPID, TPCF_SPID, PLF_SPID tttnnnnppp 4380
    Monitor parameter PCF_NAME, OCF_NAME, OCP_NAME, PLF_NAME, PTV_PARNAM SMiiippp 5130
    Numerical, textual, polynomial calibration CAF_NUMBR, TXF_NUMBR, MCF_IDENT (and detail tables) tttnnnrrr (sss) 5370
    Alphanumeric, graphical, scrolling display DPF_NUMBE, GPF_NUMBE, SPF_NUMBE SAiiippp, SGiiippp, SLiiippp 6100, 6110, 6130

    Patterns from the note.20 The components are:21

    • iii, the theoretical parameter identifier: first character the subsystem ID, third character the parameter unit ID.
    • nnn/nnnn, running numbers from zero; ttt, the system element number; rrr, the real element number; ppp, the position identifier; sss, an alternative identifier for calibration curves in case SCOS-2000 cannot handle 8-character names.
    • System element numbers: OBS 480, DPU 490, DCU 500, MCU 510, SCU 520, EGSE 528, test facility (TFCS) 529, each with its subsystem letters (for example SCU: C calibrator, H heater, K sub-K, T temperature).21
    • Real element numbers start at 100 (AVM), 300 (QM), 500 (FM) and 700 (FS) and increase by one for each new configuration, so a data set records which hardware build it describes.22
    • Unit IDs: A current, B limit, E error, F status flag, H frequency, K temperature, L lower limit, M mode, N count, P position, R phase, S speed, T time, U upper limit, V voltage, W power.2223

    Note that the leading S identifies SPIRE. The HCSS comments explain that instrument-related mnemonics start with H, P and S, and during instrument-level tests with I, O and Q.35

    The HCSS MIB Clarification and Tailoring Note¶

    The Herschel Common Science System (HCSS) used the MIB to build instrument commands and to interpret downlinked data for quick-look and interactive analysis. The HSC note HSC/DOC/0300 (issue 1.5, 21 December 2004), approved by the HSC and the three Herschel instrument teams, specifies the MIB interface into the HCSS. It clarifies the ICD (issue 5.2) and the naming convention (issue 2.1), adds Herschel constraints, and lists the checks of the HCSS MIB ingestion software.242527

    Clarifications of the ICD. Three of them (4.1.4, 4.1.6 and 4.1.7) correspond to Document Change Requests that ESOC raised against the ICD (DCR 286, 309 and 308):2837

    Point Clarification
    4.1.1 A line is one record, ended by LF (Unix) or CR LF (Windows). A record has N−1 tabs for N fields. Trailing fields that SCOS-2000 ignores (grey in the ICD) may be left out.
    4.1.2 Mandatory fields must hold a value of the right type, and numeric fields must not be empty or blank.
    4.1.3 A non-mandatory field without a stated default defaults to 0, 0.0 or the empty string.
    4.1.4 The separator must always be present even when the value is empty (DCR-286).
    4.1.5 An out-of-limits condition is raised only strictly below the low or above the high limit, for hard and soft limits.
    4.1.6 PLF_OFFBY/PLF_OFFBI count from the end of the SCOS-2000 packet header, which equals the start of the TM source packet header with the generic packetiser (DCR-309).
    4.1.7 Bit 0 of PLF_OFFBI is the most significant bit (DCR-308).
    4.1.8 Real numbers use the decimal point, not a comma.

    Naming clarifications. Of the naming convention, only NMCVT-0100-C (identifiers) and NMCVT-7600-C (descriptions) affect ingestion. NMCVT-0100-C forbids I, O and Q as leading characters. NMCVT-7600-C limits descriptions to letters, digits, space, +, - and _, asks for meaningful text and understandable abbreviations, and forbids an empty short description.29 For the HCSS the short description must match [a-zA-Z0-9_]+, because the scripting language of the Common Uplink System (CUS) cannot use + or -. The combination of the first character of the name and the full description must be unique for commands, command parameters and monitoring parameters, and PID_APID with PID_DESCR must be unique for packets.3236

    Constraints for the final interface:3031

    Point Herschel constraint
    5.1 All ICD tables in one directory; synthetic definitions accepted in subdirectory synthetic; everything else ignored. An extra two-field table gives each command's duration for the CUS.
    5.2.3 VDF ignored.
    5.2.4 Constants (PCF_NATUR = C) ignored; all other natures accepted.
    5.2.5 The SPID is the only key to a parameter's location; a packet is identified by type, subtype, APID and, where relevant, SID; one SPID per packet type is assumed.
    5.2.6 A PID row may not give a SID value greater than 0 when the matching PIC row says no SID (PIC_PI1_OFF = -1).
    5.2.7 Except pseudo commands starting with Z, every CCF_PKTID must have at least 4 PCDF rows (version, type, data field header flag, APID). The note observes that this contradicts the ICD's statement that PCDF_TCNAME is unique.
    5.2.9 CDF_CNAME + CDF_PNAME unique; repeated groups instead of repeated parameters.
    5.2.10–11 Command sequences (CSF, CSS, SDF, CSP) and parameter sets (PST, PSV, CPS, PVS) ignored.
    5.2.12–13 TXP_FROM ≤ TXP_TO, and textual calibration ranges must not overlap.

    Software version 0.2 was stricter: only R parameters, so no synthetics; only OCF_CODIN values R and I; no variable packets; and for engineering command parameters no raw default value.33

    Checks. Section 7 numbers the checks of the ingestion software from 7.0.1 to 7.0.34 (7.0.6 is marked "check removed"), and marks those not yet in version 0.2 as "To be implemented", for example the validation of synthetic and variable packet definitions. Examples: input file names, field counts per line, field types (with a null value assigned on mismatch), non-R natures flagged with an assumed length of −1, missing calibrations, uniqueness of PCF_NAME, OCF_NAME, CPC_PNAME and CCF_CNAME, the description rules above, TXP range order and overlap, consistency of numerical and textual de-calibrations, CPC_RADIX limited to D, H and O, and PID_INTER allowed only for periodic (3,25) packets.34

    SPID uniqueness. Section 10 records an e-mail exchange of September 2002. PACS reported that all its TC verification packets shared SPID 10006, because the SCOS-2000 version of the time did not allow a range of SPIDs for packet type 1. ESOC confirmed that all TM packets of type 1 with a given subtype had to share one SPID, because the Verifier listened only to a predefined list of SPIDs. Rosetta had implemented a change allowing any SPID for service 1 and CryoSat one allowing a range of SPIDs, and these were to be merged into release 3.1 by a function that reads all type-1 SPIDs from pid.dat.38 See Command verification in the MIB.

    HPSDB: how the system database processed MIB files¶

    Alcatel Alenia Space's note H-P-1-ASP-TN-1060 (issue 1, February 2006) documents how HPSDB ingests SCOS-2000 (instrument EGSE, ICD 5.1) and CCS MIB files and regenerates them as "bridge files". Constraints in bold in the note cannot be checked by HPSDB and are the user's responsibility. The note warns that 100% round-trip compatibility cannot always be reached. For example, HPSDB allows an N-to-1 relation between TM packets and SPIDs, while the ICD allows N-to-N.40

    Rule Content
    G1 object data model MIB data is wrapped in objects identified by identifier and position; every (object, generic object) pair must be consistent.
    G2 naming First letter of a character identifier gives the item type; curves are Number(6) (3 digits theoretical element + 3 free); subsystem letter prefixed and 3-digit position appended at instantiation; generic items use subsystem G, number 07, position 000.
    G3–G5 short S2K identifiers S2K curves Number(3) for specific and 1xxx for generic curves (G000xxx000); verification stages Number(4)/1xxxx; range sets Number(3)/1xxx.

    • the EGSE subsystem letter is Y, written as the number 25 (Y being the 25th letter) in remote monitoring packet names;
    • each EGSE item owns a range of positions: ACMS SCOE 920-939, CCS 940-941, PLM SCOE 942-943, CDMU DFE 944-945, TM/TC DFE 946-947, CDMU SCOE 948-949, TT&C SCOE 950-951, LPS 952-953, SAS 954-955, BATSIM 956-957, cryo SCOE 958-959, cryo COTE 960-961, HIFI 962-963, PACS 964-965, SPIRE 966-967, HFI 968-969, LFI 970-971;

    Configuration control at SPIRE¶

    SPIRE's note on database management and CUS configuration control (issue 1.0, February 2007) shows the other half of tailoring, namely how a validated MIB is kept traceable in tests. The rationale is to know, at any later time, which version of which script produced a given set of telemetry.53 The steps for a new test database are: create a Versant database, create a mission configuration (config1), ingest the MIB with ingestmib under a user label, load calibration tables, import the CUS definitions, set the initial observation ID and create an instrument model for the configuration.54 Ingestion runs semantic checks and writes mibchecker.log. Serious problems stop the ingestion, while minor ones are only logged.55

    Scripts are tagged in CVS as LABEL_CONFIGN, for example AVM_TEST_CONFIG6. During a test, changes are tracked only by the database's automatic versions (a CVS version 1.2 becomes 1.2.1 on ingestion), and the results are checked back into CVS afterwards. A new configuration freezes a snapshot of definitions and calibration tables.56 A calibration table TestSetup.txt with the keys configuration, environment (moc, ilt, hsc, ist, par), test type, prime or redundant instrument, thermal condition and debug level lets the same CUS definitions serve every test environment.57

    pcf_glob_det: detail parameters inside global parameters¶

    Each of the 56,631 rows names a global parameter, a detail parameter and a number. All names are PCF parameters, each detail belongs to exactly one global, and there are 8,704 globals with up to 1,024 details each. A typical example is the 8-bit NAH0Z000 "APMHA_TM_1 [000]", split into the 3-bit NAHD0000 "APMHA_Mode" at offset 0 and five 1-bit flags at offsets 3 to 7.62

    Global Detail Offset Detail description Detail type
    NAH0Z000 (PTC 3, PFC 4) NAHD0000 0 APMHA_Mode ⅔
    NAHD0001 3 APMHA_Mode trans 2/1
    NAHD0002 4 APMHA_SafePos achieved 2/1
    NAHD0003–NAHD0005 5–7 APMHA_Survnce_ Stat, APMHA_Vind_Elev_Stat, APMHA_Va_Elev_Stat 2/1

    The number is a bit offset. In every packet where both a global and one of its details are located by the PLF (215,859 such pairs), the detail starts exactly that many bits after the global: in SPID 33500, for instance, NAH0Z000 and NAHD0000 both start at octet 67, bit 0, and NAHD0001 at octet 67, bit 3.62 12,074 rows have a global with no PLF entry. Of the 8,704 globals, 5,124 are octet strings (PTC 7; 1,913 of them 8 octets long) and 3,580 are unsigned integers (PTC 3), mostly of 8 bits (1,607) or 16 bits (1,464).62

    Inference

    The table records, as data, the structure that the PLF expresses only implicitly through overlapping entries: a raw word is located once as a global parameter, and its fields are located again as overlapping detail parameters. Tools can use it to show a word together with its decoded fields, or to check that the overlaps are consistent. The ICD allows overlapping PLF entries,8 but has no table that ties a field to its container.

    dup: duplicating packets under a pseudo-APID¶

    The 69 rows of dup.dat map a SPID to an APID. Every SPID exists in the PID, and every target APID is one of 41 APIDs between 1953 and 1996 that appear in the PID with their own packet definitions. The duplicated packets are generic reports: event reports (5,1), (5,2) and (5,3), memory dumps (6,6), monitoring list reports (12,9), functional monitoring reports (142,11) and some private services.63

    The ICD offers one piece of the mechanism. Since issue 6.5 (release 4.2) the PIC table has an optional field PIC_APID, so the position and width of the extra identification fields PI1 and PI2 can be defined per APID and type/subtype instead of per type/subtype only.910 In the 2025 release 47 PIC rows set PIC_APID, and their APIDs are exactly the 41 dup targets.63

    The chain for the AOCS monitoring list report shows how the pieces fit together:63

    1. The spacecraft sends a (12,9) monitoring list report from APID 179. The MIB defines it as SPID 20129 "Monitoring List Report", a variable packet (PID_TPSD = 20129), with no PI1/PI2.
    2. dup.dat maps SPID 20129 to APID 1986.
    3. For type 12, subtype 9 and APID 1986, the PIC places PI1 at octet 19 (8 bits) and PI2 at octet 883 (8 bits).
    4. The PID has three (12,9) packets on APID 1986: SPID 65909 "AOCS - Monitoring List Report #1" (PI1 = 1, PI2 = 41), SPID 65910 "#2" (122, 142) and SPID 65911 "#3" (220, 242). All are fixed packets (PID_TPSD = -1).
    5. SPID 65909 has 1,275 PLF entries, one fixed slot per expected monitor. PI1 is the ID field of the first slot (NXAS001A, octet 19), and PI2 the ID field of a later slot (NXAS041A, octet 883).
    6. Synthetic "consistency" parameters check every slot's ID and act as validity parameters for the slot's fields (see Synthetic parameters).

    s13a, s13p and s13t: file transfer definitions¶

    The three s13 files are new in 2025. s13p lists 11 partitions with numeric identifiers 161 to 195, such as 161 "OMM TC Files (A)", 162 "OMM OBCPs (A)", 163 "OMM System Files (A)", 177 "OMM TC Files (B)" and 193 "SGM-EEPROM CSW TC Files (A)". s13a lists 7 codes 0 to 6: PLAIN, OBCP, DELAYED TC, IMMEDIATE TC, PAYLOAD CONTEXT, INVALID and OTHER. s13t lists 12 file types with codes −2 to 9, such as "TC sequence (CSF type 1)", "Time tagged TC sequence (CSF type 2)", "Backup MTL (CSF type 3)", "SCOS stack file" and "OBCP". Its sixth column refers to an s13a entry, and its seventh to a default s13p partition (TCFA, SYSA, OBCA).64

    The partition numbers match the commanding side of the MIB. The command ZCD00D09 "Accept First Uplink Part", a PUS service 13 telecommand (13,9), has the parameters FTS Id, Partition Id, File IDentifier, File size, File Attribute and the file content. Its Partition Id is decalibrated by CCDT0192TX "Partition", whose 11 values are the same numbers 161 to 195 as in s13p (for example 161 OMM_TC_FILES_A, 193 SGMA_TC_FILES). Its File Attribute uses CCDT0082TX "File types": 0 FT_INVALID, 1 FT_OBCP, 2 FT_DEL_TCSEQ, 3 FT_IMM_TCSEQ, 4 FT_PL_CTX, 5 FT_PS, 6 FT_PLAIN, 7 FT_FAT.65

    Inference

    The s13 tables appear to configure a ground tool that uploads files to the on-board mass memory with service 13: s13p names the target partitions, s13a the attribute values, and s13t the kinds of file to upload with their default attribute and partition. Codes 1 to 4 of s13a match the File Attribute calibration, but codes 0, 5 and 6 do not (s13a has 0 PLAIN, 5 INVALID, 6 OTHER, while the calibration has 0 FT_INVALID, 5 FT_PS, 6 FT_PLAIN), and the s13p description of 164/180 ("OMM Spare") differs from the calibration (OMM_PAYLOAD_A/_B). The meaning of the one-letter flags in the second column (M, B, N in s13p; C, W in s13t) is not stated in the available sources.
