    The MIB: Mission Information Base¶

    The Mission Information Base (MIB) is the body of data that tells ESA's mission control system SCOS-2000 everything it must know about one spacecraft: every telemetry parameter and how to extract, calibrate and limit-check it, every telemetry packet and how to recognise it, every telecommand and how to encode, check and verify it, and the command sequences and displays built on top of them. The MIB is delivered to SCOS-2000 as a set of tab-separated ASCII files, one file per table, whose layout is fixed by the SCOS-2000 Database Import ICD (EGOS-MCS-S2K-ICD-0001). SCOS-2000 then imports these files into its own run-time database.1

    This page explains what the MIB contains and how the interface works. It then maps all 53 tables of the ICD and takes a tour of a real, publicly posted MIB: the one used to operate Solar Orbiter. Related pages go deeper:

    • MIB data model: how the tables reference each other (keys and join paths).
    • MIB parameter types: the PTC/PFC codes that define every value's encoding.
    • History of the Database Import ICD: how the tables evolved from issue 3.2 (1999) to 7.2 (2019).
    • Topic pages on monitoring, calibration, monitoring checks, commanding, command verification, sequences and parameter sets, displays, synthetic parameters, mission tailoring and tooling.
    • One generated reference page per table under MIB tables, and the interactive MIB explorer for browsing the Solar Orbiter data.

    What the MIB is¶

    Static database and dynamic archive¶

    The ICD divides the SCOS-2000 Mission Information Base into two parts. The static part, usually just called "the database", holds the definitions described on this page. The dynamic part is the packet archive, which holds the telemetry and telecommand history that SCOS-2000 records during operations.2 The Database Import ICD only concerns the static part. The other sources in this library also use "MIB" for the static database, for example the HIFI team's description of the MIB as a set of ASCII files,22 and that is how this wiki uses the word. Issue 5.1 of the ICD (2001) still called the dynamic part the "history files"; issue 6.7 replaced that term with "packet archive".34

    The scope of the ICD: generic tables only¶

    The ICD describes how a "client mission" must present its data so that the SCOS-2000 importer can read it. It covers only the "generic" portion of the static database, meaning the data that standard SCOS-2000 functions need. The abstract states explicitly that mission-specific extensions are possible.5 Two mechanisms support this:

    • Extra fields. A mission may add its own fields to any table, but only at the end of each record. The length of these extra fields is limited only by the maximum string size of the computer that runs the importer.6
    • Extra tables and files. A mission may deliver further files for its own applications. For some tables that SCOS-2000 itself does not use, the ICD prints a complete suggested structure, so that mission-specific implementations stay harmonised. These "grey" tables are not imported.8

    The Solar Orbiter MIB uses both mechanisms (see the tour below). Mission tailoring in general is covered in Mission tailoring of the MIB.

    Raw, engineering and encoded values¶

    Three words describe a parameter's value throughout the ICD, and the distinction matters for every table:2

    Term Meaning in the ICD
    Raw value For a monitoring parameter, the value before calibration. For a command or sequence parameter, the value after de-calibration. For a synthetic parameter, the output of its OL or hard-coded routine.
    Engineering value The calibrated value, for example a temperature in °C.
    Encoded value The actual bits carried in the TM or TC packet. SCOS-2000 encodes and decodes it automatically according to the parameter type, and never displays it.

    The raw value and the encoded value are identical only for unsigned integers. The ICD's own example: a 16-bit signed integer with raw value −1 has the encoded value 0xFFFF.2 The encoding rules for each type are on MIB parameter types.

    Names and identifiers¶

    When an item's unique ID is an alphanumeric string (typically up to 8 characters, such as a parameter name), the ICD calls it a name. When the ID is a number (such as a command verification stage), it calls it an identifier.2 Names must be unique regardless of letter case: A1000 and a1000 may not coexist, and the importer does not warn if they do. Spaces inside names are discouraged.7 Some names are reserved. Monitoring parameter names may not start with VAR, GVAR or $, because the Operations Language uses those prefixes to identify other kinds of objects. The prefixes NNO, CEB, KRU, MSP, VL2, PER, RED and MLG followed by four digits are reserved for ground-station telemetry.9

    From the off-line database to the run-time system¶

    The ICD describes a four-step activation process:1

    1. The mission's MIB is converted or exported from its off-line database system into ASCII files that follow the ICD.
    2. The ASCII files are copied to a directory that the SCOS-2000 importer can read.
    3. The importer converts them into the SCOS-2000 run-time database format and location.
    4. Each application that needs the data uses it after its next restart.

    Where missions get their MIB¶

    In practice, the MIB is generated from a larger engineering database that the spacecraft prime contractor or instrument team maintains. The sources in this wiki's library describe several such set-ups:

    • The ICD's own view. Appendix C notes that new housekeeping packets are best defined in the TM/TC database first, with the matching PUS service 3 commands then generated from that definition. ESA missions typically do this in a mission-specific "TM/TC database manager", not in the run-time SCOS-2000 kernel.67 The library sources do not name or describe a specific ESA database-manager product (such as a "DBM").
    • Satellite Reference Database (SRDB). A paper by Intecs and Thales Alenia Space Italia (the PDF carries no date; the newest document it cites is ICD issue 6.1 of 2006)17 notes that SCOS-2000 had become standard in ESA missions, so the SRDB holding all spacecraft data definitions was "almost always" based on the SCOS-2000 run-time database. Their SRDB Translator imports a SCOS-2000-compliant SRDB into the ECHO checkout system. It was first developed for Galileo GIOVE-B, whose SRDB was delivered as a single MS Access 2000 file, and was reused for Sentinel-1 and BepiColombo.1415 The paper also documents mismatches between data models. Two examples: SCOS-2000 numerical calibration curve IDs are Char(10), while ECHO uses integers from 1 to 9999. SCOS-2000 handles logarithmic curves, which ECHO originally did not.16
    • Solar Orbiter. The spacecraft TM/TC ICD states that on-board parameter IDs are defined in the SRDB and are frozen for a given central software (CSW) release.18
    • Herschel/Planck. The Herschel/Planck System Data Base (HPSDB), developed by GMV, kept data consistent between engineering, on-board software, AIT and flight operations.19 An Alcatel Alenia Space technical note describes how HPSDB ingested instrument MIBs written to ICD issue 5.1, and generated SCOS-2000 or Central Checkout System MIB files from its own object model. It lists the constraints that make a round trip loss-free. For example, the output files are sorted by the ICD primary keys, orphan items are not loaded, and every description field must be filled in.2021
    • Instrument teams. For the Herschel (then "FIRST") instruments, which used SCOS-2000 as EGSE, the HIFI team specified a MIB editor. It required one table per SCOS-2000 file and column names exactly as in the ICD, and it described the MIB as "more than 30 ASCII files".22 Their evaluation of ESOC's MS Access-based editor (the "Integral MS Access editor", version 2.0) shows typical problems. In the version they assessed, a polynomial curve could not be referenced from PCF_CURTX, and the VDF table was filled in automatically at export.23

    Tools and open-source libraries that read and write MIBs are collected in MIB tooling. The relationship between the MIB and the CCSDS XTCE exchange format and the ECSS monitoring and control data definition standard is discussed on those pages.

    Configuration identification in ECSS-E-ST-70-31C

    ECSS-E-ST-70-31C requires that any electronic database used to transfer monitoring and control data is under configuration management. The database must carry an identifier, a version number, a generation date, a supplier ID and a list of its files with checksums.24 In the MIB, the vdf table plays a comparable role for identification (see below), although the ICD defines no checksums.

    The file format¶

    Location and naming¶

    Each ASCII file holds exactly one table, which is why the ICD uses "ASCII file" and "ASCII table" interchangeably.2 The rules for files are:25

    • Each file is named after its table in lower case with the extension .dat, for example pcf.dat. The operating system is case sensitive, so the lower-case rule is binding, even though the ICD text writes table names in either case.2
    • SCOS-2000 can control several domains (separately managed entities). Each domain has its own set of ASCII files in a configurable directory, with sub-directories for the synthetic parameter files.
    • The General Domain also needs the files of every domain, plus its own small "multi-domain database". That database contains only multi-domain synthetic parameters.
    • Each dynamic synthetic parameter is defined in its own file. The file is named exactly after the parameter (PCF_NAME), without an extension, and contains the Operations Language (OL) expression.25 For dynamic OL parameters, the importer reads these files from the directory given by the MISCconfig variable IMPT_EXPR_DIR. SPEL-based parameters come from IMPT_SPEL_DIR.26 See Synthetic parameters and the OL language.

    Issue 5.1 gave the typical locations as /home/sops1/data/ASCII and /home/sops1/data/ASCII/SYNTHETIC. The multi-domain rules first appear in the later issues.27

    Record structure¶

    The record syntax is deliberately simple:106

    Rule Detail
    Line format Unix text files. One line per record. End of file is EOF. (The "Unix format" statement was added in issue 7.0, change S2K-7551.13)
    Field separator One TAB character. A mission may use a different separator, but the importer must then be reconfigured.
    Empty fields Every field must be present. A null field consists of its separator only, so two TABs in a row mean an empty field.
    Field order Fixed. It is the order of the "Fi. Nr" column in the ICD. Mission fields go after the last ICD field.
    Field length The lengths in the ICD are maxima. Shorter values are allowed. A longer value is truncated with a warning.
    Sorting Some tables have no position field, so their records must arrive sorted. The ICD says so for each table where this applies, for example "The VPD is expected to be sorted in VPD_TPSD and VPD_POS order".28

    Field types and value syntax¶

    Each field is declared either Number(n) or Char(n), where n is the maximum number of digits or characters.78

    • Number fields take integers only (signed or unsigned). In issues 6.7 Draft A, 6.9 and 7.0, integers may be written in decimal, hexadecimal or octal using the C++ convention. 0x12F4 is hexadecimal, 0767 is octal and 767 is decimal. Floating-point values must be written in decimal. Issue 5.1 still required decimal for everything unless a field said otherwise.83029
    • Char fields take alphanumeric ASCII characters (A–Z, 0–9) plus underscore, plus, minus, dot and dash. Other characters "shall be avoided".7
    • Some fields have no declared length. Their length depends on another limit. This is the case for command parameter values, whose size is bounded by the maximum allowed command size.7
    • A parameter value must use the syntax of its parameter type. Absolute times, for example, are written yyyy.ddd.hh.mm.ss (see parameter types).7

    Mandatory fields, defaults and presentation conventions¶

    The last column of every ICD table, "Ma/Def", is either M (mandatory: the field may not be null) or an import default, which the importer uses when an optional field is left null. An optional null field without a default is imported as null. All key fields are mandatory. The ICD stresses that an import default is not the same as a default proposed by an off-line database editor.8

    Fields whose position number carries an asterisk (1*) are table keys. The table may contain only one record for each combination of key values. The ICD's example: plf is keyed on PLF_NAME and PLF_SPID, so one parameter can appear only once in a given packet.7 The data model page lists the keys of every table.

    The printed ICD also uses typography as a signal:78

    • a grey row marks a field that SCOS-2000 never uses. Such fields usually exist for the off-line consistency checker or for historical reasons;
    • italics mark options or fields that SCOS-2000 does not support yet;
    • a whole grey table is not imported at all. It is printed as a suggested structure for mission-specific applications.

    A real record, field by field¶

    The first record of pid.dat in the Solar Orbiter MIB released on 2025-09-16, with each TAB shown as →:31

    0→0→1→0→0→1000002→Bad complete transfer frame→→-1→0→N→→Y→1→N→

    Read against the 16 fields of the ICD's pid table, this is: PID_TYPE=0, PID_STYPE=0, PID_APID=1, PID_PI1_VAL=0, PID_PI2_VAL=0, PID_SPID=1000002, PID_DESCR="Bad complete transfer frame", PID_UNIT empty, PID_TPSD=−1 (not a variable packet), PID_DFHSIZE=0, PID_TIME=N, PID_INTER empty, PID_VALID=Y, PID_CHECK=1, PID_EVENT=N, PID_EVID empty. The record ends with a TAB followed by the newline. TYPE=STYPE=0 is the ICD's convention for a packet that is identified by APID alone.32 Two other ground-frame packets (SPIDs 1000003 and 1000006) use the same lookup key and are also flagged valid, which the ICD resolves at import by keeping only the last valid record (see data model).3133 All .dat files of this release use LF line ends only and contain nothing but printable ASCII and TABs.31 The SWA instrument database is different: all 20,552 lines of its .dat files end in CR LF (DOS line ends), although issue 7.0 states that the files are in Unix format.4510

    Import: checks and options¶

    What the importer checks¶

    The importer is designed to catch only "the most dangerous inconsistencies", not every possible one. Ensuring consistency is the job of the off-line database system. From R4.0 an off-line consistency checker is delivered with the SCOS-2000 test environment.34 The checks and their effects are:35

    Check Effect when it fails
    Field characteristics (type, length) against the ICD Warning (if the warning flag is set when the import is launched). A field that is too long is truncated.
    Mandatory field (M) left null Warning. The value is set to 0 for numbers and to an empty string for strings.
    Relational integrity (for example, a reference to a parameter that does not exist) The record is not imported, with a warning.
    Syntax of command and sequence parameter values against their type Warning. The value is replaced by 0 (integers, reals, delta times), an empty string, or 1970.001.00.00.00 (absolute times).

    All importer messages go to an ASCII log file that is overwritten at each import. The ICD gives the path /home/sops1/Import.log.35 The vdf table is explicitly declared mandatory: vdf.dat must exist in the import directory with at least one record.36

    Import options¶

    Issue 7.0 lists two options:37

    • Full database import (default). This builds a completely new internal database. It can target one domain via a command-line domain identifier. From a specific domain only that domain's database can be imported. From the General Domain any domain, including the multi-domain database, can be imported. The importer cross-checks the domain identifier in vdf against this option.36
    • Check only. This changes nothing and only reports the results of the structure and field-length checks.

    Issue 5.1 also offered "Monitoring tables only", "Commanding tables only" and "Selected tables only".38 The 7.0 change log records their removal from §2.5, because the evolution line of SCOS-2000 did not support them.4

    Sequences and displays live in the FARC (from R5.0)¶

    From SCOS-2000 release 5.0, command sequence and TM display definitions are no longer loaded into the run-time ("POST") database. On user request, the importer converts the relevant ASCII tables into XML files and stores them in the FARC (File Archive79; see Mission archives). Command sources and the TM desktop then load the definitions from there.11 This has two consequences:11

    1. Sequences and displays can be updated without importing a new version of the whole TM/TC database.
    2. The conversion is a delta import. Only the definitions present in the delivered files are updated, and existing definitions in the FARC are kept. Displays created in the TM desktop editor survive a re-import as well.39

    The ASCII tables affected are csf, css, sdf and csp for sequences, and dpf/dpc, gpf/gpc and spf/spc for displays.1139 The XML formats are specified in two separate ICDs: ICD-0051 for TC sequences and ICD-5001 for TM displays and printouts.40

    The database version: vdf¶

    vdf names the database version. If it holds several records, the last one imported sets the internal name and description. The version name is shown on displays and used to make sure, for example, that a saved command stack is loaded against the same database version that created it.36

    # Field Type Meaning Default
    1 VDF_NAME Char(8) Name of the database version M
    2 VDF_COMMENT Char(32) Free comment —
    3 VDF_DOMAINID Number(5) Domain identifier (0 to 2^16−1). If null, the local domain is assumed. —
    4 VDF_RELEASE Number(5) Database release (0 to 2^16−1) 0
    5 VDF_ISSUE Number(5) Database issue (0 to 2^16−1) 0

    Fields 3 to 5 appeared with SCOS-2000 R4.0 (ICD 6.0). Issue 5.1 has only VDF_NAME and VDF_COMMENT.364142

    The real data shows two quite different styles:

    • Solar Orbiter delivers one record per release. The 2025-09-16 MIB has VDF_NAME=25925PFM, VDF_COMMENT=20250916-CSW3.1.2_MAS7.33, domain 0, release 25925, issue 733. The 2020-04-16 MIB has 10720PFM, 20200416-CSW3.0.3p1_MAS6.51, 0, 10720, 651.3143
    • The SWA instrument database uses vdf as a release history with 70 records, from SWA_00.2 ("Received from MSSL") to SWA_6.3.4 ("Released on 29/11/2021"). By the ICD rule only the last record counts. 67 of the 70 names are longer than Char(8), the longest having 14 characters, so the SCOS-2000 importer would truncate them with a warning.4535

    Inference

    In the Solar Orbiter VDF, the number at the start of VDF_NAME (25925, 10720) repeats VDF_RELEASE, and the suffix of the comment repeats VDF_ISSUE (MAS 7.33 → 733). "CSW" matches the Solar Orbiter abbreviation for Central Software.46 What "MAS" stands for is not stated in the available sources.

    Special kinds of monitoring parameter¶

    Not every row in pcf is a parameter extracted from spacecraft telemetry. The field PCF_NATUR gives the parameter's nature:56

    PCF_NATUR Nature Where the value comes from
    R Raw telemetry parameter (also a "dynamic" user-defined constant) Extracted from TM packets using plf or vpd
    D Dynamic OL synthetic parameter Evaluated from an OL expression file
    P SPEL-based dynamic synthetic parameter Evaluated from a SPEL file. Only in the EGSE delivery of SCOS-2000.26
    H Hard-coded synthetic parameter C++ code linked into SCOS-2000
    S Saved synthetic parameter Computed centrally by the SPPG and stored in "synthetic packets"
    C Constant ("static" user-defined constant) PCF_PARVAL

    The MIB also describes packets that SCOS-2000 generates itself, because they are processed like spacecraft telemetry and so need pid, tpcf and plf entries:57

    • the constants TM packet carrying the dynamic user-defined constants, which operators set through TM SPACON;58
    • the MISC packet, in which the MISC server publishes selected dynamic configuration variables as pseudo-telemetry. These must be typed as 32-bit signed integers (PTC 4, PFC 14), double reals (5/2) or character strings (8/n);59
    • synthetic packets, which hold the saved synthetic parameters. Each one occupies a 13-byte slot in its packet;60
    • system control packets of the SCTL application. A tool, SCTLgenerateMIB, appends default entries for them to the MIB ASCII files.61

    The Solar Orbiter MIB defines exactly such packets on APID 1966, with mission-specific type numbers between 160 and 166 and 251. Examples are SPID 66830 "Dynamic UDCs" (160/3), 66832 "MISC_PACKET" (160/5), 66838 "Saved Synthetics" (251/2) and 66840 "Time Correlation Report" (164/1). It also defines packets with APIDs from 2048 to 2065, named "LMS_CEB", "LMS_MLG" and "LMS_NNO". That APID range is the one the ICD reserves for packets not generated by the spacecraft.3162 In packet 66838, the two saved synthetic parameters NTTSS030 and NTTSS031 sit at byte offsets 0 and 13, which matches the 13-byte slot rule.3160

    SCOS-2000 and the PUS services¶

    Appendix C of the ICD (added in issue 6.7, change S2K-DCR-5303) states how far SCOS-2000 supports the Packet Utilization Standard, and therefore what a MIB can describe.63 In general, SCOS-2000 can decode and encode every PUS packet type and subtype, within the limits on data types and structures described on MIB parameter types. However, it adds special processing for only a few services:64

    PUS service Specific SCOS-2000 support and notable limitations (ICD 7.0 Appendix C)
    1 Verification The verifier matches reports to commands through the 4 echoed header bytes, which must be at the same position in every type-1 packet. The subtype-to-stage mapping is mission-wide. Progress reports map only to progress step 0. Failure codes are ignored.65
    2 Device access No specific processing. Commands can be blocked at TC segment level, but not aggregated inside one packet.66
    3 Housekeeping No specific processing. Every packet must already be in the MIB before it is enabled on board. Sample time offsets and generation intervals are static in the MIB.67
    4, 12 All reports are variable packets, so the variable-packet limitations apply (see below).68
    5 Event reporting Any TM packet can raise a SCOS-2000 event with a severity and message (PID_EVENT, PID_EVID).68
    6 Memory management Handled by the OBSM subsystem. The packet structures are mission-specific.69
    9 Time management Time reports feed time correlation (generic from R5.2).70
    11 Time-based scheduling Automatic wrapping in TC(11,4), a ground model of the on-board schedule and delayed verification. The packet structure follows Rosetta. Absolute time tags only.71
    13 Large data transfer Not supported generically. Needs a mission-specific implementation.72
    15 On-board storage No modelling of on-board stores. Packets wrapped in (15,8) are not unwrapped.72
    19 Event-action Easier to define with "Command ID" parameters, but the embedded TC uses fixed header values.73

    The variable-packet limitation applies throughout. Values extracted from variable packets (vpd) do not take part in full TM processing: validity, monitoring checks, validation/verification and synthetic parameters. The reason is that their identity and time reference become known only when the packet is opened. The ICD therefore advises against using variable packets for regular housekeeping.74 Solar Orbiter's use of PUS is described in How Solar Orbiter uses PUS.

    Some observations from these numbers:

    • Scale. The 2025 release defines 126,745 monitoring parameters and 11,150 TM packet types on 293 distinct APIDs, located by 400,792 plf records. It also defines 5,454 telecommands and 3,404 command sequences.31
    • Fixed and variable packets. 9,056 of the 11,150 packets have a fixed layout in plf, and 2,063 have a variable layout in vpd (a TPSD other than −1). No packet has both, and 31 have neither.31
    • Growth. Between April 2020 and September 2025, the number of parameters grew by 24,641 (24,801 names added, 160 removed), packets by 2,123 (2,135 SPIDs added, 12 removed) and commands by 216 (239 added, 23 removed). The number of sequences grew by 703 (790 added, 87 removed) and the number of sequence elements (css) by 53%.3143
    • Unused features. Solar Orbiter defines no logarithmic calibrations, no parameter sets and no graphic displays. The 2025 release declares one parameter group (GRPPAR, "Example for Parameters") but gives it no members (grpa is empty). The only populated group is the packet group GRPHK with 4 packets. Only five static pre-transmission checks exist, all added after 2020.3143
    • Parameter natures. In 2025, 125,161 parameters are raw telemetry (R), 1,582 are dynamic OL synthetics (D) and 2 are saved synthetics (S). The release ships 1,582 synthetic parameter files, one per D parameter.31

    Inference

    From the column contents, ASW_sw_para appears to map MIB names to on-board software symbol names, and the s13* files appear to configure large-packet or file transfer categories.     Where the real data departs from the ICD¶

    Real MIBs are not always fully within the ICD limits. Two examples from the 2025 release:

    • CCF_DESCR is Char(24) in the ICD,77 yet 2,876 Solar Orbiter commands have longer descriptions, up to 40 characters.31 A standard SCOS-2000 importer would truncate them with a warning, which for a display-only text has no further effect.35 How Solar Orbiter's own ground tools handle the longer field is not stated in the available sources (see tailoring).
    • The header layout NOM_TC uses a pcdf element type O for its "Source ID" field, linked to a header parameter DFH_SRC. ICD 7.0 lists only the types F, A, T, S, K and P.7831 In the 2020 release the same field was still a fixed area (F, value 0), and DFH_SRC did not exist in pcpc.43 See the data model page.

    Referential integrity is otherwise very good. All 400,792 plf records point to an existing packet, and all but one point to an existing parameter. The exception is NYM0796V in SPID 66028.31
