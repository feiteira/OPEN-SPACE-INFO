    MIB PUS SCOS-2000 Solar Orbiter Telecommand Verification

    Command verification in the MIB¶

    Releasing a telecommand is only the start. The flight control team needs to know, for every command, whether the ground station received it, whether it was radiated, whether the spacecraft received the frame, whether the addressed application accepted the packet, and whether the action actually took effect. SCOS-2000 tracks each command through these verification stages and shows their status in the command history. The ground stages are driven by the NCTRS and the COP-1 protocol. The on-board stages, called command execution verification, are defined per command in three MIB tables: cvs (what a stage is), cve (which telemetry values prove it) and cvp (which stages a command has).12 This page explains those tables, how SCOS-2000 combines them with the reports of PUS ST[01] request verification, and how the Solar Orbiter MIB uses them. The command definitions themselves are on Commanding in the MIB.

    Two kinds of check¶

    SCOS-2000 supports two kinds of verification check:1

    • Report-based checks rely on dedicated telemetry packets that report the success or failure of an execution stage, that is the PUS Service 1 reports.
    • Parameter-based checks compare the value of one or more monitoring parameters with a criterion, for example "the converter status reads ON".

    A stage is defined once in cvs and can be shared by many commands; the many-to-many relationship with commands is resolved by cvp. A parameter-based stage owns one or more expressions in cve, which are ANDed. cve has a second job: it names the parameters that a command is expected to change, so their status consistency checking can be suspended while the command executes.2 Verification of sequences is foreseen by the table design but not supported by SCOS-2000 at issue 7.0.1

    erDiagram
    CCF ||--o{ CVP : "CVP_TASK"
    CVS ||--o{ CVP : "CVP_CVSID"
    CVS ||--o{ CVE : "CVE_CVSID (source V only)"
    PCF ||--o{ CVE : "CVE_PARNAM"
    CDF ||--o{ CVE : "echo value (CVE_INTER C)"
    PID }o--o| CVS : "CVS_SPID"

    The relationships follow the field definitions of the three tables in ICD 7.0.61113

    The stages of a command's life¶

    The ICD names five stages that an interlock can wait for: reception at the ground station (R), uplink, also called radiation or transmission (U), on-board reception, also called transfer and the final uplink verification (O), application acceptance (A) and completion (C). When commanding in BD mode O is automatically handled as U; the Rosetta/Mars Express command history likewise marks on-board reception as applicable only in AD mode.336 The on-board side adds start of execution and up to ten progress steps.6

    Stage Name in TC history Evidence (summary) Defined in
    Release R Command passed PTV and was handed to the NCTRS (or SLE user) SCOS-2000 itself
    Ground station reception (1st uplink stage) G (CRV) Station TC front-end reports the command received NCTRS
    Uplink / radiation (2nd uplink stage) T (CSV) Station TC front-end reports the command sent NCTRS
    On-board reception / transfer (3rd uplink stage, AD only) O (CUV) CLCW verification of the transfer frame COP-1 via NCTRS
    Application acceptance A (CAV) TM(1,1)/(1,2) or parameter check cvs type A
    Start of execution SS TM(1,3)/(1,4) or parameter check cvs type S
    Progress step 0–9 1122… TM(1,5)/(1,6) (step 0 only) or parameter check cvs type 0–9
    Completion of execution C (CEV), CC TM(1,7)/(1,8) or parameter check cvs type C

    The history letters and abbreviations come from the command history descriptions of the Rosetta/Mars Express control system and of the EDDS external user ICD (version 24.0), which also shows that the execution stages are tracked twice, once from real-time and once from playback telemetry.3637 The SCOS-2000 EGSE manual describes the three uplink acknowledgements as returned by the ground station or SCOE TC front-end on reception, on sending in BD mode, and on the spacecraft's confirmation in AD mode.9 CRV, CSV, CUV, CAV and CEV are the stage abbreviations of the Rosetta/Mars Express document (the EDDS ICD uses only the letters); CUV is described there as the CLCW verification of the transfer frame.3436

    Background: PUS Service 1¶

    ECSS-E-ST-70-41C defines ST[01] request verification with three subservices: routing and reporting, acceptance and reporting, and execution reporting. The acceptance subservice checks a request before it is passed to the service that executes it; the execution reporting subservice issues reports on behalf of that service when it notifies start, progress or completion of execution.21 Each request carries four flags that ask for the successful acceptance, start, progress and completion reports; a failure is always reported.2223

    Report PUS-C name Generated when
    TM[1,1] successful acceptance verification report acceptance passed and the acceptance flag is set
    TM[1,2] failed acceptance verification report acceptance failed (always)
    TM[1,3] / TM[1,4] successful / failed start of execution flag set / always
    TM[1,5] / TM[1,6] successful / failed progress of execution flag set / if configured for the request type
    TM[1,7] / TM[1,8] successful / failed completion of execution flag set / always
    TM[1,10] failed routing verification report a routing check failed (PUS-C only)

    232425

    In ECSS-E-ST-70-41C the flags occupy the 4-bit acknowledgement field of the TC secondary header: bit 3 for acceptance, bit 2 for start, bit 1 for progress and bit 0 for completion.26 PUS-A (ECSS-E-70-41A), which Solar Orbiter follows, uses the same assignment and states that the Ack field also tells the ground which stages to expect, so it can show "packets uplinked but not yet verified".28 In the MIB the default value of the field is CCF_ACK, a decimal number from 0 to 15; 9 means acceptance plus completion.5

    Every report starts with a copy of the request's packet ID and packet sequence control, which together identify the request. Failure reports add a failure code and optional data; progress reports add a step number.2729

    The Solar Orbiter TM/TC ICD defines these reports with 2-byte packet ID, 2-byte sequence control and, for failures, a 2-byte failure ID followed by optional parameters.32 PUS-A defines six standard acceptance failure codes: 0 illegal APID, 1 incomplete or invalid length, 2 incorrect checksum, 3 illegal packet type, 4 illegal packet subtype, 5 illegal or inconsistent application data.29 The service in general is covered on ST[01] Request verification.

    How SCOS-2000 uses Service 1 reports¶

    Appendix C of the ICD states how the SCOS-2000 verifier handles Service 1:16

    • It extracts the four bytes that echo the TC packet header (packet ID and sequence control) from each Service 1 packet and uses them to find the command instance. The four bytes must be at the same position in all type 1 packets.
    • The mapping of subtypes to stages is static configuration (subtype 1 is typically success of the acceptance stage) and is the same for every command of the mission.
    • Progress reports (subtypes 5 and 6) can only feed progress step 0; further steps must be parameter-based.
    • The failure code of negative reports is ignored; only the subtype tells the verifier that a stage failed.
    flowchart TD
    A["TM packet of service type 1 arrives"] --> B["Read 4 echo bytes:<br/>TC packet ID + sequence control"]
    B --> C{"Released command<br/>with this ID?"}
    C -- no --> X["Not used for verification"]
    C -- yes --> D["Map subtype to stage<br/>(mission-wide static table)"]
    D --> E{"Stage in the command's<br/>verification profile (cvp)?"}
    E -- no --> X
    E -- yes --> F{"Success or failure<br/>subtype?"}
    F -- "1, 3, 5, 7" --> P["Stage PASSED"]
    F -- "2, 4, 6, 8" --> Q["Stage FAILED<br/>(failure code ignored)"]

    The flowchart restates the Appendix C rules; the exact matching order inside the verifier is not stated in the available sources.16

    Inference

    Because the request ID in a report does not contain the source of the request, PUS-C notes that the destination ID of the report's secondary header is needed to identify the request uniquely.27 SCOS-2000 as described in ICD 7.0 matches only on the 4 echo bytes. A ground system that runs several command sources with independent sequence counters for the same APID could therefore see ambiguous matches; how SCOS-2000 avoids this is not stated in the available sources. The Solar Orbiter TM/TC ICD asks for the TC sequence count to be maintained per APID and Source ID, which makes such duplicates possible in principle on that mission.30

    cvs: verification stages¶

    cvs has one record per stage; the same stage may be used by many commands.6

    # Field Type Meaning and values Default
    1* CVS_ID Number(5), M Unique stage identifier, 0–32767
    2 CVS_TYPE Char(1), M Stage in the execution profile: A application acceptance, S start of execution, 0–9 progress step n, C completion
    3 CVS_SOURCE Char(1), M R based on TM report packets; V based on monitoring parameter values checked against cve
    4 CVS_START Number(5), M Seconds after release (after execution for time-tagged commands) before the verification window opens
    5 CVS_INTERVAL Number(5), M Seconds; length of the sampling interval used to compute the overall verification window
    6 CVS_SPID Number(10) SPID of the TM packet whose arrival closes the stage after the window (future extension; source V only)
    7 CVS_UNCERTAINTY Number(5) Seconds; stage-specific window replacing the default window of the TC SPACON; -1 keeps the default -1

    67

    Two constraints shape every profile. The verifier processes TM(1,5) progress reports only for stage 0, so a report-based progress stage can only have CVS_TYPE = 0; this is a limitation of the SCOS-2000 Service 1 implementation.6 And a command may have at most one stage of each CVS_TYPE, so only one acceptance stage and one completion stage.13

    Without CVS_SPID, a parameter-based stage closes as soon as any valid sample of any of its parameters arrives with a time stamp during or after the window closure time. That is why the ICD recommends taking all parameters of one stage from the same TM packet.710

    The window formula is not in the ICD

    The ICD says that CVS_INTERVAL is used to calculate the overall verification window "as specified in [AD-2]", the SCOS-2000 Commanding SRD (SRD-0002). That document is not among the available sources, so the exact formula is not stated here.718

    cve: verification expressions¶

    cve has one record per check. All checks of one stage are ANDed, and only stages with CVS_SOURCE = V may have checks.1011

    # Field Type Meaning and values Default
    1* CVE_CVSID Number(5), M Stage (CVS_ID, source V)
    2* CVE_PARNAM Char(8), M Monitoring parameter with a numerical raw value, processed by the TM model (in plf or synthetic)
    3 CVE_INTER Char(1) R raw values (for synthetics, the OL output); E engineering values (calibrated parameters only); C CVE_VAL names a command parameter whose value is echoed, CVE_TOL raw R
    4 CVE_VAL Char(17) Expected value, decimal if raw; for C, the command parameter name (first instance if it repeats). Only used if CVE_CHECK = B
    5 CVE_TOL Char(17) Tolerance: the check passes if the parameter lies within CVE_VAL ± CVE_TOL. Must be null for engineering checks of status parameters
    6 CVE_CHECK Char(1) B used for verification and for status consistency checking (the value becomes the new expected value at the end of the window); S only suspends status consistency checking, and only alongside a B check of the same stage B

    1112

    The ICD adds several consistency rules:101112

    • The validity of the parameter is part of the check: a check passes only if the parameter is valid and satisfies the criterion.
    • For a parameter subject to status consistency checking (PCF_USCON = Y) the representation in CVE_INTER must match that of its out-of-limits checks (OCF_INTER); echo checks then require raw OOL checks.
    • A parameter must use the same representation in every cve record; engineering is allowed only if all its records use it.

    Echo verification (CVE_INTER = C) compares telemetry with the value the operator actually gave to a command parameter, for example a commanded set point, so one stage definition can serve every value of the command.11 Status consistency checking compares the valid value of a parameter, typically a status affected by commanding, with a reference value that SCOS-2000 maintains from the predicted or detected effect of commands.8 The cve records of a command tell SCOS-2000 which parameters to leave alone during the window and, with CVE_CHECK = B, what the new reference is afterwards. See Monitoring checks.1012

    cvp: verification profiles¶

    cvp attaches stages to commands, one record per stage of a command.13

    # Field Type Meaning Default
    1* CVP_TASK Char(8), M Command (CCF_CNAME) or sequence (CSF_NAME)
    2* CVP_TYPE Char(1) C command; S sequence (not supported) C
    3* CVP_CVSID Number(5), M Stage (CVS_ID); at most one per CVS_TYPE

    Since SCOS-2000 R4.0 an operator can disable a report-based stage when loading a command, by clearing the corresponding acknowledgement flag. The mechanism can only switch off stages that are already in the profile; it cannot add one. Every command for which the receiving application generates a Service 1 report must therefore have the matching stage in cvp.13

    The interlock stage of a command (CCF_ILSTAGE, overridable per sequence element with CSS_ILSTAGE) is checked against the profile on import: if it asks for an execution stage the profile does not have, the importer replaces it with the highest stage that applies.3

    Stage status and the verification window¶

    SCOS-2000 reports each stage with a status. The Rosetta/Mars Express data delivery ICD encodes it in a 16-bit word per stage with exactly one bit set (bit 0 is the least significant bit); an all-zero word means the stage did not apply, because it was not in the database or was disabled before release.35

    Only PASSED, FAILED and UNVERIFIED are final; a command is complete when all its stages are final.35

    stateDiagram-v2
    [*] --> IDLE: command released
    IDLE --> PENDING: window opens (CVS_START)
    PENDING --> PASSED: report or parameter check succeeds
    PENDING --> FAILED: failure report or check fails
    PENDING --> UNKNOWN: window closes, no applicable TM
    UNKNOWN --> UNVERIFIED: consolidated by controllers
    PENDING --> TIMEDOUT: CUV only, no CLCW in time
    PENDING --> ASSUMED: CUV only, later CAV or CEV passes
    TIMEDOUT --> ASSUMED: later CAV or CEV passes
    PASSED --> [*]
    FAILED --> [*]
    UNVERIFIED --> [*]

    The state diagram is this wiki's rendering of the status definitions; the source defines the statuses, not the transitions.35 The EDDS TC report, whose ASCII layout follows the Command History application of SCOS-2000 5.⅗.4, lists more statuses: Fail, Unverified, Unknown, Pending, Time-out, Success, Idle, Assumed Passed, Affected, Uncertain Successful, Uncertain Failed and Superseded, plus "D" for execution stages of a time-tagged command disabled at execution and "DELETED" for a time-tagged command deleted before execution.37

    For time-tagged commands CVS_START counts from the execution time instead of the release time.6 SCOS-2000 supports this delayed verification from live and from playback telemetry, but playback data must arrive in chronological order for parameter-based verification to work.17

    Verification data stays with the command

    The command history must remain readable after the MIB has changed. In the Solar Orbiter control system each released command is archived as a SCOS-2000 TC packet that holds the static MIB information (mnemonic, parameters, verification details) and the dynamic status of the verification checks. A separate packet with SPID 200 stores the PTV/CEV details of each command, such as the expected values of parameter-based checks.38 See Mission archives and EDDS.

    Interlocks¶

    An interlock holds back further commanding, within its scope, until the chosen stage of the interlocking command has been verified; the ICD calls this the WAIT state. Its scope is CCF_ILSCOPE (or CSS_ILSCOPE in a sequence) and its stage CCF_ILSTAGE (or CSS_ILSTAGE):314

    Scope Effect (ICD 7.0) EDDS TC report label
    G Interlocks the whole system Wait-Fail Global
    L Interlocks only the local command source Wait-Fail Local
    S Interlocks local commanding of the command's subsystem Wait-Fail Subsystem Local
    B Interlocks global commanding of the command's subsystem (not listed)
    F Local source, only on verification failure (no WAIT state) Fail-Only Local
    T Subsystem-local, only on verification failure Fail-Only Subsystem Local
    N No interlock

    337

    The ICD's recommendation for BC frames illustrates the use: a global interlock at the uplink stage ensures that no further command leaves before the AD set-up directives have gone through.4 Within a group or block of a sequence, the scopes G and L are allowed only on the last command.14 Group and block semantics are on Command sequences and parameter sets.

    Solar Orbiter: the verification set-up¶

    The September 2025 Solar Orbiter MIB has 206 stages, 171 expressions and 10,697 profile records, the same number of stages and expressions as the April 2020 release (which had 10,277 profile records).4142

    Kind CVS_TYPE / CVS_SOURCE Stages
    Acceptance by report A / R 16
    Completion by report C / R 23
    Completion by parameter check C / V 167

    41

    No start or progress stage exists, which matches the Solar Orbiter rule that the start and progress acknowledgement bits are always zero.4131 The same ICD describes 0001 as "acceptance success or failure" with no TM(1,7) or TM(1,8), and 1000 as execution success or failure with no TM(1,1) or TM(1,2), so on Solar Orbiter the two remaining bits select which report stages exist at all, not only whether success is reported.31 Every stage opens its window immediately (CVS_START = 0) and no stage overrides the default window (CVS_UNCERTAINTY is never set). All 167 parameter-based stages use CVS_INTERVAL = 60 s and each is used by exactly one command.41

    Profiles agree with the acknowledgement flags¶

    Grouping the 5,454 commands by the shape of their profile and by their default Ack value shows a consistent design:41

    Profile Commands CCF_ACK Typical commands
    Acceptance report + completion report 5,225 9 (1001) almost all PUS commands
    Acceptance report + completion by parameters 78 1 (0001) TC(2,128) power commands such as ZPW04604
    Completion by parameters only 89 null 88 CPDU (HPC1_TC) commands and REIN_TTR
    No verification 62 0 (21) or null (41) 6 NIS throw events, 7 FDIR TC-file executions, 8 instrument commands (7 EUI ZID…, ZIM02028), 37 CPDU commands, RESET, SETVR, TC_ONLY, UNLOCK

    Two more cvp records point at a command, ZCSD2005, that does not exist in ccf.41 The CPDU commands have no data field header and hence no Ack field, so they cannot ask for Service 1 reports; they can only be verified through telemetry.4130

    Report-based stages¶

    60001 / 60007 and 70001 / 70007 20 / 20 45 each 652 and 668 (40, 41: star trackers A and B)

    4133

    Several instruments have more than one completion stage, differing only in the interval, so that long-running commands get a longer window: EUI's 51927 allows 36,000 s (10 hours) for 19 commands, STIX's 54004 allows 9,999 s for 16.41

    CVS_SPID on report-based stages

    The ICD says CVS_SPID may only be given for parameter-based stages and is irrelevant for report stages.7 In the Solar Orbiter MIB it is empty on every parameter-based stage, but set on 20 report-based ones. Some values point at the instrument's own TM(1,1) and TM(1,7) packets (MAG 50001/50010, STIX 54001/54013), others at SPID 20000, which is an unrelated TM(5,1) event packet "CPS_Activation_Ended", and stages 14001/14007 carry 0.41 The SWA instrument database gives its two stages 58901/58907 the same value 20000.45 The Herschel/Planck System database (HPSDB) forced the field to null on output.39

    Inference

    Since the ICD calls CVS_SPID a future extension and the values found are inconsistent, the field is most likely ignored by the Solar Orbiter control system for report-based stages. This is not stated in the available sources.

    How failure reports are identified¶

    The verifier only looks at the subtype of a failure report, but the MIB still describes each failure code separately. The packet identification criteria (pic) give TM(1,2) and TM(1,8) an additional identification field at byte 20 of the packet, 16 bits wide, while TM(1,1) and TM(1,7) need none. Across 29 report APIDs the MIB defines 29 TM(1,1), 274 TM(1,2), 29 TM(1,7) and 1,477 TM(1,8) packets.44 For example the platform report APID 161 (process ID 10, category 1) has TM(1,2) SPID 14068 "Illegal CCSDS packet version number" for code 256 and SPID 14064 "Illegal packet type" for code 257.4433 See Monitoring in the MIB for pid and pic.

    Inference

    Byte 20 is where the failure ID follows the 4 echo bytes in the Solar Orbiter report layout, so each failure code becomes its own packet type with a readable description. Operators therefore see why a command failed even though the verifier itself ignores the code. This reading combines the pic data with the report layout; neither source states it.

    Parameter-based examples¶

    ZPW04604 "PCDU A BDR1_C1 SwitchON" (the worked example on Commanding in the MIB) has stages 11 (acceptance report) and 32. Stage 32 is a completion check with one expression: NPWD0753 "IFA_BDR1_Conv1_ST" must equal raw 1 with tolerance 0, within a 60 s window.43 Its CCF_ACK is 1, so the spacecraft sends only the acceptance report and the completion is proven by telemetry.43

    ZBC04001 "Select PM A EEPROM Image 1", a CPDU command, has a single stage 9000: parameter NCDD05GE "PM A Image select status" must read IMAGE_1 in engineering form.43

    Stage 9082, used by ZBC06011 "RIU Ctrl-A On", has two expressions, ANDed: NCD2Z003 "OBCA RIU A Status A" and NCD2Z00U "OBCA RIU A Status B" must both read On. Four stages of the MIB have two expressions; the other 163 have one.4341

    Stage 84, for ZPW04300 "PCDU A EOC 25.200 V Set", checks the synthetic parameter NPWSX001 for raw 1. Its OL source returns 1 when at least two of three voltage readings (NPWD5012, NPWD5013, NPWD5014, engineering values) lie strictly between 25.1 and 25.3, a two-out-of-three vote that a single cve comparison could not express.43 Of the 171 expressions, 25 use dynamic synthetic parameters (PCF_NATUR = D) and 146 use status parameters acquired from telemetry (PCF_NATUR = R, PCF_CATEG = S); 90 are engineering and 81 raw; all use CVE_CHECK = B, none uses echo verification, and none of the parameters is status-consistency checked.41 See Synthetic parameters and the OL language.

    Turning verification off in sequences¶

    Sequence elements can disable the CEV checks of a command with CSS_CEV = Y.15 Solar Orbiter does this for 17 elements, all in two sequences that define on-board TC files: AACC362D "Define SNAFU TCF v02" and ATTC810F "Def LossOfUL REC TCF v02".41

    Inference

    Commands written into an on-board TC file are stored for later execution, not executed at once, so their normal execution checks would fail or time out. Disabling CEV for exactly these elements fits that explanation, which is not stated in the available sources.

    How the verification tables evolved¶

    ICD issue Change
    6.0 (R4.0) Acknowledgement flags can be changed at load time, disabling report-based stages
    6.1 CVS_TYPE/CVS_SOURCE clarified: report-based progress stages only for step 0 (S2K-40-DCR-0821)
    6.7 (R5.2) CVS_UNCERTAINTY added to override the TC SPACON window (S2K-SCR-3774); CVS_ID restricted to a signed short (S2K-DCR-3909)
    6.9 CVE_CVSID and CVP_CVSID lengths aligned with CVS_ID as Number(5); CVS_UNCERTAINTY description updated (S2K-NCR-5531)

    1920

    The Solar Orbiter SWA instrument database still uses six-field cvs records (without CVS_UNCERTAINTY) and defines only the two stages 58901 and 58907, for all 198 of its commands.45 Other projects attached meaning to stage numbers; the Herschel/Planck System database (HPSDB), for example, coded specific stages with four digits and generic ones as 1xxxx.40 More on mission conventions in Mission tailoring of the MIB.

    SQL used

    Queries ran with sqlite3 -readonly on this wiki's SQLite copy of the Solar Orbiter MIB (solo-2025-09-16.sqlite). The three verification tables are not in the automatic schema, so their columns are COL1..COLn in file order. From the ICD field order: cvs COL1 CVS_ID, COL2 CVS_TYPE, COL3 CVS_SOURCE, COL4 CVS_START, COL5 CVS_INTERVAL, COL6 CVS_SPID, COL7 CVS_UNCERTAINTY; cve COL1 CVE_CVSID, COL2 CVE_PARNAM, COL3 CVE_INTER, COL4 CVE_VAL, COL5 CVE_TOL, COL6 CVE_CHECK; cvp COL1 CVP_TASK, COL2 CVP_TYPE, COL3 CVP_CVSID.

    SELECT COL2 AS type, COL3 AS source, count(*) FROM cvs GROUP BY 1, 2;
SELECT COL4, COL5, count(*) FROM cvs GROUP BY 1, 2 ORDER BY 3 DESC;
SELECT * FROM cvs WHERE COL6 <> '' ORDER BY cast(COL1 AS int);
-- profile shape per command, against the default Ack flags
SELECT c.CCF_ACK, ifnull(prof, '(none)'), count(*)
  FROM ccf c LEFT JOIN (SELECT p.COL1 AS cmd, group_concat(s.COL2 || s.COL3, '+') AS prof
                          FROM cvp p JOIN cvs s ON s.COL1 = p.COL3 GROUP BY p.COL1) x
    ON x.cmd = c.CCF_CNAME
 GROUP BY 1, 2;
-- report-based stages, their users and APIDs
SELECT s.COL1, s.COL2, s.COL5, s.COL6, count(p.COL1), group_concat(DISTINCT c.CCF_APID)
  FROM cvs s LEFT JOIN cvp p ON p.COL3 = s.COL1 LEFT JOIN ccf c ON c.CCF_CNAME = p.COL1
 WHERE s.COL3 = 'R' GROUP BY s.COL1 ORDER BY cast(s.COL1 AS int);
-- expressions
SELECT e.*, f.PCF_DESCR, f.PCF_NATUR, f.PCF_USCON FROM cve e LEFT JOIN pcf f ON f.PCF_NAME = e.COL2;
SELECT SOURCE FROM synthetic WHERE NAME = 'NPWSX001';
-- Service 1 packets and their identification
SELECT * FROM pic WHERE PIC_TYPE = '1';
SELECT PID_STYPE, count(*), count(DISTINCT PID_APID) FROM pid WHERE PID_TYPE = '1' GROUP BY 1;
-- CEV disabled in sequences
SELECT CSS_SQNAME, CSS_ENTRY, CSS_ELEMID FROM css WHERE CSS_CEV = 'Y';
