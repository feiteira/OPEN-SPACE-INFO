# cve.dat: Verification expressions

<div class="osi-chips"><span class="osi-chip">ICD 7.0 §3.3.3.4.2</span><span class="osi-chip">171 rows in Solar Orbiter 2025-09-16</span></div>

The cve table holds the checks that make up the criteria of parameter-based verification stages: one record per check, naming a monitoring parameter, the expected value, a tolerance and the representation (raw, engineering, or echo of a command parameter value). All checks of the same stage are ANDed. The ICD recommends taking all verification parameters of a stage from the same telemetry packet (see CVS_SPID). Parameter validity is taken into account automatically: a check passes only if the parameter is valid and its value meets the criterion. The table has a second role: it identifies the monitoring parameters affected by a command, so that their status consistency checking (PCF_USCON) is suspended during the verification window and, at the end, the expected value is updated. For status-consistency-checked parameters the check must use the same raw or engineering form (CVE_INTER) as the parameter's out-of-limits checks (OCF_INTER), and all cve records for the same parameter must use the same representation, across all stages.[^icd]

**Key:** `CVE_CVSID`, `CVE_PARNAM`

## Relationships

- `CVE_CVSID` → [cvs.CVS_ID](cvs.md#cvs_id): Stage must have CVS_SOURCE = 'V'.
- `CVE_PARNAM` → [pcf.PCF_NAME](pcf.md#pcf_name): Numeric-raw, TM-model parameter. Its PCF_USCON, PCF_CATEG, PCF_CURTX and PCF_PTC constrain CVE_INTER, CVE_VAL and CVE_TOL.
- `CVE_INTER` → [ocf.OCF_INTER](ocf.md#ocf_inter) / [ocf.OCF_CODIN](ocf.md#ocf_codin): For status-consistency-checked parameters CVE_INTER must match OCF_INTER. ocf says OCF_CODIN must be compatible with CVE_INTER when the parameter is used in cve (§3.3.2.3.1, PDF p.74).
- `CVE_VAL` → [cdf.CDF_PNAME](cdf.md#cdf_pname): Echo verification (CVE_INTER = 'C'): command parameter whose instantiated value is the reference.

## History across ICD issues

ICD 5.1 §3.3.3.4.2 (icd-5-1-tos-gci, PDF p.94-96) has the same 6 fields, with CVE_CVSID Number(5). The differences are in the text. In 5.1 any TM or synthetic parameter with a numerical raw value is allowed, 'E' requires PCF_CURTX not Null (a single calibration curve), and the introduction requires OCF_INTER = 'C' when CVE_INTER = 'E' and advises against status consistency checking of echo-verified parameters. ICD 6.0 added 'describe constraint in the use of parameter views in the CVE table' (Annex 1 item 6, PDF p.244), giving the same-representation rules. ICD 6.4 restricted CVE_PARNAM, like other TM references, to parameters processed by the TM model (PDF p.254). ICD 6.7 Draft A prints CVE_CVSID as Number(10) (icd-6-7-drafta PDF p.182). ICD 6.9 changed it back to Number(5) to match CVS_ID (S2K-DCR-3909, PDF p.260; tracked change visible in icd-6-9-archive-org PDF p.187). ICD 7.0 (PDF p.194-199) keeps Number(5). Not modelled in pyscos2000 (7.2).

!!! note "Notes from the extraction"
    Column mapping: COL1..COL6 = CVE_CVSID, CVE_PARNAM, CVE_INTER, CVE_VAL, CVE_TOL, CVE_CHECK; all 171 lines of the 2025 cve.dat have 6 fields. Consistency with ICD 7.0: every CVE_CVSID refers to a cvs stage with CVS_SOURCE = 'V', every 'V' stage has at least one check (167 stages, 171 checks; stages 9082-9085 have two ANDed checks each), and every CVE_PARNAM exists in pcf. CVE_INTER is 'R' in 81 rows and 'E' in 90. There is no echo verification ('C'), and CVE_CHECK is always 'B'. All 90 'E' checks use status parameters (PCF_CATEG = 'S', textual calibration) with text values such as ENABLED/DISABLED, On/Off, IMAGE_0/IMAGE_1, and CVE_TOL empty, as the ICD requires. No parameter used in cve has PCF_USCON = 'Y'. Release difference: in 2025, 78 'R' rows have CVE_TOL = '0', whereas the same rows have an empty tolerance in the 2020-04-16 release. This is the only change in cve between the releases. The SWA IDB cve.dat is empty. pyscos2000 has no cve model.
