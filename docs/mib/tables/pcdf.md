# pcdf.dat: Packet headers definition

<div class="osi-chips"><span class="osi-chip">ICD 7.0 §3.3.3.1.3</span><span class="osi-chip">20 rows in Solar Orbiter 2025-09-16</span></div>

The pcdf table describes the bit-level structure of each TC packet header defined in TCP, with one record per element of the header. An element is either a fixed area, whose constant value is written in the record, or a header parameter (named in PCPC) whose value SCOS-2000 fills in when the command is encoded: APID, service type, service subtype and acknowledgement flags are copied from the corresponding CCF fields of the command being encoded, while other parameters such as the packet length (computed from the actual length, including expanded repeated groups) and the source sequence counter (maintained by the multiplexer per APID) are set automatically by the command subsystem. Each record gives the length in bits and the bit offset from the start of the packet, so the table fully describes the header that precedes the application data defined by CDF. The header length (sum of PCDF_LEN) is part of the overhead deducted from the maximum command size. Header parameters cannot be edited by operators on a SCOS-2000 manual stack. For special command types (CCF_CTYPE R or F) the PCDF/CDF entries describe the frame data field instead of a packet.[^icd]

**Key:** `PCDF_TCNAME`, `PCDF_BIT`

## Relationships

- `PCDF_TCNAME` → [tcp.TCP_ID](tcp.md#tcp_id): Header to which the element belongs.
- `PCDF_PNAME` → [pcpc.PCPC_PNAME](pcpc.md#pcpc_pname): Header parameter for elements of type A, T, S, K or P; PCPC_CODE decides how PCDF_VALUE is read.
- `PCDF_TYPE` → [ccf.CCF_APID](ccf.md#ccf_apid) / [ccf.CCF_TYPE](ccf.md#ccf_type) / [ccf.CCF_STYPE](ccf.md#ccf_stype) / [ccf.CCF_ACK](ccf.md#ccf_ack): Elements of type A, T, S and K are filled from these fields of the command being encoded; a CCF field may be empty only if its header has no element of the corresponding type.

## History across ICD issues

Structure unchanged from ICD 5.1 (section 3.3.3.1.3, PDF p.61-62) through ICD 6.7 Draft A (PDF p.122), ICD 6.9 (PDF p.126-128) and ICD 7.0 (PDF p.129-131): eight fields with key PCDF_TCNAME + PCDF_BIT, PCDF_VALUE Char(10) mandatory and PCDF_RADIX defaulting to 'H'. The PCDF_TYPE options F, A, T, S, K and P are the same in ICD 5.1 and ICD 7.0. pyscos2000 (ICD 7.2) has the same eight columns in the same order, the same keys (PCDF_TCNAME, PCDF_BIT), the same mandatory fields and the default 'H' for PCDF_RADIX.

!!! note "Notes from the extraction"
    Columns match ICD 7.0 and pyscos2000 one to one (8 columns in every line of the Solar Orbiter pcdf.dat). Discrepancy with ICD 7.0: in the 2025-09-16 Solar Orbiter MIB the NOM_TC element 'Source ID' (8 bits at bit 72, parameter DFH_SRC) has PCDF_TYPE='O', a value that is not among the options listed in ICD 7.0 (F, A, T, S, K, P); in the 2020-04-16 release the same element was a fixed area (type F, value 0). The meaning of 'O' is not stated in the available sources (the pyscos2000 schema dump does not list the allowed enumeration values). Solar Orbiter NOM_TC layout (real data, bit offsets from packet start): version 3 bits at 0 (F=0), type 1 bit at 3 (F=1), data field header flag 1 bit at 4 (F=1), APID 11 bits at 5 (A), sequence flags 2 bits at 16 (F=3), sequence count 14 bits at 18 (P), packet length 16 bits at 32 (P), secondary header flag 1 bit at 48 (F=0), PUS version 3 bits at 49 (F=1), ack 4 bits at 52 (K), service type 8 bits at 56 (T), subtype 8 bits at 64 (S), source ID 8 bits at 72 (O), i.e. an 80-bit (10-octet) header. HPC1_TC has only the 48-bit primary header with data field header flag 0. All Solar Orbiter PCDF_VALUE entries are 0, 1 or 3 and PCDF_RADIX is 'H' everywhere. Related tailoring: the Herschel HCSS MIB note (hcss-mib-clarification-tailoring-note, point 5.2.7, PDF p.13) requires at least four PCDF rows per packet header ID and remarks that its reference ICD then described PCDF_TCNAME as unique; in ICD 7.0 PCDF_TCNAME is only part of a composite key with PCDF_BIT, so that conflict does not arise.
