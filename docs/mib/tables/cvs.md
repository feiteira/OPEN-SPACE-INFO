# cvs.dat: Verification stages file

<div class="osi-chips"><span class="osi-chip">ICD 7.0 §3.3.3.4.1</span><span class="osi-chip">206 rows in Solar Orbiter 2025-09-16</span></div>

The cvs table defines the command execution verification (CEV) stages used by SCOS-2000, one record per stage. SCOS-2000 supports two kinds of verification check: report based, which relies on dedicated telemetry packets (PUS service 1 verification reports) announcing the success or failure of an execution stage, and parameter based, which compares the values of one or more monitoring parameters with criteria held in cve. Each stage record says which step of the command execution profile it covers (application acceptance, start, a numbered progress step or completion), which kind of check it uses, when the verification window opens after release (or execution, for time-tagged commands), the sampling interval used to compute the window, optionally the packet that closes a parameter-based stage, and optionally a stage-specific window that overrides the TC Spacon default. Stages are defined once and shared: cvp attaches them to commands. The ICD notes that only verification of commands, not of sequences, is supported by current SCOS-2000 versions.[^icd]

**Key:** `CVS_ID`

## Relationships

- `CVS_ID` → [cve.CVE_CVSID](cve.md#cve_cvsid): Parameter-based stages (CVS_SOURCE='V') have one or more cve checks, logically ANDed.
- `CVS_ID` → [cvp.CVP_CVSID](cvp.md#cvp_cvsid): Many-to-many relationship between commands and stages, resolved by the mapping table cvp (§3.3.3, PDF p.126).
- `CVS_SPID` → [pid.PID_SPID](pid.md#pid_spid): Packet that closes a 'V' stage.
- `CVS_TYPE` → [ccf.CCF_ILSTAGE](ccf.md#ccf_ilstage): The importer checks that a command's default interlock stage ('A' or 'C') is foreseen in its cvp/cvs definition, and otherwise replaces CCF_ILSTAGE with the highest applicable level ('A' or 'O') (§3.3.3.2.1, PDF p.138).
- `CVS_SOURCE` → [ccf.CCF_ACK](ccf.md#ccf_ack): Since R4.0 report-based stages attached to a command can be disabled at load time by clearing the corresponding acknowledgement flag (PDF p.140, p.200).

## History across ICD issues

ICD 5.1 §3.3.3.4.1 (icd-5-1-tos-gci, PDF p.93-94) has 6 fields (no CVS_UNCERTAINTY). CVS_ID is already Number(5), 0-32767, and there is no stage-0 note. ICD 6.0 brought in the Herschel/Planck CCS functions, including a CVS identifier range raised 'from NUM(5) to NUM(8)' (ICD 7.0 Annex 1, PDF p.247). ICD 6.1 (S2K-40-DCR-0821) updated CVS_TYPE and CVS_SOURCE to say that progress reports are only handled for stage 0 (PDF p.251). ICD 6.2/6.3 record 'CVS_ID Field Type changed' (PDF p.253). ICD 6.7 S2K-DCR-3909 restricted CVS_ID to signed short values (PDF p.259): ICD 6.7 Draft A prints Number(5), 0-32767, with 6 fields (icd-6-7-drafta PDF p.180-181). CVS_UNCERTAINTY was added for R5.2 by S2K-SCR-3774 (override of the TcSpacon verification window, PDF p.260; it arrived in ICD 6.7 Draft B per the change log, PDF p.5). It is printed in ICD 6.9 (icd-6-9-archive-org PDF p.186), whose S2K-NCR-5531 updated its description (PDF p.260). ICD 7.0 (PDF p.192-194) is unchanged from 6.9. Not modelled in pyscos2000 (7.2).

!!! note "Notes from the extraction"
    Column mapping: COL1..COL7 = CVS_ID, CVS_TYPE, CVS_SOURCE, CVS_START, CVS_INTERVAL, CVS_SPID, CVS_UNCERTAINTY. All 206 lines of the 2025 cvs.dat have 7 fields (ICD 6.9/7.0 layout), but CVS_UNCERTAINTY is empty in every row, so the importer default -1 (TC Spacon window) applies everywhere. The SWA IDB cvs.dat has only 6 fields per line (pre-R5.2 layout without CVS_UNCERTAINTY) and holds 2 stages, 58901 and 58907, which have the same values as the stages with those IDs in the Solar Orbiter MIB. Content: only types 'A' and 'C' are used, with no start or progress stages: A/R 16, C/R 23, C/V 167. CVS_START is 0 everywhere (the ICD describes it as a positive integer). CVS_INTERVAL ranges from 4 to 36000 s; stage 51927 changed from 8000 to 36000 between the 2020-04-16 and 2025-09-16 releases, the only cvs difference. Discrepancy 1: 33 CVS_ID values exceed the ICD 7.0 range 0-32767 (IDs run from 11 to 70007, for example 50001, 54004, 70007), which conflicts with the signed-short restriction of S2K-DCR-3909. Discrepancy 2: CVS_SPID is filled in 20 rows, all report-based (CVS_SOURCE='R'), although ICD 7.0 allows it only for 'V' stages and calls it irrelevant for 'R'. The values are 0 (stages 14001/14007), SPIDs of TM(1,1) or TM(1,7) success-report packets (for example 52000 'TM 1,1 accept report ok', 54013 'STIX TC EXEC SUCCESS'), or 20000, which in pid is a TM(5,1) event packet. Inference, not stated in the sources: the mission control system may use CVS_SPID to tell the verifier which report packet to expect. The 2002 e-mail reproduced in the HCSS note explains that the SCOS-2000 verifier then listened to a predefined list of SPIDs for report-based verification (hcss-mib-clarification-tailoring-note PDF p.29). ICD 7.0 cites [RD-2] for report packets, but its reference list gives RD-2 as the SCOS-2000 Operations Language ADD and the PUS as RD-6 (PDF p.19), so the citation looks stale. pyscos2000 has no cvs model, so no 7.2 cross-check is possible. The HPSDB note forces CVS_SPID to Null (h-p-1-asp-tn-1060-mib-processing-hpsdb PDF p.38).
