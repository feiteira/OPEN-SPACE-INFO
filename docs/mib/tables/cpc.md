# cpc.dat: Command parameters

<div class="osi-chips"><span class="osi-chip">ICD 7.0 §3.3.3.2.2</span><span class="osi-chip">7,155 rows in Solar Orbiter 2025-09-16</span></div>

The cpc table defines the command parameters, one record per parameter. A command parameter is any part of a command's application data whose value has to be edited, calibrated or checked; it can be reused in any number of command definitions, where CDF places each instance. The record gives the parameter type and length (PTC/PFC pair, see Appendix A of the ICD), how engineering values are entered and displayed, the default radix for unsigned raw values, the engineering unit, the kind of calibration or special processing (numeric, textual, 'Command ID' or 'Parameter ID'), references to a range-check set (PRF), a numeric (de-)calibration curve (CCA) or a textual (de-)calibration (PAF), and a default value with its representation. Default values can be given at three levels - parameter (CPC_DEFVAL), command definition (CDF_VALUE) and sequence (SDF_VALUE) - and the 'D' options of CDF_INTER and SDF_VTYPE propagate the lower-level default upwards, so a value can be maintained centrally. Special PUS-oriented types are supported: 'Command ID' parameters encode the raw packet of another command as a variable octet string; 'Parameter ID' parameters encode the on-board identifier of a telemetry parameter; and, since R5, 'Deduced' parameters (PTC=11) inherit type, width and calibration from a TM parameter named by a preceding 'Parameter ID' parameter in the same (repeated) group. Time parameters can be time-correlated using a selected on-board clock.[^icd]

**Key:** `CPC_PNAME`

## Relationships

- `CPC_PNAME` → [cdf.CDF_PNAME](cdf.md#cdf_pname): Instances of the parameter in command definitions (many-to-many between CCF and CPC through CDF).
- `CPC_PRFREF` → [prf.PRF_NUMBR](prf.md#prf_numbr): Range set used to check values (many parameters may share a set).
- `CPC_CCAREF` → [cca.CCA_NUMBR](cca.md#cca_numbr): Numeric (de-)calibration curve, required when CPC_CATEG=C.
- `CPC_PAFREF` → [paf.PAF_NUMBR](paf.md#paf_numbr): Textual (de-)calibration (alias set), required when CPC_CATEG=T.
- `CPC_DEFVAL` → [ccf.CCF_CNAME](ccf.md#ccf_cname) / [pcf.PCF_NAME](pcf.md#pcf_name): For 'Command ID' (CATEG=A) the default names a fully defaulted command; for 'Parameter ID' (CATEG=P) a monitoring parameter with PCF_PID.
- `CPC_UNIT` → [cca.CCA_UNIT](cca.md#cca_unit) / [prf.PRF_UNIT](prf.md#prf_unit): Units of the referenced curve or range set are checked for consistency.

## History across ICD issues

ICD 5.1 (2001, section 3.3.3.2.2, PDF p.67-70) has 13 fields: CPC_PRFREF, CPC_CCAREF and CPC_PAFREF are Number(4), CPC_DEFVAL is Char(17), and CPC_CATEG offers only C, T, B and N. ICD 6.0 introduced the 'Command ID' and 'Parameter ID' categories A and P (Annex 1, PDF p.249) and later changed the calibration and range identifiers to Char(10) (PDF p.247 and p.253); 'Deduced' parameters (PTC=11) came with ICD 6.4 for R5.0 (PDF p.254). CPC_CORR and CPC_OBTID were added in ICD 6.7 for R5.2 (S2K-SCR-4917, PDF p.258) and the CPC_OBTID description updated in 6.9 (S2K-DCR-5743, PDF p.260); ICD 6.7 Draft A (PDF p.133-140) and ICD 6.9 (PDF p.137-145) therefore have 15 fields. ICD 7.0 (PDF p.142-151) made CPC_DEFVAL variable-length, bounded by the maximum command size (S2K-8073, PDF p.261), stated that CPC_CORR must be N for relative times (S2K-8778, PDF p.263; ICD 6.9 had spoken of absolute or relative times), and added CPC_ENDIAN as field 16 for future use (S2K-7749, PDF p.262). pyscos2000 (ICD 7.2) lists 17 columns: it names the key CPC_NAME, field 15 CPC_OBTIP, inserts CPC_DESCR2 (default empty string) as field 16 and moves CPC_ENDIAN (default B) to field 17.

!!! note "Notes from the extraction"
    Several discrepancies. (1) Names: ICD 7.0 (and 5.1, 6.7, 6.9) call the key CPC_PNAME, whereas pyscos2000 and the Solar Orbiter SQLite use CPC_NAME; ICD 7.0 field 15 is CPC_OBTID, whereas pyscos2000 and the SQLite use CPC_OBTIP (apparently a misspelling). (2) Order/content: ICD 7.0 has 16 fields ending with CPC_ENDIAN; pyscos2000 (7.2) has CPC_DESCR2 at position 16 and CPC_ENDIAN at 17. A 16-column cpc.dat would therefore be read differently by the two schemas. (3) The Solar Orbiter cpc.dat files (2020 and 2025) have only 15 columns, i.e. the ICD 6.7/6.9 layout; CPC_DESCR2 and CPC_ENDIAN exist in the SQLite only because of the pyscos2000 schema and are empty in every record, and CPC_OBTIP (CPC_OBTID) is also never filled. (4) No record uses PTC=11 ('Deduced'). Time parameters are PTC=9 with PFC 15 or 17 (58 records) and one PTC=10/PFC=17 relative time (PCD0B071, CPC_CORR='N', as ICD 7.0 requires); these 59 time parameters leave CPC_CATEG empty, as allowed. (5) CPC_CORR='Y' is set on 12 non-time parameters (ENISTE*, PTC 2, 3 or 8) used only by the 6 NIS throw-event commands, where the ICD gives the flag no meaning. (6) Category usage in 2025: N 4991, T 1624 (all with CPC_DISPFMT='A'), C 327, P 152 (all PTC=3/PFC=14, i.e. 32-bit parameter IDs), A 2 (PCD0B044 and PCD13013, PTC=7/PFC=0, as required). (7) 316 records use CPC_INTER='E' (311 textual, 5 numeric), consistent with the rule that E needs a calibration. (8) All CPC_PRFREF, CPC_CCAREF and CPC_PAFREF values resolve to existing PRF, CCA and PAF records; every CPC_UNIT of a numerically calibrated parameter equals the unit of its curve. 7155 records in 2025, 6947 in 2020.
