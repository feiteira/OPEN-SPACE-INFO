## Summary

The CCSDS Recommended Standard for the **Space Data Link Security (SDLS) Protocol**, an optional security sublayer inside the Data Link Layer that adds authentication, encryption or authenticated encryption to the frames of the [TM](../ccsds/tm-sdlp.md), [TC](../ccsds/tc-sdlp.md), [AOS](../ccsds/aos.md) and (new in issue 2) [USLP](../ccsds/uslp.md) Space Data Link Protocols. It does not apply to Proximity-1, and it does not mandate any cryptographic algorithm: CCSDS 352.0 lists the recommended ones.

Section 2 explains the concept. A Security Association (SA) is a one-way, stateful cryptographic session bound to one or more Global Virtual Channels (GVCIDs) or, for TC and USLP, GMAP_IDs. Authentication uses a MAC over a masked part of the frame, with anti-replay sequence numbers checked against a window. Section 3 defines two abstract functions. ApplySecurity runs at the sending end. ProcessSecurity runs at the receiving end and returns a verification status code: invalid SPI, MAC failure, anti-replay failure or padding error. The section also lists the parameters of the SA database. Section 4 specifies the PDUs. The Security Header carries a 16-bit Security Parameter Index (SPI), followed by an optional Initialization Vector, Sequence Number and Pad Length, up to 64 octets in all. The Security Trailer carries the MAC. Section 4 also gives the SA management, sending and receiving procedures. Section 5 shows where the header and trailer sit in each frame type, and Table 5-1 says which data link services are protected. Section 6 (Table 6-1) lists the managed parameters, for example SPI 1-65534, IV 1-32 octets and MAC 8-64 octets. Annex A is the PICS proforma, Annex B covers security considerations (no key management, COP directives and the CLCW are unprotected) and Annex E gives baseline modes: AES-GCM for TM, AOS and USLP, and AES-CMAC for TC.


## Key points

- Issue 2 (July 2022) adds USLP support and a normative reference to the SDLS Extended Procedures (CCSDS 355.1-B-1); issue 1 (September 2015) is superseded. *(PDF p. 7)*
- The Security Protocol works only at the Data Link Layer (OSI layer 2), with the TM, TC, AOS and USLP Space Data Link Protocols. It is not applicable to Proximity-1. *(PDF p. 14)*
- The standard mandates no cryptographic algorithm; CCSDS 352.0-B-2 lists the recommended algorithms, and Annex E gives non-normative baseline implementations. *(PDF p. 10)*
- The Security Header is a mandatory 16-bit Security Parameter Index (SPI), followed by an optional Initialization Vector, Sequence Number and Pad Length (each fixed-length for the life of the SA). The whole header is at most 64 octets. *(PDF p. 35)*
- SPI values 0 (all zeros) and 65535 (all ones) are reserved by CCSDS; the managed-parameter range is 1-65534. *(PDF p. 35)*
- The Security Trailer, when present, holds only a fixed-length MAC; it is present whenever authentication or authenticated encryption is applied. *(PDF p. 37)*
- Every SA specifies exactly one service type: authentication, encryption, or authenticated encryption. A 'clear mode' SA with a no-op algorithm is possible for testing but not recommended in operations. *(PDF p. 39)*
- At the sending end, only one SA at a time can be active on a given GVCID or GMAP_ID. SAs are not created for Virtual Channels that carry Only Idle Data frames. *(PDF p. 38)*
- ProcessSecurity must at least distinguish these failure codes: no failure, invalid SPI, MAC verification failure, anti-replay sequence number failure, and padding error. *(PDF p. 30)*
- In a TM frame only the Frame Data is encrypted. The MAC covers the Primary Header, Secondary Header, Security Header and Frame Data, but not the ASM, OCF or ECF. *(PDF p. 47)*
- For TC, each SA must be associated with exactly one VC. The COP Management, VCF and MCF services are not protected. *(PDF p. 47)*
- Table 5-1 shows that the TM VC_FSH can be authenticated but not encrypted, and that the OCF-based services (VC_OCF, MC_OCF) are never protected. *(PDF p. 50)*
- Managed transmitted lengths: IV 1-32 octets, Sequence Number 2-8 octets, Pad Length 1-2 octets, MAC 8-64 octets. Authentication algorithms are HMAC, CMAC, GMAC, GCM or agency-specific; encryption algorithms are AES/Counter Mode, GCM or agency-specific. *(PDF p. 52)*
- The protocol gives no protection against jamming, traffic-flow analysis or false COP directives/CLCW contents, and it provides no key management. *(PDF p. 64)*
- The TM baseline is AES-GCM authenticated encryption with a 256-bit key, a 96-bit IV sent in-line and a 128-bit MAC, giving a 14-octet Security Header and a 16-octet Security Trailer. *(PDF p. 70)*
- The TC baseline is AES-CMAC authentication with a 256-bit key, a 32-bit anti-replay sequence number and a 128-bit MAC, giving a 6-octet Security Header and a 16-octet Security Trailer. *(PDF p. 71)*
