## Summary

The CCSDS Recommended Standard for the **Monitored Data Cross Support Transfer Service (MD-CSTS)**. CSTS is the family of cross support transfer services documented alongside the [SLE](../ccsds/sle/index.md) transfer services. Through MD-CSTS, a mission can watch the ground station that is supporting it. The mission can receive cyclic or on-change reports of monitored parameters, query current values, and receive notifications of events for everything in a service package: antennas, RF carriers, frame decoders, and the SLE and CSTS provider instances. The service delivers only current values, not history. It is built from procedures of the CSTS Specification Framework (CCSDS 921.1-B-2, not in the library) and uses the SANA Functional Resource registry to name parameters and events. The relevant wiki pages are [SLE service management](../ccsds/sle/service-management.md) and [SLE over TCP/IP and the SLE API](../ccsds/sle/isp1-and-api.md), since MD-CSTS PDUs are carried by ISP1.

Section 2 explains production and provision and the naming scheme. A Parameter Name combines a Parameter Identifier (an OID on the CCSDS registration tree) with a Functional Resource Name (type OID plus instance number), and Event Names are built the same way. Section 2 then gives a long operational scenario. Section 3 composes the service from four procedures: one Association Control; the prime On-Change-Option Cyclic Report (1..*); an optional Information Query (0..1); and Notification (0..*). Section 4 specifies the on-change extension to the framework Cyclic Report. Sections 5-7 refine Information Query and Notification and set the inherited configuration parameters. Sections 8-9 define the service-level functional resource items mdResponseTimeout, mdProdStat and mdProdStatChange. The annexes give the ICS proforma, the ASN.1 OIDs and PDUs, the production-process requirements, security and SANA considerations, and an informative example Functional Resource set (antenna, CCSDS 401 carriers, FCLTU and RAF providers).


## Key points

- MD-CSTS lets a mission receive cyclic reports on, and query current values of, the parameters of the cross support services provided by a Cross Support Complex (an Earth Space Link Terminal), and receive event notifications. *(PDF p. 12)*
- The standard does not define which parameters are reported or which events are notified, nor how they are measured. *(PDF p. 13)*
- The service delivers only current parameter values. It cannot deliver stored values from earlier times. *(PDF p. 25)*
- A service package may contain several MD-CSTS instances. Each instance can report all monitored parameters and events of the package, including RF links and SLE transfer service instances. *(PDF p. 26)*
- Implementations must use the SANA Functional Resource Registry as the normative source of Functional Resource Types, parameters and events. Annex F is only an example. *(PDF p. 28)*
- A Parameter Name combines a Parameter Identifier (a Published Identifier OID, for example ccsds-401-carrier-xmit-actual-carrier-freq) with a Functional Resource Name (Functional Resource Type OID plus a positive Functional Resource Instance Number assigned at scheduling). *(PDF p. 29)*
- The On-Change-Option Cyclic Report procedure lets the user choose a parameter list, a delivery cycle, and whether to report every value or only changed values. Several instances can run concurrently. *(PDF p. 30)*
- The service consists of Association Control (exactly 1), On-Change-Option Cyclic Report as prime procedure (1..*), Information Query (0..1) and Notification (0..*). *(PDF p. 50)*
- With the on-change option, a parameter whose value changes and changes back between two cycles is not reported. *(PDF p. 51)*
- Cyclic reporting of procedure configuration parameters is optional, because those parameters are static for the life of an MD service instance. *(PDF p. 52)*
- MD-CSTS supports the framework's response-timeout and production-status parameters (mdResponseTimeout, mdProdStat) and the production status change event (mdProdStatChange). It does not support the production configuration change event. *(PDF p. 65)*
- The Monitored Data Production Process must keep each monitored parameter's value until a new one is available. It delivers values as QualifiedParameter and events as [eventName: eventValue] pairs. *(PDF p. 98)*
