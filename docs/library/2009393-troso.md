## Summary

A seven-page conference paper from Vitrociset (Rome) presenting the Health Monitoring System (HM), a plug-in that lets a SCOS-2000-based EGSE or mission control system watch its own computers and links. The HM collects operating-system resources (disk usage, memory, CPU load), the status of processes, point-to-point TCP connections between hosts and the state of time synchronisation on every EGSE machine. Its key design choice is to report all of these as ordinary telemetry parameters defined in the SCOS-2000 MIB and carried in dedicated TM packets, so that they can be shown on standard SCOS-2000 displays, limit-checked and used by watchdogs in test procedures.

The architecture follows the three levels of Java Management Extensions (JMX): an instrumentation level of MBean plug-ins, one per kind of managed resource; an agent level with an MBean server and an RMI connector on each host; and a manager level. An HM Agent runs as a service on each subsystem, and a single HM Manager, started with the normal SCOS-2000 start-up and optionally with a GUI, packs the collected values into configurable TM packets and injects them into the SCOS-2000 telemetry chain through the CORBA-based EXIF interface; a port to the newer SMF module is planned. Configuration is XML-based: an agent file lists the managed objects in containers, and a manager file maps each monitored object identifier to a MIB parameter name. The paper shows mimic displays and the complete mapping table (HM_* parameters) for the VEGA launcher EGSE, where the system was in use on three servers and three clients.


## Key points

- The HM is conceived as a Central Checkout System (CCS) component with a client-server structure, potentially extensible as a topological graph over the whole EGSE. *(PDF p. 1)*
- Monitored items: OS resources (disk usage, memory, CPU load), status of processes, point-to-point connections between hosts, and the status of the time synchronisation process. *(PDF p. 2)*
- Driving factor: model every monitored entity as a TM parameter defined in the SCOS-2000 MIB, contained in ad-hoc defined TM packets, so it can be shown on a SCOS-2000 display. *(PDF p. 2)*
- The architecture uses JMX MBean technology with instrumentation, agent and manager levels; agents run on the same machine as the resources they control, or in a mediation/concentrator element when no JVM is available. *(PDF p. 3)*
- The HM Manager is installed on one EGSE machine as central collector and is normally launched within the standard SCOS-2000 startup process, optionally with a GUI showing the flow of data from agents to SCOS-2000. *(PDF p. 4)*
- The HM Manager inserts the collected information into a configurable set of TM packets and injects them regularly into the SCOS-2000 telemetry chain through the CORBA EXIF interface; a porting to the new SMF module is foreseen. *(PDF p. 4)*
- Mapping EGSE status to TM parameters makes it visible at display and procedure level, so dedicated watchdogs can react to anomalies; mimic displays of the VEGA EGSE status are shown. *(PDF p. 5)*
- Each agent mounts its plug-ins at start-up from an XML file organised in containers of managed objects (ClassType and Name attributes, e.g. Sampler, TCPMonitor, disk, process, connection, ntp). *(PDF p. 6)*
- A second XML file for the HM Manager associates monitored object Ids with SCOS-2000 TM parameter names as defined in the MIB; the VEGA example maps hosts CL1-CL3, PAR, MCK and CMD to parameters named HM_32_xx, HM_16_xx, HM_FL_xx and HM_1_xx. *(PDF p. 7)*
- At the time of writing the HM was in use on the VEGA launcher EGSE, monitoring three servers and three clients plus the connection status and status words of various SCOEs; it can be adopted on any SCOS-2000 MCS or EGSE by writing the XML configuration and populating the MIB. *(PDF p. 7)*
