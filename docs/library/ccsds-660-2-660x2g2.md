## Summary

A short (42-page) CCSDS Green Book that introduces the **XML Telemetric and Command Exchange (XTCE)** format at a high level. It is the entry point of the three CCSDS XTCE books: the Blue Book [CCSDS 660.0-B-2](../library/ccsds-660-0-660x0b2.md) adopts the OMG schema, and the Element Description Green Book [CCSDS 660.1-G-2](../library/ccsds-660-1-660x1g2.md) explains each element in detail. The wiki page is [XTCE](../ccsds/xtce.md).

Section 2 explains why a non-proprietary telemetry and telecommand database format is useful (exchange between spacecraft and instrument manufacturers, simulators, control, planning and trending systems), gives the version history (XTCE 1.0 in 2006, 1.1 in 2008, 1.2 in 2019) and lists the main changes in 1.2. It also covers the GovSat/XUSP conformance profile for users who find XTCE too large, and six ways to handle features XTCE lacks, from AncillaryData name/value pairs to OMG change requests. Section 3 walks through the schema: the SpaceSystem hierarchy and Header; TelemetryMetaData with its ten ParameterTypes, four DataEncodings, calibrators, ParameterSet, SequenceContainer inheritance, MessageSet, StreamSet and AlgorithmSet; CommandMetaData with ArgumentTypes, MetaCommand inheritance, CommandContainer, transmission constraints, significance, interlocks and the eight verifier stages; and ServiceSet, which was added for European PUS-style services. Section 4 shows XTCE as the exchange format between subsystem suppliers, the spacecraft Source Database and the operational databases. Annex A is a small GovSat example with a CCSDS packet header, one telemetry packet and one command. For SCOS-2000 readers, the counterpart is the [MIB data model](../mib/data-model.md).


## Key points

- XTCE 1.0 was published in 2006, XTCE 1.1 in 2008 after a CCSDS review, and XTCE 1.2 in 2019. The OMG manages the associated schema. This report pertains to all versions but specifically to 1.2. *(PDF p. 10)*
- XTCE 1.2 is largely backwards compatible with 1.1. The biggest syntax change is that array dimension sizes can be defined in the ArrayParameterType itself. Other changes include a new SpaceSystem namespace, normalised enumeration strings, changed byte order, integer exponents and updated float encoding sizes. *(PDF p. 10)*
- XTCE is not tied to a particular telemetry format such as CCSDS Space Packets or major/minor frames. *(PDF p. 11)*
- Several SpaceSystems can be defined in separate files and combined with XInclude, for example one database per instrument plus one for the spacecraft bus. *(PDF p. 13)*
- GovSat, published by the OMG as the XTCE US Govt Satellite Conformance Profile (XUSP), is not a new schema but a set of executable rules that restrict XTCE, for example to a single SpaceSystem. *(PDF p. 14)*
- For missing features the report lists six options, from AncillaryData name/value pairs (the easiest, and schema-compatible) to local schema changes, external schemas, overloading elements (least preferred) and OMG change requests. *(PDF p. 15)*
- XTCE defines ten ParameterTypes: Integer, Float, Enumerated, String, Boolean, Binary, RelativeTime, AbsoluteTime, Array and Aggregate. A ParameterType without a DataEncoding describes a ground-side value, and its Parameter should set dataSource to 'local'. *(PDF p. 20)*
- All ParameterTypes except Array and Aggregate use one of four DataEncodings: Integer, Float, String or Binary. The numeric encodings support spline, polynomial and MathOperation calibrators. *(PDF p. 21)*
- It is common practice for each Parameter to have its own ParameterType, so that changing alarms or calibrators in a shared type cannot propagate by mistake. *(PDF p. 22)*
- Container inheritance is the preferred way to define packets. The report recommends defining packets, not framing information, in XTCE. *(PDF p. 22)*
- MessageSet ('has a' construction) is kept only for backwards compatibility and may be considered deprecated. StreamSet is seen by many as too simple for front-end configuration. *(PDF p. 23)*
- Derived or pseudo parameters are typically Parameters without a DataEncoding, with dataSource set to 'derived' and an algorithm in AlgorithmSet that names them in its OutputSet. *(PDF p. 25)*
- Command Arguments are local to a MetaCommand and cannot be reused, but MetaCommands can inherit through BaseMetaCommand. ArgumentTypes have no alarm definitions. *(PDF p. 14)*
- Significance levels are none, watch, warning, distress, critical and severe. There are eight verifier stages: Transferred to range, Transferred from range, Received, Accepted, Queued, Execution, Complete and Failed. *(PDF p. 29)*
- ServiceSet was introduced for European organisations that use services as in the ECSS Packet Utilization Standard (ECSS-E-ST-70-41C). *(PDF p. 30)*
- XTCE is meant for exchanging database information, not as the direct interface for sending commands or receiving telemetry. *(PDF p. 31)*
- The Annex A example defines an abstract CCSDSPacket container with the seven primary header fields (3-bit version, 1-bit type, 1-bit secondary header flag, 11-bit APID, 2-bit flags, 14-bit count, 16-bit length) and a status packet restricted to APID 47. *(PDF p. 38)*
