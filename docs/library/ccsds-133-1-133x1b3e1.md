## Summary

The CCSDS Recommended Standard for the **Encapsulation Packet Protocol (EPP)**. EPP is a thin 'shim' protocol that lets the [TM](../ccsds/tm-sdlp.md), [TC](../ccsds/tc-sdlp.md), [AOS](../ccsds/aos.md), Proximity-1 and [USLP](../ccsds/uslp.md) data link protocols carry data units that have no CCSDS-authorised Packet Version Number. Examples are IP datagrams (through IP over CCSDS), DTN/LTP traffic and private mission data. Each user data unit goes unchanged into one Encapsulation Packet (Packet Version Number '111', 'Version 8 CCSDS Packet'), which then travels in a VC, MAP or Proximity-1 packet service. Earlier issues (called 'Encapsulation Service') could also wrap data in a [Space Packet](../ccsds/space-packet.md); issue 3 removes that option.

Section 2 gives the concept and features: one-way, asynchronous, unconfirmed and order-preserving delivery with possible gaps. Users are addressed by the Encapsulation Protocol Identifier (EPI), and a SAP combines PVN, EPI and the SDLP channel (GVCID, GMAP ID and so on). Section 3 defines the ENCAPSULATION.request and ENCAPSULATION.indication primitives.

Section 4 specifies the packet. The variable header is 1, 2, 4 or 8 octets: version, 3-bit EPI, 2-bit Length of Length, then (for the longer headers) a 4-bit User Defined field, a 4-bit EPI Extension, a 2-octet CCSDS Defined field and a 1, 2 or 4-octet Packet Length that counts the whole packet. Table 4-2 gives the resulting size limits, from a 1-octet idle packet to 4,294,967,295 octets. The section also covers Encapsulation Idle Packets (EPI '000'), the extended-ID escape ('110') and private data ('111'). Section 5 lists the managed parameters, and the annexes note that EPP has no security of its own ([SDLS](../ccsds/sdls.md) or BPSec provide it) and rename the two SANA protocol-ID registries.


## Key points

- Issue 3 removes the Space Packet as an encapsulation format, renames the standard from 'Encapsulation Service' to 'Encapsulation Packet Protocol' and adds USLP support. *(PDF p. 7)*
- EPP carries CCSDS-recognised protocol data units that lack an authorised Packet Version Number over the packet services of the Space Data Link Protocols. *(PDF p. 16)*
- One user data unit goes unchanged into one Encapsulation Packet; delivery is one-way and unconfirmed, preserves order, and may have gaps. *(PDF p. 17)*
- A SAP is identified by PVN + EPI + SDLP channel; the channel is the GVCID for VCP services and the GMAP ID for TC and USLP MAP Packet services. *(PDF p. 19)*
- An Encapsulation Packet is 1 to 4,294,967,295 octets: a 1 to 8-octet header plus 0 to 4,294,967,287 octets of encapsulated data. *(PDF p. 23)*
- Header fields: Packet Version Number (3 bits, '111'), EPI (3 bits), Length of Length (2 bits), then optionally User Defined (4 bits), EPI Extension (4 bits), CCSDS Defined (2 octets) and Packet Length (1, 2 or 4 octets). *(PDF p. 24)*
- EPI '000' marks an Encapsulation Idle Packet (usable as the idle packet of TM, AOS and USLP), '110' means the EPI Extension field identifies the protocol, and '111' means mission-specific private data. *(PDF p. 25)*
- Length of Length '00', '01', '10', '11' gives a Packet Length field of 0, 1, 2 or 4 octets; '00' is allowed only for a one-octet idle packet. *(PDF p. 25)*
- The Packet Length field holds the total packet length in octets, header included (unlike the Space Packet's length-minus-one). *(PDF p. 26)*
- Maximum packet sizes for 2, 4 and 8-octet headers are 255, 65,535 and 4,294,967,295 octets (Table 4-2); the 4-octet length accommodates IPv6 jumbograms. *(PDF p. 27)*
- Managed parameters: minimum and maximum data unit length, and the valid (and valid extended) Encapsulation Protocol Identifiers from SANA. *(PDF p. 30)*
- EPP provides no security; SDLS (355.0-B, 355.1-B) at the data link layer or the Bundle Security Protocol at the network layer can be used. *(PDF p. 31)*
