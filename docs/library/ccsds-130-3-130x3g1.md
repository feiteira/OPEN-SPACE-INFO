## Summary

A short CCSDS Green Book that explains, from the user's point of view, the two CCSDS packet protocols: the [Space Packet Protocol](../ccsds/space-packet.md) (SPP, [133.0-B-2](ccsds-133-0-133x0b2e2.md)) and the [Encapsulation Packet Protocol](../ccsds/encapsulation.md) (EPP, [133.1-B-3](ccsds-133-1-133x1b3e1.md)). It specifies nothing itself; it gives the concepts, the rationale and guidance on when to use one, the other or both.

Section 2 presents the SPP as a self-delimited carrier whose only addressing feature is the Application Process Identifier (APID). It stresses that the SPP defines no routing or network service: packets flow along *managed data paths* configured by management, and the APID naming domain (usually one spacecraft) is allocated by the project. The service is preconfigured, one-way, asynchronous, unconfirmed, incomplete and not sequence-preserving. A worked example shows an instrument that uses three managed data paths: images to the ground, commands to the instrument and status back to the control system, with store-and-forward handled transparently.

Section 3 describes the EPP as a 'shim' that carries protocol data units (PDUs) without an authorised Packet Version Number over the Space Data Link Protocols (TM, TC, AOS, Proximity-1, USLP). The Encapsulated Protocol Identifier, registered in SANA, identifies the user. An example shows CFDP over EPP.

Section 4 is a FAQ. It covers layering, coexistence with IP and DTN (IP over CCSDS), reliability (COP-1, COP-P, CFDP, LTP or the application itself), real-time traffic (priority Virtual Channels, the AOS/USLP Insert Zone), segmentation of large data with the Sequence Flags, extending the APID domain through the secondary header, and the SPP versus EPP trade-off: header size, ancillary data and maximum length.


## Key points

- The Report defines both the SPP and the EPP as protocols that are 'not a Network Layer protocol'; the SPP can act as an Application Layer protocol or as a 'shim' between upper-layer protocols and the Space Data Link Layer. *(PDF p. 9)*
- The SPP defines no path, network or routing functionality; aside from the APID it defines none of the mechanisms of a managed data path, which is configured by design or by a management system before data transfer. *(PDF p. 13)*
- APIDs are unique only within one naming domain, which usually corresponds to a spacecraft; the space project that owns the domain allocates the APIDs. CCSDS defines no standard APID domain naming service; missions sub-allocate the domain or extend it with mission-specific secondary-header fields. *(PDF p. 14)*
- SPP services are preconfigured, unidirectional, asynchronous, unconfirmed, incomplete and non-sequence-preserving; two-way exchanges need two managed data paths, one per direction. *(PDF p. 15)*
- The SPP gives no delivery confirmation and no retransmission; reliability is left to the user application or to higher-layer protocols such as LTP or CFDP, or to the Data Link Layer. *(PDF p. 17)*
- The nominal example uses three managed data paths for one instrument: preprocessed images to the ground analysis system, commands from the ground to the instrument, and periodic status back to the control system. *(PDF p. 19)*
- The main purpose of the EPP is to carry PDUs that have no authorised Packet Version Number over the Space Data Link Protocols, using their VC, MAP or Proximity-1 Packet Services. *(PDF p. 21)*
- The EPP carries exactly one user data unit per Encapsulation Packet, unchanged; the maximum data unit length is 4,294,967,287 octets. Unlike the SPP service, the EPP service is sequence-preserving, and the provider may signal gaps. *(PDF p. 22)*
- An EPP user is identified by the Encapsulated Protocol Identifier (EPI), registered in SANA; a SAP is the combination of a PVN, an EPI and an SDLP channel. *(PDF p. 23)*
- IP over CCSDS (CCSDS 702.1-B-1) carries IP PDUs one-for-one in Encapsulation Packets, using the Internet Protocol Extension (IPE) convention. *(PDF p. 25)*
- Point-to-point reliability for packets can come from COP-1 (telecommand frames) or COP-P (Proximity-1 frames); isochronous data can use the Insert Zone of AOS or USLP. *(PDF p. 25)*
- The maximum Space Packet is 65536 octets; larger data units are segmented by the source application, and the primary-header Sequence Flags mark the first and last segments, with the secondary header available for a segment number. *(PDF p. 26)*
- Trade-off: the Encapsulation Packet header is configurable from 1 to 8 octets against the fixed 6-octet Space Packet primary header, but it has no field for ancillary data such as time or for extending the naming domain. *(PDF p. 27)*
