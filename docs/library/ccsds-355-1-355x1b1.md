## Summary

The CCSDS Recommended Standard for the **auxiliary procedures needed to operate [SDLS](../ccsds/sdls.md) over a space link**. The SDLS Blue Book defines how frames are protected; this one defines how keys and Security Associations (SAs) are managed and how the on-board security function is monitored. The model is an Initiator, usually the mission operations centre, commanding a Recipient, usually the spacecraft.

Section 2 outlines three services:

* **Key Management**: a two-tier symmetric scheme of master keys and session keys, a key lifecycle from pre-activation through active and deactivated to destroyed, and Over-The-Air Rekeying (OTAR), which is recommended but optional for missions with pre-loaded keys.
* **SA Management**: a state model Null, Unkeyed, Keyed and Operational, with Create, Rekey, Start, Stop, Expire and Delete transitions, plus setting and reading the anti-replay sequence number (ARSN) and its window.
* **Monitoring and Control**: Ping, security log status, dump and erase, Self-Test and Alarm Flag Reset.

Section 3 defines each procedure. Section 4 covers interfaces. EP PDUs travel as packets on a dedicated TC MAP, a TM or AOS VC packet service or a USLP MAP, and they must be protected by SDLS authentication or authenticated encryption. Section 4 also defines the 32-bit **Frame Security Report (FSR)**, a new Type-2 OCF carried in TM, AOS or USLP frames and alternated with the CLCW. Section 5 gives the PDU formats: a TLV-based EP PDU with an 8-bit tag (command or reply, CCSDS or user, service group, procedure ID) and a 16-bit length. Sections 6 and 7 cover managed parameters and conformance. Annex D gives a baseline implementation: AES-GCM with 256-bit keys, 96-bit IV and 128-bit MAC for OTAR and key verification, at most 28 keys per OTAR command so that it fits a 1024-octet frame, and the reserved SPIs 0 and 65535 for EP traffic.


## Key points

- The standard defines the Key Management, SA Management and SDLS Monitoring and Control services, their data structures and their interfaces with the SDL and SDLS protocols; it does not mandate cryptographic algorithms for key generation and management. *(PDF p. 11)*
- A goal is a new telemetry OCF type, the Frame Security Report, fully compatible with TM, AOS and USLP. *(PDF p. 12)*
- Initiator (usually the MOC) and Recipient (usually the spacecraft) are the two peers; the ARSN starts at zero when an SA is activated and increments for every frame sent on it. *(PDF p. 13)*
- Key management is a two-tier symmetric infrastructure: master keys (key-encryption keys) for management and session keys (traffic keys) for SDLS operations, refreshed by OTAR; OTAR is recommended but not required if a mission flies with pre-loaded keys only. *(PDF p. 17)*
- Key lifecycle states are Pre-Activation, Active, Deactivated and Destroyed, with Key Activation, Deactivation, Destruction and Verification transitions; the Suspended state of the Symmetric Key Management practice is not used. *(PDF p. 17)*
- SA state model: Null -(Create SA)-&gt; Unkeyed -(Rekey SA)-&gt; Keyed -(Start SA)-&gt; Operational, reversed by Stop SA, Expire SA and Delete SA; static missions need only Start and Stop with pre-loaded SAs. *(PDF p. 18)*
- Because an OCF can hold only one control word, the FSR is multiplexed with the CLCW in a mission-specific pattern. *(PDF p. 19)*
- EP PDUs use a dedicated MAP of the TC MAP packet service, the TM or AOS VC packet service, or the USLP MAP packet service. *(PDF p. 63)*
- The 32-bit FSR holds Control Word Type '1' (1 bit; a CLCW is '0'), FSR Version Number '100' (3 bits), Alarm flag (1), Bad SN, Bad MAC and Bad SA flags (1 bit each), Last SPI (16) and the 8 LSBs of the ARSN (8), and it is sampled for each received SDLS-protected frame. *(PDF p. 64)*
- The FSR Alarm Flag latches at '1' once any frame has been rejected by the Recipient Security Function and stays set until reset by a dedicated command; the other flags reflect only the last frame. *(PDF p. 65)*
- All EP command PDUs must be sent over an SDLS channel protected by authentication or authenticated encryption; the reserved SPIs 0 and 65535 may be used for EP traffic, and using a different SA from the one being affected is good practice. *(PDF p. 67)*
- EP commands and replies use a TLV format: an 8-bit Tag (Procedure Type, User Flag, 2-bit Service Group, 4-bit Procedure ID) and a 16-bit Data Field Length in bits. *(PDF p. 69)*
- Service Group values: 00 Key Management, 01 SA Management for Initiator-to-Recipient SAs, 10 SA Management for Recipient-to-Initiator SAs, 11 Security Monitoring and Control; Table 5-1 assigns procedure IDs (for example OTAR 0001, Start SA 1011, Ping 0001). *(PDF p. 71)*
- SA management managed parameters include SPI 1-65534, service type, Security Header IV (1-32 octets), SN (2-8 octets), PL (1-2 octets) and Trailer MAC (8-64 octets) lengths, the authentication bit mask, ARSN and ARSN window. *(PDF p. 102)*
- Baseline mode: FSR as OCF Type 2 alternating with the CLCW when COP-1 reports on the same VC, no TLV nesting, and the two reserved SPIs for EP PDUs. *(PDF p. 120)*
- Baseline OTAR and Key Verification use AES-GCM with 256-bit keys, a 96-bit IV and a 128-bit MAC; Key Destruction and Key Inventory are not in the baseline. *(PDF p. 121)*
- A baseline OTAR command carries a 16-bit master key ID, a 96-bit IV, N encrypted key blocks of 272 bits (16-bit key ID plus 256-bit key) and a 128-bit MAC, with N &lt;= 28 so that the PDU (at most 995 octets) fits a 1024-octet frame. *(PDF p. 122)*
