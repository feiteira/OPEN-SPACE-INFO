## Summary

A short CCSDS Blue Book in the 902 family of Space Communication Cross Support Service Management (SCCS-SM) standards, which grew out of the concept in [CCSDS 902.0-G-1](../library/ccsds-902-0-902x0g1.md). It defines the **Service Package Data Format (SPDF)**. This is the XML message a TT&C service provider (a ground-station or relay network) sends back to a mission to report which requested service packages were scheduled. The message gives the scheduled times, the antenna (aperture) and the configuration that apply. It closes the loop on a Service Package Request made with the SMURF format (CCSDS 902.9-B-1). The concepts of online services and service packages come from the SLE Cross Support Reference Model ([CCSDS 910.4-B-2](../library/ccsds-910-4-910x4b2e1s.md)). The wiki page is [SLE service management](../ccsds/sle/service-management.md).

Section 1 places the SPDF among the other 902 books (Simple Schedule Format, Service Catalog, Service Agreement and Configuration Profile, Event Sequence, Common Data Entities, and others) and gives the mission-planning use case. Section 2 explains the two equivalent encodings. **Type 1** is compact: it references configuration profiles, trajectories, event sequences and Delta-DOR scan patterns, and lists only the parameters that were modified. **Type 2** embeds the complete configuration profile, event sequence and DDOR scan pattern contents. Section 3 specifies the UML classes, most of which inherit from the Common Data Entities (CCSDS 902.12-M-2). These are the header with its servicePkgUsage enumeration, the body with spaceUserNode and serviceReqRef, and the ServicePkg with its ID, beginning/end of track in CCSDS ASCII Time Code B and an optional status. Section 3 also covers aperture location and the Type 1/Type 2 online-package classes. Annex A is the ICS proforma, Annex B covers security and the SANA registries (with the 'UNR::' prefix for unregistered values), and Annex C points to the normative XSD '902x04b01-SPDF.xsd'.


## Key points

- The SPDF expresses a package of one or more services (typically telecommand, telemetry and tracking) from a service provider to a mission user. It tells spacecraft operators which ground-station or relay resources are scheduled for them and how they are configured. *(PDF p. 9)*
- Service package data can be sent in a 'Type 1' or a 'Type 2' format. They differ only in how much is conveyed directly and how much is referenced: Type 1 references the Service Configuration Profiles, and Type 2 includes them in full. *(PDF p. 10)*
- The standard covers only the data format and content, not the protocols or methods used to exchange it. *(PDF p. 10)*
- The Service Package is sent by the Provider CSSS to the Mission when the source Service Package Request has been scheduled, in reply to later queries, and to document later modifications. *(PDF p. 15)*
- Parameter extensions are outside the scope of the standard. They should be documented in an ICD agreed by the parties and registered with SANA. *(PDF p. 16)*
- One SPDF instance can carry several ServicePkg elements. All of them should use the same type (all Type 1 or all Type 2). *(PDF p. 16)*
- A Type 1 online package holds a configuration profile reference, optional trajectory, event sequence and DDOR scan pattern references, and a list of modified parameters (resource, parameter, value). *(PDF p. 17)*
- The normative XML Schema mapping is a 'virtual annex' published as separate schema files. *(PDF p. 17)*
- servicePkgUsage is a mandatory enumeration with the values INTERFACE-TEST, OPERATIONAL and OTHER. When the header startTime and endTime are present, they must span the earliest start and latest end of the contained services. *(PDF p. 20)*
- ServicePkgBody carries the mandatory spaceUserNode (a SANA-registered spacecraft name) and serviceReqRef (for example the ServiceReqID of the SMURF request). *(PDF p. 21)*
- ServicePkg carries servicePackageID, beginningOfTrack and endOfTrack (CCSDS ASCII Time Code B) and an optional servicePackageStatus. The recommended status values are CREATED, SCHEDULED, DELETED, ARCHIVED, EXECUTING and ABORTED. *(PDF p. 22)*
- In a Type 1 package, one concrete AbstractModCProfParm (or AbstractModESeqParm) instance is required for each configuration-profile (or event-sequence) parameter that differs from the referenced profile. *(PDF p. 29)*
- Only SANA-registered values should be used for originatingOrganization, spaceUserNode, siteRef and apertureRef. Unregistered values should be prefixed with 'UNR::'. *(PDF p. 48)*
- The schema file is '902x04b01-SPDF.xsd', which includes '902x12m02-CDE.xsd'. Both are distributed through the SANA service-management XML schema registry and a CCSDS-CSSM GitHub release (SANA_Release-20260526). *(PDF p. 50)*
