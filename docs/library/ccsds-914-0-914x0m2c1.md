## Summary

The CCSDS Recommended Practice that defines a **C++ Application Program Interface for SLE transfer services**. It is a component-based API, independent of the communications technology, that SLE user applications (such as a mission control system) and provider applications (ground station equipment) can link against, so that SLE software packages can be exchanged and reused. It also eases gateways between different technologies. This core document covers what is common to all services; the service-specific parts are in the companion books 915.1/915.2/915.5 (RAF, RCF, ROCF) and 916.1/916.3 (FCLTU, FSP). See [SLE over TCP/IP (ISP1) and the SLE API](../ccsds/sle/isp1-and-api.md).

The API supports three generations of service specifications, identified by the BIND version number. It deliberately omits BIND version negotiation and provider-initiated binding. Section 2 is a UML logical model with six packages: API Proxy (technology-specific communication, the PDU translator, access control and peer authentication), API Service Element (it creates and configures service instances, handles BIND/UNBIND and enforces the SLE state tables), Common Control Interfaces, SLE Application (interfaces the application must supply, for example ISLE_Reporter, ISLE_Trace and ISLE_TimeSource), SLE Operations (operation objects such as ISLE_Bind and ISLE_TransferBuffer) and SLE Utilities (time, credentials, service instance identifiers). Section 3 specifies each component, including the 'Protected 1' credential generation with a DER-encoded HashInput, which Cor. 1 points to CCSDS 913.1-B for the hash algorithm, and the handling of threads and events. Section 4 gives the state tables for associations and service instances. Annex A is the normative C++ interface specification. Annex B defines COM-style HRESULT result codes, Annex C the service instance identifier for version-1 services, Annex D a COM-like 'simple component model' (IUnknown-style interfaces with reference counting), and Annex E the conformance options.


## Key points

- Issue 2 (September 2015) supersedes issue 1 (October 2008). Technical Corrigendum 1 (August 2016) makes the one-way hash function refer to CCSDS 913.1-B and removes the reference to the Secure Hash Algorithm standard. *(PDF p. 7)*
- The Recommended Practice defines a C++ API for SLE transfer services that is independent of the communications technology. The API can be configured for user or provider applications and simplifies gateways. *(PDF p. 11)*
- Only the parts common to all SLE services are defined here. The service-specific APIs are in CCSDS 915.1-M-2 (RAF), 915.2-M-2 (RCF), 915.5-M-2 (ROCF), 916.1-M-2 (FCLTU) and 916.3-M-2 (FSP). *(PDF p. 11)*
- Exceptions to SLE conformance: BIND version-number negotiation is not supported (an unsupported version is rejected with 'version number not supported'), and provider-initiated binding for return services is not included. *(PDF p. 12)*
- Three generations are supported. G1: RAF, RCF and FCLTU with BIND version 1. G2: RAF, RCF and FCLTU version 2, plus ROCF and FSP version 1. G3: RAF, RCF, ROCF, FCLTU and FSP with BIND version 4, as printed. *(PDF p. 12)*
- G1 interoperates with peers that follow the TML of ESOC's 'Specification of a SLE API Proxy for TCP/IP and ASN.1' (SLES-SW-API-0002-TOS-GCI, Issue 1.1, February 2001). G2 and G3 interoperate with peers that follow ISP1 (CCSDS 913.1-B-2). *(PDF p. 13)*
- The API is decomposed into the packages API Proxy, API Service Element, Common Control Interfaces, SLE Application, SLE Operations and SLE Utilities. *(PDF p. 29)*
- The API Proxy hides all technology-specific aspects and performs system-level access control and peer authentication. Its PDU Translator is the only proxy element that depends on the SLE service type. *(PDF p. 30)*
- Credentials are generated and checked with the 'Protected 1' procedure of ISO/IEC 9594-8, applied to a DER-encoded HashInput (time, random number, user name, password). Cor. 1 points to 913.1-B for the hash function. *(PDF p. 143)*
- Result codes follow the COM HRESULT layout: a 1-bit severity, 2 reserved bits, a facility and a 16-bit code. SLE-specific codes are in facility ITF (4), above hex 0200. *(PDF p. 312)*
- The API defines its own minimal COM-like component model, because COM itself needs a special run-time and registry that are not available on all platforms. *(PDF p. 321)*
- Conformance allows limited implementations, such as a 'lightweight' user-only API or a provider-only API, through defined optional features of the Proxy and the Service Element. *(PDF p. 330)*
