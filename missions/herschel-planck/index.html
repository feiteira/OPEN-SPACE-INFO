    Herschel and Planck¶

    Herschel and Planck are two very different ESA science satellites that were developed together: ESA commissioned them jointly under the Horizon 2000 scientific programme, and commonality between the two missions and between their mission phases was a key design driver for cost reasons.1 Herschel is an infrared observatory; Planck measures the Cosmic Microwave Background with receivers cooled to very low temperatures. Both were to fly to Lissajous orbits around the second Lagrange point (L2), separate soon after launch and then operate independently.2

    For this wiki the pair matters because it is a well-documented example of a project that put SCOS-2000 everywhere: in the ESOC Mission Operations Centre, in the spacecraft Central Checkout System used for system tests, and in the instrument teams' own electrical ground support equipment (EGSE) and real-time assessment systems.6962 One system database, the Herschel/Planck System Database (HPSDB), collected the MIB data and generated the SCOS-2000 and checkout files for them.627 This page follows the data: the operations requirements that shaped the packets, the packet structures and the space link, the HPSDB and its rules for reading and writing MIB files, how a database release was produced and named, the Herschel science ground segment's tailoring of the MIB, the Planck LFI telemetry chain, and the EGSE history. The SCOS-2000-centred case study, including the April 2000 decision meeting and the HCSS telecommand-history interfaces, is on Herschel/Planck: SCOS-2000 in a science mission ground segment; the bit-level layouts of the interface control documents (packets, frames, the EGSE router, the PIPE protocol and the checkout system's MIB) are on Herschel/Planck interface documents.

    The industrial organisation explains why so many database interfaces existed.     Operations requirements: the OIRD¶

    The Herschel/Planck Operations Interface Requirements Document (SCI-PT-RS-07360, issue 2.2, printed date "31 September 2003", prepared at ESOC by S. J. Dodsworth and S. Matussi) states what the spacecraft and payloads must provide so that ESOC can operate them, and what must be delivered to the MOC to prepare operations.11 Its packet chapter is derived from the PUS (applicable document AD-1, ECSS-E-70/41 Draft 5.3, April 2001); the Space/Ground ICD (SCI-PT-ICD-07418) and the Packet Structure ICD (PS-ICD, cited as SCI-PT-IF-07527) hold the detailed frame and packet layouts.11 Both are now in the library, as SGICD issue 3.2 of 1 December 2004 and PS-ICD issue 6.0 of 25 January 2008 (see below). The PS-ICD's own reference is SCI-PT-ICD-07527; for traceability its requirements name their parent requirements with tags such as [P:SCI-PT-RS-07360#3.1-PACK-14, which points to OIRD requirement PACK-14.907879 Requirements marked "P" apply to spacecraft and payloads, "PO" apply to the spacecraft and may be relevant to payloads, and unmarked ones apply to the spacecraft only.11 The 2001 revision made the SCOS-2000 Database Import ICD an applicable document.12

    Operations concept¶

    Science operations run from an on-board schedule outside ground contact, so the spacecraft and instruments need on-board monitoring and autonomy; packet telemetry is expected to help order the daily dump (status first, then events and command verification reports, then observation data).14 The document insists that operations use the same telemetry and telecommand database as the EGSE, delivered to the operations implementers in time.14 The general concepts it fixes are:1516

    • Telecommand delivery. Every command is a telecommand packet sent via the Command and Data Management System (CDMS), from ground, the mission timeline or an on-board procedure. The APID names the destination; APID plus sequence control identify one command instance; type and subtype give its meaning; the acknowledgement field selects the verification reports (ST[01]).
    • Telemetry collection. Data are polled from units by the CDMS and kept in mass memory until erased by ground command. Packet kinds are housekeeping, science (not processed by the CDMS), telecommand reports, event reports and memory dumps.
    • Packetisation by the CDMS for units that only deliver discrete signals.
    • On-board monitoring by tables, with an event packet at each transition. The document notes this deviates from the PUS, which offers a transition reporting list (ST[12]); events can trigger a telecommand (ST[19]).
    • On-board control procedures (OBCPs) written in a Spacecraft Control Language running in the CDMS (ST[18]; see also ECSS-E-ST-70-01C).
    • Functions as permanently available "black boxes" that can be started, stopped or given instructions (ST[08]).
    • One spacecraft time reference that time-stamps all TM packets, distributed to the instruments at power-on and then updated at agreed intervals (ST[09]).

    The Satellite Database requirements¶

    Section 4.2 of the OIRD defines the database that became the HPSDB:20

    • The prime contractor and the instrument teams deliver a Satellite Database (SDB) with all telemetry and telecommand data, command sequences, software parameters and commands; it is a single common database for system engineering, AIV and operations (SDBC-1, SDBC-2).
    • Its content follows the SCOS-2000 Database Import ICD (AD-8, issue 5.1) and Annex 2, is internally consistent, consistent with the Flight Dynamics Database and with all on-board software, has no duplications and no irrelevant data, and records every update down to field level (SDBC-4 to SDBC-12).
    • Deliveries: version 0 for the instrument AVM, version 1 at launch minus 36 months, version 2 at L-24 months, version 3 one month before SVT 1 (complete, with flight values), version 4 one month before SVT 2, and a pre-launch update at L-1 month (SDBD-1). Each delivery carries a configuration control file with field-level changes, the spacecraft build standard and the on-board software versions; the database is delivered as ORACLE data files (SDBD-2 to SDBD-5).

    Annex A2 adds that the SDB is delivered "according to AD-8" together with a Configuration Control File (version, release date, per-file versions and change tables listing old and new values, date and initials) and a Spacecraft Configuration File (model EQM or PFM, build standard, on-board software versions).21 Annex A4 delegates item names to the Herschel/Planck Naming Convention (H-P-1-ASPI-SP-0141) and names flight procedures FCP_<subsystem>_nnnn, contingency procedures CRP_<subsystem>_nnnn and timelines TDoyFfNn.22

    The Packet Structure ICD¶

    The Packet Structure ICD (PS-ICD, SCI-PT-ICD-07527) complements the ESA packet telemetry and telecommand standards with all mission-specific details of the data exchanged between on-board applications and their ground counterparts, for both spacecraft and all instruments; Appendix 9 adds the protocol of the satellite data bus. It is agreed between the ESA project manager, ESOC and the prime contractor and then controlled by the prime.79 Issue 1 dates from 1 September 2000 and issue 2 from 12 July 2001; requirement identifiers came with issue 3 (2002-2003), issue 4 draft 0 of 25 July 2003 was the first after the document's hand-over to Alcatel Space, and issue 6.0 of 25 January 2008 is the formal release in the library.808182 The full specification is read field by field on Herschel/Planck interface documents; this section keeps what matters for the mission's databases.

    Headers and limits¶

    Both headers follow the ESA packet standards with mission rules.838485

    • Telecommands are stand-alone packets (sequence flags 0b11) of at most 248 octets, a packet length field whose value (octets in the data field minus 1) is always odd, so that the packet is a whole number of 16-bit words, and a 32-bit data field header with a secondary header flag of 0, PUS version 0, four acknowledgement bits, type, subtype and a spare octet. Commands stored in the mission timeline are encapsulated as variable octet strings in MTL telecommands, inserted with TC(11,4), which leaves 228 octets for the embedded packet.156
    • The 14-bit TC sequence count is split: the 3 most significant bits are a source part that names the generator of the command, the other 11 bits a counter kept by that source for each APID, which the receiver never checks for monotony. A verification report must copy the full sequence control field to identify the command.
    • Telemetry packets are at most 1024 octets, with one source sequence count per APID so the ground can detect losses; only science packets TM(21,x) may use the grouping flags. The 80-bit data field header holds a spare bit, PUS version 0, 4 spare bits, type, subtype, a spare octet and a 48-bit CUC time (4 octets coarse, 2 fine).159 The data field header flag is 0 only in time and idle packets.
    Source part Generator of the telecommand
    0b000 Ground, highest priority, all sources
    0b001 Failure detection, isolation and recovery (FDIR) telecommands of the CDMU
    0b010 Mission timeline (maintained by ground, executed by the CDMU)
    0b011 On-board control procedures executed by the CDMU
    0b100 Ground, low priority, all sources
    0b101 FDIR telecommands of the attitude control computer (ACC)

    The source part is how the mission met OIRD requirement TCV-6 (see above).8319 Its definition was extended in issue 3.0 of April 2003.80 In a database release of late 2007 the prime switched all telecommands from "ground high priority" to "ground low priority" by default, that is from source 0b000 to 0b100.100

    Inference

    Reading the release note's priority change as a change of the default source part is this wiki's interpretation: the note does not name the header field, but "ground high priority" and "ground low priority" are the PS-ICD's names for the source values 0b000 and 0b100.

    The packets as seen by instrument test equipment¶

    Almost two years before the PS-ICD's first formal release (issue 4.0 of 7 November 2003),157 the HIFI team's TEI TMTC packet ICD (SRON-U/HIFI/SP/2001-011, issue 1.0, 19 December 2001) restated the headers for the packets exchanged with HIFI's test equipment interfaces (TEI), citing the PS-ICD issue 2.0 draft 2 as applicable document.23 Its header layouts are the same as those of PS-ICD issue 6.0 above, which is this wiki's comparison of the two documents.248385

    Telecommand source packet. The primary header is the usual 48-bit Space Packet header, but the 14-bit sequence count is split into a 3-bit source field (always 0b000 for these test equipment commands) and an 11-bit counter, which each source maintains per APID and which wraps to 0.23 This matches the note to the OIRD's requirement TCV-6, which places the command source in the source sequence counter of the packet header.19

    Telemetry source packet. The TM primary header has the 2-bit segmentation flags and a 14-bit source sequence counter; its packet length is always odd. The 80-bit data field header holds a spare bit, a 3-bit PUS version (0), 4 spare bits, type, subtype, a spare octet, and a 48-bit on-board time of 32 bits of coarse seconds and 16 bits of fine sub-seconds; the packet ends with a 16-bit packet error control field.24

    The PUS version value 0 is printed in both headers of the TEI ICD, whereas ECSS-E-70-41A (2003) tells users to set the TC and the TM PUS version to 1, noting in footnotes that version 0 was used by the earlier ESA PUS.2326 The TEI ICD predates that issue and follows a PS-ICD draft, so its value 0 matches the earlier ESA PUS convention. The PS-ICD settles the question for the mission: issue 6.0 of 2008 permits only PUS version number 0, in the telecommand and in the telemetry data field header alike, five years after ECSS-E-70-41A had asked for 1.8385 Every TEI accepts a Set OBS-ID command TC(8,4) (function 1, activity 1, a 16-bit structure ID and a 32-bit observation identifier, matching PACK-15) and a connection test TC(17,1), and reports acceptance with TM(1,1) or TM(1,2); the failure report carries an 8-bit code (0 illegal APID, 1 bad length, 2 bad checksum, 3 illegal type, 4 illegal subtype, 5 illegal or inconsistent application data) and an 8-bit parameter.25

    The Herschel/Planck System Database (HPSDB)¶

    Why a system database¶

    The HPSDB was procured by AAS-F to keep data consistent between engineering, on-board software, AIT and flight operations, and to support the commonality between the two satellites; GMV developed it.6 It is operated at a central site where final data are stored and consistency is maintained, with several mirror sites; the system EGSE requirement GRQT-0002b asks the Central Checkout System to support an HPSDB mirror site.670 Export files from the HPSDB are used to build the on-board software and to produce the TM/TC definitions in SCOS-2000 format for AIT and operations.6 Looking back in 2015, Thales Alenia Space summarised the two ESA requirements behind it: commonality (between the two spacecraft, and the same data shared by different users), achieved through physical instantiation and category flags, and smooth transition (reuse of validated data from one programme phase to the next, up to operations), achieved through logical instantiation and category flags.148

    The data model has four levels:6

    • Element - building blocks such as a star tracker or the ASW elements for common, Herschel and Planck data;
    • Subsystem - for example the ACMS or the Central Data Management Subsystem (ground support equipment is also modelled as a subsystem), built from element data plus subsystem-specific data;
    • Model - for example the Herschel and Planck service modules or the protoflight models, built from subsystems;
    • Generic - data usable by any other definition, such as ON/OFF curves and TM/TC packet headers.

    Consistency is enforced by instantiation of "boxes": every box exists at least as a theoretical box (design data, e.g. a default reaction-wheel friction coefficient) and as real boxes (measured data for one unit). Logical instantiation builds subsystems from elements and models from subsystems; physical instantiation creates several real copies of a theoretical box, for example two real star trackers.6

    How HPSDB reads and writes MIB files (H-P-1-ASP-TN-1060)¶

    The Alcatel Alenia Space note MIB files processing by HPSDB (H-P-1-ASP-TN-1060, issue 1, dated 07/02/2006; draft 1D1 of 02/02/2006 was sent to ESA to close an action from an instrument database meeting in September 2005) documents how HPSDB ingests and generates two flavours of MIB "bridge files": S2K files for the instrument EGSE, which used MIB ICD issue 5.1 and was "version 2.3eP5 based on SCOS 2000 2.3e", and CCS files for the HPCCS central checkout, which had its own external ICD (H-P-4-TE-ID-8020).27 It lists the constraints that an input file must satisfy so that HPSDB writes back an identical file. Constraints printed in bold cannot be checked by HPSDB and remain the user's responsibility; the others are checked at load time.27

    Full round-trip compatibility was not always possible. The note's first example is the packet-to-SPID relation: HPSDB allows several TM packets to map to one SCOS packet (SPID), while the MIB ICD allows any-to-any mappings provided that only one is valid at a time.27 The CCS also had functions that SCOS-2000 then lacked, for example selection of a calibration by condition, event limits and critical telecommands, and SCOS configuration files such as MISCconfig differed between installations.27

    The note's twenty general rules (G1-G20) are the clearest public statement of what a system database needs on top of the MIB ICD:28303132

    The naming convention, with a real example¶

    HPSDB identifiers are built hierarchically. At element level, the first letter of a character identifier gives the item type and the remaining characters are free. At subsystem or model level, a subsystem letter is put in front (Z for a pseudo subsystem) and a three-digit position is appended (999 for the system pseudo position); numeric identifiers get a two-digit subsystem number in front instead (A = 00 ... Y = 25, 26 for the pseudo subsystem). Generic items use subsystem letter G, subsystem number 07, position 000 and element number 000.28

    Curves are NUMBER(6) in HPSDB (three digits of theoretical element number and three free digits) and unique across curve types. Because the S2K MIB fields were too short, an instrument S2K file codes a specific curve as a three-digit number matching the three free digits, and a generic curve as 1xxx, which stands for the HPSDB generic curve G000xxx000; verification stages and parameter range sets use the same trick (1xxxx for 07xxxx000, 1xxx for GRxxx000).29 GMV's user manual of 2005 describes a different mechanism for the generic items, mapping files loaded with the bridge files: in its examples SCOS curves 900, 901 and 905 are read as the generic curves 000900, 000901 and 000905, verification stage 9000 as the generic stage 079000000 and range set 0 as GR000000, and the files limit SCOS curve numbers to 999 and stage and range set numbers to 9999 "for HPSDB compliance".129130 Which of the two mechanisms the Herschel/Planck deliveries used is not stated in the available sources. The HIFI MIB of 2008 indeed numbers its curves with three digits, for example textual curve 249 (HI_Prime_red), numerical curves 293 to 301 and command curves 100 (HRH_switch) and 134 (HIF_mxbias_step_V), as the prime's fax of January 2003 had required (see Mission tailoring of the MIB).113114

    Table by table: examples of HPSDB processing¶

    Chapter 5 of the note goes through every MIB table field by field, stating the input processing, the HPSDB field, the output processing and the constraint.33 Some examples show how much a system database rewrites:

    • VDF is not loaded; on output HPSDB computes the version name from the selected date (by default the last validation date) and creates several records.34
    • PCF holds all kinds of parameter in one table - TC, TC software, TC header, TM, TM software, dynamic and static UDC, saved synthetic, MISC and (CCS only) system parameters.34
    • PID: HPSDB splits the MIB table into a TM packet definition and a SCOS packet definition, allows only many-to-one links from TM packets to SPIDs (AIT wanted one-to-one), forces PID_TPSD to the SPID or -1, PID_TIME and PID_VALID to Y, and requires one PID_DFHSIZE (default 16) per SPID.35
    • PIC is never loaded: to support smooth transition it is defined once in the generic part of HPSDB, every Herschel/Planck SCOS and CCS user had to implement the same table, and it is regenerated from generic data on output.35
    • Parameter sets (PST, PSV, CPS, PVS, PSM): "Not supported by CCS", constraint "do not use", although HPSDB can load them.36
    • Specific CCS data: the note also processes tables that existed only in the CCS ICD - conditional calibration CUR, groups GRP, GRPA, GRPK, SCOE definitions SCO, TC and TM distribution TCD and TMD, and logarithmic curves LGF.37 That ICD, Terma's CCS External ICD H-P-4-TE-ID-8020 (issue 1.8, 18 January 2006), declares the import ICD issue 5.1 fully applicable to the checkout system except for its listed changes; they are analysed on Mission tailoring of the MIB.131132

    The HPSDB after Herschel and Planck¶

    At SESP 2015 Thales Alenia Space presented the System Reference Data Base (SRDB), an adaptation of HPSDB for the MTG programme.     The HCSS MIB Clarification and Tailoring Note¶

    The Herschel Common Science System (HCSS) is the common software of the Herschel science ground segment. It uses MIB data to build instrument-related commands and to interpret downlinked data for clients such as Quick Look Assessment (QLA) and Interactive Analysis (IA); the MIB itself is produced by an external MIB editor and handed over as ASCII files that the HCSS MIB ingestion software validates.45 Note HSC/DOC/0300 defines that interface. The library copy is issue 1.5 (21 December 2004, prepared by H. Siddiqui, approved by the Herschel Science Centre and the PACS, HIFI and SPIRE teams); its change record runs from issue 0.1 (14 January 2003) and issue 1.5 moved the applicable ICD to 5.2 and the naming convention to 2.1.46 The note says that the ICD and the naming convention "are however found to be ambiguous in places" and therefore clarifies them, tailors them for Herschel and lists the checks.45

    Clarifications of the ICD include: one line per record with OS line endings and exactly N-1 tabs for N fields (trailing grey fields may be omitted); mandatory numeric fields must not be blank; non-mandatory fields without default are empty (0, 0.0 or empty string); an out-of-limits condition is raised only strictly below the low or above the high limit; PLF_OFFBY/PLF_OFFBI count from the end of the SCOS-2000 packet header, which equals the start of the source packet when the generic packetiser is used; bit 0 of PLF_OFFBI is the most significant bit; and decimal numbers use a point.48 Three of these came with ESOC Document Change Requests: DCR 286 (an optional field may be left empty but its separator must be present), DCR 309 (the PLF_OFFBY reference point) and DCR 308 (bit 0 of PLF_OFFBI is the most significant); the note reproduces their text with the e-mail exchange between the Herschel Science Centre and the SCOS-2000 team of 5 December 2002. The note cites no DCR for the decimal-point rule.4849

    Herschel constraints for the final interface include:505152

    • all ICD tables in one directory, synthetic parameter definitions in synthetic/, plus an extra two-column command durations table used by the HCSS Common Uplink System (CUS);
    • VDF ignored, constant parameters (PCF_NATUR = C) ignored;
    • a packet is identified by type, subtype, APID and SID, and a unique SPID is assumed for every packet type;
    • a PID_PI1_VAL greater than 0 is not allowed where PIC_PI1_OFF = -1;
    • every non-Z command needs at least four PCDF rows (version, type, data field header flag and APID), which contradicts the ICD statement that PCDF_TCNAME is unique;
    • CDF_CNAME plus CDF_PNAME unique (repeated groups instead of repeated names);
    • command sequences (CSF, CSS, SDF, CSP) and parameter sets (PST, PSV, CPS, PVS) ignored;
    • TXP_FROM not above TXP_TO, and no overlapping textual calibration ranges;
    • short descriptions restricted to [a-zA-Z0-9_]+, and the first character of the name plus the description unique for commands, command parameters and parameters, as is APID plus PID_DESCR.

    Section 7 lists the checks, numbered 7.0.1 to 7.0.34 (7.0.6 removed), with their actions, from file names (7.0.1) to consistency of CDF_VALUE with de-calibration curves (7.0.32), CPC_RADIX (7.0.33) and a PID_INTER that must be null for every packet other than the periodic housekeeping report type 3, subtype 25 (7.0.34).53 Check 7.0.27 is worded as an error when TXP_TO is greater than TXP_FROM, the reverse of constraint 5.2.12 (the check itself cites 5.2.13); this wiki reads the constraint, not the check wording, as the intended rule.

    The SPID uniqueness discussion (2002)¶

    Constraint 5.2.5 assumed one SPID per packet type, but the PACS MIB of 2002 gave every TC verification packet SPID 10006, because the SCOS-2000 version of the time did not allow a range of SPIDs for packet type 1. The PACS team argued that this broke the ICD (a SPID must define the packet structure uniquely, and a parameter may have only one location per packet) and that SCOS-2000 abused PCF_VALID to select the location.54 ESOC's answer of 23 September 2002 confirmed the limitation - the verifier only "listens" to a predefined list of SPIDs for report-based verification - and added that Rosetta had implemented any SPID for service 1 packets and Cryosat a range of SPIDs, with integration of the useful Rosetta and Cryosat changes planned for SCOS-2000 R3.1 (reading all service-1 SPIDs from pid.dat).54

    The restriction has left no trace in the Solar Orbiter MIB of 2025: its 1 809 service-1 packet definitions on 31 APIDs (29 for each subtype) all have different SPIDs, one for each acceptance or completion success report and one for each failure code of TM(1,2) and TM(1,8), selected by a 16-bit identification field at offset 20.42 See command verification in the MIB for how those SPIDs are used today.

    The ACMS operations database (NLR-TP-2007-240)¶

    The NLR report Turning requirements into operations - Herschel/Planck ACMS Database Experience (April 2007, based on SpaceOps 2006 paper AIAA-2006-590) is a first-hand account of how a subsystem team produced MIB data for both satellites.1 The relevant PUS services for ACMS operations were service 3 (generated by the basic software from a datapool of ASW and BSW parameters), service 5 and service 8 (most ACMS-specific commands).4 The ASW held an on-board database (OBDB) of more than 3 000 parameters. Because service 3 can only report datapool parameters, every parameter of interest had to be in the datapool; a later interface let the ASW define its own 16/32/64-bit datapool entries and identifiers (DIDs).4

    A dedicated database was not planned at first. It became necessary in phase B because the Word telemetry document could not be kept consistent by hand, the interface was larger than for other Dutch Space subsystems, SCOS-2000 in the ACMS test equipment needed every TM/TC detail including operational identifiers, and the HPSDB was not yet mature enough to rely on.5 The team built it in the DOORS requirements tool, with formal modules for parameters, parameter types (with their PTC/PFC), units (with HPSDB and SCOS-2000 representations of at most four characters), enumerations, conversions, command characteristics, TC and TM packet structures, packet identification criteria, packet identifiers, alphanumeric displays, HPSDB boxes and a change log.8 The off-the-shelf SCOS-2000 MS Access database was rejected because it served one mission only, had no object-level configuration control and could not link ASW data to the ASW specification.7

    Each object carries spacecraft (Herschel, Planck or common), software (ASW or BSW) and first/last version attributes, so that version-specific SCOS-2000 and HPSDB files are generated from one CSV export; exports are kept under CVS instead of DOORS baselines, and a ccsdiff script compares the .dat files generated by HPSDB with those used in ACMS AIT. GMV provided the tool that converts the ACMS XML into HPSDB XML.9 The report's five recommendations - integrate the database with specifications and ICDs, use database identifiers in tests, keep TM/TC identifiers independent between requirements, software, test and operations but traceable, version every object, and use inheritance and instantiation - end with a call to standardise the database design for all space programmes.10

    Planck LFI: SCOS-2000 inside an instrument ground segment¶

    The paper Level 1 on-ground telemetry handling in Planck LFI (Zacchei et al., JINST 4 T12019, 2009; arXiv:1001.4730) describes the first processing level of the Low Frequency Instrument's Data Processing Centre (DPC). The Planck science ground segment consists of the LFI and HFI DPCs, the MOC and the Planck Science Office; Level 1 takes raw telemetry compliant with the ESA packet telemetry standard and the PUS and produces Time Ordered Information (TOI) per housekeeping and science parameter.55

    What the instrument sends¶

    LFI has 22 radiometers behind 11 feed horns at 30, 44 and 70 GHz; each radiometer gives two outputs, so there are 44 science channels. A 14-bit ADC in the Data Acquisition Electronics digitises each output, and the Radiometer Electronics Box Assembly (REBA) runs the on-board software, builds the HK and science packets and executes telecommands.56 To stay within 53.5 kbps the REBA offers seven processing types: PType 0 raw samples, 1 co-added samples, 2 and 3 mixing with gain modulation factors and requantisation to 16-bit integers, and 4 to 6 lossless adaptive arithmetic compression of types 0, 2 and 3. Nominally all 44 detectors use PType 5, and every 15 minutes one detector is additionally processed in PType 1 for calibration.5657

    Packets follow the ESA packet telemetry and telecommand standards, the CCSDS packet telemetry recommendations and the PUS: a primary header (type, APID, sequence counter modulo 16384, length), a fixed secondary header (service type, subtype and a 48-bit CUC on-board time), a Structure ID, a data segment and a 16-bit CRC; science packets add a tertiary header with detector, phase-switch status, processing type, REBA parameters and number of samples.58 The four fields APID, type, subtype and SID identify the structure of a packet for the ground software, and the mission defined custom services for science telemetry.58

    Part Content Source
    Primary header Packet type, APID, sequence count (modulo 16384), packet length 58
    Secondary header Service type and subtype; on-board time as 48-bit CUC 58
    SID Structure identifier; with APID, type and subtype it selects the layout 58
    Tertiary header (science only) Detector ID, phase switch status, processing type, REBA parameters, number of samples 59
    Data segment Science: up to 980 bytes; HK: parameter fields per the PUS parameter types 5960

    Housekeeping is periodic (essential every 32 s, for low-gain-antenna periods; fast every 1 s, with some packets super-commutated into four identical sub-fields so that a packet comes every 4 s; slow every 64 s) or non-periodic (command responses, events and alarms).60 The paper notes that the MIB's PLF table gives, besides the offset, the number of occurrences of a parameter in super-commutated packets, the field PLF_NBOCC; that the sub-field spacing goes into PLF_LGOCC follows from the ICD field definitions rather than from the paper.6240

    The Level 1 architecture¶

    Level 1 has three subsystems: a Real-Time Assessment system (RTA) based on SCOS-2000; a Telemetry Handler (TMH) built largely by the ISDC team in Geneva by reusing software from the INTEGRAL ground segment; and a Telemetry Quick-Look system (TQL) built on ROOT.61 SCOS-2000 receives the telemetry, maintains a local raw packet archive, checks for missing, damaged or duplicated packets, displays calibrated HK, sends telecommands and raises out-of-limits alarms; it could not process the compressed science telemetry, which is why it served mainly as EGSE and HK monitor.62

    Configuring SCOS-2000 for LFI meant writing the MIB: the paper names PID (APID, type, subtype and SID as the packet's "primary key"), PCF (parameter ID, description, type and calibration reference) and PLF (parameter offset and number of occurrences for super-commutated packets), plus out-of-limits values with validity criteria for different test conditions (e.g. warm or cryogenic), conditional calibrations and displays.62 The TMH then reads the same MIB files to extract and calibrate HK parameters, so one database serves both the SCOS-2000 displays and the scientific pipeline.63

    The tailoring followed the SCOS-2000 releases. For instrument-only tests the EGSE ran SCOS 2.3e; its telemetry receiver was modified to replay simulated LFI data, and a task using the Flight Dynamics Interface (FDIF) let the TMH register as a SCOS client and receive live packets. From the Planck integration tests onward the EGSE was the HPCCS, which talks to external equipment through the Packet Interface Protocol for EGSE (PIPE); a new LFIGateway relayed telemetry from the HPCCS operated by the spacecraft team to the LFI team's own HPCCS and TMH/TQL.62 The PIPE format is defined in the prime's EGSE Interface Requirement Specification (H-P-1-ASPI-IS-0121, issue 4.1, 14 December 2004): every message starts with a 10-byte header (message ID, virtual channel ID, remaining length, a 4-byte request ID and the synchronisation word 0xFADE) followed by a body, which for spacecraft telecommands and telemetry is the TC packet or the TM source packet, embedded unchanged,158 and the CCS distributes telemetry to the instrument stations on their own LAN with message ID 0x20; the LFI EGSE was the station with APID 2041.135137138140 The protocol is described on SCOS-2000 as EGSE and field by field on the interface documents page.

    The TMH pipeline has three parts: Data Receive stores raw packets in a FITS archive and forwards them to TQL; the TeleMetry Unscrambler (TMU) groups HK packets by APID, type, subtype and SID and science packets by detector and processing type, into hour-long FITS files of an intermediate archive; and TM2TOI produces the final TOI archive, one FITS file per HK parameter, with raw and calibrated values and quality flags.63 Science samples are then decompressed, dequantised, demixed and converted from ADU to volts using parameters from the tertiary header and from HK telemetry, and each sample's time is rebuilt from the packet time, the sample index and the sampling frequency.64

    Instrument EGSE: from the 2000 decision to SCOS EGSE 2.3e P5¶

    The decision. At an ESOC meeting on 19 April 2000 with all FIRST/Planck instrument teams, ESA confirmed SCOS-2000 as the baseline for MOC operations and stated that it would support the product for flight operations and EGSE; the minutes record that "All PI groups unanimously stated their intention to use SCOS 200 as a basis for EGSE and RTA" (sic).6566 The PROBA experience (SCOS 2 with an ORACLE database, a Delphi router and Tcl/Tk procedures) was presented as the model, and the database question was left to the prime contractor, with ORACLE, MS Access (the Integral tool) or custom solutions as options.65 The SCOS-2000 presentation of 18 April 2000 proposed reusing PROBA's router and Tcl/Tk procedure tool with MS Access database editors from Integral.67 The full story is on Herschel/Planck: SCOS-2000 in a science mission ground segment and SCOS-2000 as EGSE.

    The building blocks. The Herschel EGSE integration plan (SRON-U/HIFI/PL/2001-1, issue 1, 6 November 2001) lists who delivered each block of the common instrument-level test EGSE (EGSE-ILT) of HIFI, PACS and SPIRE: SCOS-2000, the OBSM and the MIB editor from ESA, the SCOS gateway from ESTEC, the test-equipment interface and TM/TC router from HIFI, test control from PACS and the CDMS simulator from SPIRE; each of the router, test-equipment interface, CDMS-simulator and test-control tests loads a test MIB into SCOS-2000 as its second step, right after connecting the subsystems.68

    The router. The HIFI team's Herschel EGSE Packet Router ICD (SRON-G/HIFI/ICD/2001-001, issue 1.1, 23 October 2001), agreed by the EGSE and ICC managers of the three instruments and the HSC, specifies the Java router that linked SCOS-2000, the test equipment interfaces, the HCSS telemetry ingester and the CDMS simulator during instrument level tests. Clients open a TCP connection, name themselves and subscribe to packet addresses: the APID for telemetry, 4096 plus the APID for telecommands. Every message has a 5-octet header (a message type from 1 to 12 and a 4-octet content length), and the same interface was to deliver raw telemetry to the HCSS in later phases.143144146147 The router has no security, handshake or flow control of its own; details are on SCOS-2000 as EGSE.145

    The kernel. ESA's EGSE based on SCOS 2000 - The EGSE & Mission Control System (TOS-EMG/01-1029, issue 4.0, 2004-03-09) is the user manual of the "SCOS EGSE Release 2.3e P5" delivered to the Herschel/Planck instrument developers.     The system level. Alcatel's EGSE General Requirements Specification (H-P-1-ASPI-SP-0045, issue 03, 10/06/02) records the baseline that instrument EGSEs and the ESOC flight control system are both based on SCOS-2000, so that instrument station software, test procedures and OBCPs move from instrument tests through system tests to commissioning with minimal change.
