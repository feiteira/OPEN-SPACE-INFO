    Rosetta, Mars Express and Venus Express¶

    Rosetta (launched March 2004 towards comet Churyumov-Gerasimenko), Mars Express (launched June 2003) and Venus Express (launched November 2005) form ESOC's interplanetary mission family: missions on Earth-escape trajectories that share a common spacecraft platform, and therefore the same processors and major software functions, similar sensors, actuators and mass-memory interfaces, reused payloads, similar autonomy and identical operator interaction with the mission control system.1 The three ground segments were built as one: Rosetta and Mars Express share near-identical data management systems and on-board software, most data-system components were developed jointly, and Venus Express was a delta development of the existing system.116 One set of interface documents serves all three missions - the Data Delivery Interface Document carries three document numbers, RO-ESC-IF-5003, MEX-ESC-IF-5003 and VEX-ESC-IF-5003.16

    This page describes that family's data systems as the public documents show them: the SCOS-2000 based Mission Control System (RMCS, MEMCS, VMCS), the GDDS-based Data Disposition System that delivered data to the principal investigators (PIs), the formats of everything that crossed that interface, the interface to flight dynamics (including the mission's MIB extensions), the interface to the ground station IF and modem system, and the lessons that went back into SCOS-2000 and on to Solar Orbiter.

    One family, one system: the delta approach¶

    ESOC's "mission family" concept groups missions with a high degree of commonality in platform or operational profile; at the time of the 2007 ESA Bulletin article the families in use were interplanetary, Earth observation, observatory and navigation.1 Interplanetary missions need things that Earth-orbiting missions do not: long signal delays must be taken into account in telecommand verification and telemetry time-stamping, special commanding protocols such as file transfer handle the delayed space-ground interaction, and the MCS must cope with two or more parallel data streams - one real-time and one or more carrying the telemetry recorded during long non-coverage periods.1 The GSAW 2005 view of the same idea summarises the planetary family as "long propagation delay, on-board autonomy".4

    For the interplanetary MCS a two-layer delta approach was used: effectively one system that could serve each of the three missions by reconfiguration, so that the effort for one mission covered all three.2 For the family's operational simulators, the article adds, the teething problems of immature or late on-board software and early spacecraft documentation were mainly borne by the first mission of the family, Rosetta.2 When Venus Express was preparing for launch its MCS used the then most recent SCOS-2000 (version 3.1) while the flying Rosetta and Mars Express stayed on the previous version; after Venus Express validation, migrating Rosetta to the new interplanetary kernel took a few months and Mars Express only a few weeks.3

    Inference

    The article calls the original interplanetary MCS approach "two-layer" (one reconfigurable system above SCOS-2000) and later speaks of a "new interplanetary kernel". Drawing that kernel as a separate layer between the missions and SCOS-2000, as in the diagram above, is this wiki's reading of those two statements.

    The ground segment¶

    The Mars Express and Venus Express chapters describe the same Operations Control Centre (OCC) architecture:611

    • the Mission Control System (MCS; VMCS for Venus Express), based on SCOS-2000, which exchanges telemetry and telecommands with the ground stations, processes housekeeping in real time (command verification, out-of-limits checks), converts on-board time to UTC with an accuracy better than 2 ms, calibrates parameters, pre-transmission-validates and sends commands, keeps a complete command history and manages the operational database and the on-board software;
    • the Data Disposition (or Distribution) System (DDS; VDDS for Venus Express), based on the Generic Data Disposition System (GDDS), for remote near-real-time and off-line access by the scientific community and for the regular production of raw data media;
    • the mission-specific Mission Planning System (MPS), producing machine-readable schedules for the spacecraft and the ground stations;
    • the off-line Flight Operations Procedure (FOP) system, whose procedures and command sequences are imported into the operational database;
    • for Venus Express, the Telemetry Data Retrieval System (TDRS), giving authorised users intranet and internet access to telemetry parameter values.11

    Telemetry reaches the MCS through the Network Controller and Telemetry Receiver System (NCTRS), after the station has time-stamped it with the Earth Reception Time (ERT); NCTRS also forwards telecommands, stores tracking data (antenna angles, range, Doppler) for the Flight Dynamics System via the File Transfer System and for the PIs via the DDS, and sends station files such as antenna pointing data.712

    How the GDDS works¶

    The DDS lets PIs and other external users request data extracted from the mission archives maintained by the SCOS-2000 kernel. That archive has two parts: a packet archive with historical telemetry, telecommand and derived data, and a file archive with flight dynamics and planning data; a SCOS-2000 file generation process can also create file-based summaries such as command history reports.914 Requests arrive in three ways - scheduled "standing orders", the web interface, or request files sent by FTP - and are expressed in a recursive XML query language, used internally and exposed on the FTP interface, which allows filters to be combined.9 A central DDS server keeps a request list, initiates (often several) low-level archive retrievals from the MCS over a CORBA interface and collates the results into a single delivery per request; it also keeps the database of authorised users and their delivery addresses.914 Delivery is on line through the web interface (for previewing small amounts, embedded as a byte stream in the XML response), by FTP, or on physical media.914 The general GDDS concept and its successor EDDS are described on GDDS and mission DDIDs and EDDS.

    The Data Delivery Interface Document (RO/MEX/VEX-ESC-IF-5003)¶

    Purpose and history¶

    The DDID defines the data delivery interface between the RMCS, MEMCS and VMCS and their science communities: requests for on-line data sent by PIs, the on-line data sent back, and the off-line full data sets on Raw Data Media (RDMs). Together with the Command Request Interface Document (CRID, RO-ESC-IF-0004) it defines the complete interface between the MCS and the science communities, and it is "broadly based on the Cluster DDID".1824 Its applicable documents include CCSDS 620.0-B-2.1 (SFDU structure and construction rules), ESA PSS-04-106 (packet telemetry) and the Rosetta/MEX and VEX generic TM/TC ICDs; the reference documents include CCSDS 301.0-B-2 for time codes.19

    What the DDS must do¶

    The on-line requirements, taken from the RMCS/MEMCS User Requirements Document, are:20

    Requirement Value
    Delivery mechanism File transfer or Web interface, always in response to a user request (client-server, DDS is the server)
    Request content One request command per request file: a subset of packets of one data source (APID), one auxiliary file, a set of auxiliary files of one type over a time range, or a catalogue
    Response content Acknowledgement, catalogue entry and the data in the same transfer; an error message in the acknowledgement on failure
    Latency Start of data within 15 minutes of the request (subject to volume and load)
    On-line retention 3 months for Mars Express; the entire mission for Rosetta
    Queue Up to 12 requested files per user at a time
    Capacity At least 1000 MB per day in total, split into configurable per-user quotas agreed with the Project Scientist; a file that would exceed the day's quota is not delivered
    Sub-sampling Every N-th packet on request (SampleRate)
    Automatic delivery New versions of selected auxiliary files, and periodic TM/TC files, sent to registered PIs

    The retention figures come from §5.4 rather than from the requirement list, which states 3 months.26 Off-line delivery was planned for Mars Express and Venus Express but not for Rosetta: an RDM (CD-ROM for Mars Express) holds an integer number of days of data split on the on-board generation time (default one day per CD-ROM for MEX), up to four RDMs per period, with only the auxiliary data of the same period and all format descriptions on every medium so that each RDM is self-describing; RDMs are produced inside ESOC by an automatic scheduler and delivered within one month (nominally three weeks for MEDDS).2131 Mars Express PIs received CD-ROMs weekly, and Venus Express data went on DVDs, one copy to the VSOC and one kept at the VMOC.813

    The interface itself¶

    Requests are made through the mission's web interface or by FTP with an ASCII XML request file, and responses come back by FTP or through the web interface; the PI side needs a web browser, FTP and an RDM reader, and the DDS hardware was a Sun/Solaris 8 server with 1 GB of memory.23 To avoid partial transfers, FTP transfers in both directions use a two-step put-and-rename with a temporary file name; a PI who receives neither data nor an error message within 2 hours resubmits.25 The DDS hosts sit on ESOC's front-end LAN, separated from the operational LAN that hosts the rest of the MCS by a bridge; access is restricted to an authorised user list controlled by the Project Scientist, each user's data go to a pre-specified node, auxiliary data are open to all authorised users and experiment data only to their own team.27 No integrity checks beyond the transport protocol are foreseen, and outages of several days over the public internet are possible.2728

    The XML request¶

    A request (onlineRequest) contains one general block and one or more item blocks. The general block (RequestInfoType) has a free comment, user information, a delivery block with exactly one of RDM, FTP or Online, format options (compression NONE or ZIP, SFDUrequired, an optional mission format) and an optional earliest start time.3267 Each item (DataItemType) gives a data type, a data source mnemonic (typically an APID, a "super-APID" or an auxiliary file type), a catalogue flag, optional keywords and an optional filter tree.33 Keywords include SampleRate (every N-th packet, applied per history file - VC0 and VC1, real time and playback - before merging) and VolumeSize (a byte limit that stops the delivery at whichever of end time or volume comes first; the C3 schema names this request keyword MaxVolumeSize).3467 Filters are trees of unary (OP_NOT), binary (OP_AND, OP_OR) and leaf nodes; leaves compare a filterable keyword with OP_GT, OP_LT, OP_EQ, OP_GTE or OP_LTE.35 The schema names the binary node element bin, whereas the DDID table calls it "Binary".6835

    Filterable keywords are SourcePktsGenTime (on-board time converted to UTC), S2KPktsGenTime (the time the MCS archived the packet), Type, SubType, P1Val, P2Val (packet SID values; omitted means wildcard), ExecutionTime and UplinkTime for command history, and Name, TimeSpan, Release and Issue for auxiliary files.36 The C3 schema also contains CreationTime, EventTime and Validity filter keywords, the data type EVT and event request keywords (Application, EventType, Severity, Workstation, MessageFilter); its change record says that this issue added the event keywords.6765

    Illustrative request (constructed for this page)

    The element names below are those of the C3 schema; the values are made up. The request asks for every 10th housekeeping packet of APID 1966, type 190, generated between two UTC times, delivered by FTP without SFDU packaging.

    <onlineRequest xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
               xsi:noNamespaceSchemaLocation="GDDSRequest.xsd" userRequestId="wiki-example-1">
  <general>
    <comment>illustrative request</comment>
    <userInfo><username>PI_ACCOUNT</username><FTPpassword>********</FTPpassword></userInfo>
    <destInfo><FTP><filename>tco_packets</filename><directory></directory></FTP></destInfo>
    <formatInfo><compression>NONE</compression><SFDUrequired>false</SFDUrequired></formatInfo>
    <dataInfo/>
  </general>
  <item>
    <dataType>TLM</dataType>
    <dataSource>1966</dataSource>
    <catalogueRequest>false</catalogueRequest>
    <keyword><SampleRate>10</SampleRate></keyword>
    <filter>
      <bin operation="OP_AND">
        <lhs><leaf operation="OP_GTE"><valuePair><SourcePktsGenTime><a_dateTime>2005-01-01T00:00:00Z</a_dateTime></SourcePktsGenTime></valuePair></leaf></lhs>
        <rhs><leaf operation="OP_LT"><valuePair><SourcePktsGenTime><a_dateTime>2005-01-02T00:00:00Z</a_dateTime></SourcePktsGenTime></valuePair></leaf></rhs>

    The DDID explains a subtlety of command history requests: SCOS-2000 associates seven times with a telecommand (specified release, uplink and execution times; actual uplink and execution times updated by verification; and the packet filing and creation times, which are the primary and secondary keys of the TC history file). The DDS can only retrieve by the two keys, so the times in a returned header may differ slightly from those in the request; requesting by specified execution time is recommended.37

    Telemetry data and the DDS packet header¶

    Requested telemetry arrives as a time-ordered set of complete, unsegmented packets, each preceded by an 18-octet DDS packet header; the MCS has already reassembled packets from transfer frames, and the packet contents are unprocessed.39 The header is bit- and byte-packed rather than written in PVL for compactness.40

    The packet itself complies with ESA PSS-04-106 and is specialised by the mission's generic TM/TC ICDs, which are not in the library.41 The SCET (Spacecraft Event Time) is the calibrated time of generation of the first bit of the packet, held as two 32-bit integers in the Sun/Solaris format.3940 The header field values are:40

    Field Values defined in issue C2
    Ground station ID 0x0D ESA Villafranca 2, 0x15 ESA Kourou, 0x16 NDIULite (SVTs), 0x17 ESA New Norcia, 0x18 ESA Cebreros, 0x22/0x67 NASA Goldstone (old/new), 0x23/0x70 NASA Canberra (old/new), 0x24/0x6C NASA Madrid (old/new), 0x7F ESA/ESOC test station, 0x82 NDIU classic (SVTs); the DSN ID change-over took place in November/December 2003
    SLE service 0-3 real-time SLC, MC, VC and bad frames; 4-7 the same with real-time flow control; 8-11 the same off-line
    Time quality 0 good, 1 inaccurate, 2 bad (see time correlation below)

    The SLE code names the service channel through which the frames arrived; the DDID lists only the abbreviations SLC, MC and VC plus bad frames. This wiki reads MC and VC as the master-channel and virtual-channel SLE return services (the DDID does not expand them); the expansion of SLC is not stated in the available sources.

    The same numbers in 2019

    The ESA station IDs in this header are the decimal numbers that the Solar Orbiter DDID of 2019 lists for the ground station field of the SCOS-2000 packet header: 0x15 = 21 Kourou, 0x17 = 23 New Norcia, 0x18 = 24 Cebreros; Solar Orbiter adds 22 Perth, 25 Malargüe and 30 Maspalomas. The time quality values 0 good, 1 inaccurate, 2 bad are also identical.4098

    Packets in one delivery file are in chronological order of either the source packet generation time or the S2K packet generation time, depending on the time keyword used. The DDID's example: with SPIDs 1200-1202 defined on APID 10 and SPID 1203 on APID 23, a request for APID 10 returns the APID 10 packets of all three SPIDs interleaved by time. The SPID is "an ID number internal to the Mission Control System".41 SPIDs are defined in the MIB's pid table.

    Command history and verification flags¶

    Command history comes either as raw TC packets or as printouts in full or brief mode.43 Each raw packet is preceded by a DDS command packet header:44

    The command uplink stage (CUV) is the CLCW-based verification that the frame reached the spacecraft (COP-1); CAV and CEV are the acceptance and execution stages verified separately on real-time (VC0) and playback (VC1) telemetry.44 Each flag word is 16 bits with exactly one bit set, numbered from the least significant bit; a word of zeros means the stage was not applicable.45

    stateDiagram-v2
  [*] --> IDLE
  IDLE --> PENDING: stage window opens
  PENDING --> PASSED: success in TM
  PENDING --> FAILED: failure in TM
  PENDING --> UNKNOWN: window closes, no TM
  UNKNOWN --> UNVERIFIED: consolidated by controllers
  PENDING --> TIMED_OUT: CUV only, no response
  PENDING --> ASSUMED: CUV only, later CAV/CEV passed
  TIMED_OUT --> ASSUMED: CUV only, later CAV/CEV passed
  PASSED --> [*]
  FAILED --> [*]
  UNVERIFIED --> [*]

    Inference

    The DDID defines the statuses and says that only PASSED, FAILED and UNVERIFIED are final; the transitions in the diagram are this wiki's reading of those definitions. The stage model itself is the SCOS-2000 one described on Command verification in the MIB.

    Two inconsistencies in issue C2 are worth knowing: the text calls the header 30 octets long and says the data record starts at octet 30, but the table continues with the command and parent-sequence names at octets 30-45 (46 octets in total); and the issue B5 text has the same 30-octet statement.4464 The data record is the encoded telecommand packet as sent to the spacecraft in a transfer frame.45

    Data sources and ADIDs¶

    Every delivered stream has a data source and a data type - CAT catalogue, AUX auxiliary, TLM telemetry, CMH command history - and a registered data description identified by an ADID.46 Per mission, ADIDs start with EROS, EMEX or EVEX: D001-D008 describe the RDM directory listing, cumulative index, off-line and on-line catalogue formats, acknowledgement, volume production information and master or partial catalogue; Txxx describes telemetry for one APID or one super-APID (all telemetry of one instrument); C001-C003 describe command history packets and full or brief printouts.46 Rosetta's super-APIDs -1 to -20 cover the instruments (LCC, RPC, OSIRIS, ALICE, MIRO, ROSINA, COSIMA, CONSERT, VIRTIS, GIADA) and service-specific streams for the RSOC and RPC (acknowledgement service 1, housekeeping service 3, events service 5, dumps service 6, science service 12) - several of these ADIDs are printed with the prefix ESOS (for example ESOSTLCC) instead of EROS; auxiliary sources include attitude (ATNR, ATPR), comet characteristics, environment and kinematics, Doppler files for flight dynamics and the radio-science AGC files AGC1/AGC2 from the IFMS.46 Mars Express has super-APIDs such as EMEXTHRS (HRSC), EMEXTPFS (PFS) and EMEXTASP (ASPERA-3).47

    SFDU packaging¶

    The DDS packages deliveries as CCSDS Standard Formatted Data Units (SFDUs), chosen because the data come in many packet and file sizes and each RDM must be understandable without external documentation; on-line users who do not want SFDUs can treat the extra header bytes as spare or switch packaging off.22 The building block is the Label-Value-Object (LVO): a fixed 20-octet label followed by a value field.48

    Class IDs fall into structure classes (Z exchange data unit, F description data unit, U application data unit), service classes (R replacement, C data administration) and data classes (I application data, S supplementary, D and E data description, K catalogue attributes, V volume production).48 CCSDS ADIDs start with CCSD, for example CCSD0001 (value contains LVOs), CCSD0003/CCSD0004 (PVL statements), CCSD0005 (a description data unit) and CCSD0009 (an application data unit).49 All products are packed in an Exchange Data Unit (EDU); a telemetry delivery is a CCSD Z 0001 EDU holding a V LVO with the request and response status, a K LVO with the catalogue entry and an I LVO whose value is the sequence of DDS headers and packets.5042 The DDID's delimitation paragraph mentions an ID "A" with an eight-octet decimal length, while the list of IDs gives "B" (binary length) and "F"; the C2 text is inconsistent here.48

    MCS products: internal packets, time correlation and command files¶

    Packets created or relabelled by the MCS¶

    Appendix K lists the packets that originate in the MCS. Externally generated data that the MCS cannot place elsewhere get APID 1966 and type 190: bad telemetry packets (subtype 30), packets undefined in the database (38), and good, bad and idle transfer frames (21, 20, 29); idle and time packets keep their externally defined APID with type 190 (subtype 0 for idle packets).51 Packets generated inside the MCS have no source packet header, only the SCOS-2000 TM packet header and a data field: the time correlation coefficient packet (1966/190/40) and the telemetry constants packet (1966/190/0), which carries operator-set parameters from the TM Spacon process.5156

    Time correlation¶

    The procedure follows ESA PSS-04-106: on board, the elapsed-time clock is sampled at the leading edge of the first bit of the attached sync marker of the VC0 frame with frame count 0 (or every 128, 64, ..., 1 frames) and sent in the spacecraft time source packet before the counter has advanced 255 frames; on ground the reception of the same bit is time-tagged in UTC.52 Rosetta, MEX and VEX could select one in every 256, 128, 64, 32 or 16 VC0 frames.52 At ESOC the packetiser takes the station's ERT of each "zeroth" VC0 frame and removes three delays - station internal (a fixed part per station plus a bit-rate part), the propagation delay from the Flight Dynamics one-way light time (OWLT) file, and the on-board frame processing (fixed plus bit-rate part) - to get the UTC at which the time packet was generated, and then emits a "time telemetry" packet (type 190, subtype 0, APID 0) pairing that UTC with the spacecraft time.53

    flowchart LR
  F["VC0 frame, count 0<br/>ERT from station clock"] --> C1["- ground station delay<br/>(fixed + bit-rate part)"]
  C1 --> C2["- propagation delay<br/>(FD OWLT file)"]
  C2 --> C3["- on-board delay<br/>(fixed + bit-rate part)"]
  C3 --> U["UTC of time-packet generation"]
  P["next spacecraft time packet<br/>(OBT sample)"] --> T
  U --> T["time telemetry packet<br/>type 190 / subtype 0 / APID 0"]
  T --> A[("archive")]
  A -- "FCT selects a time range" --> L["least-squares fit"]
  L -- "accepted, with validity start" --> K["TCO coefficient packet<br/>APID 1966 / 190 / 40"]

    The Flight Control Team triggers the fit manually over a chosen time range, accepts or rejects the result and gives a validity start time; a correlation stays valid until the next one, and packets stored on board are time-stamped with the correlation valid for their OBT, not the current one. The gradient should be nominally 1; one "substantially different from 1 should be treated with caution".53 The coefficient packet is not a spacecraft packet; its big-endian data field is 240 bits:54

    For this packet the SCET in the DDS header is the time from which the correlation is valid.54 The time quality of every other packet follows from the top bit of its OBT (set = invalid OBT): 0 good uses the correlation; 1 inaccurate means an invalid OBT on VC0, time-stamped with the frame ERT minus the delays; 2 bad is the same on VC1. Plausibility checks then compare a VC0 time stamp with the frame-derived UTC (at most a configurable, usually 2 s, ahead and 15 s behind) and a VC1 time stamp only for the "ahead" case; with autocorrection enabled, failures become bad with the frame time, otherwise a warning is logged.55 The current SCOS-2000 mechanism is described on Time correlation in SCOS-2000.

    Lander telecommand verification file (LTVF) and a decoded example¶

    The LTVF is a human-readable text file of the bit patterns of the commands on a manual stack, created on request for Lander operations; it lists for each command the stack row, mnemonic, description, source sequence count (SSC), PUS version, packet error control, packet header and data field.57 Its example contains 18 real encoded commands. Row 9, ZSV00007 "Set Period of HK packet 1 generation", reads:58

    Header : 1F 9C C0 01 00 09 19 03 1B 00      CRC: 3CBB
Data   : 00 01 00 50
    Bytes Field Value Meaning
    1F 9C Packet ID 0b000 1 1 11110011100 TC packet with data field header, APID 1948
    C0 01 Sequence control flags 0b11, count 1 stand-alone packet, SSC 1 (the LTVF "SSC" column shows 0001)
    00 09 Packet length 9 data field of 10 octets = 4 header + 4 application data + 2 CRC
    19 Data field header byte 0 0b0 001 1001 PUS version 1; acknowledge acceptance and completion
    03 1B Service type / subtype 3 / 27 housekeeping service, subtype 27
    00 Source ID 0
    00 01 00 50 Application data not decoded in the source
    3C BB Packet error control 0x3CBB CRC over the 14 preceding octets

    The PUS-A primary and data field header layouts are those of ECSS-E-70-41A §5.3.2-5.3.3; with the CRC-16 of its Annex A.1 (generator x^16 + x^12 + x^5 + 1, register preset to all ones) the 14 octets give 0x3CBB, exactly the value in the file. The same check reproduces the CRCs of rows 1, 4, 6 and 10.858858

    Inference

    PUS-A defines service 3 subtypes 1 to 26 only, so subtype 27 is a Rosetta-specific command, presumably the one named in the row description; its definition (the Rosetta/MEX generic TM/TC ICD) is not in the library.87 The LTVF "PUS" column shows 00 for every row while the encoded headers carry PUS version 1; the meaning of that column is not stated in the available sources. Row 4 (ZRP230D4, "MACRO: Execute Macro") uses service 230, which lies in the mission-specific range 128-255 of PUS-A.86

    How the CRC check was done

    A 20-line Python function computing the PUS-A CRC (initial value 0xFFFF, polynomial 0x1021, MSB first, no final XOR) was run with python3 -I on the hexadecimal strings of rows 1, 4, 6, 9 and 10 of the LTVF example; all five results equal the printed CRCs (D764, 1043, EAEC, 3CBB, 4AA0).

    Detailed Agenda Files (DAF)¶

    DAFs are text files that import telecommands into the RMCS/MEMCS/VMCS command sources (pass stack, mission timeline (MTL) stack, manual stack), normally written by the Mission Planning and Scheduling applications; MTL DAFs are also delivered to users through the DDS for traceability of their requests.59 They extend the SCOS-2000 Stack Import Interface (S2K-MCS-ICD-0002) and assume that the command definitions in the run-time database come from the same version of the mission database as the DAF; a version mismatch raises a warning.5960 Pass DAFs contain category (a) commands with absolute or ASAP release times; MTL DAFs carry service 11 time-tagged commands or deletions. The categories are (a) absolute release times, (b) absolute execution times with ASAP release, © release times relative to the first command, and (d) a mixture.60

    Final DAFs follow the file transfer system naming ffff_sordes_txxxxxxxxxxxxxx_vvvvv.ROS, with MDAF or PDAF as type, SCH (Rosetta scheduler) as source, RMA (RMCS prime) as destination, D for data, a 14-character field holding __YYMMDDhhmmss and a five-digit version.61 A file is a sequence of |-separated records: a base header (category, source, database version, start time, pass), then per command a header record (type, identifier, dispatch and release conditions, group, block and interlock conditions, verification stage, static and dynamic PTV states, parameter count, time-tagging, planning state, execution time, parent sequence, destination subsystem, source, earliest and latest release, insert/delete state, external ID) followed by one record per editable parameter (CDF_ELTYPE = E) in the order of CDF_BIT.62 These fields map onto the commanding tables and sequences of the MIB.

    The MCS-FDS interface and the mission's MIB extensions¶

    The Flight Dynamics System - Mission Control System ICD (RO-ESC-ID-5003, issue B1, 2003-03-07, prepared by Anite Systems for Rosetta and Mars Express) specifies everything exchanged between the MCS and ESOC flight dynamics.69 From the MCS, flight dynamics receives the MIB files extracted from the source database, packetised data (TM source packets, TC history packets and time coefficient history packets) retrieved from the DAS by the SCOS-2000/ORATOS Data Access software (SoDA) through the SCOS-2000 FDIF interface, tracking data files, and payload auxiliary data (scenario parameter lists from the RSOC).7071 ESA tracking files (ranging, Doppler 1 and 2, meteorological data, antenna angles, received signal strength) are stored on the IFMS at each station; the MCS "via the Network Interface Subsystem (NIS)" fetches them and stores them in the MCS FARC, while NASA/DSN tracking data come from the flight dynamics computer RACSO.70 In the other direction flight dynamics sends orbit, attitude, event and cometary files (archived in the DAS for the PIs), Flight Dynamics Requests and Direct Operations Requests (command request files defined in the CRID), trajectory data for ESA stations (STDMs, sent on through NIS) and for the DSN (EPMs, via RACSO to JPL), the OWLT file and the "interplanetary WIMPY" with ground station information.70 Mission archives and NCTRS and NIS describe the FARC and NIS in general.

    All files use the FTS naming TTTT_SSSDDD_txxxxxxxxxxxxxx_vvvvv.yyy (document type, source, destination, D, 14 free characters, version 00000-99999 with wrap-around, mission ROS or MEX, all upper case); external files are wrapped with tar inside an FTS file.72 The file tables list 40 file types for Rosetta and 33 for Mars Express, for example D1FD/D2FD Doppler, RGFD ranging, MTFD meteo and AAF_ antenna angles from the NIS nodes, ODF_ DSN tracking, OWLT, STDM, EVTR/EVTM event files, the planning files FECS, FTL_, PTR_ and SECS for Mars Express, and MIB_ - the MCS database files, sent from the MCS to flight dynamics (for Mars Express also to the MPX and POS nodes).7374

    The MIB as delivered to flight dynamics¶

    The MIB files are generated from the source database and tarred into one file. They follow the SCOS-2000 MIB ICD with mission-specific extensions:75

    Table Extension Definition
    ccf.dat CCF_DESCR widened Char(40) instead of 24 characters
    ccf.dat CCF_SUBSCH (field 20) Number(3), the on-board sub-schedule of the command
    pcf.dat PCF_DESCR widened Char(24) instead of 16 characters
    pcf.dat PCF_WDLEN (field 20) O = 8-bit or W = 16-bit boundary in the service 3 command
    pcf.dat PCF_GRPID (21), PCF_OFFSET (22) group ID and offset of the corresponding on-board parameter
    pcf.dat PCF_GLOBAL (23) G global or D detailed; only global parameters are named in service 3 telecommands

    Utility files travel with the tables: spid_hash.txt (source database packet name to SPID), calib_hash.txt (calibration name to calibration number), synparhash.txt (expressions of automatically generated synthetic parameters) and a list of packet types not converted into the vpd table.75 The DAF section names the mission database "RSDB" and the run-time database "RTDB", and the DAF reference list gives Database Import ICD issue 4.2 as the baseline of the time.6059

    Inference: the same extensions in the Solar Orbiter MIB

    Solar Orbiter's MCS shares its packetiser ICD and its MCS software requirements with BepiColombo (see Other missions).97 Its September 2025 MIB shows traits that match the Rosetta/MEX extensions: 2 876 of its 5 454 command descriptions are longer than the 24 characters of CCF_DESCR in ICD 7.0, the longest being exactly 40; parameter descriptions are at most 24 characters, the width that ICD 7.0 adopted after ICD 5.1's 16; all but 150 commands carry CCF_SUBSCHEDID, the sub-schedule field that ICD 6.0 standardised; and a non-ICD table pcf_glob_det links 8 704 "global" parameters to 56 631 "detailed" ones, with a third column whose values (0, 3, 4, 5, ...) look like bit offsets, the global/detailed split that PCF_GLOBAL expressed for Rosetta.9993949596 The lineage is this wiki's reading; no source states that Solar Orbiter inherited these conventions from Rosetta. The table is described on Mission tailoring.

    The IFMS-OCC interface: tracking and radio-science data¶

    The IF and Modem System (IFMS) in the ESTRACK stations produces the Doppler, ranging, gain and meteorological data (the measurements themselves are described on RF and ranging) that flight dynamics receives and that the DDS offers to radio-science users as AGC1/AGC2 files.7046 Its IFMS-OCC interface ICD (MakaluMedia, issue 11.4.0, 2006-08-09) describes the interface between the IFMS and data clients such as NCTRS; the library copy was taken from a Mars Express radio-science data set in ESA's Planetary Science Archive.76 The interface is pure FTP over TCP/IP: the IFMS is a read-only file server (stream mode, file structure, ASCII or image type), catalogue access is a directory listing, and "pseudo-on-line" access means fetching small data-set files that cover a short measurement duration.7778

    Data sets live under <root>/station/spacecraft/ and are named like PER1_CLU3_2002_108_OP_RG_145513_0001: station (4 characters), spacecraft (4), year, day of year, data-set kind (e.g. OP, TS, CL), DAP type, DAP start time hhmmss and a sequence ID that grows when a data set is closed and reopened (up to 7200 for a 20-hour DAP, coded on five digits beyond 9999); uncorrected ranging data get a .raw extension and compressed copies .gz.79 The ICD's own example states the DAP start as 1999-04-18 14:55:13 although the file name carries 2002, day 108 and 145513.79

    DAP type Content of each sample (besides sample number and time)
    D1, D2 Doppler 17.5 MHz NCO clock count, unwrapped carrier phase (turns), spurious-carrier flag, accumulated one-way delta delay (s)
    G1, G2 gain (AGC) carrier level (dBm), polarisation angle, incoherent AGC gain, channel A/B input power, carrier lock status
    ME meteo humidity (%), pressure (hPa), temperature (°C)
    RG ranging round-trip delay modulo ambiguity, code number 1-24, ambiguity-resolved flag, spurious flags, Doppler estimate, DSP lock and quality figures
    OL open loop binary records of complex RHC and LHC baseband samples

    Every data set starts with a header (station, spacecraft, kind, DAP type, reference time tag, first and last sample times, requestor DCP or STC, reason for opening such as DAP_Started or Max_Size_Reached, number of samples, sample period, oscillator and carrier indicators, ranging correction flag, sequence ID and the active configuration tables).80 The Doppler section gives the algorithm that turns phase counts into delta delay, with different formulas for coherent and non-coherent transponders.8182

    Open-loop data sets are binary: records of a 44-byte header (magic number 0xA3C725B6, length, message word, sample time and offset, filter centre frequency, gain and offsets) followed by 136 blocks of 6 bytes; depending on quantisation (1, 2, 4 or 12 bits) a block holds 12, 6, 3 or 1 complex samples of both polarisations, packed from the most significant bit.83

    The ICD is not fully consistent here either: the record layout comments the message word as type "3, 4, 5 or 6 dep on quantization", while the encoding table fixes bits 2-0 to message type 7 and puts the quantisation in bits 5-3, and it describes a sp_frameid word that the record layout does not contain.83 Support-log files record data-set open, close and delete events as a backup monitoring aid.84

    What the family gave back to SCOS-2000¶

    The SCOS-2000 documents record several capabilities that started as Rosetta mission specifics:

    • Service 1 SPIDs. In 2002 SCOS-2000 gave all TM(1,x) packets the same SPID because the verifier listened to a fixed SPID list; Rosetta modified it to accept any SPID for service 1 packets, and integration of the Rosetta (and Cryosat) changes was planned for R3.1.89 See Herschel and Planck.
    • Service 11 ground model. The on-board queue model in SCOS-2000 assumes the structure of the Rosetta spacecraft's service 11 packets as its reference implementation; missions with a different structure need modifications.90
    • Service 13 uplink. SCOS-2000 has no generic support for large data transfer, but a mission-specific uplink implementation exists from Rosetta, based on SCOS-2000-R3.1.91 See ST[13] Large packet transfer.
    • Reference documents. The MIB ICD issue 7.0 still lists the Rosetta Space/Ground ICD (RO-ESC-IF-5002, 1998) among its reference documents.92

    Already in 2003, ESOC listed the Rosetta, Mars Express and Venus Express MCSs among the SCOS-2000 client missions under development.5 Their data-delivery ideas - XML requests, catalogues, the SCOS-2000 packet header in deliveries, time quality - live on in EDDS and the Solar Orbiter DDID.
