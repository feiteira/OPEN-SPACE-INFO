    Uplink: from operator command to on-board execution¶

    A telecommand starts as a line in the MIB: a name, a packet header template, a list of parameters with their calibrations and allowed ranges, and the checks that will tell the ground whether it worked. An operator loads it onto a SCOS-2000 command stack, edits its parameters, and releases it. SCOS-2000 checks it (pre-transmission validation), encodes it as a PUS telecommand packet, and puts it into a TC transfer frame. The frame is protected by COP-1 retransmission and encoded as a CLTU. The SLE FCLTU service then radiates it at the ground station within its scheduled time window. On board, the decoder checks the frame, the FARM accepts it in sequence, and the destination application executes the request and reports back with PUS ST[01] verification reports. The ground matches these, and selected telemetry parameters, against the verification stages defined in the MIB. This page follows the command through every stage, links each one to its detailed page, and uses real Solar Orbiter definitions. The telemetry direction is described on Downlink.

    1. Command definition in the MIB¶

    In the SCOS-2000 database the central entity is the command definition in the ccf table. A command has PTV expressions (ptv, one-to-many and ANDed together) and verification stages (cvs, shared by many commands through the mapping table cvp). It also has parameter sets (pst via psm) and parameters (cpc, placed in the application data field by cdf). Each command parameter may reference one numerical (de-)calibration (cca/ccs), one textual calibration or alias set (paf/pas) and one range set (prf/prv). Each command also references one packet header (tcp), whose fields are described by pcpc and placed by pcdf.1

    The packet header template¶

    The PCDF rows say, bit by bit, where each header element sits and where its value comes from. The type is F for a fixed value, A, T, S or K for the APID, service type, subtype or acknowledgement flags taken from the CCF, and P for values that the command subsystem sets itself, such as the packet length and the source sequence counter.2 Operators cannot edit header parameters on the manual stack. The multiplexer maintains the source sequence counter per APID.2 The Solar Orbiter MIB defines four headers: NOM_TC for normal PUS commands (5,318 commands), HPC1_TC for CPDU high-priority commands (125), NO_HDR for frame-level control commands (5) and NOS2KHDR for NIS throw events (6).96 HPC1_TC is only the 6-octet primary header with the data field header flag fixed to 0, and its 125 commands have no service type or subtype.     Commands and their parameters¶

    The CCF row gives the name, description, header (CCF_PKTID), type, subtype and APID, and the number of elements. It also gives whether the command can be loaded stand-alone (CCF_EXEC) and which sources may plan it (CCF_PLAN).5 The default interlock scope and stage (CCF_ILSCOPE, CCF_ILSTAGE) and the subsystem follow.6 Then come the high-priority flag and fixed MAP ID for CPDU-type commands (CCF_HIPRI, CCF_MAPID), a redundant APID, the default acknowledgement flags (CCF_ACK, 0 to 15) and the default on-board sub-schedule.78 CCF_CTYPE marks the special cases. R is a control segment (reset MAP) and F a control frame (BC frame: Unlock or Set V(R)); for both, PCDF/CDF describe the frame data field instead of a packet. S is a packet without CRC, and T and N are SLE and NIS throw events that are never uplinked.4

    Each command element in CDF is a fixed area (A), a fixed parameter (F) or an editable parameter (E), at a bit offset from the start of the application data field. SCOS-2000 uses that offset only to sort the elements, which it then encodes one after the other without gaps.10 The value of an editable parameter can come from the parameter default (D), from a raw (R) or engineering (E) value given in CDF, or from a live telemetry parameter (T, a dynamic default).11 Unlike monitoring calibrations, command calibrations work in both directions: engineering to raw for encoding, raw to engineering for display. They must be one-to-one, and in ccs the engineering value is in CCS_XVALS and the raw value in CCS_YVALS.22 A range set accepts a value that lies within, or equals, the limits of any of its PRV rows, and a PRV row with no maximum is a single allowed value.23

    2. Command sequences¶

    A command sequence (csf) is an ordered list of elements (css), each a command, a nested sequence or a comment. Elements carry their own parameter values (sdf), and the sequence may declare formal parameters (csp) that act as placeholders filled in at load time. Nested sequences are expanded like macros when loaded, and a sequence must never contain itself. Since R5.0 the sequences are kept as XML in the FARC, and the ASCII tables remain for backward compatibility.13 Each element can say how its release time is computed: relative to the previous command (R), or relative to the sequence start (A), as a delta hh.mm.ss. It can also say whether it needs a separate manual dispatch ("ARM&GO", CSS_MANDISP), whether it is grouped (released as an uninterrupted batch) or blocked (aggregated into one segment), and how its interlock, PTV and CEV are set.15 The sequence-level flag CSF_IFTT says whether the sequence contains execution time-tagged commands. B lets the user choose at load time between on-board time-tagged and ground time-tagged release.14

    MIB sequences are one way of grouping commands. ECSS standardises two others: a language for checkout and operations procedures (PLUTO, ECSS-E-ST-70-32), and on-board control procedures that run on the spacecraft itself (OBCPs, ECSS-E-ST-70-01), which the PUS controls through ST[18].111 See PLUTO, OBCPs and, for how missions prepare their databases and procedures, operations preparation.

    3. The command stack and the release chain¶

    SCOS-2000's commanding functions include the manual stack, where commands are loaded with their parameters (with de-calibration) and execution time-tags. The stack also supports release dependencies, grouping, blocking, delta release times, interlocking, a master manual mode and a wait mode, static and dynamic PTV, and sequences with formal parameters. Next to it sit an autostack with restricted functions and no editing, and a multiplexer that lets several sources command in parallel. The command releaser interfaces to the external destination, the NCTRS. An on-board queue model tracks time-tagged commands, and a command verifier performs multi-stage verification and disables status consistency checks on the affected parameters.26 The command history records, for each command, the sequence that loaded it and the type of command source, its release and execution times, the transmission mode (AD or BD), the PTV and CAV/CEV check states, the interlock, the AD frame count, and the status of each verification stage. These are the columns of the TC history printout of the Rosetta, Mars Express and Venus Express control systems, whose data delivery interface document is public.29

    Interlocks stop further commanding until a command reaches a given stage. The scope can be global (G), local to the command source (L), local to the subsystem (S), global for the subsystem (B), local or subsystem only on verification failure (F, T), or none (N). The stage waited on can be ground station reception (R), uplink (U), on-board reception (O, treated as U in BD mode), application acceptance (A) or completion (C).6 Every Solar Orbiter command in the release defaults to no interlock (CCF_ILSCOPE = N). 5,443 commands name the completion stage C as their default interlock stage. The 5 frame-level NO_HDR commands carry the undocumented value N, and the 6 NIS throw events leave the field empty.99101

    Routing¶

    The releaser sends spacecraft commands to the NCTRS unless the optional dst table routes their APID elsewhere. The other choice is EGSE, as EGSE.SCOE for non-spacecraft commands or EGSE.TC.<address> for a TC front end.9 Solar Orbiter's release has a single DST row, which sends APID 1372 to EGSE.TC.0x8800, the very example given in the ICD.999 The NCTRS links the MCS to the ground station network and uses SLE for non-ESA stations.27 Outside ESA, DLR's GECCOS (derived from SCOS-2000) speaks the same bespoke NCTRS protocol, which is translated to standard SLE.28 See NCTRS, NIS and the ground station interface.

    4. Pre-transmission validation¶

    Before release, SCOS-2000 runs static PTV. Each ptv row requires a monitoring parameter (numerical, processed by the TM model) to equal a raw or engineering value. All rows of a command are ANDed together, and an invalid parameter fails the check.12 Dynamic PTV covers feasibility checks, time checks and interlocks, and both kinds can be overridden per sequence element (CSS_DYNPTV, CSS_STAPTV).17 In the Solar Orbiter archive the SCOS-2000 TC packet header records an uplink flag, which is 1 if the command passed PTV and is to be released and 0 if it failed.32

    Solar Orbiter uses static PTV sparingly. The release has five PTV rows. ZCD00D09 "Accept First Uplink Part" (TC(13,9)) requires the synthetic parameter NCDXS005 "Nb Immediate TCF" to be 0. Four SSMM file-transfer commands, among them ZSM00120 "SSMM Abort LLFT" (TC(13,145)), require NMAXS005 "SSMM FTS COMMANDING PTV" to be 0. Both parameters are dynamic OL synthetic parameters.100

    5. The PUS TC secondary header¶

    A telecommand packet carries a request from a ground application process to an on-board one.34 Apart from CPDU command packets, every PUS telecommand has a secondary header.36

    Field Bits Values Meaning
    TC packet PUS version number 4 2 Version 0 = ESA PUS, 1 = ECSS-E-70-41A.36
    Acknowledgement flags 4 bit 3 acceptance, bit 2 start, bit 1 progress, bit 0 completion Which successful stages to report. PUS numbers bits from the most significant (bit 0), so acceptance is the least significant bit of the field.3733
    Message type ID 8 + 8 service type, message subtype Identifies the request.37
    Source ID 16 Identifies the issuing application process; with the sequence count it identifies the packet uniquely.3735
    Spare optional Pads the header to whole words.37

    After the application data and optional spare comes the 16-bit packet error control field. For telecommands it is mandatory, and the mission chooses the ISO checksum or the CRC.38

    PUS-A has a 1-bit CCSDS secondary header flag (0 = non-CCSDS header), a 3-bit PUS version (1), a 4-bit Ack field, 8-bit type and subtype, an optional source ID of mission-defined length, and optional spare bits. Failure reports are generated by default, so the Ack bits request only the success acknowledgements. Service types 0 to 127 are reserved for the standard and 128 to 255 are mission-specific. The PEC is a checksum or CRC fixed for the mission.40

    Solar Orbiter sets the version to 1 and uses only the acceptance bit and the completion bit; the start and progress bits must be zero.49 Its CRC uses the generator polynomial \(X^{16}+X^{12}+X^5+1\) with an all-ones preset, computed over the whole packet except the CRC itself.50 Ground source IDs include 110 for the mission timeline, 111 for TC sequences, 112 for event-action recovery commands, 113 for the back-up timeline and 120 for direct commands.51 In the MIB, 5,225 commands have CCF_ACK = 9 (0b1001, acceptance and completion), 78 have 1 (acceptance only), 21 have 0, and 130 have none.99

    The ICD notes that SCOS-2000 matches each TM(1,x) report to its command by the 4 octets that echo the TC packet ID and sequence control, which must sit at the same position in every type-1 packet. Clearing an Ack bit at load time disables the corresponding report-based stage, but it cannot add a stage that the CVP table does not define.2421

    6. The Space Packet primary header for telecommands¶

    The primary header has the same layout as on the downlink. Here the packet type is 1, the APID names the destination application process, and the 14-bit field holds a sequence count or a packet name. With the source ID this identifies the packet.4735 Solar Orbiter splits the APID into a 7-bit process ID and a 4-bit category, which is fixed to 12 for telecommands. It sets the sequence flags to 0b11, and it keeps the sequence count per APID and source ID for ground traceability only: the application accepts commands whatever the counter.48 The packet data field is at most 242 octets: 4 octets of data field header, 236 octets of application data and the 2-octet CRC.48

    Two limits that agree

    SCOS-2000 limits a command to CMDP_MAX_BLOCK_SIZE octets, 248 by default. The space for parameters is then reduced by the header, the CRC and any time-tag wrapper (the TC(11,4) insert command).3 For Solar Orbiter, 6 octets of primary header plus the 242-octet maximum data field also give 248 octets. The match is this wiki's observation; the Solar Orbiter configuration value of the MISC variable is not stated in the available sources.

    7. The TC transfer frame and segment¶

    The TC Space Data Link Protocol carries packets in variable-length frames of up to 1,024 octets. A frame has a 5-octet primary header, a data field of up to 1,019 octets (1,017 with an FECF) and an optional 2-octet frame error control field.60

    Source: CCSDS 232.0-B-4 table 4-1.62

    The segment header is one octet: 2 sequence flags and a 6-bit multiplexer access point (MAP) ID. It is needed on a VC that has more than one MAP or that carries service data units too large for one frame. If it is used on a VC it must be used in every data frame of that VC, but it is never present in control-command frames. Sequence flags 0b11 mean an unsegmented service data unit or several whole packets.65

    The two control commands are Unlock, a single all-zeros octet, and Set V(R), three octets 0x82 0x00 followed by the new V(R).66 The receiving end applies frame validation checks to every frame, Type-A or Type-B. It checks the expected version number and MCID, header values consistent with the spacecraft's implemented features, a frame length that matches the octets received, and, if present, the FECF CRC. A frame that fails any check is discarded.68 The FECF uses the same CRC-16 as TM frames.67

    8. COP-1: FOP-1 on the ground, FARM-1 on board¶

The FARM-1 at the receiving end accepts Type-A frames only in strict sequence and reports its state in the CLCW.70 The AD service guarantees, with high probability, that no frame data unit is lost, duplicated or delivered out of order on that VC. It uses Type-AD frames for data and Type-BC frames for the Unlock and Set V(R) control commands. The BD service sends Type-BD frames that bypass acceptance and are only counted.71

    FARM-1's sliding window has a total width W that is fixed for the mission.     9. The CLTU: BCH coding, start and tail sequences¶

    The communications link transmission unit (CLTU) delimits and synchronises the coded frames. With BCH coding it is a 16-bit start sequence, a series of 64-bit BCH codewords and a 64-bit tail sequence.79

    Part Value Purpose
    Start sequence 0xEB90 (1110101110010000) Marks the start of the encoded data; also resolves bit-sense ambiguity.8078
    BCH codewords 56 information bits + 7 complemented parity bits + 1 filler bit (0) (63,56) modified BCH code, \(g(x) = x^7 + x^6 + x^2 + 1\); the complemented parity helps bit synchronisation and detects bit slips.82
    Fill alternating 0/1, starting with 0 Completes the last codeword.83
    Tail sequence 0xC5C5C5C5C5C5C579 A deliberately non-correctable pattern that stops decoding.81

    With BCH coding, randomization of the frames before encoding is required unless the designer verifies that the system works without it. The randomizer sequence comes from \(h(x) = x^8 + x^6 + x^4 + x^3 + x^2 + x + 1\) and repeats every 255 bits. With the LDPC option (64-bit start sequence 0x034776C7272895B0, (128,64) or (512,256) codewords) randomization is always applied.8580 The decoder on board moves between three states: inactive (no bit lock), search (bit-by-bit search for the start sequence) and decode. It returns to search when a codeword cannot be corrected, which is what the tail sequence provokes on purpose.84

    10. The physical layer operations procedure¶

    A PLOP defines the sequence of carrier modulation modes in a pass. CMM-1 is the unmodulated carrier, CMM-2 the carrier modulated with the acquisition sequence (alternating bits, preferably at least 16 octets), CMM-3 the carrier with a CLTU, and CMM-4 the carrier with the idle sequence.8788 PLOP-1 turns the modulation off after every CLTU, forcing the receiver back to inactive. PLOP-2 keeps the channel active and separates CLTUs by the tail sequence (and optional idle), leaving the receiver in search. At least one octet of idle sequence between CLTUs is recommended, to avoid a rare false start inside a tail. Missions whose planning began after September 2010 must use PLOP-2.8689

    11. SLE FCLTU: from the control centre to the antenna¶

    The Forward CLTU service lets the user send CLTUs to the spacecraft through a forward space link channel. The provider radiates them in the order received, bit for bit, without interpreting them. It can only check constraints such as the maximum length, and it works only in online delivery mode, with one service instance per physical channel.90 Its operations are:92

    Operation Invoker Purpose
    CLTU-BIND / CLTU-UNBIND user Establish or release the association
    CLTU-START / CLTU-STOP user Prepare for, or stop, transfer and radiation
    CLTU-TRANSFER-DATA user Hand over one CLTU, confirmed
    CLTU-ASYNC-NOTIFY provider Report events such as radiated, expired or production interrupted
    CLTU-SCHEDULE-STATUS-REPORT / CLTU-STATUS-REPORT user / provider Periodic or immediate status
    CLTU-GET-PARAMETER user Read a service parameter
    CLTU-THROW-EVENT user Ask complex management to act, for example on production settings
    CLTU-PEER-ABORT either Abort the association

    Each CLTU-TRANSFER-DATA invocation carries a monotonically increasing CLTU identification, an earliest and a latest radiation time (either may be null), a delay time (the minimum gap in microseconds before the next CLTU, interpreted according to the PLOP in effect), and whether a radiation report is wanted.9394 If radiation has not started by the latest radiation time, the provider notifies "sldu expired", discards the buffered CLTUs and blocks further transfers until the user stops and restarts the service. A "production interrupted" event has a similar blocking effect.95 The provider also reads the CLCWs from the return link to decide whether the physical channel is available, unless management configures it to ignore them.91 The same function generates the acquisition and idle sequences of the PLOP.91

    Inference

    Because the FCLTU provider radiates CLTUs unchanged, everything above the physical layer (packet, segment, frame, FOP-1, BCH encoding) must happen on the control-centre side before CLTU-TRANSFER-DATA. Which ESOC component (SCOS-2000 or the NCTRS) runs FOP-1 and builds the CLTU is not stated in the available sources. The SCOS-2000 ICD does say that commands can be blocked into one segment and sent "as a single frame/CLTU".9025

    SLE also defines forward services at higher levels. With the Forward Space Packet service the user hands over only packets, and the provider builds the frames, runs COP-1 (using the CLCWs of the ROCF service) and generates the CLTUs, so that several users can command one spacecraft without coordinating with each other.106 The library's copy of that book is stamped historical; see FSP for a side-by-side comparison with FCLTU.107 Which service instances run in a pass, and with which production parameters, is agreed through SLE service management.

    The radiated CLTU modulates the uplink carrier, the subject of the CCSDS radio frequency and modulation book 401.0 and of ECSS-E-ST-50-05C.109110 The Solar Orbiter MIB lists the telecommand bit rates that its deep-space transponder can be set to: 7.8125, 15.625, 250, 1000, 2000 and 4000 bit/s.108 See radio frequency, modulation and ranging.

    12. Closing the loop: ST[01] reports and MIB verification¶

    On board: ST[01] request verification¶

    PUS-C's request verification service has three subservices. Routing and reporting checks that a request can be routed and is not corrupted, and reports failures as TM[1,10]. Acceptance and reporting checks the request before it is handed to the service, for example its integrity and the availability of the service, and reports TM[1,1] or TM[1,2]. Execution reporting issues the start, progress and completion reports on behalf of the executing service.4243 Failures are always reported. Successes are reported only when the corresponding acknowledgement flag was set.4445

    Report Meaning Solar Orbiter
    TM[1,1] / TM[1,2] successful / failed acceptance both mandatory57
    TM[1,3] / TM[1,4] successful / failed start of execution not used (Ack bit 2 = 0)49
    TM[1,5] / TM[1,6] successful / failed progress of execution not used (Ack bit 1 = 0)49
    TM[1,7] / TM[1,8] successful / failed completion of execution both mandatory57
    TM[1,10] failed routing defined only in PUS-C; PUS-A lists subtypes 1 to 84341

    Each report starts with the request ID: the packet ID and the packet sequence control of the telecommand. That is not unique by itself; the source is given by the destination ID of the report.46 Failure reports add a failure code and optional data.46 In the Solar Orbiter MIB, the PIC extracts the 16-bit failure code of TM(1,2) and TM(1,8) at octet 20, just after the request ID. Combined with the APID, this gives a separate SPID per failure code: 274 SPIDs for TM(1,2) and 1,477 for TM(1,8).103 The SCOS-2000 verifier itself ignores the failure code and uses only the subtype.24

    On the ground: the verification stages¶

    SCOS-2000 tracks each released command through a chain of stages. The ground-side uplink verification stages are release to the NCTRS, ground station reception, uplink (radiation) and on-board reception, the last only in AD mode. Execution verification follows as acceptance (CAV) and completion (CEV).29 A stage is pending, passed, failed, timed out, unverified, unknown or idle, among other states.30 In the EGSE version the ground acknowledgements are explicit: the front end returns a GS_Ack on reception, a UL_Ack when a BD-mode command has been sent, and an ONB_Ack when the spacecraft confirms an AD-mode command.31

    The MIB defines the execution stages. Each cvs row has an ID and a stage type: A acceptance, S start, 0 to 9 progress steps, C completion. Each requires a valid parameter to equal a value within a tolerance, all rows of a stage are ANDed together, and each row can also suspend status-consistency checking of the parameter during the window.20 cvp attaches at most one stage of each type to a command.21

    Worked example: ZCD00305 from packet to CLTU¶

    The command ZCD00305 "Enable HK Para Rpt Gen" is TC(3,5) to APID 172, with NOM_TC header and Ack 9. It has one editable element, PCD03011 "HK SID" (PTC 3 / PFC 4, 8-bit unsigned, range set VCD00353: 1 to 192).9759 On board it asks the housekeeping service to enable periodic generation of the report with the given SID. Solar Orbiter lists TC(3,5) as "Enable Housekeeping Parameter Report Generation".3958 The values below are illustrative: SID 1, source ID 120 (direct commands), sequence count 1, VC 1, MAP ID 1, N(S) = 0x2A and no randomization; the TC FECF is included, as the ICD's figure 3.1-1 shows.104 The CRCs and BCH parity were computed by this wiki with the algorithms cited. The bytes are not taken from a real uplink.
