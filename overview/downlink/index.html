    Downlink: from on-board parameter to operator display¶

    A temperature measured on board a spacecraft passes through about a dozen transformations before an operator sees it as a number with a unit and a colour on a screen. The on-board software samples it and places it in a PUS housekeeping report. The report travels in a Space Packet, the packet is cut into fixed-length TM transfer frames, and the frames are protected by channel coding and modulated onto a radio carrier. On the ground the station recovers the frames and forwards them over Space Link Extension (SLE) services. At ESOC, NCTRS hands them to the SCOS-2000 mission control system, which rebuilds the packets, identifies them with the MIB, extracts and calibrates the parameter, checks its limits, archives it, displays it, and makes it available to external users through EDDS. This page walks through each stage in transmission order. It says what each layer adds and why, and it links to the page that covers that layer in full. Real values from the public Solar Orbiter documentation and MIB are used throughout. The return path for commands is described on Uplink, and the overall picture is on How it all fits together.

    1. Sampling an on-board parameter¶

    An on-board parameter is anything the spacecraft can read: a sensor measurement or a software variable held in memory. Each has exactly one on-board parameter identifier, unique across the whole spacecraft. Each is also associated with an on-board parameter minimum sampling interval, which is shared by groups of parameters (PUS gives 125 ms for a platform and 500 ms for a payload as an example). All parameters accessed by one application process use the same minimum sampling interval, and that interval is the unit in which the housekeeping and monitoring services express their own time intervals.1

    On the ground, the same quantity is a monitoring parameter in the MIB pcf table (see pcf), identified by an 8-character name such as NRW01300, with a raw type (PTC/PFC), an optional validity condition, a calibration and a description. The link between the ground name and the on-board identifier is not made by the name: the ground finds the value by its position in a known packet (section 12). The MIB does carry the on-board identifier in PCF_PID, which must be unique and which SCOS-2000 uses to recognise values delivered in PUS-compatible variable packets; for NRW01300 it holds 185585667.96102 PUS parameter types are explained on PUS parameter types and their SCOS-2000 encoding on MIB parameter types.

    2. Housekeeping and event reports¶

    ST[03] housekeeping¶

    The housekeeping service gives visibility of on-board parameters assembled into report structures. It has a housekeeping reporting subservice for nominal operations, a diagnostic reporting subservice for contingency investigations, and a parameter functional reporting configuration subservice that switches whole sets of reports on and off, for example at a mode change.2 Each housekeeping parameter report structure consists of:3

    Element Meaning
    Report structure identifier (the SID) Unique within the application process that hosts the subservice.
    Collection interval How often a report is generated, in units of the minimum sampling interval.
    Simply commutated parameters An ordered list; each appears once per report.
    Super commutated parameter sets Each set has a repetition number and an ordered list of parameters; each parameter is sampled that many times per collection interval at a sub-period of interval / repetition number.
    Periodic generation action status Enabled or disabled, if the subservice can manage periodic generation.

    When periodic generation is enabled, the subservice emits one TM[3,25] housekeeping parameter report per collection interval. Each report contains exactly one notification: the SID followed by the sampled values in the declared order, with super-commutated samples interleaved set by set (value 1 of A, value 1 of B, value 2 of A, value 2 of B).4 The packet format is therefore just the SID followed by a "deduced" list of parameter values, whose layout the ground must already know.6 Generation is switched on by TC[3,5] and off by TC[3,6].5 The diagnostic equivalent is TM[3,26].6

    Why the ground needs the MIB

    Nothing in a TM[3,25] packet says which parameter sits at which position. The ground can only interpret the report if its database describes the same structure as the on-board definition. The SCOS-2000 ICD makes the consequence explicit: a new report structure created on board with ST[03] cannot be processed until its packet definition has been added to the database, and ESA missions typically define the packet in the database first and generate the ST[03] commands from that definition.88

    ST[05] event reporting¶

    The event reporting service reports occurrences of operational significance that other services do not already report: failures and anomalies (including those found by FDIR), progress of activities, built-in test results and normal payload events.7 Each event definition has an identifier, unique within its application process, optional auxiliary data, and one of four severity levels. The severity is coded in the message subtype, which makes detection and routing on the ground easier.7

    Report Severity Source data
    TM[5,1] informative event report informative event definition ID + auxiliary data (deduced)8
    TM[5,2] low severity anomaly report low same structure
    TM[5,3] medium severity anomaly report medium same structure
    TM[5,4] high severity anomaly report high same structure

    What Solar Orbiter does¶

    Solar Orbiter tailors the 2003 PUS-A issue (ECSS-E-70-41A). Its packet ICD lists TM(3,25) "Housekeeping Parameter Report" and TM(5,1) to TM(5,4) as mandatory, with the event subtypes named "Normal / Progress Report" and "Error / Anomaly Report" of low, medium and high severity, and adds mission-specific subtypes such as TC(3,129) "Update HK Report Generation Period".23 In the 2025-09-16 MIB release, 288 SPIDs are TM(3,25) packets, 7,156 are ST[05] packets and 1,809 are ST[01] verification packets, out of 11,150 packet definitions.103

    3. The PUS TM secondary header and the time stamp¶

    PUS carries its messages in CCSDS Space Packets. A telemetry packet carries a report from an on-board application process to the ground; a telecommand packet carries a request the other way.9 Every PUS telemetry packet except the spacecraft time packets has a TM packet secondary header (PUS-C name) or data field header (PUS-A name).1214

    Field Bits Values Meaning
    TM packet PUS version number 4 2 Version 0 was the ESA PUS (PSS-07-101), version 1 is ECSS-E-70-41A.12
    Spacecraft time reference status 4 0 if not supported Status of the on-board time reference used for the time tag.12
    Message type ID 8 + 8 service type, message subtype Identifies the report, for example 3 and 25.12
    Message type counter 16 0 if not supported Count of generated messages of that type per destination.12
    Destination ID 16 application process user ID The addressee of the report.12
    Time absolute time, PFC declared by the mission The time tag of the report.12
    Spare optional Pads the header to an integral number of words.12

    The user data field that follows holds the source data (structure deduced from the message type), an optional spare field that pads the packet to the mission's padding word size, and an optional 16-bit packet error control field. Whether TM packets are checksummed, and with the ISO 16-bit checksum or the 16-bit CRC, is a mission tailoring choice.13

    The PUS-A data field header starts with a spare bit (formerly the CCSDS secondary header flag), a 3-bit PUS version set to 1 and 4 spare bits, followed by the service type and subtype (8 bits each), an optional packet sub-counter, an optional destination ID, an optional time field in CUC or CDS format, and optional spare bits.15

    Solar Orbiter sets the PUS version to 1 and all spares to zero, and stamps each packet with the time at which its generation started, in CUC with 4 octets of coarse time and 2 octets of fine time.17 A destination ID is used: solicited telemetry copies the command's source ID, while housekeeping, table, diagnostic and dump packets always carry 0x00 (ground).18 The packet data field is at most 4,106 octets: 4,096 octets of source data plus the 10-octet data field header.16

    Inference

    The Solar Orbiter header figure is an image that is not part of the extracted text. The field order shown is the PUS-A order, and the sizes are deduced from the 10-octet total, the 8-bit destination ID and the 6-octet time. This leaves no room for the optional packet sub-counter. The MIB agrees: 11,138 of its 11,150 packet definitions, every spacecraft PUS packet among them, have PID_DFHSIZE = 16 (6 + 10 octets), and the PIC places the housekeeping SID at octet 16. The other 12 are the time report on APID 0 (no data field header, 6), three complete-frame packets on APID 1 and eight control-system packets on APID 1966.104 The sibling page Worked example: decoding a real Solar Orbiter telemetry packet reaches the same conclusion.

    The time field¶

    The CCSDS Unsegmented Time Code (CUC) is a binary count of basic time units (normally seconds) from an epoch, optionally followed by octets of binary fraction. Its optional P-field says, in octet 1, whether the field is extended (bit 0), which epoch is used (bits 1 to 3: 001 for the 1958 January 1 TAI epoch, 010 for an agency-defined epoch), how many coarse octets there are minus one (bits 4 to 5), and how many fine octets there are (bits 6 to 7).26 The PUS secondary header does not carry a P-field. PUS-C instead requires the format (PFC) of the time field to be declared when the mission's time service is specified.12 Solar Orbiter's standard spacecraft time source packet is the exception that carries an explicit P-field, 0b00101110 (agency epoch, 4 coarse and 2 fine octets). It has APID 0, no data field header, and an 8-octet data field. Its time refers to the leading edge of the first bit of the attached sync marker of the VC 0 frame whose virtual channel frame count is 0.2526

    The on-board time in the packet is not UTC. The ground converts it with a time correlation built from such time packets: the frame's Earth reception time (from the NIS header) minus the ground delay, propagation delay and on-board radiation delay gives the frame transmission time, which is paired with the latched on-board time.67 Mars Express quotes an accuracy below 2 ms for this conversion.61 See Time correlation in SCOS-2000 and Time code formats.

    4. The Space Packet primary header¶

    The Space Packet Protocol defines a fixed 6-octet primary header followed by a packet data field of 1 to 65,536 octets.2729

    Field Bits Values Meaning and rationale
    Packet version number 3 0b000 Identifies a Version 1 CCSDS packet.27
    Packet type 1 0 TM, 1 TC Separates reports from requests.27
    Secondary header flag 1 1 if present Static per APID for a mission phase; always 0 for idle packets.27
    APID 11 0 to 2047; 2047 = idle Names the managed data path. In PUS it identifies the source application process of a TM packet.2711
    Sequence flags 2 0b11 = unsegmented PUS uses 0b11 (stand-alone) for all its packets.2811
    Packet sequence count 14 modulo 16,384 Counted per APID, so the ground can detect missing packets and restore order.28
    Packet data length 16 C = octets - 1 The packet is 6 octets longer than the data field.2911

    Solar Orbiter structures its 11-bit APID as a 7-bit process ID (the source application) followed by a 4-bit packet category. APID 0 is reserved for the time packet and the all-ones APID for idle packets.16 The categories include 1 for TC verification, 2 for HPTM housekeeping (platform only), 4 for routine housekeeping, 7 for events, 9 for dumps, 10 for file transfer and 12 for private science or telecommand.19 Solar Orbiter keeps a source sequence count per APID and destination ID, raises a ground alarm on every discontinuity, and uses the sequence flags as grouping flags for multi-packet answers (for example a memory dump), while each packet stays self-contained.16

    Worked example (values from the MIB; sequence count illustrative)

    The RW1 bearing temperature used later on this page travels in the packet with APID 178. In binary, 178 is 0b00010110010: process ID 0b0001011 = 11 (the AOCS application in the Solar Orbiter PID table) and category 0b0010 = 2.10219 The first two octets of the primary header are therefore 0x08B2 (version 0, type 0, secondary header flag 1, APID 178). With stand-alone flags and an illustrative count of 0x0123, the next two octets are 0xC123.

    5. Into transfer frames: virtual channels and the master channel¶

    Packets have variable length, but the weak, noisy space link needs fixed-length protocol data units so that the receiver can synchronise simply and robustly. The TM Space Data Link Protocol therefore defines the TM Transfer Frame, whose length is fixed per physical channel and mission phase.3032 One physical channel is shared among several data streams by virtual channels (VCs).30 Frames are addressed by three identifiers. The transfer frame version number (TFVN) plus the spacecraft ID (SCID) form the master channel ID (MCID), and the MCID plus the VCID form the global VCID.31 For a single spacecraft the master channel is usually the whole physical channel.3110

    Component Size Presence
    Transfer frame primary header 6 octets mandatory
    Transfer frame secondary header up to 64 octets optional
    Transfer frame data field integral number of octets mandatory
    Operational control field (OCF) 4 octets optional
    Frame error control field (FECF) 2 octets optional

    Source: CCSDS 132.0-B-3 §4.1.1.32

    Field Bits Values Meaning and rationale
    TFVN 2 0b00 TM version 1. TC frames share the value; they are told apart by the ASM or start sequence.33
    Spacecraft ID 10 SANA-assigned Static for all mission phases.33
    VCID 3 0 to 7 No numbering constraint.33
    OCF flag 1 1 = OCF present Static per master or virtual channel.33
    Master channel frame count 8 mod 256 Lets the receiver check completeness of the master channel.33
    Virtual channel frame count 8 mod 256 Per-VC accountability, needed to extract packets systematically.33
    Secondary header flag 1 Signals the frame secondary header.34
    Synchronization flag 1 0 packets, 1 VCA_SDU Static per VC.34
    Packet order flag 1 0 Reserved when the sync flag is 0.34
    Segment length ID 2 0b11 Legacy field, fixed when the sync flag is 0.34
    First header pointer 11 offset; 0x7FF; 0x7FE Lets the receiver find packet boundaries even after losing a frame.34

    How packets enter frames. For each VC, the packet processing function concatenates packets into the fixed-length data field. A packet that does not fit is split, and the rest continues in the next frame of the same VC. The first header pointer marks the first packet header that starts in each frame, and idle packets fill the space when no data is ready. The virtual channel generation function adds the header and a per-VC frame count. The virtual channel multiplexing function interleaves VCs in an order set by the project, and it inserts an only-idle-data (OID) frame when nothing is ready, so that the stream stays continuous. The master channel generation function adds the master channel frame count and any master-channel OCF or secondary header. The all frames generation function computes the FECF.37 The FECF is a 16-bit CRC with generator \(G(X) = X^{16} + X^{12} + X^5 + 1\) and an all-ones preset.36

    The operational control field. The 4-octet OCF carries real-time reports. When its type flag (bit 0) is 0 it holds a Type-1 report, the CLCW of COP-1, which is how the spacecraft acknowledges telecommand frames. When the flag is 1 it holds a Type-2 report (project-specific or an SDLS frame security report). The spacecraft must send OCF-carrying VCs often enough for the COP not to time out.35 The CLCW layout is defined by the TC Space Data Link Protocol.40

    AOS frames instead of TM frames

    Missions with higher rates or more channels may use the AOS Space Data Link Protocol. Its frame has a 6- or 8-octet primary header with TFVN 0b01, an 8-bit SCID, a 6-bit VCID (so up to 64 VCs), a 24-bit VC frame count, a signalling octet and an optional 16-bit header error control. An optional insert zone may follow, and the same 4-octet OCF and 2-octet FECF trailer are available.3910 Issue 5 of the AOS book (October 2025) widens the spacecraft ID to 10 bits by adding two bits elsewhere in the header; missions built to issue 4 or earlier keep the 8-bit field.108 See AOS and, for the newer unified protocol, USLP. Every identifier field of these frames is listed on space link identifiers.

    6. Channel coding and the attached sync marker¶

    Between the data link protocol and the physical layer sits the synchronization and channel coding sublayer. It provides error-control coding (including frame validation), frame synchronization and pseudo-randomization.41 At the sending end, the frames are first Reed-Solomon, turbo or LDPC encoded (optional), then randomized (optional), then preceded by an attached sync marker (ASM), and finally convolutionally encoded (optional) into channel symbols.43

    Code Main property
    Convolutional (basic or punctured) Inner code. The punctured rates expand the bandwidth less.42
    Reed-Solomon (255, 255 - 2E), E = 16 or 8 Burst-error correction with interleaving depth I. Also validates the frame with a very low undetected error rate.44
    Concatenated (RS outer, convolutional inner) More coding gain than either alone.42
    Turbo, LDPC Even greater coding gain.42

    Frame validation. The receiver must know whether each decoded frame can be used. Reed-Solomon and LDPC decoders give that answer themselves. Otherwise the FECF of the TM, AOS or USLP frame is used.42

    The ASM and the CADU. Synchronization is acquired by recognising the regularly spaced ASM, which is placed between frames (uncoded or convolutional), between RS codeblocks, or between turbo and LDPC codewords. The ASM plus the frame, codeblock or codeword is the channel access data unit (CADU).45 The 32-bit ASM used for uncoded, convolutional, Reed-Solomon, concatenated and rate-⅞ LDPC data is 0x1ACFFC1D. Turbo and the other LDPC rates use longer markers, such as the 64-bit 0x034776C7272895B0.46

    Why randomize. The receiver's symbol synchronizer needs enough bit transitions, the spectrum must be free of strong lines, and codeword synchronization must not be fooled by repetitive patterns. Problems have been seen on real links when the randomizer was not used. The pseudo-randomizer XORs each frame, codeblock or codeword (but not the ASM) with a 131,071-bit sequence from \(h(x) = x^{17} + x^{14} + 1\), seeded with 11000111000111000. A legacy 255-bit sequence from \(h(x) = x^8 + x^7 + x^5 + x^3 + 1\) is still allowed. Its use is fixed per physical channel and is not signalled in the data.47 Issue 6 of the book (April 2026), also in the library, makes the pseudo-randomizer mandatory.109

    Solar Orbiter coding

    The coding scheme, interleaving depth and randomizer choice of the Solar Orbiter downlink are not stated in the available sources. The packet ICD fixes the frame layout but not the coding sublayer.20

    7. Modulation¶

    The channel symbols modulate an RF carrier. ECSS selects the space-link modulation to minimise occupied bandwidth and the channel coding to minimise transmitted power, and it defines the permissible schemes in ECSS-E-ST-50-05.48 That standard covers frequency bands, spectral and power constraints and the allowed modulations, among them GMSK, filtered OQPSK and SRRC-4D 8PSK TCM. Where a ranging service is needed, the modulation choice must also stay compatible with ECSS-E-ST-50-02.4950 On the CCSDS side the same ground is covered by the omnibus Radio Frequency and Modulation Systems book, CCSDS 401.0.110

    The Solar Orbiter MIB shows the options of the spacecraft's deep-space transponder as data: its housekeeping report "PLF DST HK" (SPID 33793) carries a telemetry modulation scheme parameter whose textual calibration allows GMSK or SPL, and a telecommand bit rate between 7.8125 and 4000 bit/s.111 Bands, modulations, ranging and the transponder telemetry are explained on radio frequency, modulation and ranging.

    8. At the ground station¶

    The receiving end runs the coding sublayer in reverse. It performs convolutional decoding (if used), frame synchronization on the ASM, derandomization, and then Reed-Solomon, turbo or LDPC decoding. It delivers frames to the data link protocol sublayer.43 The SLE standards describe the same chain from the station's point of view. The return space link processing function steers the antenna, acquires the carrier and demodulates the symbol stream. It synchronizes at node, codeblock and frame level, removes the randomization, decodes, checks the FECF and recovers the frames.53 A frame counts as acquired when the ASMs before and after it are found with the same polarity and the correct number of bits between them.53

    Each frame is then annotated. The annotation gives its Earth reception time (ERT), the antenna that acquired it, whether it contains detected uncorrectable errors, and its continuity with the previous frame.53 A frame counts as "good" when all its RS or LDPC codewords are valid or, without RS or LDPC, when its FECF checks. For a good RS frame the check symbols are removed before delivery, and an erred frame is delivered whole.5354

    The receiving side of the TM SDLP then demultiplexes frames by VCID and discards frames with an invalid VCID. It can flag a gap in a VC frame count, and it uses the first header pointer and the packet length fields to extract packets, assembling a packet that spans frames from the start of the next frame on the same VC. Idle packets and OID frames are discarded.38 The ESA sources place this packet reconstruction in the SCOS-2000 packetiser at the control centre (section 11): the MCS builds packets out of the received frames.6575

    9. SLE return services to the control centre¶

    Space Link Extension carries the station's output to the user's control centre over terrestrial networks, with standard operations, so that any agency's station can support any mission. Three return services matter here:

    Service Delivers Typical use
    RAF, return all frames all frames of one physical channel, annotated51 complete frame stream
    RCF, return channel frames all frames of one master channel or one virtual channel59 one spacecraft or one VC
    ROCF, return operational control fields all or a subset of the OCFs of one master or virtual channel60 CLCWs for commanding

    A service instance is scheduled in a service package. Its production parameters (carrier frequency, modulation, bit rate, coding, session times) can only be changed by service management. Its provision parameters (provision period, delivery mode, quality of service) belong to the individual instance.5255 How agreements and packages are negotiated is on SLE service management. The RAF operations are BIND, UNBIND, START, STOP, TRANSFER-DATA, SYNC-NOTIFY, SCHEDULE-STATUS-REPORT, STATUS-REPORT, GET-PARAMETER and PEER-ABORT.     10. NCTRS and NIS: into the control centre¶

    At ESOC the mission control system does not talk to stations directly. The NCTRS interfaces the MCS with the ground station network and uses SLE for non-ESA stations.64 For Mars Express it receives the telemetry that the station has already checked and time-stamped with the ERT, and passes the housekeeping and science telemetry to the MCS for processing and archiving. It also collects tracking data and moves files such as station schedules.62 DLR's mobile control centre runs GECCOS, which is derived from SCOS-2000. It reaches stations through what the DLR paper calls the bespoke NCTRS protocol, and an SLE switch board translates that protocol to standard SLE.66

    The SCOS-2000 time correlation note describes telemetry frames arriving at the MCS with a NIS header that holds the UTC reception time of the frame.67 On the MCS side, the SCOS-2000 TM packetiser rebuilds packets from frames, extracts the CLCW, and runs quality and continuity checks.65 Solar Orbiter's archive keeps the ID of the receiving station with each packet: 21 Kourou, 22 Perth, 23 New Norcia, 24 Cebreros, 25 Malargüe, 30 Maspalomas, plus test identifiers.73 The GDDS binary format even keeps an "SLE service Id" field that records over which SLE service and channel type the data was received.71 The names and acronyms of these systems vary between sources. The NCTRS, for example, is the "Network Control and TM/TC Router System" in a 2005 ESA presentation and the "Network Controller and Telemetry Receiver System" in the Mars Express data handling paper.6462 See NCTRS, NIS and the ground station interface.

    11. Packet identification in SCOS-2000¶

    SCOS-2000 must decide what each packet is before it can extract anything. The packetiser first reads the APID from the primary header. It then reads the type and subtype from the packet, at a position configured once for the whole spacecraft (a constraint on the on-board design). If the PIC table requires it, it also reads up to two additional identification fields from the application data. With this key it looks up the PID table, which gives the SPID (SCOS-2000 packet ID) and the TPSD, and it files and distributes the resulting SCOS-2000 TM packet.80

    12. Parameter extraction: PLF and VPD¶

    For fixed packets, each row of the plf table places one parameter in one SPID. It gives the byte offset from the start of the source packet (PLF_OFFBY), the start bit within that byte with bit 0 the leftmost (PLF_OFFBI), and for super-commutated parameters the number of occurrences, the bit distance between them and their time spacing. It also gives a time offset that corrects each sample's time stamp relative to the packet time.8586 The width comes from the parameter's PTC/PFC in pcf. Overlaps and gaps are allowed, but a parameter may appear only once per packet.86

    For variable packets, the vpd table describes the structure with repeated groups and choices. It is referenced through the TPSD, with offsets counted from the end of the data field header (PID_DFHSIZE).85 Values from variable packets cannot take part in full TM processing: validity, monitoring checks, verification and synthetic parameters. This is because their time reference is only known once the packet is opened. Variable packets are therefore meant for special reports rather than regular housekeeping.87 SCOS-2000 also time-stamps each housekeeping sample from the packet time plus a static database offset, so the offsets must be known in advance.88 The release holds 400,792 PLF rows and 19,863 VPD rows.103

    Parameters that are computed rather than received, the synthetic parameters, enter the same chain. Solar Orbiter defines 1,582 dynamic OL parameters and 2 saved synthetic parameters, next to 125,161 raw telemetry parameters.105 See Synthetic parameters and the OL language.

    13. Validity and calibration¶

    Before calibration, SCOS-2000 applies the parameter's validity condition. PCF_VALID names another parameter and PCF_VALPAR gives the raw value it must have. SCOS-2000 uses this expression, and the validity of the validity parameter itself, to decide whether a sample is valid. The validity parameter must have an integer raw value and be processed by the TM model.8982 20,692 Solar Orbiter parameters have a validity parameter.105

    Calibration turns a raw value into an engineering value. It applies to raw, constant and synthetic parameters of numerical nature only.90 The category PCF_CATEG is N for numerical, S for status (textual calibration) and T for character strings. PCF_CURTX names a single calibration, while the cur table selects one of several at run time with an applicability condition.9193

    14. Monitoring checks¶

    Calibrated (or raw) values are checked against limits. At most one ocf row per parameter gives the number of consecutive valid violating samples needed to declare it out of limits (OCF_NBCHCK). It also gives the number of checks (1 to 16), whether the limits are raw (U) or calibrated (C), and their coding (real, ASCII or integer).97 The checks themselves are ocp rows, evaluated in order:9899

    OCP_TYPE Check Solar Orbiter rows
    S Soft limit check 3,096
    H Hard limit, or soft status check 4,153
    D Delta check against the last valid value 105
    C Status consistency against the value expected from commanding 15
    E Event generation only (no OOL display) 0

    Each check can carry an applicability condition (OCP_RLCHK = OCP_VALPAR), so that, for example, limits apply only when a unit is on. The search for applicable checks stops at the first applicable check or the first soft/hard pair. A value exactly on a limit is not out of limits.98100 The applicability parameter must have an integer raw value and be processed by the TM model.100 See Monitoring checks and, for on-board limit checking, ST[12].

    15. Archiving and display¶

    SCOS-2000 keeps a packet archive of historical telemetry, telecommands and derived data, and a file archive for files such as flight dynamics and planning products. It can also generate summary files such as command history reports.63 In the Solar Orbiter MCS, the long-term archive server holds the packet archive (PARC) for packets, events and telecommands, the parameter archive (DARC) for parameter values, and the file archive (FARC) for auxiliary files.69 Telemetry is normally retrievable within seconds of reception at the ground station.69 See Mission archives: PARC, DARC and FARC.

    The standard monitoring displays are the alphanumeric display (AND, 32- or 64-parameter), the graphical display (GRD) and the scrolling display (SCD). They use the PLF definitions to pull values out of packets,86 and only TM-model parameters (PLF or synthetic) can appear on them. Since R5.0 their definitions are XML files in the FARC, although the ASCII dpf/dpc, gpf/gpc and spf/spc tables are still imported for backward compatibility.101 The packetiser, displays and retrieval functions together cover packet reconstruction, parameter extraction with super-commutation, synthetic parameters, calibration, validity, limit, expected-status and status-consistency checking, and retrievals from a given time with up to four merged streams.65 See Display definitions in the MIB.

    16. Dissemination via EDDS¶

    People outside the control room see the data through the EGOS Data Dissemination System (EDDS). It gives controlled access to telemetry, telecommand history and auxiliary data for users without access to the MCS. It offers management services, data services (batch and stream) and notification services. Management covers user accounts and configuration, with access policies based on missions, users, privileges and roles. Clients are a web portal, a standalone or web application, or the user's own client through the web-services interface.7879

    For Solar Orbiter, EDDS serves packets and reports from the PARC, parameters from the DARC, and files from the FARC. A batch request delivers a complete data set as binary, XML or ASCII, while a stream request delivers data continuously in near real time. Requests are XML documents.70 Quotas restrict each user by APID, SPID, parameter name, file and time range.70 The science ground segment nominally receives all archived packets in RAPID files: SCOS-2000 packets collected for a configurable period (50 s for Solar Orbiter) and pushed by the generic file transfer system. Telecommand packets can reappear in later files when their verification status is updated.6877 See EDDS, EDDS request and data formats, TDRS and GDDS and DDIDs.

    Inference

    ICD issue 7.0 defines the calibration points and the extrapolation flag but does not spell out how values between points are computed. Issue 6.9 describes interpolation from the points on either side, and ECSS-E-ST-70-31C defines a linear-interpolation interpretation function.112113 Assuming linear interpolation between (1315, 30) and (1734, 20), raw 1500 gives \(30 + (1500-1315)\times\frac{20-30}{1734-1315} \approx 25.6\) °C, well inside the soft limits. The curve falls as the raw count rises, which is typical of a thermistor; this is also an inference from the numbers.

    The parameter also appears in five other packets (SPIDs 29531, 65832, 65949, 65950 and 65951) at their own offsets. One definition in pcf thus serves every packet that carries the value.102 The full parameter view is in the explorer: NRW01300.
