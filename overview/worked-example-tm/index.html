    Calibration MIB PUS SCOS-2000 Solar Orbiter Space Packet Telemetry Worked example

    Worked example: decoding a real Solar Orbiter telemetry packet¶

    This page follows one real housekeeping packet of the Solar Orbiter spacecraft through the ground system, byte by byte. The packet definition, every parameter, every calibration curve and every limit come from the public Solar Orbiter Mission Information Base (MIB), release MIB__20250916M25925PFMS001_SOL (database 25925PFM, comment 20250916-CSW3.1.2_MAS7.33).1 The meaning of each MIB field comes from the SCOS-2000 Database Import ICD issue 7.0, which the public Solar Orbiter document site (hosted at IRAP) files among its MOC documents as the "MOC-applicable MIB" ICD.2 The packet structure comes from the Solar Orbiter TM-TC and Packet Structure ICD (SOL.S.ASTR.TN.00079 issue 7).3 The bytes at the end are a constructed example: no real downlinked telemetry is used on this page.

    What is real and what is illustrative

    Real (from the sources cited): the APID, type, subtype, SID, SPID, packet layout, parameter names and types, calibration points, polynomial coefficients, textual aliases, limit values, and the header conventions of Solar Orbiter. Illustrative (constructed by this wiki): the source sequence count, the on-board time and the raw parameter values in the byte string of step 6. They were chosen to look plausible and to exercise every calibration type. They are not spacecraft data.

    The companion page Worked example: building a real Solar Orbiter telecommand builds the command that switches this very report on. The general flow is explained on Downlink: from on-board parameter to operator display.

    The packet we picked¶

    We want a fixed-layout PUS housekeeping report (service type 3, subtype 25) that is small enough to decode completely and that still uses every kind of monitoring calibration the MIB offers. The MIB holds 288 TM(3,25) packet definitions on 62 APIDs.58 Filtering them by size and by the calibration tables their parameters reference leaves only two packets of 5 to 45 parameters that combine numerical curves, polynomials, textual calibrations and a limit check (SPIDs 59208 and 54101, the latter with 44 parameters; query in the SQL box below). The best fit is the METIS instrument's "HK SID 108 - HVU - LED" report:59

    Property Value Source table
    SCOS-2000 packet ID (SPID) 59208 PID PID_SPID
    Description TM(3,25) - HK SID 108 - HVU - LED PID_DESCR
    APID 1092 (0x444) PID_APID
    PUS service type / subtype 3 / 25 (housekeeping parameter report) PID_TYPE, PID_STYPE
    First extra identifier (PI1) 108 (the structure ID, SID) PID_PI1_VAL
    Packet mnemonic YIT59208 TPCF TPCF_NAME
    Packet size 37 octets TPCF_SIZE
    Parameters 11, all at fixed positions PLF
    Calibrations used 2 textual, 3 two-point numerical, 1 175-point numerical, 1 polynomial TXF, CAF, MCF
    Limit checks soft and hard limits on the HVU temperature OCF, OCP

    Values from the 2025 release.59616364 The same layout (the same eleven parameters at the same offsets), the same numerical curves, polynomial and limits are already present in the April 2020 release MIB__20200416M10720PFMS001_SOL, with two differences: in 2020 SAFE_Param (NIT0E072) is an uncalibrated 16-bit unsigned integer (PTC 3 / PFC 12, category N, no CITT1072TM), and the SID alias set CITT1120TM has 17 entries (no HK_SID_110).66

    APID 1092 splits into a 7-bit Process ID of 68 and a 4-bit packet category of 4 (1092 = 68 × 16 + 4). The Solar Orbiter ICD allocates Process IDs 67 to 71 to the METIS payload instrument and reserves category 4 for routine, cyclic TM(3,25) housekeeping.18 The same APID carries 16 different TM(3,25) packets in the MIB, told apart only by their SID (1, 102 to 110, 112 to 116 and 120).59 That is why the SID matters so much in the identification step below.

    Inference

    The parameter descriptions use the abbreviations HVU, MCP and LED (for example HVU_mcp_V, LED_curr_set). The MIB does not expand them. They plausibly refer to a high-voltage unit, a micro-channel plate and a light-emitting diode used for calibration, but this is not stated in the available sources. Nothing on this page depends on that reading.

    The path of the packet through the ground system¶

    flowchart LR
    A["TM transfer frames<br/>1115 octets, SCID 650"] -->|"first header pointer,<br/>packet length"| B["TM source packet<br/>37 octets"]
    B --> C["TM packetiser:<br/>APID, type, subtype<br/>+ PIC: PI1 = SID"]
    C -->|"PID lookup"| D["SCOS-2000 TM packet<br/>filing key SPID 59208"]
    D --> E["Parameter extraction<br/>PLF offsets + PCF PTC/PFC"]
    E --> F["Calibration<br/>TXF/TXP, CAF/CAP, MCF"]
    F --> G["Monitoring checks<br/>OCF/OCP"]
    G --> H["Displays, archive,<br/>EDDS delivery"]

    The order of the steps follows the ICD's description of the telemetry packetiser and of parameter extraction from fixed packets.3236 The frame-level steps are specified by the Solar Orbiter ICD and by CCSDS 132.0-B-3.1026

    Step 0: from frames to packets¶

    Solar Orbiter telemetry transfer frames have one allowed length of 1115 octets (8920 bits) before encoding, carry the CCSDS spacecraft identifier 650 (0x28A), always have a frame secondary header, always carry a Command Link Control Word in the operational control field and always end with a frame error control word.10 The frame data field has a constant size of 1099 octets and TM source packets may be up to 4112 octets long, so a long packet is split across frames.5 Data sources are mapped onto virtual channels: real-time TM uses VC0, playback from the on-board computer mass memory VC1, playback from the solid state mass memory VC2 and VC3, high-priority real-time TM VC4, the critical event log VC5 and idle frames VC7; VC6 is marked "not required".11

    The receiver locates the first packet of a frame with the 11-bit first header pointer and finds each following packet from the packet length field of the one before.1026 The first header pointer is all ones (0b11111111111) when no packet starts in the frame, and 0b11111111110 for Solar Orbiter idle frames on VC7.10 Our 37-octet packet is short enough to sit inside one frame data field, but it may also straddle two frames. The details are on TM Space Data Link Protocol.

    Step 1: the Space Packet primary header¶

    Every Solar Orbiter TM source packet starts with the 6-octet CCSDS Space Packet primary header, which ECSS-E-70-41A (PUS-A) reuses unchanged.2420

    Field Bits Solar Orbiter rule This packet
    Version number 0-2 0b000 for all TM; the ground rejects any other value with an alarm 0b000
    Packet type 3 0 for telemetry 0
    Data field header flag 4 1 for every TM packet except the standard spacecraft time packet 1
    APID 5-15 7-bit Process ID followed by 4-bit packet category; APID 0 is the time packet, all ones the idle packet 1092 = PID 68, category 4
    Grouping flags 16-17 11 stand-alone; 01/00/10 mark a group of self-contained packets answering one request 0b11
    Source sequence count 18-31 separate counter per APID and destination ID, +1 per packet, wraps from \(2^{14}-1\) to 0 and must never "short-cycle" illustrative: 1234
    Packet length 32-47 octets in the packet data field minus one; at most 4106 octets (10-octet header + 4096 source data) 30

    Rules from the Solar Orbiter ICD §4.2.1;678 field positions from CCSDS 133.0-B-2 §4.1.3.24 Solar Orbiter numbers bits from 0 at the most significant, first transmitted bit and transmits the most significant byte first, the same convention as CCSDS.1625

    The packet length is fixed by the definition: the TPCF gives 37 octets, and the last PLF entry ends at octet 36 (see step 4), so the field must read 37 − 6 − 1 = 30.61 The MIB sets PID_CHECK to 0 for this packet, which tells the packetiser not to verify a packet error control field.5933 Only 6 of the 11,150 PID rows set it to 1: three describe complete transfer frames (APID 1) and three sit on APID 1966, which the Solar Orbiter data delivery ICD uses for packets generated by the control system, such as time correlation packets.5830 None is a spacecraft source packet. The Solar Orbiter TM source packet drawing (figure 4.2-1) ends with the source data and has no packet error control field; the ICD defines that field and its CRC for telecommand packets only.612

    Step 2: the PUS data field header (PUS-A, version 1)¶

    Solar Orbiter does not use PUS-C. Its packet ICD applies ECSS-E-70-41A of 30 January 2003 (PUS-A) as applicable document AD1 and states that the on-board application-layer data structures follow that standard.34 The TM data field header carries PUS version number 1, the value PUS-A prescribes; PUS-C later records that version 1 "corresponds to the ECSS-E-70-41A".92123 The time field uses the CCSDS unsegmented time code (CUC) with 4 octets of coarse time and 2 octets of fine time, and the whole header is 10 octets long.98

    Field Bits Values Meaning
    Spare 1 0 PUS-A keeps this bit at zero for symmetry with the TC header; it used to be a CCSDS secondary header flag.
    PUS version number 3 0b001 Version 1 (ECSS-E-70-41A). Version 0 was the older ESA PUS.
    Spare 4 0b0000 Completes the octet; Solar Orbiter requires all spares to be zero.
    Service type 8 3 Housekeeping and diagnostic data reporting.
    Service subtype 8 25 Housekeeping parameter report.
    Destination ID 8 0x00 Solar Orbiter uses the optional destination field. Packets of categories 2, 3, 4, 8 and 9 always carry 0 (ground).
    Time 48 CUC, 4 + 2 octets The time at which generation of the packet started.

    Field definitions from PUS-A §5.4.3,21 Solar Orbiter values from SOL.S.ASTR.TN.00079 §4.2.2.1 and Annex 8 §13.3.919 PUS-A also defines an optional packet sub-counter; Solar Orbiter does not include it: figure 4.2-2 of the ICD has no such field.9

    Checked against the drawing

    Figure 4.2-2 of the Solar Orbiter ICD, which draws this header, is a picture and is not part of the extracted text. Read directly in the PDF (page 26), it lists exactly the fields and sizes above, in this order: spare (1 bit), PUS version = 1 (3 bits), spare = 0 (4 bits), service type (8 bits), service subtype (8 bits), destination ID (8 bits) and S/C time (48 bits, CUC), and the ICD notes that this uses optional fields of PUS-A.9 The MIB agrees on the total: the PIC places the SID at octet 16 = 6 + 10, and every spacecraft TM packet in the PID table has PID_DFHSIZE = 16, except the time report TM(9,2) on APID 0, which has no data field header and PID_DFHSIZE = 6.6058

    A PUS-C header with the same 6-octet time would be 13 octets long, three more than Solar Orbiter's.23 The differences between issues are summarised on PUS-A vs PUS-C and PUS packet structures.

    The time field¶

    The 6-octet time is a CUC T-field: an unsegmented binary count of seconds followed by a binary fraction of a second.27 In the packet header the P-field is implicit. The standard spacecraft time packet TM(9,2), which has no data field header, carries the same 4 + 2 format together with an explicit P-field 0b00101110.15 Read with CCSDS 301.0-B-4, that P-field means: no extension (bit 0 = 0), agency-defined epoch (bits 1-3 = 010, a level 2 time code), 4 octets of coarse time (bits 4-5 = 11, i.e. 3 + 1) and 2 octets of fine time (bits 6-7 = 10).27 The Solar Orbiter ICD gives 00:00 on 1 January 2000 as the spacecraft zero time reference, and also says that the on-board time starts at 0 at computer power-up and is then set by TC(9,128) relative to an arbitrary zero point.14 With 2 octets of binary fraction, the fine time resolution is \(2^{-16}\) s, about 15.26 µs.27

    The MIB describes the same format. In the time report (SPID 9999, APID 0, PID_DFHSIZE = 6) the PLF places the S-field NCD09021 at octet 6, the P-field NCD09022 at octet 7 and the on-board time NCD09023 at octet 8, and NCD09023 has PTC 9 / PFC 17.54 ICD Appendix A defines PTC 9 / PFC 17 as an absolute time in CUC format with 4 octets of coarse and 2 octets of fine time, 6 octets in all.53

    Inference

    The Solar Orbiter ICD calls the packet time format "CUC 9/17".9 It does not explain the label; it is presumably the same SCOS-2000 PTC/PFC pair 9/17.

    The ICD adds that the structure of the time field "allows the identification of non-synchronised time", but does not explain how; the phrase occurs nowhere else in its text.9 The ground converts on-board time to UTC by time correlation, using the time packets on VC0.14

    Step 3: how SCOS-2000 identifies the packet¶

    The SCOS-2000 telemetry packetiser cannot interpret a packet from its APID alone. It reads the APID from the primary header and the type and subtype from configured positions. If the PIC asks for it, it then extracts up to two more identification fields (PI1, PI2) from the data field. With the full key it looks up the PID, which gives the processing keys: the SPID for fixed packets and the TPSD for variable ones.32

    flowchart TD
    A["Received packet:<br/>APID 1092, type 3, subtype 25"] --> B{"PIC row for<br/>3 / 25 / APID 1092?"}
    B -- no --> C{"PIC row for<br/>3 / 25 (any APID)?"}
    B -- yes --> E
    C -- "yes: PI1 at octet 16,<br/>8 bits; PI2 unused" --> E["Extract PI1 = 108"]
    C -- no --> F["Search PID with PI1 = PI2 = 0"]
    E --> G["PID lookup:<br/>3, 25, 1092, 108, 0"]
    G --> H["SPID 59208, TPSD -1<br/>(fixed packet, PLF)"]

    The precedence rules come from the ICD's PIC description.34 The Solar Orbiter MIB has one PIC row for type 3 / subtype 25, with no APID, so it applies to every APID:60

    PIC_TYPE PIC_STYPE PIC_PI1_OFF PIC_PI1_WID PIC_PI2_OFF PIC_PI2_WID PIC_APID
    3 25 16 8 -1 0 (empty: all APIDs)

    PIC_PI1_OFF counts octets from the start of the TM source packet, which SCOS-2000 files complete in the body of its own packet; PIC_PI1_WID is in bits. An offset of -1 means "no second identification field".34 Octet 16 is the first octet of the source data, which the Solar Orbiter ICD defines as the 1-octet SID of a TM(3,25).13 PUS-A also says the ground identifies a housekeeping report by its SID together with the APID and the packet nature.22

    The PID row that matches the key is:59

    Field Value Meaning (ICD §3.3.2.4.1)
    PID_TYPE, PID_STYPE 3, 25 PUS type and subtype; 0 would mean "no data field header"
    PID_APID 1092 APID; 0-2047 for spacecraft packets
    PID_PI1_VAL, PID_PI2_VAL 108, 0 values of the extra identification fields
    PID_SPID 59208 SCOS-2000 packet ID: names the fixed structure in the PLF and is the archive filing key
    PID_DESCR TM(3,25) - HK SID 108 - HVU - LED free text, also used for event messages
    PID_UNIT (empty) on-board subsystem, reserved for future filtering
    PID_TPSD -1 not a variable (VPD) packet
    PID_DFHSIZE 16 start offset for variable-packet processing; irrelevant for a fixed packet
    PID_TIME Y the packet carries a time field
    PID_INTER (empty) no generation period declared; the ICD's "expired" timeout is computed from this field, which it says to leave empty for non-periodic packets
    PID_VALID Y this key combination is the valid one
    PID_CHECK 0 do not check a packet error control field
    PID_EVENT, PID_EVID N, (empty) do not raise a SCOS-2000 event on reception

    Field meanings from the ICD;33 the expiry rule from the PCF remark.41 The matching TPCF row gives the mnemonic YIT59208 shown on displays and a size of 37 octets.59 The ICD recommends that TPCF_SIZE include the SCOS-2000 packet header when the field is used to size history files, but the field is informative only and is not imported.35

    Inference

    TPCF_SIZE = 37 equals the length of the bare source packet. Solar Orbiter's MIB therefore appears to fill this field with source packet sizes, without the SCOS-2000 header. The same holds for the other packets inspected on this page.

    The SCOS-2000 packet around it¶

    Once identified, the source packet is filed and distributed as a SCOS-2000 packet. The Solar Orbiter data delivery ICD describes that wrapper as a common header followed by a TM-specific header, and then the full, un-stripped source packet.28 For Solar Orbiter the common header carries spacecraft ID 650, packet structure version 5, a stream ID that maps to the virtual channel (for example 1000 for VC0 real-time non-science data), and the SPID as "filing key". It also stores the MIB release number (VDF_RELEASE) used when the packet was archived.29 The TM header repeats the TPSD, the APID, the source sequence count and the type and subtype.31 Adding up the field lengths listed in the DDID gives 60 octets for the common header and 16 for the TM header, 76 in total, so our packet is stored as 76 + 37 = 113 octets. The ICD quotes the same 76 octets for SCOS-2000 packet header version 4.35

    Step 4: the PLF layout¶

    For fixed packets the PLF lists every parameter occurrence. PLF_OFFBY is the octet offset from the start of the source packet (the end of the SCOS-2000 header) and PLF_OFFBI the bit within that octet, with bit 0 the leftmost. The length is not in the PLF: it follows from the parameter's PTC/PFC pair in the PCF.3739 The eleven entries of SPID 59208 are:61

    Octets PLF_OFFBY / OFFBI Parameter Description PTC / PFC → width Calibration (PCF_CURTX) Unit
    16 16 / 0 NIT83001 HK_SID 2 / 8 → 8-bit enumerated textual CITT1120TM
    17-18 17 / 0 NIT0E070 SCREEN_Param 3 / 12 → 16-bit unsigned none
    19-20 19 / 0 NIT0E071 MCP_Param 3 / 12 → 16-bit unsigned none
    21-22 21 / 0 NIT0E072 SAFE_Param 2 / 16 → 16-bit enumerated textual CITT1072TM
    23-24 23 / 0 NIT0E0B6 HVU_mcp_V 3 / 12 → 16-bit unsigned numerical CITP1058TM V

    27-28 27 / 0 NIT0E0B5 HVU_temp 3 / 12 → 16-bit unsigned numerical CITP1074TM degC
    29-30 29 / 0 NIT0E0B7 HVU_scr_V 3 / 12 → 16-bit unsigned numerical CITP1089TM V
    31-32 31 / 0 NIT0E090 LED_curr_set 3 / 12 → 16-bit unsigned polynomial CIT01081TM

    Positions and types from the MIB;6162 widths from ICD Appendix A, where PTC 2 is an unsigned enumerated value of PFC bits and PTC 3 / PFC 12 an unsigned 16-bit integer.52 Every entry has PLF_NBOCC = 1 (no super-commutation), PLF_LGOCC = 0, PLF_TIME = 0 (every sample takes the packet time stamp) and PLF_TDOCC = 1.6137 The packet has no gaps: octets 16 to 36 are fully covered.     Layout from the MIB PLF and PCF tables.6162 The data field as a whole is 10 + 21 = 31 octets, which matches the packet length field value 30 from step 1.

    Inference

    Three of the four numerical curves (CITP1058TM, CITP1088TM, CITP1089TM) span raw values 0 to 4095 (CAP_XVALS), the temperature curve CITP1074TM stays inside 1130 to 2689, and the Solar Orbiter ICD requires parameters of 8 bits or more to be right-aligned in their octets.6317 This suggests that the values are 12-bit converter counts right-aligned in 16-bit slots, with the top four bits normally zero. The MIB itself declares 16-bit fields, so SCOS-2000 extracts and calibrates all 16 bits.

    For contrast: a bit-packed packet¶

    Not every packet is this tidy. In the PHI instrument's report PHI_monitoredHousekeeping (SPID 53001, APID 1156, SID 1) several parameters share an octet and PLF_OFFBI does real work.65 Octets 17 and 18 hold seven status fields, and a 16-bit parameter overlaps all of them:

    The parameter NIPGH102 (PHI_MONHK_status, PTC 3 / PFC 12) starts at octet 17 bit 0 and spans the same 16 bits, so SCOS-2000 extracts the whole status word as well as its fields.65 The ICD explicitly allows such overlapping PLF entries and gaps.37

    Step 5: five parameters in depth¶

    All eleven parameters are raw telemetry parameters (PCF_NATUR = R) with no validity parameter (PCF_VALID empty), no on-board parameter ID (PCF_PID empty), no status consistency checking (PCF_USCON = N) and PCF_SUBSYS = 110.62 Without a validity parameter no validity condition is evaluated for these samples.40 The ICD declares the parameters of a periodic packet "expired" when no new packet arrives within PID_INTER plus a global margin; with PID_INTER empty, this packet declares no period for that check.4133

    Inference

    The ICD does not say explicitly how SCOS-2000 treats a periodic report whose PID_INTER is empty. Since it prescribes an empty field for non-periodic packets, SPID 59208 is presumably handled like a non-periodic packet, with no expiry timeout.

    PCF_INTER = F is present but ignored: SCOS-2000 takes the extrapolation rule from the calibration curve.43 The CUR table has no rows for these parameters, so each one has at most the single calibration named in PCF_CURTX.6345

    5.1 NIT83001 HK_SID: a textual calibration¶

    PCF field Value Meaning
    PCF_PTC / PCF_PFC 2 / 8 8-bit enumerated value
    PCF_CATEG S status parameter: needs a textual calibration
    PCF_CURTX CITT1120TM name of the TXF entry

    The TXF row CITT1120TM ("HK SID") has raw format U and 18 aliases in the TXP. Each alias maps a single raw value (TXP_FROM = TXP_TO) to a text: 1 → SID_1_BOOT, 20 → IIC_SID_20, 101 to 110 → HK_SID_101 to HK_SID_110, 112 → TASKs_Status, 113 to 116 → HK_SPARE_1 to HK_SPARE_4 and 120 → IIC_COPY.63 A raw value with no alias gives the invalid engineering value ****.43 Category S must be used only with a textual calibration and makes PCF_CURTX mandatory.42 Textual calibrations are described on Calibration in the MIB.48

    In this packet the SID can only ever be 108, because the packetiser used it to choose SPID 59208. The textual calibration is still useful: the same parameter NIT83001 is the SID field of 18 METIS packets in the PLF (SPIDs 59201 to 59221 and 59290), so one alias set serves them all.61

    5.2 NIT0E072 SAFE_Param: a 16-bit status word with two states¶

    NIT0E072 is a 16-bit enumerated parameter (PTC 2 / PFC 16), category S, calibrated by CITT1072TM "HV_SAFE STATUS", which has exactly two aliases: raw 0 → HV_ENABLED, raw 1 → HV_DISABLED.63 Any other raw value would show ****.43 No status check (OCP) is attached.64

    5.3 NIT0E0B6 HVU_mcp_V: a two-point numerical curve¶

    PCF field Value CAF field Value
    PCF_PTC / PFC 3 / 12 CAF_NUMBR CITP1058TM ("hvu_mcp_v")
    PCF_CATEG N CAF_ENGFMT / RAWFMT / RADIX R / U / D
    PCF_CURTX CITP1058TM CAF_UNIT V
    PCF_UNIT V CAF_NCURVE 2
    PCF_DECIM 2 CAF_INTER (empty → default F)
    PCF_DARC 1

    Values from the PCF and CAF;6263 field meanings from the ICD.434446 The CAP holds two points, (0, −330.4) and (4095, 1084.372).63 ICD 7.0 defines a numerical curve as a list of raw/engineering point pairs and uses CAF_INTER only for raw values outside the range; it does not spell out the rule inside the range.4647 The earlier ICD issue 6.9 describes it: a value between two points is interpolated linearly from the points on either side.57 The ECSS ground-segment data standard ECSS-E-ST-70-31C defines this kind of interpretation function the same way.56 Read that way, two points make the curve a straight line:

    \[V = -330.4 + x \cdot \frac{1084.372 - (-330.4)}{4095} \approx -330.4 + 0.345488\,x \quad \text{[V]}\]

    Engineering values are real numbers (CAF_ENGFMT = R) shown with 2 decimals (PCF_DECIM). CAF_INTER is empty, and its import default F makes a raw value outside 0-4095 return an invalid engineering value instead of an extrapolated one.46 PCF_DARC = 1 asks the parameter archive (DARC) to add the parameter to its recording list. The field is read by DARC only and not imported by SCOS-2000.44 See Mission archives.

    NIT0E0BF HVU_mcp_i and NIT0E0B7 HVU_scr_V use the same pattern with their own two-point curves: CITP1088TM from (0, −61.3) to (4095, 121.77) µA, and CITP1089TM from (0, −2220.18) to (4095, 7585.263) V.63

    5.5 NIT0E090 LED_curr_set: a polynomial¶

    NIT0E090 is calibrated by the MCF polynomial CIT01081TM "ILED", with coefficients A0 = 0, A1 = 6.6E-5 and A2 = A3 = A4 = 0.63 SCOS-2000 evaluates \(Y = A_0 + A_1 X + A_2 X^2 + A_3 X^3 + A_4 X^4\),49 here simply

    \[Y = 6.6 \times 10^{-5} \cdot X\]

    A full-scale 12-bit count of 4095 gives 0.27027. PCF_UNIT is empty and the MCF table has no unit field, so the display shows a bare number with 2 decimals.6249 led_cal_nom and led_cal_red share the same polynomial.61 A polynomial needs no point table and no extrapolation flag: it is defined for every raw value.49

    The two remaining parameters, SCREEN_Param and MCP_Param, have no calibration. The ICD says that the unit of an uncalibrated parameter would be shown next to the raw value, but both units are empty here.38

    A few "what if" cases show the checks at work:

    • HVU_temp raw 2560 (0A 00) calibrates to about 55.3 °C. That is above the soft high limit (50) but below the hard high limit (60). After two consecutive such samples (OCF_NBCHCK = 2) the parameter is reported soft out of limits.6450
    • HVU_temp raw 1000 lies below the first calibration point (1130). With CAF_INTER = F the engineering value is invalid.46 Limit checks work on valid values only, so this sample is not limit-checked at all.51
    • SAFE_Param raw 2 has no alias in CITT1072TM, so the display shows ****.43
    • SID 107 instead of 108 (octet 16 = 6B) would make the PID lookup return SPID 59207 ("HK SID107 - PMP Polarization"), and an entirely different PLF layout would apply.59

    The same decoding, written as a short Python sketch (illustrative code, not part of SCOS-2000):

    import struct
pkt = bytes.fromhex("0C44C4D2001E100319002F5E100080006C0000000000"
                    "0103BC055B07F8039F0BB800000000")
w0, w1, plen = struct.unpack(">HHH", pkt[:6])
apid, ssc = w0 & 0x7FF, w1 & 0x3FFF            # 1092, 1234
svc, sub, sid = pkt[7], pkt[8], pkt[16]         # 3, 25, 108
coarse, fine = struct.unpack(">IH", pkt[10:16])
obt = coarse + fine / 65536                     # on-board seconds
raw = lambda off: struct.unpack(">H", pkt[off:off + 2])[0]
hvu_mcp_v = -330.4 + raw(23) * (1084.372 + 330.4) / 4095   # CITP1058TM
led_curr = 6.6e-5 * raw(31)                                  # CIT01081TM

    Step 7: what happens after decoding¶

    SCOS-2000 has no special processing for service 3 packets: each one must be defined in the database before the spacecraft starts sending it. The time stamp of each parameter sample is the packet time plus the static offset in the database (PLF_TIME, 0 here). The collection interval is also static and does not follow service 3 commands that change it on board.55 With the packet time stamped, each sample is calibrated, checked and archived, and is then available to displays, to the parameter archive and to external users through EDDS. The archived SCOS-2000 packet carries a time-stamp policy flag: for spacecraft TM it can be the correlated spacecraft event time, with a quality flag.29 The Downlink page follows that chain further.

    SELECT * FROM vdf;
-- candidate HK packets: parameter count and calibration kinds per SPID
WITH x AS (SELECT p.PID_SPID spid, p.PID_APID apid, t.TPCF_SIZE sz, c.PCF_NAME pn, c.PCF_CURTX cx
             FROM pid p JOIN tpcf t ON t.TPCF_SPID = p.PID_SPID
