    How it all fits together¶

    A temperature sensor on a spacecraft produces a number. Before an engineer in Darmstadt or a scientist at a university sees that number as "25 °C, in limits", it passes through a chain of standards and systems. On-board software packs it into a report defined by the ECSS Packet Utilization Standard (PUS). The report travels inside a CCSDS Space Packet. Packets are multiplexed into transfer frames, and the frames are protected by channel coding for the radio link. A ground station recovers the frames and hands them over the ground network using Space Link Extension (SLE) services. The SCOS-2000 mission control system then decodes every bit, using a database that describes every packet, parameter and command: the Mission Information Base (MIB). Finally the data are archived and disseminated to users through EDDS. Telecommands make the reverse trip, with a retransmission protocol (COP-1) and a verification loop that closes in the telemetry.113335773

    This page explains the whole chain once, at the level an engineer new to ESA mission operations needs, and links every step to the page that explains it in full. Two real examples from the public Solar Orbiter MIB run through it: a solar-array drive temperature on the way down and a connection-test command on the way up.

    The CCSDS overview places these protocols in a five-layer model (physical, data link, network, transport, application). The data link layer has two sublayers: the Data Link Protocol Sublayer, which moves higher-layer data in Transfer Frames, and the Synchronization and Channel Coding Sublayer, which delimits, synchronises and protects those frames on the link. Below it, CCSDS has one omnibus physical-layer standard, Radio Frequency and Modulation Systems (CCSDS 401.0), for links between spacecraft and ground stations; short-range links between spacecraft, landers and relays use the separate Proximity-1 protocol family.9899 The Space Packet Protocol sits above the data link layer. The PUS is an application-layer protocol on top of it; the ECSS communications handbook of 2008 notes that ESA and ECSS developed it independently and that CCSDS has not adopted it.2311

    1. On board: parameters, application processes and services¶

    An on-board application process is the unit that sends and receives packets: its APID names the source of each telemetry packet and the destination of each telecommand packet.17 It can be software, firmware or hardware, a spacecraft can have one or many, and the PUS does not prescribe how they map onto subsystems and computers.13 Application processes host subservice providers and subservice users; usually the providers are on board and the users on the ground, but the standard does not require this. A message that a user sends to a provider is a request; a message that a provider sends back is a report. The PUS distinguishes three kinds of report: verification reports (routing, acceptance, start, progress and completion of a request), data reports (on request or autonomous, for example periodic housekeeping) and event reports.13

    The PUS is a menu. It defines a set of service types, every one optional, and each mission selects which services each application process implements and at what capability level. The result is documented in a mission "Space-to-Ground Interface Control Document".12 ECSS-E-ST-70-41C defines 20 standard service types; identifiers 7, 10 and 16 are reserved because earlier versions used them.14

    A parameter is the smallest unit of monitoring: a temperature, a voltage, a status bit. The PUS housekeeping service collects sampled parameters into reports. Each report structure has an identifier, a collection interval and an ordered list of parameters, some of them super-commutated (sampled several times per report).93 The ground must know the layout of every report it can receive. The SCOS-2000 ICD states this plainly: a new housekeeping packet defined on board through service 3 is not processed until its definition has also been added to the TM/TC database, and ESA missions usually create the definition in the database first and generate the service 3 commands from it.66 That is the first reason the MIB exists.

    2. Packets: a PUS message inside a CCSDS Space Packet¶

    When messages travel between ground and space, the PUS puts them in CCSDS Space Packets.13 A telecommand packet carries a request from a ground application process to an on-board one; a telemetry packet carries a report the other way.16 A Space Packet is a 6-octet primary header followed by a data field of 1 to 65,536 octets, so a packet is 7 to 65,542 octets long.23

    Solar Orbiter speaks PUS-A

    A mission applies the PUS issue its interface documents name. The Solar Orbiter TM/TC ICD sets the PUS version field to 1 (ECSS-E-70-41A) in both directions. Its TM data field header is 10 octets, its largest TM source packet is 4,112 octets, and its 11-bit APID is split into a 7-bit process ID and a 4-bit packet category.8185 PUS-A's TC header is 1 + 3 + 4 + 8 + 8 bits plus an optional source ID whose size the mission chooses.22 See PUS-A vs PUS-C and how Solar Orbiter uses PUS.

    The Space Packet Protocol itself does not route. Every node that handles a packet looks at the APID and forwards it along a path that management has set up; the APID-to-path rules are agreed per mission and are not part of the protocol.7 CCSDS also defines an Encapsulation Packet for carrying other protocols' data units over the same links.4

    3. Frames: many packet streams share one link¶

    A spacecraft has one downlink but many packet sources and data types with different needs: real-time housekeeping, recorded science, event logs. The data link protocols solve this with virtual channels. A physical channel (the bit stream in one direction) is split into several logical channels; every transfer frame belongs to exactly one of them. All frames with the same transfer frame version number and spacecraft ID form a master channel.4 Most missions use the TC Space Data Link Protocol forward and the TM Space Data Link Protocol in return, and only one data link protocol may be used on a given physical channel.8

    Telemetry frames¶

    TM frames have a fixed length on a physical channel during a mission phase, which makes synchronisation on a weak, noisy signal simple and robust.9 A TM frame is a 6-octet primary header, an optional secondary header of up to 64 octets, a data field, an optional 4-octet Operational Control Field (OCF) and an optional 2-octet Frame Error Control Field (FECF).25

    Packets are packed end to end into the data fields of the frames of their virtual channel; a long packet can span frames, and the First Header Pointer tells the receiver where the first new packet starts.26 Neither the TM nor the AOS data link protocol retransmits lost frames: if complete delivery matters, a higher layer must provide it.4

    Telecommand frames and COP-1¶

    TC frames have a variable length, given in the header, so that short commands go out with little delay.9 A TC frame is a 5-octet header, a data field of up to 1,019 or 1,017 octets and an optional 2-octet FECF, to a maximum of 1,024 octets (5 + 1,017 + 2 = 1,024 when the FECF is present). The ECSS adoption notice makes the FECF mandatory and keeps only the 1,017-octet figure.2728

    The Communications Operation Procedure-1 gives the forward link reliable, in-order delivery. It is a "go-back-n" retransmission scheme: the sending end runs FOP-1, the spacecraft runs FARM-1, and FARM-1 accepts Type-A frames only in strict sequence. FARM-1 reports its state in the Communications Link Control Word (CLCW), which travels back in the 4-octet OCF of the telemetry frames; FOP-1 retransmits on a "Retransmit" flag in the CLCW or on a timeout. Type-B frames bypass the sequence check and are used for control commands and recovery.2910925 The COP-1 page has the state machines.

    Solar Orbiter's link configuration

    Spacecraft ID 0x28A (650) on both links. TM frames are always 1,115 octets (8,920 bits) with a 1,099-octet data field; TM source packets longer than that are split across frames. Virtual channels carry, from highest to lowest downlink priority, real-time high-priority TM (VC4), real-time TM (VC0), the critical event log (VC5), playback from the on-board computer's mass memory (VC1) and from the solid-state mass memory (VC2, then VC3), and idle frames (VC7); the ICD lists VC5 second but sends it only when neither VC4 nor VC0 has data. TC frames are at most 256 octets on one of two virtual channels, one per on-board TC decoder.858687

    4. Channel coding: getting bits through the noise¶

    The Synchronization and Channel Coding Sublayer adds three functions to a stream of frames: delimiting and synchronising them, error-correcting coding, and bit-transition generation (pseudo-randomisation).6

    On the downlink every frame (or codeblock) is preceded by an Attached Sync Marker; for uncoded, convolutional, Reed-Solomon and rate-⅞ LDPC data it is the 32-bit pattern 0x1ACFFC1D.30 On the uplink the unit of transmission is the Communications Link Transmission Unit (CLTU): a start sequence, the frame encoded as a series of codewords, and, for BCH coding, a tail sequence. A BCH codeword carries 56 information bits, 7 parity bits and a filler bit set to zero.3132

    The 64-bit LDPC start sequence is 0x034776C7272895B0, and the (512, 256) LDPC code uses no tail sequence at all because a conventional LDPC decoder reliably fails when it runs past the end of the CLTU.32 The details are on the TM coding and CLTU pages.

    The coded symbols finally modulate a radio carrier. CCSDS 401.0 and ECSS-E-ST-50-05C define the frequency bands, spectral limits and permitted modulations, and ECSS-E-ST-50-02C the ranging and Doppler tracking that share the same link.10010110298 The Solar Orbiter MIB shows the choices as data: the deep-space transponder housekeeping report ("PLF DST HK", SPID 33793) reports a telemetry modulation scheme of GMSK or SPL and a telecommand bit rate between 7.8125 and 4000 bit/s.107 See radio frequency, modulation and ranging.

    5. The ground station and the ground network¶

    ESA's ground stations form the ESTRACK network.5376 At ESOC the operational LAN (OPSLAN) is the centre of the IP-OPSNET network that connects to the ESTRACK ground stations; it is a restricted network, and data for outside users must be relayed through separate RELAY LANs.76 In SLE terms, the SLE System at the ground end of the space link demodulates the signal, terminates the space link protocols and adds annotation: the time of reception, the receiving location, and the quality and sequence status of each data unit.3537 The station's Intermediate Frequency and Modem System (IFMS) also measures Doppler, ranging, signal gain (AGC) and meteorological data and offers them as files over FTP.5354 For Rosetta and Mars Express the mission control system fetched these files through its Network Interface Subsystem, stored them in the file archive and passed them to flight dynamics.55

    Space Link Extension¶

    SLE standardises how space link data units travel on the ground, so that the ground assets of different organisations can work together without ad hoc gateways built for each new mission and one agency's station can serve another agency's spacecraft.34 It "extends" the space link in three ways: over distance (processing can happen far from the antenna), in information (annotation) and in time (data can be stored and delivered later).36 SLE has transfer services, which move the data, and management services, which schedule them.33 How a mission books station time through service agreements and service packages is on SLE service management.

    After CCSDS 910.3-G-3 §4.2.1 and §4.3.1.3839 The ROCF service matters on the forward side as well: the CLCW it delivers tells the CLTU service provider whether the physical link is available and tells the provider of the VC and packet services whether TC frames must be retransmitted under COP-1.39 Over terrestrial networks, SLE runs on TCP/IP with ASN.1 encoding using the Internet SLE Protocol (ISP1).40 The library holds the 2023 issues of the RAF, RCF and ROCF and FCLTU specifications, the historical Forward Space Packet book with its API, the ISP1 and API books, and the cross support reference model and service management documents; the standards landscape lists their issues.

    NCTRS and NIS: the control centre's door¶

    At ESOC, SCOS-2000 does not talk to stations directly. The NCTRS sits between the mission control system and the ground station network and uses SLE for non-ESA stations.49 The sources expand the acronym in several ways, among them "Network Control and TM/TC Router System" and "Network Controller and Telemetry Receiver System".4951 For Mars Express it received telemetry already checked and time-stamped with the Earth reception time by the station equipment, passed it to the mission control system, collected the telecommands from the control system and forwarded them to the right station, and also handled tracking data and station files.51 In the SCOS-2000 R5 era the SLE service user role belongs to the NIS, while the station's TMTCS is the SLE service provider.72 The acronym appears as "Network Interface System" in an ESOC presentation and as "Network Interface Subsystem" in the Rosetta and Mars Express flight dynamics ICD.9155 SCOS-2000 can send two kinds of "throw event" directives: SLE throw events go to the station equipment, NIS throw events are executed by the NIS itself.7270

    The Solar Orbiter MIB shows this interface as data. It defines six NIS throw-event commands (open and close the TC link, the TM link and the session) on a header called NOS2KHDR, and two COP-1 control frames, UNLOCK ("FARM UNLOCK directive") and SETVR ("SETV( R ) Directive"), as command type F, which the ICD defines as BC control frames. Three more directives (RESET "PAC RESET directive", REIN_TTR and TC_ONLY) have type R, a control segment.7088

    Inference

    The sources place the SLE service user (NIS) on the control-centre side and the FCLTU provider at the station, and the MIB defines FARM control frames as commands. Together this implies that TC frames, COP-1's FOP-1 and CLTU generation run on the ground side before the FCLTU interface. Which ESOC component hosts FOP-1 is not stated in the available sources.

    6. The control centre: SCOS-2000 and the MIB¶

    SCOS-2000 is ESA's mission control system kernel, a distributed client-server system built on the CCSDS packet standards, the PUS and SLE.43 Its servers include the packetiser, the limit checker, the synthetic-parameter generator, the command multiplexer, releaser, verifier and on-board queue model, the archive and the event servers.44 The packetiser rebuilds packets from frames, extracts the CLCW and checks quality and sequence continuity; the command side offers manual and automatic stacks, pre-transmission validation and multi-stage verification.4645

    What the MIB is¶

    The SCOS-2000 Mission Information Base has a static part, the "database", and a dynamic part, the packet archive.58 The static part reaches SCOS-2000 as a set of tab-separated ASCII tables, one file per table named after it (pcf.dat, pid.dat, ...), exported from the mission's off-line database and imported into the run-time system.5759 The Database Import ICD (EGOS-MCS-S2K-ICD-0001) defines those tables. It distinguishes three representations of a value: the encoded bits in the packet, the raw value after type decoding, and the engineering value after calibration; for a 16-bit signed integer, raw −1 is encoded as 0xFFFF.58 The data model page shows how the tables relate. Independently of any tool, ECSS-E-ST-70-31C specifies what monitoring and control data a supplier delivers, and ECSS-E-ST-70-32C the language of the procedures that use it.103 How missions build and maintain such databases and procedures is on operations preparation, with the ECSS-E-ST-70-31C and PLUTO pages for the standards.

    How a telecommand is built¶

    On the command side the central table is ccf, one row per command. Its parameters are defined in cpc and placed in the application data by cdf; pre-transmission checks live in ptv; verification stages in cvs, linked to commands through cvp; and each command names a packet-header template in tcp, whose fields are laid out by pcdf.67 The header fields take their values from the command definition (APID, type, subtype, acknowledgement flags) or are filled in by the command subsystem (length, sequence count).68 The default maximum command size is 248 octets, and the total CLTU size is limited to a mission-specific value.69

    Time: from on-board clock to UTC¶

    A PUS telemetry packet carries its on-board time tag in the time field of its secondary header, and the ground must translate that into UTC.18 SCOS-2000 does this by time correlation. The spacecraft latches its clock when it transmits a frame whose frame count is a multiple of N (a power of 2 between 1 and 256) and reports the latched time in a later time packet. The ground knows the Earth reception time of the triggering frame from the NIS header and subtracts the ground, propagation and on-board delays. Each pair of on-board time and UTC is a "time couple"; a least-squares fit over many couples gives a gradient and an offset, or for a clock synchronised to an external source such as GPS only the offset is computed.56 For Mars Express the conversion was accurate to better than 2 ms.50 See time correlation and CCSDS time codes.

    7. Archives and dissemination¶

    SCOS-2000 files every packet it receives, indexed by type, SPID, data stream and time, and serves retrievals independently of real-time processing.47 In the EGOS ground system the archives are separate components: the packet archive (PARC) holds telemetry, telecommand and event packets, the parameter archive (DARC) holds parameter values, and the file archive (FARC) holds mission files.7580 A dedicated parameter archive was built because generating parameter values on the fly from packets could not meet the dissemination system's performance targets.78

    For Mars Express, the MCS sat on the operational LAN, only ESOC operations staff could reach it, and external users reached mission data through the DDS.52 The EGOS Data Dissemination System (EDDS) gives users who have no access to the MCS monitoring and control facilities controlled access to telemetry packets and parameters, telecommand history, events and auxiliary files through batch requests (a finite data set, possibly scheduled) and stream requests (a continuous feed), plus management and notification services.737479 Its requirements were based on three earlier ground-segment subsystems and a fourth prototype:77

    Why so many standards?¶

    The chain is layered so that each part can change on its own. ESA's control systems show the history. MSSS processed frame telemetry and telecommand; the SCOS-II paper says it entered service in 1977, while a 2003 ESA presentation gives 1984 to 1996. SCOS-I (from 1989) moved to packet telemetry; SCOS-II and then SCOS-2000 added a generic telecommand chain on a distributed architecture.11042 The standards evolved alongside: ESA's own PSS documents adapted CCSDS recommendations with European options and have all been withdrawn in favour of ECSS standards or CCSDS books; the history page traces the packet standards of 1988 to 1994 into today's documents.111 ESOC's reuse strategy rests on the same standards: CCSDS packet TM/TC, the ECSS PUS, SLE and XML.48 ESOC presents the payoff as cost and risk reduction, because a new mission develops and validates only a small amount of new software.94 CCSDS presents it as cross support: ground station owners can offer standard services to any operator whose spacecraft uses the CCSDS space link protocols.34 The standards landscape explains who publishes each document, how the issues relate and which ones this wiki holds.
