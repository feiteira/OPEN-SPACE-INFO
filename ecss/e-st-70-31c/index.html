    ECSS-E-ST-70-31C: monitoring and control data definition¶

    ECSS-E-ST-70-31C ("Space engineering – Ground systems and operations – Monitoring and control data definition", 31 July 2008) answers a simple question: when a supplier delivers a product (an instrument, a subsystem, a whole spacecraft), what data must come with it so that the customer can integrate, test and operate it? The standard calls that data the space system model (SSM). It specifies what data is delivered, not how (spreadsheet, XML or anything else is out of scope), and it assumes missions that follow ECSS-E-ST-50, ECSS-E-ST-70, the PUS (ECSS-E-ST-70-41) and the procedure language standard ECSS-E-ST-70-32.12 Formally the data is part of the user manual of the product.2

    In ESA practice the same knowledge ends up in a mission's Mission Information Base (MIB), the set of ASCII tables imported by SCOS-2000.90 This page explains the standard in full and then compares it, concept by concept, with the SCOS-2000 Database Import ICD and with the real Solar Orbiter MIB.

    At a glance

    Item Value
    Issue ECSS-E-ST-70-31C, 31 July 2008 (first issue ECSS-E-70-31A, 9 October 2007; B never issued)3
    Normative references ECSS-E-ST-50, -70, -70-01 (on-board control procedures), -70-11 (operability), -70-32 (PLUTO), -70-41 (PUS)4
    Core concepts System elements, reporting data (parameters and compound parameters), activities, events
    Languages Activity Call, EXPL, IFL, SPEL, VAL, PLUTO, all specified with railroad diagrams and ISO EBNF
    Size Clause 6 has 111 data requirement tables; Annex A gives tailoring flowcharts and packet layouts for 16 PUS services

    The space system model¶

    Products, system elements and views¶

    Throughout a project, suppliers deliver products: hardware, software or both, with the documentation needed over the whole life cycle. To make that knowledge shareable and reusable, the standard requires it to be organised as a space system model that mirrors the functional breakdown of the space system: system, subsystem, set, equipment or software product, assembly, and part (hardware) or module (software). Each level is a system element (SE), a data structure whose properties capture the knowledge.5

    Each system element carries three kinds of monitoring and control knowledge:6

    • Activities: monitoring and control functions implemented in the EGSE or mission control system (EMCS). An activity can be a telecommand to the space or ground segment, a procedure, an operating system command (print, e-mail, FTP) or any implementation-specific command, for example to a special check-out system or a ground station.
    • Reporting data: information a system element provides, whatever it is used for. It may be a measurement of the element's state or a product meant for another element (for example manoeuvre parameters from flight dynamics). A parameter is the lowest level of elementary information with a meaning for monitoring and control; a compound parameter is a record of parameters, arrays and sub-records interpreted together, such as a complete anomaly report.
    • Events: occurrences of a condition of operational significance, used to trigger functions (for example acquisition of signal starting telemetry processing at a station).

    The model consists of entity types (such as system element) and value types (such as APID). Every actor has its own view: one or more root system elements and the part of the hierarchy below them that interests it, so that a payload manufacturer only sees its payload and its EGSE.7 The same activity keeps its name and description whether it is implemented as a simulated command in testing or as a procedure in operations.7 For a given product the model is tailored: a subset of the entity and value types is selected and product-specific types are added (a 1553 bus protocol, mission-specific PUS services, an antenna controller's proprietary protocol).8

    The standard's own example is an attitude and orbit control subsystem decomposed into electronics, star trackers, reaction wheels, a sun sensor and a propulsion system, with activities such as "Switch On", events such as "Switch On Failure" and reporting data such as wheel speed or tank pressure attached at the appropriate level.5

    Naming¶

    Because suppliers work in parallel, names that are unique for one supplier may clash at a higher level of integration. The standard therefore uses relative names (one or more words of letters and digits, separated by spaces, such as "Star Tracker") made unique where needed by a reference path after the keyword "of" ("X Thruster of Branch 1", "temperature of XGyro"). Names are case-insensitive. The same scheme names the model itself: "Severity of Event" is the value type Severity of the entity type Event.14

    Conventions and data types¶

    Data requirement tables¶

    Each entity type is specified as a table of three columns: the value type name, its definition and constraints, and its data type; "List of" and "Ordered list of" mark lower-level entities with arity above one. When a row is conditional, the data is not provided if the condition is false. Language syntax is given with railroad diagrams (non-terminals in rectangles, terminals in rounded boxes, branches for options, return lines for repetitions) and again in ISO/IEC 14977 EBNF in Annex B.151617

    PUS types. Two further families come from the PUS. Service type and subtype: standard service types 0–127 and mission-specific 128–255; standard subtypes 0–127, mission-specific subtypes 128–255 within a standard service, or 0–255 within a mission-specific service.21 And the parameter code (PC) = parameter type code (PTC) + parameter format code (PFC):22

    PTC Data type PFC range
    1 Boolean 0
    2 Enumerated 1–16, 24, 32
    3 Unsigned integer 0–16
    4 Signed integer 0–16
    5 Real 1–4
    6 Bit-string 0 to any
    7 Octet-string 0 to any
    8 Character-string 0 to any
    9 Absolute time 0–18
    10 Relative time 0–16
    11 Deduced 0

    There is a subtle shift of meaning: in the PUS the PFC defines the size of the encoded value, whereas here it expresses the range of values (PTC 3 PFC 0 is an integer from 0 to 15; PTC 8 PFC 12 a fixed 12-character string). PTC 11 is not used, because every deduced parameter is instantiated as one of the other types. Booleans are 0 (false) and 1 (true) in packets.2223 The SCOS-2000 view of the same codes is on MIB parameter types and PUS parameter types.

    User-defined enumerated types. A user can define an enumerated set by name and list of values. When the values are sampled in packets, each element gets a raw correspondence: one raw value (PTC 2) for a one-to-one mapping, or, for many-to-one mappings, a raw type (PTC 3, 4 or 5) with a list of raw intervals per element, plus a default raw value for encoding telecommand arguments. The standard's examples are a battery charge status (trickle 0, full 1, discharge 2) and a filter wheel readout where raw 5–6 means "red", 7–8 "green" and 0–4 or 13–15 "non-operational".2425

    Value type sets and value type data types let a data item take any populated value of another item (for example "ID of system element of Type application process", the set of all APIDs) or inherit its type ("same as Data Type of current parameter").26

    The languages¶

    Complex data items are strings in one of six languages.27

    Language Used for Specified in
    Activity Call Instantiating an activity with argument values or a predefined value set and directives (MAP ID, AD or BD mode, requested verification reports); corrective actions ECSS-E-ST-70-32 Annex A.3.9.28
    EXPL (expression language) Validity, selection and pre/post-conditions Annex B.5
    IFL (interpretation function language) Raw-to-engineering interpretation and the reverse Annex B.6
    SPEL (synthetic parameter expression language) Synthetic parameters Annex B.7
    VAL (value language) Default values and value sets Annex B.9
    PLUTO Procedures ECSS-E-ST-70-32 (see PLUTO)

    Sources: §6.2.2 to §6.2.7 and Annex B.282930

    EXPL, IFL and SPEL share an expression grammar: Boolean operators AND, OR, XOR and NOT; relational comparisons, between ... and ... and in (...); + - * / and **; functions from ECSS-E-ST-70-32 Annex C; constants with units; and, in IFL, the keyword raw value. The requirements behind them insist on engineering units on constants, free mixing of compatible units and automatic unit conversion.313228

    A glitch in the prose

    The prose under the railroad diagrams of B.5, B.6 and B.7 lists the relational operators as "AND, OR, XOR" (a copy of the Boolean operator list). The EBNF of B.7.3 gives the intended set: =, !=, <, >, <=, >=.3133

    SPEL adds what a synthetic parameter needs (requirements 6.2.6): a trigger (on update of a reporting data, meaning a new sample rather than a changed value, or on an event, or any combination); a declaration of typed local variables and persistent variables that keep their value between evaluations; if ... then ... else and in case ... is ... or is ... otherwise flow control; a context statement (in the context of ... do ... end context); property requests (get Raw Value of ...; a bare parameter name means its engineering value); bit functions bitand, bitor, bitxor, bitnot, bitshl, bitshr; and an assignment of the result with set ... with ... end with. The result is an engineering value that needs no further calibration.353637383334

    synthetic parameter
  trigger
    on update of Bus Voltage of PCDU or on update of Bus Current of PCDU
  end trigger
  declare
    variable Power of type real with units W described by "instantaneous bus power",
    persistent Peak of type real with units W set to 0 W described by "highest power so far"
  end declare
  main
    Power := Bus Voltage of PCDU * Bus Current of PCDU;
    if Power > Peak then
      Peak := Power;
    end if;
    set engineering value with Power end with;
  end main
end synthetic parameter

    VAL writes simple values, records (record ... end record) and arrays (array ... end array), each optionally named after the component it fills, with constants, activity calls, reporting data references or system element references as values.39

    Data exchange and the data life cycle¶

    Exchange rules¶

    The supplier delivers a subset of the model plus product-specific types; the product data schema must be specified, machine-processable and lossless on re-import. The formal languages above should be used, and any other language must be specified in EBNF. The electronic database is under configuration management and is identified by a configuration item ID, a version number, a generation date, a supplier ID and the list of digital files, each with type and checksum; each file is uniquely identified and compressed with a standard tool.4041

    Product configuration data¶

    Each delivered product is described as either a specification (a theoretical product) or a realization (a real one), and typed as a developed hardware configuration item (CI ID, part, serial and lot numbers, model such as EM, STM or FM, manufacturer), a developed software CI (software identifier, version, release date), a COTS or standard product, or a non-CI product.4243

    Versioning. A system element gets a new version when any of its properties change or when any of its activities, reporting data, events or constituent elements are created or deleted; activities, reporting data and events get a new version when any of their properties change (for reporting data, also when sub-components appear or disappear). Every version records number, date, originator, reason and a validation status: not validated, validated by review, by simulation or by testing. The same data is kept for every constituent product, so that knowledge supplied at lower levels or earlier phases stays traceable.4445

    Population rules¶

    Rule (6.4) Content
    Language and case All data in English, case-insensitive except engineering units
    Renaming If an object is renamed during integration, its former names are retained
    Consistency The data agrees with the product documentation (ICD, user manual)
    Uniqueness Object names unique within a delivery
    Life-limited items Accumulated operational cycles or life provided with each delivery
    Sub-suppliers Provide enough to populate everything the customer needs
    Domains Domain-specific data (Software, AIV, Operations) identified as such
    Validation All data validated (review, simulators, real hardware); for operations, with real hardware wherever possible

    "Fully populated" is defined precisely. For reporting data it means: everything in the documentation, including dumpable software tables and memory; redundancy links between items conveying the same information; all interpretation functions with their applicability conditions; validity conditions; ground monitoring checks for all reporting data (except those that can take any value); status consistency checks where values depend on activities or events; and corrective actions for violations. For activities: everything in the documentation, all atomic activities, arguments in engineering values with their de-interpretation, pre- and post-conditions, verification conditions for start, progress and completion deduced from low-level telemetry whether or not the PUS verification service is used, redundant and reverse links, criticality, corrective actions, execution profile and resources. For events: all events and their corrective actions.464748

    System element data¶

    Every system element has a name unique within the product, a description, a type and a nature (specification or realization), references to the sub-product elements integrated into it, and its redundant elements. The type list is long: system, subsystem, set, equipment, software product, assembly, part, module, element, facility (ground), application process, MAP, VC, any service, function, memory block, memory sub-block, store, CPDU, On/Off device, register load device and sensor.9 Elements that send telecommands or receive telemetry get a PUS source or destination ID; life-limited elements get maximum cycles and duration plus the record of operations.10

    Application process (6.5.4) APID (PTC 2 PFC 11, unique in the system); service accesses (commanding path, monitoring path, memory and store management, store access, event report access) with the elements concerned; word length (8, 16, 24, 32 or 64 bits) for padding; PFCs of the length fields of variable bit, octet and character strings; TC checksum type (ISO or CRC); PFC of the TM time field; whether there is a packet sub-counter; TM checksum type

    Service data and PUS tailoring¶

    For each standard PUS service an application process hosts, the supplier provides three things: the tailoring variables (Booleans stating which capabilities are implemented), the data types of the packet fields (the PFC of each field that the tailoring leaves present) and the service-specific configuration data the ground needs to model the service.57 Annex A gives, for each service, a short summary of the PUS service model, a yes/no flowchart whose "yes" branches set tailoring variables, and the packet layouts with semantics, field names, data types and presence conditions.5859

    Telecommand verification is the simplest. Three tailoring variables say whether the service verifies start (S1 ST3 and ST4 Provider), progress (S1 ST5 and ST6 Provider) and completion (S1 ST7 and ST8 Provider); the field types are the PFCs of the Code and (if progress is verified) Step Number fields; and the service data is the list of command failure codes valid for all commands, with the stages they apply to and the parameters that accompany them (codes 0 to 5 have a special meaning in the PUS).60

    Reporting data¶

    Generic data¶

    Every reporting data item names its system element and itself (relative name), describes its purpose, says whether it is a parameter or a compound parameter, lists the domains (AIV, Operations, Software) where it applies, gives per domain a validity condition (an EXPL Boolean expression saying when its interpretation is meaningful), traces back to the sub-product item it came from, and lists redundant reporting data conveying the same information (the standard's example is two boom release sensors).11

    Parameters and interpretation¶

    A parameter has the data type of its engineering value; if it is referenced inside packets it has a Parameter Number (the PUS "Parameter#", never 0, assigned system-wide). If the transported value can be taken directly as the engineering value, only the PFC of the raw value is given. Otherwise an interpretation is defined: the PTC and PFC of the raw value, and per domain an ordered list of interpretation functions, each with an EXPL selection condition; the first function whose condition is true applies. A function is either a linear interpolation between calibration points (raw, engineering), with an extrapolation flag ("extrapolate" from the last two points or declare "invalid" outside the range), or an IFL script. For every interpretation a raw value must give a unique engineering value.676869

    Compound and synthetic reporting data¶

    A compound parameter is a record (ordered components, each with a sampling time offset when in a packet), an array (fixed or variable, minimum and maximum repetitions, components, time offset of the first element, delta time between elements, PFC of the repetition counter of a variable array) or a deduced structure (a list of alternative component lists, each selected by an EXPL condition; more than one can be true).7071 Reporting data computed in the EMCS is synthetic and carries a SPEL script, which can set one or several components of a compound parameter.72

    Activities¶

    Definition¶

    An activity names its system element and itself, describes its function, has a type (ground procedure, on-board procedure, telecommand, operating system command), domain applicability, traceability references, lists of redundant activities (same effect) and reverse activities (opposite effect), a criticality taken from ECSS-E-ST-70-11 (non critical, locally critical, mission critical) and an ordered, flat list of arguments. Each argument has a name, description, type (any simple type, record or activity call), arity (single value or array, with minimum and maximum repetitions), and a default or fixed value in VAL. Predefined argument value sets can be named and described.127778 ECSS-E-ST-70-11C gives the meaning of the criticality levels.

    Procedures¶

    Procedures are initiated explicitly (foreground) or run permanently (background) and have earliest and latest validity dates. A ground procedure is a PLUTO script with a default automatic or manual execution mode; an on-board procedure is an ECSS-E-ST-70-01 script with a preloaded flag and a high, medium or low priority for conflicts.88

    Events¶

    An event names its system element and itself, has a description, a type (anomaly report, progress report, information, software error, scheduling event...), domain applicability, references, a severity (normal, low, medium, high, with a pointer to the PUS event reporting service), the reporting data accompanying it with their time offsets from the event time, and per domain the activity to run when it occurs.13

    Inference

    The rows "System element hierarchy", "Procedures" and "Service tailoring data" compare concepts the ICD never relates to ECSS-E-ST-70-31C; the pairing is this wiki's. The ICD does not cite ECSS-E-ST-70-31C at all.

    The ICD also documents what SCOS-2000 does with the PUS services that 70-31C asks suppliers to describe. For example, service 1 reports are matched to commands by the 4 echoed header octets and only the subtype (not the failure code) drives verification; housekeeping packets must be defined in the database before they are enabled on board, with fixed time offsets and collection intervals; service 11 has a ground model of the on-board schedule built around the Rosetta packet structure; services 4 and 12 reports are variable packets and so excluded from full processing.111112113

    Why the standard matters¶

    ECSS-E-ST-70-31C is the reason a supplier's database can be specified contractually: it lists what "complete" means for every parameter, command and event, and it makes ground-side knowledge such as calibration, checks, verification conditions and corrective actions part of the delivery rather than something the operator reconstructs from documents. Its companion requirements in ECSS-E-ST-70-11C (for example that every packet carries what is needed to calibrate and validate its data, or that the same parameter always has the same interpretation) are what make such a model possible on the spacecraft side.46116

    Inference

    The previous paragraph is this wiki's assessment of the standard's role; the standard itself only states its purpose (defining the data a supplier provides for monitoring and control).2
