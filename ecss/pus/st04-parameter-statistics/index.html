    ST[04] Parameter statistics reporting¶

    The parameter statistics reporting service, service type 4 of the Packet Utilization Standard, lets an on-board application process watch a list of on-board parameters and compute, for each of them, the maximum, minimum, mean and (optionally) standard deviation of the values it samples during a time interval. Instead of downlinking every sample, the spacecraft sends a single parameter statistics report TM[4,2] that summarises the interval.1 The standard names the typical use: missions with limited ground coverage, such as low Earth orbiters, can read one report after acquisition of signal and learn how parameters behaved during the previous period of "no contact".134

    This page describes the service as defined by ECSS-E-ST-70-41C ("PUS-C", clause 6.4 for the system requirements and clause 8.4 for the packet layouts), compares it with ECSS-E-70-41A ("PUS-A", clause 9), lists the tailoring data required by ECSS-E-ST-70-31C, summarises the changes in the 2024 Rev.1 draft, and explains how ground systems such as SCOS-2000 handle it - including the finding that the real Solar Orbiter MIB contains no service 4 packet at all.

    At a glance

    Item Value
    Service type 4, "parameter statistics reporting"17
    Subservice types exactly one: the parameter statistics reporting subservice1
    Providers per application process at most one2
    Message types (PUS-C) 7 requests TC[4,1], [4,3]-[4,8]; 2 reports TM[4,2], TM[4,9]27

    Always evaluated maximum, minimum, mean; standard deviation by declaration4

    Solar Orbiter "Service 4: Not Used"; no type 4 packet or command in the MIB6062

    1. Concept and rationale¶

    1.1 Why evaluate statistics on board¶

    PUS-A presents "statistical data reporting" as a second mechanism, next to housekeeping reporting, for reducing the quantity of engineering data sent to ground: evaluate mean, minimum, maximum and standard deviation on board and report only the results. In its minimum form the parameter set and the evaluated attributes are predefined and evaluation is continuous; optional extensions let the ground change the parameters and the evaluation intervals.34 PUS-A also suggests the service as an alternative to housekeeping reporting during non-coverage when on-board storage capacity is limited.35 PUS-C keeps that rationale - the service is "especially appropriate" for missions with limited ground coverage - and adds that it can reduce the engineering data that is systematically reported.1

    1.2 The model¶

    Each parameter statistics definition names one parameter and its sampling interval. The subservice keeps a list of such definitions (the "list of evaluated parameters"), at most one definition per parameter, and the maximum number of definitions it can evaluate at the same time is a declared constant of the subservice.3 For each listed parameter it evaluates all the supported statistic types at any time: maximum, minimum and mean always; standard deviation only if the subservice declares that it supports it.4 A default sampling interval is declared per parameter.5

    Evaluation is continuous. What varies is when results are reported and when the accumulators are cleared:

    flowchart TB
  S["Every sampling interval<br/>(per parameter)"] --> U["Update accumulators:<br/>number of samples, max + time first attained,<br/>min + time first attained, mean, (std. deviation)"]
  U --> S
  R1["TC[4,1] report the parameter statistics"] --> G["Generate one TM[4,2]<br/>(one notification per parameter<br/>sampled at least once since last reset)"]
  P["End of periodic reporting interval<br/>(if periodic reporting enabled)"] --> G
  G --> D{"Reset?"}
  D -- "periodic report: always" --> Z["Clear accumulators,<br/>restart evaluation"]
  D -- "TC[4,1]: if reset flag set,<br/>or subservice auto-resets" --> Z
  D -- "otherwise" --> S
  R3["TC[4,3] reset the parameter statistics"] --> Z
  Z --> S

    Sources for the diagram: the sampling and notification rules of clause 6.4.5.3, the reset rules of clauses 6.4.4, 6.4.5.1-6.4.5.2 and 6.4.6.2h.967811

    The PUS-A version of the concept is the same: statistics are evaluated continuously from successive samples, reports are generated on request or periodically, the evaluation is systematically reset when a periodic report is generated and can be reset on request at any time.36 PUS-A gives the operational recipe for covering a non-coverage period: reset the evaluation just before loss of signal (LOS) and request the report shortly after acquisition of signal (AOS).36

    Which time is in the packet header?

    Because the interval between reports can be long, PUS-A recommends that the time field of the packet header indicates the report generation time, not the beginning of the evaluation interval.36 PUS-C sidesteps the ambiguity by putting both the start time and the end time of the evaluation interval in the report itself.9

    1.3 Statistics: what is and is not defined¶

    Quantity Defined by PUS-C Notes
    Number of samples yes, per parameter, in each notification9 new in PUS-C; PUS-A has no such field37
    Maximum and its time the maximum sampled value and the time it was first attained9
    Minimum and its time the minimum sampled value and the time it was first attained9
    Mean mean of the sampled values during the interval9
    Standard deviation of the sampled values, only if supported94 population or sample formula: not stated in the available sources
    Value format specific to the parameter identified by the parameter ID (deduced)19 the format of a mean or standard deviation of an integer parameter is not stated in the available sources

    2. Declarations a mission must make¶

    PUS-C leaves most choices to the mission and records them as declarations "when specifying that subservice". The full list for ST[04]:

    Declaration Clause
    Maximum number of parameter statistics definitions evaluated at the same time 6.4.3.1a3
    Whether the standard deviation is evaluated 6.4.3.2b4
    Default sampling interval of each parameter 6.4.3.3a5
    Exactly one of: reset flag carried in TC[4,1], or automatic reset after every TC[4,1] 6.4.5.1a-c7
    Whether periodic reporting is supported 6.4.6.1a10
    Periodic reporting interval implicitly known (and its value), or carried in TC[4,4] 6.4.6.1b-d10
    Whether definitions can be added or updated (TC[4,6]) 6.4.7.1a13
    Whether TC[4,6] can set the sampling interval 6.4.7.1b13
    Whether the definitions can be reported (TC[4,8]/TM[4,9]) 6.4.7.3a15

    Sampling intervals are expressed against the spacecraft's on-board parameter minimum sampling interval: each on-board parameter is associated to exactly one such interval, all parameters accessed by an application process share the same one, and the standard gives the example of a platform at 125 ms and a payload at 500 ms.29 The 2024 draft adds an explicit note to the ST[04] sampling interval clause pointing to that requirement.46

    4. The messages field by field¶

    Field types below are the PUS types of clause 7.3: enumerated (PTC 2), unsigned integer (PTC 3), Boolean (PTC 1), absolute time (PTC 9), relative time (PTC 10) and deduced (PTC 11, format deduced from a preceding field).30313233 Their sizes (PFCs) are mission choices, so the byte layouts depend on the mission.

    4.1 TC[4,1] report the parameter statistics¶

    Field Type Presence Meaning
    reset flag Boolean optional Present only if the subservice uses the "explicit reset flag" option; asks for a reset after the report is generated.188

    Each request contains exactly one instruction (which itself has no argument) and produces exactly one TM[4,2]. After the report is generated, the statistics are reset if the request asked for it or if the subservice is configured to reset automatically after every request.8 A Boolean value greater than zero means TRUE.30

    4.2 TM[4,2] parameter statistics report¶

    Field Type Presence Meaning
    start time absolute time always Start of the evaluation interval.199
    end time absolute time always End of the evaluation interval.199
    N unsigned integer always Number of parameter statistic notifications that follow.19
    repeated N times:
    parameter ID enumerated always The sampled parameter.19
    number of samples unsigned integer always Samples used to produce the statistics.199
    max value deduced always Maximum sampled value.19
    max time absolute time always Time the maximum was first attained.199
    min value deduced always Minimum sampled value.19
    min time absolute time always Time the minimum was first attained.199
    mean value deduced always Mean of the sampled values.19
    standard deviation value deduced optional Present only if the subservice evaluates the standard deviation.194

    The subservice emits one notification for each parameter that has been sampled at least once since the last reset; parameters never sampled are left out.9 The deduced fields take the format of the parameter named by the preceding parameter ID.19

    The field order follows Figure 8-54;19 the bit widths in the diagram are an illustrative mission choice (they are the sizes used in the worked example of section 7), not values set by the standard.

    4.3 TC[4,3] reset the parameter statistics¶

    No application data.20 The subservice stops the evaluation, clears every accumulated result and restarts the evaluation. The reset is independent of report generation.6

    4.4 TC[4,4] enable the periodic parameter statistics reporting¶

    Field Type Presence Meaning
    reporting interval relative time optional Present only if the subservice lets TC[4,4] set the periodic reporting interval.2111

    The subservice keeps a periodic parameter statistics reporting status (enabled or disabled).10 TC[4,4] is rejected - with a failed start of execution notification, see ST[01] - if it specifies a reporting interval shorter than the sampling interval of any evaluated parameter.11 Otherwise the status becomes "enabled" and the interval, if given, is stored. While enabled, the subservice generates exactly one TM[4,2] at the end of each reporting interval and systematically resets the statistics each time.11

    4.5 TC[4,5] disable the periodic parameter statistics reporting¶

    No application data. It sets the status to "disabled".2212 Evaluation itself goes on: in PUS-A terms, periodic reporting and resetting stop "and the parameter statistics evaluation shall continue".39

    4.6 TC[4,6] add or update parameter statistics definitions¶

    Field Type Presence Meaning
    N unsigned integer always Number of instructions.23
    repeated N times:
    parameter ID enumerated always Parameter to add or update.23
    sampling interval relative time optional Present only if TC[4,6] may set sampling intervals.2313

    Each instruction is checked on its own and rejected (failed start of execution for that instruction) if the parameter is unknown, if its sampling interval is greater than the reporting interval, or if it would add a definition when the maximum is already reached; the valid instructions are executed regardless of faulty ones.13 A new parameter is added and its evaluation starts immediately; an existing one gets the new sampling interval and its evaluation restarts.13

    Partial intervals and duplicates

    Because evaluation of a newly added parameter starts at once, independently of the reporting interval, the next report (and only that report) covers that parameter over a shorter interval than the others. If one request contains two instructions for the same parameter, the second overrides the first.13

    4.7 TC[4,7] delete parameter statistics definitions¶

    Field Type Presence Meaning
    N unsigned integer always Number of parameter IDs; N = 0 deletes all definitions.24
    parameter ID enumerated repeated N times Parameter whose definition is removed.24

    An instruction naming a parameter that is not in the list is rejected; valid instructions are executed anyway. If the list is empty after the request, the periodic reporting status is set to "disabled".14

    4.8 TC[4,8] report the parameter statistics definitions and TM[4,9]¶

    TC[4,8] has no application data.25 Its response TM[4,9] has the following source data:

    Field Type Presence Meaning
    reporting interval relative time optional Present if the subservice lets TC[4,4] change the interval; set to 0 s when periodic reporting is not enabled.2615
    N unsigned integer always Number of definitions.26
    parameter ID enumerated repeated N times Parameter.26
    sampling interval relative time repeated, optional Present if sampling intervals can be set.2615

    4.9 Observables¶

    PUS-C defines no observables for this subservice.16 The 2024 draft defines one: the number of parameter statistics definitions currently defined on board.49

    5. State model¶

    The only persistent state, besides the accumulators and the list itself, is the periodic reporting status. Its initial value after start-up is not stated in the available sources.

    stateDiagram-v2
  direction LR
  state "Periodic reporting DISABLED" as D
  state "Periodic reporting ENABLED" as E
  D --> E: TC[4,4] accepted (interval stored if present)
  E --> D: TC[4,5]
  E --> D: TC[4,7] leaves the list empty
  E --> E: end of reporting interval / TM[4,2] then reset
  E --> E: TC[4,1] / TM[4,2] (reset if requested or automatic)
  D --> D: TC[4,1] / TM[4,2] (reset if requested or automatic)
  D --> D: TC[4,3] / reset
  E --> E: TC[4,3] / reset

    Transitions from clauses 6.4.4, 6.4.5.2, 6.4.6.2, 6.4.6.3 and 6.4.7.2i.68111214

    6. A typical exchange¶

    sequenceDiagram
  participant G as Ground (MCS)
  participant P as On-board AP (ST[04] provider)
  G->>P: TC[4,6] add PARAM_A (120 s), PARAM_B (10 s)
  P-->>G: TM[1,1] / TM[1,7] (if requested by the ack flags)
  G->>P: TC[4,4] reporting interval 600 s
  Note over P: periodic status ENABLED
  loop every 600 s
    P-->>G: TM[4,2] start, end, N=2, statistics
    Note over P: automatic reset
  end
  Note over G,P: LOS ... AOS
  G->>P: TC[4,8]
  P-->>G: TM[4,9] interval 600 s, 2 definitions
  G->>P: TC[4,5]
  Note over P: periodic status DISABLED, evaluation continues

    The behaviour follows clauses 6.4.6 and 6.4.7;11121315 request verification reports are those of ST[01], and whether successful stages are reported depends on the acknowledgement flags in the TC secondary header.

    7. Worked example (illustrative bytes)¶

    Illustrative TM[4,2] source data

    All values below are constructed for explanation; they are not from any mission. The assumed mission choices are: absolute times in CUC with 4 octets of coarse and 2 of fine time (PTC 9, PFC 17, since (17 + 1) / 4 = 4 rem 231), N as an 8-bit unsigned integer, parameter ID and number of samples as 16-bit fields, and a parameter 0x0102 whose format is an IEEE 754 32-bit real. Five samples of a temperature are taken every 120 s from coarse time 1 000 000 000 (0x3B9ACA00): 21.50, 21.75, 22.00, 21.25, 21.50 degC.

    Offset (octets) Bytes Field Value
    0 3B 9A CA 00 00 00 start time 1 000 000 000 s
    6 3B 9A CC 58 00 00 end time start + 600 s
    12 01 N 1
    13 01 02 parameter ID 0x0102
    15 00 05 number of samples 5
    17 41 B0 00 00 max value 22.0
    21 3B 9A CA F0 00 00 max time start + 240 s (third sample)
    27 41 AA 00 00 min value 21.25
    31 3B 9A CB 68 00 00 min time start + 360 s
    37 41 AC CC CD mean value 21.6
    41 3E 82 88 EF standard deviation 0.2550 (population formula)

    The source data is 45 octets. With the sample (n - 1) formula the standard deviation would be 0.2850 - PUS-C does not say which one applies, so a mission specification must.

    8. PUS-A (ECSS-E-70-41A) differences¶

    PUS-A clause 9 defines the same service with ten subtypes.45

    Aspect PUS-A (2003) PUS-C (2016)

    Name of the list parameter statistics list, maximum <PSLIST_MAX_PARAMS>36 list of evaluated parameters made of parameter statistics definitions3
    TC 4,1 reset flag Enumerated, "No" = 0, "Yes" = 1, omitted if the service always resets37 Boolean, optional18

    TM 4,2 per parameter Parameter#, Maxval, tmax, Minval, tmin, Meanval, optional Stddevval3738 adds the number of samples; max/min times are "first attained"199

    Sampling interval rule must be smaller than the reporting interval when periodic40 rejected if greater than the reporting interval13
    Subtype 6 "Add Parameters to Parameter Statistics List"; NPAR omitted if one parameter at a time40 "add or update ... definitions"; N always present; update restarts evaluation2313

    Subtypes 8/9 "Report Parameter Statistics List" / "Parameter Statistics List Report"; reporting interval 0 s if not periodic; omitted if no periodic concept or a default is used42 "report the parameter statistics definitions" / "definition report"; 0 s if not enabled26

    9. Tailoring data in ECSS-E-ST-70-31C¶

    ECSS-E-ST-70-31C, the standard for ground-segment monitoring and control data, defines the data a mission database must hold to describe its tailoring of service 4. Its model follows the PUS-A subtype numbering.53

    Tailoring item (Boolean) Meaning Condition
    S4 ST4 and ST5 Provider periodic reporting supported -
    S4 Default Reporting Interval a default reporting interval is used if periodic supported
    S4 Add Parameters parameters can be added -
    S4 Default Sampling Interval a default sampling interval is used if add supported
    S4 Multiple Parameters several parameters per request if add supported

    10. Changes in the 2024 Rev.1 draft¶

    ECSS-E-ST-70-41C Rev.1 DIR1 (11 December 2024) keeps the nine message types and their layouts (only the figures are renumbered, 8.4-1 to 8.4-6)50 but changes the error semantics of list maintenance:4748

    • TC[4,6] and TC[4,7] now carry an ordered list of instructions, and the whole request is rejected if any instruction is invalid (unknown parameter, sampling interval greater than the reporting interval, list full, parameter not in the list). A request with only valid instructions is executed in order. In PUS-C each faulty instruction was rejected on its own and the others were executed.1314
    • TC[4,7]'s "delete all" becomes "a single instruction".48
    • A subservice observable is added: the number of definitions currently on board.49

    11. Ground segment view¶

    11.1 SCOS-2000¶

    The SCOS-2000 Database Import ICD states that there is no specific processing of service 4 in SCOS-2000 and no specific limitation, except that all service 4 reports are variable packets and therefore inherit the general variable-packet limitation.54 That limitation is important: parameter values extracted from variable packets cannot take part in full telemetry processing - validity, monitoring checks, verification checks, synthetic parameters - because their parameters and time references are only known once the packet is opened.55 On the command side SCOS-2000 offers command parameters of type "Parameter ID", which take the name of a telemetry parameter and encode its on-board identifier; the ICD names TC(4,6) as an example.56

    Inference: how a MIB would describe TM[4,2]

    The ICD does not give a service 4 example. In the SCOS-2000 MIB a TM[4,2] would be identified by PID (type 4, subtype 2, APID), given a TPSD and described in the VPD table: N as a repeat counter (VPD_GRPSIZE), the parameter ID with VPD_PIDREF = 'Y' so that its value is matched against PCF_PID in PCF, followed by the deduced value fields.58 Because of the variable-packet limitation, statistics delivered this way could be displayed and archived, but not limit-checked like ordinary telemetry.

    11.2 Not to be confused with ground-side statistics¶

    ESA's ground archive services compute their own statistics. For example the EDDS "Parameter Statistics" request returns statistics records with start time, storage time, minimum, maximum, average, standard deviation and the number of valid and invalid samples.59 These are evaluated on ground from archived samples; they are unrelated to the on-board ST[04] service.

    12. Mission usage¶

    12.1 Solar Orbiter: not used¶

    The Solar Orbiter space-to-ground ICD, whose applicable PUS is ECSS-E-70-41A, lists the service simply as "Service 4: Not Used".6160 The public MIB agrees: neither the April 2020 nor the September 2025 release contains a single TM packet (PID), packet identification rule (PIC) or telecommand (CCF) of service type 4, and neither does the SWA instrument database.626364 The only packet with "statistic" in its description is a housekeeping report, TM(3,25) "DAS Housekeeping Parameter Report (failure statistics)" on APID 1204.62

    SQL used 
    -- run on solo-2025-09-16.sqlite, solo-2020-04-16.sqlite and swa-idb.sqlite
SELECT COUNT(*) FROM pid WHERE PID_TYPE = '4';        -- 0 in all three
SELECT COUNT(*) FROM pic WHERE PIC_TYPE = '4';        -- 0 in all three
SELECT COUNT(*) FROM ccf WHERE CCF_TYPE = '4';        -- 0 in all three
SELECT PID_TYPE, PID_STYPE, PID_APID, PID_DESCR
  FROM pid WHERE PID_DESCR LIKE '%statistic%';        -- one TM(3,25) packet
-- infrastructure that ST[04] would need on the ground side:
SELECT COUNT(*), SUM(PCF_PID IS NOT NULL AND PCF_PID <> '') FROM pcf;  -- 126745, 19803
SELECT CPC_CATEG, COUNT(*) FROM cpc GROUP BY 1;       -- 152 'P' (Parameter ID) parameters

    The ground infrastructure that ST[04] would rely on does exist in the database: 19 803 of the 126 745 monitoring parameters carry an on-board parameter identifier (PCF_PID), and 152 command parameters are of the "Parameter ID" category (CPC_CATEG = P), the SCOS-2000 type that encodes a telemetry parameter name as its on-board identifier.625657

    12.2 Herschel and Planck: no requirement¶

    The Herschel/Planck Operations Interface Requirements Document (2003) keeps a section "Statistics Reporting (Service 4)" only as a placeholder: no requirement had been identified for such a service.65 See Herschel and Planck.

    Inference: why ST[04] is rare in ESA science missions

    Both missions documented in this wiki's library chose not to use ST[04]. A plausible reason, not stated in the sources, is that deep-space and L2 missions store all housekeeping on board and dump it at each pass, so a statistical summary adds little; the standard itself targets missions with limited ground coverage.1 The service drew only 8 of the 664 discrepancy review reports raised on the PUS-C draft, against 44 for ST[06].66
