    ST[06] Memory management¶

    The memory management service, service type 6 of the Packet Utilization Standard, lets the ground load data into on-board memories, dump their contents to ground and ask the spacecraft to check an area by computing a checksum on board.1 It is the low-level tool behind on-board software maintenance: patching code, uploading tables, reading back registers and logs, and verifying that memory has not been corrupted. PUS-A described it as an "off-line" activity for troubleshooting and software maintenance rather than routine operations, and asked that any on-board memory be readable and any RAM area loadable from ground.56

    PUS-C (ECSS-E-ST-70-41C, 2016) turned the PUS-A service into four subservices: raw data memory management (absolute addresses), structured data memory management (memory objects such as files or on-board control procedures, addressed by a base plus an offset), a common subservice (abort all dumps) and a memory configuration subservice (scrubbing and write protection).1 This page covers all 22 message types, the declarations each mission must make, the checksum algorithms, the PUS-A original (clause 11), the tailoring data of ECSS-E-ST-70-31C, the 2024 draft, the ground side in SCOS-2000, and the real memory map and commands of Solar Orbiter as described in its ICD and MIB.

    1. On-board memories¶

    1.1 The memory as a system object¶

    In PUS-C an on-board memory is a logical memory space; the mapping onto physical memories, possibly managed by different processors, is out of the standard's scope.4648 Each memory has exactly one memory identifier, unique across the spacecraft at any time - although the same identifier may serve several physical memories that cannot be accessed at the same time, as in cold redundancy.48 For each memory the mission declares:48

    Characteristic Values
    Memory access alignment constraint minimum number of bytes the services use to address the memory
    Memory size in bytes
    Allowed operations "read only", "read and write" or "write only"
    Addressing scheme absolute and/or base plus offset exposed to ground
    Scrubbing supported yes / no
    Write protection supported yes / no

    Behind the alignment constraint sits the physical smallest addressable unit, the minimum number of bytes a physical memory can address.48 With absolute addressing, addresses and offsets are in bytes. With base plus offset addressing, addresses are byte offsets from a base reference that gives the "byte-zero" address - an explicit address, or a symbolic one such as a table, a parameter set or a file whose absolute address is known on board.49

    The 2014 draft of PUS-C presented three subservices (raw, structured, and a common one that also handled scrubbing and write protection);73 the published standard separates the memory configuration subservice, which manages each memory "as a whole", independently of content and addressing scheme.374 With 44 discrepancy review reports (DRRs), ST[06] was the second most discussed service type of the review, after ST[12] with 58 (the foundation model of clause 5 drew 72).75

    1.3 Checksums¶

    Whether the raw and the structured subservices checksum their data is declared per subservice.514 PUS-C does not fix the algorithm in the service: for each checksum algorithm used on board, the spacecraft architecture declares which subservice providers use it, so that every service checksumming the same object (for example an OBCP stored in a file, checked by both the OBCP service and the memory service) uses the same algorithm; the algorithm implies the type (ISO or CRC) and the size.50 In the packets the checksum is always a 16-bit bit-string.30 The two candidate algorithms are those of Annex B: the CRC-16-CCITT (polynomial \(x^{16}+x^{12}+x^5+1\), encoder and decoder initialised to all ones) and the ISO 8473-1 checksum, which Annex B says can be used to check memory areas through the memory management service.5455

    PUS-A was more prescriptive: memory management uses the 16-bit ISO checksum, computed over all octets of the memory area.63

    3. Request processing: why loads and dumps behave differently¶

    PUS requests are made of instructions (for example one memory area each) and produce notifications inside reports.47 Clause 5.3.5.2.3 lets each request type declare whether all instructions must be suitable before execution starts; PUS-C names the raw memory load as an example of a request that can only execute if all its instructions are suitable.45 ST[06] applies two regimes:

    4. Raw data memory management¶

    The raw subservice declares the list of memories it manages (all with absolute addressing), uses memory identifiers if it manages more than one, and declares its write access per writeable memory.6 In all raw messages the memory ID field is omitted when the subservice manages a single memory.630

    4.1 TC[6,2] load raw memory data areas¶

    Field Type Presence Meaning
    memory ID enumerated optional Target memory.30
    N unsigned integer always Number of instructions (areas).30
    repeated N times:
    start address unsigned integer always Byte pointer aligned on the access alignment constraint.307
    data to load variable octet-string (length + data) always The PFC of the length field is declared per application process (requirement 7.3.8d).3053
    checksum bit-string (16 bits) optional Present if the subservice checksums; verified after writing.307

    The request is rejected (failed start of execution) for an invalid memory ID, no write access, a write-protected memory, a start address beyond the memory size or misaligned, a load length that is not a multiple of the alignment constraint, or data running past the end of the memory.7 Otherwise instructions run in order; a write error, or a checksum mismatch after writing, aborts the request immediately with a failed execution notification and a failed completion of execution report.7

    4.2 TC[6,11] load a raw memory atomic data area in a non-interruptible transaction¶

    This request changes selected bits of one aligned memory word without touching the others, in a single non-interruptible transaction; it holds exactly one instruction.8

    Field Type Presence Meaning
    memory ID enumerated optional Target memory.35
    start address unsigned integer always Aligned byte pointer.35
    bit mask fixed octet-string, deduced size always Selects the bits to change; size = access alignment constraint of the memory.358
    data to load fixed octet-string, deduced size always New values for the selected bits; same size.358

    The subservice reads the current value of the addressed word, replaces the bits selected by the mask with the corresponding bits of the data, and writes the result:8

    \[\text{new} = (\text{old} \land \lnot\,\text{mask}) \lor (\text{data} \land \text{mask})\]

    It needs both read and write access and rejects an unknown or write-protected memory, an address beyond the memory or misaligned, and a request whose size does not match the deduced mask and data sizes. Its verification profile includes completion of execution.8

    TC[6,5] field Type Presence
    memory ID enumerated optional
    N unsigned integer always
    start address unsigned integer repeated N times
    length unsigned integer repeated N times
    TM[6,6] field Type Presence
    memory ID enumerated optional

    Layouts from Figures 8-70 and 8-71.32 The request is rejected as a whole for an invalid memory ID, no read access, or a response that would exceed the maximum CCSDS packet size of 65 542 octets.952 Each instruction is then checked (address in range and aligned, length within the memory and a multiple of the alignment); faulty instructions get their own failed start notification and the valid ones are dumped anyway. Each valid instruction yields one notification with the start address, the data and, if the subservice checksums, the checksum of the dumped area; all go into a single TM[6,6].9 Because a response may not exceed one packet, PUS-C foresees file management for data larger than a packet; other mechanisms are mission-specific.52 The 2024 draft replaces the rejection by splitting the response over several packets (section 9).70

    4.4 TC[6,9] check raw memory data and TM[6,10]¶

    Same request layout as the dump; the report carries, per instruction, the start address, the length and the 16-bit checksum.34 Checking on board and comparing the checksum on ground avoids downlinking memory suspected to be faulty.10 The capability is "by declaration".43

    4.5 TC[6,19] load raw memory data areas by reference¶

    The data to load are not in the telecommand but in an on-board file (see ST[23] file management):1139

    Field Type Presence
    memory ID enumerated optional
    repository path variable character-string always
    file name variable character-string always
    N unsigned integer always
    start address unsigned integer repeated N times
    offset in file unsigned integer repeated N times
    length unsigned integer repeated N times
    checksum bit-string (16 bits) repeated, optional

    Rejection adds two file conditions to those of TC[6,2]: the file does not exist, or is not recognised as a file containing memory data; an offset beyond the file size is also an error.11 Execution reads each area from the file and writes it, with the same abort rules as TC[6,2].11 An object path is the combination of a repository path and an object name.51

    4.6 TC[6,20] dump raw memory data areas to file¶

    Field Type Presence
    memory ID enumerated optional
    repository path, file name variable character-strings always
    N unsigned integer always
    start address, length unsigned integers repeated N times

    The request is rejected if the destination file already exists. The subservice creates the file and appends each dumped area; the standard does not specify the formatting of the data in the file (raw bytes or with headers).1240 The raw subservice defines no observables.13

    5. Structured data memory management¶

    The structured subservice manages memories with base plus offset addressing; write access is declared per memory.15 All its requests carry, after the optional memory ID, a base field of type deduced: its format depends on the memory (a base address or a memory object identifier).2916

    TC[6,3] dump object memory data N; offset, length x N Rejected for unknown object, no read access, or response too large.1831
    TM[6,4] dumped object memory data report memory ID, base, N; offset, dumped data (variable octet-string), checksum (optional) x N One notification per valid instruction.1831
    TC[6,7] check object memory data N; offset, length x N By declaration.1933

    Offsets are byte offsets within the object identified by the base, independent of how the object is physically stored.49 The structured subservice defines no observables.23

    6. Common memory management: TC[6,12]¶

    TC[6,12] "abort all memory dumps" has no application data.36 It aborts every dump request under execution by the raw subservice and by the structured subservice - including dumps to file. The subservice exposes one observable: a flag saying that at least one dump is in progress.24

    7. Memory configuration: scrubbing and write protection¶

    For scrubbing, PUS-C does not specify the mechanism, which is memory dependent and can be hardware or software; the service only keeps a memory scrubbing status per memory, which is used to trigger the scrubbing.25 Write protection can likewise be hardware or software; its status is the memory write protection status.26 For each, the mission declares support, the list of memories concerned, and (for scrubbing) the initial status.2526

    9. Changes in the 2024 Rev.1 draft¶

    ECSS-E-ST-70-41C Rev.1 DIR1 (11 December 2024) keeps the 22 message types and makes these changes:

    • Dumps and checks become all-or-nothing. TC[6,3], TC[6,5], TC[6,7], TC[6,9], TC[6,20] and TC[6,22] carry an ordered list of instructions; the whole request is rejected if any instruction is invalid, and otherwise instructions execute in order. In PUS-C faulty instructions were rejected individually.666769
    • Large dumps are split instead of rejected. The general rule of clause 5.4.11.3.2 changes: a response too long for one packet of the maximum size is split into several self-contained PUS telemetry packets, with splitting criteria declared per subservice and the group marked by the primary header sequence flags (01 first, 00 continuation, 10 last, 11 stand-alone); the draft names memory dumps as a typical case. Accordingly the TC[6,5] and TC[6,3] rejection lists no longer contain the packet-size condition.706667
    • The note allowing loads to skip checking the instructions that follow a faulty one, present in four PUS-C load clauses, no longer appears.771
    • Hosting is reworded. In PUS-C, 6.6.2.2a says each subservice provider is hosted by exactly one application process, only a note adds that all of them are therefore in a single application process, and 6.6.2.2b allows at most one memory management subservice provider per application process. DIR1 makes the single hosting application process a requirement and limits each application process to the subservice providers of at most one memory management service.465
    • Scrubbing and write protection statuses are maintained by the memory configuration subservice (PUS-C said "the memory management service").6825

    11. Solar Orbiter: the space-to-ground ICD¶

    11.1 Service description¶

    Solar Orbiter's ICD (PUS-A based)83 defines service 6 for loading, dumping and checking a contiguous area of RAM, PROM, EEPROM, safeguard memory (SGM) or mass memory, identified by a memory ID:84

    • Only absolute addressing is used; addresses are expressed in single addressable units (SAU) of the selected memory.84
    • TC(6,2) and TC(6,5) contain one block each. A scatter patch is obtained with TC(6,128), which applies a set of patches pre-loaded with TC(6,2).84
    • TM(6,6) is not limited in length: the application generates as many dump packets as needed for the commanded area.84
    • TC(6,9) requests a check whose result TM(6,10) is sent via real-time telemetry.84
    • The memory ID is 2 bytes. Units A and B nominally use the same memory IDs, the unit being selected by APID; for cross-access between redundant units, unit A memories use 1-255 and unit B memories 257-511 (most significant byte 1 plus the unit A ID).86
    • The SAU can be 8, 16 or 32 bits; the address multiplier (MUL) is the address increment from one SAU to the next.86

    11.4 The RAM patch mechanism (TC(6,128))¶

    The patching buffer is a RAM area with a patch table of up to 30 descriptors (number of bytes, source address in the pre-loading area, destination address) and a pre-loading area holding the patch bytes. The ground loads both with TC(6,2), checks their content and consistency, then sends TC(6,128) with the number of descriptors to apply (the first n entries); after execution the buffer is erased.93

    Inference

    The mechanism makes a scatter patch atomic from the software's point of view: the patches are staged harmlessly and then applied in one step, instead of a series of TC(6,2) loads that would leave running code half-patched between packets. The ICD calls it a "safe loading/patching" of different RAM addresses but does not give the rationale.87

    11.5 Masked load: Solar Orbiter and PUS-C compared¶

    The ICD rule is (existing data AND inverse mask) OR (loaded data AND mask), the same formula as PUS-C's TC[6,11] (section 4.2), but with data before mask in the packet.968 In the MIB, ZCD0068C "Load Memory With Mask" has exactly these four fields with a 32-bit word to load.103

    14. Other missions: Herschel and Planck¶

    The Herschel/Planck Operations Interface Requirements Document asks that memory areas be split into code, fixed data and variables; that the ground can load any changeable area, with a contiguous area per telecommand; that each load packet be self-consistent (not dependent on earlier packets, and re-sendable alone); that the destination detect corrupted loads (for example by checksums); that end-to-end verification confirm the data in memory, possibly by dumping; that any memory, including non-volatile and mass memories, be dumpable with a single request even if several TM packets are needed; and that a checksum check over a start address and length be available.107 It also requires that on-board software can be modified, by changing the non-volatile image or patching the working copy, while the unit is operational.108 See Herschel and Planck.
