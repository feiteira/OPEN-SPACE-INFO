    ST[09] Time management¶

    Every spacecraft keeps a spacecraft time reference (an on-board clock), and every PUS telemetry report is time-tagged with it. The ground, however, works in UTC. The time management service (service type 9) closes that gap: it periodically samples the on-board clock at a precisely defined instant, the start of a particular telemetry transfer frame, and sends the sample to the ground in a time report. The ground, which also time-stamps the reception of that frame, can then pair the two times and maintain a correlation between on-board time and UTC, and from it reconstruct when every other reported event happened.1 This page covers the PUS-C service (ECSS-E-ST-70-41C, 2016) in full, compares it with PUS-A (2003) and the 2024 Rev.1 draft, explains how SCOS-2000 turns time reports into time correlation coefficients, and shows Solar Orbiter's real time packet and time commands from its MIB.

    At a glance

    Item Value
    Service type 911
    Subservices (PUS-C) time reporting (exactly one); time reporting control (at most one)3
    Message types (PUS-C) TC[9,1] set the time report generation rate; TM[9,2] CUC time report; TM[9,3] CDS time report13
    Where the reports come from application process APID 0, in packets without a secondary header311
    Sampling trigger leading edge of the first bit of the attached synchronization marker of selected VC 0 frames9
    Generation rate every 1, 2, 4, ... 256 VC 0 frames, set as a rate exponential value 0 to 8410
    Added in the 2024 Rev.1 draft TC[9,4] to TC[9,7]: set the reference time, distribute time to on-board users39
    Ground counterpart time correlation (SCOS-2000 TCO)40
    Solar Orbiter SPID 9999 "Time Report", OBT in CUC 4+2, private TC(9,128) to TC(9,131)5261

    1. Concepts¶

    1.1 Spacecraft time, time codes and correlation¶

    PUS-C does not say how the on-board clock is built: it may be a free-running counter or a clock synchronized to a GPS receiver.4 What it fixes is how the clock is reported. The time in a time report uses one of two CCSDS time code formats:2

    • CUC (CCSDS unsegmented time code), consecutive bits of a binary counter, suited to spacecraft time measurement;
    • CDS (CCSDS day segmented time code), typically used when the on-board time is synchronized with a ground reference such as TAI or UTC.

    Both consist of a preamble field (P-field), which says how to read the time, and a time specification field (T-field), which carries the value.2 In CCSDS 301.0-B-4 the CUC T-field is a count of basic time units (normally seconds) since an epoch plus an optional binary fraction, and the first P-field octet encodes the epoch type (001 for 1958 January 1, 010 for an agency-defined epoch), the number of coarse octets minus one, and the number of fine octets.21 The CDS T-field is a day count, milliseconds of day and an optional submillisecond field; its P-field identifies the code (100), the epoch, the day-segment width and the submillisecond resolution.22

    A time reporting subservice supports exactly one of the two formats.25 PUS-C uses this choice as its own example of an "exclusive-or" capability constraint.6

    The correlation itself is a ground function. PUS-A summarises why it matters: once the correlation is known, the ground can reconstruct the on-board time of every event or parameter sample, whether the sample is explicitly time-stamped or deduced from implicit time offsets relative to the packet time. PUS-A leaves on-board time distribution and GPS-based schemes out of scope.25

    1.2 What the operability standard requires¶

    ECSS-E-ST-70-11C Rev.1 (space segment operability, October 2025) states the system-level requirements that ST[09] serves. Among them:24

    Requirement Content (paraphrased)
    5.4a the space segment provides timing information that lets the ground keep the OBT-UTC correlation better than <TIME_CORREL_ACCUR> over <TIME_CORREL_PERIOD>
    5.4b the ground can set the on-board time by telecommand
    5.4c on-board time increases monotonically in all modes, including standby and survival
    5.4d all on-board timing derives from a single Central Time Reference
    5.4e to g engineering telemetry shows whether an application process has achieved time synchronization
    5.4h, j no on-board clock, and no telemetered on-board time, wraps around during the mission
    5.4i every TM source packet should carry its on-board generation time
    5.4o, w the on-board time system's contribution to correlation error is bounded (<ONBOARD_STABILITY> ms/day) and every on-board delay is documented

    The angle-bracket items are mission parameters to be filled in during tailoring.24

    2. Service layout¶

    PUS-C constrains where the two subservices live:3

    Rule Clause Content
    One service per spacecraft 6.9.2.1a each spacecraft contains exactly one time management service
    One time reporting subservice 6.9.2.2.1a exactly one per time management service
    Optional rate control 6.9.2.2.2a at most one time reporting control subservice
    APID 0 6.9.2.3a the time reporting subservice provider is hosted by the application process with APID 0
    One control provider per process 6.9.2.3b each application process hosts at most one time reporting control subservice provider; the note adds that the two subservices may be hosted by different application processes
    No reports from APID 0 other than time reports 6.9.2.3c if the control subservice can generate reports, it must not be hosted by the APID 0 process

    The last rule exists because APID 0 packets have no secondary header: a report of any other type sent from APID 0 could not be identified.3 PUS-C reserves APID 0 for spacecraft time packets (and APID 2047 for idle packets) in its general application process rules.14

    3. Spacecraft time reference and its declared parameters¶

    PUS-C leaves several properties for the mission to declare. Together they are the "managed parameters" of the service:4578

    Declaration Clause Notes
    default time report generation rate 6.9.3b used until TC[9,1] changes it
    supported generation rates 6.9.3c a subset of 1, 2, 4, 8, 16, 32, 64, 128, 256; counted in VC 0 transfer frames
    sampling accuracy of the time reference 6.9.3d declared at spacecraft architecture level; contributes to correlation accuracy
    accuracy of the time between frame transmission and the reported sample 6.9.3e PUS-C does not require the time packet to go down in the frame that triggered it
    format: CUC or CDS 6.9.4.1a exactly one
    time reference status reported? and its meaning 6.9.4.1b, c optional field of the time report
    generation rate included in the report? 6.9.4.1d optional field of the time report
    P-field explicit or implicit, and the implicit value 6.9.4.2b, c / 6.9.4.3b, c an omitted P-field is "considered implicit"

    The service also supplies the synchronized time that all services use to time-stamp their reports (6.9.3f).4 Each on-board application process time-tags every report with the on-board reference time, declares whether it time-tags before or after collecting the parameter values, and declares whether it can report the status of the time reference.15 That status travels in the 4-bit spacecraft time reference status field of every PUS-C TM secondary header; an application process that does not support it sets the field to 0. The PFC of the TM header time field is declared when specifying the time service.1617 See PUS packet structures for the header itself.

    Inference

    PUS-C defines no values for the spacecraft time reference status; requirement 6.9.4.1c leaves its meaning to the mission.5 A typical use would be to flag an unsynchronized or freshly reset clock, as the operability requirements 5.4e to g ask for, but that pairing is this wiki's reading.24

    4. The time report generation process¶

    This is the heart of the service. The time reporting subservice:9

    1. samples the spacecraft time reference once for each telemetry transfer frame on virtual channel 0 whose virtual channel frame count modulo the generation rate equals 0;
    2. takes the sample at the instant of the leading edge of the first bit of the attached synchronization marker (ASM) of that frame;
    3. generates the time report at the required rate, with the T-field set to the sampled value formatted in the chosen time code;
    4. applies a new rate immediately to determine the next frame that triggers sampling.
    sequenceDiagram
  participant TFG as TM frame generator (VC 0)
  participant CLK as Spacecraft time reference
  participant TR as Time reporting (APID 0)
  participant GS as Ground station
  participant MCS as Ground (SCOS-2000)
  Note over TFG: VC frame count mod rate = 0
  TFG->>CLK: first ASM bit of the frame leaves (trigger)
  CLK->>TR: sampled time value
  TFG->>GS: the trigger frame (ERT stamped on reception)
  TR->>TFG: time packet TM[9,2] / TM[9,3]
  TFG->>GS: a later frame carries the time packet
  GS->>MCS: frames with ERT
  MCS->>MCS: pair the sample with the trigger frame's ERT minus delays = time couple

    The on-board part of the diagram follows PUS-C clause 6.9.4.4; the ground part follows the SCOS-2000 time correlation note (section 9).944

    The VC frame count is an 8-bit, modulo-256 counter in bits 24 to 31 of the TM transfer frame primary header.23 A rate of \(2^n\) frames, \(n\) = 0 to 8, therefore divides the 256-frame counter cycle exactly: with rate 32 the frames with counts 0, 32, 64, ..., 224 trigger a sample, 8 per counter cycle; with rate 256 only count 0 does.1023 PUS-A's annex C gives the reason for the upper limit: the sample taken at frame count 0 must be telemetered before the VC 0 frame counter has counted 255 more frames, "so as to avoid ambiguity"; for a higher sampling rate it must be sent before the selected number of frames has elapsed.32

    Which frames trigger a sample? (illustrative)

    Rate exponential value 5, so rate \(2^5 = 32\). VC 0 frames are numbered by their VC frame count.

    VC 0 frame count 30 31 32 33 ... 63 64 ... 255 0
    triggers sampling? no no yes no no yes no yes

    If TC[9,1] sets the exponent to 8 while the count is 40, the next trigger is the frame with count 0 (the next multiple of 256), because the new rate applies immediately.9

    5. Spacecraft time packets: TM[9,2] and TM[9,3]¶

    5.1 The packet¶

    Time reports are spacecraft time packets. They have no packet secondary header, so their secondary header flag is 0, and their APID is 0. They therefore carry no service type or subtype on the wire. PUS-C still associates the message types TM[9,2] and TM[9,3] with them, so that other services can refer to them, for example ST[14] real-time forwarding control.11 PUS-C's TM secondary header rule makes the same exception.16

    The fixed values are those of PUS-C clause 8.9.1; the field sizes are those of the Space Packet primary header.1118

    5.2 Source data¶

    TM[9,2] (CUC) and TM[9,3] (CDS) have the same structure:12

    Field PUS-C type Presence Meaning
    rate exponential value unsigned integer optional (6.9.4.1d) \(n\) such that the report rate is \(2^n\) VC 0 frames, 0 to 8
    spacecraft time absolute time always the sampled time reference, CUC (TM[9,2]) or CDS (TM[9,3]) per CCSDS 301.0-B-4
    spacecraft time reference status deduced optional (6.9.4.1b) mission-defined status of the time reference

    Each report contains a single time notification with these items.78 PUS-C does not fix the width of the rate field; PUS-A makes it one octet.1227

    Inference: a copy-paste slip

    Requirement 6.9.4.3e.2 says the subservice generates "a single CDS time report containing the CUC time notification". In the CDS clause this can only mean the CDS notification of item 1; the wording repeats the CUC clause.8

    5.3 The time field: PTC 9¶

    An absolute time in a PUS-C packet is of PTC 9, a positive offset in seconds and fractions of a second from an epoch. CUC may use the CCSDS 1958 epoch or an agency epoch, in which case the value is a free-running counter converted on ground with the time correlation coefficients; CDS must use the 1958 epoch.19 The PFC selects the format:20

    PFC Format Length
    0 explicit: P-field included (CUC or CDS) variable
    1 CDS, 2-octet day, no µs 6 octets
    2 CDS, 2-octet day, with µs (day, ms of day, µs of ms) 8 octets
    3 to 18 CUC, implicit P-field: coarse octets = (PFC + 1) div 4, fine octets = (PFC + 1) mod 4 1 to 7 octets
    19 to 46 CUC, implicit P-field: coarse octets = (PFC - 12) div 7, fine octets = 4 + (PFC - 12) mod 7 up to 14 octets

    A note of clause 7.3.10 says PUS-C implements CUC with 1 to 4 coarse octets and 1 to 10 fine octets, where CCSDS 301.0-B-4 allows up to 7 coarse octets.19 PFC 17, for example, is 4 coarse and 2 fine octets, the format Solar Orbiter uses (section 10). The full catalogue is on PUS parameter types.

    6. TC[9,1] set the time report generation rate¶

    The time reporting control subservice exists for missions whose time correlation accuracy needs vary.2 Its single request:1012

    • contains exactly one instruction, with one argument: the rate exponential value, where rate = \(2^{\text{rate exponential value}}\);
    • is rejected, with a failed start of execution notification, if the rate is invalid (not one of the supported rates);
    • otherwise sets the rate used by the time reporting subservice.

    The subservice's only observable is the current time report generation rate.10

    Field PUS-C type Meaning
    rate exponential value unsigned integer 0 to 8 (1 to 256 frames), limited to the declared supported rates

    PUS-A calls the request "Change Time Report Generation Rate (9,1)" and fixes the field as a 1-octet unsigned integer in the range 0 to 8.27

    7. Capability sets¶

    Edition Message Capability
    PUS-C TM[9,2] CUC time report exactly one of TM[9,2] / TM[9,3] is "minimum"; each is "by declaration"13
    PUS-C TM[9,3] CDS time report (see above)13
    PUS-C TC[9,1] set the time report generation rate minimum for the time reporting control subservice13
    PUS-A (9,2) Time Report minimum capability set of the time reporting sub-service, provided only by APID 0 (Table 21)28
    PUS-A (9,1) Change Time Report Generation Rate minimum set of the optional rate control sub-service, which requires time reporting (Table 20)28

    PUS-A adds that sending the time packet to the ground is enabled and disabled with the packet forwarding control service, and that there are no additional capability sets.28

    8. Edition differences¶

    PUS-A clause 13 defines the two sub-services. The rate control sub-service maintains one of the rates 1 to 256 and passes it to the time reporting sub-service, which samples the "satellite time reference" (a free-running counter from a given epoch) at VC 0 frame count 0 and every frame where the count modulo the rate is 0, downlinks it before the next sample, and applies a new rate from the next qualifying frame.26 The Time Report (9,2) holds an optional 1-octet Rate (omitted if the rate is fixed), the Satellite Time in CUC only, with an implicit or explicit P-field (implicit value: the mission constant <MISSION_TIME_CODE>), and an optional Status whose type and values are not specified.27

    Annex C, transcribed from ESA PSS-04-106, details the older ESA scheme:29303132

    • the on-board reference is "Spacecraft Elapsed Time", a free-running counter from an arbitrary epoch, in TAI seconds, coded CUC with 1 to 4 coarse and 0 to 3 fine octets (P-field 0010 followed by the octet counts);
    • the standard time source packet has APID all zeros and no data field header; its first data octet carries the sampling rate in bits 4 to 7 (0000 = 1 frame to 1000 = 256 frames), then the P-field and T-field, then mission-defined time-system parameters such as fixed on-board delays;
    • the ground time-tags, in CDS-coded UTC, the reception of the first ASM bit of the VC 0 frame with count 0, extracts the CUC sample from the time packet, and thereby correlates elapsed time with UTC.

    PUS-C keeps the frame-count sampling rule and the APID 0 packet, and adds:24512

    • the CDS report TM[9,3] next to the CUC report TM[9,2];
    • the rate as an explicit rate exponential value in TC[9,1] and, optionally, in the report;
    • the spacecraft time reference status, optional in the report and present in every TM secondary header;
    • declared sampling and timing accuracies;
    • formal rejection of TC[9,1] with a failed start of execution notification.

    The draft grows ST[09] to four subservices:3334

    • time reporting and time reporting control, as in PUS-C; the time reporting subservice is now described as hosted by the application that provides the spacecraft time reference from the on-board clock (still APID 0);
    • time control: at least one per service, hosted by the process maintaining the reference time and by every on-board user that receives distributed time. TC[9,4] sets the reference time to an absolute time, TC[9,5] adds a signed relative offset; both may carry an optional time reference status whose processing is application-specific;3739
    • time distribution: at most one per service. TC[9,6] starts a one-shot (interval 0) or periodic (interval in seconds) distribution to N application processes; TC[9,7] stops it. The distributed time can travel in a TC[9,4] packet or any other on-board means; the observable is each periodic distribution's period.3839

    It also requires the time reference and its status to be accessible on board by all services (6.9.3g).36 The draft "may not be referred to as an ECSS Standard until published as such" (see PUS-A vs PUS-C).35

    9. Ground side: SCOS-2000 time correlation¶

    9.1 What SCOS-2000 does with time reports¶

    The SCOS-2000 Database Import ICD lists service 9 among the services with specific ground processing: time report packets feed the time correlation function, which builds time couples (an on-board time and the corresponding UTC). Support for both free-running and synchronized clocks is available from SCOS-2000 R5.2; before that, time correlation was a mission-specific function. One limitation matters operationally: SCOS-2000 does not automatically update its ground parameters when a TC(9,1) succeeds.40

    Inference

    Because the ground's frame-matching rule depends on the rate (section 9.2), a rate change by TC(9,1) presumably has to be mirrored in the ground configuration by the operators. The ICD states only the absence of the automatic update.4049

    9.2 From a time report to a time couple¶

    The SCOS-2000 time correlation technical note (EGOS-MCS-S2K-TN-1030) describes the mechanism. The spacecraft samples its clock when a frame whose counter is a multiple of \(N\) (a power of 2 from 1 to 256) is transmitted, and sends the sample in a later frame; knowing \(N\), the ground identifies the triggering frame and takes its Earth reception time (ERT) from the NIS header.44 It then removes the delays:4447

    \[ \text{FTT} = \text{ERT} - \text{ground delay} - \text{propagation delay} - \text{on-board processing (radiation) delay} \]
    \[ \text{OLT} = \text{FTT} + \text{on-board latching delay} \]

    FTT is the frame transmission time, when the frame generator starts the frame and requests the clock sample; OLT is the OBT latching time, when the sample is actually latched. The pair (OBT in the time report, OLT in UTC) is the time couple. For SLE service providers the ground delay is zero by definition, because the provider already corrects the ERT.47 Because the time packet arrives in a later frame, the packetiser opens a configurable window after each triggering frame; a time packet outside the window is ignored (the "plausibility check", bounded by the MISCdynamic variables TCO_FAR_FTT_PLAUSIBILITY_LIMIT and TCO_CLOSE_FTT_PLAUSIBILITY_LIMIT).4449

    A time couple (illustrative numbers)

    Quantity Value
    ERT of the triggering VC 0 frame 12:10:00.250 000 UTC
    ground delay 0.000 120 s
    propagation delay (one-way light time) 480.000 000 s
    on-board frame radiation delay 0.000 050 s
    on-board latching delay 0.000 010 s
    FTT = ERT - 0.000 120 - 480 - 0.000 050 12:02:00.249 830 UTC
    OLT = FTT + 0.000 010 12:02:00.249 840 UTC
    OBT in the time report 811 339 200.5 s (CUC)

    The couple is (811 339 200.5, 12:02:00.249 840). The formulas are from TN-1030; the numbers are invented by this wiki.44

    9.3 Coefficients, accuracy and validity¶

    From the couples the time correlation server computes the coefficients of a linear OBT-to-UTC relation, expressed relative to the last couple used (\(\text{UTC}_N\), \(\text{OBT}_N\)) for resolution:4543

    Clock type Method Relation
    free-running least-squares fit over a set of couples (gradient and offset) \(\text{UTC(OBT)} = \text{UTC}_N + \text{Gradient}\,(\text{OBT} - \text{OBT}_N) + \text{Offset}\)
    synchronized (e.g. GPS) difference, one couple suffices (gradient 1) \(\text{UTC(OBT)} = \text{UTC}_N + \text{OBT} - \text{OBT}_N - \text{Offset}\)

    The two methods can be switched at run time.48 Every new couple is checked: the deviation is the difference between the couple's UTC and the UTC computed from its OBT with the current coefficients. Against two configurable limits (accuracy, the tighter, and validity) the coefficients are "valid and accurate", "valid and inaccurate" or "invalid and inaccurate". For synchronized clocks a separate synchronization status compares the computed offset with the expected offset of the time source (for example the GPS-UTC leap-second offset).4448

    stateDiagram-v2
  VA: Valid, accurate
  VI: Valid, inaccurate
  II: Invalid, inaccurate
  VA --> VI: couple with deviation above the accuracy limit
  VA --> II: deviation above the validity limit, or reset
  VI --> II: deviation above the validity limit, or reset
  VI --> VA: new coefficients computed and committed
  II --> VA: new coefficients computed and committed

    The state machine is TN-1030 Figure 6.48 In automatic mode the system recalculates the coefficients from the latest couples when the deviation grows, and after a configurable number of consecutive invalid deviations (TCO_AUTORESET_INVALID_DEVIATIONS) it resets: the couple buffer is emptied and a new correlation is computed once two new time reports have been received.49

    Inference: two triggers for the automatic update

    TN-1030 states the automatic recalculation trigger in two ways. Section 4, section 6.2 and the summary at the end of the engine description say it happens when the deviation exceeds half the accuracy limit (section 6.2 writes "accuracy" for "deviation"). Step 6 of the engine description states the condition as a deviation within the validity interval but above the accuracy interval.444849 The available sources do not say which one the software implements.

    The full SCOS-2000 design (TCO engine, client library, coefficient packets) is on Time correlation in SCOS-2000.

    10. Solar Orbiter¶

    10.1 The on-board time¶

    In Solar Orbiter's packet structure ICD, service 9 carries the mnemonic M: a user must implement the service.5051 The on-board computer (OBC) maintains the On Board Time (OBT), normally synchronized with a controlled oscillator, from which clock signals and a PPS (pulse per second) signal are distributed. The mission's zero time reference is 00:00 on 1 January 2000. The OBT is CUC with 4 coarse octets and 2 fine octets; it starts at 0 at OBC power-up, is set to real time with the private TC(9,128) "Set OBT", and is maintained in the OBC processor module and in two TTR boards.52 Every TM data field header carries the packet time in the same CUC 4+2 format (PTC 9, PFC 17).57

    10.2 The time packet¶

    The standard spacecraft time source packet has the name and layout of PUS-A annex C: APID 0, no data field header, 8 octets of data (packet length C = 7), and a T-field referred to the first ASM bit of the VC 0 frame with frame count 0. The annex does not restate the other multiples of the rate; TC(9,1) sets the rate.5853 The TM(9,2) definition gives process ID 0 and packet category 0, the category that the ICD reserves for the service 9 time packet.5360

    The layout is from the ICD (annex 4 and TM(9,2), where the Rate is a 1-octet enumerated "S-field" and the OBT is 6 octets).5853 In the MIB the packet is SPID 9999 "Time Report": type 9, subtype 2, APID 0, PID_TPSD = -1 (a fixed packet), PID_DFHSIZE = 6 and PID_TIME = Y; the tpcf record names it YCD00902 with a size of 14 octets. Its plf entries extract three parameters:61

    Octet Parameter Description PTC/PFC Calibration
    6 NCD09021 OBCHP_Time Rep S-Field 2/8 textual CCDT0043TX: 0 = EVERY_TMFR ... 8 = EVERY_256_TMFR
    7 NCD09022 OBCHP_Time Rep P-Field ¾ none
    8 NCD09023 OBCHP_OBT 9/17 none; PCF_CORR blank, so the ICD default Y (correlate) applies

    Inference

    The S-field occupies a whole octet but its upper 4 bits are always zero, so reading it as an 8-bit enumerated value gives the same 0 to 8 as the PUS-A bit 4-7 code. PID_DFHSIZE = 6 equals the 6-octet primary header, consistent with a packet without a data field header, but the ICD says the field is irrelevant for fixed packets (PID_TPSD = -1). What locates the parameters is plf: its offsets count from the start of the packet header, so octet 6 is the first data octet.614142

    Decoding a complete Solar Orbiter time packet (illustrative bytes)

    00 00 C3 4A 00 07 05 2E 30 5C 0D C0 80 00

    Octets Field Value
    00 00 version 0, type 0, no secondary header, APID 0 time packet
    C3 4A sequence flags 0b11, count 842 (illustrative)
    00 07 data length C = 7 8 data octets
    05 S-field: rate code 5 every 32 VC 0 frames (EVERY_32_TMFR)
    2E P-field 0 010 11 10 CUC, agency epoch, 4 coarse, 2 fine
    30 5C 0D C0 coarse 811 339 200 s
    80 00 fine 0.5 s

    The OBT is 811 339 200.5 s after the zero reference, nominally 2025-09-16 12:00:00.5. That is not UTC: SCOS-2000 applies the correlation of section 9 to obtain it. The bytes are constructed by this wiki.5852

    10.3 Commands, then and now¶

    The ICD defines one standard and four private telecommands:5153545556

    Message Name Application data
    TC(9,1) Change Time Report Generation Rate Rate, 1-octet unsigned, 0 to 8: once every \(2^{\text{Rate}}\) VC 0 frames
    TC(9,128) Set OBT Action (1 octet: 0 = set absolute value, 1 = add delta, 2 = subtract delta), OBT seconds (4 octets), OBT subseconds (2 octets, "n/a if action = 0")
    TC(9,129) Accept Time Synchronisation OBT at the next synchronization signal, CUC, 6 octets with the fine part zero
    TC(9,130) Start Time Synchronisation to User PID of the user (1 octet; SSMM, STR or payload), Period (1 octet: 0 = one-shot, 1 to 255 s)
    TC(9,131) Stop Time Synchronisation to User PID (1 octet)

    TC(9,129) is the interesting one. The CSW does not execute it: it generates it and sends it to other packet terminals (for example the solid-state mass memory) at the frequency set by TC(9,130). The time it carries is that of the next synchronization signal the addressee will see: the PPS, the MIL-STD-1553 bus major frame synchronization, or a SpaceWire time code.55 It is the only service 9 message with an entry in all four software columns of the summary table: X (shall be implemented) for the CSW, SSMM and STR software, and M for payload software.5051

    Inference

    Solar Orbiter's private TC(9,128), TC(9,129)/(9,130) and TC(9,131) cover the same ground as the time control (TC[9,4], TC[9,5]) and time distribution (TC[9,6], TC[9,7]) subservices that the 2024 Rev.1 draft standardizes: a one-shot or periodic distribution to named application processes, with interval 0 meaning one-shot.3955 The available sources do not say whether the draft was inspired by such mission practice.

    The two MIB releases differ markedly here:6162

    Subtype 2020-04-16 release 2025-09-16 release
    1 ZCD00901 ZCD00901 (APID 172, parameter PCD09011, 2/8, calibration CCDT0043TX)
    128 ZCD00980 "Set OBT" (action + 9/17 time), ZCD2Z01R add and ZCD2Z01S subtract (fixed action + 10/17 relative time), ZCD2Z01T absolute (32-bit seconds + 16-bit fixed zero) none
    129 11 commands, one per user: ZSM00045/46/47 (SSMM), ZIX09129 (STIX), ZIA58057 (SWA), ... none
    130 ZCD00982, ZCD2Z00U ("to SSMM": fixed PID OP_SSMM, period 0) unchanged
    131 ZCD00983 unchanged

    The PID parameter of TC(9,130) and TC(9,131) (PCD09821, calibration CCDT0130TC) lists the 7-bit process IDs of the ICD's APID annex: OP_SSMM = 30, SSMM_DEBUG_A/B = 31/32, STAR_TRACKER_A/B = 40/41, PLOAD_BCAST = 49 and the payload process IDs 50 to 104.6159 The SWA instrument database still contains its own TC(9,129) "SWA_TC_ACC_TIME" with the time split into COARSE_TIME (PTC 9, PFC 15) and FINE_TIME (PTC 3, PFC 12).63

    Inference

    Why the 2025 release drops TC(9,128) and all TC(9,129) commands is not stated in the available sources. One fact points to a deliberate removal of the command definitions only: the 2025 release still contains the TC(9,128) command parameters PCD09801, PCD09802 and PCD2Z05D and the action calibration CCDT0044TC, but no ccf, cdf or sequence entry uses them.61 For TC(9,129) a plausible reason is that the CSW, not the ground, generates it. For TC(9,128) the definitions may have moved to a restricted database, but this is speculation.

    10.4 Ground-generated time correlation packets¶

    The Solar Orbiter MIB also describes the packets SCOS-2000 itself generates for time correlation, on APID 1966 with service type 164:61

    SPID Description Main fields (offset in octets)
    66840 Time Correlation Report period from/to (PTC 9, PFC 30, Unix time), packets received, bit rate, offset, gradient, standard deviation and error, deviation
    66841 TCO Time_Couples OBT OBT (16), OBT latching time (24), frame transmission time (36), Earth reception time (48), light time delay (60), on-board frame radiation delay (68), ground station delay (76), ground station ID (84), deviation (88), frame counters (96, 97), OBT size (98), raw OBT 9/17 (99)
    66842 TCO_Coefficients OBT validity (16), accuracy (17), gradient (18), offset (26), OBT_N (34), UTC_N (42), standard deviation (50), standard error (58)

    The time couple packet carries most of the quantities of the TN-1030 time couple packet (OBT, OLT, FTT, ERT, light time delay, radiation delay, ground station delay and ID, deviation), plus frame counters and the raw OBT. TN-1030's Table 1 also has an 8-octet OBT latching delay between the radiation delay and the ground station delay. The Solar Orbiter definition has no such field: its ground station delay starts at octet 76, which is where the latching delay would be (TN-1030 offset 60 plus the 16 octets that the MIB offsets of SPIDs 66840 to 66842 start from, PID_DFHSIZE = 16).4661
