    ST[12] On-board monitoring¶

    The on-board monitoring service type, ST[12] of the Packet Utilization Standard, moves part of the limit checking that a mission control system does on the ground into the spacecraft. An on-board application process samples its own parameters, compares them with checks loaded by the ground, records every change of check result ("check transition"), reports those transitions to the ground and, when a monitoring condition is violated, raises an event. The event can go to the ground through ST[05] event reporting and can be caught on board, for example by ST[19] event-action, to start an autonomous recovery.1 PUS-A explained the purpose plainly: monitoring on board removes the need to downlink all low-level housekeeping and to have the ground permanently watching it.64 Abbreviations such as PMON and FMON are expanded in the glossary.

    At a glance

    Item Value
    Service type 122
    Subservices (PUS-C) parameter monitoring (exactly one), functional monitoring (at most one)3
    Check types limit-check and expected-value-check (minimum), delta-check (optional)8
    Message types (PUS-C) 22 requests and 6 reports: TC[12,1]-[12,8], [12,10], [12,13], [12,15]-[12,25], [12,27]; TM[12,9], [12,11], [12,12], [12,14], [12,26], [12,28]58
    Minimum capability TC[12,1], [12,2], [12,15], [12,16], TM[12,12]; plus TC[12,17]-[12,20] if functional monitoring exists58
    Depends on one ST[05] event reporting subservice per monitoring service45
    PUS-A (2003) clause 15 "On-board monitoring service", subtypes 1-1265
    Solar Orbiter PUS-A based service 12 in six Central Software applications plus METIS; functional monitoring in private service 1427994

    Service layout¶

    • Each on-board monitoring service contains exactly one parameter monitoring subservice and at most one functional monitoring subservice; when both exist they are hosted by the same application process.3
    • Each service is associated with exactly one event reporting subservice, declared in the service specification. That subservice catches the events raised by the monitoring service and issues the event notifications; an event is identified by the application process that hosts the event reporting subservice plus an event definition identifier.4
    • The foundation model lists this dependency among the few cross-service rules: the on-board monitoring and event-action services require an event reporting service.5
    • The parameter monitoring subservice can monitor every on-board parameter accessible to its hosting application process.6 On-board parameters are identified by a spacecraft-unique parameter identifier, and each belongs to an "on-board parameter minimum sampling interval", the time unit used by monitoring and housekeeping (the standard's example: 125 ms for a platform, 500 ms for a payload).7

    Parameter monitoring subservice¶

    Check types¶

    Check type What is compared Success condition Capability
    Limit-check the parameter value with a low and a high limit low limit <= value <= high limit minimum
    Expected-value-check the parameter value after a bitwise AND with a mask, with an expected value masked value = expected value minimum
    Delta-check the difference between two consecutive values with a low and a high threshold low threshold <= delta <= high threshold optional, declared

    Sources: requirements 6.12.3.2.1 and 6.12.3.2.2.8 The standard notes that the applicable check depends on the nature of the parameter: analogue values are limit or delta checked, status values are expected-value checked.11 There is no limit on how many checks one parameter may have: one definition can hold warning limits and another danger limits for the same parameter, and a parameter can be limit-checked and delta-checked at the same time through two definitions.1

    The parameter monitoring definition¶

    Each check is a separate parameter monitoring definition, kept in the PMON list. Its maximum size is declared for the subservice, which must accept several definitions for the same parameter, for example to adapt the monitoring plan to spacecraft modes through different validity conditions.9

    Element Content Present
    PMON identifier identifier of the definition always
    Monitored parameter ID on-board parameter to monitor always
    Check validity condition validity parameter ID, bit-mask, expected value; the check runs only when (sample AND mask) = expected value if conditional checking is declared
    Monitoring interval time between two evaluations, in minimum-sampling-interval units if definition-specific intervals are declared (otherwise one subservice-wide interval)
    Check definition repetition number, check type and type-dependent criteria (below) always

    Sources: requirements 6.12.3.3d-i.910

    Check type Type-dependent criteria
    Limit-check low limit, event definition ID for "below low limit", high limit, event definition ID for "above high limit"
    Expected-value-check expected value, mask applied to the sample, event definition ID for "unexpected value"
    Delta-check number of consecutive delta values averaged, low delta threshold, event ID for "below low threshold", high delta threshold, event ID for "above high threshold"

    Every event ID is optional in the sense that the value 0 means "no event report to generate".1049

    The repetition number is the count of successive, consistent check results needed before a new checking status is established; it filters out single noisy samples. For a delta check, the averaged delta is

    \[\overline{\Delta} = \frac{1}{n}\sum_{k=1}^{n}\left(x_k - x_{k-1}\right),\]

    where \(n\) is the "number of consecutive delta values" and \(x_k\) are consecutive samples; the standard defines the delta as the difference of two consecutive values and compares the average of \(n\) such deltas with the thresholds.810 (Arithmetically the sum telescopes to \((x_n - x_0)/n\).)

    Statuses¶

    Status Scope Values
    PMON function status whole subservice enabled, disabled; "enabled" when the subservice starts
    PMON status each definition enabled (1), disabled (0)
    PMON checking status each definition depends on the check type (table below)

    The checking status is the established result. "Unchecked" and "invalid" mean that no checking status is currently established.12

    Raw value Expected-value-check Limit-check Delta-check
    0 expected value within limits within thresholds
    1 unchecked unchecked unchecked
    2 invalid invalid invalid
    3 unexpected value below low limit below low threshold
    4 - above high limit above high threshold

    Sources: Tables 8-7 to 8-9 and 8-10 of the interface specification.56

    The monitoring process¶

    At the end of each monitoring interval, for each enabled definition (and only while the PMON function is enabled), the subservice:

    1. computes the check validity condition, if conditional checking is supported;
    2. if it is false, sets the checking status to "invalid" and resets the repetition counter;
    3. otherwise performs the check with a newly sampled value and, if the last "repetition number" checks all produced the same result, establishes a new checking status;
    4. if the newly established status differs from the previous one, records a check transition in the check transition list and, if an event definition is attached to that transition, raises the event.17

    For a limit-check, "above high limit" is established only when every one of the repeated checks was above the high limit, "below low limit" only when every one was below the low limit, and "within limits" when all passed; the delta-check works the same way with thresholds, and the expected-value-check distinguishes only "expected" and "unexpected".18

    Inference

    The standard does not say explicitly whether entering "invalid" because the validity condition is false is itself a recorded check transition, since requirement 6.12.3.6.3c.2 sets the status directly rather than "establishing" it. The out-of-limits rules (6.12.3.12) do treat "invalid" as a valid previous status.

    Worked example (illustrative values)

    A limit-check with low limit 10, high limit 50 and repetition number 3, starting "unchecked". Samples arrive at t1, t2, ...

    Sample Value Result Established status Recorded transition
    t1-t3 30, 31, 29 pass x3 within limits unchecked -> within limits (time t1)
    t4-t6 55, 56, 48 above, above, pass (unchanged) none: the three results differ
    t7-t9 57, 58, 60 above x3 above high limit within limits -> above high limit (time t7); event raised if its ID is not 0
    t10-t12 5, 4, 6 below x3 below low limit above high limit -> below low limit (time t10)

    The transition time is the sampling time of the first of the samples that established the new status, and the reported value is the last sample used.19

    Reporting the check transitions: TM[12,12]¶

    The subservice reports the check transition list in a TM[12,12] check transition report, then removes the reported transitions from the list. A report is issued when either the declared maximum number of transitions is reached or the maximum transition reporting delay has elapsed since the first transition in the list. The delay is expressed in minimum-sampling-interval units; its default is declared, and if the capability exists TC[12,3] changes it.1920 Each notification carries: PMON ID, monitored parameter ID, check type, the expected-value mask (expected-value checks only), the parameter value that caused the transition, the limit crossed, the previous and new checking statuses and the transition time.19

    Out-of-limits: TC[12,10] and TM[12,11]¶

    On request, TM[12,11] lists only the transitions that represent a violation:28

    Check type Reported transitions
    Expected-value unchecked, invalid or expected value -> unexpected value
    Limit unchecked, invalid or within limits -> below low limit / above high limit; below low <-> above high
    Delta unchecked, invalid or within threshold -> below low / above high threshold; below low <-> above high threshold

    Generating an out-of-limits report does not clear the check transition list; only a check transition report does.29

    Printed typo

    Requirement 6.12.3.12e.5 prints "within threshold" to "below high threshold"; from the structure of the list it is evidently meant to read "below low threshold". Figure 8-122 is also captioned "limit-checking" although it shows the delta-checking fields.2850

    Functional monitoring subservice¶

    Functional monitoring watches the health of an on-board element (a software application, a hardware unit) by combining parameter monitoring definitions. A functional monitoring definition (in the FMON list) names a set of PMON definitions; when at least a "minimum PMON failing number" of them are in violation at the same time, the functional definition fails and its event is raised. A minimum of 1 behaves as a logical OR; a minimum equal to the number of members behaves as a logical AND. If the subservice does not support the parameter, 1 is used.3132

    Element Present
    FMON identifier always
    Check validity condition (validity parameter ID, mask, expected value) if conditional checking is declared
    Event definition ID of the event to raise always
    Minimum PMON failing number if declared
    List of one or more PMON identifiers (maximum count declared) always

    Sources: requirement 6.12.4.2.1.32

    The subservice keeps an FMON function status, a per-definition FMON status (enabled/disabled), an FMON checking status ("unchecked" 0, "running" 1, "invalid" 2, "failed" 3) and, if protection is supported, an FMON protection status (unprotected 0, protected 1).3357 Whenever a member PMON definition establishes a new checking status, an enabled FMON that is not "failed" first evaluates its validity condition ("invalid" if false) and, if not invalid, counts its members in violation: reaching the minimum sets "failed" and raises the event, otherwise the status becomes "running".35

    Inference

    Requirement 6.12.4.5.1 evaluates the validity condition only when the status is not "failed", and counts violations only when it is neither "failed" nor "invalid". Read literally, nothing moves an "invalid" definition back to "running" when its validity condition becomes true again, except disabling and re-enabling it. The arrow FI to FR above is this wiki's assumption; it matches the rule Solar Orbiter's service 142 states explicitly (see below).92

    Protection freezes a functional monitoring definition and its members: a protected FMON cannot be deleted, and the PMON definitions it uses cannot be enabled, disabled or modified.3337 The standard gives no rationale; guarding FDIR monitoring against accidental changes is the obvious use (this wiki's reading).

    Message types and data fields (PUS-C)¶

    PUS-C gives field types but leaves most widths to the mission ("enumerated", "unsigned integer"); "deduced" fields take the format of the monitored or validity parameter.49 The tables below restate the interface figures; the Solar Orbiter section draws real layouts with sizes. Type names follow the PUS parameter types.

    Simple identifier lists¶

    TC[12,1], [12,2], [12,6] and [12,8] carry N (unsigned integer) followed by N PMON IDs (enumerated); TC[12,8] uses N = 0 for "all". TC[12,19]-[12,22], [12,24] and [12,25] carry N and N FMON IDs; TC[12,25] uses N = 0 for "all". TC[12,3] carries one unsigned integer, the maximum reporting delay. TC[12,4], [12,10], [12,13], [12,15]-[12,18] and [12,27] have no application data.434445464748

    The 2024 Rev.1 draft¶

    The ECSS-E-ST-70-41C Rev.1 DIR1 draft (public review until 28 February 2025) keeps the service structure and adds two requests, TC[12,29] and TC[12,30], to start and stop logging check transitions in the check transition list (stopping also empties the list).59 It renames TC[12,10]/TM[12,11] "report the current out-of-limits", drops the separate mask from the check transition notification (the value is reported after the mask is applied), and changes the add request so that a faulty instruction rejects the whole ordered request.626061 The draft also proposes 2-byte PMON and FMON identifiers in its key element size table.63 Until published, these remain proposals; see PUS-A vs PUS-C.

    PUS-A (ECSS-E-70-41A, 2003)¶

    PUS-A organised the service around a monitoring list of parameters, each carrying a set of check definitions, instead of one definition per check.66 Per parameter it stored: whether its monitoring is enabled, an optional Boolean validity parameter, a monitoring interval in units of the mission constant <DIAG_MIN_INTERV>, and the check definitions.67 Each check definition held its type, its limits/thresholds/expected value, an optional Boolean check selection parameter (the check applies only while it is TRUE), a number of repetitions #REP and the report identifier (RID) of the event to generate.67 For delta checks #REP was the number of deltas averaged, not a repetition filter.67

    A check definition was used only if monitoring was enabled at service level and for the parameter, the validity parameter was TRUE and the selection parameter was TRUE. Otherwise its status became "unchecked", "invalid" or "unselected" respectively - a status PUS-C dropped.68 Violations generated an event report TM(5,4) "high severity" containing the RID and no auxiliary data.69 One behaviour differs from PUS-C: from "within limits", samples alternating below and above the limits counted towards the repetition, and the new status was the result of the current sample.69 PUS-C requires all repeated results to be the same.18

    Solar Orbiter¶

    Solar Orbiter's spacecraft interface follows PUS-A tailored by Airbus (see also How Solar Orbiter uses PUS and The Solar Orbiter MIB). In the service table of the TM/TC and packet structure ICD, service 12 is optional for payload software, with TC(12,1), TC(12,2) and TM(12,12) mandatory if implemented; all subtypes 1-12 are provided by the Central Software (CSW) of the on-board computer.79 Each CSW application hosts its own instance: a request applies only to the service 12 instance of the application addressed by the packet's APID. In TC(12,1) and TC(12,2), N = 0 enables or disables monitoring at service level and leaves each entry in its current state; N > 0 acts on the listed monitoring IDs (1 byte each).80

    Data structures¶

    The ICD fixes the field sizes. Monitoring IDs are 1 byte (1-255), parameter IDs 4 bytes, and limits and expected values occupy fixed 8-byte and 4-byte fields, right-aligned and padded with zeros on the left when the parameter is shorter.8384

    Unlike PUS-A's separate add and modify, Solar Orbiter's TC(12,5) adds or replaces: an existing monitoring ID is overwritten. Each entry has either a limit check (NOL = 1) or an expected-value check (NOE = 1); there is no delta check and no check selection parameter.8384 TC(12,7) modifies only the criteria (N, monitoring ID, NOL, 20-byte limit criteria, NOE, 10-byte expected-value criteria).85 The ICD recommends not using TC(12,4) "Clear Monitoring List" in flight.82 TC(12,3) carries a 1-byte delay counted in 8 Hz cycles (125 ms), where 0 means no transition report is generated.81

    TM(12,11) has the same entry layout, and TM(12,9) echoes TC(12,5) preceded by the global monitoring status (1 byte) and the maximum reporting delay (1 byte).878688 The checking status uses the PUS-A codes: 0 valid (within limits or expected), 1 unchecked, 2 invalid, 4 unexpected or below low, 5 above high; 3 (unselected) is not used.8788 When a monitor triggers, the event report carries the monitoring ID, parameter ID, mask, value, limit crossed, both statuses and the transition time (CUC, 4 + 2 bytes).89

    Solar Orbiter in the MIB¶

    The 2025 MIB release defines 254 service 12 commands and 32 service 12 packet definitions (the April 2020 release: 247 and 19).9497 The commands are addressed to seven APIDs. Decoding APID = 16 x PID + category with the ICD's allocation, 172/188/204/220/236/268 are the DMS, AOCS, payload, platform, system control and thermal control applications of the CSW (PID 10, 11, 12, 13, 14, 16, category 12) and 1084 is METIS (PID 67).9094

    Subtype Commands Applications (APID)
    1 / 2 enable / disable 13 each 6 CSW applications (one each) + 7 METIS variants
    3 change delay 7 6 CSW + METIS
    4 clear, 6 delete, 8 report list, 10 report OOL 6 each 6 CSW
    5 add 114 6 CSW (15-36 per application)

    The MIB (see commanding in the MIB) shows how operators fill the "deduced" limit fields. Besides one generic command per application whose limits are 8-byte octet strings, there are typed variants such as ZCD2Z08A "Add param monitor high/low (uint8)": fixed areas zero-fill the leading bytes and an 8-bit editable limit sits at bit 200, the last byte of the 8-byte low-limit field - the right alignment the ICD asks for.95 Variants exist for uint8/16/32, sint16/32 and float4/8 limits and for uint/sint expected values. The thermal application adds sensor-specific modify commands such as ZTC2X02F "Mod Hi/Lo ANY PT-1000", whose limits are entered in degrees Celsius and converted to raw values by the 31-point command calibration CTC4Z102TC (cca).9596 The parameter identifiers use command parameters of category P in cpc: the operator types a telemetry parameter name and SCOS-2000 encodes its on-board identifier.95110 The system control application also carries predefined monitors such as "Define SWA_A_OFF S12" (ZCSX0019).94

    Inference: repetition field width

    In every MIB definition of the DMS add command (ZCD00C05, bits 96-127) and of the monitoring list reports, "Repetition Interval" is a 32-bit unsigned integer (PTC 3, PFC 14), making each entry 48 octets, while the ICD prints "Rep" as 1 byte (45-octet entry). The fixed-layout reports confirm 48-octet entries (consecutive monitoring IDs at byte offsets 19 and 67).9510183 The MIB reflects what the ground actually sends, so the ICD table is probably out of date on this point; the available sources do not say.

    On the telemetry side the 2025 MIB defines TM(12,9), TM(12,11) and TM(12,12) for each of the six CSW applications at category 3 ("table generation") APIDs 163, 179, 195, 211, 227 and 259, and a TM(12,12) for METIS at APID 1075.9790 They are variable packets: for example SPID 14171 decodes a 16-bit count, then per entry the monitoring ID, the monitored parameter ID NCD0C095 flagged VPD_PIDREF = Y, the mask, the value and limit as deduced parameters (PTC 11), both statuses through the text calibration CCDT0011TX and a CUC time (PTC 9, PFC 17).98 VPD_PIDREF = Y tells SCOS-2000 to look the value up among the PCF_PID values to find the parameter.107108 Each deduced field names NCD0C095 in PCF_RELATED, which identifies the parameter whose value gives the on-board parameter ID, and carries a PCF_WIDTH of 64 bits (32 for the expected value); for a deduced parameter with a PCF_WIDTH the import ICD says the value is extracted from a fixed-width field rather than one sized by the parameter type. This matches the ICD's fixed 8-byte (4-byte) slots.98105 CCDT0011TX maps 0 VALID, 1 UNCHECKED, 2 INVALID, 4 BELOW_LOW, 5 ABOVE_HIGH and 6 OUT_OF_LIMIT; the identifier calibration PARAMIDTM has 19 803 entries.99 The value 6 is not a service 12 checking status in the ICD. It does appear there as the "check state type" "Out of Limit" (below low or above high) that a service 142 FMON can trigger on (TC(142,5)).8793

    Inference: two ways to decode the monitoring list

    The MIB also holds fixed-layout definitions of TM(12,9) at APIDs 1986-1990 (PID 124, inside the EGSE range 112-127 of the ICD), one set per application, keyed by the first monitoring ID at byte 19 (PIC PI1) and holding up to 85 entries each: AOCS 189 entries, payload 129, platform 228, system 47 or 49, thermal 216.10010190 The parameter names (PID11_S001_...) suggest ground-side decoders for the fixed 8-byte limit fields; the available sources do not explain these APIDs. The per-monitor S12 event definitions described below sit on APIDs 1954-1979 (PIDs 122 and 123), also inside that EGSE range.10290 The SCOS-2000 import ICD does not say where, inside a 64-bit PCF_WIDTH slot, a shorter deduced value is taken from. The Solar Orbiter ICD right-aligns it.10584

    Monitoring violations reach the operators as ST[05] events. The MIB defines TM(5,3) event packets with event IDs 33537 "S12_Higher_Limit_Exceeded", 33538 "S12_Lower_Limit_Exceeded" and 33539 "S12_Unexpected_Value", each with the SCOS-2000 event severity A (alarm), and TM(5,2) warning variants 32512 (unexpected value), 32513 (lower limit) and 32514 (higher limit) with severity W.102109 In the ICD, TM(5,2) is a low-criticality (warning) and TM(5,3) a medium-criticality anomaly report, which needs a ground recovery action. PUS-A §15.2.3 instead prescribes a TM(5,4) high-severity report for monitoring violations.10369 In hexadecimal, 33537-33539 are 0x8301-0x8303, inside the ICD's TM(5,3) range for general application software events. 32512-32514 are 0x7F00-0x7F02, inside the TM(5,2) range that Annex 9 allocates to ESOC (this conversion is this wiki's).104 Besides one generic definition per CSW application (for example SPID 14425 for the DMS), 573 high-limit, 573 low-limit and 220 unexpected-value definitions distinguish individual monitors through PI2 at byte 18 (the monitoring ID), for example "S_DST1A_A DST TX-A Temp_HI".102

    Functional monitoring as service 142¶

    Solar Orbiter's service set is tailored from PUS-A (its capability sets refer to ECSS-E-70-41A), which has no functional monitoring, so this function is the private service 142.7965 It groups service 12 monitors into an FMON with OR or AND logic, can be protected, and is used for FDIR.91 Rules from the ICD: a disabled FMON becomes "unchecked"; enabling it makes it "running"; a false validity condition makes it "invalid"; after triggering it stays enabled in a failed state until disabled and re-enabled; and new FMONs start disabled and protected.92 Each FMON also has a timeout, in cycles, before it is re-enabled if the triggered event-action sequence has not done so.93 The MIB carries 59 service 142 commands (58 in April 2020): subtypes 1, 2, 5, 6 and 8 for the six CSW applications and the SSMM (APID 492), 10, 12 and 13 for the CSW applications only, and 3, 4 and 14 only for the SSMM, whose own service 142 manages redundancy. It also carries the FMON event 45718 (a TM(5,3) on the system control application, alias "FMON_TRIGGERED" in the event-ID set CCDT0004TX).9410291
