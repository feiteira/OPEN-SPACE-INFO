    ST[14] Real-time forwarding control¶

    Every report an on-board service generates - a verification report, a housekeeping packet, an event - costs processing, on-board network capacity and downlink bandwidth. The real-time forwarding control service type, ST[14] of the Packet Utilization Standard, lets the ground decide which of those reports actually leave the spacecraft in the real-time telemetry channel, per application process, per service type, per report type and, optionally, per housekeeping or diagnostic structure and per event definition.1 Whether the same reports are stored on board is a separate matter, handled by ST[15] on-board storage and retrieval.29 Abbreviations are expanded in the glossary; the PUS-A and PUS-C issues are compared in PUS-A vs PUS-C.

    At a glance

    Subservice real-time forwarding control (one), hosted at most once per application process3
    Configurations application process forward-control (always); housekeeping, diagnostic and event-blocking forward-control (each by declaration)5
    Messages (PUS-C) TC[14,1]-[14,3], [14,5]-[14,7], [14,9]-[14,11], [14,13]-[14,15]; TM[14,4], [14,8], [14,12], [14,16]28

    Solar Orbiter PUS-A based, hosted by the CSW Data Management System application, real-time VC only, everything enabled by default4252

    Generation versus forwarding¶

    PUS-A set out the principle: generating telemetry is controlled inside each originating service (for example ST[03] enables or disables a housekeeping structure), but forwarding is a higher-level control, done either by the originating application process (a packet may be generated but not forwarded) or by a centralised application process that receives all packets bound for the ground and routes the downlink.33 PUS-C keeps the idea: a subservice controls reports of its own application process and of the other application processes declared for it, and it knows those application processes but not which service and report types they can produce, so keeping the configuration meaningful is a ground responsibility.46

    Service layout and accessibility¶

    • Each real-time forwarding control service contains at least one subservice, and each application process hosts at most one subservice provider.3
    • The list of controlled application processes is declared; the hosting application process is always included, and the subservice must be able to handle all reports from all of them at any time.4

    The four forward-control configurations¶

    Capabilities declared per mission decide which configurations exist: per housekeeping structure, per diagnostic structure, per event definition, and, if either structure-level control exists, whether a subsampling rate can be attached to a structure.5

    Configuration One definition per controlled AP contains Empty configuration means Present
    Application process forward-control AP ID; 0..n service type definitions, each with 0..n report type (message subtype) definitions block all reports always
    Housekeeping parameter report forward-control AP ID; 0..n housekeeping structure IDs (each with a subsampling rate if supported) block all housekeeping reports by declaration
    Diagnostic parameter report forward-control AP ID; 0..n diagnostic structure IDs (each with a subsampling rate if supported) block all diagnostic reports by declaration
    Event report blocking forward-control AP ID; 0..n event definition IDs block nothing by declaration

    Sources: §6.14.3.2.2-6.14.3.2.5.68910 The maximum number of definitions in each configuration equals the number of controlled application processes (that can produce that kind of report); the maximum numbers of service types per AP, report types per service type, structure IDs per definition and event IDs per definition are declared.68910

    Inside a definition an empty list means "all": an AP definition without service types forwards every report of the AP, a service type definition without report types forwards the whole service type, a housekeeping definition without structure IDs forwards all its housekeeping reports - and an event-blocking definition without event IDs blocks all events of the AP.6810 The first three configurations are therefore allow-lists and the last a block-list.

    Forwarding control processing logic¶

    A report is blocked as soon as one applicable configuration blocks it.11

    flowchart TD
  R["Report from AP a, type (s, t)"] --> A{"AP definition<br/>for a?"}
  A -- no --> B["BLOCK"]
  A -- yes --> S{"AP definition has<br/>service types?"}
  S -- no --> K["passes AP level"]
  S -- yes --> S2{"definition for s?"}
  S2 -- no --> B
  S2 -- yes --> T{"s definition has<br/>report types?"}
  T -- no --> K
  T -- yes --> T2{"t listed?"}
  T2 -- no --> B
  T2 -- yes --> K
  K --> H{"HK report and HK<br/>control declared?"}
  H -- yes --> H1{"HK definition for a,<br/>and SID listed or list empty?"}
  H1 -- no --> B
  H1 -- yes --> E
  H -- no --> E{"event report and event<br/>control declared?"}
  E -- yes --> E1{"blocking definition for a<br/>with empty list, or EID listed?"}
  E1 -- yes --> B
  E1 -- no --> FWD["FORWARD"]
  E -- no --> FWD

    The decision tree restates requirements 6.14.3.3a-i; diagnostic reports follow the same branch as housekeeping reports with the diagnostic configuration.11 If none of the optional capabilities is provided, only the application process configuration applies.7

    Managing the configurations: requests¶

    Each instruction rejected in a request produces a failed start of execution notification (ST[01]); the valid instructions of the same request are still executed.13

    Application process forward-control¶

    TC[14,1] add report types carries any mix of three instructions: add a report type (AP ID, service type, message subtype), add all report types of a service type (AP ID, service type), and add all report types of an AP (AP ID). It creates the AP and service type definitions as needed; adding a whole service type deletes its report type list, and adding a whole AP deletes its service type list - turning the definition into "all".1213 Instructions are rejected when:1213

    • the AP is not controlled by the subservice;
    • a new service type definition would exceed the maximum per AP, or a new report type would exceed the maximum per service type;
    • the instruction is meaningless because the whole AP (empty service type list) or the whole service type (empty report type list) is already forwarded.

    TC[14,2] delete report types carries either any mix of "delete a report type", "delete a service type" and "delete an AP", or one "empty the configuration" instruction. Unknown items are rejected. Deletions cascade: removing the last report type of a service type removes that service type definition, and removing the last service type of an AP removes the AP definition.14

    Inference: why the deletions cascade

    Without the cascade, deleting the last listed report type would leave an empty list, which means "forward everything" - the opposite of the intention. Deleting the emptied definition instead makes the report types (or service types) fall back to "blocked". The standard states the rule but not this rationale.

    TC[14,3] (requires TC[14,1]) asks for TM[14,4], one notification per AP definition with its service types and their report types.15

    Housekeeping and diagnostic parameter report forward-control¶

    TC[14,5] adds housekeeping structure IDs (AP ID, SID and, if supported, a subsampling rate) or "all structure IDs" of an AP (which empties the list); it is rejected for an uncontrolled AP, when the maximum number of SIDs is reached, or when the AP already forwards all its SIDs.16 TC[14,6] deletes SIDs, whole APs, or empties the configuration, with the same cascade (an emptied definition is deleted, so that AP's housekeeping becomes blocked); deleting a SID also deletes its subsampling rate.17 TC[14,7] (requires TC[14,5]) returns TM[14,8] with each AP, its SIDs and their subsampling rates.18 TC[14,9] to TC[14,11] and TM[14,12] do the same for diagnostic structures.19

    Subsampling rate

    The standard lets missions declare a subsampling rate per structure but does not define its meaning (for example "forward one report in N"); that is not stated in the available sources.516

    Event report blocking forward-control¶

    TC[14,14] adds event definition IDs to block (AP ID, event ID) or blocks all events of an AP (empty list); it is rejected for an uncontrolled AP, when the maximum is reached, or when the AP already blocks all events.21 TC[14,13] deletes event IDs, whole APs, or empties the configuration; an emptied definition is deleted, which un-blocks that AP's events.20 TC[14,15] (requires TC[14,14]) returns TM[14,16].22

    The 2024 Rev.1 draft¶

    The Rev.1 DIR1 draft adds that the configuration policy applied when the subservice starts and restarts must be declared, keeps only the housekeeping and event capabilities (its Annex C no longer lists TC[14,9]-[14,12] for diagnostic structures), and says explicitly that ST[14] is fully independent of ST[15].302931 The 2015 status presentation records that the service was "completely remodelled" during the PUS-C review to keep service types independent of each other.32

    PUS-A (ECSS-E-70-41A, 2003)¶

    The PUS-A packet forwarding control service kept, per application process, sets of enabled types, enabled subtypes per type, and enabled housekeeping, diagnostic and event report definitions (SID and RID). A packet was forwarded only if its type and its subtype were enabled and, for housekeeping, diagnostic and event packets, also its SID or RID - three independent attributes that all had to be "enabled".35 The service could sit in the originating application process (then N1 and the APID were omitted from the requests) or in a centralised one.3536

    Subtype PUS-A request or report Data
    (14,1) / (14,2) Enable / Disable Forwarding of Telemetry Source Packets N1, APID, N2, type, N3, subtype
    (14,3) / (14,4) Report Enabled Telemetry Source Packets / report same layout
    (14,5) / (14,6) Enable / Disable Forwarding of Housekeeping Packets N1, APID, N2, SID
    (14,7) / (14,8) Report Enabled Housekeeping Packets / report same layout
    (14,9) - (14,12) the same for diagnostic packets N1, APID, N2, SID
    (14,13) - (14,16) the same for event report packets N1, APID, N2, RID

    Sources: §17.3.3637383940 For (14,1)/(14,2), N2 = 0 enabled all types of the AP, or disabled them and cleared their subtype sets; N3 = 0 added or removed the listed types (removing also cleared their subtypes); N3 > 0 added or removed subtypes of a type. These requests did not touch the SID/RID level, and an unknown type or subtype was an error that did not stop the rest of the request.36 The minimum capability set was (14,1) and (14,2); the rest were additional, and control of a kind of definition was offered only if the AP generated it.41

    Inference

    Read literally, PUS-A enabling a type with N3 = 0 adds the type but no subtype, and the report (14,4) says that N3 = 0 means none of its subtypes is enabled; yet the forwarding rule needs both. Solar Orbiter's private status report instead uses N3 = 0 to mean that the status applies to all subtypes of the type (see below).3748

    Model enable/disable flags at type, subtype, SID/RID level add/delete definitions in four configurations
    Default meaning of "nothing defined" not stated AP and HK/diagnostic: blocked; events: not blocked
    Events enable list (RID) block list (event definition ID)
    Subsampling none optional per HK/diagnostic structure
    Status reports (14,3)/(14,4), (14,7)/(14,8), (14,11)/(14,12), (14,15)/(14,16) TC[14,3]/TM[14,4], TC[14,7]/TM[14,8], TC[14,11]/TM[14,12], TC[14,15]/TM[14,16]

    Solar Orbiter¶

    In Solar Orbiter's TM/TC ICD (see also How Solar Orbiter uses PUS), service 14 applies only to the real-time virtual channel; the service keeps, per process ID, which packets may be transmitted, and by default every packet of every on-board process ID is enabled. The forwarding rule is PUS-A's: type and subtype, plus the SID or EID for housekeeping, diagnostic and event packets, must all be enabled.42 The ICD's service table marks every service 14 message for the CSW only, with no entry for the SSMM, star tracker or payload software.43 Instead of PUS-A subtypes ¾ and 15/16, Solar Orbiter defines private reports: TC(14,128)/TM(14,129) for TM source packets and TC(14,130)/TM(14,131) for event packets.43

    Solar Orbiter addresses applications by their 7-bit process ID (the high bits of the APID); the ICD shows it as a 1-bit filler and a 7-bit PRID.4450

    Sources: §5.15.1-5.15.12.444546

    Printed typo

    §5.15.8 of the ICD gives TC(14,10) "Disable Forwarding of Diagnostic Packets" the service subtype 6; its heading, the service summary and the MIB (ZCD00E0A) all use subtype 10.454352

    The status reports carry a forwarding status FSTAT (0 disabled, 1 enabled) at each level. TM(14,8) and TM(14,12) list, per PRID, the SIDs with their FSTAT (SID 0 meaning all); TM(14,131) lists EIDs (2 octets, 0 meaning all) with FSTAT; TM(14,129) gives an FSTAT for the process ID, each type and each subtype, where N2 = 0 applies the status to all types, N3 = 0 to all subtypes of a type, and type or subtype 0 means "all".474849

    Service 14 in the MIB¶

    The 2025 Solar Orbiter MIB has 12 service 14 commands and 4 service 14 packets, the same as in April 2020, all on the DMS application: commands on APID 172 (PID 10, category 12) and reports on APID 163 (category 3).525350

    Command Subtype Name in the MIB

    ZCD00E05 / ZCD00E06 / ZCD00E07 5 / 6 / 7 Enable / Disable Forwarding HK Pkts, Report Housekeeping Packets Forwarding S (description truncated in the MIB)
    ZCD00E09 / ZCD00E0A / ZCD00E0B 9 / 10 / 11 Enable / Disable Forwarding of Diagnostic Packets, Report Diagnostic Packets Forwarding Sta (truncated)

    Source: ccf.52

    The three nested repeat groups of TC(14,1) are encoded with cdf group sizes: "Number of Process IDs" (bit 0) repeats the next 5 parameters, "Number of PUS Types" (bit 16) the next 3 and "Number of PUS Subtypes" (bit 32) the next 1 - the same technique the SCOS-2000 import ICD illustrates with a two-level (14,2) example.5456 The process ID is an 8-bit enumerated parameter with a 70-value text alias set CCDT0018TX (TIME 0, DMS 10, AOCS 11, PAYLOAD 12, PLATFORM 13, SYSTEM 14, OBCP 15, THERMAL 16, OBDB 17, OP_SSMM 30, SSMM_DEBUG_A/B 31/32, SSMM_HK_SOURCE 33, STR1/STR2 40/41, then the instrument process IDs from EPD_0 50 to SPICE_8 104, for example SWA_0 95 to SWA_4 99), and the event IDs of TC(14,13) are 16-bit unsigned integers.54 The reports are variable packets: SPID 14160 decodes TM(14,129) with a status parameter after the PID, each type and each subtype, matching the ICD.5548

    Inference: where the ranges come from

    The maxima are exactly what fits in Solar Orbiter's 236 octets of TC application data: for TC(14,13) with one process ID, 3 octets of N1, PRID and N2 leave room for 116 two-octet event IDs; with one event each (4 octets per process ID) 58 process IDs fit after N1. TC(14,5) and TC(14,1) give 233, 78, 117, 116 and 231 the same way. The MIB does not state the derivation.5154 The minimum of 1 for N2 in TC(14,5) also means that the MIB offers no N2 = 0 ("all structures") form there; neither PUS-A §17.3.3 nor the Solar Orbiter ICD defines one for (14,5) - only PUS-C TC[14,5] does.384525

    The Herschel/Planck Operations Interface Requirements Document asked for the same control on that mission - per APID, all packets, types and subtypes, housekeeping, diagnostic and report packets - and classified these commands as hazardous; each application also had to report, on request, which packets were enabled and their generation frequency.58 SCOS-2000 itself does no specific processing of service 14 packets.57

    -- solo-2025-09-16.sqlite (MIB__20250916M25925PFMS001_SOL); counts repeated on solo-2020-04-16.sqlite
SELECT CCF_CNAME, CCF_DESCR, CCF_STYPE, CCF_APID, CCF_NPARS
  FROM ccf WHERE CCF_TYPE = '14' ORDER BY CAST(CCF_STYPE AS INT);
SELECT PID_TYPE, PID_STYPE, PID_APID, PID_SPID, PID_DESCR, PID_TPSD FROM pid WHERE PID_TYPE = '14';
SELECT c.CDF_ELTYPE, c.CDF_ELLEN, c.CDF_BIT, c.CDF_GRPSIZE, c.CDF_PNAME,
       p.CPC_PTC, p.CPC_PFC, p.CPC_DESCR, p.CPC_PAFREF, p.CPC_PRFREF
  FROM cdf c LEFT JOIN cpc p ON p.CPC_NAME = c.CDF_PNAME
 WHERE c.CDF_CNAME IN ('ZCD00E01','ZCD00E05','ZCD00E0D') ORDER BY c.CDF_CNAME, CAST(c.CDF_BIT AS INT);
SELECT * FROM paf WHERE PAF_NUMBR = 'CCDT0018TX';
SELECT * FROM pas WHERE PAS_NUMBR = 'CCDT0018TX' ORDER BY CAST(PAS_ALVAL AS INT);
SELECT r.PRF_NUMBR, r.PRF_DESCR, v.PRV_MINVAL, v.PRV_MAXVAL
  FROM prf r JOIN prv v ON v.PRV_NUMBR = r.PRF_NUMBR
 WHERE r.PRF_NUMBR IN ('VCD00243','VCD00254','VCD00153','VCD00176','VCD00270',
                       'VCD00246','VCD00353','VCD00186','VCD00268','VCD00187');
SELECT v.VPD_TPSD, v.VPD_POS, v.VPD_NAME, v.VPD_GRPSIZE, p.PCF_DESCR, p.PCF_PTC, p.PCF_PFC
  FROM vpd v JOIN pcf p ON p.PCF_NAME = v.VPD_NAME
 WHERE VPD_TPSD IN ('14158','14159','14160') ORDER BY 1, CAST(VPD_POS AS INT);
