    ST[11] Time-based scheduling¶

    A spacecraft is not always reachable from the ground: a low Earth orbiter sees a ground station only part of the time, and a deep-space probe suffers long signal propagation delays. The time-based scheduling service (service type 11) lets the ground load telecommands in advance, each with a release time, into an on-board time-based schedule; the service releases each request to its destination application process when its time comes.143 ESA ground systems call these execution time-tagged commands, and the Solar Orbiter project calls its schedule the Mission Timeline (MTL).7084 This page describes the PUS-C service (ECSS-E-ST-70-41C, 2016) in full: its model, every one of its 27 message types, the filters and the capability sets. It then covers the PUS-A predecessor ("on-board operations scheduling", with interlocks and relative times), the 2024 Rev.1 draft, how SCOS-2000 builds and models TC(11,4) commands, and how Solar Orbiter uses the service, with data from its real MIB.

    1. Concepts¶

    1.1 The scheduled activity¶

    The schedule holds scheduled activities. Each consists of scheduling data (the release time and, if supported, a sub-schedule identifier and a group identifier) and the request to release later. An activity is identified by the identifier of its request.2 A PUS request identifier combines the source identifier of the issuer, the destination (APID of the executing process plus a system identifier) and the packet sequence count; in a TC packet these are the source ID field of the secondary header and the APID and sequence count of the primary header.37

    1.2 An extension of ground control¶

    PUS-C describes the service as an extension of ground monitoring and control. A released request is executed as if it had come straight from its original source: the executing process sends its verification reports, if any, to the source identified in the request, not to the scheduler. The release of a request does not depend on the success or failure of earlier released requests.24 The schedule is therefore open-loop. This differs from PUS-A, whose optional interlocks let a release depend on the outcome of an earlier command (section 7).43

    1.3 Sub-schedules and groups¶

    Two optional grouping concepts organise the schedule:2

    Sub-schedule Group
    Purpose one coherent on-board operation a spacecraft entity, for example one instrument or a software item
    Creation automatically, when an insert request names an unknown sub-schedule (created disabled) explicitly, by TC[11,22], with an initial status
    Deletion automatically, when its last activity is released or deleted; also by reset explicitly, by TC[11,23], only when empty
    Can exist empty? no yes
    Control enable or disable by TC[11,20] / TC[11,21] enable or disable by TC[11,24] / TC[11,25]
    Status report TC[11,18] gives TM[11,19] TC[11,26] gives TM[11,27]

    Groups let operations disable, for example, all activities of one instrument when the conditions for their execution are not met, independently of the application processes and sub-schedules the activities belong to.2 The PUS-C working group presented the service with exactly these two concepts at ADCSS 2015, as one of three services resulting from a complete re-assessment of the PUS-A scheduling service. The other two were then called "telecommand sequencing" (ST21) and "orbit-based scheduling" (ST22); PUS-C publishes them as ST[21] request sequencing and ST[22] position-based scheduling.6942

    1.4 Operational requirements behind the service¶

    The space segment operability standard ECSS-E-ST-70-11C Rev.1 defines an on-board operations schedule as an on-board facility that stores and releases telecommands loaded in advance, and asks, among others, that:6768

    • any telecommand can be loaded into the schedule (5.8.5a);
    • the schedule content can be changed both while the execution function is enabled and while it is disabled (5.8.5b, c);
    • its capacity covers at least the autonomy period (5.8.5d);
    • the transfer delay to the destination process is predictable, and transfer errors are reported to the ground and to the schedule service (5.8.5e to g);
    • a telecommand with the same release tag as one already loaded is not rejected but released immediately after it (5.8.5h);
    • telecommands that "elapsed" while their schedule, sub-schedule or application process was disabled are not released when it is re-enabled (5.8.5i).

    2. Service layout and accessibility¶

    Each time-based scheduling service contains at least one subservice, and each application process hosts at most one provider.3 The mission declares the list of application processes the subservice may release requests to; all requests of an addressable process can be scheduled, and the hosting process is addressable by nature. A released request is processed by the service named by its service type in the destination process.4

    4. State and execution logic¶

    4.1 The three statuses¶

    The subservice keeps a time-based schedule execution function status (enabled or disabled), set to "disabled" when the subservice starts; one sub-schedule status per sub-schedule; and one group status per group.71316

    4.2 Releasing activities¶

    The execution process handles activities in the order of their release times. An activity is disabled if the execution function is disabled, or its sub-schedule is disabled, or its group is disabled. When an activity's release time is reached, the process, in sequence: releases the request if the activity is not disabled; deletes the activity; and deletes the sub-schedule if that was its last activity.12

    flowchart TD
  T["Release time of the next activity reached"] --> D{"Execution function enabled<br/>AND sub-schedule enabled (if any)<br/>AND group enabled (if any)?"}
  D -- yes --> R["Release the request to its destination<br/>(verification reports go to the original source)"]
  D -- no --> X["Do not release"]
  R --> DEL["Delete the scheduled activity"]
  X --> DEL
  DEL --> L{"Last activity of its sub-schedule?"}
  L -- yes --> DS["Delete the sub-schedule"]
  L -- no --> N["Next activity"]
  DS --> N

    The flowchart restates clause 6.11.4.6.12 Three consequences are worth spelling out. First, a disabled activity is lost, not postponed: disabling the schedule over a release time discards what falls due. Second, PUS-C prescribes no notification to the ground when an activity is deleted without release. Third, PUS-C does not prescribe the release order of activities with exactly the same time.12 The operability standard and the 2024 draft both fill that last gap with "insertion order" (sections 1.4 and 9).6864

    5.2 Controlling the schedule: TC[11,1], TC[11,2], TC[11,3]¶

    These three requests have no application data.28 Enable and disable set the execution function status; neither depends on whether the schedule contains activities.8 Reset is accepted whatever the execution status, and in sequence sets the status to "disabled", deletes all activities, deletes all sub-schedules (if supported) and enables all groups (if supported).9

    5.3 Inserting: TC[11,4]¶

    Field Type Presence Meaning
    sub-schedule ID enumerated if sub-schedules are supported one sub-schedule for the whole request
    N unsigned integer always number of instructions
    group ID enumerated repeated N times; if groups are supported group of this activity
    release time absolute time repeated N times when to release
    request TC packet repeated N times the complete telecommand packet to release

    The layout is PUS-C Figure 8-91.28 The processing rules are:1011

    • The request is rejected as a whole (failed start of execution) only if it would create a new sub-schedule while the maximum number of sub-schedules is already reached.
    • Each instruction is rejected individually, with its own failed start of execution notification, if the schedule is full, if its release time is earlier than now + time margin, if it names an unknown group, or if the embedded request fails the declared verification checks.
    • Valid instructions are processed regardless of faulty ones in the same request.
    • If the named sub-schedule is unknown, it is created with status "disabled"; each valid instruction then creates an activity with its request, release time, sub-schedule and group.

    Inference

    PUS-C fixes the field types of Figure 8-91, not their widths. The 8, 8, 8 and 40-bit widths and the 64-bit placeholder for the embedded packet are illustrative. Section 11 shows the real Solar Orbiter layout.

    5.4 Selecting by request identifier: TC[11,5], TC[11,7], TC[11,9], TC[11,12]¶

    These four requests list activities by the identifier of their request:2930

    Field Type Presence
    time offset relative time TC[11,7] only, before the list; applies to every instruction
    N unsigned integer always
    source ID enumerated repeated N times
    application process ID enumerated repeated N times
    sequence count unsigned integer repeated N times

    Putting the time offset before the instruction list is an application of a general PUS-C rule: arguments that constrain the scope of all instructions of a request are grouped at request level.36

    Request Action on each identified activity Rejection
    TC[11,5] delete delete it; delete its sub-schedule if it was the last activity instruction: unknown request identifier
    TC[11,7] time-shift add the offset to its release time request: earliest identified activity + offset earlier than now + margin (nothing shifted); instruction: unknown identifier
    TC[11,9] detail-report one detail notification each, all in one TM[11,10] instruction: unknown identifier
    TC[11,12] summary-report one summary notification each, all in one TM[11,13] instruction: unknown identifier

    The rules are those of clauses 6.11.9.2 to 6.11.9.5; in all four, valid instructions are processed regardless of faulty ones.22

    5.5 Selecting by filter: TC[11,6], TC[11,8], TC[11,11], TC[11,14]¶

    A filter is a time window combined with zero or more sub-schedules and zero or more groups. The set selected is the intersection of the time-window set with the union of the listed sub-schedules' activities and with the union of the listed groups' activities; unknown sub-schedules in a filter are ignored.23

    Field Type Presence
    time offset relative time TC[11,8] only, first
    time window type enumerated always (Table 8-5)
    time tag 1 absolute time deduced presence: "from time tag" and "from time tag to time tag"
    time tag 2 absolute time deduced presence: "to time tag" and "from time tag to time tag"

    7. PUS-A: the on-board operations scheduling service¶

    Solar Orbiter's on-board software implements the 2003 version of service 11: its applicable PUS document is ECSS-E-70-41A.8486 SCOS-2000's built-in service 11 support also predates PUS-C: it assumes the Rosetta packet structure, and its section references match the clause numbers of PUS-A (see the inference on ST[08]).70 The PUS-A service is therefore described here in detail.

    7.1 Concept¶

    PUS-A motivates on-board scheduling by two scenarios: missions out of ground contact for long periods (low Earth orbit, deep space), and missions that want to minimise their dependency on the ground even when permanently in view, such as geostationary telecommunication or meteorological spacecraft. The simplest form stores time-tagged commands and releases them when their on-board time is reached, open-loop. Optional extensions are:43

    • sub-schedules, logical partitions without their own size limit, to group commands per destination or per sequence;
    • interlocks: a command's release can depend on the success, or the failure, of one earlier command of the same sub-schedule, giving simple preconditions and even IF-THEN-ELSE branches;
    • time-shift "en bloc" by a delta time, instead of deleting and reloading;
    • relative times, counted from a scheduling event such as the start of the schedule or of a sub-schedule, or the execution of the interlocking command.

    7.2 The command schedule¶

    Each telecommand in the PUS-A command schedule has these scheduling attributes: its sub-schedule, the interlock it sets (if any), the interlock it depends on (if any), whether it depends on the success or the failure of that interlock, and an absolute or relative release time, all in CUC.46 Its release status is "enabled" only if release is enabled at three independent levels, the whole schedule, its sub-schedule and its destination application process:47

    Schedule Sub-schedule Destination APID Release status
    enabled enabled enabled enabled
    any other combination disabled

    This collapses PUS-A Table 22, whose eight rows give "enabled" only in the all-enabled case.47

    7.3 Interlocks and scheduling events¶

    When a command that sets an interlock is due: if its release status is disabled or its own interlock status is "locked", it is not released and its execution result becomes "failure"; otherwise it is released, the destination is told to report its completion back to the scheduler, and the result becomes "success" or "failure" on that report, or "failure" if no report arrives within the command's execution timeout. A dependent command is locked if it waits for success and the interlock result is failure, or waits for failure and the result is success.48

Once an event has occurred, the absolute times of the dependent commands are known; a repeat of the event does not change them. Insertions and time-shifts that would put an interlock-dependent command before the end of its interlocking command's execution window are refused.49

    7.4 Auxiliary information and the scheduling activity¶

    The PUS-A service also needs the maximum size of the schedule, the maximum numbers of sub-schedules and interlocks, the list of sources it accepts commands from and the list of destination processes, which it uses for error detection.50 A command whose release time is due is always processed, even if the schedule is disabled: if its release status is disabled or its interlock status locked, it is not released, its execution result becomes "failure" if it sets an interlock, and the time of the scheduling event it defines (if any) becomes the current time; otherwise it is released. The service must also detect and report on-board CUC time jumps, and on a jump suspend itself once it has processed the commands interlocked with commands already released.51 Requests that would make the schedule inconsistent are refused as a whole.45

    ECSS-E-ST-70-41C Rev.1 DIR1 keeps the 27 message types (its Table C-17 lists the same interface clauses 8.11.2.1 to 8.11.2.27) and changes the model in several places:66596061626364

    10.3 The size budget¶

    The maximum size of a command is the MISC variable CMDP_MAX_BLOCK_SIZE (default 248 octets). The space for parameters shrinks by the header, the CRC (CMD_CRC_SIZE, default 2 octets) and, for time-tagged commands, the size of the time-tag wrapper named by CMD_LOAD_TT_NAME (20 octets if that command is not found). With a 10-octet header, a command can then carry at most 238 octets of parameters without time tag or CRC, or 216 with both. The final encoded time-tagged command is larger than CMDP_MAX_BLOCK_SIZE by the wrapper, so the variable must be set to the maximum CLTU size minus the length of the wrapper parameters.71

    Solar Orbiter's numbers match

    On Solar Orbiter a TC data field is at most 242 octets (4 header, 236 data, 2 CRC), so a TC packet is at most 248 octets. A command for the MTL is limited to 228 octets (216 of application data), so that its TC(11,4) stays within 248.9688 The TC(11,4) overhead is 6 (primary header) + 4 (data field header) + 1 (sub-schedule) + 1 (N) + 6 (time tag) + 2 (CRC) = 20 octets, exactly the ICD's default wrapper size, and 248 - 10 - 2 - 20 = 216 is the ICD's own example.7188 The arithmetic is this wiki's.

    Inference: two decoding tricks

    In SPID 14175 the TC packet length C is used as the repeat counter of a one-octet data field, followed by a "last byte": C repetitions plus one octet equals the C + 1 octets of the packet data field, so the embedded TC is unpacked octet by octet. In SPID 14176 the first data field header sub-field has VPD_OFFSET = -32, so the 32 bits just read as "Data field header" are read again field by field.10181

    11.4 How the sub-schedules are organised¶

    Every command definition with a value has CCF_SUBSCHEDID equal to CCF_SUBSYS, so the default sub-schedule is the subsystem number. Platform commands use 1, 2 and 4 to 8; the ten instruments use 101 to 110.101

    The "further sub-schedules" are the ones the MIB's own commands and sequences address:101

    • 141 to 150 are each instrument's iVSTP sub-schedule: sequences ADMF740A to ADMF740U "Enable iVSTP instrument" and "Disable iVSTP instrument" send TC(11,1) or TC(11,2) with exactly that sub-schedule.
    • 161 to 170 are the default sub-schedules of each instrument's recovery sequences, for example AIMC805A "Recover MAG OFF" and AIMC805B "Rcvr MTL P_OFF MAG".
    • 121 to 130 appear only where an instrument's whole set of sub-schedules is disabled or re-enabled: the protection and recovery commands below, the emergency-configuration sequences ASYC602C to ASYC602K, and the EPD and RPW pre-action sequences AIDC060A, AIWC060A and AIWC060B.
    • Sequences default mostly to sub-schedule 1 (780 of 3 404), 2 (404) and the instrument numbers; 56 sequences use 254, the top of the allowed range.

    Inference

    "iVSTP" is not expanded in the available sources; given Solar Orbiter's planning cycles it probably denotes an instrument very-short-term-planning product. The meaning of the 101-110 and 121-130 bands, beyond being per-instrument, is not stated in the available sources.

    11.5 Protecting the MTL when an instrument switches off¶

    The MIB shows a complete on-board protection loop built from events, event-action definitions and the MTL:101

    1. Sequence ADMF730A "Define P_OFF S12 S19" loads on-board monitoring and event-action definitions. Each TC(19,1), for example ZCSX0031 "Define P_OFF_EPD S19", ties an event such as "EPD scvTM OFF" (a fixed event ID parameter) to a TC to send (a fixed "Command ID" parameter).
    2. That TC is a fixed TC(11,2), for example ZCSX0023 "P_OFF_EPD SSID", whose four fixed octet pairs disable sub-schedules 0x67, 0x7B, 0x8F, 0xA3, that is 103, 123, 143 and 163, with N2 = 0 each (raw cdf values 4 67 0 7B 0 8F 0 A3 0).
    3. When the instrument is recovered, a sequence such as AIDC805B "EPD_Enable_MTL" sends TC(11,1) with sub-schedules 103, 123 and 163.

    The recovery sequences re-enable three of the four sub-schedules and leave the iVSTP sub-schedule (14x) disabled; enabling it is a separate operation (ADMF740x).     Between the April 2020 and September 2025 releases the protection loop changed:101102

    • the four SWA sensor commands ZCSX0043 to ZCSX0046 and their event-action definitions ZCSX0047 to ZCSX0054 were added, as was the MAG OBCP definition ZCSX0042;
    • the ten fixed TC(11,2) commands ZCSX0021 to ZCSX0030 disabled three sub-schedules in 2020 (raw cdf values 3 67 0 7B 0 8F 0 for EPD: 103, 123 and 143). In 2025 they disable four, with the 16x band added, and the SWA command also disables 111 to 114;
    • the 2020 release has none of the recovery sequences AI?C805x, iVSTP sequences ADMF740x or emergency sequences ASYC602x, and no sequence defaults to sub-schedules 161 to 170.

    11.6 Verification¶

    Every service 11 command in the MIB has two report-based verification stages, acceptance and completion: stages 14001 and 14007 for the 17 ZCD00Bxx commands, stages 11 and 17 for INSERTTT, INSERTBU and the 14 ZCSX commands; all four stages open at 0 s with a 20 s interval.101 This matches the ICD, which has each of these TCs generate TM(1,2) on a failed static check and TM(1,8) on a completion failure.87 See Command verification in the MIB.

    The bytes below insert TC(9,1) "Change Time Report Generation Rate" (MIB command ZCD00901, rate code 5) into sub-schedule 1, its default CCF_SUBSCHEDID, for release at OBT 811 339 200.0 s.
