    ST[23] File management¶

    ST[23] file management is the PUS-C service type that lets the ground manage on-board file systems: create, delete, lock and inspect files, manage directories, search for files, and copy or move files between file systems, including between the spacecraft and the ground.56 The user need not be on the ground: the standard's own example of an on-board subservice user is a payload controlling a solid-state mass memory through file management subservices.1 It is an interface service: it does not care what is inside a file, and it sits on top of an on-board file handling system that does the real work.54 For moving files across the space link it assumes a separate file transfer layer, for example the CCSDS File Delivery Protocol (CFDP), but it does not standardise that layer.6

    At a glance

    Item Value
    Defined in ECSS-E-ST-70-41C (15 April 2016): system clause 6.23, interface clause 8.23, Annex C Tables C-32 and C-3353851
    Previous edition none: PUS-A (2003) has no file management service61
    Subservice types file handling (exactly one per service) and file copy (at most one); if both exist they are hosted by the same application process7
    Message types 24: 20 requests (TC) and 4 reports (TM)51
    Minimum capability TC[23,1] create, TC[23,2] delete, TC[23,3]/TM[23,4] report attributes; TC[23,14] copy a file when the optional file copy subservice exists517
    Related protocol CFDP (CCSDS 727.0-B-5) as a possible underlying file transfer layer662
    Draft revision Rev.1 DIR1 (2024) adds checksum and directory protection, a new ST[24] file transfer service built on CFDP and a new ST[25] file data storage service7778
    Solar Orbiter no ST[23]; files are managed with private service 133 and SSMM extensions of services 13 and 158086

    Files, repositories and paths¶

    PUS-C defines a small vocabulary for file systems:235

    Term Definition
    On-board file system a system that controls data organised in files; each one has exactly one identifier, unique across the whole spacecraft
    Object a file or a directory
    Repository path the logical path to where an object is located: a physical path such as a directory, or a logical path such as a mounted device (the standard's examples are /mm1 for a mass memory and /mm1/dir1)
    Object name the identifier of an object within its repository
    Object path repository path + object name (a file path or directory path); unique at mission level
    Flat / structured a flat file system has no directories; a structured one stores files in directories

    For each file system the mission declares whether files may have unbounded size (limited only by the physical memory), which attributes exist (for example type or creation date), and whether files can be locked. A file system may be accessed by only one file management service.3 The service must always be able to read the size in bytes of any file, and, where locking exists, its lock status; the readable and settable attribute sets are declared per file system.11 Each file system also declares the wildcard characters it recognises.10

    Who detects which error¶

    The standard deliberately leaves argument checking to be shared between the service and the file handling system, and defines only the outcome:8

    Error found by Example Reported as
    the file management service an invalid object path, a wildcard where none is allowed failed start of execution
    the on-board file handling system creating a file that already exists, deleting a missing or protected file failed completion of execution

    Both appear as ST[01] request verification reports (TM[1,4] and TM[1,8]).58

    Field types used by ST[23]¶

    Almost every ST[23] request is built from variable-length character strings (PTC 8, PFC 0): an unsigned integer length followed by that many characters. The characters must be visible ASCII characters, one octet each, and the width of the length field is declared per application process.53 Paths are always split into two strings, repository path and object name, except in the found-files report, which returns whole matching paths.3943 Other types used are Boolean (PTC 1; PFC 0 is one bit, PFC n > 1 is n bits) for the lock status, unsigned integer for sizes, counters and operation IDs, enumerated for object type and operation status, relative time (PTC 10) for the reporting interval, and deduced (PTC 11) for the mission-defined additional attributes.525556 See PUS parameter types for the full PTC/PFC rules.

    File handling subservice¶

    TC[23,1] create a file¶

    Instruction content: the object path; the maximum size in bytes (if the file system does not support unbounded files); the lock status (if locking is supported); and any additional attributes that can be set at creation. The request is rejected (failed start) for an invalid path or an invalid maximum size; if the file system then fails to create the file, a failed completion is reported.12

    Field Type Presence Meaning
    repository path variable character-string always where to create the file
    file name variable character-string always name of the new file
    maximum size unsigned integer always on the wire size limit in bytes; 0 means unbounded
    file locked status Boolean optional (locking supported) create the file locked or unlocked
    additional file attributes deduced optional mission-defined attributes

    This is Figure 8-261, together with rule 8.23.2.1c on the value 0.39

    A dangling \"repeated N times\"

    Figures 8-261 and 8-264 print a "repeated N times" label above the additional file attributes field, but neither figure contains an N field.3941 The available sources do not explain how the number of additional attributes is encoded; presumably it is part of the mission-defined (deduced) structure.

    TC[23,2] delete a file¶

    One instruction with the object path (Figure 8-262: repository path + file name). Rejected if the path is invalid or contains wildcard characters that the file system recognises: one request deletes exactly one file. A locked file cannot be deleted.1340

    TC[23,3] report the attributes of a file and TM[23,4] file attribute report¶

    The request carries one object path (Figure 8-263).40 If the file system returns the attributes, the service sends one TM[23,4] with:1441

    Field Type Presence
    repository path variable character-string always
    file name variable character-string always
    file size unsigned integer always (the minimum capability)
    file locked status Boolean optional (locking supported)
    additional file attributes deduced optional

    TC[23,5] lock a file and TC[23,6] unlock a file¶

    Locking a file makes it read-only: the file handling system must write-protect it and refuse to delete or move it, and the only change allowed on a locked file is unlocking it. File systems usually also protect files while they are open. Both requests carry one object path (Figures 8-265 and 8-266) and reject wildcards. Unlock exists whenever lock is declared.151642

    TC[23,7] find files and TM[23,8] found files report¶

    The request carries a repository path and a search pattern (Figure 8-267). Wildcards are allowed in the pattern only, never in the repository path, so one request cannot search several repositories. Whether the search covers only the given directory or descends recursively is declared by the mission.1742 The report repeats the repository path and the pattern, followed by N (unsigned integer) and N matching file paths, each a single variable character string (Figure 8-268). Finding nothing is not an error; the list is then empty.1743

    TC[23,9] create, TC[23,10] delete and TC[23,11] rename a directory¶

    Directory operations belong to structured file systems, and the three requests come as a set: delete and rename are implied by create.851

    • Create a directory: one directory path (repository path + directory name; Figure 8-269).1844
    • Delete a directory: one directory path (Figure 8-270), no wildcards. The kind of deletion depends on the file handling system and is declared: only empty directories, only directories without sub-directories, or recursive deletion. A locked file anywhere below the directory prevents its deletion.1944
    • Rename a directory: repository path, old directory name and new directory name (three strings, Figure 8-271). Support must be declared, and a locked file below the directory also prevents renaming.2044

    TC[23,12] summary-report the content of a repository and TM[23,13]¶

    The request carries one repository path, without wildcards (Figure 8-272). The report lists only the direct children of that repository, never recursively. TM[23,13] contains the repository path, N, and for each object its object type (enumerated: 0 file, 1 directory) and object name (Figure 8-273). An empty repository gives an empty list, not an error.214550

    File handling observable¶

    For each file system, the subservice exposes the available unallocated memory.22

    File copy subservice¶

    File systems and operations¶

    The copy subservice works across the file systems declared for it, as source, destination or both. They include on-board file systems and remote ones such as the ground. A file on a remote file system is identified by a remote file path (repository path + file name).23 Each copy or move is a file copy operation with an operation ID that is unique for the operation's lifetime. The requester (usually the ground) puts the ID in the copy or move request; the ID is then used to suspend, resume or abort the operation and appears in its status reports.2425

    TC[23,14] copy a file and TC[23,15] move a file¶

    Both requests have the same layout (Figures 8-274 and 8-275):46

    Field Type Meaning
    operation ID unsigned integer identifier of the new file copy operation
    source file path: repository path variable character-string where the source file is
    source file path: file name variable character-string source file name
    target file path: repository path variable character-string destination repository
    target file path: file name variable character-string destination file name

    Rejection (failed start): the operation ID is already used by an ongoing operation; the source or target path is invalid; or both source and target are on a remote file system, because remote-to-remote copies are not allowed.2526

    Execution: the subservice picks the underlying file transfer handler from the two paths. That handler may be a file transfer layer or a capability of a local file system; the choice is implementation-dependent. The subservice then processes the handler's execution notifications and turns each one into an ST[01] execution verification report: successful ones only if the acknowledgement flags asked for them, failed ones always. For example, a lack of space on the target file system makes the handler fail and produces a failed execution report.2526 The attributes of the created target file, such as permissions, depend on the file system and the implementation.25

    Inference

    Because the copy request is verified through the handler's notifications, a single TC[23,14] can produce progress or completion reports long after it was accepted, for example when a CFDP transfer spans several passes. The standard does not define how many progress steps there are; that follows from the request's execution verification profile.

    Suspending, resuming and aborting¶

    Request Fields Behaviour
    TC[23,16] suspend file copy operations N, N × operation ID each unknown ID is rejected on its own; the handler is asked to suspend each valid one2747
    TC[23,17] resume file copy operations N, N × operation ID mirror of TC[23,16]2847
    TC[23,18] abort file copy operations N, N × operation ID the handler is asked to abort each valid operation3147
    TC[23,19] suspend all file copy operations involving a repository path repository path suspends every ongoing operation whose source or destination lies within the path2948
    TC[23,20] resume all file copy operations involving a repository path repository path resumes operations that are on hold3048
    TC[23,21] abort all file copy operations involving a repository path repository path rejected if no operation is ongoing; otherwise aborts ongoing operations3248

    The standard suggests using the repository path variants with the logical path that represents the ground, to act on every transfer to or from the ground at once, or with the root path to act on all transfers.2932 All six requests apply equally to operations started by TC[23,14] and TC[23,15].27

    As printed

    Only the suspend all requirement (6.23.5.3.3d) states the repository-path condition. The resume all (6.23.5.3.4d) and abort all (6.23.5.4.2f) requirements, read literally, act on every operation that is on hold or ongoing.3032 The caption of Figure 8-281, the layout of TC[23,21] abort all, also says "Suspend all".48 Both look like editorial slips.

    Periodic file copy status reporting¶

    TC[23,22] enables periodic status reports with a reporting interval (relative time, Figure 8-282); an invalid interval is rejected. TC[23,24], with no data, disables them.343549 While enabled, the subservice sends exactly one TM[23,23] file copy status report at the end of every interval, with one entry per ongoing operation:3649

    Field Type Presence Meaning
    N unsigned integer always number of ongoing operations
    repeated N times: operation ID unsigned integer always the operation
    operation status enumerated always Table 8-27: 0 "pending", 1 "in progress"
    progress indicator unsigned integer optional (declared) percentage of completion

    Three states, two codes

    The system requirement lists three operation states: in progress, pending (waiting for on-board resources) and on hold.36 Table 8-27 encodes only "pending" (0) and "in progress" (1), so the on-hold state of a suspended operation has no raw value.50 Figure 8-283 also labels its array "repeated N2 times" while the counter is called N; the 2024 draft prints "repeated N times".4977

    stateDiagram-v2
  [*] --> Pending : TC[23,14] or TC[23,15] accepted
  Pending --> InProgress : resources available
  InProgress --> OnHold : TC[23,16] / TC[23,19]
  Pending --> OnHold : TC[23,16] / TC[23,19]
  OnHold --> InProgress : TC[23,17] / TC[23,20]
  InProgress --> [*] : completed (TM[1,7] or TM[1,8])
  Pending --> [*] : TC[23,18] / TC[23,21] abort
  InProgress --> [*] : TC[23,18] / TC[23,21] abort
  OnHold --> [*] : TC[23,18] / TC[23,21] abort

    Inference

    The three state names come from requirement 6.23.5.5.4c; the transitions are this wiki's reading of the suspend, resume and abort requirements. PUS-C does not draw a state machine for file copy operations.

    File copy observables¶

    Three flags: at least one operation in progress, at least one operation on hold, and whether status reporting is enabled.37

    Worked example: creating a file (illustrative)¶

    The bytes below are constructed for explanation: the field widths are a possible tailoring, not values from the standard or from a mission.     ST[23] and CFDP¶

    What the standards say¶

    PUS-C states that it assumes a dedicated file transfer layer, CFDP being the example, to copy files between ground and space, and that it does not standardise that protocol.6 CFDP (CCSDS 727.0-B-5) moves a file from one filestore to another, typically across a space link. The unit it moves is a file delivery unit (FDU): the file plus metadata such as file names, filestore requests or messages to the user. Each end-to-end delivery is a transaction between a sending and a receiving entity, run in unacknowledged or acknowledged mode.62 Its user interface consists of the request primitives Put, Report, Cancel, Suspend and Resume, plus a set of indications.66 A transaction ID combines the source entity ID with a sequence number specific to that entity.67 See the CFDP page for the protocol itself.

    CFDP also manipulates files. It assumes a virtual filestore that can at least create, delete, rename, append to and replace files, create and remove directories, and list directories.64 These actions travel as filestore requests inside a transaction and are executed by the destination when the data transfer is complete, in the order submitted.68 On the wire each request is a Filestore Request TLV (type 0x00) with a 4-bit action code:70

    CFDP action code Action Second file name Closest ST[23] request (Inference)
    0b0000 Create File no TC[23,1] create a file
    0b0001 Delete File no TC[23,2] delete a file
    0b0010 Rename File yes none (ST[23] renames directories only, TC[23,11]); TC[23,15] move a file is the nearest
    0b0011 Append File yes none
    0b0100 Replace File yes none
    0b0101 Create Directory no TC[23,9] create a directory
    0b0110 Remove Directory no TC[23,10] delete a directory
    0b0111 Deny File (delete if present) no none
    0b1000 Deny Directory (remove if present) no none
    (directory listing user operation) list directory - TC[23,12] / TM[23,13], TC[23,7] / TM[23,8]
    - - - TC[23,5] / TC[23,6] lock and unlock have no CFDP counterpart

    CFDP returns directory listings through its directory operations, not through filestore responses.6863

    Inference: one way to stack them

    The right-hand column and the mapping below are this wiki's reading; neither PUS-C nor CFDP defines a mapping between the two.

    • TC[23,14] copy a file from an on-board path to a ground path would make the on-board file copy subservice issue a CFDP Put.request to the ground entity. A copy from the ground to the spacecraft would need the ground CFDP entity to send the file, for example through a CFDP proxy operation, which CFDP describes as a way to make a remote entity deliver a file.6369
    • TC[23,16], TC[23,17] and TC[23,18] correspond to CFDP Suspend, Resume and Cancel requests on the transaction behind the operation; TM[23,23] corresponds to what a Report.request returns.66
    • The ST[23] operation ID is chosen by the requester, while a CFDP transaction ID is allocated by the source entity, so an implementation has to keep a table linking the two.2467

    The 2024 draft: ST[24] file transfer and ST[25] file data storage¶

    The Rev.1 DIR1 draft fills the gap. It introduces File Based Operations (FBO) built from communication links, file management systems (ST[23]), file transaction entities using CFDP, downlink managers and data sources. Two new services carry it: ST[24] file transfer, with a CFDP file transaction subservice and a file downlink manager subservice, and ST[25] file data storage, which stores on-board data into files. These subservices need a file management system on board, which implies at least one ST[23] file handling subservice.78

    Files elsewhere in PUS-C¶

    Several other services read or write the files that ST[23] manages:

    Service Requests Use of files
    ST[06] memory management TC[6,19], TC[6,21] load ... by reference; TC[6,20], TC[6,22] dump ... to file memory loads read data from a file (path + offset + length); dumps create a file at the given object path57
    ST[18] on-board operations procedure TC[18,13] load an OBCP by reference; TC[18,19] load by reference and activate the OBCP code is already on board in a file59
    ST[21] request sequencing TC[21,2] load a request sequence by reference; TC[21,8] load by reference and activate the sequence is already on board in a file60

    The standard notes this explicitly: the file management service has no exclusive access, and request sequencing can, for example, load a sequence from an on-board file.8

    What the 2024 Rev.1 draft changes in ST[23]¶

    The draft is under public review and is not yet a standard.71 For ST[23] it proposes:

    • Wildcards in delete: the delete-a-file request may delete several files when wildcards are used in the file name inside one directory, and a locked file is an explicit rejection reason.72
    • Checksum a file: new TC[23,25] checksum a file and report subtype 26, checksum report of a file, with a 16-bit bit-string checksum; the checksum type is mission-specific. The draft's clause 8 heading prints the report as "TC[23,26]" although its text describes a telemetry packet.7377
    • Directory protection: new TC[23,27] and TC[23,28] enable and disable protection, so that a directory cannot be deleted, moved or renamed.7477
    • Repository report: TC[23,12] and TM[23,13] lose the word "summary", and each file entry now carries its attributes.7577
    • Copy and move with wildcards: source file names may contain wildcards; the target name is then ignored.76
    • Atomic requests: suspend, resume and similar multi-instruction requests are rejected as a whole if one instruction is invalid, and valid ones execute in order.76

    Solar Orbiter: file management without ST[23]¶

    Solar Orbiter is a PUS-A mission and has no ST[23]; neither the 2020 nor the 2025 MIB contains any packet or command of type 23.798687 Files exist on board all the same, and the mission handles them with private services.

    Service 133 "File Management" (OBC)¶

    The ICD reserves service 133 for the OBC central software. It manages files in the OBC local storage areas, the OBC Mass Memory (OMM), the Safe Guard Memory (SGM) RAM and the SGM EEPROM. Files carry uplinked command material (OBCPs, TC files, the back-up MTL), profiles and ephemerides, or software patch data; the service manages the files but not the use of their contents.8182 Files are named by a partition ID (1 byte) and a 32-bit file ID instead of character-string paths:81

    Subtype ICD name Application or source data (ICD)
    TC(133,6) Copy File source partition ID, source file ID, destination partition ID, destination file ID
    TC(133,7) Delete File partition ID, file ID
    TC(133,8) Modify File Attributes partition ID, file ID, type, protection
    TC(133,9) Request File Information partition ID, file ID
    TM(133,10) File Information Report partition ID, file ID, address, size, type, protection, mode (closed/open), creation time
    TC(133,11) Request Partition Mapping partition ID
    TM(133,12) Partition Mapping Report partition ID, N, then N × (file ID, address, size)
    TC(133,128) Verify File Checksum partition ID, file ID, expected checksum

    For Copy File the ICD lists the accepted combinations: same name to another partition, new name in the same partition, or new name in another partition. A second list, also headed "accepted" as printed, names the remaining case, same name in the same partition.81

    Both layouts are real: the field order and sizes come from the ICD, and the MIB definitions match them bit for bit. ZCD08506 places its four parameters at bits 0, 8, 40 and 48, and SPID 14319, a 47-byte packet, places its parameters from byte 16 to byte 41, the 6-octet creation time filling the last bytes.8186 Under the PUS-C rule for absolute time, PFC 17 means 4 octets of coarse and 2 of fine time, which agrees with that layout.54

    The MIB calibrations give the actual values:86

    Protection polarity

    The ICD describes the protection field as "0 = Delete Enabled, 1 = Delete Disabled" for TC(133,8) but as "0 = Delete Disabled, 1 = Delete Enabled" for TM(133,10). The MIB simply labels both 0 DISABLED and 1 ENABLED.8186 Which polarity the software implements is not stated in the available sources.

    The MIB holds six service 133 commands, all on APID 172, and two reports on APID 163:86

    Inference

    The file type value FT_PL_CTX ("payload context") fits the Solar Orbiter context-saving service, whose instrument contexts the CSW stores as files in the OMM, reachable through service 133 (see ST[22]).83 Likewise FT_OBCP, FT_DEL_TCSEQ and FT_IMM_TCSEQ fit the OBCP and TC-file uses named in the ICD. The MIB does not document these meanings.

    SSMM packet stores as files (service 15) and file transfer (service 13)¶

    On the Solid State Mass Memory (SSMM) side, the ICD lists private service 15 subtypes 129 to 133 to create, resize, delete, rename and list packet stores on the SSMM, and TM(15,134), the SSMM packet stores list report. The MIB names the same commands "SSMM Create File", "SSMM Resize File", "SSMM Delete File", "SSMM Rename File" and "SSMM List Files" (ZSM00190 to ZSM00210, APID 492) and the report "SSMM List File Report" (SPID 80021, APID 483).8486 Files are moved across the link with private service 13 subtypes. The ICD calls them file transfer sessions and low-level file transfers, with an "End Of File Transfer" timeout; the MIB names the same subtypes with the abbreviations FTS, LLFT and EOFT. The CFDP page describes them.8586

    Inference

    Matching the ICD subtype names with the MIB descriptions suggests that, on Solar Orbiter, FTS stands for "file transfer session", LLFT for "low-level file transfer" and EOFT for "end of file transfer". The MIB itself does not spell out these abbreviations.
