    PUS parameter types (PTC/PFC)¶

    Every field of a PUS packet - a housekeeping value, a command argument, a time tag, even the spare bits - has a type that is identified by two small numbers: the packet field type code (PTC), which says what kind of value the field holds (Boolean, unsigned integer, real, absolute time ...), and the packet field format code (PFC), which says how that value is encoded (how many bits, which floating-point format, which time code).1 The pair is the common vocabulary between the on-board software, the space-to-ground ICD and ground systems such as SCOS-2000, whose MIB stores a PTC and a PFC for every monitoring parameter (PCF) and every command parameter (CPC).5153 This page lists every type and format defined by ECSS-E-ST-70-41C ("PUS-C"), compares them with ECSS-E-70-41A ("PUS-A") and the 2024 Rev.1 draft, and shows what the SCOS-2000 import ICD and the Solar Orbiter database actually use. The MIB-specific view continues on MIB parameter types.

    Why a type code system¶

    PUS-A explains the motivation: the standard does not fix a length or encoding for each field of each packet; instead a mission selects, field by field, the length and encoding that best suit it, and records the choice as a parameter code.22 The tabular notation is a simple alternative to ASN.1, and the encoding rules deliberately differ from the ASN.1 Basic Encoding Rules, mainly because of the limited space-link bandwidth.22 PUS-C keeps the idea but renames the codes: a "packet field code" is the combination of a PTC and a PFC, and the meaning of a PFC depends only on its PTC.1 The scheme is older than ECSS: the ESA PUS of 1994, PSS-07-101, already combined a "Parameter Type Code" and a "Parameter Format Code" into a parameter code, valid for both telecommand and telemetry data (see the history page).33

    Tailoring therefore happens at two moments:1

    • when a mission defines a new message type, it declares the PTC of each of its fields;
    • when a standard message type leaves a format open (for example the length of a parameter identifier), the mission declares the PFC when specifying the application process that uses that message type.

    PUS-A describes four scopes at which such a choice can be made: mission defined (one format everywhere), application process defined, service instance defined, or request/report defined (the format is deduced from preceding fields, possibly together with mission constants).24

    Conventions used in packet structure diagrams¶

    PUS specifies packet contents with structure diagrams: the first row names each field and the second row gives its type. A field marked "optional" is present or absent at mission, application process or service-instance level, and its omission can mean that both ends already know the value (a fixed value, a "current value" set by other means, or a look-up table indexed by earlier fields).2 A group of fields marked "repeated N times" is an array; for a variable-length array, N is carried explicitly in front of the entries, while for a fixed-length array N is a mission constant.2 The Rev.1 draft adds that N is 0 when the array is empty.43

    Bits are numbered from the left: the first, most significant bit of an n-bit field is "Bit 0" and the last is "Bit N-1"; 8 adjacent bits form an octet.3 This is the same convention as CCSDS (see Space Packet Protocol).

    Boolean (PTC 1)¶

    A Boolean field is PTC 1. A value greater than 0 means TRUE and 0 means FALSE. PFC 0 is a 1-bit Boolean; any PFC n > 1 is an n-bit Boolean (for example PFC 8 is an 8-bit Boolean).4 PUS-A defined only the 1-bit form (PFC 0), with 1 = TRUE and 0 = FALSE.26

    Enumerated (PTC 2)¶

    An enumerated value is an unsigned integer that may appear in logical and comparative expressions but not in arithmetic: each value stands for a text meaning, an error code being the typical example (0 "unchecked", 3 "invalid").5 The PFC is simply the length in bits, from 1 to 64.5 PUS-A allowed only the lengths 1-16, 24 and 32 bits.27

    Enumerated is the type of every identifier in the PUS headers: PUS version, acknowledgement flags, service type, message subtype, source ID and destination ID are all enumerated fields (see packet structures).21

    Unsigned integers are encoded with Bit 0 as the most significant bit.6

    Signed integer (PTC 4)¶

    Bit 0 is the sign (0 positive, 1 negative) and negative values are the two's complement of the absolute value.7

    PFC Size Range
    0-12 (PFC + 4) bits \(-2^{PFC+3}\) to \(2^{PFC+3}-1\) (from -8..7 for PFC 0 up to -32 768..32 767 for PFC 12)
    13 3 octets -8 388 608 to 8 388 607
    14 4 octets \(-2^{31}\) to \(2^{31}-1\)
    15 6 octets \(-2^{47}\) to \(2^{47}-1\)
    16 8 octets \(-2^{63}\) to \(2^{63}-1\)

    The signed formats are the same in PUS-A and PUS-C; unlike PTC 3, PTC 4 has no 1-3 bit formats.729

    Real (PTC 5)¶

    PFC Format Size
    1 IEEE 754 single precision 4 octets
    2 IEEE 754 double precision 8 octets
    3 MIL-STD-1750A single precision 4 octets
    4 MIL-STD-1750A extended precision 6 octets

    The four formats are the same in PUS-A and PUS-C.830

    Normal values are \((-1)^{sign} \times 2^{exponent-127} \times 1.fraction\); exponent 255 encodes infinities (fraction 0) and NaN (fraction not 0); exponent 0 encodes zero and denormalized values. Range about \(1.12 \times 10^{-38}\) to \(3.40 \times 10^{38}\) with a precision of about \(1.15 \times 10^{-7}\).9

    Exponent 2 047 encodes infinities and NaN; range about \(2.22 \times 10^{-308}\) to \(1.79 \times 10^{308}\), precision about \(2.22 \times 10^{-16}\).9

    The 1750A formats are a normalized fractional two's-complement mantissa times 2 to the power of a two's-complement exponent: 24-bit mantissa plus 8-bit exponent for single precision, and a 40-bit mantissa split around the 8-bit exponent for extended precision. Zero is all zeros. Real example from the standard: 40 00 00 7F is \(0.5 \times 2^{127}\) and 80 00 00 00 is \(-1.0\).1031

    Bit-string (PTC 6)¶

    A bit-string carries bits whose meaning is application process specific. PFC 0 is a variable-length bit-string; PFC n > 0 is a fixed-length bit-string of n bits.11

    The length field is an unsigned integer whose own PFC is declared per application process.11 Two rules make PTC 6 special:11

    • every spare field of a TM or TC packet is a fixed-length PTC 6 field, and all its bits are zero;
    • the length of a fixed-length bit-string may be deduced, but only from preceding fields of the same packet, from mission constants, or both - never from later fields.

    Inference

    The widths in the diagram above (8-bit length, 24-bit data) are illustrative. The standard leaves the length-field size to the application process declaration.

    Octet-string (PTC 7)¶

    PFC 0 is a variable-length octet-string with the same "length then data" structure as the variable bit-string, the length counting octets; PFC n > 0 is a fixed string of n octets.12 The length-field PFC is declared per application process, and a deduced fixed length may only depend on preceding fields or mission constants.12 As with bit-strings, the meaning of the octets is application process specific;12 the Solar Orbiter examples below show octet strings carrying whole tables, science blocks and embedded commands.

    Character-string (PTC 8)¶

    Character strings hold visible characters, each encoded as its ASCII code on one octet. PFC 0 is variable length (length then characters), PFC n > 0 is a fixed string of n characters.13 The Rev.1 draft makes "visible" precise - the space 0x20 plus the printable characters 0x21 to 0x7E - and requires shorter values to be padded at the end with spaces up to the PFC length.44

    Absolute time (PTC 9)¶

    An absolute time is a positive number of seconds and fractions of a second from an epoch. With CUC, the epoch is either the CCSDS epoch of 1 January 1958 or an agency-defined epoch - in the latter case the field is effectively a free-running counter that the ground converts with time correlation coefficients. CDS always uses the 1958 epoch.14 Both codes are defined in CCSDS 301.0-B-4 (see time code formats); PUS-C notes that CCSDS allows 1-7 octets of coarse time and 1-10 octets of fine time, of which PUS implements coarse time of 1-4 octets and fine time of 1-10 octets.14

    PFC Encoding Length
    0 explicit format, P-field included (CUC or CDS) variable
    1 CDS, 2-octet day, no microseconds 6 octets
    2 CDS, 2-octet day, with microseconds 8 octets
    3-18 CUC: coarse = (PFC + 1) div 4 octets, fine = (PFC + 1) mod 4 octets; implicit P-field 1-7 octets
    19-46 CUC: coarse = (PFC - 12) div 7 octets, fine = 4 + (PFC - 12) mod 7 octets; implicit P-field 5-14 octets

    The rows paraphrase PUS-C Table 7-10.15 PUS-A had PFC 0-18 with the same meanings; PFC 19-46 (fine time of 4-10 octets) are new in PUS-C.32

    For PFC 18 the time is \(t = C_1 256^3 + C_2 256^2 + C_3 256 + C_4 + F_1 256^{-1} + F_2 256^{-2} + F_3 256^{-3}\) seconds from the epoch.15

    Decoding a CUC value (illustrative bytes)

    The six octets 1E 2C 9A 00 80 00 read as PTC 9, PFC 17 give coarse time 0x1E2C9A00 = 506 239 488 s and fine time 0x8000 / 65 536 = 0.5 s, so the value is 506 239 488.5 s after the mission epoch. The bytes are invented for illustration.

    Relative time (PTC 10)¶

    A relative time is a positive or negative offset in seconds and fractions from an event identified by other fields, or the difference between two absolute times. Negative offsets are the two's complement of the positive offset.16

    PFC PUS-A (2003) PUS-C (2016) Rev.1 DIR1 (2024 draft)
    0 explicit CUC, P-field included - -
    1 CUC 1 coarse, 0 fine - CDS without microseconds, 6 octets
    2 CUC 1 coarse, 1 fine CDS with microseconds, 8 octets CDS with microseconds, 8 octets
    1-16 (PUS-A) coarse = (PFC + 3) div 4, fine = (PFC + 3) mod 4 - -
    3-18 (PUS-A meanings continue up to 16) CUC, coarse = (PFC + 1) div 4, fine = (PFC + 1) mod 4 same as PUS-C

    Sources: PUS-A clause 23.5.10, PUS-C Table 7-11 and Rev.1 DIR1 Table 7-11.351645 In the full 7-octet CUC form, a positive offset has C1 in the range 0-127, leaving the sign bit free.16

    Inference: the relative-time renumbering

    The two formulas mean that a PUS-A relative-time format n equals the PUS-C format n + 2: PUS-A PFC 1 (1 coarse octet) is PUS-C PFC 3, and PUS-A PFC 16 (4 + 3 octets) is PUS-C PFC 18. PUS-C thereby aligns the relative-time CUC numbering with the absolute-time numbering. Anyone converting a PUS-A interface document into a ground database must therefore not copy relative-time PFC values blindly.

    Deduced (PTC 11)¶

    A deduced field (PTC 11, PFC 0) has a structure and format that is worked out from preceding fields of the same packet, from mission constants, or both; the rule must be declared when the field is specified.17 PUS-A illustrates it with a pair "Parameter#" (enumerated) followed by "Parameter Value" (deduced): the value field changes type from packet to packet according to the parameter identifier in front of it.36 Ground databases use the same idea for generic reports that carry values of arbitrary parameters, for instance the value of a parameter that failed an ST[12] monitoring check (see the Solar Orbiter examples below).

    Packet (PTC 12)¶

    PTC 12 carries a whole packet inside a field: PFC 0 is a CCSDS telemetry packet and PFC 1 a CCSDS telecommand packet, both compliant with PUS.18 For example, TC[11,4] "insert activities into the time-based schedule" of ST[11] carries an optional sub-schedule ID and a count N, followed by N instructions, each an optional group ID, a release time (absolute time) and the request itself as a "TC packet" field,19 and TC[21,1] of ST[21] loads a sequence of "TC packet" fields each followed by a relative-time delay.20 PUS-A had no PTC for this; its structure diagrams simply used the abbreviations "Any TC" and "Any TM".42

    Structured fields¶

    Simple types are combined into structures. PUS-A formalised this as structure rules set #1:37

    • a record is a fixed sequence of distinct components (simple or structured);
    • an array repeats one component; a fixed array repeats it an implicit number of times, a variable array is preceded by an unsigned integer D giving the number of entries;
    • a deduced structure is one component whose type is chosen by "determining parameters" (preceding fields or mission constants), which may only be Boolean, enumerated, integer or character-string values, or themselves deduced.

    PUS-A added six nesting and identification rules (NIR1-NIR6): fields outside any array are at level 1 and array components one level deeper; a concrete parameter may be named only once, at level 1 or 2, unless each extra occurrence has a specialised meaning (NIR5); and the last determining parameter must sit at the level of the structure it determines or one level above, the first one at level 1 or 2.39 Encoded fields are packed bit-aligned one after the other, with optional zero padding to reach a mission word boundary.4024

    flowchart TB
  R["Record Ra (level 1)"] --> P1["Records Rb, Rc<br/>Pa .. Pd"]
  R --> FA["Fixed array FAa<br/>n entries known implicitly"]
  R --> VA["Variable array VAa<br/>D entries, D given explicitly"]
  R --> RD["Record Rd<br/>Ph, Pi"]
  FA --> RE["Record Re (level 2)<br/>Pe, Pf"]
  VA --> RF["Record Rf (level 2)<br/>Pg"]

    The solid part of the diagram follows the second example of PUS-A clause 23.6.5; the dashed deduced structure S is added from the example of clause 23.6.4, where S is a variable array, a record A or a record B depending on a preceding parameter P.4140 PUS-C expresses the same ideas with "repeated N times" arrays and PTC 11 deduced fields instead of a separate set of structure rules.217

    The 2024 draft adds a requirement that fixes the size of common elements "to ensure inter-operability of PUS-C implementations from different providers".46 Its Table 7-13:

    Collection interval 4 bytes
    Parameter ID, event ID 4 bytes each
    Housekeeping report structure ID 2 bytes
    Memory ID 2 bytes
    Memory start address, register address, memory bit-mask 4 bytes
    Sub-schedule ID, group ID 2 bytes each
    PMON ID, FMON ID 2 bytes each
    APID 2 bytes (11 bits in the primary header)

    OBCP ID 2 bytes
    CPDU ID 1 byte
    CFDP entity ID 2 bytes
    CFDP transaction sequence number 4 bytes
    Data source ID 2 bytes

    The rows restate DIR1 Table 7-13.46 Until the revision is published, these sizes are a proposal; PUS-C (2016) leaves them to each mission.

    PTC/PFC in SCOS-2000¶

    The SCOS-2000 Database Import ICD lists, in its Appendix A, every PTC/PFC combination the importer accepts and how it is held internally. It refers to the original ESA PUS, ESA PSS-07-101 (1994), as its PUS reference.4750 Monitoring parameters store their type in PCF_PTC (range 1-13) and PCF_PFC, command parameters in CPC_PTC and CPC_PFC.5153

    PTC PFC accepted by SCOS-2000 Internal type Restrictions and extensions
    1 0 unsigned integer, 1 bit -
    2 1-32 unsigned integer only limit is 32 bits
    3 0-14 unsigned integer PFC 15 and 16 (48 and 64 bits) not supported
    4 0-14 signed integer PFC 15 and 16 not supported
    5 1, 2, 3, 4 real PFC 4 (1750A extended) only for command parameters, from R3.0
    6 1-32 unsigned integer PFC 0 not supported; monitoring side only
    7 0, n octet string PFC 0 only for command/sequence parameters
    8 0, n ASCII string PFC 0 only for command/sequence parameters
    9 1, 2, 3-18, 30 absolute time PFC 0 not supported; PFC 1 from R5.0; PFC 2 only for commands; PFC 30 = Unix time (SCOS-2000 extension)
    10 3-18 relative time CUC only
    11 0, n > 0 deduced PFC > 0 forces a fixed width, command parameters only
    13 0 saved synthetic parameter SCOS-2000 extension, characteristics taken from PCF_RELATED

    Sources: ICD 7.0 Appendix A, Table 4, the PCF/CPC field descriptions, and the summary of exceptions in Appendix C.4748515349 The bold values are not defined by the PUS. The PCF_WIDTH field lets a monitoring parameter occupy a padded slot wider than its PTC/PFC implies, which matters for variable packets and deduced parameters.52

    Inference: where SCOS-2000 and PUS-C disagree

    • PTC 9 PFC 30: SCOS-2000 uses it for Unix time (4 octets of seconds since 1970 plus 4 octets of microseconds), described as "Not defined in PUS".48 The ICD's PUS reference is ESA PSS-07-101,50 which, like PUS-A, defines absolute-time PFCs only up to 18 (in PSS-07-101: 0 a full definition with P-field, 1 and 2 CDS, the higher codes CUC),3432 but PUS-C assigns PFC 30 to a CUC code of 2 coarse and 8 fine octets.15 A PUS-C mission that needs that CUC format cannot express it with this code in an ICD 7.0-compliant SCOS-2000 database.
    • PTC 3 PFC 17-19, PTC 9 PFC 19-46, PTC 12 are absent from the ICD 7.0 table. Whether later SCOS-2000 releases accept them is not stated in the available sources.
    • PTC 10: SCOS-2000 numbers relative CUC times with the absolute-time formula (PFC 3-18), i.e. the PUS-C numbering, not the PUS-A one (see the relative-time inference above).

    SCOS-2000 also defines special command parameter types that build PUS requests more easily: Command ID parameters (CPC_CATEG = A, PTC 7 PFC 0) are filled with the raw encoding of another command; Parameter ID parameters (CPC_CATEG = P, PTC 3) receive the on-board identifier of a telemetry parameter; and Deduced command parameters (PTC 11) inherit type, width and calibration from the TM parameter named by the preceding Parameter ID.54 Configuration variables must be 32-bit signed integers (PTC 4, PFC 14), double-precision reals (PTC 5, PFC 2) or character strings (PTC 8).55

    Observations from the same queries:5758

    • Reals are almost all IEEE single precision: 28 316 of the 29 718 real monitoring parameters are PTC 5 PFC 1, and 630 of 702 real command parameters. No MIL-STD-1750A format is used.
    • Time: 2 116 absolute-time parameters are PFC 15 (4-octet CUC seconds) and 1 677 are PFC 17 (4 + 2 octets, the packet time stamp format). Two parameters of the "Time Correlation Report" packet (SPID 66840, type 164, APID 1966) use the SCOS-2000 Unix format PFC 30 (NYG02101 "Period From" and NYG02102 "Period To"), and one uses CDS with microseconds, NYG02204 "GS Acceptance Time" (see the inference box below).
    • No PTC 12 and no PFC beyond the ICD 7.0 table appear: unsigned integers stop at PFC 14, absolute CUC times at PFC 17.
    • Deduced parameters are the value fields of generic on-board reports, for example NCD0C0B5 "OBCHP_S12_Par value", whose type follows the parameter identifier NCD0C095 given in PCF_RELATED. It is placed in eight fixed event packets (SPIDs 66652-66659, TM(5,3) "RW Mom Lvl Check" reports on APIDs 1964 and 1973) and in 1 431 variable-packet (VPD) structures.
    • Saved synthetic parameters (PTC 13): NTTSS030 and NTTSS031 ("Last C_Lock DST-½"), derived from the synthetic parameters NTTSX030 and NTTSX031. The April 2020 release had none (it had 102 104 PCF records and no PTC 13).60 See synthetic parameters.
    • Variable-length strings appear only on the command side: 13 command parameters are PTC 7 PFC 0 and one is PTC 8 PFC 0, as the ICD requires.48
    • Long fixed octet strings (up to PFC 6448, i.e. 6 448 octets) hold whole tables and science blocks as single parameters, for example NCAMBP00 "SSE segments" (6 448 octets) and NIM02004 "1920 Science" (4 048 octets).

    Inference

    NYG02204 is a monitoring parameter (PCF_NATUR = R) of type PTC 9 PFC 2, a combination that ICD 7.0 says is supported only for command parameters.48 It belongs to a packet that, judging by its description, is produced by the ground segment; whether the SCOS-2000 release used by Solar Orbiter accepts it for monitoring is not stated in the available sources. The packet is SPID 66850, "TM Packet used by the Releaser G/S response" (type 165, subtype 1, APID 1966). APID 1966 also carries packets described as "MISC_PACKET", "Saved Synthetics", "Time Correlation Report" and "TCO Time_Couples", so the PFC 30 and PFC 2 time parameters most likely belong to packets generated by SCOS-2000 on ground rather than to spacecraft telemetry.

    A real command: time-tagging with PTC 9 and PTC 7¶

    The command ZCD00B04, TC[11,4] "Insert Telecommands in Command Schedule", shows four types working together. Its application data, as defined in the CDF and CPC tables, is:59

    CDF_BIT Parameter Description PTC/PFC Size
    0 PCD0B041 Sub_schedule Identifier ¾ 8 bits
    8 PCD0B042 Nb TCs to add in Sub-Sch (repeat counter, group size 2) ¾ 8 bits
    16 PCD0B043 Time Tag 9/17 48 bits (CUC 4 + 2)
    64 PCD0B044 Complete TC packet (Command ID, CPC_CATEG = A) 7/0 variable

    The repeated group (time tag plus embedded packet) is the PUS-A equivalent of a "repeated N times" array, and the embedded command is a variable octet string filled by SCOS-2000 with the encoding of another command - the role PTC 12 plays in PUS-C. Event-action definitions such as ZCS01301 (TC[19,1]) use the same Command ID mechanism with PCD13013 "TC to send upon event".59 Explore it in the MIB explorer.

  FROM cpc GROUP BY 1 ORDER BY CAST(CPC_PTC AS INT);
