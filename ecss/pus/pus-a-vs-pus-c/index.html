    ECSS PUS PUS-A PUS-C Standards history

    PUS-A vs PUS-C (and the 2024 Rev.1 draft)¶

    Three generations of the Packet Utilization Standard are in use or in preparation today: PUS-A (ECSS-E-70-41A, 30 January 2003), flown by many ESA missions of the 2000s and 2010s; PUS-C (ECSS-E-ST-70-41C, 15 April 2016), the current standard; and Rev.1 DIR1 (ECSS-E-ST-70-41C Rev.1, 11 December 2024), a draft distributed for public review.153 Behind them stands the ESA PUS, ESA PSS-07-101 Issue 1 of May 1994, whose packets carry PUS version number 0 and from which PUS-A inherited most of its structure and numbering.114111 A ground segment often has to support more than one of these, so the differences matter in practice: the same service number can mean different things, the same field can have a different size, and the same PFC value can encode a different time format. This page compares the documents clause by clause. The bit-level PUS-A and PUS-C header details are on PUS packet structures, the data types on PUS parameter types, and the wider history of the ESA packet standards on From ESA PSS to CCSDS and ECSS.

    Before PUS-A: ESA PSS-07-101 (1994)¶

    PUS-A did not start from a blank page. Its direct ancestor, ESA PSS-07-101 Packet Utilisation Standard, Issue 1 (May 1994), was prepared by ESA's Committee for Operations and EGSE Standards (COES), set up in 1987 to define a monitoring and control system common to satellite checkout and mission control, and it was approved by the ESA Inspector General after an Agency-level review in 1993.114139142 Why it was written, how a prototype validated it and how XMM tailored it first are told on the PUS overview. This section compares its content with its successors.

    Source note: a scanned standard

    PSS-07-101 exists here only as a scanned PDF. This wiki read it through OCR text, which contains recognition errors, merged words and scrambled table layouts, and checked every field size, bit position, value and subtype number quoted on this page against the rendered page images. The same applies to the two 1994 conference papers on NTRS.

    Concepts in 1994¶

    The 1994 vocabulary is already close to PUS-A's. A Service is a set of on-board functions with conceptually related capabilities that a ground system controls and monitors through Service Requests and Service Reports; a report that only returns requested data is a Service Response, every other report a Service Indication. The Service Provider is the on-board application process that executes the service, the Service User is the ground system, and a Supporting Service is one used only in the context of another service.121122 Three criteria selected the standard services: commonality (functions many missions need), coherence (strongly related capabilities with an unambiguous scope and minimal interaction with other services) and implementation independence (no assumed on-board architecture).120 One rule differs from today's model: a service cannot be split across application processes, although one process may host several services and, where permitted, several processes may host distinct instances of a service.121 PUS-C instead deploys services subservice by subservice: each subservice has exactly one provider, each subservice entity is hosted by an application process on board or on ground, and an application process hosts at most one provider of a given subservice type.106

    The 1994 document puts operational requirements first (chapter 3, each with a mnemonic such as TC-1 or TRAFF-1 and with mission parameters in angle brackets) and then one chapter per service with its scope, concept, requests and reports and capability sets; it ends with the summary of requests and reports in chapter 22 and the parameter types in chapter 23 - the same clause numbers that PUS-A kept.11711911639

    The 1994 packet headers¶

    PSS-07-101 takes the packet header from the ESA packet telemetry (PSS-04-106) and telecommand (PSS-04-107) standards and standardises the start of the packet data field, the data field header. In both directions it has the same 24-bit core; telemetry adds an optional time field. The 1994 paper presenting the standard prints the same two layouts.124125127140

    PUS version number 3 bits Only version 0; a new version was foreseen for telemetry packets carrying more than one service data unit.125127
    Checksum type 1 bit Selects the packet error control algorithm: ISO 16-bit checksum (0) or CRC (1). In telemetry, 0 can also mean that no check is included.125127
    Ack (TC only) 4 bits Which success reports the application process sends, one bit per stage; failure reports are always sent. 1111 means at least four verification steps are expected.125

    Service type, subtype 8 + 8 bits Unique across all application processes; on ground their combination may set the processing priority (TM).125127

    The packet header around this core also differs from later practice:124126

    • telecommand packets have version number 0, but telemetry source packets have "version 2", coded as the value 4 (0b100); PUS-A and PUS-C use 0 for both;46109
    • the 14-bit telecommand sequence count is split: its <NUM_SOURCE_BITS> most significant bits carry a source ID (for example, one per ground control centre; zero bits if there is a single source) and the rest a sequence count kept per source and per APID - PUS-A moved the source ID into an optional data field header field, PUS-C made it a 16-bit field;454
    • telecommand sequence flags are always 11 for ESA missions and telemetry "segmentation flags" are always 11 (unsegmented);
    • the telecommand packet error control field (16 bits) is mandatory, and the largest telecommand packet is 65 542 octets; the telemetry error control field is optional.124127

    The CRC of Appendix A.2 is the one still used today: generator polynomial \(x^{16} + x^{12} + x^5 + 1\), encoder and decoder initialised to all ones, computed over the whole packet except the error control field; PUS-C Annex B specifies the same CRC-16-CCITT.137110 For the PUS-A and PUS-C fields see Packet header changes below and PUS packet structures.

    Inference: reading the first four bits

    In PSS-07-101 the first data-field-header bits are the 3-bit version 000 followed by the checksum-type bit; PUS-A starts with a 0 flag bit followed by the 3-bit version 001; PUS-C has a 4-bit version 0010.125454 Read as one 4-bit number, a PSS-07-101 telecommand using a CRC therefore shows the same value (1) as a PUS-A packet. A decoder that must tell the ESA PUS from PUS-A cannot rely on these bits alone and needs mission knowledge. The multi-SDU telemetry version foreseen in 1994 (and again in PUS-A) does not appear in PUS-C, whose version 2 simply identifies ECSS-E-ST-70-41C.

    Inference

    Because of this continuity, a decoder written for PUS-A and keyed on (type, subtype) would find the same message types in a mission built to the 1994 PUS for services 1, 4, 5, 6, 13 and 17 and for most of services 3 and 12. The differences that matter are the sampling-time-offset, masked/unfiltered and out-of-limit/check-transition subtypes of services 3 and 12, services 2, 7-11 and 14-16, and the headers above.

    Parameter types in 1994¶

    PSS-07-101 already uses the parameter code made of a parameter type code (PTC) and a parameter format code (PFC), with eleven PTCs: Boolean (1), enumerated (2), unsigned (3) and signed (4) integer, real (5), bit string (6), octet string (7), character string (8), absolute time (9), relative time (10) and deduced (11). Packet structures follow a single "structure rules set number 1" of records, fixed and variable arrays and "choice structures" (whose type is deduced from preceding fields, a deduced parameter being a special case), and each mission selects the physical format of each field by giving its parameter code.133134136 Notable details:

    • enumerated parameters may be 1, 2, 4, 8, 12, 16, 24 or 32 bits long (PUS-A: 1-16, 24, 32; PUS-C: 1-64), and unsigned integers use PFC 0-16 as in PUS-A;13451
    • absolute and relative time share one format table: PFC 0 is an explicit format with P-field, PFC 1 and 2 are CDS without and with microseconds (absolute time only), and PFC 3-18 are CUC with (PFC + 1) div 4 octets of coarse time and (PFC + 1) mod 4 octets of fine time;135
    • the time code reference is the CCSDS time code format CCSDS 301.0-B-1 together with a planned ESA time code standard, PSS-04-202, "not available before mid 1995".115

    Inference: where SCOS-2000 got its relative-time numbering

    PUS-A renumbered relative time (PFC 1-16 with (PFC + 3) div 4 coarse octets), and PUS-C went back to PFC 3-18 with (PFC + 1).11322 The SCOS-2000 Database Import ICD 7.0 lists ESA PSS-07-101 as its PUS reference (RD-6) and numbers relative CUC times like PSS-07-101: PTC 10 PFC 4 is 1 coarse plus 1 fine octet.106158 SCOS-2000's relative-time numbering is therefore most likely inherited from the 1994 standard rather than borrowed from PUS-C. See parameter types.

    Why PUS-C was written¶

    The PUS-C change log gives five reasons for replacing issue A: remove its deficiencies and inject lessons learned, meet the needs of future missions, acknowledge newer ECSS and CCSDS standards, apply the ECSS drafting rules (for example naming every requirement for tailoring and traceability), and keep backward compatibility when possible.1 By January 2011 the working group had collected 190 change requests.92 At the 2014 SAVOIR Mass Memory Day the convenor listed the planned service types, still showing large data transfer (ST13) and a new "large packet transfer" (ST24) as "TBC", and the options under study for transferring data larger than one packet.8788 The final standard kept number 13 for a simplified "large packet transfer" that only moves packets of up to about 65 KB, without retransmission.98

    Service-by-service changes from PUS-A to PUS-C¶

    The message names below are those of PUS-A clause 22 and PUS-C Annex C and clause 8.5023 Where PUS-C kept a subtype number, the meaning is usually close; where a number disappears, the function was redesigned.

    ST[01] request verification¶

    Subtype PUS-A PUS-C
    1-8 TC acceptance, execution started, execution progress and execution completed reports, each success and failure successful/failed acceptance, start, progress and completion of execution verification reports
    10 - failed routing verification report

    PUS-C adds a routing and reporting subservice for the on-board routing of requests and its failure report TM[1,10].2417 PUS-A listed standard acceptance failure codes (0 illegal APID, 1 invalid length, 2 incorrect checksum, 3 illegal type, 4 illegal subtype, 5 illegal or inconsistent application data);48 PUS-C instead asks each request type to declare an execution verification profile with its own codes and failure parameters.13 See ST[01].

    ST[02] device access¶

    PUS-A had three requests: distribute on-off commands (2,1), register load commands (2,2) and CPDU commands (2,3).50 PSS-07-101 had a fourth, (2,4) "distribute command in TC segment", for hardware commands carried at telecommand segment level that need no software to execute, for example to unblock or reset the on-board packet assembly controller; PUS-A dropped it.132141 PUS-C keeps (2,1) and (2,2), moves CPDU commands to TC[2,4], and adds register dumps (TC[2,5], TM[2,6]) and physical and logical device commanding and data acquisition (TC[2,7]-TM[2,12]); subtype 3 is no longer used.25 The 2015 presentation lists these as new capabilities for register acquisition, software-distributed CPDU commands and low-level device commands.95 See ST[02].

    Inference

    The subtype numbers line up: PUS-A's base-plus-offset messages (1, 3, 4, 7, 8) became PUS-C's object memory messages and its absolute-address messages (2, 5, 6, 9, 10) became raw memory messages. A ground system decoding by subtype number alone would still find the right report family, but the field layouts of clause 8.6 differ from PUS-A clause 11.

    ST[08] function management and ST[09] time management¶

    ST[08] is unchanged in substance: PUS-A "Perform Function" (8,1) and PUS-C TC[8,1] "perform a function".5029 ST[09] keeps TC[9,1] (change / set the time report generation rate) but splits PUS-A's single time report (9,2) into TM[9,2] "CUC time report" and TM[9,3] "CDS time report", of which a mission provides exactly one.502921 Both services were larger in 1994: PSS-07-101 function management had "activate", "de-activate" and "perform activity of function" (8,1)-(8,3), and the time report was a separate service 10, so service 9 only changed the time report generation rate.132 See ST[08] and ST[09].

    ST[11], ST[21] and ST[22]: scheduling split in three¶

    The PUS-A "on-board operations scheduling service" was "completely re-assessed" into three service types: time-based scheduling (ST[11]), telecommand - later "request" - sequencing (ST[21]) and orbit-position-based scheduling (ST[22]).97 ST[11] keeps the first four subtypes (enable, disable, reset, insert) and the detail and summary reports TM[11,10] and TM[11,13], adds sub-schedules and groups (subtypes 18-27), and reuses subtype 19 for a sub-schedule status report where PUS-A had a "Command Schedule Status Report".5030 The report numbers 10 (detailed) and 13 (summary) and the first four request subtypes already had these roles in the 1994 "onboard scheduling service", which also allowed a command to be interlocked to the success or failure of an earlier one.132141 See ST[11], ST[21] and ST[22].

    ST[14] forwarding and ST[15] storage¶

    PUS-A ST[14] enabled and disabled the forwarding of whole packet classes (TM source, housekeeping, diagnostic, event report packets).50 PUS-C ST[14] manages forward-control configurations: add or delete report types per application process, housekeeping and diagnostic structure identifiers, and event definitions to block.33 The 2015 presentation says the service was "completely remodelled" to keep service types independent.100 PUS-C ST[15] keeps the two subservices (packet selection, storage and retrieval) but redefines them around packet stores that can be created, deleted, resized and copied, with open and by-time-range retrieval.5034 See ST[14] and ST[15].

    New in PUS-C: ST[20] and ST[23]¶

    Reserved numbers and mission-specific collisions¶

    PUS-C reserves service types 7, 10 and 16 because they were used in earlier versions of the standard, while allowing existing implementations to be reused.2 The earlier version is PSS-07-101: 7 was task management (start, stop, suspend, resume and abort on-board software tasks, in many missions only for contingencies), 10 the time reporting service carrying the spacecraft time packet, and 16 on-board traffic management, meant for on-board routing (for example APID to MAP mapping), packet assembly controller reports, packet bus load and retransmission statistics, and ground control of traffic problems, but never given any subtypes.128132131141 PUS-A already listed all three as "not used".47 Missions designed to PUS-A sometimes used numbers in the standard range for their own services. Solar Orbiter, whose applicable PUS is ECSS-E-70-41A, defines:103104

    20 Information distribution (incl. TC(20,128) inter-instrument communication) parameter management
    21 Science data transfer request sequencing
    22 Context saving position-based scheduling

    All four are present in the 2025 Solar Orbiter MIB: 5, 17, 33 and 6 commands, and 0, 0, 334 and 1 telemetry packet definitions respectively.108 Solar Orbiter also numbers its CPDU command as TC(2,3), the PUS-A subtype, where PUS-C uses TC[2,4].10525

    Inference

    A ground system that serves several missions cannot interpret a service type number without knowing the mission's PUS edition and tailoring. The 4-bit PUS version field (1 for PUS-A, 2 for PUS-C) identifies the edition, but not the mission-specific use of standard-range numbers. Solar Orbiter's service 16 also carries the name of the 1994 service 16, "Onboard Traffic Management", and its requests TC(16,1)-TC(16,5) set the MilBus configuration and switch the bus and its remote-terminal channels between nominal and redundant, close to the 1994 scope of on-board routing and bus control. This suggests that the mission or its platform reused the PSS-07-101 number and name for a function PUS-A had dropped, but no source in this library says so.159131

    What the 2024 Rev.1 draft proposes¶

    ECSS-E-ST-70-41C Rev.1 DIR1 is a draft for public review (12 December 2024 to 28 February 2025) and "may not be referred to as an ECSS Standard until published as such".53 Its change log repeats the PUS-C goals - remove deficiencies, meet future missions' needs, stay consistent with ECSS and CCSDS, apply drafting rules - and adds consistency with the foundation model. It lists the main changes:54

    • evolution of the request verification approach (ST[01]);
    • evolution of housekeeping reporting (ST[03]);
    • deletion of a service not used in current and future missions: ST[08] function management;
    • standardization of services used in current and future missions: ST[26] parameter extraction and ST[27] critical packet log management;
    • standardization of services for file based operations: ST[24] file transfer and ST[25] file data storage;
    • configuration policies formalised as requirements for the applicable services.

    PUS-C in practice: tailoring and tooling¶

    Two ESA activities give a practitioner's view of the PUS-A to PUS-C step. The Generic OIRD talk of 2019 calls PUS-C "a major step forward compared to PUS-A": a solid foundation model, clear and extensive system requirements in which the behaviour of each service type and its requests is (almost) unambiguous, an interface definition separated from the system requirements, and new service types and subservices such as file management and housekeeping functional reporting.149 The same talk counts what that thoroughness costs - 20 service types, 33 subservices, 316 message types of which 88 are mandatory (this wiki's own count of the clause 8 headings is 318, 81 of them "minimum" in Annex C; see the message type catalogue),23 and 382 "shall be declared" options - and concludes that ESA missions need one common PUS-C tailoring, which the GOIRD provides.150151 The 2020 PUSCGen study, which rebuilt PUS-C from its foundation model in a database, raised 21 change requests (7 major) and showed that the standard can be regenerated and tailored automatically and turned into ASN.1/ACN definitions from which ESA's ASN1SCC compiler generates encoders and decoders.154155156 Both are described on the PUS overview, under the Generic OIRD and tooling built on the foundation model.

    The contrast with the 1990s is instructive. In 1994 XMM selected services from the draft PUS and gave them its own type numbers (periodic housekeeping as TM type 1, telecommand verification as TM type 3, time-tagged commands as type 7), a process its author called "missionisation".143144 Twenty-five years later the GOIRD aims for the opposite: a single selection of services, subtypes and capabilities shared by all new ESA missions, with mission OIRDs limited to deltas, constants and sizing.151148

    Practical consequences¶

    Inference

    • Ground databases are edition-specific. Header sizes (PID_DFHSIZE and the PCDF header definitions), service numbering and PFC values all change between PUS-A and PUS-C. Solar Orbiter's MIB, for example, defines a 4-octet PUS-A TC data field header and a 10-octet TM data field header (see packet structures).
    • SCOS-2000 documentation predates PUS-C. The Database Import ICD 7.0 (2017) still refers to the ESA PUS PSS-07-101 for data types and quotes PUS-A section numbers for service support, and it uses PTC 9 PFC 30 for Unix time where PUS-C defines a CUC format (see parameter types).106107 Reading PSS-07-101 alongside the ICD explains some SCOS-2000 conventions, such as its relative-time PFC numbering and the 4-octet telecommand identification at the start of verification reports, which the 1994 standard already defines (see above).135129
    • Migrating to PUS-C or Rev.1 is less about new services than about identifiers: the 16-bit source and destination fields, the message type counter, the time reference status and, in Rev.1, APID-based addressing all have to be reflected in the MIB and in on-board routing.
