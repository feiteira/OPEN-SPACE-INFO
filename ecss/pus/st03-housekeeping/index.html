    ECSS Housekeeping MIB PUS Service 3 Solar Orbiter Telemetry

    ST[03] Housekeeping¶

    Housekeeping telemetry is the steady stream of temperatures, voltages, currents, modes, counters and status flags that tells the ground what state the spacecraft is in. Service type 3 of the Packet Utilization Standard defines how an on-board application process assembles such on-board parameters into periodic reports, how the ground creates, changes, enables and disables those report definitions, and how it asks for one-shot snapshots. A second, parallel set of reports, the diagnostic reports, serves anomaly investigation with fast, temporary sampling. PUS-C adds a third layer, parameter functional reporting, that switches whole sets of reports at once on mode changes.123 This page covers every concept, request and report of ECSS-E-ST-70-41C, the very different PUS-A service with its filtered mode and sampling-time offsets, the categories of the 2024 Rev.1 draft, and the full decoding chain in SCOS-2000, with real Solar Orbiter packets from the MIB.

    Where this page sits

    The packet headers around a housekeeping report are on PUS packet structures; the parameter encodings are on PUS parameter types. How SCOS-2000 describes parameters and packets in general is on Monitoring in the MIB. Whether a generated report actually reaches the ground is decided by ST[14] Real-time forwarding control and, for stored data, ST[15] On-board storage and retrieval.

    2. Concepts¶

    2.1 Report structures and their identifier¶

    A housekeeping parameter report structure is the on-board definition of one kind of report. It consists of an identifier, a collection interval, an ordered list of simply commutated parameters, an ordered list of super commutated parameter sets and, if the subservice can enable and disable reports, a periodic generation action status.5 The structure is identified by the combination of the hosting application process and the structure identifier,5 traditionally called the SID (structure identification) in PUS-A, where the ground uses it together with the APID and the report's nature (housekeeping or diagnostic) to interpret the content.54 A diagnostic parameter report structure has the same elements, except that its status field is always present.17

    The on-board resources available for structures (how many, how many parameters) and for evaluating them at the same time are declared when the subservice is specified.5 Structures may be predefined on board or created on request, and the standard assumes that all of them, including predefined ones, can be deleted, appended to and re-timed.191213

    2.2 Collection interval and sampling interval¶

    The collection interval of a structure is the interval at which its parameters are collected and one report is generated. It is expressed in units of the minimum sampling interval of the on-board parameters.25 Each on-board parameter has a spacecraft-wide unique identifier and is associated with exactly one minimum sampling interval; all parameters accessed by one application process share the same interval, and different subsystems may use different ones (the standard's example is 125 ms for the platform and 500 ms for a payload).30 The sampling interval of a parameter, by contrast, belongs to the application process that acquires or computes its value.2

    2.3 Simply and super commutated parameters¶

    A simply commutated parameter contributes one sampled value per report. A super commutated parameter contributes several values, sampled at a sub-period equal to the collection interval divided by the super commutated sample repetition number. Each parameter appears only once in a structure, in one of the two forms.2 Super commutated parameters come in sets, and the samples are interleaved by set: for a set of A and B with two samples, the report contains A1, B1, A2, B2.6 If the sub-period is shorter than the update period of the on-board value, some samples are identical.6

    For a real example of the timing, see the Solar Orbiter AOCS diagnostic report in section 9.7: a 2 s collection interval with 16 samples, so one sample every 125 ms.97

    2.4 Periodic generation and its status¶

    When the periodic generation of a structure is enabled, the subservice generates one report per collection interval, collecting one value of each simply commutated parameter and all samples of each super commutated parameter during that interval.6 A newly created structure always starts disabled.8 If a housekeeping subservice offers no enable/disable capability, its reports are always enabled.5 Clause 6.3 of PUS-C does not state whether predefined structures start enabled or disabled; the Rev.1 draft makes the start and restart configuration policy a declaration of the subservice.49

    2.5 Housekeeping versus diagnostic¶

    The two reporting subservices provide "similar functions": housekeeping for nominal operations, diagnostic for contingency operations. A diagnostic report type can be enabled when a particular anomaly occurs and disabled at other times.2 PUS-A calls the scenario "diagnostic mode", a selected set of parameters sampled at a higher rate than normal, and says it was previously known as "dwell mode" or "oversampling mode".69 It also explains why the reports are distinct even though they work the same way: the different subtypes let them be routed, stored and processed separately.5769

    2.6 Parameter functional reporting¶

    The parameter functional reporting configuration subservice controls the reports of the housekeeping and diagnostic subservices of its own service, for example on mode transitions.320 A parameter functional reporting definition has an identifier and a list of entries; each entry names a report structure (by optional APID when the service is distributed over several application processes, by its nature as housekeeping or diagnostic, and by its identifier) together with the status and collection interval to apply.21 Applying a definition can be exclusive: all reports of the service are disabled first.322

    3. The housekeeping reporting subservice¶

    Every request of the subservice follows the same pattern. Rejected instructions (or, for single-instruction requests, rejected requests) produce a failed start of execution notification, which reaches the ground as a TM[1,4], and the valid instructions of a multi-instruction request are executed regardless of the faulty ones.79

    Capability Request Instructions Rejected if Effect

    Delete TC[3,3] one or more unknown identifier; status enabled structure deleted
    Enable TC[3,5] one or more unknown identifier status enabled
    Disable TC[3,6] one or more unknown identifier status disabled
    Report structures TC[3,9] one or more unknown identifier one TM[3,10] per valid instruction
    One-shot TC[3,27] one or more unknown identifier one TM[3,25] per valid instruction

    Report generation properties TC[3,33] one or more unknown identifier one TM[3,35] holding all notifications

    Three details are easy to miss:

    • Report structures answers each instruction with its own TM[3,10], while report generation properties puts all answers into a single TM[3,35].1014
    • One-shot reports of structures with super commutated parameters are not specified: the content of the super commutated part is implementation dependent.11
    • Append to a structure that already has super commutated sets may only add further sets, which keeps the simple parameters in front of the arrays.12

    TC[3,5] and TC[3,6] are mandatory when the service includes a parameter functional reporting configuration subservice, since that subservice works by enabling and disabling reports.7

    4. The diagnostic reporting subservice¶

    The diagnostic subservice mirrors the housekeeping one: TC[3,2], [3,4], [3,7], [3,8], [3,11], [3,28], [3,30], [3,32] and [3,34] correspond to TC[3,1], [3,3], [3,5], [3,6], [3,9], [3,27], [3,29], [3,31] and [3,33], with TM[3,26], [3,12] and [3,36] as reports.16 The differences are:

    Status in the structure only if enable/disable is provided always present
    One-shot report generates one report generates one report "independently" of the periodic generation status
    Number per service at least one subservice zero or more subservices

    5. The parameter functional reporting configuration subservice¶

    5.1 Applying configurations: TC[3,37]¶

    A TC[3,37] carries a configuration execution flag and one or more definition identifiers. The whole request is rejected if the flag is invalid; unknown definitions are rejected individually. If at least one instruction is valid and the flag is "exclusive", every enabled housekeeping and diagnostic report of the service is first disabled. Then, for each valid definition, each referenced report structure is told to take the entry's collection interval and to enable or disable its periodic generation; entries pointing at structures that do not exist produce a failed execution notification.22

    7.2 Filtered mode¶

    PUS-A's second generation mode, the filtered mode, produces a report at the end of a collection interval only if at least one unfiltered parameter changed by more than its threshold since the previous interval; for parameters sampled several times, any change of a sample counts.55 The threshold of each parameter is either a percentage (threshold type 0) or an absolute delta (type 1), and a timeout, a multiple of the collection interval, forces a one-shot report when nothing has changed for too long.6455 The optional mode field of (3,25) and (3,26) tells the ground why the report exists: 0 periodic, 1 filtered and a threshold was exceeded, 2 filtered but generated by the timeout.66 Filtered mode was intended mainly for status parameters, so that a report is only sent when something changes, with noisy analogue values filtered out of the comparison.6855 Selecting a mode that is already active generates an error report.64

    7.3 Sampling-time offsets¶

    PUS-A requires that absolute and relative sampling times of housekeeping parameters can be determined on the ground to accuracies set by mission constants, and allows three methods: knowledge of the on-board sampling mechanism, explicit time-stamping of parameters, or offsets measured on board and reported with (3,15)/(3,16). In the third case the report is also generated automatically when a new SID is defined, before its first report, and only the first sample of each array is given an offset.5663 The static time offsets of SCOS-2000 (section 9.1) suit the first method, or the third once the measured offsets have been entered in the database; this pairing is this wiki's reading, not a statement of either source.7056

    8. The Rev.1 draft: one subservice, six categories¶

    The December 2024 draft for public review restructures the service. It defines only two subservice types, housekeeping reporting and parameter functional reporting configuration; the diagnostic subservice disappears.48 Instead, every housekeeping structure has one of six categories, statically deduced from its structure identifier, and the category selects the message type of the report: TM[3,25] for category 1, TM[3,26] for category 2 and the new TM[3,50] to TM[3,53] for categories 3 to 6.5051 The draft's example of a tailoring is category 1 for nominal reports, 2 for diagnostic reports, 3 for essential reports used at low bit rate and 4 for troubleshooting reports stored only on board.50 The diagnostic requests disappear from the interface clause, and the housekeeping periodic generation properties report is printed as TM[3,34] instead of TM[3,35], consistently in clause 6.3.3.11, in clause 8.3.2.11 and in Annex C, so it is not a single misprint; the reason is not stated in the available sources.52

    Solar Orbiter separates kinds of housekeeping with the packet category field of its APIDs (section 9.4) rather than with the message type.89 The parallel with the Rev.1 categories is this wiki's comparison; neither document draws it.

    9. SCOS-2000 and the Solar Orbiter MIB¶

    9.1 What SCOS-2000 does (and does not do) with service 3¶

    The SCOS-2000 import ICD says that there is no service-specific processing of service 3 packets, and lists the consequences:70

    • every TM packet must be recognised from the MIB, so a new housekeeping or diagnostic packet created with service 3 commands must first be added to the database; the efficient approach, typical of ESA missions, is to define the packet in the database first and generate the service 3 commands from it, in the mission's database manager rather than in the SCOS-2000 kernel;
    • the time stamp of each parameter sample is the packet time plus a time offset statically defined in the database, so the offsets must be known in advance and identical for every instance of the packet;
    • the collection interval of periodic packets is also static in the database and is not updated when a service 3 command changes it on board.

    9.2 How a housekeeping packet is recognised¶

    The SCOS-2000 telemetry packetiser identifies a packet from its APID, type and subtype and, for some type/subtype combinations, up to two additional identification fields defined in pic by byte offset and bit width. The full key (type, subtype, APID, PI1, PI2) is then looked up in pid to find the SCOS-2000 packet ID (SPID) and, for variable packets, the structure definition (TPSD).7173 For housekeeping this first additional field is naturally the SID.

    In plf, each parameter of a fixed packet has a byte offset PLF_OFFBY counted from the start of the TM source packet, a bit offset PLF_OFFBI, and four fields for super commutation and timing: PLF_NBOCC (number of occurrences, 1 for a simply commutated parameter), PLF_LGOCC (bits between consecutive occurrences), PLF_TIME (offset of the first occurrence from the packet time, in ms) and PLF_TDOCC (ms between occurrences). A super commutated parameter is a single record.74 Overlapping records and gaps are allowed.74 Variable packets such as the structure reports TM(3,10) and TM(3,12) are described in vpd instead, and PID_INTER gives the expected interval of periodic packets, after which their samples expire.7572

    9.3 How a definition command is built¶

    A create command contains parameter identifiers. SCOS-2000 supports a special command parameter type, "Parameter ID" (CPC_CATEG = P, PTC 3), that accepts the name of a monitoring parameter and encodes its on-board identifier PCF_PID, which corresponds one to one to the PUS parameter#.767778 This is how a generic "Define New Housekeeping Parameter Report" can be filled from the database.

    10. Design notes¶

    • One packet type, many structures. All housekeeping reports share TM[3,25]; the SID is what makes them different. Ground systems therefore need an identification rule that looks inside the packet, which SCOS-2000 provides with pic, and an on-board design that puts the SID at a fixed position.71
    • Ground and board must agree. Because SCOS-2000 decodes packets only from the database, a service 3 change on board without a matching MIB change produces undecodable telemetry; changing an interval on board does not change the expected interval or the sample time offsets on the ground.70
    • Delete and append need a disabled report. Both are rejected while periodic generation is enabled, so a change to a running report is a disable, change, enable sequence.912 Solar Orbiter applies the same rule to its clear and diagnostic interval commands.8385
    • Diagnostics are temporary by design. PUS-A asks the ground to weigh carefully how much of the downlink diagnostic packets may take; PUS-C makes their enabling and disabling a minimum capability.6947
