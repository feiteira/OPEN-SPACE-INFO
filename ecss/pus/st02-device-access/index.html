    ST[02] Device access¶

    Most of the time a spacecraft is operated through high-level functions: "switch the instrument to science mode", "load this schedule". Underneath, every such function ends in a handful of elementary actions on hardware: a relay pulse, a register write, a message on a data bus. Service type 2 of the Packet Utilization Standard gives the ground direct access to those elementary actions. It exists for contingencies and troubleshooting, when the nominal on-board function may itself be the problem, and for assembly, integration and test, when the basic communication with a unit must be validated before any software runs on it.137 This page describes the device model of ECSS-E-ST-70-41C, every request and report with its data field, the command pulse distribution unit (CPDU) of clause 9, the capability rules, the much smaller PUS-A service, and the way Solar Orbiter implements the service with CPDU pulses, MIL-STD-1553 bus commands and SpaceWire packets in its MIB.

    Related pages

    The CPDU packet is the one standard telecommand packet without a PUS secondary header; its header rules are on PUS packet structures. CPDU packets travel over the lowest layers of the telecommand chain, the TC Space Data Link Protocol and the CLTU. Memory loads, which some missions use instead of register loads, belong to ST[06] Memory management.

    2. Why the service exists¶

    PUS-A explains the motivation in its telecommanding concept. A spacecraft design contains many elementary control actions implemented in hardware or software, such as switching a relay, loading a hardware register or starting a software task; higher-level commands end up triggering one or more of them. Although routine operations do not use them, the ground system must have direct access to all elementary control actions, so that it can bypass a malfunctioning on-board function during contingencies.37 One group of these actions, the device commands, is executed by hardware: hard wired pulse commands, on-off commands and register loads.38

    PUS-A lists three ways to route device commands: embedded directly in a telecommand segment and routed by the decoder to the device (bypassing software, for example when the processor has failed); through a CPDU inside the telecommand decoder; or inside a telecommand packet to an application process that extracts and forwards them. It also recommends that commands of the same type can be packed into one packet so that a multi-command function is executed completely or not at all.38

    PUS-C keeps the purpose but generalises the devices. A device is any on-board entity that can be configured by commands or that generates data, including actuators, sensors, transponders and units with no PUS support of their own. Device commands bypass the nominal functions of the on-board software, so the service performs only a minimum of verification on board.1

    3. The device model¶

    ECSS-E-ST-70-41C defines five kinds of addressable object for this service. All of them are declared when the subservice (or, for CPDUs, the spacecraft architecture) is specified; none is created by telecommand.4691114

    Object Declared properties Requests
    On/off device the list of devices and, per device, the hardware addresses used to command it (for example switch on, switch off, cold or warm reset, open or close a valve) TC[2,1]
    Register hardware address, the register fields, and the "register consistency checks" applied when loading it; the sets of loadable and dumpable registers may differ TC[2,2], TC[2,5]
    CPDU the CPDUs managed by the subservice (see section 6) TC[2,4]
    Physical device device identifier, communication links (for example a MIL-STD-1553B bus and a SpaceWire link) and, per link, the protocols for commanding and for receiving data TC[2,7], TC[2,8]
    Logical device logical device identifier, supported commands and their arguments, and the parameter identifiers usable for data acquisition TC[2,10], TC[2,11]

    4691114

    The physical/logical distinction is explained with a MIL-STD-1553B remote terminal. Commanded as a physical device, the request contains the bus command word itself: address, transmission direction, subaddress and data word count. Commanded as a logical device, the request contains only a logical device identifier, a command identifier and its parameters, and the on-board software maps them onto the right link and protocol.1

    4. On/off device and register commands¶

    4.1 TC[2,1] distribute on/off device commands¶

    A request contains an ordered list of one or more instructions; each instruction holds a single device address. The delay applied between consecutive instructions depends on the spacecraft architecture.5 The request is rejected as a whole, with a failed start of execution notification, if any instruction names an unknown address; otherwise the instructions are executed in the order in which they appear.5

    Field PUS-C type Repetition Meaning
    N unsigned integer once number of instructions
    on/off device address enumerated N times hardware address to which the on/off command is sent

    19

    4.2 TC[2,2] distribute register load commands¶

    Each instruction holds a register address and the data for the register fields. The whole request is rejected if any instruction names an unknown register or fails its register consistency checks, because, as the standard notes, a partial load can leave a device in an unknown or inconsistent state.7 Valid requests are executed in order.7

    Field PUS-C type Repetition Meaning
    N unsigned integer once number of instructions
    register address enumerated N times hardware address of the register
    register data deduced N times values of the register fields; structure deduced from the address

    20

    4.3 TC[2,5] distribute register dump commands and TM[2,6] register dump report¶

    Register dumps are processed differently from loads. Each instruction (a register address) is checked on its own: an unknown address produces a failed start of execution notification for that instruction, and the valid instructions are processed regardless. For each valid instruction the subservice distributes the dump command and builds a register dump notification (address plus the value of each register field); all notifications of one request go into a single TM[2,6] report.8 Dumping requires the load capability.8

    Field (TM[2,6]) PUS-C type Repetition Meaning
    N unsigned integer once number of dumped registers
    register address enumerated N times address of the dumped register
    register data deduced N times value of each register field

    2223

    Request-level versus instruction-level rejection

    All "distribute" requests of ST[02] (on/off, register load, CPDU, physical and logical commands, and both acquisition requests) are rejected as a whole when one instruction is invalid, and their instructions are executed in order. Only the register dump request is checked instruction by instruction.57810 The consequences for verification reports are described on ST[01] Request verification.

    5. Physical and logical devices¶

    5.1 TC[2,7] distribute physical device commands¶

    Each instruction contains a physical device identifier, protocol-specific data and command data. For a MIL-STD-1553B remote terminal the standard's example maps them to the terminal address (which also selects the bus), the transfer direction, subaddress or mode code indicator and word count or mode code, and up to 32 sixteen-bit data words.12 Instructions for the same device are sent in order at the maximum rate the protocol allows; no ordering can be assumed between instructions for different devices.12

    The request is rejected if any instruction names an unknown device or contains invalid protocol data. During execution the subservice checks the result of each transmission. A failed transmission produces a failed execution notification with the instruction index, the transmission return code and any auxiliary data, and the request then ends with a single failed completion of execution report containing the first of these notifications.12

    Field PUS-C type Repetition Meaning
    N unsigned integer once number of instructions
    physical device ID enumerated N times device (and implicitly link) to address
    protocol-specific data deduced N times for example the 1553 direction, subaddress and word count
    command data deduced N times the data to transmit

    24

    5.2 TC[2,8] acquire data from physical devices and TM[2,9]¶

    The acquisition request is the read counterpart. Each instruction carries a transaction ID, chosen by the requester to recognise the answer, the device ID and the protocol data that select the data to report. For each successful acquisition the subservice generates one TM[2,9] report; a failed acquisition produces a failed execution notification with the transaction ID and the transaction execution status, and the request ends with one failed completion report containing the first such notification.13 The data acquisition return codes and their auxiliary data are declared per device and link.13

    Field (TC[2,8]) PUS-C type Repetition
    N unsigned integer once
    transaction ID unsigned integer N times
    physical device ID enumerated N times
    protocol-specific data deduced N times
    Field (TM[2,9]) PUS-C type Meaning
    transaction ID unsigned integer copied from the instruction
    data acquisition return code enumerated part of the transaction execution status
    auxiliary data deduced, deduced presence detail for the return code, if any
    data block deduced the acquired data

    2526

    5.3 TC[2,10] and TC[2,11]: logical devices and TM[2,12]¶

    A logical device command names the logical device, a command ID and the command arguments, with no reference to the physical link or protocol. The subservice maps the logical device to a physical device, link and protocol, maps the command ID to protocol-specific data, formats the arguments as command data, transmits and checks the result, reporting failures as for physical commands.15 The standard's stated benefit is that the same request can be used during on-board software development and in flight, even though the physical access to the device differs.15

    A logical acquisition names the logical device and a parameter ID; the subservice maps the parameter to protocol data, acquires it, and returns one TM[2,12] report per successful acquisition with the acquired parameter value.16 Logical commanding requires physical commanding, and logical acquisition is implied by logical commanding.35

    Message Fields in order
    TC[2,10] N (unsigned integer); repeated N times: logical device ID (enumerated), command ID (deduced), command arguments (deduced)
    TC[2,11] N (unsigned integer); repeated N times: transaction ID (unsigned integer), logical device ID (enumerated), parameter ID (enumerated)
    TM[2,12] transaction ID (unsigned integer), data acquisition return code (enumerated), auxiliary data (deduced, deduced presence), parameter value (deduced)

    272829

    6. The command pulse distribution unit (CPDU)¶

    6.1 Concept¶

    Clause 9 of ECSS-E-ST-70-41C defines the CPDU: a simple unit that gives the ground direct access to equipment, for example to reset a transponder or a sensor during a contingency. Each CPDU is logically an application process with its own APID. It can be reached directly, through a virtual channel and a multiplexer access point (MAP) that is physically linked to it, or indirectly, through an application process that hosts a device access subservice and receives TC[2,4].30 A CPDU request is a list of command pulse instructions, each naming an addressable output and the duration of the pulse.30

    6.2 Rules¶

    Property Rule (PUS-C)
    Pulse duration unit declared per CPDU, from 10 ms to 15 ms
    Addressable outputs declared per CPDU; up to 2^12 (4,096), identified by values 0 to 2^12 - 1; only some are equipped with output lines
    Instructions per request maximum declared per CPDU, at least 12 and at most 504, constrained by the TC segment size
    Duration exponential value 0 to 7
    Pulse length pulse duration unit × 2^(duration exponential value)
    Access APID, MAPs physically linked to the CPDU and the VC used for each MAP declared in the spacecraft architecture; MAP 0 is usual for a CPDU behind a decoder without cross-coupling
    Connected outputs each physically connected output has a declared minimum and maximum pulse duration

    313233

    With the allowed range of the unit, the eight duration codes span from 10 ms (unit 10 ms, code 0) to 1.92 s (unit 15 ms, code 7):

    Code Factor Unit 10 ms Unit 15 ms
    0 1 10 ms 15 ms
    1 2 20 ms 30 ms
    2 4 40 ms 60 ms
    3 8 80 ms 120 ms
    4 16 160 ms 240 ms
    5 32 320 ms 480 ms
    6 64 640 ms 960 ms
    7 128 1.28 s 1.92 s

    The table is computed from the formula in requirement 9.2.3c.33 PUS-A gives the same end point, 128 × D "between 1,28 and 1,92 seconds".52

    6.3 The CPDU packet¶

    A CPDU request travels in a CCSDS Space Packet with version 0, type 1, secondary header flag 0, the CPDU's APID, sequence flags 11 and sequence count or name 0. Its data field has no secondary header and no spare, only the application data and a 16-bit CRC identical to the frame error control field of the TC data link.34

    3433

    When a device access subservice receives TC[2,4], it rebuilds the CPDU request in the format the CPDU expects and distributes it; the standard imposes no delay between consecutive CPDU requests.10 The TC[2,4] data field wraps the instructions in two levels of repetition:

    Field PUS-C type Repetition Meaning
    N1 unsigned integer once (optional) number of CPDU instructions
    CPDU ID enumerated N1 times (optional) which CPDU, if the subservice manages several
    N2 unsigned integer N1 times number of command pulse instructions
    output line ID enumerated, 12 bits N2 times output to pulse
    reserved bit-string, 1 bit N2 times -
    duration exponential value unsigned integer, 3 bits N2 times pulse length code

    2110

    Inference

    The upper limit of 504 instructions matches the largest CCSDS TC frame. A TC transfer frame is at most 1,024 octets, of which 5 are the primary header, 2 the frame error control field and 1 the segment header, leaving 1,016 octets for one packet.53545556 A CPDU packet of 6 header octets, 504 two-octet instructions and a 2-octet CRC is exactly 6 + 1,008 + 2 = 1,016 octets. PUS-C only says that the limit is constrained by the segment size.31 The same arithmetic links the PUS-A maximum of 120 instructions to its maximum CPDU packet length of 248 octets (6 + 240 + 2).4151

    7. Capability rules and verification¶

    PUS-C requires at least one of four capabilities: on/off commands, register commands, software CPDU commands, or physical device commanding.3 The remaining message types depend on them (section 1). Each of the "distribute" and "acquire" requests reports a rejected request with a failed start of execution notification. Execution checks are defined only for the physical and logical device requests: there, a failed transmission or acquisition produces a single failed completion report built from the first failed notification.512131516 The device access subservice defines no observables.17

    Device commands bypass the nominal on-board functions and get only a minimum of on-board verification.1 The confirmation that a relay actually switched therefore has to come from telemetry: Solar Orbiter verifies the completion of its PCDU power commands with parameter checks rather than with a completion report (section 10.4).71

    8. Rev.1 draft¶

    The December 2024 draft for public review keeps the same eleven message types with the same subtypes, TC[2,1] to TM[2,12], and the same clause structure.36

    9. PUS-A: the device command distribution service¶

    PUS-A's service 2 is much smaller. It distributes on/off and register load commands and CPDU commands for the reconfiguration of vital spacecraft functions, and it defines no reports.3942

    PUS-A request Application data Notes
    (2,1) Distribute On-Off Commands N (unsigned integer, optional), then N addresses (enumerated) N is omitted if the service handles one command at a time
    (2,2) Distribute Register Load Commands N (optional), then N × (register address, register data) the data structure is known from the address and follows structure rule set 1
    (2,3) Distribute CPDU Commands a CPDU packet: N × (output line ID, 1 octet; duration, 1 octet) no data field header; processed by the CPDU itself

    434445

    On reception, the application process unpacks the commands, reformats them for the internal bus or device driver (the address structure is mission-dependent and may contain subfields) and distributes them in packet order. Annex A.3 of PUS-A gives an example with a 24-bit OBDH command.40

    The PUS-A CPDU is described in more detail than in PUS-C, in Annex D, which is transcribed from ESA PSS-04-151 (the telecommand decoder specification, issue 1, which PUS-A dates September 1993; the cover of the document itself says September 1992 and its inner pages September 1993, see the history page):414849

    • a CPDU is solely accessible from the ground, has up to 256 output lines and a dedicated APID, and receives one complete packet per telecommand segment, in practice on MAP 0 (MAP 1 is a likely second interface when CPDUs are cross-coupled);4150
    • the packet is 10 to 248 octets long, always an even number, ends with the frame CRC, and is checked to be "CLEAN" (length and CRC) and then "LEGAL" (version 0, type 1, data field header flag 0, programmed APID, sequence flags 11); a packet failing a check is erased;51
    • each instruction is two octets: the first selects one of 256 outputs, and in the second the 5 most significant bits are reserved and ignored and the 3 least significant bits select a duration of 1 × D to 128 × D, with D between 10 and 15 ms;52
    • once a packet is accepted, the CPDU ignores further segments until all its pulses are issued; there is no "abort", and an instruction for an output that is not physically implemented is processed as if the output existed, without any anomaly report;5052
    • the mission constants <CPDU_DURATION_UNIT> (10 to 15 ms) and <CPDU_MAX_INSTR> (12 to 120 instructions) characterise each CPDU.47

    52

    A small inconsistency in PUS-A

    The text of request (2,3) describes the duration as "a value between 0 and 8", while Annex D defines a 3-bit field with values 000 to 111, i.e. 0 to 7.4552 PUS-C settles the range at 0 to 7.33

    The capability sets of PUS-A require either (2,3), because a CPDU is a dedicated application process, or one of (2,1) and (2,2); a service without CPDU commands may add the other of the two.46

    Aspect PUS-A PUS-C

    10. Solar Orbiter¶

    10.1 What the ICD defines¶

    Solar Orbiter's TM/TC ICD, based on PUS-A, describes service 2 as the distribution of CPDU commands for the reconfiguration of vital unit functions, of MIL-STD-1553 bus command messages and of SpaceWire command messages. It distinguishes two CPDU paths: packets received by the CPDU TC decoder on MAP 0, with no software involved and a non-PUS structure, and the software-distributed TC(2,3), which the central software (CSW) receives on MAP 1 and routes to the CPDU. If the processing of a CPDU packet is not complete, new commands are ignored. No register load commands exist, because all OBC registers are mapped in memory and reachable through service 6.59

    The ICD names three kinds of CPDU pulse command. HPC-1 commands are sent from the ground directly to the CPDU inside the on-board computer, without the central software; HPC-2 commands use the same command lines but are issued by the on-board computer's reconfiguration module; HPC-3 commands are generated by the CSW writing dedicated CPDU registers.64 The ICD's acronym list expands HPC as "High Power Command".65 Its MAP assignments are not fully consistent: the segment header clause gives MAP 0 ("CPDU") for "CPDU command (i.e. TC(2,3))" and MAP 1 for all other commanding, whereas the TC(2,3) clause says that the CSW receives TC(2,3) on MAP 1.6459 In the MIB, only the 125 HPC-1 commands carry CCF_MAPID = 0, while the TC(2,3) commands leave CCF_MAPID empty (section 10.2).67

    Request / report Content Verification
    TC(2,3) CSW-distributed CPDU commands (HPC3) command number (1 octet), filler (5 bits), pulse length (3 bits) TM(1,2) for static check failures, TM(1,8) as defined in a referenced document
    TC(2,128) Distribute MilBus 1553 Commands bus, bus coupler, N command words, then per command the 1553 command word fields and M data words same
    TM(2,129) MilBus 1553 Commands Answer bus, echoed command word, bus coupler and its status word, RT status word, N and the returned data words -
    TC(2,130) Distribute SpaceWire Commands SpW link (1 octet), coupler (1 octet), N (2 octets), raw SpW packet same

    59606162

    These four are the only service 2 entries in the mission's service list.63 The TC(2,3) layout is the PUS-A Annex D instruction; TC(2,128) is a mission-specific implementation of what PUS-C calls physical device commanding, with the 1553 command word fields given explicitly; TC(2,130) carries a complete SpaceWire packet, whose data is a PUS command plus a 4-octet SpaceWire header.596212

    10.2 What the MIB contains¶

    The September 2025 MIB holds 1,363 service 2 commands and one service 2 report, plus 125 CPDU commands without a PUS header:67

    Kind Header (CCF_PKTID) APID Commands CCF_ACK Verification profile
    Direct CPDU (HPC-1), MAP 0 HPC1_TC 44 125 null parameter check or none
    TC(2,3) software CPDU (HPC-3) NOM_TC 172 105 9 acceptance + completion reports
    TC(2,128) MIL-STD-1553 NOM_TC 172 1,257 9 (1,179) or 1 (78) reports, or acceptance report + parameter check
    TC(2,130) SpaceWire NOM_TC 172 1 9 acceptance + completion reports
    TM(2,129) 1553 command report - 161 SPID 14002 - variable packet (VPD)

    6768

    APID 44 is process ID 2 (OBC hardware, high-priority TC functions to the CPDU on MAP 0) with packet category 12; APID 172 is process ID 10, the CSW data management application.6667 The single report, TM(2,129), is defined on APID 161, i.e. process ID 10 with packet category 1, although the ICD gives TM(2,129) packet category 2 and Annex 8 reserves category 1 for service 1 acknowledgements.686166 The April 2020 release had the same counts for TC(2,3), (2,128) and (2,130).73 No TC(2,1), (2,2) or (2,4) exists in either release, which matches the ICD.6759

    The pcdf definition of HPC1_TC is the CPDU packet header of PUS: fixed version 0, type 1, data field header flag 0, the APID from CCF_APID, sequence flags 0b11, and the sequence count and length set by the commanding system. It has no secondary header elements at all.69

    69

    All 125 HPC-1 commands carry exactly one instruction: two 8-bit fixed areas, an output line (values 2 to 215 in the MIB) and a pulse length code. Code 2 is used 81 times and code 1 38 times; one series of "Dummy commands" (ZBC04100 to ZBC04107) uses each of the eight codes 0 to 7 once.69 Since fixed areas in cdf are hexadecimal raw values, the pulse code octet holds the 3-bit duration code in its least significant bits, as in the PUS-A instruction.5852

    10.4 Worked example: a PCDU switch-off over MIL-STD-1553¶

    ZPW04800 "PCDU A APR1_C1 SwitchOFF" is a TC(2,128) with Ack 1 (acceptance report only). Its cdf entries fill the generic 1553 layout of ZCD00280 "Distribute 1553 commands" with fixed values:71

    Bits Element Value in the MIB Meaning
    0-7 Bus ID (PCD02801, textual calibration) BUS_1 (engineering) MIL bus 1
    8-15 Bus Coupler ID (PCD02802) BUSCPLR_DEF (editable) default coupler
    16-23 number of bus commands 0001 one 1553 message
    24-39 command word 2281 (hex) see the bit field below
    40-47 number of data words 1 one data word
    48-63 data word RPW04800 "APR1_APR1_OFF" default 8401 (hex) the PCDU command itself

    7160

    The bit split (5 + 1 + 5 + 5 bits) is the one defined by the generic command ZCD00280 (RT address, transmit/receive flag, subaddress or mode, number of data words or mode code), and the word count of 1 agrees with the separate data word count field.71 The command's completion is verified by stage 40: telemetry parameter NPWD0764 "IFA_APR1_Conv1_ST" must read raw 0 (tolerance 0) with a CVS_INTERVAL of 60 s.71 The hex values and the field layout are real MIB data; the assignment of remote terminal 4 to PCDU A is not stated in the available sources beyond the command description.

    The answer path uses TM(2,129) (SPID 14002), defined as a variable packet in vpd: the bus ID, the 16-bit command word decoded again into its four fields by negative offsets, the bus coupler status, the RT status word with its individual flags (message error, instrumentation, service request, busy, terminal flag and others), and a counted list of data words.68

    Inference

    The unit names are read from the command descriptions, and the group boundaries from a naming convention that is not documented in the available sources. The picture they give is that Solar Orbiter implements the PUS idea of "physical device commanding" mainly for power distribution, heaters and RF equipment, with each useful bus message stored in the MIB as a fully defined command, rather than with on/off or register commands.

    11. How SCOS-2000 handles service 2¶

    The SCOS-2000 import ICD states that the mission control system does no specific processing of service 2 packets. It can aggregate several packets into one TC segment, and so into one frame and CLTU, but it cannot dynamically pack several command definitions into one TC packet. A TC(2,3) therefore either holds one pulse instruction or has several instructions defined in the database, in which case it is handled as a single command for history and verification. CPDU commands can be defined so that they may not be inserted into a time-tagged TC(11,4) or aggregated with other commands in the same segment.57

    Where the bits are defined

    Because SCOS-2000 has no service-specific logic here, everything about a device command lives in the MIB: the header in tcp and pcdf, the command in ccf, its elements in cdf and cpc, and the check of its effect in cvs and cve. See Commanding in the MIB and Command verification in the MIB.
