    ST[20] On-board parameter management¶

    The parameter management service (service type 20) gives the ground direct access to on-board parameters: it can read their current values, set new values and, optionally, redefine where a parameter lives in memory and how it is encoded.1 Each parameter definition binds a spacecraft-wide parameter identifier to a memory location and a packet field code (PTC and PFC). A predefined identifier can be pointed at a new memory location or field code, for example to make a parameter for an OBCP, or to export an internal software variable as a parameter for housekeeping or monitoring.2 ST[20] is new in PUS-C (ECSS-E-ST-70-41C, 2016): the PUS-A list of standard services stops at service 19.3434

    The service is small, with seven message types and no observables, but it touches the foundations of the standard: the on-board parameter, the on-board memory and the packet field code. This page covers each clause, then the 2024 Rev.1 draft. It then turns to Solar Orbiter, whose PUS-A based design uses the number 20 for something else entirely and puts its parameter management in private service 139.

    Two names

    Clause 6.20 and Table 4-1 call the service "parameter management", and clause 8.20 calls it "on-board parameter management".153 This wiki uses the planned page title "On-board parameter management" and treats both names as the same service.

    2. Foundations: parameters, memories, definitions¶

    2.1 On-board parameters¶

    PUS-C defines the on-board parameter as a system object in its generic service model. Each parameter has exactly one identifier, unique across the whole spacecraft. It can be a sensor measurement or a software variable held in memory, and services read it as part of their routine work, for example to monitor it or to compute another value.8 The baseline parameter set comes from the spacecraft design. The standard foresees defining new parameters in orbit, changing an existing definition, or setting a value through ST[20]. NOTE 3 of 5.4.3.2 adds that this is naturally limited to software parameters in memory, and that the on-board software may protect essential parameters against being overwritten.8

    Every parameter is also associated with one minimum sampling interval. The interval is the unit in which services such as housekeeping and monitoring express their time intervals, and all parameters accessed by one application process share it. The standard's example is 125 ms for the platform and 500 ms for a payload.8

    2.2 On-board memories and addressing¶

    A parameter definition points into an on-board memory, a logical memory identified by a memory ID. For each memory the mission declares its access alignment constraint, its size in bytes, the allowed operations ("read only", "read and write" or "write only"), and whether scrubbing and write protection are supported.9 Two addressing schemes can be exposed in the space-ground interface:10

    • Absolute addressing: addresses and offsets are in bytes from the start of the memory.
    • Base plus offset: a byte offset from a base reference. The base can be an absolute address or a symbolic one, "e.g. the name of a table, a parameter set or a file", whose address is known on board.

    The base-plus-offset scheme is what makes TC[20,5] useful. Offsets count from the first byte of the referenced object "independently of the actual physical storage", so a parameter can be defined inside a table or a file without the ground knowing where the object physically sits.10 The 2014 ECSS status presentation says the same of ST[6]: the base-plus-offset concept "has been extended to access memory objects such as files", and it lists for ST[20] the "dynamic creation (!) of new parameters based on raw or structured data memory access".34

    2.3 The parameter definition¶

    The mission declares the parameter identifiers whose definitions the subservice manages. Each parameter definition consists of:11

    1. the on-board parameter identifier, unique in the spacecraft;
    2. a memory ID, if the subservice manages more than one memory;
    3. an address: base plus offset for a base-plus-offset memory, or a byte offset from the start for an absolute-addressed memory;
    4. the packet field code (PTC and PFC) of the memory field used to read or write the value.

    The packet field code tells the software how to read or write the value at the address. The value fields of TM[20,2] and TC[20,3] are "deduced" from the parameter ID, so in this wiki's reading the same code also fixes how the value appears in those messages.21 See PUS parameter types for the PTC/PFC table and MIB parameter types for its SCOS-2000 form.

    2.4 Layout and accessibility¶

    Each parameter management service contains at least one parameter management subservice. An application process hosts at most one provider.12 For the definition-changing capabilities, the mission declares two lists:7

    • the parameters whose definitions may be changed;
    • the memories that may be used for parameter definitions, which, the note says, "allows restricting the memories on which new parameters can be mapped".

    PUS-C defines no observables for this subservice.13

    3. Requests and reports¶

    All ST[20] requests are multi-instruction requests. In PUS-C 2016, an invalid instruction gets its own failed start of execution notification (reported as TM[1,4]), and the valid instructions of the same request are still processed.1415 The field types follow the PUS-C conventions. "Enumerated" and "unsigned integer" widths are mission choices. "Deduced" (PTC 11 PFC 0) means that the structure and format follow from preceding fields or mission constants, here from the parameter ID.1619

    3.1 TC[20,1] report parameter values / TM[20,2] parameter value report¶

    This is the only mandatory capability. Each instruction names one parameter. An unknown parameter is rejected. Each valid instruction yields one parameter value notification (identifier and value), and the request yields one TM[20,2] with all of them.14

    Message Field Type Meaning
    TC[20,1] N unsigned integer number of parameters
    parameter ID enumerated repeated N times
    TM[20,2] N unsigned integer number of values reported
    parameter ID enumerated repeated
    value deduced format specific to that parameter ID

    Source: Figures 8-219 and 8-220.2021

    3.2 TC[20,3] set parameter values¶

    This capability exists if declared. Each instruction gives a parameter ID and its new value, with the same layout as TM[20,2]: N, then N pairs of parameter ID and deduced value. An unknown parameter is rejected. Otherwise the parameter is set to the new value.2223

    Inference

    The only rejection criterion that PUS-C 2016 lists for TC[20,3] is "unknown parameter". It names no range check, read-only check or memory-protection check. The protections that NOTE 3 of 5.4.3.2 mentions would therefore be implementation checks beyond the standard, or go into the list of parameters that the mission declares as manageable. The standard does not say which.

    3.3 TC[20,4] change raw memory parameter definitions¶

    This capability exists if declared. Each instruction gives the definition to change (by its parameter identifier), the memory ID if there is more than one memory, the start address as a byte offset, and the new PTC and PFC.24

    Field Type Presence Meaning
    N unsigned integer always number of instructions
    parameter ID enumerated repeated the definition to change
    memory ID enumerated optional (repeated) when more than one memory is managed
    absolute address unsigned integer repeated byte offset of the new location
    PTC enumerated repeated new packet field type code
    PFC enumerated repeated new packet field format code

    Source: Figure 8-222.25 An instruction is rejected if:24

    1. the parameter definition identifier is unknown;
    2. the memory ID is not allowed for parameter definitions;
    3. the memory address is invalid;
    4. the packet field code is not compatible with the memory alignment constraint;
    5. the packet field code is invalid.

    A valid instruction installs the new definition.

    3.4 TC[20,5] change object memory parameter definitions¶

    This capability exists if declared. It is the same as TC[20,4], except that the address is a base plus an offset inside an object memory, and the base field is "deduced". Its form depends on the memory and can be an address or a symbolic reference.2627 The five rejection conditions are those of TC[20,4].26

    Field Type Presence
    N unsigned integer always
    parameter ID enumerated repeated
    memory ID enumerated optional (repeated)
    base deduced repeated
    offset unsigned integer repeated
    PTC, PFC enumerated, enumerated repeated

    Source: Figure 8-223. Clause 8.20.2.5b cites "Figure 8-222", but the figure printed under it is Figure 8-223, so this is an editorial slip in the 2016 text.27 The Rev.1 draft keeps the slip: its 8.20.2.5b cites Figure 8.20-4 (raw memory) above Figure 8.20-5.33

    3.5 TC[20,6] report parameter definitions / TM[20,7] parameter definition report¶

    This capability exists if declared, and only if at least one of TC[20,4] and TC[20,5] is provided.28 Each instruction names a parameter. Unknown parameters are rejected. Each valid instruction yields a parameter definition notification containing the parameter ID, the memory ID (if several memories), the addressing scheme (if any memory uses base plus offset), the absolute or base-plus-offset address, and the PTC/PFC.28

    PTC, PFC enumerated repeated

    3.7 A redefinition, step by step¶

    The next diagram shows how the ground could turn a spare identifier into a new housekeeping parameter. The parameter number and the subsequent ST[03] step are illustrative.

    sequenceDiagram
  participant G as Ground
  participant PM as ST[20] subservice
  participant HK as ST[03] housekeeping
  G->>PM: TC[20,6] report definition of parameter P (spare)
  PM-->>G: TM[20,7] P: memory m, address a0, PTC/PFC f0
  G->>PM: TC[20,4] redefine P as memory m, byte offset a1, PTC 3 PFC 12
  Note over PM: checks: P known, m allowed, a1 valid, alignment and PFC valid

  HK-->>G: housekeeping reports now carry the 16-bit value at a1

    The rules come from clauses 6.20.5.2 and 6.20.5.4.2428 PTC 3 PFC 12 is a 16-bit unsigned integer.17

    4. The 2024 Rev.1 draft¶

    A word-by-word comparison of clauses 6.20 and 8.20 of the Rev.1 public-review draft with the 2016 text, made by this wiki, finds a single substantive change. A request that contains an invalid instruction is now rejected as a whole, with one failed start of execution notification. A request with only valid instructions is executed in instruction order. This is the same change Rev.1 makes across the standard.32 The message types and packet layouts are unchanged.33

    5. Relations to other services¶

    • ST[06] memory management loads and dumps memory areas. ST[20] works one level higher, on named, typed parameters. The base-plus-offset addressing is shared.1034
    • ST[03], ST[04], ST[12] sample parameters by identifier. Redefining a parameter changes what they all see.7
    • ST[18] OBCPs are the standard's own example of a user of new parameters.2
    • ST[23] file management: a base-plus-offset base may be a file, so a parameter can live inside an on-board file.10

    6. Solar Orbiter¶

    6.1 Service type 20 is "information distribution"¶

    Solar Orbiter's packet structure ICD follows ECSS-E-70-41A and lists the mission's Operations Interface Requirements Document (OIRD, SO-ESC-RS-05001) as a reference document.35 The same mission-level numbering appears earlier in ESA's Herschel/Planck OIRD (2003), which lists service 20 as "Information Distribution CDMS - User", 21 as "Science Data Transfer" and 22 as "Context Saving". Services 20 and 22 are marked "Not used" there, and only 21 is mandatory for instruments.36 PUS-C later gave these three numbers to new standard services. On Solar Orbiter, service 20 is Information Distribution. Its packets go from the OBC to the payload instruments, both as an OBC heartbeat (so that instruments can switch down in a controlled way if the spacecraft enters Survival Mode) and to distribute inter-instrument communication data.37 It has nothing to do with PUS-C's ST[20].

    Message Direction Content
    TC(20,1) Start Information Distribution for User ground to CSW instrument ID (1 octet), period (2 octets: 0 = one shot, otherwise a number of 125 ms software cycles)
    TC(20,2) Stop Information Distribution for User ground to CSW instrument ID (1 octet)
    TC(20,128) Inter-Instruments Communication CSW to all instruments 236 octets: 36 octets of platform data and 200 octets of instrument data

    Source: §5.21.3839 Table 5.1-1 makes the service optional for payloads. The CSW implements TC(20,1) and TC(20,2), and TC(20,128) is optional for the payload.40

    The ICD fixes the TC(20,128) packet itself. APID 796 is process ID 49 ("Payload broadcast") with category 12. The sequence count increments at 8 Hz and wraps every 2048 s. The acknowledgement flags are 0, so payloads generate no TM(1,1)/TM(1,7) for it, and the source ID is 14 (System Control). The CSW fills it from the system data pool. Each instrument's share comes from a dedicated TM(3,25), extracted by the TM extraction service. An instrument served at less than 8 Hz sees gaps in the sequence count.39

Each instrument opens its block with a 4-octet heartbeat copied from the on-board time coarse field. Spare octets were allocated in advance, including all 14 of SPICE's, because SPICE did not then plan to take part.4344

    The 2025 MIB contains five TC(20,128) definitions at APID 796, all from instrument databases: EPD's ZID52530, MAG's ZIM02028 (one undivided 1888-bit, that is 236-octet, block), PHI's ZIP14800, and two from STIX, ZIX20128 and ZIXX0128 "STIX Information Distribution Aligned". The CCF_DESCR2 text of ZIXX0128 is cut off after "Duplicated from ZIX201". ZIXX0128 is new in 2025, and the 2020 release has the other four.5859 EPD's ZID52530 and STIX's ZIXX0128 follow the SGS note's sizes and order.45 STIX's older ZIX20128 has the SGS sizes but puts SPICE before STIX and SWA. PHI's ZIP14800 uses an even 20 octets per instrument, in the same order as ZIX20128. That is the layout of the issue 7 ICD, which lists the instruments alphabetically (EPD, EUI, MAG, METIS, PHI, RPW, SoloHI, SPICE, STIX, SWA) at 20 octets each, with a remark that deviations must be agreed between the PIs and ESA.39

    Inference

    The orders cannot all describe the same on-board packet. The "Aligned" STIX copy reads as a later correction of ZIX20128 to the SGS allocation. ZIX20128 and ZIP14800 then look like definitions left over from the ICD's even split. Which definition matches the flight CSW is not stated in the available sources.

    The agreed cadences are 1 Hz generation for most instruments' TM(3,25) (MAG 8 Hz, SWA 0.25 Hz, SPICE none) and 1 Hz distribution of TC(20,128) (SWA 8 Hz). Delays are at most 250 ms in each direction, so 500 ms in total.4647 In the 2025 MIB, eleven TC(20,1) commands (ZCD01401 plus one canned command per instrument, ZCD2Z010-ZCD2Z019) and one TC(20,2) are addressed to APID 172 (process ID 10, DMS). Ground sequences use them 90 and 58 times respectively.58 The instrument reactions to service 20 data are still "To be written" in the SGS note.48

    6.2 The real counterpart: private service 139¶

    Solar Orbiter's equivalent of ST[20] is service 139. The service clause heads it "Parameter Management service" and Table 5.1-1 lists it as "Datapool Management Service", reserved for the CSW.4940 It "allows the ground to manage on board data", software variables or equipment acquisitions, by reading or changing values. There are two kinds of data:49

    • Variables, used by housekeeping (service 3) and monitoring (service 12);
    • Updatable constants, "system level tuneable parameters" used in algorithms such as the AOCS, for which service 139 is a more convenient interface than memory management (service 6).

    Parameters are addressed by a 32-bit Parameter ID defined in the SRDB (the ICD uses the acronym without expanding it). The ID is made of a process ID, a read-only/read-write flag and a local ID. The SRDB and the CSW map each ID to a start address, a length and a parameter type. The set is "frozen for a given CSW release", but new parameters can be defined with TC(139,4).49

    Solar Orbiter Purpose PUS-C ST[20] analogue
    TC(139,1) Change Value of onboard Parameters NPAR (1 octet), then NPAR pairs of parameter ID (4 octets) and value (deduced). Not usable for "Byte Array" parameters. TC[20,3]
    TC(139,2) Get Value of On-board Parameters NPAR (1 octet), NPAR parameter IDs (4 octets) TC[20,1]
    TM(139,3) On-board Parameters Value Report NPAR, then ID and value pairs TM[20,2]
    TC(139,4) Define Onboard Parameters NPAR (1-18), then ID (4), RAM address (4), length (1), type (4). Maps a predefined "spare" ID to a RAM location. TC[20,4]
    - no definition report TC[20,6] / TM[20,7]

    Source: §5.29.1 to §5.29.4.5051

    The ICD lists the type codes: 0x00020008/10/20 for 8-, 16- and 32-bit enumerations, 0x00030004, 0x0003000C and 0x0003000E for UINT8, UINT16 and UINT32, 0x00040004, 0x0004000C and 0x0004000E for INT8, INT16 and INT32, and 0x00050001, 0x00050002 and 0x00050003 for single, double and "double read as single" floats.51 The MIB calibration CCDT0017TC holds the same values in decimal, plus BYTE_ARRAY = 0.58

    Inference

    Eleven of the twelve listed codes read as a PUS PTC in the upper 16 bits and the matching PFC in the lower 16 bits: 0x0003000E is PTC 3 PFC 14 (4-octet unsigned), 0x00020010 is PTC 2 PFC 16 (16-bit enumerated), 0x00050002 is PTC 5 PFC 2 (IEEE double precision).1718 The exception is 0x00050003, "Float Double Precision read as Float Single Precision", whereas PTC 5 PFC 3 is the 4-octet MIL-STD simple precision format.18 Solar Orbiter's TC(139,4) therefore carries in effect a packet field code, as PUS-C's TC[20,4] does, with one mission-specific value. The ICD does not state this encoding rule. It is deduced from the values.

    The parameter ID. Annex 11 of the ICD defines the common 32-bit structure for system data pool parameters: a 1-bit filler (0), the 7-bit process ID of Annex 8, a read/write flag (0 = read and write, 1 = read only, "not modifiable via service 132") and a 23-bit local ID. The local ID is a 3-bit filler (0b010), an 8-bit unit ID (for example CSW or IMU) and a 12-bit counter, a free-running number whose last 4 bits give the functional type for CSW parameters.52 The bit widths are in a figure that the text extraction misses. This wiki read them from the rendered PDF page.

    In the MIB, all but one of the 19,803 on-board parameter IDs (PCF_PID) have a most significant octet between 10 and 17: 12,178 with 17, 3,140 with 11 (AOCS), 1,176 with 14 (SYSTEM), 1,138 with 13 (PLATFORM), 1,000 with 16 (THERMAL), 598 with 10 (DMS), 529 with 12 (PAYLOAD) and 43 with 15 (OBCP). The exception is DUMMYVAL "ALWAYS_VALID" with ID 0. Process IDs 10 to 16 are the OBC software processes of Annex 8. Annex 8 lists 17 as a spare, but the MIB's process ID calibration CCDT0018TX names it "OBDB".5853 The read/write bit is 0 in all 19,803 IDs. The 3-bit filler is 0b000 in 15,433 IDs, 0b001 in 1,778 and 0b010 in only 2,592, so the MIB does not follow the Annex's fixed filler value.58

    Inference

    The text's reference to service 132 (SGM management in the same ICD) may be meant for service 139, since service 139 is the one that changes data pool values. The meaning of process ID 17 "OBDB" and of the varying filler bits is not stated in the available sources.

    6.3 Service 139 in the MIB¶

    The 2025 MIB has 217 TC(139,1), 10 TC(139,2) and 7 TC(139,4) definitions, none of them flagged critical, and 26 TM(139,3) packet definitions.58

    APID Process TC(139,1) TC(139,2) TC(139,4)
    172 10 DMS 8 2 1
    188 11 AOCS 29 2 2
    204 12 PAYLOAD 3 1 1
    220 13 PLATFORM 8 3 1
    236 14 SYSTEM 161 1 1
    268 16 THERMAL 8 1 1

    Most TC(139,1) commands are canned settings with fixed parameter IDs, for example "Set DST RX A SCV Health", "Set TWTA SCV Presel = A", "Set GFE Gyro Biases" and "Update SC Mass CSWv3_0". The generic forms are ZCD2Z004/5/6 "Set value of (½/4-byte integer) parameters".58 Ground sequences use TC(139,1) 358 times (in 270 sequences), TC(139,2) 64 times and TC(139,4) 9 times.58

    In the generic commands, and in all TC(139,2) and TC(139,4) definitions, the parameter ID fields are of the SCOS-2000 type Parameter ID (CPC_CATEG = 'P', PTC 3 PFC 14). The operator gives a telemetry parameter name and SCOS-2000 encodes its on-board identifier PCF_PID.5558 The same command parameter, PCD03014 "Datapool parameter ID" (unsigned, 32 bits), appears in 49 service 139 commands, 114 service 12 commands, 24 service 3 commands and 2 service 130 commands.58 Most canned TC(139,1) commands do it differently: 173 of the 217 have no Parameter ID field at all, and 163 of these carry the identifier as a 32-bit fixed area. "Set DST RX A SCV Health" (ZCS2Z03T), for example, holds the fixed areas 0x01 (NPAR) and 0x0E0C83B0, which is the PCF_PID of NCST3H20 "DST-RX A SCV Health", followed by an editable 8-bit value.58

    Reading values back. The generic TM(139,3), for example SPID 10114 from APID 227, is a variable packet. A count NCD8B031 repeats a pair made of NCD0C095 "Monitored Par ID" (32 bits, with VPD_PIDREF = 'Y') and NCD8B033, a value of PTC 11, deduced.58 In SCOS-2000, VPD_PIDREF = 'Y' means that the value is an on-board parameter ID, which is compared with the PCF_PID values to find the telemetry parameter.56 The deduced value then takes that parameter's type: NCD8B033 has PCF_RELATED = NCD0C095, the field that names the parameter whose value supplies the on-board parameter ID for a deduced parameter.5758 This is the ground half of PUS-C's "deduced" value field. Twenty more TM(139,3) definitions at APID 1953 decode particular reports with fixed layouts, keyed on the first parameter ID (pic: offset 17, width 32), for example SPID 65908 "TC Link Mon Params Report".58

    Inference

    APID 1953 falls in the EGSE process ID range (process ID 122).53 In the mission-specific dup file, three of the generic TM(139,3) SPIDs are paired with APID 1953: 14177 (APID 163, DMS), 20131 (APID 179, AOCS) and 27108 (APID 211, PLATFORM). The first parameter IDs that key the twenty fixed-layout definitions all have 10, 11 or 13 in their top octet, which are exactly these three processes. This suggests that the MOC maps the real reports onto this APID to apply the fixed-layout definitions. This is not documented in the ICD or the TN.

    6.4 Worked example: a real redefinition¶

    ZCAX8B04 "Define SPARE RWAB THR 3.1.2" is a TC(139,4) to the AOCS application (APID 188) with every value fixed in the MIB:58

    # Parameter (name, PCF_PID) RAM address (raw CDF_VALUE) Length Type
    1 NCAT2PB0 "RW1_GgHtr_MON__GgHtr_MMH", 185118745 = 0x0B08B019 40077920 4 UINT32 (0x0003000E)
    2 NCAT2PC0 "RW2_WDE_2_URP__GgHtr_MMH", 0x0B08B01A 40077940 4 UINT32
    3 NCAT2PD0 "RW3_GgHtr_MON__WDE_3_URP", 0x0B08B01B 40077960 4 UINT32

    The three IDs are consecutive AOCS spares (top octet 0x0B = 11). Their entries in the mission file ASW_sw_para.dat (next section) are HKA_SPARE_PARAM26-28, "Reserved parameter 26 [27, 28] in the AOCS application".58 TC(139,4) gives these spare identifiers a memory location and a type. The MIB parameter descriptions, such as "RW1_GgHtr_MON__GgHtr_MMH", give them their new meaning, which from the names relates to the reaction wheels. This is the PUS-C TC[20,4] use case, "exporting an existing internal variable as a parameter for housekeeping or monitoring".2

    The RAM addresses are given as printed. Their command parameter has CPC_RADIX = 'D'.58 Read as decimal, 40077920, 40077940 and 40077960 are 0x02638A60, 0x02638A74 and 0x02638A88, 20 bytes apart. All three fall inside the OBC "Processor RAM" range 0x0200 0000 to 0x027F FFFF of the ICD's memory ID allocation (Figure 5.7-1).54 Read as hexadecimal, 0x40077920 would fall in none of the listed RAM ranges. The two other fixed RAM addresses found in the MIB's ground sequences, 40111920 and 40116648 (sequences AACF612A and AACF613A), also fall in that range when read as decimal.58

    Inference

    The memory map therefore supports the declared decimal radix, and the encoded RAM address field of the first definition would be 02 63 8A 60. The ICD does not say which memory a TC(139,4) address refers to beyond "PM-RAM", so this remains a consistency check, not a statement of the sources.

    A request that needs no such interpretation is a TC(139,2) reading the first parameter back. This octet string is illustrative: it is built from the real MIB layout of ZCA08B02 and the real PCF_PID, but it was not captured from the spacecraft:58

    TC(139,2) application data: 01 0B 08 B0 19
  01           NPAR = 1
  0B 08 B0 19  Parameter ID = PCF_PID of NCAT2PB0 (185118745)

    6.5 The ASW_sw_para table and its possible relation to ST[20]¶

    The 2025 release contains a file that the ICD does not define, ASW_sw_para.dat, loaded into this wiki's database as table asw_sw_para with three columns. The first column holds MIB names and the second on-board software symbol names. The third holds a description, empty in 15,662 of the 105,222 rows.58 The MIB overview lists it among the mission-specific files and gives first statistics.

    First column matches Rows Example (column 1, column 2)
    pcf.PCF_NAME (monitoring parameters, prefix N) 77,565 NCAP0001, OBDB_ACCSETPARAMS_ACCUNITA_ACCAXIS1_COEFPOLYTACCBIAS_0
    ... of which have an on-board ID PCF_PID 19,397 NCAT2PB0, HKA_SPARE_PARAM26
    cpc.CPC_NAME (command parameters, prefix P) 3,676 PCA8B021, PTC_GET_N_PARAM
    ccf.CCF_CNAME (commands, prefix Z) 2,221 ZAHG0001
    tpcf.TPCF_NAME (telemetry packet names, prefix Y) 7,665 YCA00101, TMA_TCACK_ACC_SUCCESS
    calibration tables txf, caf, paf, cca, mcf, lgf (prefix C) 260 CCDT0001TX, AOCS_PROFILE_ID
    prf.PRF_NUMBR (value range sets, prefix V) 77 VCD00147, Z_IDINT0TO1
    no MIB table (prefix B) 13,727 BCAY0000, SSEA_SEGMENTS_END_TIME_C

    Source: this wiki's queries.58 Of the 19,803 pcf entries with an on-board ID, all but 406 appear in asw_sw_para. The 2020 release has 85,430 rows.5859

    Inference

    ASW_sw_para looks like an export of the on-board software's view of the database. Each MIB item (parameter, packet, command, command parameter, calibration, value range, and B-prefixed items that match no MIB table) is paired with the symbol of the application software (ASW) that implements it. The relation to ST[20]-style parameter management is that the 19,397 parameters with an on-board ID are the data pool parameters that service 139 (and services 3 and 12) address by Parameter ID. ASW_sw_para then tells which software variable each identifier is bound to, including the "spare" variables that TC(139,4) can map. This matches the ICD's statement that the parameter definitions come from the SRDB and are frozen per CSW release.49 The file's purpose and origin, and the nature of the B-prefixed items, are not stated in the available sources.
