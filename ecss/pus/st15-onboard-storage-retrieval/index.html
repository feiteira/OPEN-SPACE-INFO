    ST[15] On-board storage and retrieval¶

    A spacecraft is out of contact with the ground for most of its life, yet the operators want to see everything it did while nobody was listening. Service type 15 of the Packet Utilization Standard provides that memory. It selects reports generated by the other on-board services, writes them into named packet stores in on-board memory, and lets the ground manage those stores and ask for their contents to be sent down later.1 The retrieved data are called playback (also "deferred" telemetry, or a packet store "dump"), as opposed to the real-time telemetry generated during a pass.578183 This page covers the ECSS-E-ST-70-41C ("PUS-C", 2016) service completely - both subservices, the three status variables of a packet store and the rules that link them, the packet selection logic, and all 37 message types with their data fields - then compares it with the very different ECSS-E-70-41A ("PUS-A", 2003) service and the 2024 Rev.1 draft. It ends with the ground view: virtual channels, how SCOS-2000 handles playback, and the two real implementations described in the public Solar Orbiter MIB.

    Where this page sits

    The reports that end up in packet stores come from services such as ST[01] request verification, ST[03] housekeeping and ST[05] event reporting. The sister service that controls which reports go directly to the ground is ST[14] real-time forwarding control; its filtering model is the same as the packet selection subservice described here. Retrieved packets leave the spacecraft on a TM virtual channel. File-based storage is handled by ST[23] file management and CFDP.

    2. Why spacecraft store telemetry¶

    PUS-C gives two reasons for storing telemetry packets on board and dumping them on request. The first is intermittent coverage or limited real-time bandwidth: the store is sized to hold every packet generated for spacecraft monitoring and control for at least the longest gap between ground station passes plus a mission-dependent margin, and the packets are retrieved in later passes in an order based on their operational significance. The second is recovery of lost packets on missions with continuous coverage: the spacecraft keeps the most recent set of packets, whose size is a mission configuration parameter, so that the ground can fetch again what the space link lost.1

    PUS-A said the same and named the two sizing constants: <PKT_STORAGE_TIME>, the margin added to the longest non-coverage period, and <PKTS_NUM_STORED>, the number of recent one-shot packets kept for loss recovery, "typically the last 100". It gives the classic example of selective retrieval - anomaly reports are needed on the ground sooner than routine status packets - and adds a rule that the 2025 operability standard repeats: storage must not be interrupted when the ground asks for a retrieval or a deletion.5880

    The 2025 space segment operability standard ECSS-E-ST-70-11C turns this into design requirements. The storage function must be able to store any packetised data generated on board, be sized to hold all engineering telemetry for the specified autonomy period, be able to put the same packet in more than one store, keep stored data retrievable through the standard services after a reconfiguration or cold restart of the managing application process, offer priorities for parallel retrievals from different stores, keep storing while a retrieval or reset is in progress, and manage separate storage devices (for example engineering and science mass memories) independently.80 Storage configuration and contents must survive safe mode and a reconfiguration of the storage unit, and stay accessible through the standard storage and retrieval subservices afterwards, without ground intervention.83

    Mission requirements documents read the same way. The Herschel/Planck operations interface requirements ask for a single centralised storage function in the data management computer, storage of all packets independent of whether they are also sent to the ground, packet stores selectable by APID and packet type, 48 hours of capacity, and retrieval by store, APID and packet time - with the note that the obvious use is to dump the event and telecommand verification packets first at the start of each visibility period.84

    PUS-C splits the service into a storage and retrieval subservice, which stores telemetry packets in packet stores and retrieves them later on ground request, and a packet selection subservice, which decides which reports of which application process may enter which store. A service contains exactly one storage and retrieval subservice and at least one packet selection subservice; how they talk to each other is left out of the standard.14 Each application process hosts at most one provider of each subservice.4 The packet selection subservice can live in the application process that generates the reports, in a process that routes them, or in the process that hosts the storage and retrieval subservice.3 PUS-A described the same choice as a decentralised design, where each generating process selects its own packets, or a centralised one in which one process that sees all telemetry does selection, storage and retrieval.6078 The diagram above is this wiki's summary of that structure.

    4. Packet stores¶

    The packet store is one of the system objects of PUS-C: an object defined and maintained within the scope of a service.5 Within a storage and retrieval subservice each store has a unique packet store identifier; its meaning and internal structure are outside the standard, and the standard suggests the name of an object in memory as an example.6 On the wire the identifier is a fixed character-string in every PUS-C message.42 PUS-A called it the "Store ID", a character string that may for example point to a physical recorder or a file.62

    4.1 What a mission must declare¶

    PUS-C does not fix any of the numbers; it lists what each mission must declare when it specifies its storage and retrieval subservice (requirement letters of clause 6.15.3.1):6

    Req. Declaration Why it matters

    b List of pre-defined packet stores stores that exist without being created
    c (rule) each store is managed by exactly one storage and retrieval subservice one owner per store

    m, n Whether retrievals are prioritised, and the priority policy adds a retrieval priority field to TC[15,9] and TC[15,15]

    4.2 Circular and bounded stores¶

    A circular store overwrites its oldest packets when it is full, so it always holds the most recent packets; a bounded store stops storing (new packets are discarded) when it is full.26 In packet fields the type is an enumerated value with raw value 0 for "circular type" and 1 for "bounded type".54 PUS-A added operational detail that PUS-C dropped: a store used for lost-packet recovery must be circular; a bounded store must be explicitly emptied (at least its oldest part) before it can store again; when a circular store is being downlinked and new packets arrive faster than they can be sent, the downlink wins and "the overwriting pointer shall always stay behind the retrieval pointer"; and the service need not record gaps caused by packets it could not store, because the ground can detect them afterwards.61

    4.3 Time-stamping¶

    Every packet is time-stamped when it is stored, and retrieval works on these storage time tags. Each subservice declares its time-stamping method; PUS-C gives two examples: storage based (the time the packet was stored) and packet based (the on-board time already in the packet's secondary header).78 PUS-A made storage time-stamping optional and only then allowed retrieval by time.60

    Inference

    With packet-based time-stamping, "retrieve from 10:00 to 11:00" means "packets generated between 10:00 and 11:00"; with storage-based time-stamping it means "packets that arrived in the store in that hour". The two differ for packets that waited in an on-board queue, for example reports relayed from an instrument. The standard only names the two methods and leaves the consequence to the mission.

    5. The three status variables¶

    The storage and retrieval subservice keeps three statuses for every packet store. They are the key to the whole service, because almost every request is accepted or rejected according to them.

    6. The storage and retrieval subservice, request by request¶

    Most PUS-C requests carry a list of instructions, one per packet store. Unless the standard says the whole request is rejected, each faulty instruction gets its own failed start of execution notification while the valid ones are still executed.9 Those notifications become ST[01] failed start of execution reports. The usual encoding is a count N followed by N store identifiers; N = 0 means "all packet stores".42

    6.1 Controlling storage: TC[15,1] and TC[15,2]¶

    For every packet it receives, the subservice time-stamps it and writes it into every enabled store whose storage selection criteria it matches.8 TC[15,1] "enable the storage function of packet stores" and TC[15,2] "disable the storage function of packet stores" set the storage status of the listed stores, or of all stores; an instruction naming a store that does not exist is rejected.9

    6.2 Open retrieval: TC[15,14], TC[15,15] and TC[15,16]¶

    Open retrieval is the routine "send me what I have not seen yet" mode. While a store's open retrieval status is "in progress", the subservice reads its packets in storage time-tag order, starting from the store's open retrieval start time tag, and routes them to the store's virtual channel (in priority order if priorities are supported). Suspending and resuming must not create a gap or an overlap in the retrieved sequence.10

    • TC[15,14] change the open retrieval start time tag of packet stores moves the start point. The request carries one time tag and a list of stores (N = 0: all). A time tag in the future rejects the whole request; an instruction for an unknown store or for a store whose open retrieval is in progress is rejected; the "all stores" form changes only the stores that are suspended.11
    • TC[15,15] resume the open retrieval of packet stores sets the status to "in progress" and, if priorities are supported, sets the retrieval priority. If the subservice does not support concurrent retrievals, it rejects a resume for a store whose by-time-range retrieval is enabled. For the "all stores" form the standard adds that each store returns to "suspended" once the last packet stored before the request started executing has been retrieved.12
    • TC[15,16] suspend the open retrieval of packet stores sets the status back to "suspended".13

    Inference

    The no-gap, no-overlap rule is what lets operators split a long dump over several passes (suspend before loss of signal, resume at the next acquisition), and TC[15,14] lets them move the start point back to fetch data again. These uses are this wiki's illustration; the standard states only the mechanisms.

    PUS-C states the "suspend at the end" rule only for the resume-all form of TC[15,15]; for an individual resume it does not say when an open retrieval stops by itself. The 2024 Rev.1 draft resolves this with an explicit per-store open retrieval policy ("suspend" or "stay open", see section 10), which suggests that the 2016 text was found incomplete on this point.

    6.3 By-time-range retrieval: TC[15,9] and TC[15,17]¶

    The by-time-range mode is meant to recover packets lost in the downlink: the ground names a window and the spacecraft re-sends the packets whose storage time tags fall inside it, then switches the by-time-range status back to "disabled" by itself when it reaches the end time.214 Support for this mode is optional and declared per subservice.14

    TC[15,9] "start the by-time-range retrieval of packet stores" carries one or more instructions, each with a store, an optional retrieval priority and the window. An instruction is rejected if the store does not exist; if concurrent retrievals are unsupported and the store's open retrieval is in progress; if the start time is later than the end time; if the window is entirely in the past and the store holds no packet in it; or if a by-time-range retrieval of that store is already enabled.15 TC[15,17] "abort the by-time-range retrieval of packet stores" disables it for the listed stores or for all stores.16

    The field order and types are those of Figure 8-165; the widths are illustrative because PUS-C leaves the integer, character-string and time formats to the mission (see PUS parameter types).44 The real Solar Orbiter layouts are in section 12.

    6.4 Reporting the status: TC[15,18] and TM[15,19]¶

    TC[15,18] "report the status of each packet store" has no application data. The response, TM[15,19] "packet store status report", lists for every store its identifier, storage status, open retrieval status and - if by-time-range retrieval is supported - its by-time-range status.1747

    Field Type
    N unsigned integer
    packet store ID fixed character-string (repeated N times)
    packet store storage status enumerated
    packet store open retrieval status enumerated
    packet store by-time-range retrieval status enumerated, optional

    6.5 Deleting contents: TC[15,11]¶

    TC[15,11] "delete the content of packet stores up to the specified time" carries a storage time followed by N store identifiers (N = 0: all stores). For each store it deletes everything from the oldest packet up to and including the last packet time-stamped at or before that time. It refuses stores that are being retrieved by either mode.1845 PUS-A explains why such a request is needed: a full bounded store must be explicitly emptied, at least its oldest part, before it can store new packets again.61

    6.6 Creating, deleting, reporting and copying stores: TC[15,20] to TC[15,24]¶

    PUS-C standardises what PUS-A left to the missions: the life cycle of the stores themselves.

    • TC[15,20] create packet stores (optional capability) carries one instruction per new store: identifier, size in bytes, type (only if both types are supported) and virtual channel (only if more than one VC is supported). The whole request is rejected if one instruction names an existing store or if two instructions name the same store; an individual instruction is rejected if the maximum number of stores is reached, if memory is insufficient (the criteria are not specified) or if the VC is invalid. A new store starts idle: storage disabled, by-time-range retrieval disabled, open retrieval suspended.19
    • TC[15,21] delete packet stores is mandatory when creation is provided. Only idle stores can be deleted (storage disabled, no retrieval running); the "delete all" form simply deletes every store that is idle.20

    6.8 Summarising the contents: TC[15,12] and TM[15,13]¶

    TC[15,12] "summary-report the content of packet stores" (N store IDs, N = 0 for each store) returns TM[15,13] packet store content summary report.     7. The packet selection subservice¶

    The packet selection subservice decides, per packet store, which reports may be stored. It always controls the reports of the application process that hosts it, can be declared to control others, must be able to handle all reports of the processes it controls, and must always have access to the stores of its storage and retrieval subservice.28

    7.1 The storage-control configuration¶

    For each store the subservice keeps an application process storage-control configuration: a set of definitions, one per controlled application process, each holding zero or more service type storage-control definitions, each holding zero or more report type storage-control definitions (a message subtype).30 An empty level means "everything below": an application process definition with no service types stores every report of that process; a service type definition with no report types stores every report of that service. An empty configuration - no definition at all - blocks every report from that store.303 The subservice knows the application processes it controls but not which service and report types they can generate, so it may accept definitions that mean nothing; keeping them consistent is left to the ground.30 The mission declares the maximum numbers of service type definitions per process and of report type definitions per service type.30

    7.3 Managing the application process configuration: TC[15,3] to TM[15,6]¶

    TC[15,3] add report types to the application process storage-control configuration and TC[15,4] delete report types from the application process storage-control configuration share one nested layout (Figures 8-161 and 8-162):43

    • In TC[15,3], N2 = 0 adds all report types of the process and N3 = 0 adds all report types of the service type. Adding at a coarse level deletes the finer definitions beneath it (adding a whole service type removes its report type list). An instruction is rejected if the process is not controlled, if a maximum is reached, or if it tries to add a report type under a service type (or a service type under a process) that is already stored in full - the standard calls such an addition "meaningless".3543
    • In TC[15,4], N1 = 0 empties the whole configuration, N2 = 0 deletes a process and N3 = 0 deletes a service type. Deleting the last report type of a service type deletes the service type definition, and deleting the last service type deletes the process definition, so the hierarchy never keeps empty levels that would silently mean "everything".3643
    • TC[15,5] report the content of the application process storage-control configuration (one packet store ID) returns TM[15,6] application process storage-control configuration content report with the same nested layout.3743

    9. PUS-A (2003): a different service under the same number¶

    PUS-A's service 15 shares the subtypes 1 to 6 and the storage-selection idea with PUS-C, but the retrieval part is built differently.626364

    10. The 2024 Rev.1 draft¶

    The December 2024 draft ECSS-E-ST-70-41C Rev.1 DIR1 keeps the architecture but tightens the storage and retrieval subservice. It is a draft for review, not an approved standard.

    • A new clause on configuration asks each mission to declare the policy applied when the subservice starts or restarts, and requires storage, routing configuration and retrieval pointers to survive spacecraft mode transitions, such as safe mode or a processor reboot.71
    • Queuing of pending retrieval requests becomes mandatory, with a declared maximum queue length; if priorities are supported, each store gets a default retrieval priority, and the subservice may not limit how many retrievals share one priority level.72
    • Each store gets an open retrieval policy that says whether an open retrieval stays open after the last packet stored before the request has been sent, or suspends.72 Its raw values are 0 "suspend" and 1 "stay open"; TC[15,15] gains an open retrieval policy field, and a retrieval priority of 0 selects the store's default priority.7674
    • New requests: TC[15,10] "abort all requests to copy the packets contained in a packet store selected by time window" (no application data) and TC[15,41] "change the default retrieval priority of a packet store" (store ID, default retrieval priority).7375
    • Storage control per diagnostic parameter report structure is gone: the draft's packet selection subservice defines only the application process, housekeeping and event-blocking configurations, and TC[15,31], TC[15,32], TC[15,37] and TM[15,38] do not appear in its list of service 15 messages.10477

    11. Playback telemetry and virtual channels¶

    PUS-C has no separate playback packet: a retrieved packet is the original packet, routed to the virtual channel associated with its store.106 Virtual channels are system objects declared in the space-to-ground interface specification,56 and PUS-C names "separating real-time data from playback data" as one of their uses.57 The operability standard adds the rules that make this work on the ground: the assignment of VCs to data classes (real-time TM, playback, high-priority TM, critical event log) is agreed with the operator and not changed during the mission; real-time and deferred telemetry must be transmittable at the same time;81 packets of one APID arrive in generation order within a VC, except across separate retrievals from storage, where the original order is not always kept;82 the ground must be able to verify completeness whatever the route; and idle data must not be interleaved while there is real data to send, "e.g. during packet store dumps".83

TC(15,150) re-partitions the OMM in flight; the old contents are lost, packets routed to the memory during the operation are discarded, and newly created stores start disabled.93

    The SSMM implementation has several features that PUS-C also standardises: stores created as "files" with a size in 1 MB sectors, a default virtual channel (0 = OBC VC3, 1 = OBC VC2) and a default downlink priority 0-15; read operations identified by a read ID; bounded and unbounded downlinks; copies between stores with a copy queue.909192106

    Inference: TN issue 7 and the 2025 MIB disagree on a few subtypes

    The ICD is not consistent about the subtypes of the two CSW configuration reports. The request sections announce TM(15,143) (SID storage selection) and TM(15,146) (storage routing table), and the TC(15,5)/TM(15,6) section also points to TC(15,145)/TM(15,146); the report sections and Table 5.1-1 call them TM(15,148) "SID Storage Selection Definition Report" and TM(15,149) "Storage Routing Definition Table Report"; both MIB releases define them as TM(15,155) and TM(15,156).889294106 Likewise, "remove SIDs from storage selection" is TC(15,147) in its section title but subtype 141 in its structure and in Table 5.1-1; the MIB uses 147.9294106 Finally, the ICD's general notes say that, unlike the SSMM, the CSW has no per-store virtual channel,86 while its CSW TC(15,154) and TM(15,152) structures list a VC field (value "VC1");93 the MIB definitions of these two (ZCD00F9A and SPID 14354) have no VC field, which matches the general note.106 The MIB is the database actually used for operations, so this wiki treats it as authoritative where they differ.

    12.3 Real layouts from the MIB¶

    The CSW TC(15,9) ZCD00F09 has a counter "Nb Packet Stores" (range 0-9) whose repeated group has four elements, so the time window is given per store:106101

    This is the PUS-A (15,9) with the PUS-A "Time Span" codes, extended to several stores at once. In SCOS-2000 terms PTC 9 PFC 17 is a 6-octet CUC time (4 octets coarse, 2 octets fine) and PTC 9 PFC 15 a 4-octet coarse-only CUC time.102 The ICD adds that the storage times are coarse seconds with the sub-second field set to zero.89

    The SSMM TC(15,9) ZSM00170 is a different structure that carries two ideas PUS-C also has - a virtual channel and a priority per retrieval:10689

    Mode 1 "retrieve all packets since end of the last retrieval" is, in effect, an open retrieval, and the ICD notes that an unbounded read is mode 1 with the end time set to 0xFFFFFFFF.89

    12.4 Which virtual channel carries the playback¶

    The ICD allocates a fixed virtual channel (VC) to each class of downlink data and fixes the order in which the telemetry encoder serves them: VC4 real-time high-priority TM first, then VC5 critical event log (playback), VC0 real-time TM, VC1 playback from the OBC mass memory, VC2 and VC3 playback from the SSMM, and VC7 idle frames; VC2 and VC3 may carry compressed packets, VC0, VC1, VC4 and VC5 never do.103 The service 15 definitions follow this split:

    • The CSW stores, which live in the OBC mass memory, are played back on VC1:103 the ICD's TC(15,154) and TM(15,152) give "VC1" as the only VC value,93 and the MIB versions of both carry no VC field at all.106
    • The SSMM chooses between its two downlink channels per store (default VC in TC(15,129) "create file" and TC(15,138)) and per retrieval (TC(15,9)): 0 = VC3, 1 = VC2, calibrated in the MIB as CSMT0104TC "SM VCA OBC VC3" / "SM VCB OBC VC2".899091106
    • On the ground, the SCOS-2000 stream IDs of the mission keep the channels apart: 1000 = VC0 real-time non-science, 1001 = VC1 playback non-science, 1002 = VC2 science, 1003 = VC3 file transfer.97

    Inference

    Read together, these sources suggest that VC1 carries the platform playback from the nine CSW stores (housekeeping, acknowledgements, events, diagnostics, dumps and reports), while VC2 and VC3 carry what the SSMM stores. No single source states this end-to-end mapping.

    12.5 Monitoring the stores¶

    All service 15 reports of both implementations except the SSMM TM(15,141) are variable packets (they have a vpd definition). SCOS-2000 cannot use values extracted from variable packets in full telemetry processing (validity, limit checks, synthetic parameters), so such packets should carry special reports rather than regular housekeeping.100 Solar Orbiter accordingly monitors its stores through fixed housekeeping packets:106

    • "DMS OMM Packet Stores" - SPID 19565 (TM(3,25) SID 9 on APID 162) and SPID 19549 (SID 85 on APID 164) - with one enable/disable bit per CSW store and, for each of the nine stores, its ID, type (circular, bounded, undef), available space and size in bytes, start address, both playback pointer addresses, write pointer, first and last valid packet pointers, last downlinked packet pointer, two fields named ARPS1/ARPS2 and an on-board time named nextDwlTmPktObt.
    • "SSMM PS Status TM" - SPID 80246 (TM(3,25) SID 4 on APID 484) - with the number of created and active stores and, for each of 64 stores, flags named "PS Created", "S15 Bounded Active", "S15 Unbounded Act", "S13 Active" and "ST Enabled", the fill level (for example NSM00808 "PS0 Filled"), accumulated data and the bounded and unbounded read IDs.

    Events and failure reports complete the picture: TM(5,1) EIDs 960 "Packet_Store_Down-link_Started" and 961 "Packet_store_Down-link_Ended"; TM(5,3) EIDs 33730-33732 for a full bounded store, an unknown store and a failed mass-memory write; TM(5,2) EID 17344 for an invalid checksum read from the downlink partition; and on APID 161 a block of TM(1,8) failure codes 3841-3900 such as 3842 "Selected store ID does not exist", 3871 "A downlink transfer is already in progress", 3879 "Playback pointer packet not found" and 3900 "packet store is enabled".106

    Inference

    The 38xx failure codes appear to be the CSW's service 15 error space: every description in that range concerns stores, storage control or downlinks. The ICD refers to a separate document ([RD8]) for the failure cases, which is not in this wiki's library.87 The MIB also defines 40 packets on APID 1985 that repeat CSW events with an extra identifier - for example EID 960 with the store ID as second key ("PS_HK Down-link Started" ... "PS_REPORTS Down-link Started"). APID 1985 (process ID 124, packet category 1) lies in the process-ID range 112-127 that the ICD reserves for EGSE, and category 1 is the one reserved for service 1 reports, not the event category 7,96 so these look like ground-side specialisations for display, not spacecraft packets.
