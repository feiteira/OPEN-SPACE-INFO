    ECSS MIB PUS ST21 Sequencing Solar Orbiter Telecommand

    ST[21] Request sequencing¶

    The request sequencing service (service type 21) stores on board an ordered list of telecommand requests and releases them one by one, with a specified delay between one release and the next. Several such request sequences can run in parallel. A sequence can be loaded directly from the ground, with the requests inside the load request, or from a file already stored on board.1 PUS-C presents it, like event-action, as an extension of ground monitoring and control. The executing application process sends the verification reports of each released request to the source named in that request. Releases do not depend on whether earlier requests of the sequence succeeded.1

    Request sequencing is new in ECSS-E-ST-70-41C (2016). It is one of three services into which the PUS-A on-board operations scheduling service was split, together with time-based scheduling and position-based scheduling.2 This page covers the service clause by clause, compares it with its neighbours and with the 2024 Rev.1 draft, and shows how Solar Orbiter, designed to PUS-A, does the same job with a private "TC Sequencer" service 134, while its own service type 21 carries science data.

    Where this page sits

    Packet headers are on PUS packet structures, field types on PUS parameter types. On-board files belong to ST[23] File management. Ground-side command sequences, which SCOS-2000 expands into individual commands before uplink, are a different thing, described on Command sequences in the MIB.

    2. Origins¶

    PUS-A (2003) had no request sequencing service. In its concept clause, a telecommand attached to an on-board event could start a command sub-schedule of the scheduling service, and such a sub-schedule "can contain a predefined command sequence".5 During the preparation of PUS-C, the PUS-A scheduling service was "completely re-assessed resulting in 3 proposed new service types": ST[11] time-based scheduling, ST[21] then called "telecommand sequencing", and ST[22] orbit-based scheduling.2 The 2015 status presentation describes ST[21] in terms close to the final text: it releases "one by one" the telecommands of an on-board sequence, with specified delays, several sequences running in parallel, loaded from an on-board file or from the ground.3 The 2014 presentation lists "load a request sequence by reference" among the standard requests that operate on files.4 The published standard uses the more general word "request".6

    3. Service model¶

    3.1 Layout and accessibility¶

    Each request sequencing service contains at least one request sequencing subservice. An application process hosts at most one provider.8 The mission declares the application processes that the subservice may address. The hosting process is always one of them, and all their requests are assumed usable.9 As with ST[19], a released request is executed by the service that its service type and APID designate. The request counts as generated by the original source, the subservice that sent the load request, and not by the sequencer.9

    3.2 The request sequence¶

    For each subservice the mission declares:10

    • the maximum number of request sequences that can be processed at the same time;
    • the total resources available for storing request sequences;
    • the verification checks applied to the requests contained in sequences.

    Each request sequence has a request sequence identifier, unique within the service. If the sequence is loaded from a file, the identifier "can be used by the loading policy". The sequence contains an ordered list of request entries, and PUS-C sets no maximum on their number. Each entry contains:10

    1. a single request;
    2. a time interval: the delay between the release of this request and the release of the next. For the last entry, it is the delay between the last release and the completion of the sequence.

    For each loaded sequence the subservice keeps a request sequence execution status, "inactive" (raw value 0) or "under execution" (raw value 1).1011

    stateDiagram-v2
  direction LR
  [*] --> Inactive : TC(21,1) direct-load / TC(21,2) load by reference
  [*] --> UnderExecution : TC(21,8) load by reference and activate
  Inactive --> UnderExecution : TC(21,4) activate
  UnderExecution --> Inactive : last release + its interval elapsed
  UnderExecution --> Inactive : TC(21,5) abort / TC(21,13) abort all
  Inactive --> [*] : TC(21,3) unload

    The state machine is drawn from clauses 6.21.5.2 to 6.21.5.8.13141516171819 "UnderExecution" stands for "under execution". Sequences are persistent. They stay loaded after completion, and to remove one automatically "the last request in the sequence can be the request to unload the request sequence".16

    3.3 Timing: a worked example¶

    The interval semantics are easiest to see with numbers. The sequence below is illustrative: three entries with intervals of 10 s, 0 s and 5 s, activated at t0.

    Entry Request Interval Released at Note
    1 R1 10 s t0 released on activation
    2 R2 0 s t0 + 10 s 10 s after R1
    3 R3 5 s t0 + 10 s together with R2 (interval 0)
    - - - t0 + 15 s status returns to "inactive"

    The rules applied are 6.21.4g and 6.21.5.5f.1016 Each interval runs from a release, not from the completion of execution. R2 is released 10 s after R1 whether R1 succeeded, failed or is still executing.1

    3.4 Loading capabilities¶

    A subservice must offer at least one of three ways to get a sequence on board:12

    • direct load (TC[21,1]): the request itself contains the requests of the sequence;
    • load by reference (TC[21,2]): the sequence already exists on board in a file, and the request names that file;
    • load by reference and activate (TC[21,8]).

    If load by reference is offered, the mission declares whether a loading policy is supported. With a policy, the policy, rather than an explicit file path, determines which file holds the sequence.1214 ST[21] does not define the policy itself. The equivalent ST[18] clause for OBCPs refers to ECSS-E-ST-70-01, clauses 5.4.4.4a to c.20

    4. Requests and reports¶

    Every ST[21] request carries exactly one instruction, so a rule violation rejects the whole request with one failed start of execution notification (TM[1,4]). This differs from the per-instruction rejection of ST[19] and ST[20] in the 2016 text.1324 The field types are the PUS-C types:252627

    • the request sequence ID is a fixed character-string (PTC 8, PFC n > 0: n visible ASCII characters, one octet each);
    • file path parts are variable character-strings (PTC 8 PFC 0: a length field followed by that many characters; the PFC of the length field is declared per application process);
    • request is a TC packet (PTC 12 PFC 1), a complete PUS-C telecommand;
    • delay is a relative time (PTC 10), a CUC or CDS offset whose PFC is chosen by the mission.

    4.1 TC[21,1] direct-load a request sequence¶

    The instruction carries the sequence identifier and its ordered list of entries.13

    Field Type Meaning
    request sequence ID fixed character-string identifier of the new sequence
    N unsigned integer number of entries
    request TC packet repeated N times: the request to release
    delay relative time repeated N times: the interval after that request

    Source: Figure 8-228.28 The request is rejected if the identifier is already loaded, if resources are insufficient, or if any contained request fails the declared verification checks. Otherwise the sequence is loaded with status "inactive".13

    The delay field width depends on the mission's choice of PFC. As an illustration, PFC 17 in the relative time table is CUC with (17 + 1) div 4 = 4 octets of coarse time and (17 + 1) mod 4 = 2 octets of fine time:26

    A 10 s delay in this format is 00 00 00 0A 00 00, an illustrative encoding computed from the formula of Table 7-11.26

    4.2 TC[21,2] load a request sequence by reference¶

    The instruction carries the identifier and, unless the loading policy is used, the file path of the on-board file.14

    Field Type Presence
    request sequence ID fixed character-string always
    repository path variable character-string optional (absent when the loading policy applies)
    file name variable character-string optional

    Source: Figure 8-229.29 A file path is the combination of a repository path and an object name, as for any on-board file system.30 Besides the TC[21,1] conditions, the request is rejected if the file does not exist or is not recognised as a request sequence file. A valid request loads the sequence with status "inactive".14 PUS-C names the request sequencing subservice as an example of a service that accesses the file system without going through ST[23].31

    4.3 TC[21,3] unload a request sequence¶

    This request is provided if either load capability is. It carries the sequence ID (Figure 8-230). It is rejected if the sequence is not loaded or is "under execution". Otherwise the sequence is unloaded.1532

    4.4 TC[21,4] activate a request sequence¶

    This is a minimum capability, and it carries the sequence ID (Figure 8-231). It is rejected if the sequence is not loaded, if resources are insufficient, or if the sequence is already under execution. A valid request sets the status to "under execution" and starts releasing. After the last release and the elapse of its interval, the status returns to "inactive".1633 Re-activating a running sequence is therefore an error, not a restart.

    4.5 TC[21,8] load by reference and activate a request sequence¶

    This capability exists if declared. It has the same fields as TC[21,2] (Figure 8-234) and combines the load and the activation in one request.1734 The rejection list is that of TC[21,2] plus activation. In the 2016 text, the lack of resources appears twice, as items 2 and 5.17 The loaded sequence remains loaded (persistent) after completion.17

    4.6 TC[21,5] abort a request sequence¶

    This is a minimum capability, and it carries the sequence ID (Figure 8-232). It is rejected if the sequence is not loaded or is "inactive". A valid request sets it to "inactive" and stops releasing.1835

    4.7 TC[21,13] / TM[21,14] abort all request sequences and report¶

    This capability exists if declared. TC[21,13] has no application data.1936 For each sequence under execution, releasing stops and the status becomes "inactive". One TM[21,14] lists the aborted identifiers: N (unsigned integer), then N request sequence IDs (fixed character-strings).1937

    4.8 TC[21,6] / TM[21,7] execution status of each sequence¶

    This capability exists if declared. TC[21,6] has no application data. TM[21,7] contains one entry for each loaded sequence:383940

    Field Type Meaning
    N unsigned integer number of loaded sequences
    request sequence ID fixed character-string repeated
    execution status enumerated 0 = inactive, 1 = under execution

    4.9 TC[21,9] / TM[21,10] checksum a request sequence¶

    This capability exists if declared. TC[21,9] carries one sequence ID and is rejected if the sequence is not loaded. TM[21,10] returns the ID and the calculated checksum, a 16-bit bit-string, the only field of the service whose size the standard fixes.414243 The algorithm is one of the spacecraft's declared checksum algorithms. PUS-C asks the mission to declare, for each checksum algorithm, the subservice providers that use it, so that all providers that checksum the same data object use the same algorithm. The algorithm also fixes the checksum type (ISO or CRC) and size.44

    4.10 TC[21,11] / TM[21,12] report the content of a sequence¶

    This capability exists if declared. TC[21,11] carries one ID and is rejected if the sequence is not loaded. TM[21,12] returns the ID and the ordered entries in the same layout as TC[21,1]: N, then N pairs of request and delay.454647 Figure 8-238 carries a note pointing to the execution status enumeration, although the report has no status field. This looks like a copy-over from Figure 8-233.47

    4.11 Observables and enumeration¶

    The subservice must expose the list of loaded sequence identifiers and their execution status, as an array sized for the maximum number of sequences that can be loaded at once.48 The status enumeration (Table 8-22) is "inactive" = 0 and "under execution" = 1.11

    5. ST[21] among its neighbours¶

    Service What triggers a release What is stored on board
    ST[21] request sequencing activation, then the delay of each entry; not conditional on earlier results1 ordered lists of (request, delay), loaded directly or from a file12
    ST[11] time-based scheduling the due on-board time2 activities inserted by TC[11,4]22
    ST[22] position-based scheduling the spacecraft reaching an orbit position position-tagged requests, with sub-schedules and groups23
    ST[18] OBCP the procedure's own logic OBCP code, loaded directly (TC[18,1]) or by reference (TC[18,13])2021
    ST[19] event-action an event occurrence one request per event definition49

    The relation to ST[19] is explicit in the standard: an event-action can "start a request sequence".49

    Inference

    The design rationale is this wiki's reading. ST[21] is the light-weight option: it needs no procedure engine and no time-tag arithmetic, and a single TC[21,8] stored as the action of an event-action definition can fire a recovery of any length. The standard does not discuss these trade-offs.

    6. The 2024 Rev.1 draft¶

    The Rev.1 public-review draft (DIR1, December 2024) changes ST[21] more than ST[19] or ST[20]. This wiki's word-by-word comparison found:

    • Directories. A new clause 6.21.5 "Usage of directories" lets the mission declare the maximum number of request sequence directories. Each directory has two attributes: immediate execution of request sequence files after creation, and immediate deletion of request sequence files after execution. A file is "created" in a directory when it is uploaded there or moved or copied into it.50
    • Three new message types: TC[21,15] change request sequence directory attributes, TC[21,16] report the attributes of a request sequence directory, and TM[21,17] request sequence directory attributes report. TC[21,15] and TM[21,17] carry a directory path (variable character-string) and two Booleans, and TC[21,16] carries the path only.5152
    • Identifier type. The request sequence ID changes from a fixed character-string to an enumerated field in every message.53
    • TC[21,8] unloads after completion. Load-and-activate now sets the status to "inactive" and unloads the sequence after the last interval. A reserved identifier value requests "the next free identifier".5455
    • Timing declaration. If TC[21,8] is provided, the mission declares the time needed to activate a sequence and release its first request.56
    • Clarifications. Aborting does not unload a sequence. The duplicated lack-of-resources item is removed. The observables add "reference of the request if activated".5758

    The draft has visible editing residue. Clause 6.21.10 d to f speaks of "the storage and retrieval subservice". Requirement 8.21.2.8c sets "N" to 0 although TC[21,8] has no N field. Clause 8.21.2.15b cites "Figure 8.15-7", 8.21.2.16b and 8.21.2.17b cite Figures 8.21-10 and 8.21-11 (the figures printed under them are 8.21-14 and 8.21-15), and their notes refer to a clause "6.21.911". The stray execution-status note of the 2016 Figure 8-238 is gone from its Rev.1 counterpart, Figure 8.21-11.51555253

    Inference

    The directory attributes standardise a pattern that missions already used. Solar Orbiter's file attribute "TC sequence - immediate" (section 7.2) executes an uplinked TC file as soon as the upload completes. That Rev.1 was influenced by such missions is not stated in the available sources.

    7. Solar Orbiter¶

    7.1 Service type 21 is "science data transfer"¶

    Solar Orbiter follows ECSS-E-70-41A. Like the earlier Herschel/Planck interface requirements, which state that "Science data Packets shall be type 21", it uses service type 21 for Science Data Transfer between the payload and the solid state mass memory (SSMM). The number has nothing to do with PUS-C's ST[21].596061 Packet category 12 is "PRIVATE-SCIENCE or TELECOMMAND", described as exclusive for service 21 telemetry and for telecommands.62 In the 2025 MIB, all 334 service 21 packet definitions and the APIDs of all 5,449 commands that have one (for example APID 236 of the CSW system control process) use category 12.71 Table 5.1-1 makes the service mandatory for payloads.63

    Message Content (SOL.S.ASTR.TN.00079 §5.22)
    TC(21,1) / TC(21,2) enable/start and disable/stop science transfer to the SSMM, as defined by each instrument; at least one pair is required
    TM(21,3) fixed length, with a 1-octet structure ID (SSID, 0-255) selecting the parameter list
    TM(21,4) fixed length, no SSID
    TM(21,5) variable-length "anonymous data stream": SSID (1 octet), N (2 octets), then N data words
    TM(21,6) variable length with fixed start and end parameter blocks around a repeated block of N1 entries
    TC(21,128) Reset Output Buffer (listed in Table 5.1-1 only)

    Source: §5.22.1 to §5.22.6 and Table 5.1-1.6163

    The 2025 MIB holds 334 service 21 packet definitions and 33 commands.71

For TM(21,3), (21,5) and (21,6), the MIB identifies the SSID as the 8-bit field at octet 16 (pic).71

    7.2 The real counterpart: private service 134 "TC Sequencer"¶

    What PUS-C calls request sequencing, Solar Orbiter's CSW provides as service 134, TC Sequencer. The service is reserved for the CSW. It manages "TC Sequences (also called TC Files)": files of telecommand packets uploaded beforehand with service 13, which Solar Orbiter calls "Large Data Transfer" (the PUS-C counterpart is ST[13] large packet transfer). Execution reads the packets in order and releases them "at a given rate, with potentially some delays between chosen consecutive TCs".6563

    • The upload attribute selects TC File - Delayed, executed on request by TC(134,1), or **TC File
    • Immediate**, executed automatically after a successful upload, "the intended mechanism for MTL uploading".65 For an immediate file the CSW creates a TC(134,1) itself, with TC sequence identifier 1 and a rate of 1 Hz.66
    • Sequences are controlled by a logical TcSeq ID. Per ID there can be at most one queued sequence, waiting while another sequence with the same ID runs.65
    • At software initialisation, service 134 executes the selected back-up timeline file in the safeguard memory and so loads the mission timeline queue with back-up time-tagged TCs. At least two file placeholders allow one to be updated safely.67
    • Among the source IDs that the ground sets, 111 is "TC Sequences", next to 110 for the mission timeline and 112 for event-action recovery commands.68
    Message Fields PUS-C analogue
    TC(134,1) Start TC Sequence TcSeq ID (1), Partition ID (1), File ID (4), TC Exec Rate (4, float) TC[21,8] load by reference and activate
    TC(134,2) Abort TC Sequence TcSeq ID, Partition ID, File ID TC[21,5]
    TC(134,3) TC Sequence Wait Delay Delay (2 octets, multiples of 125 ms); used only inside a sequence the per-entry delay
    TC(134,4) TC Sequence Set Frequency TC Exec Rate (4, float); used only inside a sequence (no analogue)

    Source: §5.28.1 to §5.28.4.6970 The receiving functions must be able to keep up with the selected rate.69

    The two models of time differ. PUS-C puts a delay in every entry. Solar Orbiter releases at a base rate and inserts TC(134,3) "wait" commands, which may only appear inside a sequence, where a longer gap is needed. A 16-bit count of 125 ms steps allows gaps of up to 65,535 × 0.125 s = 8,191.875 s, about 2 h 16 min. This figure is arithmetic on the field definition, not stated in the source.70 Neither the TN service list nor the MIB has telemetry of type 134, so Solar Orbiter has no equivalent of TM[21,7], TM[21,10] or TM[21,12].6371

    Inference

    With no service 134 reports, the ground presumably follows TC file execution through the verification reports of the released TCs (source ID 111) and through CSW housekeeping. The sources do not describe how sequence status is monitored.

    7.3 Service 134 in the MIB¶

    Both MIB releases contain TC(134,1) to TC(134,4) (ZCD08601-ZCD08604) and two subtypes absent from the issue 7 ICD: TC(134,5) "Start Two Part Id TC Sequence" (ZCD08605, shortened to "Start Two Part Id TC SEQ" in 2025) and TC(134,6) "Abort Two Part Id TC Sequence" (ZCD08606). These add a "Storage Partition ID" octet between the partition ID and the file ID. TC(134,6) has no rate field.7172 All are addressed to APID 172 (process ID 10, DMS). Both partition parameters use the calibration CCDT0192TX, with values such as OMM_TC_FILES_A = 161, OMM_TC_FILES_B = 177, SGMA_TC_FILES = 193 and SGMB_TC_FILES = 195.71

    The 2025 release adds seven canned TC(134,5) commands that start FDIR TC files. The 2020 release has only the generic ZCD08605:7172

    Command Description TcSeq ID File ID (hex) Rate (Hz)
    ZCDX8605 Execute Loss-of-UL FDIR TC File 58 00840010 1
    ZCDX8606 Execute SNAFU FDIR TC File 54 00440010 1
    ZCDX8607 Execute REC_SpW3_SpW OL FDIR TC File 53 00340010 10
    ZCDX8608 Execute REC_SSMM1 A FDIR TC File 53 00340020 10
    ZCDX8609 Execute REC_SSMM1 B FDIR TC File 53 00340030 10
    ZCDX8610 Execute REC_SSMM2 A FDIR TC File 53 00340040 10
    ZCDX8611 Execute REC_SSMM2 B FDIR TC File 53 00340050 10

    All seven use partition OMM_TC_FILES_A with storage partition OMM_TC_FILES_B.71 The first two are the actions of the event-action definitions ZCSX1301 and ZCSX1302. On an unexpected loss of uplink, or on the AOCS event chosen for "SNAFU", the CSW's event-action service starts the corresponding TC file, which is exactly PUS-C's "event-action starts a request sequence" pattern.7149

    Inference

    "Two Part Id" plausibly means that the file is identified by a pair of partitions, here the A and B copies of the OMM TC-file area, so that the sequencer can fall back to the other copy. The five SpaceWire and SSMM recovery files (ZCDX8607 to ZCDX8611) share TcSeq ID 53, so under the rule of at most one queued sequence per ID they cannot run in parallel: while one runs, only one other can wait. Neither reading is stated in the available sources.

    In ground sequences, TC(134,1), TC(134,2) and TC(134,6) are used once each and TC(134,5) twice.71
