    ST[05] Event reporting¶

    The event reporting service, service type 5 of the Packet Utilization Standard, is how a spacecraft tells the ground that something happened: a failure or anomaly detected on board (including by FDIR - failure detection, isolation and recovery), the start, progress or end of an activity initiated from ground or autonomously, a built-in test result, or a normal payload event.1 Each report carries a severity (informative, low, medium or high), encoded in the message subtype to make ground detection and routing easier, and an event definition identifier that, together with the APID of the reporting application process, tells the ground exactly which event occurred and how to read the auxiliary data that follows.2

    Events are also an on-board currency. They feed the event-action service ST[19], on-board control procedures (ST[18]), the on-board monitoring service ST[12] raises them, and the forwarding and storage services can block them per event definition.7202425 This page covers the PUS-C definition (clauses 6.5 and 8.5), the PUS-A one (clause 10), the tailoring data of ECSS-E-ST-70-31C, the 2024 draft, the SCOS-2000 event packet mechanism of the MIB, and a data-driven tour of the 7 156 service 5 packet definitions of the public Solar Orbiter MIB.

    Item Value
    Service type 5, "event reporting"11

    Providers per application process at most one3

    1. Concept¶

    1.1 Events, event definitions and event reports¶

    PUS-C defines an event report simply as a report related to the occurrence of an event, generated by a subservice provider; it is one of three report kinds, next to verification reports and data reports.18 The service exists to report information of operational significance that the provider-initiated reports of other services do not already carry.1

    The standard separates three notions:

    Notion What it is Identified by
    Event report type one of four, by severity; all low-severity reports share TM[5,2], and so on message subtype16
    Event definition one detectable event, its severity, its identifier and its auxiliary data event definition system identifier = APID of the hosting application process + event definition identifier, unique within that APID4
    Event notification one occurrence: the event definition identifier plus the auxiliary data, if any carried in exactly one event report of the definition's severity5

    The note to clause 5.3.5.4 explains the design: since all reports of one severity share one message type, the message type cannot say which event happened, so the standard adds event definitions, each tied to a single event and a single event report type.16

    1.2 Severity levels¶

    Subtype PUS-C name PUS-A name Typical meaning
    1 informative event report Normal/Progress Report normal progress, autonomous action not related to a fault
    2 low severity anomaly report Error/Anomaly Report - Low Severity anomaly of low severity
    3 medium severity anomaly report Error/Anomaly Report - Medium Severity anomaly of medium severity
    4 high severity anomaly report Error/Anomaly Report - High Severity anomaly of high severity

    Names from PUS-C clause 6.5.4 and PUS-A clause 10.2-10.3.52829 Neither standard defines what each level implies operationally; missions do. Solar Orbiter, for example, uses "low" for warnings needing no recovery action, "medium" for anomalies requiring ground recovery action, and "high" for anomalies requiring on-board recovery action (section 8.1).56

    PUS-A explains why severity sits in the header: event reports are infrequent and often unexpected, so they should be unambiguous, by flagging the severity in the data field header to ease ground detection and routing, and by including auxiliary data so that the ground understands context and cause.26

    • Every on-board monitoring service is associated with exactly one event reporting subservice, which catches the events it raises; a check definition can name an event definition for each kind of violation (below low limit, above high limit, unexpected value, delta thresholds), raised when the new checking status is established.202122
    • The event-action subservice is associated with at least one event reporting subservice and must be able to react to all of its event reports.23
    • The real-time forwarding control service keeps an "event report blocking forward-control" definition per application process, listing event definition identifiers whose reports are not forwarded to ground; the storage and retrieval service has the equivalent per packet store.2425
    • PUS-C notes that event reports are used by the ground but also by on-board functions such as event-action services and OBCP engines, which is why disabling an event definition also stops those on-board reactions (section 4.3).78

    The event definition identifier is an enumerated field and the auxiliary data a deduced field whose presence and structure follow from the definition; their sizes are mission choices.1219

    4. The messages field by field¶

    4.1 TM[5,1] to TM[5,4]: the event reports¶

    All four reports have the same source data field:12

    Field Type Presence Meaning
    event definition ID enumerated always Together with the APID, identifies the event definition - and therefore the presence and structure of the auxiliary data.12
    auxiliary data deduced deduced presence Context and cause of the occurrence, as declared for that event definition.124

    A subservice that supports enabling and disabling generates an event notification for an occurrence only if the definition is enabled; one that does not support it reports every occurrence. Each notification goes into one event report of the definition's severity.5

    Inference: the time of an event

    The PUS-C event report has no time field of its own.12 This wiki reads that as relying on the time stamp of the TM packet secondary header, unless a mission adds a time to the auxiliary data. PUS-C does not say whether that time stamp is the occurrence time or the report generation time; Solar Orbiter's ICD defines the packet time as the time "when the generation of the packet was started".52

    4.2 TC[5,5] enable and TC[5,6] disable the report generation¶

    Both requests have the same application data:13

    Field Type Meaning
    N unsigned integer Number of instructions.
    event definition ID enumerated, repeated N times Event definition to enable or disable.

    The subservice keeps, for each detectable event, an event report generation status (enabled or disabled).6 Processing is per instruction: an instruction naming an unknown event definition is rejected with a failed start of execution notification, and the valid instructions of the same request are executed regardless.78 Valid instructions set the status to "enabled" or "disabled".78

    4.3 What "disabled" really means¶

    PUS-C is explicit: disabling the report generation of an event definition means the ground is no longer told about occurrences and the on-board services configured to react to those event reports are not triggered either. It does not prevent on-board software from catching the occurrence directly, without going through event reports.8 The standard gives the reduction of on-board processing load as an example reason to disable reporting.8

    stateDiagram-v2
  direction LR
  state "ENABLED - each occurrence gives a TM[5,x]" as EN
  state "DISABLED - not reported, no ST[19] or OBCP reaction" as DIS

  [*] --> DIS: initial status declared disabled
  EN --> DIS: TC[5,6] instruction
  DIS --> EN: TC[5,5] instruction

    State per event definition, from clauses 6.5.5.1-6.5.5.3.678

    4.4 TC[5,7] report the list of disabled event definitions and TM[5,8]¶

    TC[5,7] has no application data. The response TM[5,8] lists every event definition whose status is "disabled":149

    Field Type Meaning
    N unsigned integer Number of disabled event definitions.
    event definition ID enumerated, repeated N times A disabled event definition.

    4.5 Observables¶

    For each severity level the subservice must expose: the accumulated number of detected occurrences, the number of disabled definitions, the accumulated number of generated reports, the event definition identifier of the last report, and the generation time of the last report.10 These are typically made available as on-board parameters that housekeeping can sample.

    Inference

    The last sentence is this wiki's reading: PUS-C defines the observables but does not prescribe how they reach the ground.

    5. PUS-A (ECSS-E-70-41A) differences¶

    Aspect PUS-A (2003) PUS-C (2016)
    Report identifier RID (Report ID), enumerated; with the APID it implicitly defines the parameters field29 event definition ID, enumerated; with the APID it identifies the event definition12
    Auxiliary data "Parameters", type Any, optional, following structure rules set #1 with standard data types2932 "auxiliary data", deduced, deduced presence12
    Enable/disable data NRID (unsigned integer, omitted if only one RID per request) + RID repeated30 N always present + event definition ID repeated13

    Initial status, destination, observables not specified declared / defined6510

    PUS-A capability sets: the minimum set is the four reports (subtypes 1-4); the additional set is subtypes 5 and 6, each requiring the other.31 PUS-A's scope lists three families of events (failures or anomalies detected on board, autonomous on-board actions, normal progress of operations), noting that one report can combine several, for example a unit switched off because a temperature exceeded its limit.27 PUS-C's list is similar but has four items, adding FDIR detections explicitly, hardware built-in test results and normal payload events.1 The motivation PUS-A gives for disabling reports is also processing load.28

    5.1 Tailoring data in ECSS-E-ST-70-31C¶

    ECSS-E-ST-70-31C, which models the PUS-A service, asks a mission database for:3435

    Item Type Meaning
    S5 ST5 and ST6 Provider Boolean event reports can be enabled and disabled
    S5 Multiple RIDs Boolean several RIDs per enable/disable request (if the above is TRUE)
    S5 RID PFC of PTC 2 size of the report identifier field
    S5 NRID PFC of PTC 3 size of the repetition counter (if multiple RIDs)
    RID (per event) PTC 2 the unique identifier of each event raised by the service

    6. Changes in the 2024 Rev.1 draft¶

    ECSS-E-ST-70-41C Rev.1 DIR1 (11 December 2024) changes the service in five ways:

    1. New TC[5,9] "generate event report", by declaration: one instruction carrying an event APID, an event severity, an event definition identifier and optional event data (a variable-length octet string); it is rejected for an invalid APID, severity or identifier, and otherwise generates the requested event report packet.394142
    2. The event list must include at least all asynchronous error conditions that any subservice can raise and that request verification does not report, for example a telecommand not dispatched on time by time-based scheduling or data lost on file swapping by file data storage.36
    3. Instead of an initial status per event, a configuration policy for start and restart of the subservice is declared, which includes the initial statuses.37
    4. TC[5,5] and TC[5,6] carry an ordered list of instructions and are rejected as a whole if any instruction names an unknown event definition; otherwise the instructions are executed in order.38
    5. TM[5,8] reports an empty list with N = 0.40

    Editorial loose ends in the draft

    In DIR1 the interface clause of TC[5,9] refers to system clause 6.5.5.4 and to "Figure 8.5-5", while the system requirement is 6.5.5.5 and the figure is numbered 8.5-8. In the Annex C table (Table C-8 in the draft) the rows for TC[5,5] and TC[5,9] both show "b" in the system-clause column, and the TC[5,9] row gives 8.5.2.5 instead of 8.5.2.9 as its interface clause.4142 These are draft-stage inconsistencies, not technical changes.

    7. Ground segment: SCOS-2000¶

    7.1 No special service 5 processing - but a general event mechanism¶

    The SCOS-2000 Database Import ICD states that SCOS-2000 has no specific processing of service 5 packets. Instead it can associate the generation of an event of a given severity and text message with any received TM packet; these events are stored (visible in retrieval) and distributed live to operators, with configurable severity depending on their role.43

    "Events & Actions (EVAC)" is one of the SCOS-2000 functions listed in a 2003 ESA Bulletin description of the system.50 The association between a TM packet and an event is made per packet in the PID table:4445

    PID field Type Meaning
    PID_DESCR Char(64) Packet description; also the message text of the SCOS-2000 event packet.
    PID_EVENT Char(1) N no event (default), I event of severity Info, W Warning, A Alarm.
    PID_EVID Char(17) Optional event number; the full event ID becomes TPKT_OBE::nnnn. The ICD suggests 1-9999, because other SCOS-2000 events use 5-digit numbers from 10000.

    Because the on-board event definition identifier is a field inside the packet, the MIB needs an extra identification rule to tell event definitions apart: the PIC table gives, per type/subtype (and optionally APID), the offset and width of up to two additional identification fields, and the packetiser then looks up PID with APID, type, subtype, PI1 and PI2 to find the packet's SPID.4746 An APID-specific PIC entry takes precedence over a type/subtype-only one.47

    sequenceDiagram
  participant S as Spacecraft
  participant P as SCOS-2000 TM packetiser
  participant D as MIB (PIC, PID, PLF/VPD)
  participant E as Event and alarm handling
  participant A as Archive
  S->>P: TM[5,4] APID 215, event ID 0xE389 + auxiliary data
  P->>D: PIC(5,4,215)? none - use PIC(5,4): PI1 at octet 16, 16 bits
  P->>D: PID(type 5, subtype 4, APID 215, PI1 58249, PI2 0)
  D-->>P: SPID 27318, PID_EVENT = A, PID_DESCR = "REC_PCDU3 - FMON_PCDU3_A PCDU A Failure"

  P->>E: SCOS-2000 event packet, severity Alarm, message = PID_DESCR
  P->>P: extract parameters (PLF) for displays

    The flow combines the ICD rules with real rows of the Solar Orbiter MIB.474474

    7.2 Other SCOS-2000 event sources¶

    Events can also be generated on ground from telemetry values: a monitoring check of type E in OCP raises an event with full ID BEHV::<parameter> when the parameter leaves the specified range, which can trigger system actions such as an e-mail or a script; such checks are not shown as out-of-limits.48 The Solar Orbiter MIB defines no check of type E (it uses only C, D, H and S checks).77 Archived events can later be retrieved from the archive; the EDDS user manual, for instance, lists "Packet Ev" requests returning raw event packets and "Event Record Report" requests returning events with their ID, category, time stamp, severity and message.51

    8. Solar Orbiter: the space-to-ground ICD¶

    Solar Orbiter uses PUS-A (ECSS-E-70-41A) as its applicable standard (see PUS packet structures).53 Its ICD extends service 5 considerably.

    8.1 Categories, size and routing¶

    • Four categories: TM(5,1) normal progress; TM(5,2) low criticality (warning, no recovery action required); TM(5,3) medium criticality (ground recovery action required); TM(5,4) high criticality (on-board recovery action required). Typically "low" events are just stored for downlink, while "high" events always have a predefined recovery response by the central software.56
    • Event reports are one of the prime means of controlling day-to-day operations.56
    • The source data field must not exceed 40 bytes (exceptions agreed with ESA); the event ID is 2 bytes, Enumerated, and the parameters field at most 38 bytes, its structure defined by the combination of event ID and APID.5758
    • Event IDs are unique per process ID (PID).57
    • A generated event can be recorded in the Safe Guard Memory (SGM) Critical Event Log (CEL) for medium and high levels, forwarded to ground, recorded in the OBC mass memory (OMM), and/or forwarded to service 19.57
    • Event packets use packet category 7, "Event generation", which is exclusive to service 5 and to TM(17,2).68

    8.2 The Critical Event Log¶

    The CEL combines a linear buffer holding the first m events and a circular buffer holding the last n; in a burst, the first m and last n events survive. An occurrence counter per event ID keeps track of history even when the buffers overflow. One TC reads the buffers and the occurrence table (possibly producing several TM packets) and one TC clears all three together to keep them consistent.57

    Inference: the EGSE-range APIDs

    1 465 event packets sit on APIDs 1954-1991 (process IDs 122-124), a range the ICD allocates to EGSE.69 Most of them share a single event ID per APID (for example 33537, 33538 or 33539) and are told apart by an 8-bit second identification field at octet 18; their descriptions (for example "S_TCS2 TCL 13 Temperature Level 2_LO", "S_MAG12_LO") look like monitoring transition messages. Their exact role is not stated in the available sources.

    9.2 How SCOS-2000 recognises them¶

    PIC has one generic rule per event subtype - first identification field at octet 16, 16 bits wide, no second field - which is exactly the 2-byte event ID right after the 16 octets of packet headers (a 6-octet primary header and the 10-octet Solar Orbiter TM data field header).7354 Twenty-five APID-specific PIC rules, all on the EGSE-range APIDs 1954-1991, add a second field at octet 18 or 19 (8, 16 or 32 bits) for APIDs that reuse one event ID for several packet layouts.73 The same rule (octet 16, 16 bits) appears in the SWA instrument database, and a 2001 packet ICD for the HIFI test-equipment interfaces (TEI) of Herschel places its 16-bit "Event ID" at the same byte position 16-17 of TM(5,4).7980

    The mapping to SCOS-2000 severities is uniform:73

    On-board report PID_EVENT SCOS-2000 event severity
    TM(5,1) I (1 374) Info
    TM(5,2) W (1 159) Warning
    TM(5,3) A (2 911) Alarm
    TM(5,4) A (1 698) Alarm
    TM(5,130/132/134) empty (default N); N for the PHI TM(5,134) none

    PID_EVID is empty for every packet in the database, so all events get the default event ID. Service 1 failure reports TM(1,2) and TM(1,8) are also mapped to A (274 and 1 477 packet definitions) - see ST[01].73

    The SWA instrument database delivered by the instrument team defines the same 248 SWA event packets with PID_EVENT = 'N'; in the spacecraft MIB they carry I/W/A.7973

    Inference

    The severity mapping is therefore applied when instrument databases are merged into the spacecraft MIB, not by the instrument teams.

    10. Worked examples¶

    10.1 Decoding a high-severity event (real layout, illustrative values)¶

    The layout below is the real one of SPID 27318 in the MIB PLF table; the byte values are illustrative, constructed for explanation.74

    Octets Bytes (illustrative) Parameter Decoded
    0-5 08 D7 C0 05 00 1D primary header TM, APID 215 (0b0001101_0111: process 13 platform, category 7 events), stand-alone, count 5, data length 29
    6-15 (10 octets) data field header type 5, subtype 4, time (CUC, 4 + 2 octets)54
    16-17 E3 89 NCD05011 EID 58249 = FMON_09; 0b11... = high severity
    18-21 00 00 00 09 NCD8E093 FMON ID 9
    22-23 00 03 NCD8E098 Nb of cycles 3
    24 01 NCD8E099 logic type AND
    25-28 00 00 00 2A NCD8E09B SMon ID 42
    29 06 NCAB0UJ0 current check status OUT_OF_LIMIT
    30-35 3B 9A CA 00 80 00 NCAB0UM0 time stamp coarse 1 000 000 000 s + 0.5 s

    The packet is 36 octets, matching TPCF_SIZE = 36. Its data field is 30 octets, so the Space Packet data length field holds 30 - 1 = 29 (0x001D). Its 20 octets of source data respect the ICD limit of 40 octets of source data.57 The auxiliary data come from Solar Orbiter's private service 142 "Functional Monitoring" (two of the parameter descriptions begin with "OBCHP_S142_"), which serves FDIR by grouping service 12 monitors into a Functional Monitor (FMON) evaluated with AND/OR logic.71 The event therefore says which FMON triggered, after how many cycles and with which logic, then - judging by the description of NCD8E09B, OBCHP_SMon_Mon_ID, an inference - which service 12 monitoring ID was involved, its check status, and when.

    11. Other missions¶

    The Herschel/Planck Operations Interface Requirements Document (2003) asks for three event packet types - normal events, progress reports and warnings; exceptions requiring on-board action; errors and anomalies requiring ground action - and requires that anomaly reports carry a unique identification, the time of occurrence and the data relevant to the detection. To save bandwidth, only transitions to and from an anomaly state are reported, with a minimum period before the same event can be reported again, and the two anomaly types are also stored in a Critical Events Log that can be read and cleared by dedicated telecommands.81 The same CEL idea reappears in Solar Orbiter (section 8.2). See Herschel and Planck.
