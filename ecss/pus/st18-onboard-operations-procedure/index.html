    ST[18] On-board operations procedure¶

    An on-board control procedure (OBCP) is a small program that runs on the spacecraft itself: it sends telecommands, reads telemetry parameters, waits, tests and branches, much as a ground operator's procedure would, but without waiting for the ground. Service type 18 of the Packet Utilization Standard is the ground's handle on these programs. It loads them into an interpreter called the OBCP engine, starts and stops them, holds and resumes them step by step, passes them values while they run, and reports their state.12 ECSS-E-70-41A ("PUS-A", 2003) called it the on-board operations procedure service; ECSS-E-ST-70-41C ("PUS-C", 2016) calls it "on-board control procedure" in clause 6.18 and "on-board operations procedure" in its Annex C.4138 This page covers the PUS-C service completely - both subservices, the execution state machine, the observability levels, every message type and its data fields, the rejection rules - then the PUS-A service, the 2024 Rev.1 draft, SCOS-2000 support, and the OBCP commands and reports of the real Solar Orbiter MIB.

    Where this page sits

    OBCPs are one of several on-board automation tools. Commands released at a given time come from ST[11] time-based scheduling, commands triggered by an event from ST[19] event-action (which can itself start an OBCP), and fixed command lists from ST[21] request sequencing. OBCP files can be uploaded with ST[23] file management or, on PUS-A missions, ST[13] large packet transfer. Every request an OBCP releases is verified through ST[01].

    2. Why OBCPs exist¶

    PUS-A explains the idea: besides standard services, a mission may have a set of procedures, loaded from the ground, that resemble the stepwise procedures executed on the ground. They can in principle also be started autonomously on board, for example when an event is detected. The language they are written in is out of scope, but each procedure must be built from logical steps so that it can be suspended and resumed at step level, and it can receive run-time parameters when started or while running.39 An event-action definition can start a procedure, which is how OBCPs become part of on-board fault management.40

    The 2025 operability standard ECSS-E-ST-70-11C defines an on-board operations procedure as a monitoring and control procedure stored on board whose activation is under ground control.51 It requires that the spacecraft can execute ground-loaded and ground-controlled OBCPs, more than one at a time; that an OBCP can send any command available to the ground and read any engineering telemetry parameter available to the ground; and that OBCP execution can be prioritised, for example to favour fault management procedures when they conflict.52

    Mission documents show what this buys in practice. For Herschel/Planck a "principle mode of operation" was the execution of pre-defined OBCPs started from the mission timeline, written in a Spacecraft Control Language and able to send commands, test parameters and branch; the document's example powers on an instrument, checks its current, waits for its boot, checks its housekeeping, sends it a time update and logs success with an event.53 The same document requires load, start, stop, suspend, resume, delete and dump of OBCPs, passing parameters without first suspending, inspecting OBCP data at any time, listing the stored OBCPs and managing multiple triggering of the same OBCP.54

    3. The PUS-C model¶

    3.1 Subservices, engine and host¶

    PUS-C defines two subservice types. The OBCP management subservice is the interface to the engine and lets the ground control the on-board execution of OBCPs; the OBCP engine management subservice starts and stops the engine itself.23 A service has exactly one of the first and at most one of the second; if both are present they live in the same application process, and an application process hosts at most one provider of each.4 Each service is tied to exactly one OBCP engine and keeps an OBCP engine status ("running" or not), which exists even when there is no engine management subservice to change it.4

    flowchart LR

  G -- "TC[18,21] / TC[18,22]" --> EM["OBCP engine management<br/>subservice"]
  F[("on-board files<br/>(ST[23])")] -. "load by reference" .-> E
  M --> E["OBCP engine<br/>(loaded OBCPs, status, traces)"]
  EM --> E
  E -- "requests released by OBCPs" --> X["executing services<br/>(any addressable APID)"]

  E -- "observability events" --> EV["ST[05] event reporting"]

    The diagram is this wiki's summary of clauses 6.18.1-6.18.4. The mission declares which application processes the service may address; the host process is always among them, and all requests of the addressable processes may be used. When an OBCP releases a request, the service type and APID in the request decide who executes it; that executing service generates the verification reports, and sends them to the process hosting the OBCP service.5 The service must be able to read every on-board parameter accessible to the addressable processes.6

    3.2 Code, arguments, parameters and steps¶

    The OBCP code is the form of a procedure that the engine can load and execute. An OBCP can declare arguments, values it expects when its execution starts, and parameters, values it expects to receive while executing; PUS-C refers to ECSS-E-ST-70-31 (see ECSS-E-ST-70-31C) for both. The OBCP itself, not the management subservice, checks that the values it receives are valid.2 Following ECSS-E-ST-70-01, a procedure can contain steps - sequences of source statements that are its smallest operational units - and each step is represented in the OBCP code by exactly one step identifier.2

    Each OBCP has a unique OBCP identifier; when an OBCP is loaded from a file, the identifier can drive the loading policy.7 PUS-C's general checksum clause 5.4.4 uses OBCPs as its example: a mission declares which subservice providers use each checksum algorithm, so that an OBCP file checksummed both by the OBCP service and by a memory service is checksummed the same way by both.28

    4. Execution status and its state machine¶

    For every OBCP loaded in the engine, the management subservice keeps an execution status: inactive, active and running or active and held. "Held" means suspended; an OBCP that is waiting for an event is still "running"; "active" covers both running and held.9 Raw values are 0, 1 and 2.37 The diagram, drawn by this wiki from the requirements of clause 6.18.4, shows which request moves an OBCP between states:

    stateDiagram-v2
  [*] --> Inactive: TC[18,1] direct-load / TC[18,13] load by reference
  [*] --> Running: TC[18,19] load by reference and activate
  Inactive --> Running: TC[18,3] activate
  Inactive --> Held: TC[18,14] activate and execute one step
  Running --> Held: TC[18,5] suspend (end of step)
  Held --> Running: TC[18,6] resume
  Held --> Held: TC[18,15] resume and execute one step
  Running --> Inactive: end of execution / TC[18,4] stop / TC[18,12] abort / TC[18,17] abort all
  Held --> Inactive: TC[18,4] stop / TC[18,12] abort / TC[18,17] abort all
  Inactive --> [*]: TC[18,2] unload / TC[18,20] / TC[18,22]
  Running --> [*]: TC[18,20] stop and unload / end of a TC[18,19] OBCP / TC[18,22] stop engine
  Held --> [*]: TC[18,20] stop and unload / TC[18,22] stop engine
    • An OBCP activated by TC[18,3] stays loaded (inactive) after it ends; one started by TC[18,19] is removed from the engine when it ends.1415
    • "Execute one step" runs the OBCP until the next step identifier is raised and then freezes it in "active and held".23
    • Stop and suspend act at the end of a step - the current one, or a named one - while abort freezes execution immediately.161821
    • Stopping the engine aborts every OBCP, unloads all of them and sets the engine status to "not running".27

    5. Observability levels¶

    How much the ground sees of a running OBCP is set by its execution observability level. Each mission declares which of the four levels it supports:8

    Level (raw) Events raised
    no-observability (0) none
    at-procedure-level (1) one event each time the status changes to running (activation, resume), to held (suspend, completion of execution of a step) or to inactive (successful or failed completion, abort, stop)
    at-step-level (2) the procedure-level events plus one event for every step reached
    at-detailed-level (3) the step-level events plus mission-declared events, for example the start of an activity, a branch (an IF or a loop) or a statement

    837

    The events are issued as ST[05] event reports by a declared event reporting subservice; their auxiliary data include the OBCP identifier and the condition that caused the event. PUS-C notes that ground-initiated activations, suspensions, resumptions, stops and aborts can also be seen in the verification reports of the requests, and that procedure-level observability is especially useful for OBCPs started autonomously from within an OBCP.8 The level is chosen in the activation request (if selectable) and can be changed for active OBCPs with TC[18,16] "set the observability level of OBCPs", which takes effect immediately: the events of the new level are enabled and those of the old level disabled.1425 Its application data are N followed by N pairs of OBCP ID (fixed character-string) and observability level (enumerated).35

    6. The requests in detail¶

    Almost every ST[18] request contains exactly one instruction, and a faulty request is rejected as a whole with a failed start of execution notification (reported through ST[01]). The exception is TC[18,16], which can carry several instructions that are checked one by one.1125 Nearly every request is rejected if the engine is not running.1127

    6.1 Loading: TC[18,1], TC[18,13] and TC[18,19]¶

    The service must offer at least one way to load an OBCP into the engine: direct load, where the request carries the code, or load by reference, where the code is already in an on-board file and the request names that file (or lets the ECSS-E-ST-70-01 loading policy pick the file).10

    • TC[18,1] direct-load an OBCP carries the OBCP identifier, the code and - if checksums are verified - the checksum, which the subservice checks before loading. The OBCP is then inactive, and the engine stores its identifier and checksum.11
    • TC[18,13] load an OBCP by reference carries the identifier and, unless the loading policy is used, the file path (repository path and file name). If checksums are verified, the code in the file is checksummed before loading (the checksum is in the file or a file attribute).127
    • TC[18,19] load by reference and activate an OBCP combines loading with activation; the OBCP is removed from the engine and its identifier freed when it ends.15

    The field order and the 16-bit checksum are from Figure 8-196; the PFC of the length field is declared per application process, as for every variable-length octet-string.3029

    Message Fields (in order)
    TC[18,1] direct-load an OBCP OBCP ID (fixed character-string); OBCP code (variable octet-string); checksum (bit-string, 16 bits, optional)
    TC[18,13] load an OBCP by reference OBCP ID (fixed character-string); file path = repository path (variable character-string) + file name (variable character-string), optional
    TC[18,19] load by reference and activate an OBCP OBCP ID; file path (optional); observability level (enumerated, optional); argument values (deduced, deduced presence)
    TC[18,2] unload an OBCP OBCP ID

    303436

    6.2 Unloading: TC[18,2]¶

    TC[18,2] "unload an OBCP" is mandatory whenever direct load or load by reference exists. It removes an inactive OBCP from the engine and cleans all information about it, so that its identifier can be reused.13

    6.3 Activating: TC[18,3]¶

    TC[18,3] "activate an OBCP" carries the identifier, the observability level (if selectable) and the argument values (if the OBCP has arguments). The subservice removes the execution trace of any previous run, enables the observability events of the chosen level, sets the status to "active and running" and starts the OBCP with its arguments.14

    The presence and structure of the argument values follow from the definition of the OBCP named by the identifier - a "deduced" field in PUS terms.31 See PUS parameter types for deduced fields.

    6.4 Stopping and aborting: TC[18,4], TC[18,20], TC[18,12] and TC[18,17]¶

    • TC[18,4] stop an OBCP carries the identifier and a step ID; step ID 0 means "at the end of the current step". If the OBCP is running, the subservice waits until it finishes that step (or reaches the named step), freezes the remaining statements, clears pending "stop at step" settings and sets it inactive. When several stop requests are pending, the OBCP stops at the first of the steps reached.1631
    • TC[18,20] stop and unload an OBCP does the same and then unloads the OBCP and cleans the engine.1736
    • TC[18,12] abort an OBCP freezes the remaining statements immediately and sets the OBCP inactive.18
    • TC[18,17] abort all OBCPs and report freezes every OBCP, sets every active one inactive and answers with TM[18,18] aborted OBCP report: N followed by the N identifiers of the aborted OBCPs.1935

    6.5 Suspending and resuming: TC[18,5], TC[18,6], TC[18,14] and TC[18,15]¶

    TC[18,5] suspend an OBCP (identifier and step ID, 0 = end of current step) waits for the end of the step, freezes execution and sets "active and held"; several pending suspends act at the first step reached. TC[18,6] resume an OBCP (identifier only) unfreezes a held OBCP where it was frozen and sets it running; it must exist whenever suspend exists.21223132

    TC[18,14] activate and execute one OBCP step activates an inactive OBCP exactly like TC[18,3] (same fields) but freezes it again as soon as the first step identifier event is raised. TC[18,15] resume and execute one OBCP step then advances a held OBCP to the next step identifier event and freezes it again.2334 Together they let the ground run an OBCP one step at a time.

    Message Fields
    TC[18,4] stop / TC[18,5] suspend / TC[18,20] stop and unload OBCP ID (fixed character-string); step ID (enumerated; 0 = end of current step)
    TC[18,6] resume / TC[18,12] abort / TC[18,15] resume and execute one step OBCP ID
    TC[18,14] activate and execute one step OBCP ID; observability level (optional); argument values (deduced)

    3132333436

    6.6 Passing parameters: TC[18,7]¶

    TC[18,7] "communicate parameters to an OBCP" passes parameter values to an active OBCP: an identifier followed by the values, whose structure is driven by the OBCP's definition.2432 This is the PUS-C form of the PUS-A ability to change a running procedure's parameters.

    6.7 Reporting: TC[18,8] and TM[18,9]¶

    TC[18,8] "report the execution status of each OBCP" has no application data. TM[18,9] "OBCP execution status report" lists, for each loaded OBCP, its identifier, its checksum (if checksums are verified) and its execution status.2033

    The required observables are the engine running status and, for each loaded OBCP, its identifier, its execution status and - when it is running or suspended - its current step.26

    6.8 The engine: TC[18,21] and TC[18,22]¶

    TC[18,21] "start the OBCP engine" and TC[18,22] "stop the OBCP engine" have no application data. Starting runs the declared engine initialisation procedure and is refused if the engine is already running; stopping aborts all OBCPs, unloads them all and sets the status to "not running".2736 The engine management subservice has no observables.27

    8. PUS-A (2003)¶

    PUS-A identifies a procedure by a Procedure ID (a character string of mission-defined length) and its steps by Step IDs.     9. The 2024 Rev.1 draft¶

    The December 2024 draft keeps the same subtypes, 18 requests and 2 reports,57 but changes several of them:

    • It adds that the service starts the OBCP engine automatically at initialisation; that the mission declares the list of event reporting subservices whose event reports the OBCP service can catch; and that it declares the configuration policy applied when the engine management subservice starts or restarts.585960
    • TC[18,2] becomes "unload OBCPs": N followed by N OBCP IDs, with N = 0 unloading all OBCPs. The whole request is rejected if any instruction names an OBCP that is not loaded or is active, and the instructions are executed in order.6162
    • TM[18,9] gains a step ID per OBCP: the step being executed for a running OBCP, the next step to execute for a held one. The subservice observables are redefined the same way.636466
    • TC[18,16] is now rejected as a whole if any of its instructions is faulty, and its instructions are executed in order.65
    • The engine management subservice gets observables, to be declared by the mission.67

    It is a draft for review, not an approved standard.

    10. Ground support in SCOS-2000¶

    The SCOS-2000 database import ICD states that SCOS-2000 has no specific processing of service 18 packets and no specific limitation for them.69 The generic PUS support covers what the service needs: variable-length octet strings (the OBCP code of a direct load) can be encoded in telecommands, although they are not decoded natively in telemetry; and deduced parameter fields - argument and parameter values - are supported, while a deduced data structure is not.7071 A command parameter of category P ("Parameter ID") lets an operator give an on-board parameter by its telemetry name, which SCOS-2000 encodes as the parameter's on-board identifier PCF_PID.7273

    11. Solar Orbiter¶

    11.1 The tailoring¶

    Solar Orbiter's TM/TC and packet structure ICD tailors PUS-A. An OBCP there is "an interpretable program" compiled on the ground with a dedicated compiler and uploaded with service 13 into one of the file partitions; the ground controls OBCPs mainly through service 18, but they can also start autonomously, for example on an event. Each OBCP has an "OBCP ID", an execution status inactive, running or held, and optional "Step ID" markers placed by the designer to report progress. OBCPs run in the OBCP interpreter in a dedicated RAM area: an OBCP is copied from its storage area (for example the OBC mass memory) into one of a limited number of execution slots, which is why the service offers an "auto-delete" option at the end of execution. An OBCP runs with "normal" or "emergency" priority, and only one emergency OBCP can run at a time.76

    The service is implemented in the central software only (CSW, APID 172). It keeps the PUS-A subtypes 5-9 and replaces load, start, stop and delete by private subtypes (the last column is this wiki's mapping to PUS-C):8285

    The generic ZCD2Z00R "Load and start OBCP (1-byte parameters)" shows the TC(18,140) structure as the MIB encodes it:8579

    The named variants fix all or most of these fields. For example ZCD2Z01E "Load and start OBCP (SWA1)" is built only from fixed areas (CDF_VALUE in hexadecimal):8574

    Bits Element Fixed value Meaning (from the ICD field definitions)
    0-31 OBCP ID 61940010 OBCP 0x61940010

    Inference: structured OBCP identifiers

    The 35 named load-and-start commands use OBCP IDs whose upper 16 bits match the owner named in the command: 0x6022 DMS, 0x6032/0x6034 SSMM, 0x6042 STR, 0x6081 TTC, 0x6114 EUI, 0x6124 MAG, 0x6132/0x6134 METIS, 0x6142/0x6144 PHI, 0x6154 RPW, 0x6164 SOL(OHI), 0x6174 SPICE, 0x6184 STI(X) and 0x6192/0x6194 SWA, with the low bits numbering the procedures (for example SWA1, SWA2, SWA3, SWA5, SWA6 and SWA7 = 0x61940010, 0x61940020, 0x61940030, 0x61940050, 0x61940060 and 0x61940070). The ICD does not document an OBCP ID numbering scheme; this pattern is deduced from the MIB values.85

    Some named OBCPs take start parameters. ZCPX0003 "Load and start OBCP (TTC2)" has 44 elements (8 fixed areas, 18 fixed and 18 editable parameters). Its fixed parameters of category P (the ICD's "Parameter ID" type; MIB description "Datapool parameter ID") hold telemetry parameter names such as NCPTT000 "TTC2_HPTM_RATE", which SCOS-2000 encodes as the parameter's on-board ID PCF_PID; each is followed by an editable value.857273

    11.3 Reports and monitoring¶

    TM(18,9) "OBCP List Report" (SPID 14405) is a variable packet repeating, for N OBCPs (16 bits), the OBCP ID (32), checksum (16), state (8), instruction pointer (16) and current step ID (16).8578 The state calibration CCDT0124TM reads 0 FREE, 1 LOADING, 2 INACTIVE, 3 RUNNING, 4 HELD; the ICD lists only values 1-4.8578 TM(18,144) "OBCP telemetry" (SPID 14406), produced cyclically when enabled by TC(18,142), carries the OBCP ID, checksum, N and N pairs of OBCP parameter ID (32 bits) and current value, the value being a deduced parameter (PTC 11) whose type follows from the parameter ID.8581 The housekeeping packets "DMS OBCP Details" (TM(3,25) SID 10 on APID 162, SPID 19566, and SID 86 on APID 164) show, among 847 parameter positions, the emergency queue entries with their OBCP ID and "IsStart&Load", "IsAutoDelete" and "IsUsed" flags.85
