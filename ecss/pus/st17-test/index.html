    ECSS MIB PUS Service 17 Solar Orbiter Telecommand Testing

    ST[17] Test¶

    The simplest question an operator can ask a spacecraft is "are you there?". Service type 17 of the Packet Utilization Standard answers it. Its core is the are-you-alive connection test: the ground sends TC[17,1] to an application process, and if the process is alive and both the uplink and downlink routes to it work, a TM[17,2] report comes back. PUS-C adds an on-board connection test, in which one on-board process checks that another one responds, and the 2024 draft adds a variable-size version of the are-you-alive test for checking long telecommands.13516 The service type is meant to hold the test functions of a mission, most of which are mission specific.12 This page covers every message of the service in ECSS-E-ST-70-41C ("PUS-C", 2016), compares it with ECSS-E-70-41A ("PUS-A", 2003) and the Rev.1 draft, and shows how the real Solar Orbiter MIB defines connection tests for its central software, mass memory, star trackers and ten science instruments.

    Where this page sits

    The test reports travel like any other telemetry, and the test commands are verified like any other telecommand: see ST[01] request verification and PUS packet structures. On the ground, the expected reports are configured as verification stages, described in Command verification in the MIB.

    2. Why a test service¶

    PUS-A placed the service under the concept of off-line testing: for troubleshooting or validation before use, an on-board unit or process can be run "off-line", outside any active control loop but with its normal outputs in telemetry, and each application process should offer a set of mission-specific end-to-end test functions under ground control. As a minimum, a standard "are you alive" function tests the end-to-end connection between the ground and an application process.15 ECSS-E-ST-70-31C describes the generic test in the same terms: a ground request makes the on-board test service generate a standard report, which confirms that the uplink and downlink routes work and that the process can do basic work, including telecommand processing and telemetry packet generation.19

    The 2025 operability standard ECSS-E-ST-70-11C makes the capability a requirement under testability: the space segment must provide end-to-end tests of any on-board application process, exercisable under ground control, with an "are you alive" function as the example. The same clause asks for off-line operation of redundant equipment for testing, health checks of unused units before use, and test modes that neither disable fault management nor trigger it with off-line data.20

    Mission requirements say the same. The Herschel/Planck operations interface requirements ask for an "are you alive" function between the ground and the data management system or any other on-board intelligent user, implemented as an "I am alive" response; the test between the data management system and an intelligent user is performed by the data management system itself, and the ground can ask it to start one.21 That last requirement resembles what PUS-C standardises as the on-board connection test TC[17,3] (section 4).

    3. The are-you-alive connection test: TC[17,1] and TM[17,2]¶

    Every test subservice provides it. A request TC[17,1] "perform an are-you-alive connection test" contains exactly one instruction, with no argument; the subservice answers with exactly one TM[17,2] "are-you-alive connection test report", which says only that the hosting application process is alive and has received the request.3 Both packets have an empty data field: the TC has no application data and the TM no source data.7

    What the report proves is spelled out in two notes. The end-to-end connection is achieved "when the application process is alive and the communication to the application process is active"; and its reception on the ground confirms that the uplink and downlink routes between the ground and the process work and that the process performs a minimum set of functions.3

    The verification reports in this diagram come from ST[01] and depend on the acknowledgement flags of the TC; PUS-C does not prescribe their order relative to TM[17,2], so the order shown is this wiki's illustration.

    Inference: what a connection test does not prove

    A TM[17,2] shows that a TC reached the process, was decoded and dispatched to the test subservice, and that the process could build and send a report. It says nothing about the process's other functions, and since the report has no data it cannot carry a test pattern. The variable-size test of the 2024 draft (section 6) fills that gap for the uplink path.

    4. The on-board connection test: TC[17,3] and TM[17,4]¶

    The second PUS-C test is between two on-board application processes: the one that hosts the test subservice and executes the request, and the one named in the request.5 The mission declares which application processes can be tested this way (the host itself is not in that list) and, for each of them, what counts as a successful test.4

    • TC[17,3] "perform an on-board connection test" carries exactly one instruction holding the identifier of the application process to test.5
    • A request naming a process outside the declared list is rejected with a failed start of execution notification.5
    • Otherwise the subservice tests the connection. If the declared criteria are met, it generates one notification carrying the tested process's identifier, sent as one TM[17,4] "on-board connection test report"; if not, it generates a failed completion of execution verification report instead.5

    How the host actually tests the target is left to the mission: PUS-C only asks for the list and the success criteria to be declared.4 The diagram's mapping of the notifications to TM[1,4] and TM[1,8] follows the PUS-C report types of ST[01].

    A discrepancy in PUS-C

    Clause 6.17.4.2a says the capability to perform an on-board connection test "shall be declared", i.e. it is optional, while Annex C, Table C-25, marks TC[17,3] as "minimum".58 A mission tailoring PUS-C has to decide which reading applies. The 2024 Rev.1 draft aligns the annex with the clause: its Table C-25 marks TC[17,3] "by declaration".18

    The standard defines no observables for the test subservice.6 ESA's 2015 status presentation, which counts per clause and service type the discrepancy reports (DRRs) processed after the 2014 public review of the draft, gives ST[17] 2 DRRs, the fewest of any service type.22 The service is listed with all others in the PUS message type catalogue.

    6. PUS-A and the 2024 Rev.1 draft¶

    PUS-A defined only the end-to-end connection test: (17,1) "Perform Connection Test" with no application data, and (17,2) "Link Connection Report" with no source data; its capability table calls the report "Connection Test Report". Both are the minimum capability set, and no additional capability was defined.1314 PUS-A requires the report to be a one-shot report generated by the application process, and its reception to confirm that the routes work and that the process performs a minimum set of functions, which includes telecommand processing.12 ECSS-E-ST-70-31C lists no tailoring choices for this service.19

    Topic PUS-A (2003) PUS-C (2016) Rev.1 draft (2024)
    Ground-to-process test (17,1) / (17,2) TC[17,1] / TM[17,2] (renamed "are-you-alive") unchanged
    Process-to-process test - TC[17,3] / TM[17,4] unchanged
    Variable-size test - - TC[17,5] / TM[17,6]
    Failure path not defined TC[17,3]: failed start (unknown APID) or failed completion (criteria not met) unchanged

    The draft's variable size are-you-alive connection test (clause 6.17.5) is a declared capability. TC[17,5] carries an arbitrary connection test data string of variable length, up to the maximum telecommand length; the subservice returns the same string in TM[17,6]. The draft notes that this allows a test command of arbitrary length, in particular of the maximum telecommand length.16 Both data fields are a variable octet-string ("test data").17

    The structure of a variable-length octet-string - a length field followed by that many octets, with the length PFC declared per application process - is defined in PUS-C clause 7.3.8.9 The draft is not an approved standard; Solar Orbiter solved the same problem with a private subtype (section 8.4).

    7. Ground support in SCOS-2000¶

    The SCOS-2000 database import ICD says there is no specific processing of service 17 packets in SCOS-2000 and no specific limitation.23 In practice a connection test is an ordinary command whose expected TM[17,2] is not modelled by the service: the ground configures the acknowledgement flags and verification stages of the command like any other (see Command verification in the MIB), and the TM[17,2] report is an ordinary packet definition in pid.24

    8. Solar Orbiter¶

    8.1 The tailoring¶

    Solar Orbiter's TM/TC and packet structure ICD (SOL.S.ASTR.TN.00079, issue 7) tailors PUS-A and calls service 17 "Connection Test". Its objective and description repeat the PUS-A text. The service is mandatory for all users: (17,1) and (17,2) are marked as implemented by the central software (CSW), the solid state mass memory (SSMM) software and the star tracker (STR) software, and as mandatory for payload software.2625 It defines four subtypes:25

    Subtype Name (ICD) Data Notes
    TC(17,1) Perform Connection Test none test between the ground and an on-board application process; result in TM(17,2) and the TM(1,x) reports; a TM(1,8) only applies to the CSW, not the SSMM
    TM(17,2) Connection Test Report none sent when the test succeeds
    TC(17,3) Request Connection Test PID (enumerated, 1 octet); time-out (unsigned, 1 octet, seconds, > 0) asks the CSW to perform a connection test by TC(17,1) to the given process ID, with a time-out
    TC(17,128) Test Command of Maximum Length filler (TBD in the ICD) on reception a TM(17,2) is generated; filler parameters build a maximum-size packet; described as SSMM only

    TC(17,3), which Table 5.1-1 marks for the CSW only, is Solar Orbiter's private counterpart of the PUS-C on-board connection test: the CSW tests another process by sending it a real TC(17,1).2625 Solar Orbiter's packet category table reserves category 7, "event generation", for service 5 events and TM(17,2), which is why every Solar Orbiter TM(17,2) has an APID ending in category 7.27

    Observations from the table:

    • For MAG, SoloHI, SPICE and SWA the TM(17,2) comes from a different process ID than the one the TC(17,1) was sent to (for example SWA: TC to PID 95, report from PID 99). The ICD allocates several process IDs to each instrument, so both are the same instrument.27
    • Only one TM(17,2) has any content: EPD's SPID 52006 defines a 16-bit parameter NID00048 "CRC" at byte offset 16, right after the 16-octet headers; all other TM(17,2) definitions are header-only.33
    • ZYP66999 "PSS Test TC" targets APID 1948, process ID 121, inside the 112-127 range that the ICD reserves for EGSE; the meaning of "PSS" is not stated in the available sources.2733

    Inference

    The differences in verification intervals (4 s for EUI, up to 180 s for SoloHI completion) presumably reflect how long each instrument's software needs to answer through the OBC, but the MIB records only the values, not the reasons.

    8.3 TC(17,3) "Request Connection Test"¶

    The CSW command ZCD01103 has two parameters:3325

    The calibration CCDT0126TX "Process IDentifier reach" lists exactly the process IDs the CSW can reach for this test: the three SSMM processes (30-32), the two star trackers (40, 41) and the payload process IDs 50-104 - but not the CSW itself, matching the PUS-C rule that the host process is not in the list of testable processes.334 The MIB also defines a TM(5,2) event, EID 17472 "TM_Timed_Out_Connection_Request_Received_(TM_17-2)", on APID 167.33 Its exact trigger is not stated in the available sources.

    8.4 TC(17,128) "Test Command of Maximum Length"¶

    The SSMM variants ZSM00265, ZSM00266 and ZSM00267 consist of 59 fixed 32-bit areas, all 0xDEADDEAD: 1 888 bits, or 236 octets of application data.33 That is exactly the largest Solar Orbiter application data field: a TC packet data field holds at most 242 octets, made of the 4-octet data field header, 236 octets of application data and the 2-octet packet error control.29 With the 6-octet primary header the packet is 248 octets long, the maximum uplink length the ICD mentions elsewhere.30 The PSS variant ZYP66998 has the same length filled with 0xAAAAAAAA; the star tracker variants (ZST17128, ZSTX7128, ZST27128, ZSTX7228) are 14 elements, 416 bits (52 octets), with the values 0x5A, 0xFFFFFFFF and 0xFFFFFF.33 Although the ICD text describes TC(17,128) as SSMM-only, its service table marks the subtype "X" (implemented) for the SSMM and STR software and "O" (optional) for payload software, with no mark for the CSW, and the MIB defines both SSMM and STR variants.252633

    8.5 Worked example: a TC(17,1) to the CSW, byte by byte¶

    The bytes below are illustrative: the APID, service type, subtype, acknowledgement flags and header layout are real (from the MIB and the ICD), while the sequence count (0) and the source ID (120, the ICD's "direct commands" ground source) were chosen for the example. The CRC was computed by this wiki with the PUS CRC (polynomial \(x^{16}+x^{12}+x^5+1\), register preset to all ones).103133

    Octets Hex Meaning
    0-1 18 AC version 0, TC, secondary header present, APID 172
    2-3 C0 00 stand-alone packet, sequence count 0
    4-5 00 05 packet data field of 6 octets
    6 19 PUS version 1, ack 1001
    7-8 11 01 service 17, subtype 1
    9 78 source ID 120
    10-11 EA 91 CRC over octets 0-9

    The whole packet is 12 octets, the minimum for a Solar Orbiter PUS telecommand, because it has no application data. For comparison, the same packet sent to the SSMM (APID 492) would be 19 EC C0 00 00 05 19 11 01 78 DA 0D, and a TC(17,3) asking the CSW to test process 30 (OP_SSMM) with a 10-second time-out, sequence count 1, would be 18 AC C0 01 00 07 19 11 03 78 1E 0A 8B 7F (all illustrative, CRCs computed by this wiki).33 The header fields are explained on PUS packet structures and a complete real command is built step by step in the TC worked example.

 WHERE l.PLF_SPID IN (SELECT PID_SPID FROM pid WHERE PID_TYPE = '17');
-- verification stages per command (cvp/cvs use generic COLn names: cvp COL1 = task, COL3 = stage;
-- cvs COL1 = CVS_ID, COL2 = type, COL3 = source, COL4 = start, COL5 = interval)
SELECT c.CCF_CNAME, s.COL2, s.COL1, s.COL4, s.COL5 FROM ccf c
  JOIN cvp v ON v.COL1 = c.CCF_CNAME JOIN cvs s ON s.COL1 = v.COL3 WHERE c.CCF_TYPE = '17';
SELECT c.CDF_CNAME, c.CDF_BIT, c.CDF_ELLEN, c.CDF_PNAME, p.CPC_PTC, p.CPC_PFC, p.CPC_PRFREF, p.CPC_PAFREF
  FROM cdf c LEFT JOIN cpc p ON p.CPC_NAME = c.CDF_PNAME WHERE c.CDF_CNAME = 'ZCD01103';
SELECT * FROM pas WHERE PAS_NUMBR = 'CCDT0126TX' ORDER BY CAST(PAS_ALVAL AS INT);
SELECT CDF_CNAME, COUNT(*), SUM(CDF_ELLEN), GROUP_CONCAT(DISTINCT CDF_VALUE) FROM cdf
 WHERE CDF_CNAME IN (SELECT CCF_CNAME FROM ccf WHERE CCF_TYPE = '17' AND CCF_STYPE = '128') GROUP BY 1;
SELECT PID_TYPE, PID_STYPE, PID_APID, PID_PI1_VAL, PID_DESCR FROM pid WHERE PID_PI1_VAL = '17472';
-- swa-idb.sqlite
SELECT CCF_CNAME, CCF_DESCR, CCF_APID FROM ccf WHERE CCF_TYPE = '17';
