    ECSS PUS Scheduling Services Telecommand

    ST[22] Position-based scheduling¶

    ST[22] position-based scheduling is the PUS-C service type that keeps telecommands on board and releases each one when the spacecraft reaches a chosen point on its orbit, instead of at a chosen time. It is the orbit-position counterpart of ST[11] time-based scheduling: the ground loads requests together with a position tag (an orbit number plus a position on that orbit), and the on-board subservice releases them when that position comes round. The standard does not say how the spacecraft knows where it is; that is left to the mission.1 Because an orbit position comes back on every revolution, ST[22] also offers something ST[11] does not: persistent activities that stay in the schedule and fire again on a later orbit.26

    Why schedule by position?¶

    PUS-C groups ST[22] with ST[11] and ST[19] event-action as service types that hold requests and release them when something happens: a time, an orbit position, or an event.50 Position-based scheduling extends ground monitoring and control. The application process that executes a released request sends its verification reports directly to the source named in the request, that is, the ground application that loaded it. The release of a request does not depend on whether earlier released requests succeeded or failed.2 The released request is not generated by the scheduling subservice: it remains a request of the original source.4

    The two scheduling services are built from the same template. Subtypes 1 to 27 have the same numbers and the same names, with "time" replaced by "position", and every capability of ST[11] has a positional twin:4647

    Aspect ST[11] time-based ST[22] position-based

    Insertion guard time margin: release time must be at least current time + margin48 position margin: release position must be at least current position + margin8
    Release accuracy maximum delta time between tag and real release, declared48 maximum delta position between tag and real release, declared8
    Shifting time-shift: TC[11,7], TC[11,8], TC[11,15]47 position-shift: TC[22,7], TC[22,8], TC[22,15]46
    Repeating activities not offered: Table C-17 ends at TM[11,27] with no persistency fields4749 optional persistent activities with a periodicity in orbits6
    Extra request - TC[22,28] set the orbit number10

    Core concepts¶

    Position tag: orbit number plus angle¶

    Every position tag has two parts: the orbit number and the position on that orbit. The orbit number never wraps round during a mission, while the position within the orbit is cyclic. The orbit number increases on board by itself, and the ground can set it with TC[22,28].5 The position is an angle measured in the plane of the osculating inertial orbit, starting from its intersection with the Earth-fixed equatorial plane. The 2016 standard goes no further: the algorithm and the accuracy used to compute the angle are mission-specific.5

    \[ \text{position tag} = (n, \theta), \qquad n \in \mathbb{N} \text{ (orbit number, never wraps)}, \qquad \theta \text{ (angle on the orbit, cyclic)} \]

    The bit layout of a position tag, and of the delta position used to shift activities, is not fixed by the standard either: both must be declared when the subservice is specified, which is why clause 8 types them as "deduced".27 A deduced field (PTC 11, PFC 0) has a structure that follows from preceding fields of the same packet or from mission constants.54

    Inference

    The standard compares positions ("earlier than", "greater than", "in the order of their release positions") without spelling out the ordering. Since the orbit number is monotonic and the angle is cyclic, the natural order is lexicographic: first by orbit number, then by angle. This wiki uses that reading in its examples.

    Scheduled activities¶

    The schedule is a set of scheduled activities. Each one holds the request to be released and its scheduling data:82

    Element Present when Meaning
    Request always the telecommand packet to release later
    Position tag always release position (orbit number, position on orbit)
    Activity persistency status persistent scheduling supported persistent or non-persistent
    Persistent activity periodicity persistent scheduling supported (and status persistent, on the wire) an integer number of orbits
    Sub-schedule ID sub-schedules supported the sub-schedule the activity belongs to
    Group ID groups supported the group the activity belongs to

    A scheduled activity is identified by the request identifier of the request it contains. PUS-C builds that identifier from the source ID (the application process user identifier of the originator), the destination (APID plus system identifier), and the packet sequence count or request name.852 On the wire, ST[22] reports and requests carry it as three fields: source ID, application process ID and sequence count.2030

    Persistent scheduling¶

    By default an entry is deleted once its request is released. If the subservice supports persistent scheduling, each activity carries an activity persistency status. A non-persistent activity is deleted after release; a persistent one stays in the schedule and can be released again or deleted later.6 When a persistent activity's release position is reached, the subservice adds its persistent activity periodicity (an integer number of orbits) to its orbit number. The activity therefore comes back every k orbits at the same angle.138

    Sub-schedules¶

    A sub-schedule is a sequence of position-tagged requests that together perform one coherent on-board operation. Sub-schedules are created automatically when an insert request names an unknown one, and they are deleted when they become empty. A new sub-schedule starts in the disabled state.212 Each sub-schedule has a status, enabled or disabled, and the mission declares the maximum number that can exist at the same time.14

    Groups¶

    A group is a second, independent way to switch requests on and off. It works regardless of the destination application process and of the sub-schedule. Groups typically map to spacecraft entities such as a unit or a piece of software, and the standard's example is an instrument whose requests are held back while its conditions are not met. Unlike sub-schedules, groups are created and deleted by explicit request and may exist while empty.217 A group that still has activities cannot be deleted.18

    The margins¶

    Two declared quantities protect the schedule:8

    • the position margin: an activity can only be inserted or shifted if its release position is at least the current position plus the margin. This keeps the schedule consistent at all times;
    • the maximum delta position: the largest allowed gap between the release position in a scheduled activity and the position at which the request is really released.

    Schedule execution¶

    The execution function¶

    The whole schedule has an on/off switch, the position-based schedule execution function status. It is disabled when the subservice starts. TC[22,1] enables it and TC[22,2] disables it, whether or not the schedule contains activities. TC[22,3] resets the schedule: it disables the function, deletes every activity, deletes all sub-schedules (if supported) and re-enables all groups (if supported).911

    stateDiagram-v2
  [*] --> Disabled : subservice start
  Disabled --> Enabled : TC[22,1]
  Enabled --> Disabled : TC[22,2]
  Enabled --> Disabled : TC[22,3] reset (schedule emptied)
  Disabled --> Disabled : TC[22,3] reset (schedule emptied)

    Release logic¶

    The execution process handles activities in order of release position. An activity counts as disabled if the execution function is disabled, if its sub-schedule is disabled, or if its group is disabled. When an activity's release position is reached, the process runs these steps in order:13

    flowchart TB
  R["Release position of an activity reached"] --> D{"Disabled?<br/>(function, sub-schedule<br/>or group disabled)"}
  D -- no --> REL["Release the request to its<br/>destination application process"]
  D -- yes --> SKIP["Request not released"]
  REL --> P{"Persistent scheduling<br/>supported?"}
  SKIP --> P
  P -- no --> DEL["Delete the activity"]
  P -- yes --> PS{"Activity<br/>persistent?"}
  PS -- no --> DEL
  PS -- yes --> INC["Orbit number += periodicity<br/>(activity stays in the schedule)"]
  DEL --> E{"Sub-schedule<br/>now empty?"}
  E -- yes --> DSS["Delete the sub-schedule"]
  E -- no --> END["Done"]
  INC --> END
  DSS --> END

    Three consequences are worth spelling out, because they are easy to get wrong in an implementation or a ground model:13

    • A disabled activity is not kept for later. When its position passes, it is deleted (or, if persistent, moved on by its periodicity) exactly as if it had been released.
    • The standard prescribes no notification to the ground when a request is deleted without having been released.
    • The release order of activities with exactly the same position is not prescribed.

    A small inconsistency in Annex C

    The system clause says the capability to report sub-schedule status (TC[22,18]) requires the capability to enable sub-schedules.16 Annex C nevertheless marks TC[22,18] "by declaration", whereas its ST[11] twin TC[11,18] is marked "requires TC[11,20]".4647

    Data fields, message by message¶

    The structure diagrams of clause 8 give field names and PUS field types but no sizes: the enumerated and unsigned integer widths are chosen by the mission, and position fields are "deduced". Fields marked optional are present or absent at mission, application process or service level (for example, the sub-schedule ID exists only if sub-schedules are supported). A "repeated N times" block is an array: for a variable-length array the count N is sent first, for a fixed-length one N is known implicitly. Every ST[22] array is of the first kind, with an explicit N field.53 See PUS parameter types for the field types.

    Requests without application data¶

    TC[22,1], TC[22,2], TC[22,3], TC[22,16], TC[22,17], TC[22,18] and TC[22,26] have no application data field at all.284043

    TC[22,4] insert activities into the position-based schedule¶

    Field Type Presence Meaning
    sub-schedule ID enumerated optional (sub-schedules supported) sub-schedule for all activities in this request; created (disabled) if unknown
    N unsigned integer always number of activities that follow
    repeated N times: group ID enumerated optional (groups supported) group of this activity
    position tag deduced always release position; structure declared by the mission
    activity persistency status enumerated optional (persistent scheduling supported) non-persistent = 0, persistent = 1
    persistent activity periodicity unsigned integer deduced presence: only when the status is persistent period in orbits
    request TC packet always the complete telecommand packet to release

    This is Figure 8-240.29 The sub-schedule ID is per request, while group, position and persistency are per instruction, mirroring the system requirements.12 The embedded request is a full PUS telecommand packet, which PUS-C types as PTC 12, PFC 1.55

    Checks. The whole request fails its start of execution if it would create a sub-schedule beyond the declared maximum. Each instruction is then checked on its own and rejected if the schedule is full, if it names an unknown group, if its position is inconsistent with the planned orbit, if it is non-persistent and earlier than current position plus margin, or if the embedded request fails the declared verification checks. Valid instructions are executed even when others in the same request fail.12

    Effect. For each valid instruction a new scheduled activity is created with the given request, position tag, persistency status, sub-schedule and group. A persistent activity whose position is already below current position plus margin is moved forward by its periodicity as many times as needed, rather than rejected.12

    Requests that identify activities by request ID¶

    TC[22,5] (delete), TC[22,9] (detail-report) and TC[22,12] (summary-report) all carry a list of request identifiers; TC[22,7] (position-shift) puts one delta position in front of the list, and that delta applies to every listed activity.3032343723

    Field Type Present in Meaning
    delta position deduced TC[22,7] only shift to apply; format declared by the mission
    N unsigned integer all four number of request IDs
    repeated N times: source ID enumerated all four originator of the scheduled request
    application process ID enumerated all four destination APID of the scheduled request
    sequence count unsigned integer all four packet sequence count of the scheduled request

    An unknown request identifier makes only its own instruction fail (failed start of execution); the others are still processed. Deleting the last activity of a sub-schedule deletes the sub-schedule too.23

    N2 + N2 × group ID unsigned integer + enumerated optional (groups supported) zero or more groups

    The window types and their raw values come from Table 8-25.45 The filter semantics are in Filtering below. A request fails as a whole if the window type is invalid or if the "from" tag is greater than the "to" tag.25

    TC[22,15] position-shift all scheduled activities¶

    The only field is the delta position (deduced).40 The request is rejected, and nothing is shifted, if the earliest non-persistent activity would end up before current position plus margin. Otherwise every activity moves by the delta, and persistent activities that would fall below the margin are pushed forward by whole periodicities.22

    TM[22,10] position-based schedule detail report¶

    Field Type Presence Meaning
    N (printed "enumerated", see note) always number of activities reported
    repeated N times: sub-schedule ID enumerated optional
    group ID enumerated optional
    position tag deduced always scheduled release position
    activity persistency status enumerated optional 0 non-persistent, 1 persistent
    persistent activity periodicity unsigned integer deduced presence (persistent only) orbits
    request TC packet always the complete stored request

    Entries are ordered by release position.3521 The detail report returns the complete stored request, usually as a telecommand packet, whereas the summary report gives only its identifier.21

    Figure 8-246 types the counter N as "enumerated", while every other ST[22] array counter, including the one of the summary report, is an unsigned integer.3538 This looks like an editorial slip in the 2016 issue; it is not discussed in the available sources.

    Sub-schedule and group management¶

    Message Fields Notes
    TC[22,20] enable / TC[22,21] disable position-based sub-schedules N (unsigned integer), N × sub-schedule ID (enumerated) N = 0 means "all sub-schedules"; unknown IDs are rejected one by one4215
    TM[22,19] position-based sub-schedule status report N, N × (sub-schedule ID, sub-schedule status) status: 0 disabled, 1 enabled4145
    TC[22,22] create position-based scheduling groups N, N × (group ID, group status) the initial status is given at creation; rejected if the group exists or the maximum is reached4218
    TC[22,23] delete position-based scheduling groups N, N × group ID N = 0 deletes all groups; a group with activities cannot be deleted4218
    TC[22,24] enable / TC[22,25] disable position-based scheduling groups N, N × group ID N = 0 means all groups4219
    TM[22,27] position-based scheduling group status report N, N × (group ID, group status) status: 0 disabled, 1 enabled4345

    The "delete all groups" variant has a twist: every group is deleted, and a failed execution notification is raised for each group that still had activities.18

    Inference

    Requirement 6.22.8.2.2h deletes the identifier of every group, yet 6.22.8.2.2d forbids deleting a group that has activities. Read together, the failure notification for such groups probably means those groups survive, but the text does not say so explicitly.

    TC[22,28] set the orbit number¶

    One field: the orbit number (unsigned integer). The new number takes effect at the end of the current orbit, not immediately. How the counter increments on board is left open.4410

    Enumerations¶

    Table Field Raw value: meaning
    8-23 sub-schedule status 0 disabled, 1 enabled
    8-24 group status 0 disabled, 1 enabled
    8-25 position window type 0 all, 1 between 2 position tags, 2 from position tag, 3 to position tag
    8-26 activity persistency status 0 non-persistent, 1 persistent

    All four come from clause 8.22.3.45

    Filtering¶

    When the position-window filtering function is declared, a filter combines a position window with optional lists of sub-schedules and groups:24

    • from tag to tag: activities between the two tags, both included;
    • from tag: activities at or after the tag;
    • to tag: activities before or at the tag;
    • all (window type 0 in Table 8-25).45

    The sub-schedule part selects every activity of the listed sub-schedules and silently ignores unknown sub-schedules. The group part selects every activity of the listed groups. When more than one part is present, the result is the intersection: (window) ∩ (union of the listed sub-schedules) ∩ (union of the listed groups).24

    Inference

    The standard says unknown sub-schedules are ignored in a filter, but is silent about unknown groups. Whether an unknown group in a filter is an error is not stated in the available sources.

    Position-shifting rules¶

    All three shift requests (TC[22,7], TC[22,8], TC[22,15]) follow the same pattern:222325

    1. All or nothing for non-persistent activities. If adding the delta to the earliest non-persistent activity selected would put it before current position plus margin, the whole request fails at start of execution and nothing moves.
    2. Persistent activities never fail. A persistent activity that would fall below the margin is moved forward by its periodicity, as many times as needed, so a shifted persistent activity can never end up with a past tag.

    Worked example (illustrative)¶

    The numbers below are invented for explanation; the standard fixes neither the units nor the encoding of positions and deltas.

    Shifting a persistent activity

    Assumptions: current position (orbit 1000, 90°); position margin 10°, so the earliest acceptable position is (1000, 100°); a persistent activity at (1000, 120°) with a periodicity of 1 orbit; no non-persistent activities are selected.

    1. TC[22,7] asks for a delta of −30°. The new tag would be (1000, 90°), below (1000, 100°).
    2. Because the activity is persistent, the request is not rejected: the orbit number is incremented by the periodicity until the tag clears the margin, giving (1001, 90°).23
    3. Had the activity been non-persistent, the same request would have been rejected with a failed start of execution and no activity would have moved.23

    Observables¶

    The subservice must publish five observables: the current orbit number; the execution function status; the number of scheduled activities; and, when supported, the number of sub-schedules and the number of groups.26 The standard lists them as observables of the subservice; how a mission reports them to the ground (for example as housekeeping parameters) is not stated in the available sources.

    A complete transaction¶

    The sequence below follows one persistent activity from loading to its second release. It combines the insertion rules, the release logic and the ST[01] reporting rule that a released request reports to its original source.12132

    sequenceDiagram
  participant G as Ground (source ID s)
  participant P as ST[22] provider (APID p)
  participant D as Destination process (APID d)
  G->>P: TC[22,4] sub-schedule 3, N=1, group 2, tag (orbit n, θ), persistent, period k, request R
  P-->>G: TM[1,1] / TM[1,7] for the TC[22,4] itself (if requested)
  G->>P: TC[22,20] enable sub-schedule 3 (new sub-schedules start disabled)
  G->>P: TC[22,1] enable the execution function
  Note over P: orbit n, angle θ reached
  P->>D: release R (still identified as a request of source s)
  D-->>G: TM[1,x] verification of R, sent to source s
  Note over P: R persistent: tag becomes (n+k, θ)
  Note over P: orbit n+k, angle θ reached
  P->>D: release R again
  D-->>G: TM[1,x] verification of R

    Illustrative encoding of TC[22,4]¶

    The diagram shows one possible tailoring, with field widths invented for this example (the standard leaves all of them to the mission): 8-bit identifiers and counter, a position tag made of a 32-bit orbit number and a 32-bit angle in units of 360°/2^32, an 8-bit persistency status and a 16-bit periodicity. Only the start of the embedded request (its 6-octet Space Packet primary header) is drawn.

    With these assumptions the first 14 octets would be 03 01 02 00 00 30 39 40 00 00 00 01 00 0F, followed by the embedded telecommand. These bytes are illustrative, not taken from any mission.

    Solar Orbiter: a different "service 22"¶

    Solar Orbiter's space-to-ground ICD tailors its services from the ESA PUS, which for this mission is ECSS-E-70-41A (PUS-A), plus an ESA operations requirements document.65 PUS-A has no position-based scheduling, and the ICD uses type 22 for its own Context Saving Service instead.6656 The service lets a payload instrument save its operational context as a file in the OBC Mass Memory (OMM) before switch-off and get it back later:67

    Subtype Direction Meaning in the Solar Orbiter ICD
    (22,1) TC, CSW to instrument request the user to report its context
    (22,2) TM, instrument to CSW context report from the user (context data up to 4094 octets)
    (22,3) TC, CSW to instrument accept the requested context: 2-byte segment counter N (1 to 18) and up to 234 octets of context data, sent at 1 Hz
    (22,4) TC, ground to CSW request the CSW to restore the stored context to an instrument (1-byte instrument PID)
    (22,5) TC, ground to CSW request the CSW to perform context saving for an instrument (1-byte instrument PID)

    The OBC central software (CSW) stores the received TM(22,2) as a file in the OMM, where the ground can reach it with the private file management service 133 (see ST[23] file management).6769 The ICD prints both "up to 234 octets" and "236 octets" as the per-telecommand maximum; the MIB definition discussed below uses 234.6874

    What the MIB contains¶

    The September 2025 Solar Orbiter MIB (MIB__20250916M25925PFMS001_SOL) has six commands and one telemetry packet of type 22, and no command or packet of type 22 with a position-based meaning:74

    Name / SPID Type, subtype APID Description in the MIB Parameters
    ZIP16010 TC (22,1) 1164 requestContextReport none
    ZIX22001 TC (22,1) 1452 STIX Request User to Report Context none
    54331 TM (22,2) 1451 STIX Context Report from User -
    ZIP16030 TC (22,3) 1164 acceptContextReport 16-bit segment counter (PTC 3, PFC 12), 1872-bit context data (PTC 7, PFC 234, i.e. 234 octets)
    ZIX22003 TC (22,3) 1452 STIX Accept Context 16-bit "N - Context Data Struct" (PTC 3, PFC 12), defined as a group repeater (CDF_GRPSIZE 1) over the 8-bit "Context Octet" (PTC 3, PFC 4)
    ZCD01604 TC (22,4) 172 Request CSW to restore context. 8-bit Process Identifier (PTC 2, PFC 8)
    ZCD01605 TC (22,5) 172 Request CSW to perform context saving fr... 8-bit Process Identifier (PTC 2, PFC 8)

    The two TC(22,3) definitions differ. ZIP16030, whose parameters are named PHI_CONTEXT_segment and PHI_CONTEXT_data, follows the ICD layout, a segment counter followed by a fixed 234-octet block. STIX's ZIX22003 makes its 16-bit N a repeat count for the octet that follows, so in the database N gives the number of context octets, not the segment number that the ICD describes.747268

    The Process Identifier parameter of ZCD01604 and ZCD01605 is decoded by the textual calibration CCDT0202TC, which lists 55 instrument process IDs from EPD_0_PID (50) to SPICE_8_PID (104). The April 2020 release had a second TM(22,2) packet, SPID 53091 "PHI_contextData" on APID 1163, which is no longer present in 2025.7475 The tables queried are ccf, cdf, cpc, pas and pid.

    SQL used 
    -- solo-2025-09-16.sqlite (MIB__20250916M25925PFMS001_SOL); same queries on solo-2020-04-16.sqlite
SELECT CCF_CNAME, CCF_DESCR, CCF_TYPE, CCF_STYPE, CCF_APID, CCF_NPARS
  FROM ccf WHERE CCF_TYPE = '22' ORDER BY CAST(CCF_STYPE AS INT);
SELECT PID_TYPE, PID_STYPE, PID_APID, PID_SPID, PID_DESCR FROM pid WHERE PID_TYPE = '22';
SELECT d.CDF_CNAME, d.CDF_ELLEN, d.CDF_BIT, d.CDF_PNAME, c.CPC_DESCR, c.CPC_PTC, c.CPC_PFC
  FROM cdf d LEFT JOIN cpc c ON c.CPC_NAME = d.CDF_PNAME
 WHERE d.CDF_CNAME IN ('ZIP16030','ZIX22003','ZCD01604','ZCD01605')
 ORDER BY 1, CAST(d.CDF_BIT AS INT);
SELECT PAS_ALTXT, PAS_ALVAL FROM pas WHERE PAS_NUMBR = 'CCDT0202TC';

    Scheduling support in the SCOS-2000 database¶

    The SCOS-2000 MIB has explicit support for time-based on-board scheduling. The ICD requires the command that loads execution-time-tagged telecommands, the "(11,4)" insert command, to be defined in the database (both ccf and cdf). SCOS-2000 wraps time-tagged commands in it, and the wrapper's name, type, subtype and parameters are configured through SCOS-2000 MISCconfig variables (CMD_LOAD_TT*); the wrapper also reduces the space left for command parameters.70 Each command can also name a default on-board sub-schedule in CCF_SUBSCHEDID.71 Solar Orbiter's MIB defines that wrapper as INSERTTT, type 11 subtype 4 on APID 172.74

    Inference

    The ICD (issue 7.0) describes no equivalent for orbit-position tags. A mission flying ST[22] with SCOS-2000 would most likely define TC[22,4] as an ordinary ccf command whose last element carries the embedded packet, and build the position tag fields as normal command parameters. This is not documented in the available sources.
