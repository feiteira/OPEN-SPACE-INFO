    GDDS and mission data delivery interface documents¶

    A spacecraft's telemetry is useful to many people who must never touch the mission control system: instrument teams, flight dynamics, science operations centres. ESOC's answer for the missions launched in the 2000s was the Generic Data Disposition System (GDDS), a reusable server that took requests from outside the operations network, retrieved data from the SCOS-2000 archives and delivered them by FTP, on the web, or on CD-ROM and DVD. Each mission configured its own instance, called simply the DDS, and documented it in a Data Delivery Interface Document (DDID).1916

    This page describes the GDDS as documented by the common DDID of Rosetta, Mars Express and Venus Express, its XML schema appendix, and the mission papers; then it follows the same conventions into EDDS, whose requirements list GDDS among its predecessors5 and which still accepts its requests and produces its binary format, and into the DDID of Solar Orbiter. Request and response formats of EDDS itself are on EDDS request and data formats.

    Architecture¶

    Rosetta and Mars Express share a near-identical on-board data management system and on-board software, so ESOC developed most components of their ground data systems jointly; the Venus Express data systems are a delta development of the same system.25 Each mission control system, based on SCOS-2000, kept a mission archive with two parts: a packet archive (historical telemetry, telecommands and derived data) and a file archive (typically flight dynamics and planning files); a SCOS-2000 file generation process could also produce summaries such as command history reports.2127 The DDID calls the repository the MCS Data Archive System (DAS), which is not the long-term archive; the DDS reached it from outside the operational LAN.41

    flowchart LR
    subgraph OPS[ESOC operational LAN]
        MCS[SCOS-2000 MCS<br/>packet archive + file archive<br/>= DAS]
    end
    subgraph FE[Front-end LAN]
        DDS[GDDS server<br/>request list, collation]
        WEB[Web interface]
        FTP[FTP server]
        RDM[RDM production<br/>scheduled inside ESOC]
    end
    PI[PIs and other external users]
    MCS <-- "CORBA archive retrievals" --> DDS
    PI -- "XML request file (FTP)" --> FTP --> DDS
    PI -- "web form" --> WEB --> DDS
    DDS -- "SFDU or raw response file" --> FTP --> PI
    DDS -- "online preview (XML)" --> WEB --> PI
    DDS --> RDM -- "CD-ROM / DVD by mail" --> PI
    SO[Standing orders<br/>automatic deliveries] --> DDS

    Requests could come from scheduled "standing orders", from the web interface or as request files sent by FTP. All were expressed in the same recursive XML query language, used internally and exposed on the FTP interface, so several filters could be combined. The central DDS server validated the user against its database of authorised users, issued the (relatively low-level) retrievals through a CORBA interface to the MCS, and collated their results into one delivery per request. Web responses were also XML, and online retrieval was meant only for previewing small amounts of data embedded as a byte stream in the XML.212227 The DDS machines sat on ESOC's front-end LAN, reachable from outside, separated by a bridge from the operational LAN that hosted every other MCS machine.39

    Service requirements¶

    The DDID quotes the user requirements that shaped the system:33343542

    Requirement Value
    Mode Client-server: the DDS responds to requests; one request command per request file
    What one request can ask for A subset of packets of one data source (APID); one auxiliary file; all auxiliary files of a type in a time range; a catalogue
    Nominal response Acknowledgement, catalogue entry and data in the same file transfer
    Latency Start of data within 15 minutes of the DDS receiving the request (load permitting)
    Online retention 3 months after acquisition (Mars Express); the whole mission for Rosetta
    Queue At most 12 requested files per user at a time
    Capacity At least 1000 MB per day in total, split into per-user quotas set with the Project Scientist
    Quota overrun The whole file is refused; further requests are rejected with an error
    Sampling Every N-th packet on request; wild cards in catalogue queries
    Automatic delivery New versions of selected auxiliary files; periodic TM and TC deliveries
    Off-line Random-access raw data media (RDM), CD-ROM for Mars Express and Venus Express, none for Rosetta; an integer number of days per RDM, default 1; at most 4 RDMs per period; delivered within one month (3 weeks nominal for MEDDS)

    The off-line split by day used the on-board generation time of each packet.35 Venus Express recorded science, housekeeping and consolidated auxiliary data on DVDs, one mailed to its science operations centre and one kept at ESOC.26 Mars Express kept all level 1 data for ten years after the end of the mission.20

    Access¶

    Requests went through the web interface or as ASCII (XML) files by FTP, protected by passwords (different for the web and for FTP requests). To avoid partial transfers, FTP in both directions used a two-step upload: write the file under a temporary name, then rename it. The DDS retried a failed delivery a configurable number of times; a user who had neither data nor an error message after 2 hours had to assume failure and resubmit. Delivery went to a node pre-registered for each user, changeable only with the PI's permission; all authorised users could access the auxiliary data, but otherwise users were restricted to their own experiment's data. The DDS had a prime and a backup node.38443940 The DDID also lists host names, addresses and support contacts, which this wiki does not reproduce.

    Request structure¶

    An onlineRequest holds one general element and one or more item elements, and an optional userRequestId attribute echoed in the response. One item only is allowed for web and online deliveries; several are allowed for RDM requests.4396

    Element Type Content
    general/comment string Free text, not processed
    general/userInfo UserInfoType username, FTPpassword
    general/destInfo DeliveryType Exactly one of RDM (attributes label, numCopies default 1, maxSpan default 1), FTP (filename, directory relative to the user's default, optional target) or Online (dataResponse as hexBinary, attribute displayAsHex)
    general/formatInfo FormatInfoType compression (NONE or ZIP), SFDUrequired (boolean), optional missionFormat (RMCS_SPECIAL)
    general/dataInfo DataInfoType Optional earliestStart: do not submit to the DAS before this time
    item/dataType DataType TLM, CMH, EVT, AUX
    item/dataSource ReqString An APID, a super-APID, or a source mnemonic
    item/catalogueRequest boolean Catalogue instead of data
    item/keyword (0..n) RequestKeywordValue SampleRate, MaxVolumeSize, TimeType, Application, EventType (LOG, MIB, SOFTWARE, SYSTEM), Severity (INFORMATION, WARNING, ERROR, FATAL ERROR), Workstation, MessageFilter
    item/onEvent (0..1) EventValue Volume (not supported)
    item/filter (0..1) FilterExpression A filter tree

    The table follows the C3 schema.92939496 Web delivery was allowed for all three methods, FTP requests for RDM and FTP only, and in practice RDM requests were not accepted from outside at all: RDMs were produced by ESOC's own scheduler.44 ZIP compressed the whole response (acknowledgement, catalogue and data) and appended a "Z" to the target file name. Without SFDUrequired the data were delivered "raw", with no acknowledgement or catalogue.45

    Schema and document differ

    The DDID body (issue C2) lists the data types CAT, AUX, TLM and CMH, whereas the C3 schema enumerates TLM, CMH, EVT and AUX; catalogues are requested with catalogueRequest instead. Appendix I C3 added the event keywords (DCR 417).739490 The body describes the volume keyword as VolumeSize (a byte count, at most 2147483647), the schema as MaxVolumeSize among the request keywords and VolumeSize among the filter keywords.4693

    Filters¶

    A filter is a tree. A unary node (operation OP_NOT) negates one subtree; a bin node joins a left and a right FilterExpression with OP_AND or OP_OR; a leaf compares one keyword with a value using OP_GT, OP_LT, OP_EQ, OP_GTE or OP_LTE.4796 The filterable keywords are:4893

    Keyword Applies to Meaning
    SourcePktsGenTime TM Spacecraft packet generation time: OBT converted to UTC
    S2KPktsGenTime TM SCOS-2000 packet generation time, i.e. the archiving time at the MCS; not usable for data in archive files split from the main online archive
    Type, SubType, P1Val, P2Val TM PUS type, subtype and the two packet identification values (SID); omitted means wildcard
    UplinkTime, ExecutionTime TC Uplink and execution time (filter on execution time recommended)
    CreationTime, EventTime (schema only)
    Name, Release, Issue AUX File name; blank release or issue means latest
    TimeSpan AUX Validity of flight dynamics attitude files and Mars Express orbit files: all files valid, even for one second, inside the range are returned in a gzipped tar
    Validity, VolumeSize (schema)

    Times use the MultiTime choice of a_dateTime (CCSDS ASCII time code A, YYYY-MM-DDThh:mm:ssZ, all sub-fields with leading zeros) or a_duration (XML duration).5092

    The DDID explains why TC filters on uplink or execution time give results that differ slightly from the times in the returned headers: a SCOS-2000 telecommand has seven times (specified release, uplink and execution times; actual uplink and execution times; packet filing time, the primary key of the TC history; packet creation time, the secondary key initialised to the specified execution time), and the DDS can only retrieve by the two keys.49

    A request (illustrative, modelled on the DDID example)

    <onlineRequest userRequestId="2004-04-27-hk-pull">
  <general>
    <comment>HK of APID 820, ten-fold decimated, zipped, no SFDU</comment>
    <userInfo><username>MEX_EXAMPLE</username><FTPpassword>...</FTPpassword></userInfo>
    <destInfo><FTP><filename>hk820</filename><directory/></FTP></destInfo>
    <formatInfo><compression>ZIP</compression><SFDUrequired>false</SFDUrequired></formatInfo>
    <dataInfo/>
  </general>
  <item>
    <dataType>TLM</dataType><dataSource>820</dataSource>
    <catalogueRequest>false</catalogueRequest>
    <keyword><SampleRate>10</SampleRate></keyword>
    <filter><bin operation="OP_AND">
      <lhs><leaf operation="OP_GTE"><valuePair><SourcePktsGenTime>
        <a_dateTime>2004-04-27T00:00:00Z</a_dateTime></SourcePktsGenTime></valuePair></leaf></lhs>
      <rhs><leaf operation="OP_LT"><valuePair><SourcePktsGenTime>
        <a_dateTime>2004-04-28T00:00:00Z</a_dateTime></SourcePktsGenTime></valuePair></leaf></rhs>
    </bin></filter>
  </item>
</onlineRequest>
    The structure follows the C3 schema and the DDID's own example (APID 1966, sample rate 10); the values here are this wiki's.5196

    With SampleRate the DDS took every N-th entry per history file: telemetry came from four data streams (VC 0 and VC 1, real time and playback), so N was applied to each stream and the results merged.46

    Data streams and ADIDs¶

    Every delivered data set is identified by a data source and a data type, and every data description is registered at ESOC under an eight-character Authority and Description Identifier (ADID): a four-character Control Authority Identifier (EROS, EMEX or EVEX) followed by a four-character data description identifier.7273

    Data source Type Content ADID
    (DDS internal) – RDM directory listing, cumulative index, off-line and on-line catalogues, acknowledgement, volume production information, master and partial catalogues xxxxD001 to xxxxD008
    <APID> (decimal) TLM Telemetry of one APID xxxxTnnn
    <SuperAPID> (negative) TLM Telemetry of a predefined list of APIDs (an instrument) per instrument
    CMDH CMH Telecommand history packets xxxxC001
    CMDPF, CMDPB CMH TC history printout, full and brief xxxxC002, xxxxC003
    auxiliary mnemonic AUX One auxiliary file type xxxx + mnemonic

    For an APID, nnn is the process ID as two hexadecimal digits followed by the packet category as one: process ID 51 (0x33) and category 4 give EROST334, the ADID of APID 820. Packets of one APID with different SIDs therefore share an ADID.77

    The super-APIDs were defined per mission:7374

    Mission Super-APID: instrument
    Rosetta −1 LCC, −2 RPC, −3 OSIRIS, −4 ALICE, −5 MIRO, −6 ROSINA, −7 COSIMA, −8 CONSERT, −9 VIRTIS, −10 GIADA, −11 to −15 RSOC streams (services 1, 3, 5, 6, 12), −16 to −20 RPC streams (services 1, 3, 5, 6, 12)
    Mars Express −1 HRSC, −2 PFS
    Venus Express −2 PFS, −3 ASPERA, −9 VIRTIS

    Issue B5 had only −1 to −9 for Rosetta; −10 to −20 came later (DCR 316 and 367).8874

    Auxiliary data per mission¶

    Auxiliary files are delivered unprocessed, exactly as held in the DAS; several files matching one request are wrapped in a Unix tar file. Appendix E of the DDID distinguishes "span valid" files, whose records apply until the next record, from "point valid" ones.61 The data sources of issue C2 are:747576

    Group Rosetta Mars Express Venus Express
    Radio science from the IFMS (RSI) AGC1, AGC2, DOP1, DOP2, RANG, MET_ same same
    Tracking for flight dynamics D1FD, D2FD, RGFD, MTFD, G1FD, G2FD same same
    Light time – OWLT OWLT
    Spacecraft orbit ORHR cruise; ORER, ORFR, ORGR Earth swing-bys; ORMR Mars swing-by; OROR, ORSR, ORHO, ORHS Lutetia and Steins; ORWR, ORPR, ORHW comet ORHM cruise; ORMM, ORMF Mars-centric (ORMF about 800 MB, FTP and RDM only) ORHV cruise; ORVV, ORVF Venus-centric
    Attitude ATNR, ATPR ATNM ATNV, ATPV, UCAV
    Events EVTR EVTM, EVTF EVTV, EVTP, EVTF
    Target environment CCHA, CENV, CKIN, PNAV (NAVCAM) STOM star occultations, VILM lander visibility STOV star occultations, SAAV sun aspect angles
    Operations requests DOR_, ECF_, FDR_, POR_, PORP, PTR_, PTRP, SOR_, MCR_, MDR_, MPR_, MDAF, MSP_, CONF, SPL_, LTVF DOR_, ECF_, FDR_, POR_, PTR_, SOR_ (OPE and MPS), MCR_, MDR_, MPR_, MDAF DOR_, ECF_, FDR_, POR_, PTRV, SOR_ (OPE and MPS), MCR_, MDR_, MPR_, MDAF, SPL_
    Planning products – DMOP, DSOP, RMOP, RSOP, FECS, SECS, FTL_ DMOP, DSOP, RMOP, RSOP, FECS, FTLV, FSCV, TMSV manoeuvre slots

    Responses¶

    SFDU packaging¶

    The DDS used the CCSDS Standard Formatted Data Unit (SFDU) concept so that each delivery, and each RDM, describes itself, while users who know the layout can treat the extra headers as spare bytes.36 The building block is the Label-Value-Object (LVO): a 20-octet LABEL, a VALUE of any length and an optional marker.79

    Class Category Use in the DDS
    Z Structure: Exchange Data Unit (EDU) Outer envelope of every product
    F Structure: Description Data Unit (DDU) Data description registration packages
    U Structure: Application Data Unit (ADU) One data file plus its catalogue entry
    R Service: replacement (reference) Points to files elsewhere on an RDM
    C Service: data administration ADIDNAME= statements
    I Data: application data object The requested data
    S Data: supplementary Index and listing files
    D, E Data: DDR and DED objects Syntactic and semantic descriptions
    K Data: catalogue attributes Catalogue entries
    V Data: volume production Acknowledgement, volume information

    The CCSDS ADIDs used are CCSD0001 (VALUE contains LVOs), CCSD0002 (ASCII encoded English), CCSD0003 (PVL statements referencing external objects), CCSD0004 (PVL identifying a data description package), CCSD0005 (a DDU), CCSD0006 (PVL) and CCSD0009 (an ADU). All DDS LVOs are version 3 with delimitation B, the length only known once the VALUE has been generated.798052

    Note

    Appendix F of issue C2 still describes the delimitation parameter for "A" (an eight-character decimal length), while §7.2.2 and the class table specify "B" (binary length) after DCR 032; this page follows §7.2.2.5279

    A successful response is one file with three LVOs inside an EDU; an error response has only the first:5263

    flowchart TB
    Z["LABEL CCSD Z 0001 - envelope (EDU)"] --> V["LABEL EROS V D005 - acknowledgement (XML)"]
    Z --> K["LABEL EROS K D004 - catalogue entry (XML)"]
    Z --> I["LABEL EROS I Tnnn / C001 / aux - the data"]
    I --> D1["DDS header 1 + packet 1"]
    I --> D2["DDS header 2 + packet 2"]
    I --> DN["... DDS header N + packet N"]

    The acknowledgement repeats the request (general), gives ackInfo (actual processing time, hardware, operating system, DDS version, error message, "NO ERROR" when nominal) and one ackItem per data item with the actual delivered volume; the DDID example reports a Sun Blade 100 running SunOS 5.8 and "GDDS 1.2.0".5397 The catalogue entry gives data type, source, ADID and keywords: first and last packet times (by source or SCOS-2000 generation time), sample rate, number of elements, or file name, creation time and version for auxiliary data.5495 Master catalogues (wildcards in both source and type) and partial catalogues (a wildcard in one) listed what was available; for performance the master catalogue for telemetry was disabled (DCR 269), and packet counts in catalogues are empty.62

    Errors are reported as ROSETTA DDS ERROR-nn, MEX DDS ERROR-nn or VEX DDS ERROR-nn:78

    Group Codes
    Request specification 01 unrecognised data source; 02 unrecognised data type; 03 illegal source/type combination; 04 no access rights; 05 illegal target file name; 06 and 07 illegal start or end time; 08 start after end; 09 illegal sample rate; 10 illegal amount
    Processing 50 maximum outstanding files exceeded; 51 no catalogue data; 52 no data packets; 53 timeout; 54 unavailable; 55 resources exceeded; 56 system error; 57 user daily quota; 58 system daily quota; 59 DDS access disabled

    A monitoring process timed out requests after a configurable period (default 120 minutes) and deleted new requests once a user had 12 queued.63

    Telemetry: the DDS packet header¶

    Telemetry is delivered as complete, reassembled, unprocessed source packets in time order, each preceded by an 18-octet DDS packet header, stamped with the Spacecraft Event Time (SCET), the calibrated generation time of the packet's first bit.5556

    Octets Field Values
    0–7 SCET Sun "MJT": 32-bit seconds since 1970-01-01 00:00 and 32-bit microseconds
    8–11 Packet length Octets of the packet that follows
    12–13 Ground station ID See below; 0 for time correlation packets (APID 1966, type 190, subtype 40)
    14–15 Virtual channel ID 0 = VC 0, 1 = VC 1
    16 SLE service Service and delivery mode, see below
    17 Time quality 0 good, 1 inaccurate, 2 bad (algorithm on the time correlation page)

    The ground station identifiers in issue C2 are:56

    ID Station ID Station
    0x0D ESA Villafranca 2 0x22 / 0x67 NASA Goldstone (old / new)
    0x15 ESA Kourou 0x23 / 0x70 NASA Canberra (old / new)
    0x16 NDIULite (for SVTs) 0x24 / 0x6C NASA Madrid (old / new)
    0x17 ESA New Norcia 0x7F ESA/ESOC test station
    0x18 ESA Cebreros 0x82 NDIU classic (SVTs)

    The NASA identifiers changed in November/December 2003; issue B5 still had "TBD" for Madrid and no Cebreros.5687 The SLE service octet combines the delivery mode and the frame selection:56

    Real time (RT) Real time flow control (RTFC) Off-line
    SLC 0 4 8
    MC 1 5 9
    VC 2 6 10
    Bad frames 3 7 11

    Inference

    The rows correspond to the SLE return services through which the frames reached the MCS: all frames of the space link channel (SLC, as in RAF), a master channel or a virtual channel (as in RCF), and frames that failed decoding; the columns to the SLE delivery modes. The DDID gives only the codes.56

    A request is answered in one file sorted by the time keyword used. The DDID example: packets of four SPIDs on APIDs 10 and 23, requested for APID 10, come back as packets 1, 4, 6, 2, 5, 3, i.e. interleaved by generation time regardless of SPID. The SPID, the SCOS-2000 packet ID, is internal to the MCS.57

    Telecommand history¶

    Raw TC history packets are the encoded telecommands as uplinked, each preceded by a DDS command packet header.58

    Octets Field Meaning
    0–7 Uplink time Release time from the MCS, later replaced by the ground station's radiation time stamp; release failure time if release failed
    8–15 Execution time The user's time tag for commands embedded in service 11 loads, otherwise uplink time plus the one-way light time
    16–17 CUV Uplink verification: CLCW-based acceptance of the frame on board
    18–21 CAV, CEV (VC 0) Acceptance and execution verification from real-time telemetry
    22–25 CAV, CEV (VC 1) The same from playback telemetry
    26–29 Packet length Octets of the TC data record
    30–37 Command ID Command name in the database
    38–45 Parent sequence ID Name of the parent sequence

    Note

    Issue C2 calls this a "30-octet header" and says the data record starts at octet 30, yet the table continues with the command and sequence names to octet 45 (DCR 037). The EDDS EUICD's description of the GDDS TC header lists all ten fields with their sizes (8, 8, 2, 2, 2, 2, 2, 4, 8 and 8 octets: 46 in total).5814

    Each verification word is 16 bits with exactly one bit set (bit 0 the least significant): bit 0 IDLE, 1 PENDING, 2 PASSED, 3 FAILED, 4 UNVERIFIED, 5 UNKNOWN, 6 TIMED-OUT (CUV only), 7 SCC ONLY, 8 ASSUMED (CUV superseded by a successful later stage). Only PASSED, FAILED and UNVERIFIED are final; an all-zero word means the stage did not apply.59 The printouts CMDPB and CMDPF reproduce the TC History display: name, description, sequence, release and execution times, sub-schedule, service type and subtype, process ID, service 11 and service 13 encapsulation, AD or BD mode, PTV and CEV check states, group, block and interlock flags, source, frame count, sequence counter and one status letter per verification stage (R release to the NCTRS, G ground reception, T uplink, O on-board reception, A acceptance, C completion, for VC 0 and VC 1); the full mode adds one line per editable parameter.60

    Raw data media¶

    Off-line delivery was entirely controlled by ESOC: every CD-ROM held all data streams of all instruments and all ESOC auxiliary data for its period, plus every data description needed, so each disc was self-contained. Six days were allowed for orbit and attitude data to be consolidated before a write-once master was sent for mastering and reproduction.64

    ROOT
├── VOLDESC.SFD            root SFDU (logically includes everything)
├── yymmddnv.IDX/.LST/.LSC cumulative index, directory listing, changed files
├── MEX (or VEX)
│   ├── TLM/<APID dirs>    telemetry, one directory per APID
│   ├── CMH                command history
│   └── AUXF               auxiliary files
├── DATADES
│   ├── TLM_DES  AUX_DES  CMH_DES  DDS_DES
└── SOFTWARE               orbit and attitude access routines

    The tree condenses §7.13.1; empty files are present when a source had no data, so a missing file means a manufacturing error.66 Data files are named yyyymmdd-xxxxDDID-nn-i.ccc: RDM generation date, file number, the four-character DDID part of the ADID, RDM set number within the day (hex), index in the set, and .cat or .dat. For example 20040427-0001T334-01-1.dat is APID 820 data on the first RDM of 27 April 2004.67

    A CD-ROM held about 650 MB; a day with more than 600 MB continued on a second disc from the split time, and a file could be split anywhere, even inside a record, so it had to be rejoined before use.68 Version control relied on a cumulative index file, yymmddnv.IDX (date, disc number in the day 1 to 9, version A to Z), present on every disc, newest first, with fixed positions: RDM ID (octets 0–7), inclusive start time (9–28), exclusive end time (30–49), disc number (51), discs that day (53), version (55), status DELETED when superseded (57–66), line feed (67).69 The printed and volume label was, for example, 20041212_2_3A for the second of three discs of 12 December 2004, first issue.70

    In the SFDU view the root file VOLDESC.SFD is an EDU containing header LVOs (volume production information in PVL: mission, producer, earliest and latest packet, total data quantity, computer, operating system, DDS software version, production time; and class R references to the index, listing and changes files), one DDU per data description (class F holding a class C ADIDNAME= statement and a class R reference), and one ADU per data file (class U holding a class K catalogue entry with RDM_FILENAME and a class R reference).65 ESOC, as Control Authority, registered descriptions in ASCII encoded English; for science telemetry they only name the experiment and its contact, the inner packet formats being the PIs' domain.7181

    Appendix K lists packets the MCS assigns or generates on APID 1966, type 190:82

    The coefficient packet (gradient, offset and standard deviation as IEEE doubles, generation time in CUC 4+2) is described on the time correlation page.83 Two text products are also delivered: the Lander Telecommand Verification File (LTVF), a listing of the bit patterns of the commands on a manual stack (row, mnemonic, description, source sequence count, PUS version, CRC, packet header and data field), created on request and stored in the directory named by the MISCconfig variable CMD_BIT_PATTERN_STACK_DIR; and the Detailed Agenda File (DAF), the command import format of the Pass, MTL and manual stacks, of which mission timeline DAFs are available to users for traceability.8485

    From GDDS to EDDS¶

    When ESOC built the EGOS Data Dissemination System, its requirements were derived from three existing subsystems giving access to SCOS-2000 data: TDRS, WebRM and the GDDS.5 A technical note analysed the reuse of TDRS, WebRM, GDDS and MUST (EGOS-MDW-EDDS-TN-1001, 2006), which is not public.3 Backward compatibility was written into EDDS:

    • Requests. The light-weight Request Submitter must convert GDDS requests (as defined in the GDDID) into EDDS requests by XSLT, supporting all requests common to both (EDDS-SR-05683).6 The EUICD documents the mapping (GDDS2EDDS.xsl). Only one item is allowed; the filter must not contain OR nodes inside AND nodes (such subtrees are ignored); MultiTime values must be absolute, except in schedule requests, where the start is a duration relative to execution and the end a duration after the start; a schedule creates ten requests at the given interval in days; RDM, online delivery, SFDUrequired and missionFormat are ignored; and mission and domain can be selected by Mission: and Domain: lines in the comment.911
    • Request types. A TLM item maps to a TM packet request with the APID as data source and a mandatory SourcePktsGenTime range (S2KpktsGenTime is mapped to the same generation time, Type, SubType, P1Val, P2Val allow OP_EQ and negation only); CMH/CMDH maps to a TC packet request on execution time; CMDPB/CMDPF to brief and full TC reports.11
    • Responses. "GDDS_BINARY" is an output format for TM and TC packets from the PARC and for TM packets from HARC and EGS-CC; the SDD names the formatters (PktTmGDDS_BINARYFormatter, PktTcGDDS_BINARYFormatter, PktTcSFDUFormatterHandler "for the backward compatibility with the GDDS"); the EDDS stream client can save TM in GDDS binary; and EDDS-SR-05680 (desirable) asks for the GDDS binary format for archived files and catalogues.1287

    The EUICD expresses the GDDS headers in its own extensible binary format: the GDDS TM header (SCET 8, packet length 4, ground station 2, virtual channel 2, SLE service 1, time quality 1 octets) corresponds to EDDS header fields 8, 10, 12, 13, 17 and 18, and the GDDS TC header to fields 9, 10, 23 to 29 and 13. The EDDS TM header field table marks the packet length and the "SleServiceID" as "added for backward compatibility with the GDDS".1413 Its worked example shows two TM packets whose GDDS header reads 4E94 46BE A7B8 D000 | 0000 0050 | 0000 | 0000 | 00 | 00: generation time 0x4E9446BE seconds plus 0xA7B8D000 microseconds, an 80-octet packet, ground station 0, VC 0, SLE service 0 and good time quality.14

    Inference

    0x4E9446BE is 1318340286 s, i.e. 2011-10-11 13:38 UTC, but the microseconds field 0xA7B8D000 exceeds 999 999, so the example bytes are not a valid time; they are best read as an illustration of the layout only.14

    Solar Orbiter: the DDID on EDDS¶

    The Solar Orbiter Data Delivery ICD (SOL-ESC-IF-05011) is the mission-specific complement to the generic EDDS ICD and user manual, aligned with the BepiColombo DDID in its last revision.10098 Its structure still follows the GDDS-era DDID (assumptions, interface characteristics, access, detailed specifications, data definition, products), but the content is EDDS:99

    Aspect Rosetta/MEX/VEX (GDDS) Solar Orbiter (EDDS)
    Name of the system Data Disposition System (DDS) Data Dissemination System (DDS), based on EDDS
    Access Web interface and FTP request files EDDS client application (Java), XML requests by SFTP, user-implemented clients; HTTPS web service
    Request types Data, catalogue, standing orders Batch and stream services, saved and scheduled requests, FARC subscriptions, user management
    Sources MCS packet and file archives (DAS) MCS long-term archive: PARC (packets), DARC (parameters), FARC (files)
    Response formats SFDU or raw; XML acknowledgement and catalogue Binary (files or Google Protocol Buffers), EDDS raw binary, GDDS binary, XML and XML transform, ASCII
    Packet header 18-octet DDS header SCOS-2000 packet headers (EDDS raw header with no mission fields, or GDDS binary header)
    Off-line media CD-ROM, DVD none; RAPID files pushed by the Generic File Transfer System (GFTS)
    Time correlation Coefficient packet type 190/40 Report, couple and coefficient packets type 164/1 to 3
    Quotas Per-user daily volume Data type filters (APID, SPID, parameter, file name or type), volume per period, relative time range, access period

    Sources for the right column: the DDID's sections 2, 3, 6, 7, 8, 9 and 10.103104105106108 Several GDDS conventions survive in detail:

    • The GDDS binary option is offered as such: a binary header (EUICD §6.1.3) followed by the source packet without SCOS-2000 header. The DDID notes that its "SLE service Id" field, which identifies the SLE service and channel type over which the data were retrieved, is not relevant to end users.106
    • Time and byte order: all times are 4-octet seconds since 1970 plus 4-octet microseconds (leap seconds not counted), the same Sun-style time as the GDDS SCET, and all data are big-endian.106
    • Ground station IDs in the SCOS-2000 header are decimal: 21 Kourou, 22 Perth, 23 New Norcia, 24 Cebreros, 25 Malargüe, 30 Maspalomas, 201 reference test station (ESOC), 202 NDIU Lite, 203 NDIU IFMS.107
    • Time quality keeps the GDDS values 0 good, 1 inaccurate, 2 bad.107
    • Internal packets stay on APID 1966 (SPIDs 66810 to 66999, including the time correlation report, couple and coefficient packets), to be filtered out except for time correlation.108
    • Command history is still available in binary, XML and an ASCII format matching the MCS TC History application, now with Science Kernel custom fields (forced sub-schedule ID, CEV check state for playback, a unique command ID, the service 13 file ID and file attribute).109

    Inference

    The Solar Orbiter decimal station IDs 21, 23 and 24 equal the GDDS-era hexadecimal 0x15 (Kourou), 0x17 (New Norcia) and 0x18 (Cebreros), so the station numbering appears to have been kept across the two generations. No source states this.10756

    The Solar Orbiter DDID's auxiliary file types and file archive, its TM files reconstructed from the service 13 downlink and the RAPID files are discussed on Mission archives; the SCOS-2000 packet header it documents is on EDDS request and data formats.
