    Operations preparation: databases, procedures and tools¶

    A mission control system such as SCOS-2000 is generic software. Before it can fly a particular spacecraft it needs a large body of tailoring data: monitoring and control data definitions, procedures, user-defined displays and more. At ESOC the Phase E operations teams prepare this data; the EGSE and AIT teams of Phases C/D prepare equivalent products for their test campaigns. ESA's own 2017 paper says that producing and maintaining a consistent set of these products takes considerable effort, and that missions and data systems had grown separate preparation environments with no complete, coherent solution.1

    This page follows the preparation chain from the requirements that shape the on-board data, through the spacecraft database and the flight procedures, to the tools that edit, check, convert and publish them. It closes with two missions that show the whole chain in operation: INTEGRAL's configuration control and CHEOPS's automated mission operations centre.

    At a glance

    • Requirements first. ESA's Generic OIRD (version 1.0, July 2019) fixes one common set of operability and PUS-C requirements for future missions; an Earth-observation technical note (PE-TN-ESA-GS-405, issue 2.6, March 2026) states, as requirements to be waived only with justification, how payload data should be packetised for ground processing.445051
    • One database, many users. Thales Alenia Space's HPSDB (Herschel/Planck) and its successor SRDB (MTG) organise the spacecraft database as objects, items and category flags so that AIT, operations and software teams see consistent subsets.2729
    • Procedures are tested data. INTEGRAL's flight procedures were generated with a tool (FOPGEN) that accessed the actual database, usually tested on the simulator and approved by the Spacecraft Operations Manager before controllers could run them.102
    • The next generation. ESA's OPEN framework (Java, Eclipse RCP, EMF) underlies OPEN-M, OPEN-S, OPEN-D and the Mission Model Editor, and OPEN-M converts SCOS-2000 MIB 6.9 data to the EGS-CC model.710116
    • The database is not always static. Terma's CCS5 builds MIB packet definitions on the fly from PUS service 3 commands, and scripts its telecommand verifier for time-tagged and cyclic commands.6169

    Requirements upstream¶

    Operations preparation starts before the spacecraft is built: what the ground can do later depends on what the space segment is required to provide. Two ESA documents in the library show how such requirements are now written.

    The Generic OIRD¶

    Operability requirements are an early input to spacecraft development. Most ESA missions write them in an Operations Interface Requirements Document (OIRD), either standalone or inside the System Requirements Document, tightly coupled with the CCSDS and ECSS standards. ESA's 2019 presentation lists the problems: each mission had its own OIRD derived from previous ones, lessons learnt did not always propagate, the documents looked more different than they were, they had evolved independently of PUS-C and the OBCP standard, and the variability hampered product orientation both on board and in the mission control system.41

    In June 2016 SAVOIR entrusted ESOC with establishing a Generic OIRD (GOIRD) that would form the baseline specification for future missions and allow compatible on-board software libraries. Mission OIRDs are to be created from it with only mission-specific deltas, plus the sizing of PUS-C services such as mission timeline capacity.41

    Why not use PUS-C as it is? The presentation counts 20 services with 33 subservices but no mapping to an architecture; 316 TCs and TM reports if all subservices are implemented, of which only 88 are mandatory (this wiki's own tally of ECSS-E-ST-70-41C Annex C, in the PUS message type catalogue, finds 318 message types, 81 of them in minimum capability sets; how the presentation counted is not stated); and 382 "shall be declared when specifying" statements, so that two untailored implementations would end up with very different interfaces. Some functions that ESOC missions need are missing (critical event log or system log, file transfer, backup mission timeline), as are some lessons from previous OIRDs.46 The PUS-C part of the GOIRD therefore consists of these classes of requirement:47

    Class Content Share of the GOIRD PUS-C requirements
    Services, subtypes and capabilities selection One common set of services, subservices, TC/TM packet types and capabilities for all future ESA missions, so that the satellite interface is fairly mission-independent about 60%
    Additional observables Parameters added to most services, because PUS-C relies on on-demand reports and mandates few housekeeping parameters about 2%
    New capabilities Critical event log / system log, parameter extraction from housekeeping, backup MTL, file-based operations; high-level requirements only, interfaces left open, to be raised as change requests to the standard about 19%
    Avionics architecture A few services centralised (for example service 11, the mission timeline); services 1, 3, 5, 6 (if applicable) and 17 mandated in all packetised units less than 1%
    Clarifications and refinements Lessons learnt from previous missions and OIRDs about 12%
    Changes to the standard Kept to the absolute minimum, never changing defined TC/TM interfaces, each justified (typos, omissions, strong operational needs) less than 1%

    The presentation warns that PUS-C leaves key low-level aspects unstandardised, such as the number of bytes used to encode certain packet fields, which matters for interoperability; it asks for coordination among PUS-C library implementers. The OBCP standard is not tailored, and a few extra requirements for service 18 sit in the PUS-C part.48 The concluding slide sets out a common requirement set to reduce variability and cost. As a long-term vision it asks whether PUS-C library developers could collaborate and whether interoperable implementations with a generic TM/TC ICD are possible, and it proposes further harmonisation of other elements such as procedures and databases.49 For the services named above see ST[01], ST[03], ST[05], ST[06], ST[11], ST[17] and ST[18]; for the differences between PUS versions see PUS-A vs PUS-C.

    Ground inputs to the on-board data architecture (PE-TN-ESA-GS-405)¶

    A technical note from ESA's Earth Observation programme, first issued in November 2014 and at issue 2 revision 6 of 26 March 2026, states what the ground segment needs from the on-board data architecture so that payload data can be analysed, simulated and processed efficiently. Its change record shows it being refined for BIOMASS, TRUTHS, FORUM, Harmony and NGGM.50 It explicitly does not apply to TT&C/S-band links. It also covers missions that use CFDP on top of the Space Packet Protocol, noting that CFDP is new to Earth-observation missions and that their payload downlink differs from space science: many short passes, through stations usually procured as a service rather than operated by the flight operations segment.51 The note's working assumptions include routing from on-board source to ground sink on the primary header or the CFDP file name, unmodified commercial CCSDS ground equipment, the Level-1 processor as end consumer, and preferably fully open-loop payload downlink.51

    Its glossary separates the data kinds that a database designer has to keep apart:52

    Term Meaning in the note
    Observation data (OBS) Instrument output, as Space Packets, when the stimuli are the mission's targets
    Calibration data (CAL) Instrument output when the stimuli are internal or external calibration targets
    Ancillary data (ANC) Space Packets generated on board, mostly by software, in support of observations: navigation, temperature, timing, configuration; "instrument ancillary" or "platform ancillary" by origin
    Auxiliary data (AUX) Files needed by ground processing but not part of the payload data (for example orbit files, calibration coefficients)
    Housekeeping telemetry (HKTM) Data for monitoring and control in the mission control centre; a separate stream not used in payload processing
    Payload Data Observation, calibration and instrument ancillary data; excludes instrument HKTM and platform ancillary data
    RAW / Level 0 Concatenated packets as received, with no header (RAW); ground-segment header plus concatenated packets (Level 0)

    These rules also shape the ground database. Under R-020 and R-150 each APID has one fixed structure and maps to one Level-0 product, and under R-010 routing relies on the APID alone.5455 The Solar Orbiter MIB, from a science mission outside the note's scope, shows the opposite choice for its science telemetry. Solar Orbiter's 11-bit APID is a 7-bit process ID plus a 4-bit packet category, category 12 being reserved for its science service 21.116 In the September 2025 release, the 45 on-board science APIDs carry 334 packet definitions. 328 of them are TM(21,3), (21,5) or (21,6), which are told apart by an additional identification field: the pic table puts PI1 for these three subtypes at byte 16, 8 bits wide (317 definitions have a non-zero PI1 value; the other 6 are TM(21,7), which has no PI1). 35 of the 45 APIDs carry more than one definition, up to 45 on APID 1548.117

    Inference

    In the note's terms, Solar Orbiter's science packets use a structure identifier inside the packet to select the layout, which R-150 asks Earth-observation payloads to avoid. The note does not discuss Solar Orbiter, and nothing here says that either design is wrong for its mission; the comparison only shows what the requirement changes in a ground database.

    Spacecraft databases¶

    From the manufacturer's database to the ODB¶

    On INTEGRAL, the ODB was derived from the Satellite Database (SDB) that the satellite manufacturer delivered before launch. The SDB was not maintained afterwards: during the routine phase all changes went directly into the ODB.103 The two spacecraft analysts of the flight control team maintained it; every modification needed the Spacecraft Operations Manager's (SOM) approval, after which the analysts updated every system that used the ODB: the IMCS, the FOP generation tool and the OBSMS.10399 Change requests could come from the flight control team, the science ground segment or the instrument teams; requests from the science side were first verified at science-ground-segment level and, if needed, went to the Configuration Control Board.103

    HPSDB and SRDB: a database with views¶

    Thales Alenia Space's 2015 presentation traces its system reference database from Herschel/Planck to MTG and towards EGS-CC. The Herschel/Planck System Data Base (HPSDB) answered two ESA requirements: commonality between the two spacecraft and between the users of the database, and smooth transition, the reuse of validated data from one programme phase to the next up to operations. Commonality was achieved by physical instantiation and category flags, smooth transition by logical instantiation and category flags. The SRDB adapted HPSDB for MTG; its one major conceptual change is that an object can be attached to a former version of another, where HPSDB could attach only the most recent one.27 How HPSDB processed SCOS-2000 MIB files is described on Mission tailoring of the MIB and MIB tooling.

    The model has three kinds of element. An object is a node of the product tree at element, subsystem or model level, such as a reaction wheel, the AOCS or the spacecraft. An item is a database entry belonging to an object: a TM packet, a TM parameter, a curve, a synthetic parameter, a group or a constant. A pseudo-item is a sub-record inside an item, for example one entry in a packet's list of parameters, with its own category flag, parameter reference, byte offset and bit offset.282931 Item identifiers have a core part with a type letter and an instantiation part that prefixes it:28

    Prefix of the core identifier Item type Example from the slides
    A TM packet A001
    C Curve C001, instantiated RWC001
    D Synthetic parameter D001, instantiated AZZZD001
    G Group G001
    K Constant K001, instantiated A101K001
    M TM parameter M001, instantiated A101M001

    283138

    Category flags select the users of each item and pseudo-item (AIT, OPS, SW in the example). The manager sees everything. In the slide's example the AIT view of the reaction wheel contains packet A001, parameter M001 without its OPS-only pseudo-item, M002 and the curve; the OPS view omits the packet, which is flagged for AIT and software only; the software view contains only the packet. The main constraint is that every view must be consistent.29

    Mechanism What it does
    Physical instantiation A defined object (reaction wheel RW) has realised instances with serial numbers (RW001 ...). An instance can physically delete, modify or add items: RW001 drops packet A001, modifies M002 and adds curve RW001C002
    Logical instantiation A higher-level object places lower-level objects at positions: the AOCS places reaction wheels at A101 and A102 and a gyro at A200, giving A101M001, A102M001, A200M001. The higher level can logically delete, modify or define items, and its own items sit at a pseudo-position (AZZZ), for example a synthetic parameter D001 = A101M002 + A102M002
    Combined instantiation Element, subsystem and model levels (RW, AOCS, HERSCHEL) each have defined and realised parts; in the slide's example a constant K001 is overridden physically at the realised element (RW001), logically at the subsystem level (AOCS) and physically at the realised model (HERSCHEL001)
    Generic object A GENERIC object at pseudo-position STD holds items visible from every object, such as STDK001

    Flight procedures under configuration control: INTEGRAL¶

    INTEGRAL's flight operations plan (FOP, issue 2.0 of February 2003) is the reference for all flight operations. Its mission rules say that the FOP's timelines and flight procedures, nominal and contingency, are to be used after separation, that FOP procedures override all other derived procedures, and that deviations need the permission of the Flight Director or SOM during LEOP and of the SOM or a nominated representative thereafter.100 The flight control team prepares and maintains the FOP under the SOM, who alone approves modifications (parts that concern the interface to the science ground segment also need its representatives' approval); changes that could affect mission performance are coordinated with the Project Scientist.102

    MOIS and ASTRAL-Prepare¶

    RHEA's MOIS, presented in 2023 as ASTRAL-Prepare, is a long-standing preparation product that RHEA says has supported over 100 spacecraft. It authors manual, semi-automated and automated procedures, checks the TM and TC they use against different spacecraft database versions, validates them, and publishes them to a flight operations manual or to operations languages for automation; it also manages spacecraft databases. Procedures can be edited in synchronised tabular, flowchart and script views; configuration management, role-based access and an approval workflow govern releases.15

    Its framework classifies configuration data into data types, whose instances are data items. The files and metadata that make up a data type are managed as a group, as a single configuration item. Each data type has common properties (name, description, type) used for search across the whole data set, specific properties, and four mandatory methods: consistency checks, query, generate products and publish, which the framework calls when it checks or publishes the entire data set, for example a FOP release.16 Data types and editors already existed for OBCPs, mission planning rules, PLUTO scripts (see ECSS-E-ST-70-32C), Writer procedures and Word documents, and SCOS-2000 synthetic-parameter scripts.16

    The established SCOS-2000 procedure format is the Writer: a per-procedure database with a forms-based editor that uses MS Excel for visualisation, plus a flowchart view. RHEA finds it comfortable for mostly linear procedures because a form can show many attributes, such as calibration curves, while scripting does better with loops, branching and complex expressions. Some ESOC missions automated routine operations with Writer procedures and the MOIS Scheduler, with an event monitor starting contingency recovery procedures on known out-of-limit events.25

    PME and the Extensible Procedure Model¶

    RHEA's newer Procedure Model Editor (PME) distinguishes two uses of a procedure. A product-generating procedure is a design document that may be detailed enough to generate EGS-CC activity lists, SCOS-2000 MIB sequences or code in an operations language (OBCPs in OL, Tcl/TOPE automation, SPELL). A plain sequence is linear and carries no logic or guidance for the operator, which is why RHEA wants to start from a richer procedure. An executable procedure is run directly by ASTRAL-Automate instead of being submitted to a control system.18

    Procedures must be reviewable by non-programmers in textual, flowchart and tabular views, so RHEA starts from a model rather than a language: the Extensible Procedure Model (XPM).18

    The Mission Model Editor¶

    The MME, developed by RHEA and now part of EGS-CC, edits data of the EGS-CC Technical Data Model (TDM).     Telemetry definitions on the fly: dynamic housekeeping¶

    The problem¶

    An on-board data pool can hold tens or hundreds of thousands of parameters from many suppliers. During AIT and on-board software validation, engineers often define new housekeeping packets on board with PUS service 3 commands, picking only the parameters they need. A central checkout system that recognises packets only from its database then cannot identify these packets unless someone has already written matching static definitions.61

    The SCOS-2000 import ICD states the conventional rule: SCOS-2000 has no service-specific processing of service 3, every received packet must be defined in the database before generation is enabled, and the efficient ESA practice is to create the packet definition first and generate the service 3 commands from it in the database manager, not in the kernel.109 Terma's CCS5 reverses the direction and derives the database entry from the command.63

    Command verification beyond the database¶

    Terma's paper on advanced telecommand verification starts from SCOS-2000, which it calls representative. Verification there is defined in the MIB rather than hard-coded, with global settings such as propagation delay and permitted jitter, and offers three methods:67

    Method How it works Strength and weakness (per the paper)
    Expected TM value Open a window after the command and require the first sample after it opens to have the expected value Fully general, no special packets, works without PUS; but no explicit link to the command that caused the change
    Service 1 reports Expect TM(1,x) reports for each stage within a time range Practically unambiguous per command; ambiguity possible if the source sequence counter wraps during verification (seen on one science mission with a reduced counter range); costs downlink bandwidth; needs PUS
    Status consistency check (SCC) Treat any change of a parameter as an error unless a command that changes it was sent, within a window Called "change on command only" (COCOMO) in other systems

    SCOS-2000 also tracks tricky cases such as a second command expecting a different value while the first is still pending; the first is then "superseded".67 The MIB side of this is described on Command verification in the MIB and Monitoring checks.

    Limitations the paper identifies¶

    • Only one type of verification per stage. To check a TM parameter as well as receiving TM(1,7) or TM(1,8) at completion, several missions "borrowed" the last progress stage; an extra finalisation stage would have been cleaner.68
    • The verifier model is encapsulated in C++ and CORBA, so customisation means recompilation and reinstallation; long maintenance had made it complicated.68
    • SCOS-2000 shifts verification timeouts for time-tagged service 11 commands to their execution time, but missions also delete, time-shift and enable or disable stored commands, for example by sub-schedule ID, and the paper knows of no ESA mission that followed PUS exactly here, so following these changes on ground is mission-specific and costly.68

    The Solar Orbiter MIB shows how one mission works within the model. It defines 16 acceptance stages by report, 23 completion stages by report and 167 completion stages by parameter, and no start or progress stage. No command has more than one completion stage, so none combines a completion report with a parameter check, and the progress-stage workaround is not used. Status consistency checks (OCP_TYPE = C) exist on 15 parameters, all of them counters (error, reject, reset, stored-packet and other counts) such as NDSD0046 "DST-A WD Reset Counter", and none of the 15 appears in a verification expression. 5,304 of the 5,454 commands name a default sub-schedule (CCF_SUBSCHEDID), using 17 distinct values (1, 2, 4 to 8 and 101 to 110).123

    Inference

    With no command expected to change them, these 15 counters behave like the paper's COCOMO case: any change is reported. The interpretation of the sub-schedule values (for example as one range for platform and one for instruments) is not stated in the available sources.

    The CCS5 approach: a scriptable verifier¶

    Because a checkout product must adapt quickly to on-board software and space-ground ICD changes found during AIT, Terma kept most SCOS-2000-like verification in C++ but made mission-specific behaviour scriptable in TOPE.69

    • TC cache. A list, visible in the user interface, of recent commands under verification. It has a configured size above which completed commands are dropped, but grows (with a warning) to keep every incomplete command. The paper sizes it as (timeout + propagation delay) × command rate: for a 30 s timeout, 10 s delay and 100 commands per second, (30 + 10) × 100 = 4,000 entries, a few megabytes.70
    • Command IDs and properties. Each command has a system-wide unique ID that includes the workstation ID in its upper 4 bits. Properties such as id, raw, apid, generationTime, executionTime, mapid and bypass are archived at every verification stage, some indexed for SQL queries, and read or written with tcprop <id> <property> ?value?.70
    • Mission timeline. tcsend ZP_00003 executiontime 12345678.0 subscheduleid 4 checks {SPTV DPTV CEV} (the paper's example) creates a carrier command from a template and postpones verification. tcsubscribe filters sent commands by properties, for example all service 11 commands, so that a script can update the ground timeline model with ::utope::mtldelete, ::utope::mtldisablerelease, ::utope::mtlenablerelease, ::utope::mtlreset and ::utope::timeshift; the verifier follows the modified times.71
    • Cyclic commands. A cyclicRepeats property (a count, or -1 for infinite) is decremented on each repetition; the command leaves the cache only at 0. updatecommand <id> <stage> <state> forces a stage closed or reopened: setting it to IDLE resets it and setting it to PENDING reopens the same window and conditions.72

    A modelled command (isModelled true, via tcsend ... model or tcmodel) is processed, verified and archived like a real one but discarded at the moment of transmission. The paper's uses are system validation tests where the MCS commands and the CCS listens, hot-redundant CCS servers that must take over verification, and commands sent by other EGSE elements such as a CFDP front end. Command sequences could be modelled in TOPE; OBCPs and event-action responses might need an external tool such as MOIS or APEX, an operational simulator or an emulator, each with an efficient API.73 The paper warns against over-engineering: false timeouts confuse operators, network jitter rules out millisecond windows, and modelling a fixed inter-command delay with a ground timer accumulates drift from cycle to cycle.74

    In hindsight the authors would have scripted even more of the verifier. They criticise PUS as so loosely defined and tailorable that ground applications cannot be moved between missions, and they worried that EGS-CC, then about to start development, might prolong PUS without a plan to replace it.75

    Monitoring the EGSE itself as telemetry¶

    Vitrociset's Health Monitoring system (HM) treats the checkout infrastructure as a monitored system. It reports operating-system resources (disk, memory, CPU), process status, point-to-point connections and time synchronisation of the EGSE machines, and models every monitored entity as a TM parameter in the SCOS-2000 MIB inside ad hoc TM packets, so the data appears on normal SCOS-2000 displays and in procedures.7679

    The parameter names appear to encode the value type: HM_32_ for disk, HM_16_ for memory, HM_FL_ for CPU load and NTP, HM_1_ for statuses. The paper gives the mapping but not the naming rule.

    Displays and user interfaces: the EGOS User Desktop¶

    The EGOS User Desktop (EUD) is ESA's framework for rich-client user interfaces in ground data systems, in mission operation since 2013. It was motivated by obsolescence, removal of COTS dependencies and cost reduction through reuse, with goals of open-source technology, Linux and Windows support, shared implementations and a harmonised look and feel.8283 It is written in Java on Eclipse RCP, uses only open-source software, and integrates user-interface components called displays, which are RCP views or editors; standard RCP views run unchanged, and an extended view base class adds EUD facilities.84

    By 2014 most ESOC ground-system user interfaces were EUD based: it replaced the GUIs of SCOS-2000, SIMSAT, NIS and FARC and underpinned new systems (ARES, GSMC, FIDES, GSSC, MPSF), with MATIS and SPMON in development and GFTS, DARC and DABYS planned. Its telemetry desktop was in operation for Gaia, and the slides show an Offline Display Development Environment (ODDE).86 One listed benefit matters most for operations preparation: display definition files are cross-compatible between ODDE, the MCS, SIMSAT, ARES and GSMC. The lessons were that consolidating functionality across domains took much effort, agile development was crucial and adapters for legacy systems can be tedious; a web version based on Eclipse RAP and use in EGS-CC were planned.87 For display definitions in the MIB see Display definitions in the MIB.

    Operations preparation in practice: CHEOPS¶

    CHEOPS, ESA's first small-class mission (launched 18 December 2019), is operated by its consortium: a Mission Operations Centre (MOC) at INTA's CEIT near Madrid and a Science Operations Centre (SOC) in Geneva. The 2025 paper describes a ground segment automated so that routine operations need no staff outside working hours, with 3 to 4 people at the SOC and 5 at the MOC.8897

    The MOC control system is SCOS-2000 version 5.4.2, configured through environment variables and the MIB, which defines every TC and TM packet. A Python module library gives automation access to the MCS, and GMV's Flyplan orchestrates all automated MCS and flight-dynamics activities, with Jython scripts and a data-driven monitorCHEOPS activity that watches directories for input files.9189

    The CommandBuilder is the preparation step that turns plans into commands. It maps each activity of the Activity Plan to one or more TCs through a configuration rule file and writes an SSF file, an ASCII file that "can be read by any standard SCOS-2000 using the MIB".     Inference

    Because the SSF stack files are generated against the MIB, they belong to one database version. The SCOS-2000 ICD says the vdf version name is used to ensure that a saved stack is loaded with the database version that generated it; whether CHEOPS relies on this check is not stated.11091

    During each of the 4 to 6 daily passes, Python scripts restart SCOS-2000 tasks as needed, load the pass TCs into one of two Auto Stack instances, read TM values through SMON from the packet archive (PARC, on MySQL), read and set MISC variables, switch to AD mode so that missing TCs are retransmitted (see COP-1), and run manufacturer health-check procedures written in Python. The on-board time is a free-running oscillator, so the SCOS-2000 time-correlation feature updates the linear OBT coefficients when accuracy degrades (see Time correlation).93 After the pass, the SCOS-2000 TM Processor splits the station file per virtual channel, the TM Replayer ingests recorded housekeeping into PARC, gaps are found from jumps in the virtual-channel frame counter (see TM SDLP), and RGTgenerator and the CHEOPS-specific HKTMreporter produce TC and TM reports; a colour-coded PDF summary is e-mailed to the operators.94 The SOC decodes science and housekeeping TM "according to the spacecraft's MIB" as well.95 A Simulus 5.4 / SIMSAT simulator validated operational procedures, and MUST/WebMUST, fed with SCOS-2000 RAPID files, complements SCOS-2000 for trend analysis.96 For PARC see Mission archives.

    Configuration control: the INTEGRAL model¶

    INTEGRAL (launched 17 October 2002) split its ground segment into an operational part (stations, MOC at ESOC, communications) and a science part (ISOC at ESTEC, ISDC at Versoix).98 Its configuration control has a ground-segment Configuration Control Board (CCB) chaired by the Project Scientist with the SOM, the ISOC and ISDC operations managers, the Project Science Coordinator and the MOC QA manager, plus local CCBs per centre.101105 The CCB acts on change requests against an agreed list of configuration items, recorded in a common tool, without necessarily meeting; it does not handle time-critical issues and has no contractual power.105

    On the space segment the MOC controls the spacecraft configuration: only approved FOP procedures are applied, FOP and ODB changes follow their configuration control concepts and need SOM approval, the timeline must be based on the latest EPOS and approved, and on-board software and parameters are tracked with the OBSMS and the ODB.101 Instrument configuration is shared: ISDC evaluates performance, ISOC approves changes and passes them to the MOC as an observation plan (POS) or a parameter change request, and the MOC converts instrument tables and software images into uplink commands with the OBSM function of the IMCS. The ISGRI table, updated every revolution, had its own interface based on Task Parameter Files processed directly by the IMCS.101
