    EDDS: EGOS Data Dissemination System¶

    The EGOS Data Dissemination System (EDDS) is the component of ESA's ground operations software (EGOS) that gives controlled access to mission data to people who have no access to the monitoring and control facilities of a SCOS-2000 mission control system (MCS).1 A principal investigator who wants every raw packet of an instrument, an industrial team that needs a month of housekeeping parameters, or a science operations centre that subscribes to new orbit files all use the EDDS. The EDDS itself does not analyse data. It retrieves data from the mission archives, filters and formats it, and delivers it as files or as a live stream.2

    The EDDS replaced three older SCOS-2000 add-ons: the Telemetry Data Retrieval System (TDRS), Web Remote Monitoring (WebRM) and the Generic Data Disposition System (GDDS). Its requirements also took ideas from the MUST parameter-analysis prototype.3 This page describes the system: history, services, architecture, processing chain, security model and the public document set. The companion page EDDS request and data formats gives the XML request structures and the binary layouts byte by byte.

    Name variants

    All EDDS documents in the library expand EDDS as "EGOS Data Dissemination System".4 A 2025 SpaceOps paper by ESOC and JPL authors expands it as "EGOS Data Disposition System" instead, which echoes the older GDDS name.5 This wiki uses the expansion printed in the EDDS documents themselves.

    History and predecessors¶

    The four systems the EDDS replaced¶

    The SRS traces the EDDS to three SCOS-2000 ground-segment subsystems and one prototype.3

    Predecessor What it did What the EDDS kept
    TDRS (Telemetry Data Retrieval System) Extracted TM parameter values from the SCOS-2000 history-file archive and returned them as MVDA or spreadsheet files. Only fixed-length TM packets were handled. Web browser and e-mail interface, with user interface and retrieval separated for security and performance.3 Parameter retrieval, the TDRS spreadsheet format (via XSLT or a native formatter)1920122
    WebRM (Web Remote Monitoring) Remote monitoring without physical MCS access. CORBA-based injection and provision servers, plus a Java client with SCOS-2000 look-and-feel displays.3 Stream services, the display client concept21
    GDDS (Generic Data Disposition System) Web and FTP front ends that multiplex requests from many users. CORBA/FTP interface to the MCS archive for continuous data (packets), files and catalogues.3 GDDS FTP-service requests (via the Request Submitter and an XSLT) and the GDDS binary response format19
    MUST (Mission Utility & Support Tool) Server/client prototype that builds its own parameter archive from scheduled MCS packet requests, with analysis clients.3 Batch retrieval of parameter definitions and batch or stream retrieval of parameter data for MUST-like clients22

    The ESOC infrastructure slide of a 2005 Ground System Architectures Workshop talk shows the pre-EDDS picture. It lists SCOS-2000, NCTRS and GDDS, and describes "TDRS and WebRM" as the web interfaces that give external users such as payload owners live telemetry, command verification, telemetry retrieval and statistics.23

    Two of the SRS reference documents give the design lineage. One is the 2003 "SCOS-2000 TM Data Retrieval Services SRD" (the TDRS requirements). Their "Source:" fields cite [RD-3] (listed as the TDRS SRD) in 29 requirements, [RD-4] (listed as the GDDS requirements document) in 25, [RD-5] (listed as the WebRM baseline) in 24 and [RD-6] (listed as the MUST Repository ICD) in 30; a few requirements cite several. Most of the others name a review (SWRR, SWRR2) or a product-backlog item, and 138 give no source at all. This wiki counted these fields in the extracted text, including sources that wrap onto a second line.27

    Inference: the reference labels may be shifted

    The identifiers quoted after the labels do not always fit the listed documents. Every [RD-4] citation carries an SR-TMDR-nnnnnn identifier, and every [RD-6] citation carries R-WEB-nnnn identifiers, although [RD-6] is listed as a MUST document.27 The SRS is known to mis-number other references (it cites the SLE reference model as [RD-15], which is listed as [RD-13]).21 Which predecessor document each requirement really came from is therefore uncertain.

    The project followed an agile method. The SDD says requirements and solutions evolve through cross-functional teams, and that the detailed design lives in the JavaDoc rather than in the document.28

    Purpose and users¶

    The SRS names two user groups: those who need remote monitoring, and those who analyse spacecraft data. Remote monitoring is served by stream services. Analysis is served by file-based delivery of archived data, reports and statistics.2 Binary packet deliveries are often used by principal investigators to populate their own local archives. The SRS models this explicitly as the use case "Populate Local Archive".29

    The system is deliberately not an analysis tool. The SRS says the EDDS provides MCS data in a format that facilitates analysis and aims to support many formats that can be added or retired.2 An ESOC presentation for Solar Orbiter users puts it more bluntly. The EDDS is not a data warehouse, since response files are stored only for a limited time. It is not a post-processing tool either, because its display and analysis features are very limited.30

    Two more design goals shape the architecture:

    • Multi-mission and multi-domain. One authentication entry point serves autonomous mission domains, and every request names its mission and domain.2 A domain is an instance of an MCS or data archive, independent of all others. A mission groups domains, and contexts such as live operations, testing or training.31
    • Generic archive access. The EDDS should be able to front any data archive, not only the MCS, through a generic extension layer.232 Recent releases use this layer for EGS-CC data providers.7

    Data types¶

    The EUICD organises everything the EDDS can deliver into six data-type families. The table shows which delivery mechanisms each family supports in issue 24.0.33

    Family Data types File server EDDS server Stream E-mail
    Packet TM, TC and EV in "EDDS raw" and "PARC raw" forms, packet statistics ✓ ✓ ✓ (not statistics) –
    Parameter TM parameter samples, statistics, preview, definition ✓ ✓ ✓ (samples only) –
    Report MCS reports, EDDS reports ✓ ✓ – –
    Archived files File, catalogue ✓ ✓ – –
    File system File catalogue, folder catalogue, file ✓ ✓ – –
    Acknowledgement Request status records ✓ ✓ – ✓
    • Packets are telemetry (TM), telecommand (TC) and MCS event (EV) packets as stored by the MCS, in network byte order. The "raw" variants return the archived packet as a hexadecimal string wrapped in XML. They can only be filtered by start time, end time and (for TM and EV) a list of SPIDs.34 An EV packet is an MCS event: the EUICD and SUM call it the "SCOS Event Log". The SRS lists on-board event (OBEV) reports as a separate report type, so an EV packet is not a spacecraft PUS event report.35
    • Parameters come either from the dedicated parameter archive DARC, or are generated on the fly by SMON from archived packets. The DARC is fast but holds only the subset of parameters a mission chooses to archive. The SMON path is slower but can reach every parameter.36 Parameter definitions (name, description, subsystem, unit) are derived from the spacecraft database, the MIB.3637 The EUICD warns that samples are not guaranteed to be time-ordered. A resumed request may also contain duplicates, unless the split size is set to 0 so that the whole request restarts.37
    • Reports: the MCS reports are the TM packet report, TM packet gap report, TC packet report, out-of-limits (OOL) data report and event record report. The EDDS reports are the system log and the EDDS usage report. Status and request-summary reports are listed but not supported in issue 24.0.38 For OOL reports the EDDS understands PARC OOL packet versions 5, 6 and 7, which correspond to different SCOS-2000 releases.38
    • Archived files are FARC contents: flight dynamics, mission planning and TT&C station files, plus catalogues. Where the FARC supports it, a user can subscribe so that a changed file is fetched automatically.39 The SRS adds that the mission database itself should be retrievable from the FARC, since TM, TC or EV data are of little use without it.40
    • Acknowledgements are status records generated by the EDDS. They are produced when a request is received, and when it completes or fails.4142

    Services¶

    The EUICD exposes four services to clients: authentication, batch, stream and user management.9 The SDD groups the same functions as data services (batch and stream), management services and notification services.10

    Batch service¶

    A batch request is an XML document that lists data types and a filter per type, and names a delivery method. The EDDS retrieves the data, builds the data set, delivers it, and then considers the request complete. A batch request can carry a schedule, for one-shot, cyclic or standing execution.4322 The response is a binary or ASCII file, optionally compressed or encrypted, or an XML file shown in the client. Compression is applied by default. The supported archive forms are zip, tar (USTAR, uncompressed) and tar.gz. AES encryption can be enabled or disabled per mission.43

    Users can edit a request in the client's forms, save it on the server, reload and re-edit it, or write the XML by hand and upload it. Uploaded requests are validated against the XML schema, and then checked for privilege and for mission-specific semantics (for example, the end date must be after the start date).44 Request queues are per mission, persistent on disk, and dispatched with a priority algorithm.44

    Stream service¶

    A stream request opens a continuous flow of data that ends only when the stream is closed by the client, an administrator or the MCS.45 The SRS bases the stream concept on the offline and online modes of the SLE return services. "Offline" means previously archived data; "online" means data routed as it arrives. Online delivery has two modes. Timely mode drops data to meet a delivery deadline; complete mode delivers everything, possibly with a long delay.2146

    In issue 24.0 of the EUICD the stream data are published on ActiveMQ topics. Clients read them either directly from the topic, or through the client API over CometD/Bayeux after calling startStreamData(RequestID).46

    Stream Source Topic Bayeux channel Body format
    Parameters DARC (v3.0.0 or later, SLES 12) parameter stream topic PARAM_STREAM Protocol Buffers parameter record
    Packet TM Data Provision Services (SCOS 5.4.21 / 5.5.4 or later) esa.egos.edds.packet.stream.tm PKT_TM_STREAM As the binary Packet TM Report
    Packet TC Data Provision Services esa.egos.edds.packet.stream.tc PKT_TC_STREAM As the binary Packet TC Report
    Packet EV Data Provision Services esa.egos.edds.packet.stream.ev PKT_EV_STREAM As the binary Event Record Report
    Out of limits Data Provision Services esa.egos.edds.packet.stream.ool PKT_OOL_STREAM As the binary OOL Record Report

    The topics and channels are from EUICD §4.1.3 and §12.1.8.6.4647 For DARC streaming, the EDDS subscribes to a DARC-owned topic with a JMS selector built from the request filter. Each DARC message carries header fields: ValueType, Value, Validity (0 valid, 1 invalid, 2 unknown, 3 expired), SystemElement, Source, State, GenericData, GenerationTime (Unix time) and Name. The EDDS re-encodes them as Protocol Buffers records tagged with RequestId and MISSION_NAME.48

    Inference

    The sources disagree about packet streaming. EUICD 24.0 §4.1.3 says only DARC parameter streaming is supported, yet §4.1.3.2 to §4.1.3.6 describe live TM, TC, EV and OOL streaming through the Data Provision Services.46 SUM 22.0 says PARC stream forms can be saved but not submitted.49 Both the EUICD (§4.1.3.2) and the SDD (§6.2.9.8.2) state that live packet streaming works only through the Data Provision Services, not the PARC Manager.4678 This wiki reads the "only DARC" sentence and the SUM note as left over from releases without that back end. Which missions use packet streaming is not stated in the available sources.

    A lightweight EDDS Stream Client attaches to an ACTIVE stream request and dumps the data to files at a fixed interval. SDD §6.2.5 lists TM, TC, OOL, event and parameter streams, and XML, Protocol Buffers, GDDS (TM and TC only) and "RawBody" binary outputs, and the EUICD defines recording file names for all five stream types.5051 Other passages still describe it as TM-only: SDD §4.5.5 and §6.1.7.5, and CIG §3.6.6, which allows only the Packet TM stream type.5253

    User management and the access model¶

    The SRS describes the problem this model solves: user-account administration used to cost ESA support staff a lot of effort.55 The EDDS therefore has a single authentication entry point and a layered model:

    • Accounts belong to users. After logging in, a user picks a mission and a role for the session.5556
    • A role bundles privileges. They cover which operations may be performed, which data types may be accessed, which services may be used, which quotas apply, and the request priority.55
    • The generic roles are System Administrator ("super user"), Mission Administrator, Manager (administers a group of users under one role, for example a PI institute) and Investigator (data access only).55

    In the implemented system, the SUM shows roles assembled from three kinds of reusable sets, plus groups.5758

    Object What it controls
    Data Access Set Data sources and request types a role may issue. A role without one cannot issue batch requests.
    Operation Data Set User-management operations the role may perform (for example create but not delete quota sets)
    Quota Set Limits: requests per period, ongoing requests (ACTIVE or QUEUED), data volume per period, disk space, and SPID, APID, parameter-name, TC-name, FARC file name/type and file-system folder restrictions, data time range and maximum time-filter duration
    Role Name, contact details, the sets above, a priority, enabled flag
    Group Binds users to roles. Disabling a group locks all its users out.

    Quota periods are given as cron expressions. With several quota sets on one role, the smallest numerical limit applies, but the SPID, APID, parameter-name and file restrictions are combined as a union. APID restrictions are converted to SPID lists before checking.58 EDDS and Mission Administrators act as super users and need no sets.58

    User records live in LDAP. The EDDS can also authenticate users against a separate "central LDAP", so that removing someone centrally also locks them out of the EDDS.59 The Solar Orbiter DDS uses the quota mechanism to limit each external user to certain APIDs, SPIDs, parameter names, file names or types, data volumes and relative time ranges. The DDID gives "the last 12 months" as an example.60

    Web-service operations¶

    The EDDS port type in the WSDL is shared by batch and stream services. Every operation runs in a session. Most operations can raise requestFault, authorizationFault or sessionFault. The exceptions are logIn, which raises authenticationFault or passwordExpiredFault, checkUserPassword (authenticationFault, sessionFault), and the one-way logOut and hasSessionExpired, which declare no fault.61 The operations, grouped by purpose:

    Group Operations
    Session logIn, logOut, hasSessionExpired, checkUserPassword
    Batch and stream submission batchRequest, streamRequest, reSubmit, startStreamData, stopStreamData
    Monitoring and control getStatus, getStatuses, getJobs, getJobsWithStatus, getJobsWithStatusAndLimit, cancel, suspend, resume, deleteData, deleteRequest, getHistoricalLog, stopHistoricalLogRetrieval
    Retrieval of results and templates getResponse, getRequest, getStreamRequest
    Catalogues and metadata getParamDefinitions, getCatalogue, getFarcCatalogue (deprecated), getDataspaces, getAlias, getLastConsolidation, getAllowedRequestTypes, getTransformations
    User management accountRequest, getUsers, getMissions, getMissionsAndDomains, getRoles, getUserAccountDetails, getMissionDetails, getUserQuota, getQuotaDetails, hasPermissionToSeeAllUsers

    The table follows EUICD §9.2.1.1.61 Issue 24.0 adds a REST API at .../edds/EddsRestService/v1/ that mirrors these operations with JSON bodies. The REST API adds a JSON Web Token (JWT, RFC 7519) authentication layer on top of the older session mechanism, which the EUICD itself calls insecure.12 The Java client API (edds-ws-client, version 3.6.0 in issue 24.0) wraps the services, and a NotificationManager delivers asynchronous push notifications over CometD.4762

    A 2025 SpaceOps paper maps these operations onto the new CCSDS Mission Product Distribution (MPD) services. batchRequest/streamRequest map to standing orders, getResponse to product delivery, getCatalogue to product listing, and the file-server and server deliveries to MPD delivery methods.63

    Architecture¶

    Components¶

    The SDD's component summary, simplified:64

    Component Role
    EDDS MMI (standalone Eclipse RCP application, or web application on Eclipse RAP) Builds batch, stream and user-management requests, shows status, downloads responses, administers users. No XML knowledge needed.65
    EDDS Client API Java façade over the SOAP and REST services, used by the MMI and by third-party tools such as MUST and ARES6462
    EDDS Web Server JAX-WS web application in Tomcat. It authenticates users, validates requests, checks privileges and serves notifications. It normally runs on the RELAY LAN.66
    EDDS Archiver Stores incoming requests in MariaDB, schedules them with Quartz, creates and updates the single acknowledgement per request, archives log messages67
    EDDS Server One instance per mission. It authorises requests, checks quotas, queues by priority, routes each request to a data provider, and produces response files.68
    Data providers PARC Manager and Data Provision Services (packets), DARC and SMON (parameters), FARC (files), file system, EDDS reports, HARC (EGS-CC HBase archive), EGS-CC REST764
    Delivery Manager Polls for finished response files and delivers them (local FTP area or push to user (S)FTP). It also sends e-mail and deletes expired responses.69
    Secure File Transfer (SFT) Separate ESOC product that moves files between two LANs through a firewall over TCP/IP. GFTS can play the same role.70
    Request Submitter Polls a directory for EDDS or GDDS request files and submits them; GDDS requests are first converted by XSLT71
    Stream Client Saves the data of an active stream request to files at intervals50

    The services are defined as WSDL files plus XSD schemas. JAX-WS wsimport generates the client stubs, server skeletons and bean classes from them. These are the baseline of the client API, web server, server and data providers.72

    The message bus¶

    All components talk through an ActiveMQ JMS broker. The SDD explains the two JMS primitives the design relies on. A message on a queue goes to exactly one listener, which allows load balancing. A message on a topic goes to every listener, which suits status broadcasts. Persistent queues and topics keep messages until a consumer returns.73 The choice explains several operating rules:

    • Run only one Archiver. Log messages arrive on topics, so two Archivers would store every log twice.74
    • Several EDDS Servers per mission are possible, because batch requests sit on a queue. But on start-up a server re-processes any request left ACTIVE in the database, so two servers could fight over the same request.74
    • Cancel and suspend messages are sent on topics. Nobody knows which server is processing a given request, so every server must see the message.75

    Typical destinations include esa.egos.edds.request.batch.unprocessed (web server to Archiver), esa.egos.edds.request.batch.tobeprocessed (Archiver to Server), esa.egos.edds.update.ack (acknowledgement updates, applied only by the Archiver) and esa.egos.edds.email.queue (outgoing mail).6775

    Deployment and network security¶

    The SRS lists the ESOC networks the EDDS must serve.76

    Security domain ESOC networks Served by EDDS
    ESA Restricted Networks OPS LAN Yes
    ESA Internal Service Networks OFFICE LAN, PRE-OPSLAN, SIMLAN OFFICE LAN and PRE-OPSLAN only
    ESA External Service Networks RELAY LAN, CITI DMZ, PISA LAN, ACCESS LAN All except ACCESS LAN
    Non-ESA Networks Public Internet Yes

    ESOC's security rules allow no inbound connections into the OPS LAN, no permanent connections between the OPS LAN and an outside LAN, and only connections initiated from inside.18 The EDDS satisfies them as follows:

    • The EDDS Server on the OPS LAN opens its JMS connection to the broker on the RELAY LAN. The connection is not permanent and is re-established when lost.1877
    • Response files go back to the RELAY LAN through SFT. Several SFT instances can be used, for example to separate stream and batch traffic.70
    • The LDAP master sits inside and pushes changes to the LDAP slave outside. It uses slurpd in "one shot" mode, so the replication connection is not permanent either.18

    The SDD describes four deployment scenarios.17

    Scenario Where the data providers are Pros Cons
    1. Base OPS LAN; Web Server and file server on RELAY LAN Simplest; easy access to OPS LAN components Heavy file traffic through the OPS LAN firewall
    2. Replicated outside Copies on the RELAY LAN, synchronised by SFT Little firewall traffic Some services impossible; data replicated into a less secure LAN
    3. Split Some inside, some outside; two EDDS Server instances All services, better performance Complex configuration; replication
    4. Office LAN replica Copies on the Office LAN; separate web and EDDS servers for internal and external users Performance for internal users; data replicated once Complex; data in a less secure internal LAN

    For scalability, one Web Server and one Archiver are shared by all missions. There is one EDDS Server per mission, one set of data-provider drivers per mission and domain, one Delivery Manager, optional Stream Clients, and at least two SFT instances (one per firewall side) per mission and domain.74

    The MIB inside the EDDS

    The EDDS needs a copy of some MIB files for every domain it serves. It uses pid.dat to convert SPIDs to APIDs and back, and tpcf.dat for packet descriptions. For the TC reports it also needs the command subsystem and command host files and MISCbase.ids, plus two hand-written mappings: command source types (CMDsourceTypeMapping.properties) and command request status types (CMD_ttRqstObqStatusMapping.properties). With the Data Provision Services it additionally needs MISCcontext_SHARED.sta to map domain and data stream names. The CIG warns that stale copies break filters such as an APID search.89 An SRN issue 14.0 fix concerns a "request incorrect status when SPID not in pid.dat".90 For scale, the September 2025 Solar Orbiter MIB has 11,150 packet definitions spread over 293 APIDs. One APID can stand for hundreds of SPIDs: APID 263 alone has 699, and 64 APIDs have 24 or more.91

    How a batch request flows¶

    The SDD scenario for an archived-packet request delivered by the Delivery Manager:77

    sequenceDiagram
    participant U as User / EDDS MMI
    participant W as Web Server
    participant Q as ActiveMQ
    participant A as Archiver + DB
    participant S as EDDS Server
    participant P as PARC provider
    participant D as Delivery Manager
    U->>W: logIn(user, password)
    W->>W: check against LDAP slave, open session
    W-->>U: sessionId
    U->>W: batchRequest(RequestMessagePart)
    W->>W: authenticate, validate, check privileges
    W->>Q: request ... .batch.unprocessed
    Q->>A: deliver
    A->>A: schedule (Quartz), assign job IDs, store, create acknowledgement
    A-->>U: job ID list (via Web Server)
    A->>Q: request ... .batch.tobeprocessed (delayed if scheduled)
    Q->>S: deliver (connection opened from OPS LAN)
    S->>S: authorise, check quota, queue by priority
    S->>P: execute (retrieve, filter, format, compress, encrypt)
    P-->>S: response file(s), progress updates
    S->>D: response file via SFT to the Delivery Manager inbox
    D->>D: deliver (local FTP or push to user SFTP), e-mail if requested
    D->>Q: acknowledgement updates
    Q->>A: update acknowledgement (single writer)

    The steps inside the EDDS Server follow a chain of responsibility.68

    1. Authorisation: the user's role must allow the request. The acknowledgement is updated.
    2. Quota check: if a generic quota check fails, the request is not executed and the acknowledgement explains why.
    3. Execution: requests are queued by role priority, with a configurable number running in parallel. A BatchRequestHandlerFactory combines retrieval, filtering and formatting handlers for the specific archive. Results are transformed by XSLT if requested, then encrypted and compressed.6877

    On a provider error the server can retry at configured intervals. The request stays ACTIVE, and the acknowledgement records the retries and the reason.77 Persistent messages mean that requests survive a server crash. On start-up the server also recovers SUBMITTED requests whose execution time is in the past.68 Suspending a request marks the last sample of the last finished file in the acknowledgement. Resuming restarts from there, with a possible small overlap; the overlap is larger for raw and OOL requests, because the PARC returns undecoded packets in batches.75

    The Solar Orbiter DDS in brief¶

    Solar Orbiter's "DDS" is an EDDS installation at ESOC, described in the mission's Data Delivery Interface Control Document (DDID) SOL-ESC-IF-05011.101 Its main features:

    • Prime and backup servers on the RELAY LAN, the backup in cold redundancy. A switch-over means users re-point their client. Scheduled requests must be resubmitted, and temporarily stored responses must be requested again.102100
    • Data come from the MCS long-term archive (LTA): packets from its PARC, parameters from its DARC and files from its FARC. TM is retrievable "within seconds" of reception at the station.103
    • File-server push over SFTP is the nominal delivery. Users whitelist the DDS addresses and can use an ESA-provided SSH public key instead of a password. Server-side storage is not a baseline option.104102
    • The nominal route to the Science Ground Segment is not the EDDS but RAPID files forwarded by GFTS, described on the formats page.104

    The DDID publishes the server host names and IP addresses for firewall configuration. This wiki does not repeat them. The full Solar Orbiter specifics, including SCOS-2000 packet headers, internal packets and RAPID records, are on the formats page.

    Other ESOC tools consume EDDS output too. The ARES analysis system, the successor of MUST, imports EDDS response files fed from the MCS DARC and PARC.105
