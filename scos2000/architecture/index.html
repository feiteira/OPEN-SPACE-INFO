    SCOS-2000 architecture¶

    SCOS-2000 is described by ESA as a mission control system kernel: a set of object-oriented components that system developers can reuse, and a set of generic executables that a mission can use as they are when their functions match its needs. The same kernel is meant for spacecraft control and for checkout systems, can be extended with mission-specific functions, and is distributed, scalable, configurable and open.1 This page explains how that kernel is organised and how data flows through it. It starts with the overall structure, then follows telemetry from the ground station to the operator's display and telecommands from the operator to the spacecraft, and ends with archives, events, external interfaces, configuration and multi-domain operation.

    The descriptions come mostly from ESA presentations and interface documents of 2000–2018. SCOS-2000 changed considerably between releases (see releases), so each statement is dated by its source. The mission database that configures all of this is described in the MIB and its topic pages.

    Overall structure¶

    Clients and servers¶

    SCOS-2000 inherits the client-server design of SCOS-II: each operator works on a workstation with local processing and local caches, while central servers coordinate the system and host the interfaces to the ground stations.163 The GSAW 2003 presentation lists the processes on each side:3

    Side Processes Domain
    Server (prime and backup) Packetiser TM
    Behaviour (limits) checker TM
    Synthetic parameter packet generator TM
    Multiplexer, Releaser, Verifier, On-Board Queue Model (OBQM) TC
    Archive TM, TC, events
    Events & Actions servers Events
    Configuration server (MISCdynamic) System
    Client (MMI applications) Desktop (with alarm display) System
    Monitoring display container, out-of-limits (OOL) display TM
    Event logger Events
    Manual and automatic stacks, TC history TC
    Caches TM, TC, events
    Configuration client (TM and TC "SPACON") System

    A typical configuration is a network of workstations, but the system can be scaled down to a "SCOS-2000 in-a-box" on a single workstation for simpler missions.13 ESOC's LEOP configuration of 2003 had prime and backup SCOS-2000 servers, prime and backup NCTRS, and 35 client workstations spread over six rooms (15 + 6 + 6 + 4 + 2 + 2).11

    Functional subsystems and layers¶

    ESA groups the functions of SCOS-2000 into subsystems with short names: telemetry processing (TM), telecommanding (TC), the online database (DB), the online archive (ARCH), general services and utilities, the Operations Language (OL), roles and privileges (USER), events and actions (EVAC), and on-board software maintenance (OBSM).13 The GSAW 2003 slides arrange the software in layers, from persistent storage and database access at the bottom, through the telemetry, command and user models, to the applications on top:4

    Operator applications¶

    Operators start SCOS-2000 from a task launcher. In the Herschel PACS instrument test set-up of 2004, the command s2.start opened the launcher; one button selected all server applications and another the standard client applications. The desktop then showed a top bar with the workstation settings, user login and alarm-tone control, and a footer with the three most recent log messages.2223 The client applications and their launcher names were:25

    Launcher name Application Purpose
    MON Telemetry desktop Alphanumeric, strip chart, scrolling and mimic TM displays
    VPD Variable packet display Contents of variable TM packets
    MSTK Manual stack Manual telecommand release
    TCHIST Telecommand history Status of every released command and its verification stages
    OOL Out-of-limits display Parameters currently out of limits
    EVLOG Event logger (message display) Scrolling display of SCOS-2000 log messages

    The 2003 slides list the display types in more detail.9

    Display Description

    Graphic display (GRD) 1 to 8 parameters against time, strip chart emulation, or parameter against parameter
    Mimic displays Schematic displays, with an editor
    Scrolling display (SCD) Parameter values scrolling with time

    The display types and SPACON functions come from the monitoring and commanding slides of GSAW 2003.897 The TQD validity panel is described in the EMCS user manual and its OL editor in the ICD.2755 The MIB defines AND, GRD, SCD and printout layouts; see display definitions in the MIB.

    Each application has its own user manual. The 2004 guide lists manuals for the external interface and TOPE, the desktop, the event logger, the telemetry desktop, the OOL display, the variable packet display, the manual stack and the command history.26 The Database Import ICD references further manuals and design documents, among them the monitoring, commanding and system-level software requirements documents, the OL design document, the Synthetic Parameters user manual, the Events & Actions user manual, the MIB Applications user manual, and interface documents for stack import, task parameter files and telemetry parameter injection.44

    Packetiser¶

    The telemetry packetiser receives telemetry transfer frames, report packets and administrative messages. It reconstructs packets from frames, extracts the Command Link Control Word (CLCW) for the commanding chain, and applies quality, continuity and sequence checks.86 The Database Import ICD added the Packetiser in issue 5.0 for release R2.2e.43 To recognise a packet, the packetiser reads the APID from its fixed place in the header, and the PUS type and subtype from a position set in the configuration (the same position for all packets of a spacecraft). For some type and subtype combinations it also reads up to two additional identification fields from the application data, as specified in the pic table. It then looks up the pid table to find the processing keys: the SCOS-2000 Packet ID (SPID) for fixed packets and the Telemetry Packet Structure Definition (TPSD) for variable packets.59 Packets without a data field header are identified by APID alone.60

    The ICD turns two on-board design choices into explicit constraints: the type and subtype must sit at the same place in every TM packet, and every packet with the same type and subtype must carry its additional identification fields at the same place.59 From R5.0 each distinct TM packet must have its own SPID, because packets are stored in a database and sharing SPIDs caused retrieval and display problems.6049 The packetiser can check the packet error control field (when PID_CHECK is 1) and can generate an event when a packet arrives (when PID_EVENT is I, W or A).61

    Time stamping. Every frame and packet that is filed or distributed gets a time stamp, which is the prime filing key of the history files. The packetiser supports three options: the time of filing in the archive (useful when replaying old frames during tests), the Frame Transmission Time derived from the Earth Reception Time minus ground, propagation and on-board delays, or the on-board time in the packet converted to UTC through the time correlation library.37 The time correlation function itself (time couples, least-squares or synchronised-clock coefficients, accuracy and validity status) is described on Time correlation in SCOS-2000.36

    The telemetry model: extraction, validity and calibration¶

    Parameter extraction follows the plf definitions for fixed packets (including super-commutated parameters) and the vpd definitions for variable packets.859 Variable packets have a limitation: the values extracted from them cannot take part in the full TM processing (validity, monitoring checks, verification, synthetic parameters), because their parameter identities and time references are only known once each packet is opened. The ICD therefore advises against using variable packets for regular housekeeping.68

    Every value carries a validity. The TOPE interface of the EGSE version exposes the validity as a bit set, and its list shows the causes that SCOS-2000 tracks: state validity false, system element not powered, transport route off, a telecommand scheduled for the parameter (transient), transport errors, an expired value (packet not arrived), unknown state, calibration failure, a time before the mission epoch, a packet not configured in the cache, an uninitialised value, retrieval errors, database errors, unknown fields or types, overflow, division by zero, and OL parse errors.27 These causes extend the validity factors already planned for SCOS-II: power, data unit quality, data routing, age, stability after commanding and user-defined status.18

    The raw value of a parameter is its value before calibration. It is not the same as the encoded bits, except for unsigned integers: a raw value of -1 in a 16-bit signed integer parameter is encoded as 0xFFFF.45 Calibration turns raw values into engineering values. See calibration in the MIB and MIB parameter types.

    Behaviour checking¶

    The behaviour checker applies the monitoring checks defined in the ocf and ocp tables. The ICD defines limit checks and status checks (each with soft or hard severity), delta checks on the change since the last valid value, and status consistency checks against a reference value that SCOS-2000 maintains from the predicted or detected effect of commands. A fifth type, E, does not raise an out-of-limits state at all: it generates a SCOS-2000 event whose full ID is BEHV:: followed by the parameter name, which can then trigger actions.58 Each check has an applicability condition (a parameter equal to a value), except status consistency checks, whose applicability is always true. The checks of a parameter are evaluated in order and the search stops at the first applicable check or soft/hard pair, unless the global variable BEHV_STOP_FIRST_SET says otherwise.58 Details are on monitoring checks.

    The Solar Orbiter MIB of September 2025 uses four of the five OCP_TYPE codes: 4,153 H, 3,096 S, 105 delta (D) and 15 status consistency (C) check records, and no event-only (E) checks.75 SCOS-II had planned "behaviour checks" against a predicted on-board state.18

    SQL used 
    -- solo-2025-09-16.sqlite
SELECT OCP_TYPE, count(*) FROM ocp GROUP BY 1;
-- C|15   D|105   H|4153   S|3096
SELECT PID_EVENT, count(*) FROM pid GROUP BY 1;
-- (blank)|1162   A|6360   I|1374   N|1095   W|1159
SELECT PID_CHECK, count(*) FROM pid GROUP BY 1;
-- 0|11144   1|6
SELECT PID_EVENT, PID_TYPE, PID_STYPE, count(*) FROM pid
 WHERE PID_EVENT IN ('A','I','W') GROUP BY 1, 2, 3;
-- A|1|2|274   A|1|8|1477   A|5|3|2911   A|5|4|1698   I|5|1|1374   W|5|2|1159
SELECT PID_TYPE, PID_STYPE, PID_APID, PID_DESCR FROM pid WHERE PID_CHECK = '1';
-- 0|0|1|Bad/Idle/Good complete transfer frame (3 rows)
-- 166|1..3|1966|MATIS BASIC HKTM OK, MATIS RX LOCK EXPECTED, MATIS SSMM FTS COMMANDING

    The same MIB flags 8,893 of its 11,150 packet definitions to raise an event on reception: 6,360 with severity Alarm, 1,374 Info and 1,159 Warning (the other 2,257 have N or the default, which is N). The severities follow the PUS report types: all 1,374 Info events are (5,1) reports and all 1,159 Warning events are (5,2) reports, while the Alarm events are (5,3) and (5,4) event reports (2,911 and 1,698) and (1,8) and (1,2) failure reports (1,477 and 274). See ST[05] event reporting and ST[01] request verification. Only 6 packet definitions ask the packetiser to check the packet error control field: the three transfer-frame entries on APID 1 and three type 166 packets on APID 1966 described as MATIS reports, so no spacecraft source packet definition has PID_CHECK = 1.7561

    Inference

    Two readings here are the wiki's own. First, the status consistency check, whose reference value follows the commands sent, can be seen as a simple form of the SCOS-II behaviour checks against a predicted on-board state; neither source draws the link. Second, since no spacecraft packet definition in the Solar Orbiter MIB sets PID_CHECK, packet error control is probably checked elsewhere in the ground chain or not at all at packet level. The MIB does not say which.

    Synthetic parameters and the OL¶

    Synthetic parameters are monitoring parameters whose value SCOS-2000 calculates (the ICD notes that older systems called them derived parameters). Once calculated they behave like telemetry: they can be displayed, calibrated, limit-checked and used in other synthetic parameters. Their validity follows from the validity of their inputs and can be restricted further with an explicit validity condition.5254 The field PCF_NATUR of the pcf table selects the kind:525355

    PCF_NATUR Kind How it is calculated Stored?
    D Dynamic OL synthetic OL expression in a file named after the parameter, evaluated locally when an application needs it, every time a contributing value or validity changes; recalculated in retrieval No
    P SPEL synthetic Like D, written in the Synthetic Parameter Expression Language; only in the EGSE delivery of SCOS-2000 No
    H Hard-coded synthetic C++ code, written directly or produced by the OL compiler, linked into a library; cheaper to run but not visible or editable online No
    S Saved synthetic Calculated centrally by the Synthetic Parameters Packet Generator (SPPG) from a linked D or H parameter, stored in synthetic packets Yes
    C Static user-defined constant Constant from PCF_PARVAL, changeable with the OL editor of the TQD –
    R Raw telemetry (and dynamic user-defined constants) Extracted from a packet; dynamic constants come from an internal "constants" packet set through TM SPACON or the parameter injection interface –

    SCOS-2000 evaluates synthetic parameters in cascade: a new sample of parameter A triggers A, then any B that uses A, then any C that uses B. Up to R3.1 this forbade circular dependencies. Later releases calculate each parameter only once per update cycle.54 The ICD warns that synthetic parameters that use super-commutated inputs are evaluated once per sample and can be very demanding.53

    Saved synthetic parameters exist because dynamic ones are recalculated on each workstation and again in retrieval. A saved value is calculated once, centrally, and stored with its validity, so every display shows the same value when moving backwards or forwards in history, even after the definition changes. The cost is that a synthetic packet is only generated when its triggering TM packet arrives, so not every intermediate value is kept. Each saved parameter occupies a 13-octet slot in its synthetic packet.53

    Example: saved synthetics in the Solar Orbiter MIB¶

    The Solar Orbiter MIB of September 2025 has 1,582 dynamic OL synthetic parameters (each with its OL file), 2 saved synthetic parameters, and no hard-coded, SPEL or constant parameters.75 The two saved parameters, NTTSS030 and NTTSS031, hold the time of the last carrier lock of the two transponders labelled DST-1 and DST-2. Each is linked through PCF_RELATED to a dynamic OL parameter (NTTSX030, NTTSX031). Both are stored in the synthetic packet SPID 66838, defined in pid as type 251, subtype 2 on APID 1966 with the description "Saved Synthetics", and in tpcf as SAVED_SYNTH. Their plf entries sit at byte offsets 0 and 13: exactly one 13-octet slot each, as the ICD requires.7553

    The OL file of NTTSX030 (real MIB data, comments omitted) updates a global variable with the time of the receiver lock parameter only when that parameter's raw value is 1 (locked), and otherwise returns the previous saved value through a "static reference" to $NTTSS030:

    if (NDSD0021.raw == 1) then
GVAR_DST_1_LastCarrierLockTime := NDSD0021.time;
endif;
$NTTSS030;

    The if (...) then ... endif; form and the := assignment are the same as in the SCOS-II OL example of 1994 described on the overview page, and the ICD documents the .raw and .eng parameter views of the SCOS-2000 OL.752155 The full OL syntax is documented in the SCOS-2000 Synthetic Parameters user manual, which is not in this wiki's library.5244 See synthetic parameters and the OL language.

    SQL used 
    -- solo-2025-09-16.sqlite
SELECT PCF_NATUR, count(*) FROM pcf GROUP BY 1;     -- D|1582  R|125161  S|2
SELECT count(*) FROM synthetic;                       -- 1582
SELECT PCF_NAME, PCF_DESCR, PCF_RELATED FROM pcf WHERE PCF_NATUR = 'S';
-- NTTSS030|Last C_Lock DST-1|NTTSX030   NTTSS031|Last C_Lock DST-2|NTTSX031
SELECT PLF_NAME, PLF_SPID, PLF_OFFBY, PLF_OFFBI FROM plf WHERE PLF_NAME IN ('NTTSS030','NTTSS031');
-- NTTSS030|66838|0|0   NTTSS031|66838|13|0
SELECT PID_TYPE, PID_STYPE, PID_APID, PID_SPID, PID_DESCR FROM pid WHERE PID_SPID = '66838';
-- 251|2|1966|66838|Saved Synthetics
SELECT * FROM tpcf WHERE TPCF_SPID = '66838';         -- 66838|SAVED_SYNTH|26
SELECT SOURCE FROM synthetic WHERE NAME = 'NTTSX030';

    Internally generated packets¶

    Several SCOS-2000 functions publish their state as internal TM packets, so that the normal monitoring displays, checks and archives can handle it. The ICD names the SPPG synthetic packets, the "constants" packet of dynamic user-defined constants, the "MISC" packet with selected dynamic configuration variables, and the system control packets of the multi-domain SCTL application. It recommends giving each of them a pid entry with a type, subtype and APID combination that no other source uses.60555657 In the Solar Orbiter MIB the saved synthetic packet uses type 251 on APID 1966 (see above). The same MIB also has pid entries for bad, idle and good complete transfer frames (SPIDs 1000002, 1000003 and 1000006, APID 1, type and subtype 0), which the ICD does not list among the internal packets.75

    Inference

    The transfer-frame entries probably let the archive and the packet history displays handle the frames that the packetiser files (GSAW 2003 lists TM transfer frames among its inputs, and TN-1030 says that frames as well as packets are time-stamped for filing).637 The MIB does not document their purpose.

    Command sources¶

    The manual stack is the operator's main tool. In 2003 it could load commands and sequences with parameters, de-calibrate parameter values, time-tag commands for on-board execution, and set release dependencies by grouping, blocking, delta release times and interlocking. It had a master manual mode and a wait mode, applied static and dynamic pre-transmission validation (PTV), and could save and load commands, sequences, stack files and task parameter files (TPFs). Sequences accept formal parameters and absolute start or execution times. The autostack offers a restricted subset with no editing, driven by release or execution times.7 A multiplexer lets several sources command in parallel.7 Command sequences and their parameters are defined in the MIB (see command sequences and parameter sets); from R5.0 they are converted to XML and loaded from the file archive.48

    Release¶

    The releaser is the interface to the external command destination, NCTRS.7 It builds the packet from the header definition and parameters in the MIB (see commanding in the MIB) and automatically appends the 16-bit CRC unless the command type says otherwise.65 Commands with an execution time-tag are automatically wrapped in service (11,4) commands.73 The maximum command size is set by a configuration variable, with a default of 248 octets that must leave room for the header, the CRC and the time-tag wrapper.63 Interlocks hold further commands until a given verification stage of a previous command is reached.6530

    The command type CCF_CTYPE marks commands that are not ordinary packets. R is a control segment (a "reset map" command) and F a control frame (a BC frame: Unlock or Set V(R)); for both, the MIB defines the frame data field rather than a packet header. S is a packet without a packet error control field, typically for EGSE equipment. From R5.0, T is an SLE throw event, sent to the SLE service provider at the ground station, and N is a NIS throw event, executed by the NIS and not forwarded to the station.6564

    The Solar Orbiter MIB uses three of these types. Its control frames are UNLOCK and SETVR, its control segments are RESET, REIN_TTR and TC_ONLY, and six NIS throw events open and close the session and the TM and TC links (for example EGENRTCO, "GENERIC OPEN TC LINK"). The throw events use a dedicated packet header named NOS2KHDR, described as "NIS Throw Events".75 See COP-1 for the Unlock and Set V(R) directives and NCTRS, NIS and the ground station interface for throw events.

    Verification¶

    The verifier performs multi-stage verification of each released command and disables status consistency checks on the telemetry parameters that the command affects.7 SCOS-2000 supports two kinds of verification stage. Report-based stages wait for PUS service 1 reports. Parameter-based stages check monitoring parameter values against criteria within a time window.66 For service 1, the verifier extracts the 4 octets that echo the command's packet ID and sequence control from each report, to identify the command instance. The echo must be at the same place in all type 1 reports. The subtype alone decides success or failure; the failure code is ignored. Progress reports can only feed progress stage 0.7067 See ST[01] request verification and command verification in the MIB.

    The full list of stages appears in the EGSE user manual, which gives the order that the TOPE language reports for each stage:28

    Order Stage Meaning
    0 PTV_DYNAMIC Dynamic pre-transmission validation
    1 PTV_STATIC Static pre-transmission validation
    2 MCS_RELEASE Release by the MCS
    3 UV_GS_RECEIVE Received by the ground station (or EGSE TC front end)
    4 UV_GS_UPLINK Uplinked
    5 UV_ONB_ACCEPT Accepted on board (reported by the ground station or TC front end when the spacecraft confirms reception of an AD-mode command)
    6 EV_APP_ACCEPT Accepted by the application process
    7 EV_START_EXEC Start of execution
    8–17 EV_PROGRESS_0 to EV_PROGRESS_9 Progress steps 0 to 9
    18 EV_END_EXEC Completion of execution

    Each stage has a status. The values listed are IDLE, PENDING, PASSED, FAILED, UNVERIFIED, UNKNOWN, TIMEOUT, SUPERSEDED, UNCERTAIN_FAILED, UNCERTAIN_PASSED, AFFECTED, SCC and NOT_APPLICABLE.28 The stages prefixed "UV" are reported by the ground side (the ground station through NCTRS, or the EGSE TC front end). Those prefixed "EV" concern execution by the application process, reported through service 1 or derived from telemetry conditions.29

    In the Solar Orbiter MIB, the 206 verification stages are all acceptance or completion stages: 16 report-based acceptance stages, 23 report-based completion stages and 167 parameter-based completion stages. There are no start or progress stages.75

    The on-board queue model¶

    The On-Board Queue Model (OBQM) keeps a ground image of the on-board schedule of time-tagged commands, displayed in the On-Board Queue Display.7 The ICD lists what SCOS-2000 does for ST[11] time-based scheduling: it wraps execution time-tagged commands in (11,4) commands, models the effect of service 11 commands on the ground image, reconstructs the image from spacecraft reports (from R5.2), supports delayed verification of time-tagged commands with live and playback telemetry, and generates service 11 commands from selections in the ground image. The limits are that the command structures follow the Rosetta reference implementation, each (11,4) command carries one TC packet, only absolute time tags are supported, and interlocks and the time-shift command are not modelled.73

    Archives¶

    SCOS-2000 files every received packet centrally. In 2003 the archive used C-Tree+ with non-circular filing (files grow continuously and are split for long-term archiving), fixed or variable length records, and filing by type (TM, TC, event), SPID, data stream (a logical grouping such as real-time or playback) and time. Retrievals run independently from real-time processing. Packets are distributed to client caches over TCP/IP. Administrators can switch filing on and off globally with the PDSadmin tool, switch hot to the backup server, and use an administration tool to delete, dump, export, print or re-send packets and to split the archive.10 In the EGSE delivery of 2004, each SPID archive was an index file and a data file in the hfiles directory. Each record had a header used for retrieval and a body with the received data.31

    Retrieval can start at any time, select a data stream, and merge up to 4 streams on one display. Synthetic parameters are recalculated for retrieved data.8 The ICD calls this dynamic part of the Mission Information Base the packet archive, in contrast with the static database.45 Release 5 changed both parts. From R5.0 packets are stored in a database, and sequence and display definitions are converted to XML and kept in the File Archive (FARC) instead of the run-time database.4948

    Later ESOC systems added further archives around SCOS-2000: the Packet ARChive (PARC) and the Data Archive (DARC) for parameters, with the PCF_DARC field of the MIB selecting the parameters to archive.4251 They are described on mission archives: PARC, DARC and FARC.

    Events and actions¶

    SCOS-2000 events are messages with a severity, stored in the archive (so they can be retrieved) and notified live to operators, with severities configurable by role.72 They come from several places:

    • the packetiser, when a packet flagged with PID_EVENT arrives; the event text comes from the packet description and the event ID has the form TPKT_OBE:: plus a number between 1 and 9999;62
    • the behaviour checker, for checks of type E, with the ID BEHV:: plus the parameter name;58
    • SCOS-2000 applications themselves, whose event numbers start at 10000.62

    The Events & Actions servers react to events with configured actions. The ICD gives the examples of sending an e-mail, setting a configuration variable and running a script.583 The event logger shows the event stream to operators.25 SCOS-II had already planned an "Events & Actions" facility, in which user-defined events identified in the incoming data are logged and trigger actions such as recovery or diagnosis, and "event-driven commanding routines" that react automatically to on-board anomalies.2019

    External interfaces¶

    EXIF and TOPE¶

    The SCOS External Interface services (EXIF) are an extension module of SCOS-2000 with a CORBA interface. External applications use it to acquire telemetry, send commands, raise events or alarms, and retrieve historical data. Some EXIF services inject events, parameters or commands into SCOS-2000. Others deliver telemetry parameters, TM packets, events or command history to the requesting application. EXIF is made of several CORBA servers, found through the CORBA naming service.38 In the PACS set-up of 2004, the EXIF tasks EXIF_TMM, EXIF_TM1, EXIF_CHM and EXIF_CH1 were started from a separate launcher (exif.start) together with the TOPE test language. Each additional TOPE client needed its own EXIF_CHx task.2433

    The Test and Operations Procedure Environment (TOPE) is a Tcl extension that uses EXIF to send commands, fetch and subscribe to parameters, and follow command verification. It is described in detail on SCOS-2000 as EGSE.3238

    Configuration¶

    MISCconfig and configuration variables¶

    Most SCOS-2000 behaviour is set by configuration variables in the MISCconfig file, documented in the SCOS-2000 Configuration Variables guide.44 Examples in the MIB ICD include the position of type and subtype in TM packets, the directory of the OL expression files (IMPT_EXPR_DIR), the default on-board clock (TCO_DEFAULT_OBT_ID), the maximum command size, and the name of the time-tag wrapper command.59525063 The EGSE user manual of 2004 lists the EGSE-specific variables: the routing mode, gateway hosts and ports, the SPIDs for system packets, time-stamping and checksum options, and the mission epoch.34 See SCOS-2000 as EGSE.

    Some variables can change at run time. The MISC server keeps their state, distributes changes to its clients, and publishes selected variables in the internal "MISC" TM packet. Each published variable needs pcf and plf entries, as a 32-bit signed integer, a double precision real or a character string. Only numeric variables can be fully processed by the monitoring applications. Their positions in the packet must stay the same across database versions, so that older MISC packets in the archive can still be read.56

    MIB import¶

    The static database enters SCOS-2000 through the importer, which reads the ASCII tables (one .dat file per table, tab-separated) and the synthetic parameter files and builds the run-time database. The importer checks field formats and lengths, mandatory fields, relational integrity and parameter value syntax, and logs its messages to a file that is overwritten at each import. It can import a whole database or only check it.47 Its full description is on the MIB.

    Domains and multi-mission operation¶

    SCOS-2000 is a single system that can manage and control several entities called domains. Each domain has its own directory of MIB files and synthetic parameter files. A special General Domain needs the files of all domains plus its own multi-domain database, which only defines multi-domain synthetic parameters. An import started from the General Domain can import the database of any domain; an import started from a specific domain only imports that domain.46 The multi-domain System Control application (SCTL) starts, stops and monitors the SCOS-2000 server families, and records their status in TM packets that the normal displays can show.57

    Multi-mission support grew over time. SCOS-II was designed to control several satellites of one family, not several missions.16 In April 2000 ESOC planned R4.0 to allow several SCOS-2000 versions on one machine and to support constellations.15 In 2003 R4.0 was announced as multi-mission (constellations and formation flying; LEO, GEO and deep space).12

    Performance and limitations¶

    Figure Value Source
    SCOS-II design goals 2 Mbps TM and 4 kbps TC concurrently, more than 10 display updates per second, up to 50 workstations 17
    SCOS-2000 telecommand chain (2010, Terma) About 2 packets per second with checking, 20 without 40

    The ICD documents several functional limits besides those already mentioned. The deduced data structure of PUS is not supported, only deduced parameter fields. Variable packets cannot feed the full TM processing. The generation interval of periodic housekeeping packets is static in the database, and the time stamp of each sample in a housekeeping packet is the packet time plus a fixed offset from the database. Commands can be blocked into one TC segment, but not aggregated into one TC packet. There is no specific processing of services 2, 3, 4, 5, 8, 12, 14 and 15 (for service 15, packets downlinked inside (15,8) reports are not extracted), and services 6 and 13 need mission-specific implementations.697174 Terma, an industrial user, added that recent ESOC developments tended to increase the size and complexity of SCOS-2000, and that some key parts of the code base had been approached in a "short term way" and needed refactoring.4041
