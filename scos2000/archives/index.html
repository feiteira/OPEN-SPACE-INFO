    Mission archives: PARC, DARC and FARC¶

    Everything a SCOS-2000 mission control system receives, sends or produces ends up in one of three archives of ESA's ground operation software (EGOS):

    • the PARC, the packet archive, holding SCOS-2000 telemetry, telecommand and event packets;
    • the DARC, the parameter archive, holding decoded telemetry parameter samples;
    • the FARC, the file archive, holding mission files: flight dynamics and planning products, MIB releases, files reconstructed from the downlink, and SCOS-2000's own sequence and display definitions.

    For Solar Orbiter all three run on the mission control system's long-term archive (LTA) server on the operational LAN, and the data dissemination system (EDDS) answers every external request from them.3836 This page collects what the public documents say about the three archives. Their own interface and design documents are not public, so much of the picture comes from their clients (EDDS, the time correlation server, the MIB import) and from the Solar Orbiter Data Delivery ICD; where the sources are silent, the page says so.

    Inference

    The arrow from PARC to DARC is this wiki's reading: SCOS-2000 decommutes parameters from packets, and the DARC returns, for each sample, the SPID and generation time of the packet it came from, which suggests that it is populated from processed packets. How samples actually reach the DARC is not stated in the available sources.21

    EDDS supports several deployment scenarios: data providers in the operational LAN, replicated in the relay LAN, split between the two, or replicated in the office LAN; when they are outside the operational LAN, the only interaction with it is their synchronisation by the Secure File Transfer daemon.7 The EDDS SRS recommends, for security and performance, replicating the long-term archives to the EDDS LAN.25 For Solar Orbiter, the redundancy of the back end (the data providers on the MCS) is that of the MCS itself, the DDS being reconfigured to the backup source if needed.37

    History: from history files to three archives¶

    History files. In the SCOS-2000 of the early 2000s the MIB was described as a static part, the "database", and a dynamic part, the "history files".53 Up to S2K-R5 the SPID of a telemetry packet also decided which history file the packet was archived in.55 Issue 5.1 therefore asks that the mapping between packet identification fields and SPIDs not change once archiving has started, and that PID entries whose SPIDs are present in the history files not be deleted, so that retrieval services "such as the Generic Data Distribution System" keep working.54 The Rosetta/Mars Express/Venus Express DDID speaks of the MCS Data Archive System (DAS), "not to be confused with the long term data archive", from which the DDS and Flight Dynamics' SCOS-2000/ORATOS Data Access (SoDA) software retrieved packets; TC packets were retrieved by the primary key of the TC history file (packet filing time) or its secondary key (specified execution time).646566 The SCOS-2000 TM retrieval service TDRS likewise extracted parameter values from fixed-length packets in "the SCOS-2000 history file archive".22

    Renaming. Among the clarifications of ICD issue 6.7, one asks that remaining mentions of "History files" be replaced by "packet archive".63

    FARC. From SCOS-2000 release 5.0, command sequence and display definitions are converted to XML and imported into the FARC instead of the run-time database (ICD issue 6.4, 2007).5862 Aeolus contributed to the Earth Explorer kernel the management of on-board software configurations through sequences stored in a "Central File Archive".69

    DARC. The DARC was developed because, in the words of the EDDS SRS, mission control systems "generate parameter data on the fly", which could not meet EDDS performance; a design document for it existed by January 2009 (issue 1.0). The same SRS section adds that a "new packet archive low level component" (PARC) had been finalised within EGOS.2223 The MIB gained the field PCF_DARC for it with ICD issue 6.7 (S2K-DCR-5146, and SPR-5711 adding PCF_DARC and PCF_ENDIAN "for DARC integration"), applicable from SCOS-2000 R5.2.63 The DARC ICD and design document reached issue 2.0 in June 2014.2 EDDS later had to distinguish DARC versions up to 2.2.2 (millisecond time stamps, engineering values only) from 2.3.0 and later (microseconds, raw values, parent packet information).2621

    PARC: the packet archive¶

    What it holds¶

    The PARC stores SCOS-2000 packets, also called TDEV packets: a common header, a header specific to telemetry (TM), telecommand (TC) or event (EV) packets, and the packet data.39

    • For spacecraft TM the packet data are the complete source packet from its primary header onwards. Some packets instead contain a whole transfer frame (for example frames filed while a science packet is incomplete) or MCS-internal data on separate data streams.4044
    • For TC the packet data are not the telecommand alone but everything the TC History needs: static information from the MIB, release conditions, verification status and finally the packet sent. SCOS-2000 also files, with SPID 200, a separate packet with the static PTV/CEV details of each command; released commands use SPID 100. Because the MIB on the MCS may change, storing the static information with each command is the only way to interpret old commands correctly.404342
    • For EV the packet data are MCS event messages, for example the metadata of TM files reconstructed from the downlink.40
    • MCS-internal packets on APID 1966: file transfer model metadata, good, bad and idle mini transfer frames, bad telemetry packets, missing packet detection, packets with no assigned SPID, dynamic user-defined constants, TC Spacon and MISC configuration packets, time correlation report, couple and coefficient packets, and releaser packets including ground station responses.45
    • The time correlation server files its couples and coefficients here, deletes couple packets in the PARC on request, and finds the earliest valid coefficients by querying it.70

    Telemetry and event packets are written once; the same packet can be stored twice (for example after a re-call to fill a gap), differing only in some header fields such as the reception time. TC packets, in contrast, are updated in place each time their verification status changes; their release time is a unique key.49

    Keys and header¶

    The common header carries the two keys. The filing time is part of the primary key and is the EDDS "generation time": for spacecraft TM, the time stamp chosen by the time-stamping policy (normally the correlated on-board generation time), for TC the release time. The creation time is a secondary key, the EDDS "storage" or "reception" time: for TM roughly when the packet was received and stored, for TC its (estimated) execution time.41 The Filing Key is the SPID.42

    The field list is the Solar Orbiter DDID's simplified version of the SCOS-2000 Packet Management ADD; for Solar Orbiter the S/C ID and mission ID are 650, context and domain 0, and the header version 5.41 A TM packet adds a 16-octet header (validity, TPSD, route ID with data unit type and qualifier, APID, source sequence count, PUS type and subtype).42 The full field semantics are on EDDS request and data formats.

    Inference: header sizes

    The fields above add up to 60 octets and the TM header to 16, i.e. 76 octets, which is the SCOS-2000 TM packet header length that the import ICD gives for header version 4 (64 octets for versions 0 to 3).414256 Solar Orbiter's version 5 therefore appears to keep the version 4 size; no source states it.

    The DB release and DB issue fields record the MIB version used when the packet was archived, from VDF_RELEASE and VDF_ISSUE of the vdf table.41 In the public releases these are 10720/651 (MIB of 2020-04-16, comment "20200416-CSW3.0.3p1_MAS6.51") and 25925/733 (2025-09-16, "20250916-CSW3.1.2_MAS7.33").7677 The Stream ID separates data streams: for Solar Orbiter 1000 to 1003 are VC 0 real-time non-science, VC 1 playback non-science, VC 2 science and VC 3 file transfer online, 2000 to 2003 the offline equivalents, stream 1 for TC, 1000 and 1001 for events, and 65535 for internal packets such as superseded time correlation coefficients.41

    TPCF_SIZE and the archive

    The import ICD keeps a field TPCF_SIZE in tpcf solely for mission tools that generate "History Files configuration files", recommending the full SCOS-2000 packet size (header plus source packet) for fixed packets and 0 for variable ones.56 Solar Orbiter fills it with source packet sizes, for example 14 octets for the time report.76

    Access paths¶

    EDDS reaches the PARC in two ways:10142719

    Path Interface Capabilities and limits
    PARC Manager CORBA (method viewSelectMode of the view operation interface); registered in the CORBA name server, hard-coded as "PAMASviews" up to SCOS 5.4 Batch only. Queries by SPID only, not APID, and no filtering by type or subtype; EDDS maps APID, type, subtype and PI1/PI2 to SPIDs using the mission's pid.dat and filters the rest itself. Supports the "PARC raw" request types and the TM gap report
    Data Provision Services CORBA HFC.StreamingService: retrieveRange for history (markers, a batch per call, 60 s processing limit), subscribe for live data; Command, Packet, Event and Out of Limits provision services Data already decoded, decoupling EDDS from packet details; parameter information for TM; the only path for streaming

    Batch retrieval selects by the PARC primary and secondary keys and the data stream, retrieves in fixed-size arrays, then filters, formats, compresses and encrypts.14 The EDDS user manual lists SMON, the SCOS-2000 monitoring service, as a third route to PARC data; SMON requests return parameter values with out-of-limit information rather than packets.19 The TM gap report needs SCOS 5.4.18 or 5.5.2 or later.19 The "new PARC API" introduced dataspaces: a request may name the dataspace to read, the first in the list being the PARC's current one.92027

    Inference

    A dataspace looks like a separate partition of the archive (for example for tests, simulations or reprocessing) within one mission and domain. A later issue of the EDDS SDD has an appendix "Dataspace and Datapartition in EGS-CC", requiring every EDDS request to EGS-CC to name a dataspace and a datapartition, so the concept carried over to EGS-CC. None of the available sources defines a PARC dataspace.92415

    RAPID: mirroring the packet archive¶

    RAPID files are binary files of SCOS-2000 packets produced by the MCS packet archive process. They were designed for mirroring packet archives across a firewall (Solar Orbiter also uses them to keep the prime and backup MCS in step), and they are the nominal way the Solar Orbiter science ground segment (SGS) receives all packet data.4850

    • Three files are open at any time, for TM (including time packets and coefficient packets), TC and EV. Each is closed after a configurable time (50 s for Solar Orbiter) and then pushed by the Generic File Transfer System (GFTS)33 across the operational LAN and corporate firewalls, up to 5 transfers in parallel to clear a backlog, so files may arrive out of order; two weeks of RAPID files are kept for recovery.485035
    • Packets appear in the order the MCS received them, so re-dumped or re-called data arrive out of generation order, and updated TC packets reappear in full.48
    • Names are PARC_<Type>_<FirstPacketTime>__<LastPacketTime>, with times in YYYY-MM-DDTHH:MM:SS.mmmmmm: reception time for TM, last update time for TC, MCS creation time for EV; for example PARC_TM_2019-04-04T12:30:00.000000__2019-04-04T12:32:50.000000.51
    • A C++ library for reading RAPID files can be delivered to the SGS.51

    A RAPID file is a sequence of records, each preceded by a 32-bit length. A record has a fixed part and a variable part:52

    Field Octets Meaning
    ID 8 Version of the record structure, value 1
    ST, ET 8 + 8 Time range of packets to delete; present but not used
    AT 8 Action time: MCS time of the insert or update in the original archive, 64-bit microseconds since 1970
    DS 8 Size of the PACKET field
    TYPE 4 0 insert (any packet), 1 update (a TC packet to overwrite), 2 delete (should not occur; ignore)
    SM 4 Sync marker 0x1ACFFC1D
    NS 4 Not used
    FS 4 Size of FIL, 0 for Solar Orbiter
    FIL 0 Filter information for deletions, absent
    PACKET DS The SCOS-2000 packet with its headers

    Inference

    The sync marker 0x1ACFFC1D is the same 32-bit pattern as the CCSDS attached sync marker of telemetry frames, presumably chosen to make record boundaries easy to verify.5271 The reuse is not commented on in the source.

    Which ICD defines RAPID?

    The Solar Orbiter DDID references a "RAPID ICD", EGOS-MCS-S2K-ICD-1005; the EDDS glossary lists the same number as the "System management SCOS-2000 - SFM service ICD", issue 5 of 2008.322 One of the two references is wrong, or the number was reused; neither document is public.

    DARC: the parameter archive¶

    What it holds¶

    The DARC stores telemetry parameter samples. EDDS documents several properties:

    • Engineering values. Up to DARC 2.2.2 only engineering values are kept, so the TDRS-compatible spreadsheet output cannot show raw values; from 2.3.0 the raw value and its type, the parent packet (the SPID for SCOS-2000) and the parent packet's generation time are also returned, and time stamps have microsecond rather than millisecond resolution.172126
    • No limit status, no statistics. The DARC does not provide the out-of-limit status of samples, and it does not compute statistics: EDDS reads all the data to compute them.17
    • Recording list. Not every parameter is archived. The MIB field PCF_DARC adds a parameter to the recording list (1) or leaves the DARC configuration unchanged (0, the default); it is not imported by SCOS-2000, only read by the DARC.57
    • Consolidation and dataspaces. The DARC has a "last consolidation time" per dataspace, which EDDS shows and lets users take as the end of a parameter request.92420
    • Live stream. Live parameter samples are published on an ActiveMQ topic (an example name in the CIG is esa.egos.darc.realtimeParams); EDDS re-encodes them in Google Protocol Buffers.1326

    In the Solar Orbiter MIB, 49,330 of 126,745 monitoring parameters (39 %) have PCF_DARC = 1; in the 2020 release, 43,456 of 102,104 (43 %).7677 All other parameters leave the field empty.

    Inference

    With 0 meaning "no change", an empty PCF_DARC presumably leaves those parameters out of the recording list unless the DARC is configured otherwise; their values remain available from the packets in the PARC. The ICD does not say what the DARC does with parameters never flagged.57

    Access¶

    EDDS uses the DARC Java API (IDataRetrieval, with getParamSamples and getStaticParameterList) for five request types: parameters, statistics, definitions, preview and report. When all parameters are requested with no quota restriction and no TDRS formatting, EDDS retrieves everything in one DARC sample request; otherwise it requests each parameter and merges.18 The CIG configures it with a database host, schema, user, dataspace and the edds.darc.post.2.3.0 switch.26 SCOS-2000's own monitoring service SMON is an alternative parameter source that also returns out-of-limit information.19

    FARC: the file archive¶

    What it holds¶

    Content Source
    Auxiliary files from flight dynamics, mission planning and ground station scheduling For Solar Orbiter: MIB, attitude (ATT, AttitudePTEL), events (EVT), orbit (Orbit, short and long term), one-way light time (OWLT), station visibility and link budget (VISTA), HGA blockage (HGAB), short-term solar aspect (SolarAspectST), CRF files (CRFG), user events (UEVT), station scheduling events (EVFM)46

    Command sequence and display definitions (XML) Since SCOS-2000 R5.058

    The EDDS view of the FARC is a catalogue (file type, creation time, release and issue per file), files retrieved by name, type or time, and subscriptions.19 A domain value of −1 denotes the FARC's "No Domain".9 With the "Consolidated FARC" version 2.0i5, EDDS must also be configured with the zone of the FARC server.28 The client interface is the FARC Client Services API (EGOS-GEN-FARC-ICD-1001, issue 4.5 of 2012), not public; EDDS isolates itself from FARC versions behind an interface jar.2911

    Subscriptions¶

    When a file changes, the FARC server posts a message on a message bus topic; EDDS matches it against its subscription table and either delivers the new version by a file request or sends an e-mail, and drops subscriptions to deleted files.12 Solar Orbiter users can subscribe to any auxiliary file received by the file archive, whether it comes from an external or an internal source.34 Streaming makes no sense for files and is not supported.12

    MIB content in the FARC¶

    The FARC holds MIB-derived content in two senses.

    1. Run-time definitions. From SCOS-2000 R5.0, sequence (csf, css, sdf, csp) and display (dpf, gpf, spf and related) definitions in the ASCII MIB are converted on request into XML files and imported into the FARC, not into the POST run-time database; command sources and the TM desktop load them from there. Sequences and displays are thus imported independently of a new TM/TC database, and incrementally: only the definitions in the imported files change, the others stay available.585960 The XML formats are in the TC Sequences definitions ICD (ICD-0051) and the TM Displays and Printout definitions ICD (ICD-5001), both not public.61 See Command sequences and Display definitions.
    2. MIB releases as files. Solar Orbiter's FARC holds the mission database file as auxiliary file type MIB, available through EDDS; Rosetta and Mars Express distributed it as file type MIB_, tarred, to Flight Dynamics.4668 The public MIB releases on this wiki (2020, 2025) are such files.

    Beyond the MCS archives¶

    A 2020 ESOC presentation describes ARES (Analysis and Reporting System), an off-line analysis system evolved from MUST and built on the EGOS User Desktop, mainly for housekeeping data in engineering format. Its server reads EDDS response files fed from the DARC and PARC on the operational LAN; a multi-mission shared store aims at keeping all data rather than a subset (Gaia alone receives around 150 million unique housekeeping samples a day), ARES itself being described as a Hadoop database cluster, and the PyARES library brings Spark-based processing to the data.72737475

    Questions the public sources leave open: the storage technology of the PARC and the FARC (the CIG names only a DARC "database" with host and schema), retention and consolidation policies, how the DARC is fed, what a dataspace is exactly, and how PARC dataspaces relate to DARC ones.26 HARC, a further source named next to the PARC and DARC in the current EDDS documents, is not an SCOS-2000 archive: the EDDS SDD describes its HARC data provider as retrieving data from the EGOS-CC HBase archive.3016
