    EDDS request and data formats¶

    This page is the format reference for the EGOS Data Dissemination System (EDDS). It covers what a client sends (XML requests), what it gets back (acknowledgements, identifiers, response files) and the binary records inside those files. The generic definitions come from the EDDS External User Interface Control Document (EUICD), mainly issue 24.0 of January 2025. That document says its XML schema files are the primary reference and the text follows them.1 The mission layer comes from the Solar Orbiter Data Delivery Interface Control Document (DDID) SOL-ESC-IF-05011 issue 1.2. The DDID explains which archive answers each request, which SCOS-2000 headers wrap each packet, and how RAPID files carry the whole packet archive to the Science Ground Segment.2

    Three real byte sequences are decoded below. One is a raw PARC telemetry packet shown in an ESOC presentation, and two are the GDDS binary examples printed in the EUICD. Every decoding step is marked as this wiki's own work.

    Overview: one request, many shapes of answer¶

    flowchart LR
  R["RequestMessagePart (XML)<br/>ContextPart + BatchRequest"] --> V{"schema and<br/>privilege checks"}
  V --> P["data provider<br/>PARC / DARC / FARC / SMON / ..."]
  P --> F["formatter<br/>EDDS raw, GDDS binary, SFDU,<br/>Protocol Buffers, XML, ASCII, TDRS"]
  F --> X["optional XSLT transform"]
  X --> S["split into chunks<br/>(splittable formats)"]

    The batch request¶

    Request types¶

    Every request names one data-access type. The enumeration DataAccessDataElement (EUICD Appendix D.24) is also the "subtype" field of the request ID.67

    Data source Request types
    DARC Param, ParamStatistics, ParamDefinition, ParamPreview
    SMON SmonParam
    PARC PktTm, PktTc, PktEv, PktTmRaw, PktTcRaw, PktEvRaw, PktTmStatistics, PktTcStatistics, PktEvStatistics, PktTmReport, PktTcReport, PktTmGapReport, EventRecordReport, OolRecordReport
    FARC ArchiveCatalogue, ArchiveFile, ArchiveSubscription
    File system FileSystemFileCatalogue, FileSystemFolderCatalogue, FileSystemFile, FileSystemSubscription
    EDDS EddsUsageReport
    Streams ParamStream, PktTmStream, PktTcStream, PktEvStream, OolStream
    EGS-CC EgsccActivityReport, EgsccLogMessageReport (and the Egscc... packet and parameter types of Table 12)

    The DataSource enumeration names the back ends: FARC, DARC, PARC, EDDS, SMON, FileSystem and DataProvisionService.8 The types that return XML are paired with response types. Param returns ParamResponse, PktTmRaw returns PktRawResponse, PktTcReport returns PktTcReportResponse, ArchiveCatalogue returns CatalogueResponse, and so on. The packet types PktTm, PktTc and PktEv and the file types return binary files.9

    Element tree¶

    The top element of a batch request is RequestMessagePart in the namespace http://edds.egos.esa/model. The tree below follows the "children" lists of the schema appendices.10111213

    flowchart TD
  RMP["RequestMessagePart"] --> CP["ContextPart<br/>MissionId, DomainId, PrivacyTag"]
  RMP --> BR["BatchRequest"]
  BR --> C["Comment"]
  BR --> SCH["Schedule<br/>ScheduleOnce, ScheduleRepeating<br/>or ScheduleWithExpiry"]
  BR --> U["User<br/>UserName, Role"]
  BR --> DR["DataRequest<br/>(exactly one request type)"]
  BR --> AD["AckDelivery<br/>EmailDelivery"]
  DR --> PT["PktTm (example)"]
  PT --> RPP["RequestPostProcessing<br/>DataCompression, DataEncrypting"]
  PT --> DEL["Delivery<br/>ServerDelivery or FileServerDelivery"]
  PT --> TF["TmPacketFilter"]
  PT --> PF["PacketFormat"]
  TF --> PNL["PacketNameList"]
  TF --> TR["TimeRange"]
  TF --> TFI["TimeFiltering"]
  TF --> TFL["TmFilterList → PktTmFilterKeyword"]
  TF --> DS["Dataspace, BriefReportFlag, IncludeRawData"]

    The common building blocks are listed below.

    Element Content Values and rules
    ContextPart MissionId, DomainId, PrivacyTag PrivacyTag is PRIVATE, ROLE, MISSION or PUBLIC1415
    User UserName, Role The role picks the privileges and the quota sets16
    ScheduleOnce Immediate or Once (AbsoluteTime, AbsoluteDOYTime or RelativeTime) Relative times use the XSD duration type17
    ScheduleRepeating RepeatingSchedule: StartTime, Repetition (CronExpression or Step), EndTime (FinalDate, FinalDOYDate, Delta or NumberOfRepetition) The Archiver creates one request, and one job ID, per execution1718
    ScheduleWithExpiry As ScheduleOnce plus RequestExpiryDate – 17
    RequestPostProcessing DataCompression, DataEncrypting ZIP, TAR, TARGZ, NONE; NONE, AES (implementation mission-specific)19
    ServerDelivery FileName, NamePrefixSuffix, TimeFormat, CustomTimeFormat TimeFormat is CCSDS, DOY or CUSTOM. File names may not contain a slash, backslash, backtick, question mark, angle bracket, vertical bar, colon, tab or line break.20
    FileServerDelivery TargetLocations (Target, FileServerUsername, FileServerPassword, TargetFolder), naming fields, KeepFileAfterDelivery Pushes the result to the user's (S)FTP server20
    AckDelivery EmailDelivery (EmailList, Default) Acknowledgement by e-mail20
    TimeRange StartTime, StartDOYTime, RelativeStartTime, EndTime, EndDOYTime, Duration, ConsolidationTime Used by all packet and parameter filters21
    TimeFiltering GENERATION_TIME or STORAGE_TIME On-board time (primary key) or archive reception time (secondary key)22

    Filters¶

    Packet filters combine a time range with keyword lists. The keywords below are the children of the filter-keyword types.23

    Filter Keywords
    PktTmFilterKeyword Apid, Pid, Category, GenerationTime, GenerationDOYTime, ReceptionTime, ReceptionDOYTime, TimeQuality, VirtualChannel, DataStream, DataBaseVersion, GroundStation, SourceSequenceCounter, SpacecraftId, MaximumDataVolume
    PktTcFilterKeyword ExecutionTime, ReleaseTime (and DOY forms), Type, SubType, Name, DataStream, DataBaseVersion, SourceSequenceCounter, SequenceName, CommandSource, the four acknowledgement flags, CommandSubSystem, CommandSubschedule, MaximumDataVolume, GroundStationId, Description, Apid, UplinkMode, OverallVerificationStatus, and one status keyword per verification stage (release, ground station, uplink, on-board reception, acceptance, execution start, steps 1 and 2, completion; real-time and playback)
    PktEvFilterKeyword GenerationTime, GenerationDOYTime, Id, MessageText, Category, Severity, ApplicationId, ApplicationName, Workstation, MaximumDataVolume
    ParamTmFilter DarcDataSpace, ParamNameList, TimeRange, TimeFiltering, DeliveryRange, OnChange, ParamFilterList, SuperCommutationFlag, MaxDecimalPlaces, the TDRS options TdrsUseDOY, TdrsStatsOnly and TdrsDataOnly, and RepresentationSelection (ENG, RAW or ALL)

    Packet names (APID, PI1, PI2, SPID, type, subtype) are written in the SpidsSpecifier syntax: a comma-separated list of values or numeric ranges such as 100-200.24 The CommandSource enumeration lists the SCOS-2000 command sources: MANUAL_STACK, AUTO_STACK, EXT_SOURCE, TC_SPACON, OBQM_DISP, SMF_SOURCE, NAVPRS_STACK, MKMF_STACK, PKMF_STACK and SKMF_STACK. UplinkMode is A (AD transmission mode) or B (BD).2526 These AD and BD modes are the COP-1 service types.

    The APID filter is not native to the PARC Manager, which can only query by SPID. The EDDS expands APID, type, subtype, PI1 and PI2 filters into a SPID list using the mission's pid.dat.27 The SRS asks that the APID filter cover "all fields of the APID (e.g. PID and PCAT)".28 This refers to the split of the 11-bit APID into a 7-bit process ID and a 4-bit packet category, as Solar Orbiter's packet ICD defines it, for example.29 The EUICD's TM header fields "PID" and "Category" are both "calculated from the APID".51

    An illustrative request¶

    The EUICD contains no complete XML request instance. Its Appendix O gives Java code that builds a DARC parameter request object by object.30 The listing below is that object tree written out as XML by this wiki. It is illustrative: the parameter names come from the Solar Orbiter MIB, but the element order, the namespace prefix and the mandatory-element rules have not been checked against the XSD.

    <RequestMessagePart xmlns="http://edds.egos.esa/model">
  <ContextPart>
    <MissionId>SOLO</MissionId>            <!-- mission name as configured in EDDS -->
    <DomainId>0</DomainId>
    <PrivacyTag>PRIVATE</PrivacyTag>
  </ContextPart>
  <BatchRequest>
    <Comment>IMU temperature, one day</Comment>
    <Schedule><Immediate/></Schedule>      <!-- ScheduleOnce/Immediate -->
    <User><UserName>investigator1</UserName><Role>PI_ROLE</Role></User>
    <DataRequest>
      <Param>
        <RequestPostProcessing>
          <DataCompression>TARGZ</DataCompression>
          <DataEncrypting>NONE</DataEncrypting>
        </RequestPostProcessing>
        <Delivery><ServerDelivery><FileName>imu_temp</FileName></ServerDelivery></Delivery>
        <ParamTmFilter>
          <DarcDataSpace>DEFAULT</DarcDataSpace>
          <ParamNameList>
            <ParamNameListElement>NMUD1113</ParamNameListElement>
          </ParamNameList>
          <TimeRange>
            <StartTime>2025-09-01T00:00:00Z</StartTime>
            <EndTime>2025-09-02T00:00:00Z</EndTime>
          </TimeRange>
          <TimeFiltering>GENERATION_TIME</TimeFiltering>
          <DeliveryRange><None/></DeliveryRange>
        </ParamTmFilter>
        <ParamTmFormat><Format>DARC_Binary</Format></ParamTmFormat>
        <DataSource>DARC</DataSource>
      </Param>
    </DataRequest>
    <AckDelivery><EmailDelivery><Default/></EmailDelivery></AckDelivery>
  </BatchRequest>
</RequestMessagePart>

    NMUD1113 is the "IMU11 SIA temperature" parameter. The Param format choices are XML, TDRS, Binary (EGS-CC binary) and DARC_Binary.31 For speed, the EUICD's own example code recommends binary output.30

    Stream requests¶

    A stream request has the same shape. StreamRequestMessagePart holds a ContextPart and a StreamRequest. The StreamRequest holds Comment, Schedule, User and a StreamDataRequest, which contains one of ParamStream, PktTmStream, PktTcStream, PktEvStream or OolStream. The packet and OOL streams each have a DataSource and a Filter; ParamStream has a ParamNameList and a ParamTmStreamFilter.32

    GDDS requests through the Request Submitter¶

    The Request Submitter accepts requests in the older GDDS XML format. It first validates a file against the EDDS schema, then against the GDDS schema. GDDS files are converted with the XSLT GDDS2EDDS.xsl and submitted under the Submitter's own user account.3334 The mapping has limits:34

    GDDS element EDDS mapping
    schedule/firstStartTime, schedule/interval Execution time of the first request; days between requests. GDDS has no end date, so 10 requests are always created.
    general/comment Request comment. Extra lines Mission: and Domain: select a mission and domain other than the default.
    general/userInfo with destInfo/FTP Credentials, file name and directory for file-server delivery; otherwise EDDS server delivery
    general/formatInfo/compression EDDS compression option (SFDUrequired and missionFormat are not used)
    item with dataType TLM TM packet request. dataSource is the APID; the filter needs a lower and an upper SourcePktsGenTime bound.
    item with dataType CMH, dataSource CMDH Raw TC packets (bounds on ExecutionTime)
    item with dataType CMH, dataSource CMDPB / CMDPF TC brief or full report
    item with dataType AUX Archive file (Name, and Release plus Issue mapped to a version)

    GDDS filters are recursive binary trees of bin and leaf nodes with operations such as OP_AND, OP_GTE and OP_LTE. The EDDS accepts them only in a simple form, with no OR inside an AND. If such an "illegal" expression occurs, the whole subtree is ignored.34

    Identifiers and acknowledgements¶

    Request and response IDs¶

    Request IDs are created by the Archiver when the request is stored.7

    Form Used for Example (illustrative)
    [RequestType].[Username].[yyyy.DDD.hh.mm.ss.SSS] AccountRequest (LDAP changes) AccountRequest.investigator1.2025.255.10.00.00.000
    [RequestType].[Subtype].[Mission].[Domain].[yyyy.DDD.hh.mm.ss.SSS].[RandomStr] Everything else BatchRequest.Param.SOLO.0.2025.255.10.00.00.000.Ab3x

    RequestType is one of BatchRequest, StreamRequest, Cancel, DeleteData, DeleteRequest or AccountRequest. The time is the creation time in day-of-year form, GMT. RandomStr is four random characters. Response files are named <request id without random part>@<creation time>.<counter>.<extension>, with the counter starting at 1 for split responses.7 The Delivery Manager recovers the request ID from the file name to look up the delivery method.35 Stream Client recordings use TmRecording_, TcRecording_, OolRecording_, EvRecording_ or ParamRecording_, followed by day, month, year, hour, minute, second and millisecond, separated by underscores.36

    The AcknowledgementPart¶

    There is exactly one acknowledgement per request. It is created by the Archiver and updated at every stage.37 Its children are:38

    Group Elements
    Identity ContextPart, RequestId, User, Priority
    Status State, Retries, Reason (for retries), Error, ProblemRecords (records that could not be retrieved)
    Times (each also in DOY form) ReportCreationDate, SubmissionTime, ScheduledTime, StartTime, CompletionTime, ExpiryTime
    Progress Percentage, RetrievedSamples, FilteredSamples
    Output ResponseFiles (each a ResponseFileEntry: FileName, Size, Status, Error, Checksum, a CRC32 of the completed file), Delivery, AckDelivery
    Resume support FilterTimeWindow (the time-range filter converted to an absolute window), LastSampleReference (the last record stored, for resumable requests)

    State takes the values of the request life cycle: SUBMITTED, QUEUED, CANCELED, SUSPENDED, COMPLETED_NO_RESULTS, SERVER_COMPLETED, DELIVERED, DELIVERED_RESP_DELETED, DELIVERED_PARTIAL_RESULTS, and the errors ERROR_LOCALLY_DELIVERED, ERROR_ACCESS_DENIED, ERROR_INVALID_REQUEST, ERROR_LIMIT_EXCEEDED, ERROR_SERVER_NOT_AVAILABLE, ERROR_DELIVERY and ERROR_UNKNOWN.39 The SUM adds ACTIVE; the state diagram is on the EDDS page.40

    Response packaging¶

    • Compression. ZIP archives compressed files. TAR bundles files without compression (USTAR format). TARGZ compresses the tar file with gzip.4142
    • Encryption. AES, enabled per mission. The SDD's delivery manager notes that a key file can be one of the response files.1935
    • XFDU. An optional post-processing step wraps the response in a CCSDS XML Formatted Data Unit (CCSDS 661.0-B-1). The SDD's XFDU formatter adds each data file in Base64, with metadata and a checksum that the XFDU library itself does not compute.4344 The SRS asks that each EDDS data-object ID map one-to-one to an XFDU data-object ID, and that a CCSDS Submission Information Package layer could later be added on top.45
    • XML transforms. Every XML-capable request can be passed through a mission stylesheet. getTransformations() lists the stylesheets available.46
    • ASCII. Similar to the XML without markup. The TC report imitates the SCOS-2000 Command History display, with one column per check and verification stage. Examples are S and D (static and dynamic PTV checks), C (CEV), IL (interlock), R, G, T, O and A (release, ground station, uplink, on-board reception, acceptance), and SS, 1122 and CC (execution start, steps and completion). Stage values include F, U, X, P, T, S, I, A, C, V, N and E.47 See command verification for the stages.
    • TDRS spreadsheet. Tab-separated parameter values in the format of the TDRS ICD, produced by Param.xsl or by a faster native formatter. The TDRS retrieval ID, execution ID and expiration day are filled with dummy values, except that the native formatter puts the EDDS request ID in the retrieval ID.48

    EDDS raw binary¶

    The "EDDS raw" (EDDS binary) format is self-describing. A mission chooses which header fields accompany each packet.49

    Part Occurs
    EDDS raw header once
    EDDS header fields (1), data element (1) per packet
    …
    EDDS header fields (N), data element (N)

    The EDDS raw header is N (1 octet), the number of header fields defined, followed by one octet per field giving its size. For a string field, the size octet only says whether the field is included, because string lengths are known only at run time. Strings are written as a length followed by the characters, both in hexadecimal.5051

    The sequence count lets a client detect missing elements. The TC and EV elements have the same three parts. For them, the EUICD calls the count and length fields "Unsigned Integer" without giving their sizes.51

    EDDS raw is hexadecimal text

    Despite the word "binary", the EUICD speaks of data "stored in a raw (ASCII hexadecimal) file".49 The Solar Orbiter DDID and the ESOC presentation describe EDDS raw as an ASCII string of the hexadecimal packet data, including the EDDS raw header.5455

    GDDS binary¶

    GDDS_BINARY reproduces the response format of the older GDDS FTP service.56 Unlike EDDS raw, it is real binary: a fixed header followed by the source packet without any SCOS-2000 header.54 The EUICD explains it by analogy with EDDS raw. The GDDS TM header fields correspond to EDDS fields 8, 10, 12, 13, 17 and 18, and the TC header fields to EDDS fields 9, 10, 23 to 29 and 13. Its examples show the header fields followed directly by the packet.57

    The EUICD says the 8-octet times hold seconds since 1970 in the first four octets and microseconds in the last four.57 The Solar Orbiter DDID adds that the seconds count ignores leap seconds.54

    Worked example: the EUICD's two GDDS telecommands¶

    The EUICD prints two TC records (real bytes from the source).57 This wiki decodes them below. The interpretation of the PUS fields uses the PUS-A TC layout of ECSS-E-70-41A.5859

    Uplink time 4FB6 5AD2 000E 9A94 1337350866 s and 957076 µs = 2012-05-18T14:21:06.957076Z

    The 13-octet packet starts with a Space Packet primary header. 0x18BC gives version 0, type 1 (TC), secondary header flag 1 and APID 0x0BC = 188. 0xC1F1 gives sequence flags 0b11 (stand-alone) and sequence count 497. The length field 0x0006 means a 7-octet data field, and 6 + 7 = 13 agrees with the GDDS length field. The data field header 0x19 03 06 reads as: CCSDS secondary header flag 0, PUS version 1, ack 0b1001 (acceptance and completion), service 3, subtype 6.58

    Record 2 is a 33-octet ZMT11004 packet (18FC C012 001A 190B 0400 0007 …): APID 252, sequence count 18, length field 26 (27-octet data field), data field header 0x19 0B 04, which is service 11, subtype 4. Its uplink and execution times are both 4FB6 5AD2 000E 9A95, one microsecond after record 1's uplink time.57

    Inference

    Record 2 looks like a PUS-A TC(11,4) "Insert Telecommands in Command Schedule" request.59 It would load record 1's command into the on-board schedule. The six octets before the embedded packet would then be its release time: 0x4FB65BE4 equals record 1's execution time in seconds, and 0x6E56/65536 = 0.431 s equals record 1's 431000 µs. The first 00 after the subtype may be an optional PUS-A source ID, and the final B539 probably the packet error control, but neither they nor the octets 00 07 before the time are explained in the available sources. Record 1's own data field (19 03 06 00 00 84 C0) would then be header, source ID, one octet of application data and a 2-octet error control field.

    Worked example: the GDDS TM records¶

    The two TM records in the same EUICD section have generation times 4E94 46BE A7B8 D000 and 4E94 46BE 6334 3000, packet length 0x50 (80 octets), and zero ground station, virtual channel, SLE service and time quality.57 0x4E9446BE is 2011-10-11T13:38:06Z.

    Inference

    The second words (0xA7B8D000 = 2813906944 and 0x63343000 = 1664364544) are larger than 106, so they cannot be microseconds as the EUICD states. The 80-octet payloads also do not decode as CCSDS packets: read that way, their length field would be 0xFFFF. The first payload ends in the ASCII text UPDATE %. Read instead as the 16-octet SCOS-2000 TM-specific header in little-endian order (see below), the first 16 octets of each payload give validity 0, TPSD -1, route ID 0, APID 200, SSC 1 (2 in the second record) and type and subtype 200, which suggests an internal SCOS-2000 packet body rather than a spacecraft source packet. This is speculation. The TM example is best read as a layout illustration only.

    Protocol Buffers binary¶

    The "Binary" format of most report and parameter types is Google Protocol Buffers. A file starts with an ASCII header line of the form # Key1: Value1; ... ; KeyN: ValueN, with the keys Type and Version. The header line is followed by length-prefixed ("framed") messages, each prefixed by its size as a varint.60 The .proto files ship in the edds-ws-common project. The EDDS uses the Protocol Buffers implementation of the ActiveMQ library, whose output is compatible with Google's implementation.61

    SCOS-2000 packets inside the PARC¶

    "Raw" PARC requests return the packet exactly as the packet archive stores it. That is a SCOS-2000 packet (also called a TDEV packet): a common header, a type-specific header for TM, TC or EV, and the packet data.67 For spacecraft TM, the packet data is the complete, unstripped source packet. Internal MCS "telemetry" (filed on a separate data stream) and occasionally whole frames can also appear. For TC, the packet data holds the MCS command details and the uplinked packet.67 The DDID takes its definitions from the SCOS-2000 Packet Management ADD, which is not in the library.68

    TM-specific header (16 octets)¶

    The TPSD is the MIB's PID_TPSD. It is -1 for fixed-structure packets and the vpd structure number for variable ones.6970 The low octet of the route ID classifies the data unit:69

    Data unit type (high nibble) Qualifier (low nibble)
    0 TM transfer frame 0 good, 1 bad, 2 idle
    1 TM source packet 0 good, 1 bad, 2 idle, 3 unknown, 4 service 9 time packet
    2 internal MCS TM packet 0 CLCW, 1 user-defined constants, 2 status consistency check, 3 dynamic MISC, 4 on-line MIB changes, 5 SPPG, 6 SPID validity, 7 TPKT configuration, 8 external source

    When frames are missing in the middle of a large science packet, the MCS files the partial packet as data unit 1, qualifier 1 (bad). It then files the remaining frames one per SCOS-2000 packet as data unit 0, qualifier 0, until it finds the next packet header. The MCS cannot detect frames missing at the start of the next packet, so the DDID tells users to separate packets by time stamp.71

    TC-specific header (44 octets)¶

    The TC packet data hold the "command details". These are the static MIB information (mnemonic, parameters, verification definitions) and dynamic status, so that the TC history stays readable even after the runtime MIB has changed. The layout is defined in a separate ICD, and the DDID warns that it changes during development.72 It is written by overlaying a C++ object on a 32-bit platform, so fields are 32-bit aligned with padding: an 8-bit field at offset 100 followed by a 32-bit field puts the second at 104.72 For decoding, the EDDS needs an XML description of this structure per mission (TCPacketStructure.xsd).53 The MCS also archives a second TC packet per command, with SPID 200, which holds the PTV/CEV details. External users should ignore it.67 There is no event-specific header: event information goes straight into the packet data.71

    • The multi-octet SCOS-2000 header fields are little-endian in this sample. Only that reading gives a plausible date, microseconds below 106, a Size of 172 and an APID and SSC that match the source packet. The CCSDS source packet itself is big-endian.     • The sample is probably not Solar Orbiter data. S/C ID and mission ID are 816, not
    • In the 2025 Solar Orbiter MIB, SPID 57000 is "SPICE Real Time and FDIR HK Report" on APID 1364, and APID 1524 does not occur in either the April 2020 or the September 2025 release.     RAPID files¶

    The nominal route from the operations ground segment to the Science Ground Segment is not the EDDS. It is a stream of RAPID (Raw Archive Packet Interceptor Dumper) files forwarded by the Generic File Transfer System (GFTS).8384 The MCS writes every SCOS-2000 packet it archives into one of three open RAPID files, one each for TM, TC and EV. It closes them after a configurable time: 50 s on the long-term archive for Solar Orbiter. GFTS then moves them across the OPS LAN firewall to the relay server, and from there to the SGS, with up to 5 parallel transfers to clear a backlog. Two weeks of RAPID files are kept for recovery.8385

    File names follow PARC_<Type>_<FirstPacketTime>__<LastPacketTime>, with times as YYYY-MM-DDTHH:MM:SS.mmmmmm. Type is TM, TC or EV. The times are the reception time for TM, the last update time for TC, and the creation time for events, for example PARC_TM_2019-04-04T12:30:00.000000__2019-04-04T12:32:50.000000.86 A file is a sequence of records, each preceded by a 32-bit length. Each record has a fixed metadata part, then the SCOS-2000 packet.87 ST, ET and AT are 8-octet fields of type "Time". The DDID's §7 defines its time fields as 4-octet seconds since 1970 plus 4-octet microseconds; it does not say whether the RAPID record uses the same encoding.8754

    The action field matters for TCs. A TC packet is rewritten whenever its verification status changes, and the new copy arrives in a later RAPID file with action "update". An ingestion tool must overwrite the earlier copy, identified by its release time. TM and EV packets are never updated, but recalls can store the same packet twice with a new reception time. Packets also arrive in reception order, not generation order.88

    Inference

    The sync marker 0x1ACFFC1D is the same 32-bit value as the CCSDS attached sync marker of TM transfer frames for uncoded, convolutional or Reed-Solomon coded data.92 The DDID gives no reason for the choice.
