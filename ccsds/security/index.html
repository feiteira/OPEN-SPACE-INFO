    Security in CCSDS space links¶

    For most of their history, civil missions sent telecommands, telemetry and science data over radio links that were neither encrypted nor authenticated. CCSDS lists several reasons why this is no longer enough: ground networks are more interconnected, principal investigators control instruments remotely, cheaper hardware makes rogue ground stations possible, and national policies ask for more protection.134 Civil missions used to rely on being unique. Open mission control systems, Internet connectivity and cross support have changed that, so security now has to be part of the system design.4 CCSDS answers with a family of documents. Two informational Green Books explain the concepts and the design choices. Three Recommended Standards (Blue Books) fix the cryptographic algorithms, the data link security protocol and the in-flight procedures that operate it.

    This page covers that family as a whole. The protocol itself, with its Security Header and Trailer, Security Associations and the ApplySecurity and ProcessSecurity functions, is described in depth on Space Data Link Security (SDLS). This page covers the context around it: the threats, the places in the stack where security can sit, why SDLS is designed as it is, which algorithms CCSDS recommends, and how keys and Security Associations are managed and monitored once the spacecraft flies. The page describes the standards. It does not give operational guidance.

    Security concepts and threats¶

    What information security covers¶

    The application report names six key elements of information security for a data communications system.6

    Element Meaning in CCSDS 350.0-G-3
    Access control Limiting system access to specified individuals, groups or processes acting for them
    Authentication Assurance that the claimed identity of the source of information is not forged
    Availability Assurance that the system will be available for use
    Confidentiality Protection against unauthorized disclosure of information
    Integrity Protection against unauthorized modification of data
    Accountability Listed, but not defined in the report

    Three kinds of thing may need protection in a space mission data system: the information it holds, its services (communications and data processing), and its resources (ground equipment and spacecraft). Security is achieved by placing one or more security services at specific points in the system.6

    Security policy and threat assessment¶

    The first task is to assess the threats. This is normally part of a System Security Policy (SSP), a formal document that describes the system, its top-level security objectives and the information-security and availability threats against it. The SSP can also give the security standards and evaluation requirements, the rules for access to security-critical systems such as a certificate authority, and, if encryption is used, how keys are distributed and managed.7

    The threat assessment looks at the vulnerabilities of the system. For each threat it then estimates the likelihood, the consequences and the cost of realization. A threat matters only if the system is vulnerable to it. Countermeasures are selected per threat, usually through a cost-benefit analysis. What remains is residual risk, which system management must accept before the system goes into production.7

    Kinds of threat¶

    A threat is any circumstance or event that could harm the system by destroying, disclosing or modifying data, or by denying service. It remains a potential violation until it is shown to be likely to cause harm. It is then reclassified as a vulnerability.8 The report lists five threats to a space mission data system:8

    1. unauthorized destruction of information or resources (spacecraft or ground systems);
    2. unauthorized corruption or modification of information;
    3. theft or loss of information or resources;
    4. disclosure of information to unauthorized entities;
    5. interruption of services.

    Threats are accidental (malfunctions, operational errors) or intentional (from casual examination to sophisticated attacks). They are also passive or active. A passive threat leaves the information and the system unchanged. It mainly concerns confidentiality, the only property that can be compromised without leaving a trace. An active threat modifies information or the state of the space or ground segment, so it attacks integrity or availability.8

    Mission security classes¶

    The report sorts missions into three classes as a guide, not a rule. A real mission may not fit any of them. The classes differ in which services they need and in how much assurance they need that those services work. High-security missions, for example, may need government-approved high-grade algorithms.11

    Class Typical missions Telecommand Telemetry Ground data system
    High Government and military; life-critical crewed missions; some commercial telecommunications missions12 All TC: confidentiality, authentication, access controls, data integrity including anti-replay, availability All TM: confidentiality, data integrity, possibly authentication and access control, availability All data: confidentiality, authentication, data integrity, availability, access controls12
    Moderate Commercial communications, meteorological and remote-sensing missions; satellite navigation (possibly high)13 Authentication, data integrity, possibly confidentiality Some or all TM: confidentiality, data integrity Some or all data: authentication, data integrity, possibly access control and confidentiality13
    Minimal All other missions14 All TC: authentication, data integrity, possibly confidentiality Some TM: confidentiality, data integrity Some data: confidentiality, data integrity, access control14

    High-security missions also need secure access to the spacecraft control system at all times and in all conditions, and protection against detection, interception and exploitation of the data links.12 Even a minimal-security mission is expected to protect its telecommand system against unauthorized access or tampering, whether intentional or not.14

    The approach chosen for a mission depends on five factors: the agency's security policy, the mission security requirements, the operational requirements (including cross support and interoperability), the CCSDS standards in use (TC, TM, AOS, SCPS-TP or Proximity-1), and the capability of the on-board systems.10

    Security mechanisms¶

    Confidentiality and encryption¶

    Encryption provides confidentiality. A key controls the transformation from plaintext to ciphertext and back, and a new key gives different ciphertext for the same plaintext. Security depends on the strength of the algorithm, the key length and the secrecy of the keys. When the algorithm is public, as AES is, the security of the system is designed to rest on handling the keys: their management, distribution, use and destruction.15

    Encryption can be arranged in three ways:15

    Arrangement Who can read the data in transit
    Point-to-point Only the two communicating end points; a link crypto device sits at each end
    Hop-by-hop Each intermediary decrypts and re-encrypts, so trusted gateways see the plaintext
    End-to-end Only the final destination; intermediaries can neither decrypt nor examine the data

    Symmetric and asymmetric keys¶

    In a symmetric system both ends use the same secret key, so a secure key distribution system has to generate, distribute and account for every key. AES is symmetric. In an asymmetric (public-key) system each end has a public key and a private key, and the decryption key cannot in practice be derived from the public one. RSA is the best-known example. In practice it is used in a hybrid scheme: a public-key exchange agrees a session key, and a symmetric algorithm then protects the data. A public key must be securely bound to its owner, normally by a certificate authority that signs it.1716

    Cryptographic systems are analysed under worst-case assumptions. The attacker is assumed to know the algorithm completely, to hold a large amount of ciphertext, and to know the plaintext of some of it. Symmetric keys are therefore the main protection of the information and must be distributed and kept securely.17 The report contrasts the old 56-bit-key DES (64-bit blocks, no longer recommended) with AES (128-bit blocks, 128-, 192- or 256-bit keys).17

    Authentication, integrity, access control and availability¶

    Authentication appends extra information to a message: a digital signature or a message digest. A digital signature, normally made with the sender's private key, proves the origin of the data. A message digest computed over a shared secret also authenticates. Symmetric encryption gives implicit authentication, because the receiver must hold the right key. That protection fails if encrypted data can be captured and replayed without replay protection.18

    Data integrity has two parts. For a single data unit an Integrity Check Value (ICV) is appended. A CRC is a simple ICV and SHA-2 a stronger one. Reed-Solomon and Turbo codes also give some integrity through error detection. To protect the integrity of a stream of data units, a sequence number protects against replay, and time stamps give limited replay protection. The ICV is often keyed, or encrypted, for example with AES CMAC.19

    Access control keeps resources available only to authorized users or processes. It is a barrier in the intruder's path, not a fundamental technique for confidentiality or integrity. The report recommends good password administration, never sending plaintext passwords over unprotected media, and keeping audit trails.20

    Availability is a security concern when an attacker tries to deny access. RF links can be jammed. Jamming the downlink can lose data or, in an emergency, the spacecraft. Jamming the uplink while telemetry still arrives can also lose the spacecraft. Spread spectrum and frequency hopping counter jamming.21

    The report places security at five points of the CCSDS stack. Each has a different scope and a different cost in compatibility.922

    Physical layer: bulk encryption and TRANSEC¶

    Bulk encryption, often called link encryption, encrypts the whole physical-layer data structure on a point-to-point basis. On a TC link this covers the CLTU and also the acquisition and idle sequences. On TM or AOS it covers the whole stream of CADUs, including the synchronization marker and any Reed-Solomon check symbols. It gives the highest possible confidentiality. Other services come only implicitly from the encryption.2324 TRANSEC (transmission security) protects the physical layer against jamming. In direct-sequence spread spectrum the signal is spread so that it looks like noise. In frequency hopping the carrier changes over time, and the receiver must stay synchronized with the transmitter.23

    The price is high. Bulk encryption denies all cross-support services unless keys are pre-placed at the access points, or public-key technology is used to protect content keys. CCSDS link synchronization cannot work, so the crypto devices must provide synchronization. No error detection and correction information is visible in plaintext, which makes CCSDS channel coding meaningless. It also gives no end-to-end security.40 See TC synchronization and channel coding, TM synchronization and channel coding and RF and modulation for the structures concerned.

    Data link layer: SDLS¶

    The data link option is SDLS. It adds authentication, confidentiality or both to the contents of transfer frames. It works in the data link protocol sublayer and leaves the synchronization and channel coding sublayer untouched. It does not apply to Proximity-1.25 Its three classes of service are authentication (integrity, source authentication and anti-replay), encryption of the frame data field (or TC segment), and authenticated encryption, which combines both. Frame headers and the error control field are not encrypted. Security can be applied to selected virtual channels, at the cost of more algorithms and more complex key management.2526

    Protocol Fully protected services Authentication only Not protected
    TC MAP Packet, MAP Access, VC Packet, VC Access Some Primary Header fields COP Management control frames; frames from external sources (VC Frame, MC Frame services)27
    TM VC Packet, VC Access Some Primary Header and auxiliary fields; the VC Frame Secondary Header VC OCF, MC Frame Secondary Header, MC OCF; frames from external sources28
    AOS VC Packet, Bitstream, VC Access Some Primary Header fields VC OCF, Insert service; frames from external sources29

    For Proximity-1 the report suggests applying security to the user data above the I/O sublayer. All Proximity-1 protocol handling then works as normal, in a way the report compares to TLS.30

    Network layer: IPSec¶

    IPSec, from the IETF, protects the payload of IP datagrams end-to-end, including the TCP header. Intermediate systems cannot read the data unless explicitly authorized, so insecure networks can carry sensitive data. IPSec defines a framework and no specific algorithm. Algorithms should come from the CCSDS algorithms standard.31 The ESP structure described in the report has an 8-byte clear header (4-byte SPI and 4-byte sequence number), a variable payload with algorithm-specific data such as an IV, optional padding, a 1-byte pad length, a 1-byte next-header field and an optional variable-length ICV.32 SDLS later borrowed the Security Association concept from IPSec and adapted it to space links (see below).77

    Because the lower-layer headers stay in clear for routing, IPSec does not protect against traffic analysis. Encrypted data can still be intercepted in intermediate networks, but it stays confidential.42

    Packet layer: space packet security¶

    Security can also be applied at the space packet level. The packet data field is encrypted, and a digital signature or ICV is added inside it. The optional secondary header may also be encrypted. The primary header and all lower-layer fields stay in plaintext. The report warns that without an authenticated replay counter in the primary header, packets are open to replay, and that fixing this would need a protocol revision. A mission that secures only some packets can use the APID to tell encrypted packets from plaintext ones.33

    Application layer: TLS, SBSP and access control¶

    At the application layer, security for space-packet users looks much like packet security. TLS lets each application secure itself, independently of the rest of the data system. For DTN, the Streamlined Bundle Security Protocol (SBSP) defines a block confidentiality block (BCB) and a block integrity block (BIB).34 Application-layer security needs no investment in the lower layers, but every application has to implement it, which risks duplicated effort and security flaws. The application layer is also where access control naturally sits, for example with access-rights databases and X.509 credentials.3443

    Combining options¶

    Options can be combined. For example, network-layer security can protect data end-to-end across the ground networks while a lower layer protects the space link against traffic analysis. The report's example architecture shows SDLS between the ground TT&C subsystem and the spacecraft and IPSec end-to-end between the end user and an on-board payload, and also marks TLS.35

    What encryption hides at each layer¶

    Confidentiality has the largest impact on the CCSDS architecture, because it can hide headers that other network and cross-support services need. Authentication and integrity only add a few fields, although those fields can add many bits.36

    Security option ASM and EDAC Frame header Frame data field Packet header Packet data field
    Network layer security Plain Plain Plain Plain Encrypted
    SDLS Plain Plain Encrypted Encrypted Encrypted
    Physical (bulk encryption) Encrypted Encrypted Encrypted Encrypted Encrypted

    Source: CCSDS 350.0-G-3, table 6-1.36

    Emergency commanding¶

    A tumbling or faulty spacecraft is commanded with short emergency commands. These are sent repeatedly in the hope that one arrives in a brief window, and are typically acted on directly by the hardware command decoder. The report poses a dilemma. Unauthenticated emergency commands open a security hole, so a risk analysis must decide whether they are allowed. Even an unauthorized reset can harm a high-availability mission, or one in the middle of a manoeuvre. But authentication makes the command longer, which may defeat the purpose of a short emergency command.37 The SDLS user requirements return to this point (see below).

    Impact on SLE cross support¶

    Comparing and choosing¶

    Option Strength Cost
    Physical (bulk) Highest confidentiality, full traffic-analysis protection Point-to-point only, no cross support, CCSDS sync and coding lost4044
    Data link (SDLS) Compromise: relatively high security while keeping sync and EDAC Protects higher-layer data but not the TC, TM or AOS protocol structures; no traffic-flow protection; hop-by-hop41
    Network (IPSec) End-to-end, transparent to applications No traffic-analysis protection42
    Packet or application Protects only the application data; a fallback for payloads Many separate implementations, risk of flaws43

    The selection guidance in §6.5 says:44

    • Most missions need encryption at one layer only. This keeps the approach simple and the costs and processing load low. Encryption at the network layer or below spares each application its own implementation.
    • Full traffic-analysis protection needs physical-layer encryption, possibly with TRANSEC.
    • High security with some traffic-flow confidentiality that keeps the CCSDS benefits points to data link security. Its protection can be extended into the ground network with low-level SLE services (Return All Frames, Forward CLTU).
    • Per-payload confidentiality on separate virtual channels points to encryption above the frame sublayer, which is the SDLS approach.
    • End-to-end protection points to application-layer or network-layer encryption.
    • Very fine granularity, such as per-application keys or selective fields, needs application-level encryption.
    • High security over RF plus end-to-end protection may need encryption at more than one layer.

    Authentication, integrity and access control have less architectural impact. Their fields can sit at the same layer as encryption to keep one "clean" security layer. Access control is likely to be implemented at the application layer.45

    Agency implementations described by CCSDS¶

    Annex A of the application report describes four missions that added security to CCSDS links.46

    ESA Copernicus Sentinels: telecommand authentication¶

    ESA and industry developed a telecommand authentication system for the Copernicus Sentinel fleet. It was one of the predecessors of SDLS and shares features with it, such as the algorithm of the SDLS telecommand baseline. It has a two-tier key hierarchy. Session (authentication) keys authenticate telecommands and are replenished by Over-The-Air Rekeying (OTAR), similar to the SDLS Extended Procedures. Master keys protect the session keys during OTAR and other critical operations.47

    Authentication happens at the segmentation layer, and security associations are distinguished by MAP. An authentication tail identifies the key in use and carries the current value of the Logical Authentication Counter (LAC) and the MAC. Figure A-1 labels the same field "Logical Authentication Channel (LAC)", split into a LAC Id and a LAC Count. ESA's older TC decoder specification also speaks of Logical Authentication Channels with LAC identifiers and LAC counters.4748231 The LAC increments with every telecommand and defeats the replay of an intercepted command. The MAC covers the whole segment except the MAC field itself, and depends on the key and the LAC. The mission control system generates the tail. The on-board security unit checks it, rejects a failing command and reports the reason to the operator.47

    Between header and tail sits the segment data field, of 1 to 1016 octets or of 1 to 904 octets as the figure gives it. The whole segment is 1 to 1017 octets.48 OTAR uses a custom PUS service at the application layer, addressed directly to the spacecraft security unit. Keys are generated on the ground in a separate, isolated Key Management Facility (KMF) with a state-of-the-art random-number generator.48

    International Space Station, STRV-1c/d and ATV¶

    • ISS. The station uses AOS for both links, with the MPDU and Bitstream services. The uplink is encrypted with Triple DES at the VCA sublayer, so the VCDU data zone is encrypted. A 64-bit Insert Zone carries cryptographic synchronization.49
    • STRV-1c/d. These microsatellites put data link security on both links: confidentiality and authentication on telecommand, confidentiality only on telemetry.49
    • ATV. The Automated Transfer Vehicle encrypted its telecommand packets with Triple DES (ANSI X9.52) and added time authentication. The segment data field held a 2-octet key index, an 8-octet IV unique to each message, and the encrypted packet data. Each packet carried a Time Authentication field that the on-board packet processor compared with on-board time, rejecting the packet when the comparison exceeded a threshold.50

    SDLS concept and rationale (CCSDS 350.5-G-2)¶

    The concept and rationale report explains why SDLS is built the way it is. It gives the architecture, the interaction with the data link protocols, the justification of each design choice, the security analyses, and guidance on choosing parameters.52

    Motivation and target topologies¶

    Before SDLS, a CCSDS mission that needed uplink command authentication or downlink confidentiality had to invent its own solution. SLE already protected the ground leg between control centre and ground station, with identification, authentication and confidentiality, but not the space link. A joint working group of the Space Link and Security areas therefore defined data link security for TM, TC, AOS and USLP without modifying those standards.55

    The target is the simple topology. A mission control centre reaches one spacecraft through a ground station, and SLE extends the data link to the control centre (Topology A). Topology B adds a separate payload downlink. Securing the path end to end is split into two tasks: protecting SLE and the ground network, and protecting the data link between the spacecraft and the mission control system, which is SDLS's job. TRANSEC can be added against denial of service and is compatible with SDLS. Secure cross support with another agency's ground station needs a service level agreement.56

    SDLS and its Extended Procedures work in a fixed master-slave arrangement with no negotiation. Directives always go from a predetermined master (the Initiator) to a predetermined slave (the Recipient). For space-to-space links a hierarchy between satellites has to be set up, together with a key management scheme. This could be keys per link pair, which becomes impractical as the number of pairs grows, or keys shared across a constellation while keeping key-IV uniqueness for AES-GCM. "Forward" and "return" link then replace "telecommand" and "telemetry". For large constellations the report suggests considering security at a higher layer.57

    Key requirements¶

    Section 2.4 of the report picks out the main requirements behind SDLS. The full set is the user requirements document of annex C (see below).59

    • Two operational modes for each logical channel on TC, TM, AOS or USLP: a Clear Mode, in which the SDU is left unchanged but the SDLS fields are present, and a Secure Mode with authentication, encryption or authenticated encryption.
    • Independent secure channels, so that clear and secure channels can share one physical channel.
    • Compatibility with three key management schemes: (1) all session keys preloaded for the whole mission; (2) master keys (key encryption keys, KEKs) and some session keys preloaded, with session keys uploaded encrypted by OTAR; (3) session keys generated on board from master keys and an uploaded non-secret seed. Key management itself is specified in the Extended Procedures.
    • Security function control directives handled either in-band, by the security device right after authentication or decryption, or out-of-band, at application level.
    • At most 32 octets of overhead per transfer frame for the complete protocol.
    • No interference between frame verification by SDLS and frame validation by the data link protocol.

    Why COP control frames and the OCF stay in clear¶

    The rationale for this is one of the most important passages in the report. SDLS must run before the COP at the sending end and after the COP at the receiving end:70

    • COP-1 is a go-back-N protocol, so it retransmits frames. If FOP-1 ran before SDLS at the sender and SDLS before FARM-1 at the receiver, SDLS would reject every retransmission as a replay and block the link.
    • The MAC detects errors far better than the BCH or short LDPC codes. If SDLS ran before FARM-1, it would discard frames with transmission errors. These would be counted as security events, the CLCW would not report them, and FOP-1 would keep retransmitting frames that FARM-1 never sees.
    • With this order the COP control commands (BC frames) and the Frame Sequence Number, which the FOP sets, cannot be authenticated. The OCF is appended by the Master Channel Generation function after SDLS has run, so it cannot be protected either.

    The report accepts the residual risk. An attacker could send false COP directives or OCF contents, but the legitimate operator can always reinitialize the COP, so the denial of service is temporary and not easy to achieve.70 It also warns about mixing frame types. If Type-AD and Type-BD frames share a secured VC, a BD frame accepted after a lost AD frame raises the expected anti-replay number. The AD retransmissions then fail the anti-replay check and are falsely reported as security failures. Mixing AD and BD frames on such a VC while AD frames are pending is therefore not advised.7080

    Compatibility with SLE¶

    SDLS security sits only at the end points, the spacecraft and the mission control centre, so it should be transparent to SLE processing. The full frame header must stay unaltered. The compatibility goals were F-CLTU and F-TCF for TC, and RAF, RCF and Return OCF for TM, AOS and USLP. Ground station equipment may route frames using fields it has not authenticated. That risk is accepted, because the end processor at mission control detects any manipulation.6375

    The threat analysis assumes trust between CCSDS agencies: protecting against an agency that acts maliciously against another is not a goal.     Algorithm agility¶

    SDLS is deliberately algorithm-agnostic, so that it does not have to change when cryptanalysis or brute-force power forces CCSDS to change its recommended algorithms.64 This shapes the fields:

    • Authentication produces a MAC over the SDU and selected header fields. To prove freshness, the data is authenticated together with a time-dependent value. SDLS prefers a counter, the sequence number. Some algorithms need an IV, and block-oriented ones such as GMAC may need padding, so the header can carry both.65
    • Encryption covers only the SDU, for compatibility with SLE and the data link protocols. Most secure modes need an IV. Encryption alone does not protect against manipulation and gives no protection against data substitution. If the plaintext is partly predictable, an attacker may even be able to recover the key. It should be selected only after a threat and risk analysis.66
    • Authenticated encryption follows Encrypt-then-MAC (the other generic compositions are MAC-then-Encrypt and MAC-and-Encrypt). It is the CCSDS-recommended way to obtain both services, and its additional authenticated data (AAD) protects the readable headers.67
    • Separate authentication and encryption algorithms are possible, each with its own key. But SDLS provides only one IV, one sequence counter and one padding field, and the 16-bit SPI limits how key changes can be signalled. CCSDS gives no pairing recommendations, so users need expert advice.68

    Design of the header and trailer fields¶

    Field Rationale in 350.5-G-2
    Security Parameter Index (16 bits) Mandatory. Up to 65,534 SAs per Master Channel, because 0 and 65,535 are reserved. The receiver uses it to find the SA and so the presence and length of the optional fields.83
    Initialization Vector (managed) Gives freedom of algorithm. Some IVs must be unique per key, others random. With 128-bit-block algorithms the IV is at most 128 bits, and shorter constructs that partly regenerate the IV at the receiver save overhead at the expense of robustness. Mismanaging the IV can make the security useless.84
    Sequence Number (managed) Used with authentication. It may be part of a longer managed counter. Sending it lets the receiver check the MAC and then the counter window as two separate tests, instead of trying every MAC in the window. With GCM-like counters the IV doubles as the transmitted sequence number and the field is omitted.85
    Pad Length (1 octet when present) Gives the number of fill bits, 0 to 127. Recommended algorithms need no padding, but the field keeps SDLS algorithm-independent. The report cites ISO Padding Method 2 (a "1" then "0"s, not transmitted), and warns that other padding schemes need careful assessment.86
    MAC (trailer) Present with authentication or authenticated encryption. It covers the SDU, selected header fields, any fields between the header and the Security Header, and the Security Header itself.87

    Two more design points come from the same section. The MAC is computed last, so placing it after the data it covers suits very high data rates. Using two structures, a header and a trailer, also helps high-rate implementations.8982 On MAC length, the report argues that a MAC needs about twice the key length to resist birthday attacks. With 128- to 256-bit keys that gives 256 to 512 bits, and 512 bits is the SDLS maximum. Shorter MACs are possible with more frequent rekeying. GCM is limited to 128 bits, even when used for authentication only. NIST-style schemes that allow very short MACs by limiting failed attempts are rejected, because locking out a spacecraft after failed attempts is worse than resisting attempts with a long MAC.88

    Security Associations and the authentication bit mask¶

    The Security Association (SA) comes from IPSec, adapted for space. It is a simplex, stateful session. Both ends must create it, give it keys and activate it before use. SAs can be preloaded or created while others are active. All frames sharing an SA on a physical channel form a Secure Channel.77 IPSec-style parameter negotiation is rejected. Contacts are short and delays long, the ground wants full authority over the spacecraft, and on-board processing is limited. Instead of an IPSec SA database, a simpler Security Association Context (SAC) exists in advance on board and on ground, and maps each SA to its GVCIDs or Global MAP IDs.78

    The authentication bit mask zeroes selected header bits before the MAC is computed. The VCID and the TC or USLP Segment Header are always included, because they identify the channel and MAP. The Security Header (except the IV) and the frame data field are also always included. The TM Master Channel Frame Count, the Insert Zone, the OCF, the error control field and the MAC are always excluded. The SCID is not in the default mask, because frame validation has already checked it. Missions can add fields, for example a sensitive VC_FSH, or the SCID when a constellation shares SAs. In cross support the mask must be exchanged out of band.7987

    Clear Mode and the Recovery SA¶

    Projects often ask for a Clear Mode that bypasses security on an otherwise protected SA. Security experts do not recommend it. A civil mission may still justify it when losing the spacecraft through a telecommand outage is a bigger risk than spoofing, and then on-board FDIR or a ground command may activate it. A Clear Mode SA can use a "no-op" algorithm, for example in testing before the cryptography is integrated. Such an SA can be enabled by a hardware strap and inhibited before flight. The header and trailer can stay present so that throughput does not change. Transitions between secure and clear should go through a separate authenticated SA.90

    A TC SA covers one VC only, but several SAs may cover the same VC. Experience with earlier ESA telecommand security led to the Recovery SA, a redundant SA used only as a last resort when the nominal SA has failed. Its context is stored separately at both ends, and its on-board keys should not be erasable, reloadable or revocable.91 The scenario section lists the emergencies it is meant for. If the telemetry link is lost, the ground commands blind, without SDLS reports, and the anti-replay counters may disagree. The programmable key storage may be corrupted. Or anti-replay synchronization may be lost. Recovery SA contexts and keys should be kept in non-erasable, non-volatile memory.110

    Signalling, monitoring and control¶

    Only the SPI, IV, sequence number, pad length and MAC travel in-line. Algorithms, keys and the other managed parameters need a separate, out-of-band logical channel for control and monitoring. The report describes two options:94

    • In-band at the crypto processor. Control messages are multiplexed and demultiplexed at the device that runs SDLS, so the security function stays controllable without the on-board computer. A dedicated VC would need its own FARM-1, COP-1 and CLCW reporting. A reserved MAP avoids that, so MAP IDs should be reserved for security control. On some missions MAPs already route high-priority commands (HPCs) to the command pulse generators.9495
    • Out-of-band through the platform computer. The security processor sits on the avionics bus and exchanges CCSDS packets with the platform computer. It may accept HPCs and software commands, so some commanding survives an OBC outage.95

    Monitoring the security function is also vital. Some missions use high-priority telemetry packets that do not need the OBC. The Extended Procedures add a data link solution, the Frame Security Report, an OCF similar to the CLCW (see below).95

    SDLS is agnostic about redundancy. It works with VC-based selection of redundant receivers, and with two identical processors running in parallel, which need fully synchronized managed parameters.96 Keys are SA attributes. Switching to another SPI changes the key from one frame to the next, provided the new SA's key is already active.97 SA scope differs by protocol. On TC an SA covers exactly one VC, because SDLS sits before FOP-1. There is no master channel SA, but several MAP-level SAs can share a VC. On TM, AOS and USLP an SA may span several VCs, but never an Only Idle Data VC. If a secured VC also carries idle frames, the idle pattern must be chosen with care to avoid known-plaintext weaknesses.9899

    Why CMAC for TC. Authentication is the key service for protecting control of the spacecraft. CMAC is a NIST algorithm and an ISO standard since 2011. It needs neither an IV nor padding, both of which are delicate to manage. Being cipher-based, it can reuse the AES engine for authentication key encryption and decryption.111

    Why GCM for TM, AOS and USLP. Authenticated encryption protects mission products. Encryption alone would not stop forgery. GCM is the CCSDS-recommended AE algorithm, it uses one key for both functions, and its deterministic 96-bit IV construction is recommended. Reusing an IV with the same key leaks information.     Worked example: the attacker budgets (arithmetic by this wiki)

    The report assumes 64 telecommands per second for 48 hours, the maximum assumed key validity. That is \(64 \times 172\,800 = 11\,059\,200\) attempts, and \(\mathrm{ld}(11\,059\,200) \approx 23.4\) bits.112 For key search it assumes 60 GIPS for 48 hours, \(1.0368 \times 10^{16}\) instructions, about 53.2 bits. Subtracting these from table A-1 gives about 54.6 bits (MAC) and 53.8 bits (key) for the medium risk, 74.6 and 73.8 for low, and 94.6 and 93.8 for lowest.

    Inference

    The near-equal differences in the worked example suggest that the analysis used a single risk value per category, about \(2^{-54}\) (some \(10^{-17}\)), \(2^{-74}\) and \(2^{-94}\). This matches the report's statement that both lengths use the same probability of success. The report does not print these risk values. They are back-calculated by this wiki.

    The 128-bit values were chosen for margin and convenience, and later research cited by the report says they hold well beyond 2032. Quantum computing changed the key length: Grover's algorithm halves the exponent of a brute-force search, so the baseline key was doubled to 256 bits. The 32-bit anti-replay counter allows about 4 billion uses of a key before it rolls over.113

    Scenarios¶

    In the basic scenario a ground centre sends telecommands over the forward link. Red marks data that needs protection and black marks data that is protected.108 In the complex scenario three on-board elements share a return link, and two of them use separate SAs and keys. A trusted baseband unit does the link-layer security on board. On the ground, separate elements receive their own VC or MC frames and manage their own keys. Because the primary headers stay readable, SLE return services still work. The scenario can represent several missions sharing a channel, or separate housekeeping and payload operations groups.109

    Telling transmission errors from security events¶

    For FDIR it matters whether a rejected frame was corrupted by noise or by an attacker. A MAC of 64 to 512 bits detects errors far better than a 16-bit CRC, so errors missed by the channel coding could appear as security failures.69 Annex D concludes:

    • TC. The TC requirement is at most one erroneously accepted frame in \(10^{9}\). It is met without a CRC at bit error rates below \(10^{-4}\) (TED mode) or \(10^{-5}\) (SEC mode). ESA's SEC mode with a mandatory CRC reaches below \(10^{-15}\). No extra CRC needs to be mandated when security is applied. The same holds for the short LDPC codes and for USLP uplinks.127
    • TM, AOS, USLP. A CRC is recommended whenever SDLS is used, except with Reed-Solomon \(E=16\) or LDPC codes. Higher integrity can come from the 32-bit USLP CRC or a non-standard longer one.128

    Cryptographic algorithms (CCSDS 352.0-B-2)¶

    Scope and rationale¶

    The algorithms standard recommends one symmetric encryption algorithm and one mode for all CCSDS missions, plus a choice of authentication and integrity algorithms. It does not say where or when to use them: that is up to mission planners and their risk analysis. Standard, well-known algorithms give high-quality cryptography, economies of scale through off-the-shelf products, and interoperability. The standard also says that using it does not by itself remove every risk, and that an information security risk assessment is still needed.131 It applies to civil missions with confidentiality or authentication requirements, on forward and return links, on ground networks and even for stored data. Security is encouraged for all missions, especially on command links, but a risk analysis may reduce or remove the need. Key management is out of scope.132133

    CCSDS does not mandate a layer for encryption. It may sit in an application (TLS), above the network layer (IPSec), at the data link layer (SDLS), at the physical layer (bulk encryption), or at several layers at once.135

    Concepts behind the choices¶

    • Hash-based and cipher-based MACs. An HMAC runs a hash such as SHA-256 over the data and a shared secret, which gives a MAC of fixed size. A cipher-based MAC uses the secret as the key of a block cipher such as AES. When both confidentiality and authentication are needed it can share one algorithm with encryption, and it is often easier to build in hardware.136
    • Digital signatures. The signer hashes the data and encrypts the hash with its private key. The receiver recovers the hash with the public key, which proves origin, and compares it with its own hash, which proves integrity. Public keys can be sent with the data, cached, or fetched from a key server. A spacecraft that cannot reach a key server can have a key cache preloaded before launch or uploaded later.137144
    • Authenticated encryption (AEAD). Encrypt-then-MAC is secure against adaptive chosen-ciphertext attacks. CCM and GCM are AE modes. GCM is fast in hardware and software, can be parallelized and pipelined, and needs no padding. The standard states that "the use of non-authenticated encryption is highly discouraged for CCSDS missions".138139

    How SDLS and the Extended Procedures use them¶

    The SDLS baselines take their algorithms from this standard: AES-CMAC for TC, AES-GCM for TM, AOS and USLP, all with 256-bit keys and 128-bit MACs.225111 The Extended Procedures baseline uses AES-GCM for OTAR and for key verification, with 256-bit keys, 96-bit IVs and 128-bit MACs.212 CCSDS 355.1-B-1 requires the challenge-related authentication algorithms to come from this standard, and its managed parameters list "AES/Counter Mode, GCM" as the OTAR algorithm choices.162206

    Security considerations¶

    The algorithms standard describes what happens if security is missing. Without confidentiality, sensitive, proprietary or private data such as crew medical information can be disclosed, for example to an RF eavesdropper, a landline tap or an insider. Without authentication, false commands could be injected into a spacecraft's command chain. Without integrity checking, a corrupted command might still be executed, and corrupted telemetry might lead controllers to act on a non-existent problem. The standard adds an availability caution: if on-board security fails and there is no bypass mode, all communication could be lost. SANA takes no action, and the algorithms are in the public domain with no known patents.145146

    SDLS Extended Procedures (CCSDS 355.1-B-1)¶

    Purpose, scope and roles¶

    The Extended Procedures (EP) define the Key Management, Security Association Management and SDLS Monitoring and Control services needed to run SDLS over a space link. They define the PDUs, the procedures, and the interfaces to SDLS and the data link protocols, including a status report in the OCF. They do not define implementations, the security protocol itself, or any particular algorithm for key generation and management.148 There are two roles:149

    • The Initiator manages the session parameters, provides the resources and always starts a procedure. It is usually the mission operations centre.
    • The Recipient configures itself according to the Initiator's procedures. It is usually the spacecraft.

    The Anti-Replay Sequence Number (ARSN) is defined as a counter set to zero when an SA is activated and incremented for each frame sent on that SA.149

    Key management¶

    The two-tier key hierarchy¶

    The key management service is an SDLS-specific version of the abstract procedures in the CCSDS Symmetric Key Management practice. Initiator and Recipient share the keys for all their links. The baseline is a two-tier symmetric infrastructure. Master keys (also called static keys or key encryption keys) are used for management, with few exceptions. Session keys (traffic protection keys) do the SDLS cryptographic work. OTAR keeps session keys fresh by sending new ones, generated by the Initiator, to the Recipient. OTAR is recommended, but a mission may fly with preloaded keys only.156

    PDU layouts¶

    Most field sizes are managed parameters. Annex D fixes them for the baseline. The OTAR command in the baseline uses a 16-bit master Key ID, a 96-bit IV, blocks of a 16-bit Key ID plus a 256-bit session key, and a 128-bit MAC. The Length field is \(N \times 272 + 240\) bits. At most 28 keys fit, so that the PDU stays within 995 octets and the command fits one 1024-octet frame.200213

    The Start SA PDU carries a 16-bit SPI and one or more 32-bit GVC/GMAP IDs. How the master channel, VC and MAP values are packed into 32 bits is mission-specific in the normative text. Annex D gives the baseline layout:202216

    The Create SA PDU starts with fixed-size fields, followed by pairs of a length and a value: the cipher suite identifiers, the IV, the bit mask, the ARSN and the window. A service type flag set to 1 means the SA provides that service, and authenticated encryption sets both. The meaning of the cipher suite identifiers is mission-specific.204

    The other SA PDUs are short. Stop, Expire, Delete, SA Status Request and Read ARSN carry only the 16-bit SPI. Set ARSN and Set ARSN Window add the new value. Rekey SA carries the SPI, the new encryption and authentication Key IDs, the new ARSN and the new IV. For an AE algorithm with a single key, the new authentication Key ID field signals that key. The SA Status reply returns the SPI and an 8-bit field holding the last state-transition procedure ID.205203167 In the baseline the Rekey and Set ARSN PDUs use a 96-bit ARSN field. TC SAs put their 32-bit ARSN in it with the left 64 bits zeroed. TM, AOS and USLP SAs put the 96-bit GCM IV in it, because for AES-GCM the IV is the anti-replay number, so setting the ARSN sets the IV. Read ARSN returns 4 octets for TC and 12 octets for TM and AOS.217218

    Baseline implementation mode¶

    Annex D gives a baseline for interoperability testing and operation:209210211212

    • The FSR is an OCF of Type 2 and alternates with the CLCW when COP-1 reports on the same VC.
    • SDLS runs in its own baseline mode, and EP PDUs use the reserved SPIs 0 and 65535. TLV nesting is not used.
    • Key Destruction and Key Inventory are left out of the baseline.
    • OTAR and Key Verification use AES-GCM with 256-bit keys, 96-bit IVs and 128-bit MACs.
    • Key IDs are 16 bits. Values 0–127 are not used to reference session keys in Key Verification.
    • Key Activation and Deactivation handle up to 16 keys per PDU (at most 35 octets, Length = \(N \times 16\)). Key Verification handles up to 21 keys (128-bit challenges; the reply carries per key a 96-bit IV, a 128-bit encrypted challenge and a 128-bit MAC).214215

    Inference

    The baseline reserves Key IDs 0–127 from session keys and leaves it to implementers to give master keys "a special range". This suggests, but does not state, that 0–127 is meant for master keys.213215

    Conformance and security considerations¶

    Conformance is claimed by filling in the PICS proforma of annex A.207 The security annex notes that EP PDUs are protected at least by authentication, which gives integrity, and that authentication of the communicating entities relies on SDLS. The protection of especially sensitive PDUs is left to the implementer. Without authentication, unauthorized procedures or software could be uploaded. Without integrity, corrupted procedures could cost the security function or the mission. Without confidentiality, session keys could be disclosed. The standard creates no SANA registries.208

    Points to watch in the sources¶

    The documents disagree in a few places. These are noted here rather than resolved.

    • Security Header maximum. 350.5-G-2 table 3-4 says the Security Header can reach 42 octets. SDLS §4.1.1.1.4 allows up to 64 octets.93223
    • TM baseline sequence number. 350.5-G-2 §4.4.2 lists a 32-bit in-line anti-replay sequence number for the TM baseline. Its annex A3.4 and SDLS annex E1 say that the 96-bit IV takes that role and the Sequence Number field is empty.106225
    • SA count. 350.5-G-2 §3.2.2 gives a maximum of \(2^{16}\) simultaneous SAs per physical channel. §3.4.2.2 gives 65,534 per Master Channel, since two SPI values are reserved.7783
    • Reserved SPIs. SDLS reserves 0 and 65535 "for future use". The Extended Procedures allow them for EP PDUs, and their baseline uses them, while their own managed parameter table gives the SPI range as 1–65534.224194210206
    • Create SA PDU. The clause text gives the authentication bit mask length field as 8 bits. Figure 5-16 draws it as 16 bits. The PICS lists encryption and authentication Key IDs as mandatory Create SA fields, but the PDU definition has none.204155
    • Switching SAs. 350.5-G-2 §3.2.2 places the mechanism for switching between active SAs in the Extended Procedures. §4.1 calls it an application layer function.77101
    • Editorial leftovers in 350.0-G-3. §6.5.1 mentions an "Option B as described in 5.3", but §5.3 of Issue 3 defines no such option.44 §3.1 first speaks of four security implementation points and then lists five, and §5.1 considers four layers.922 §5.5 cites reference [9], the Cross Support Reference Model, for the space packet layer, while the Space Packet Protocol is reference [8].335
    • Overhead budget. 350.5-G-2 §2.4 limits the SDLS overhead to 32 octets per transfer frame, while its table 3-4 allows a 42-octet Security Header and a 64-octet Security Trailer. The baselines use 6 + 16 = 22 octets (TC) and 14 + 16 = 30 octets (TM, AOS, USLP); these sums are this wiki's arithmetic.5993225
    • Length units. The EP Length field counts bits. The baseline Key Verification lengths (\(N \times 18\) and \(N \times 46\)) match the field sizes only when counted in octets.199215
