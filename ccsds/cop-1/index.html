    COP-1: FOP-1, FARM-1 and the CLCW (CCSDS 232.1-B-2)¶

    The Communications Operation Procedure-1 (COP-1) is the closed-loop retransmission procedure of the CCSDS telecommand link. It runs inside the TC Space Data Link Protocol (and the Unified Space Data Link Protocol) on every virtual channel, and it uses an Automatic Repeat reQuest (ARQ) scheme of the go-back-n type: the receiver accepts Type-A frames only in strict sequence, and the sender, on any sign of a loss, sends again every frame that has not yet been acknowledged. The result is delivery of telecommands to the spacecraft without omission, duplication or reordering.1

    COP-1 is a pair of synchronised state machines per virtual channel: the Frame Operation Procedure-1 (FOP-1) at the sending end, normally on the ground, and the Frame Acceptance and Reporting Mechanism-1 (FARM-1) at the receiving end, on board. The FARM-1 reports its state back in a 32-bit Communications Link Control Word (CLCW), which travels in the Operational Control Field of the telemetry frames.12 This page follows CCSDS 232.1-B-2 (Blue Book, September 2010, with Technical Corrigendum 1 of April 2019), the CLCW definition of CCSDS 232.0-B-4, the ECSS adoption notice ECSS-E-AS-50-26C, the superseded ECSS-E-ST-50-04C (31 July 2008) whose clause 7 was the European COP-1 text, and the real Solar Orbiter documentation and MIB.34106

    Why COP-1 exists¶

    Space links are noisy. Correctness of what is delivered is guaranteed, within known probabilities, by the channel coding of the CLTU and by the Frame Validation Checks of the data link protocol. Completeness, order and absence of duplicates on a virtual channel need something else: a numbering scheme for frames and a feedback loop. That is the job of COP-1.9 ECSS-E-ST-50C turns this into a system requirement: a service shall guarantee in-sequence delivery of telecommands, and the space communication system shall support both commanding in the blind and the return of telecommand acknowledgements.10

    COP-1 handles, strictly speaking, partial frames: FDUs plus the header fields that COP-1 generates (Bypass Flag, Control Command Flag, N(S)); the rest of the frame is completed by the frame generation procedure.1

    The two services¶

    Sequence-Controlled Service (AD Service). With high probability no FDU is lost, duplicated or delivered out of sequence. Two frame types are used: Type-AD frames carry the FDUs, Type-BC frames carry the control commands that configure COP-1 (Unlock and Set V(R)). The service is started with one of four "Initiate AD Service" directives; once initialised, FDUs are sent in the order in which they are presented. The guarantee holds per virtual channel only. A Wait mechanism lets the receiver signal that it has no resources for more data.1516

    Expedited Service (BD Service). Type-BD frames are sent once, with no retransmission and no guarantee of delivery. FOP-1 gives them immediate access as far as the lower layers allow, and FARM-1 passes their FDUs on immediately. The service is for exceptional situations such as spacecraft recovery, or for use under a higher layer that retransmits by itself. "Expedited" does not mean faster: if a reliable AD service is running, AD is recommended even for urgent data, and an inserted frame must not use the MAP of an unfinished multi-segment transfer.1718

    Valid Type-B frames are always accepted by FARM-1 and only counted (in the FARM-B counter of the CLCW). Both frame types are protected by the coding sublayer and must pass the Frame Validation Checks, so accepted Type-B frames are very probably error-free, but their order is not controlled.1 ECSS-E-ST-50-04C put it differently: its expedited service delivers data in order and without duplication, but with possible omissions, and passes a BD FDU on even when FARM-1 is in Wait or Lockout. The two texts agree that nothing is retransmitted; only the CCSDS book declines to promise anything about order.10717

    Shared buffers

    Some FARM-1 implementations use one buffer for both Type-AD and Type-BD FDUs. A Type-BD frame then erases an FDU that is being delivered or is waiting, without any sign of it in the CLCW. With such receivers the sender should terminate the AD service before using the BD service on the same virtual channel.18

    Interfaces of COP-1¶

    COP-1 is defined through abstract signals between procedures, not through an implementation.19

    At the sending end, FOP-1 sits between the Higher Procedures (segmentation, blocking, conversion of service primitives) and the Lower Procedures (frame generation, multiplexing, coding):20

    Signal Direction Parameters Purpose
    Directive Request Higher → FOP-1 Request Identifier, GVCID, Directive Type, Directive Qualifier From DIRECTIVE.request21
    Directive Notification FOP-1 → Higher Request Identifier, GVCID, Notification Type To DIRECTIVE_Notify.indication
    Asynchronous Notification FOP-1 → Higher GVCID, Notification Type, Notification Qualifier To Async_Notify.indication22
    Request to Transfer FDU Higher → FOP-1 Request Identifier, GVCID, FDU, Service Type One per FDU (one service data unit may become several FDUs)23
    Transfer Notification FOP-1 → Higher Request Identifier, GVCID, Notification Type Accept, Reject, Positive or Negative Confirm23
    Transmit Request for Frame FOP-1 → Lower GVCID, Bypass Flag, Control Command Flag, N(S), data field Hand a frame to the lower procedures24
    Abort Request FOP-1 → Lower GVCID Cancel ongoing processing of AD and BC frames, to retransmit quickly24
    Response Lower → FOP-1 GVCID, Response Type AD_Accept, AD_Reject, BC_Accept, BC_Reject, BD_Accept, BD_Reject: flow control per frame25

    The CCSDS book has an Abort Request cancel only Type-AD and Type-BC processing, and lets it optionally reach into the coding sublayer. ECSS-E-ST-50-04C spells out three details: Type-BD frames are not deleted by an abort, a frame already being radiated as a CLTU is completed rather than cut, and the lower procedures return no response to the abort.24108

    At the receiving end, the Lower Procedures validate and demultiplex frames and signal each valid frame with Valid Frame Arrived Indication (GVCID). FARM-1 places an accepted Type-AD FDU in a buffer only if one is free, otherwise the frame is discarded; a Type-BD FDU is placed in a buffer even if none is free, overwriting older data. Each new FDU is announced with FDU Arrived Indication (GVCID), and an optional Aborted Indication may report data erased in favour of a BD FDU. If the on-board flow control can ever set the Wait flag, it must also provide a Buffer Release Signal when space for at least one more maximum-size frame becomes available.262728

    Directives and notifications¶

    Directives¶

    An authorised user controls COP-1 of a virtual channel through directives passed with DIRECTIVE.request (in TC-SDLP terms, the COP Management Service). Table 4-1 defines eleven directive types in four groups: four Initiate AD Service directives, one Terminate, one Resume and five FOP-1 Setup directives (Set V(S) and the four Set directives for K, T1_Initial, Transmission_Limit and Timeout_Type). The standard's text calls them "twelve Directives" corresponding to events E23 to E40; the count in the categories and the table is eleven. Any other directive is rejected as invalid.2930

    Directive Type Qualifier FOP-1 event Effect (from S6 Initial unless stated)
    Initiate AD Service (without CLCW check) none E23 Initialise, confirm at once, go to S1 Active
    Initiate AD Service (with CLCW check) none E24 Initialise, start the timer, go to S4; a clean CLCW with N(R) = V(S) confirms and leads to S1
    Initiate AD Service (with Unlock) none E25, E26 If BC_Out_Flag is Ready: initialise, send an Unlock BC frame, go to S5
    Initiate AD Service (with Set V(R)) V*(R), the new V(R) E27, E28 If BC_Out_Flag is Ready: initialise, set V(S) and NN(R) to V*(R), send a Set V(R) BC frame, go to S5
    Terminate AD Service none E29 In S1 to S5: Alert [term] and go to S6; in S6: just confirm
    Resume AD Service none E30 to E34 In S6 with SS = 1 to 4: resume in S1 to S4 respectively; rejected if SS = 0
    Set V(S) to V*(S) V*(S) E35 Only in S6 and only if SS = 0: set V(S) and NN(R) to V*(S)
    Set FOP_Sliding_Window_Width new K E36 Accepted in every state
    Set T1_Initial new T1_Initial E37 Accepted in every state
    Set Transmission_Limit new limit E38 Accepted in every state

    any other — E40 Rejected

    Directive list from table 4-1; events and effects from the FOP-1 state table (parts 4 to 6).2911 The four Initiate directives differ in how much they rely on the receiving end. Two of them send a control command and wait for its effect to show in the CLCW, retrying on a timer up to a limit; the other two start without waiting for any receiving-end action, one of them after checking for a good CLCW.15

    Notes in the standard: Terminate has no effect on a suspended AD service in S6 (it is accepted and confirmed, but the service stays suspended and the queues are not purged); resume it first, or re-initiate it. Set V(S) is meant for re-aligning FOP-1 with FARM-1 after a break in contact, with V*(S) taken from N(R) of the CLCW, and should not be used while suspended. Setup directives are allowed while AD is active but also affect frames already on the Sent_Queue.31

    Directive and transfer notifications¶

    For every directive FOP-1 first returns Accept Response to Directive or Reject Response to Directive (if rejected, nothing else follows), then later Positive Confirm or Negative Confirm Response to Directive. A negative confirm carries no reason, but every condition that can cause one also raises an Alert.32

    For each Request to Transfer FDU, FOP-1 returns Accept or Reject Response to Request to Transfer FDU; for AD FDUs it later returns Positive Confirm (the FDU was received and acknowledged by a CLCW) or Negative Confirm (COP-1 cannot guarantee the transfer). The user-level XXX_Notify.indication primitives carry the same four types. An AD FDU whose acceptance FOP-1 delays sits in the one-place Wait_Queue, and the Higher Procedures may not submit another until it is accepted or rejected; this is the flow control seen by the user.3334

    Between acceptance and Positive Confirm an FDU is in a "gray area": nobody can know yet whether it reached the spacecraft. A Negative Confirm means a break in the sequence-controlled guarantee, and the FDU may or may not have arrived. BD FDUs are only accepted or rejected (there is no Wait_Queue for them, no copy is kept, and no confirmation is given).3435

    ECSS-E-ST-50-04C names the span of the guarantee: a sequence-controlled session begins when the management entity receives the Positive Confirm of an Initiate AD Service directive and ends with the next Alert. It also lists cases in which the guarantee does not hold at all: FOP-1 and FARM-1 sequence numbers not synchronised at the start of a session, several FOP-1 instances sending to one FARM-1 at the same time, and CLCWs delivered to FOP-1 from the wrong spacecraft.110109

    Alert and Suspend¶

    Two asynchronous notifications exist: Alert, with a Reason Code, and Suspend.36 An Alert means an unrecoverable condition and the end of the sequence-controlled guarantee; higher layers may need to recover. After an Alert no further Alert occurs until an Initiate AD directive is received, except Alert [LLIF], which can occur at any time.3738

    Reason Code Condition
    Limit A CLCW negatively acknowledges a frame while Transmission_Limit = 1
    T1 The timer expires with Transmission_Count at Transmission_Limit (only if TT = 0), or the transmission limit of a BC frame (Unlock, Set V(R)) is exhausted
    Lockout The CLCW shows Lockout
    Synch A CLCW with Retransmit = 0 and N(R) = NN(R) arrives after one with Retransmit = 1; or all frames are acknowledged but Retransmit = 1; or frames are acknowledged during the initialising phase S4
    NN(R) A CLCW with an invalid N(R) arrives
    CLCW A CLCW with Wait = 1 and Retransmit = 0 arrives, or a CLCW with an invalid bit pattern
    LLIF Lower Layer Interface: FOP-1 and the lower procedures are out of step (a frame is rejected although the Out flag was Ready)
    Term A Terminate AD Service directive arrived

    Restated from table 4-4.37

    Alerts linked to the transmission count can be caused by a physical-layer break outside the data link layer. All others report a breakdown of the protocol itself: some part of the system does not work to specification, and earlier reports may have been wrong. Because the VCID in received data may then be corrupt, one failure can raise Alerts on several virtual channels.38 ECSS-E-ST-50-04C adds that after an Alert the management entity should take recovery actions so that no data is lost, duplicated or erroneous; that an implementation may report, with the Alert, the FOP-1 event number and state that caused it; and that FOP-1 should pass further, implementation-dependent status information to management for performance monitoring and diagnosis.111112

    Suspend is the deep-space tool: with TT = 1 and a small T1_Initial, FOP-1 sends a sequence of AD frames a set number of times and then suspends itself without clearing its buffers; a later Resume directive continues in the same state.39

    FOP-1: the sending end¶

    FOP-1 variables¶

    FOP-1 keeps fifteen variables per virtual channel. The state table and actions, not the variable descriptions, are the master definition.40

    FOP-1 states¶

    State Name Meaning
    S1 Active Normal state: no recent errors, no flow-control incidents
    S2 Retransmit without Wait The CLCW shows Retransmit = 1, nothing else exceptional
    S3 Retransmit with Wait The CLCW shows Wait = 1 (and therefore also Retransmit = 1, because Wait is only set after a frame has been discarded)
    S4 Initialising without BC Frame After Initiate AD (with CLCW check), waiting for a clean CLCW
    S5 Initialising with BC Frame After Initiate AD (with Unlock or with Set V(R)), waiting for the BC frame to be sent and a clean CLCW
    S6 Initial AD service not running: at start-up, after Terminate, after any Alert, and while suspended; only BD frames can be sent

    Restated from §5.1.2.5 The initial state must be re-enterable many times during a mission, because the link is interrupted and several sending ends may serve one receiver.5

    Timer, transmission limit and timeout type¶

    Every transmission of an AD or BC frame starts (or restarts) the timer with T1_Initial; the timer is not used for BD frames. Without it, the loss of the last frame sent would never be noticed. If an acknowledgement arrives and nothing new has been sent, the timer is cancelled.46

    For normal operation, T1_Initial must be at least the sum of eight delays:47

    1. processing below FOP-1 at the sending end;
    2. transmitting a maximum-length frame as a serial bit stream, including CLTU and coding overhead;
    3. one-way light time to the receiver (including any relay satellite);
    4. processing below FARM-1 at the receiving end;
    5. the worst-case time to sample FARM-1 status and encode it as a CLCW;
    6. the worst-case time to send the CLCW in the return-link data structure;
    7. one-way light time back;
    8. extracting the CLCW and delivering it to FOP-1.

    The transmission limit applies only to the first frame on the Sent_Queue, and the count is reset whenever any frame is acknowledged. So the limit is in effect a property of the queue: each frame is sent at least Transmission_Limit times (unless the limit is 1, in which case nothing is ever retransmitted), and a frame that moves to the head of the queue may be sent more often. When the count reaches the limit, a negative acknowledgement raises Alert [Limit] (limit 1) and a timer expiry raises Alert [T1] if TT = 0 or suspends the AD service if TT = 1. BC frames are retransmitted only on timer expiry, with Alert [T1] when the limit is reached.4849

    The FOP sliding window¶

    The FOP sliding window limits how many frames may be sent ahead of the last acknowledged one, so that a new frame can never carry the same N(S) as a frame that the receiver rejected. A new AD frame is sent only while V(S) < NN(R) + K (modulo 256). K must satisfy 1 ≤ K ≤ PW and K < 256, where PW is the positive window of the FARM.5051 ECSS-E-ST-50-04C warns implementers that comparisons of V(S), N(R) and NN(R) must respect the valid ranges of the sequence number: with K greater than 127 a conventional modulo-256 comparison can give the wrong answer.113

    FARM-1: the receiving end¶

    Variables and states¶

    FARM-1 keeps nine variables per virtual channel: State, Lockout_Flag, Wait_Flag, Retransmit_Flag, V(R), FARM-B_Counter, and the window widths W, PW and NW.57

    State Name Behaviour
    S1 Open Accepts in-sequence Type-AD frames and passes their FDUs on
    S2 Wait No buffer is free for another Type-A FDU; entered when an in-sequence frame cannot be stored, left when a buffer is released
    S3 Lockout Entered when a frame arrives with N(S) outside the range a correctly working FOP could produce; a safe state in which no Type-A FDU is accepted; left only by an Unlock command

    Restated from §6.1.2.8

    • Lockout_Flag is 1 exactly in Lockout and Wait_Flag exactly in Wait; both are copied into the CLCW.58
    • Retransmit_Flag is 1 whenever FARM-1 knows a Type-AD frame was lost or discarded for lack of buffer space. At the sender it negatively acknowledges every frame with N(S) ≥ N(R). It is cleared by receiving the frame with N(S) = V(R), by Set V(R) (unless locked out) and by Unlock.58
    • FARM-B_Counter counts valid Type-BD and Type-BC frames. It is not used by either state machine; it gives higher layers a minimal error-control loop for the BD service. Only its two least significant bits go into the CLCW.59
    • V(R) is the N(S) expected in the next Type-AD frame.60

    The FARM sliding window¶

    The windows protect FARM-1 against an uncontrolled sequence of frames whose N(S) runs at least 256 ahead of V(R), and more generally against a malfunctioning or wrongly set-up FOP-1. The window has a total width W, a positive part PW starting at V(R) and a negative part NW ending at V(R) − 1, the number of the last accepted frame. Everything else (256 − W values) is the lockout area.61

    When retransmission is allowed (the normal case), W is an even integer from 2 to 254, fixed for the mission unless otherwise specified (there is no command to change it), and PW = NW = W/2. A received Type-AD frame then falls in one of four cases:6263

    Case Condition (modulo 256) FARM-1 action Typical cause
    In sequence N(S) = V(R) Accept (if a buffer is free), V(R) := V(R) + 1, Retransmit := 0 Normal operation, or a retransmission after a loss
    Positive window V(R) < N(S) ≤ V(R) + PW − 1 Discard, Retransmit := 1 An earlier frame was lost; retransmission has not started
    Negative window V(R) − NW ≤ N(S) < V(R) Discard, nothing else Frames resent although already accepted: T1 too short, a link outage, or deliberate repetition in deep space
    Lockout area otherwise Discard, Lockout := 1, go to Lockout FOP and FARM out of step

    If a mission sends each Type-AD frame only once per session (Transmission_Limit = 1), it may set PW > NW, down to NW = 0 and PW = W, with W from 1 to 256. K may never exceed 255 in any case.64 ECSS-E-ST-50-04C spells out one exception to the fixed window: a mission whose commanding performance depends on different window widths in different mission phases fixes W, PW and NW per phase rather than for the whole mission.115

    • the CLCW to travel in the OCF of a TM (version 1) or AOS (version 2) frame, and to be given to FOP-1 only if it comes from an error-free frame (a successfully corrected frame counts as error-free) of the spacecraft to which the TC virtual channel belongs;

    Retransmission and flow control¶

    Retransmission starts either on a Retransmit flag in the CLCW or on timer expiry, and always resends all unacknowledged frames; the windows prevent a new frame from reusing the number of a missing one.1 A worked example is in the loop in one picture. If the spacecraft runs out of buffers, FARM-1 discards the in-sequence frame, sets Wait and Retransmit and enters Wait; FOP-1 moves to S3 and stops sending new frames, and when the buffer release signal clears Wait, the next CLCW shows Retransmit alone and FOP-1 resends from N(R).1211 A CLCW showing Wait without Retransmit is a protocol error (Alert [CLCW]), because Wait is only ever set after a frame has been discarded.537

    Lockout and its recovery¶

    Lockout means that FARM-1 received a Type-AD frame with an N(S) that a correct FOP could not have produced: typically FOP and FARM lost step, for example after a break in contact, a reset of either end, or two sending ends commanding the same receiver, a case COP-1 cannot handle.856 FOP-1 sees the Lockout flag and raises Alert [lockout], ending the AD service.11

    Inference: recovery recipe

    Unlock clears Lockout, Wait and Retransmit but leaves V(R) unchanged, and a FOP that is initialising with a BC frame (S5) only confirms on a clean CLCW whose N(R) equals V(S). The usual recoveries are therefore either (1) Set V(S) to V*(S) with V*(S) taken from the N(R) of the latest CLCW, followed by Initiate AD Service (with Unlock); or (2) Initiate AD Service (with Unlock), then, once FARM-1 is open, Initiate AD Service (with Set V(R)) to realign both ends on a chosen number (Set V(R) alone does nothing in Lockout). In recipe (2), if V(S) differs from V(R), the first directive cannot get the confirming CLCW (event E1) and, once the BC frame has been sent Transmission_Limit times, ends with Alert [T1] (event E17), although the Unlock itself has reached FARM-1; the second directive then starts from S6. These recipes are this wiki's reading of the state tables and of the note on Set V(S); the operational procedure of a given mission is not stated in the available sources.121131

    The SCOS-2000 database ICD strongly recommends defining the BC-frame commands with a global interlock on at least the second uplink verification stage, so that the ground releases no further commands until AD mode has been set up.103 In the Solar Orbiter MIB, UNLOCK and SETVR are defined without an interlock (CCF_ILSCOPE = N); see TC-SDLP control commands.98

    Deep-space options¶

    On a long-delay link the normal T1 leaves the uplink idle for most of the round trip. COP-1 offers two remedies, which can be combined with the coding sublayer's systematic retransmission:8283

    • Early automatic retransmission. A small T1_Initial forces FOP-1 to resend the whole Sent_Queue several times before any acknowledgement arrives. With TT = 1 it then suspends instead of raising an alert, and is resumed to process the acknowledging CLCWs. The resulting pattern is ABCDEF ABCDEF …; it resists error bursts but loses the rest of a cycle after an early loss.8284
    • Set V(R) without verification. A small T1_Initial lets the Set V(R) command be sent a few times without waiting for its confirmation; the user is alerted when the transmissions are used up and can then issue Initiate AD Service (without CLCW check).82
    • Systematic retransmission in the coding sublayer repeats each CLTU (pattern AAABBBCCC…), which is good against sporadic losses. It is invisible to FOP-1: it changes neither its state nor its counters, and duplicate frames are simply rejected by FARM-1 in the negative window.8285

    The CCSDS overview report confirms that the sequence-controlled service still delivers each FDU once and in order even when frames are transmitted several times.83 See the CLTU page for the coding-sublayer side.

    Blind commanding¶

    When no telemetry, and thus no CLCW, is available, the BD service can be used because it does not need the feedback loop. Data then arrives with high probability of being error-free but possibly with gaps. Alternatively the AD service can be combined with multiple transmissions; for deep space this can be more efficient than BD.86 The FARM-B counter in the CLCW lets the sender check afterwards that BD frames arrived.74 The ECSS handbook recommends that near-Earth missions use the sequence-controlled service and keep the expedited service for exceptional situations such as recovery.87

The 2019 corrigendum of the CCSDS book does not affect the adoption notice.9091 The notice changes one thing: when a Type-BD FDU is accepted with no free buffer, the buffered data is erased and the FDU Arrived Indication carries a mandatory FDU aborted indication parameter, set exactly in that case, which tells the higher procedures that data were overwritten.92 Its annex records that the special FARM-1 with a single back-end buffer, specified in ECSS-E-ST-50-04C, is not part of the CCSDS book.93 The ECSS handbook explains why: some European on-board hardware has a single back-end buffer per virtual channel, so a new frame can overwrite the previous FDU, and operators must understand the link between uplink and on-board flow control.94 The coding notice ECSS-E-AS-50-24C records the same three-way replacement in its change log.125

    COP-1 in ECSS-E-ST-50-04C¶

    Clause 7 of ECSS-E-ST-50-04C (31 July 2008) was the ECSS text of COP-1, written against CCSDS 232.1-B-1 (2003). It covers the same ground: FOP-1 and FARM-1 with their variables, the eleven directive types, the eight Alert reasons and the two state tables (its tables 7-8 and 7-9), and it states that its FOP-1 is the updated revision B ("FOP-1B"), whose revision explains the non-sequential numbering of some events. This wiki compared the directive and Alert lists, which match the CCSDS tables above, but not the state tables entry by entry.106119126 Its annex C lists two differences from CCSDS 232.1-B-1, both on the receiving side, and both are what ECSS-E-AS-50-26C still records today:1209293

    • the FDU Arrived Indication always carries the FDU aborted indication, which CCSDS 232.1-B-1 left optional;
    • it specifies how a FARM-1 with only one back-end buffer per virtual channel behaves, a case the CCSDS book did not consider.

    The single-buffer rules of §7.5.4 are short. FARM-1 needs at least one front-end buffer for one maximum-length frame and at least one back-end buffer for one maximum-length FDU. With a single back-end buffer a valid Type-BD frame always wins, in all three FARM-1 states: if the buffer is free the FDU is copied and announced normally; if not, the FDU overwrites the previous one, which may have come from a Type-AD or a Type-BD frame, and the FDU Arrived Indication is raised with the aborted indication set. The erasure is invisible in the CLCW, and if the lost FDU came from a Type-AD frame it has already been acknowledged, so the sequence-controlled guarantee is broken. Hence the companion rule of §7.4.4.2: with such a FARM-1 the sending-end management must terminate any ongoing AD service before starting the BD service on the same virtual channel. The standard sees the design's merit in reduced complexity and resource use, hence reliability.121122123

    From COP-1A to COP-1B. Annex B of ECSS-E-ST-50-04C records that ESA's Packet Telecommand Standard PSS-04-107 (issue 2, April 1992) specified the older version, now called COP-1A, and that the changes affect only the sending end (FOP-1), not FARM-1. The PSS text also differed around the report: its CLCW Status Field was always zero, it fixed the CLCW sampling through two Standard Insertion Schemes, which ECSS-E-ST-50-04C replaced by project-specific rates, and it spoke of the Command Operation Procedure and the Command Link Control Word; one PSS CLCW field called Report Type became a Reserved Spare.124 The CCSDS book gives the same lineage from its side: FOP-1B was introduced in issue 2 of the old Command Operation Procedures-1 recommendation, FOP-1A being defined in issue 1.7 The history is told on From ESA PSS to CCSDS and ECSS.

    COP-1 on Solar Orbiter¶

    Spacecraft side. The Solar Orbiter TM/TC ICD addresses its two on-board telecommand decoders through two TC virtual channels, VC1 (0b000001) and VC2 (0b000010), and requires the same values in the CLCWs. Every TM frame has the OCF flag set and carries a CLCW (type flag 0) in its OCF. The frame sequence number is V(S) for AD frames and zero for BC and BD frames.959697 The ICD sentence that still calls the suggested VCIDs "Zero and One" appears, from its change record, to be a leftover of an earlier issue;99 see the Solar Orbiter profile of TC-SDLP. Choosing 1 and 2 also avoids the all-zeros VCID that the ECSS handbook advises against.79

    In the MIB. The MIB defines the two control frames UNLOCK and SETVR (see TC-SDLP control commands), and decodes the CLCW in two places:100101

    • On board, each decoder's CLCW is reported in the "DMS OBC Status Slow" housekeeping packets TM(3,25) (SPID 19541 on APID 164 and SPID 19550 on APID 162). Decoder A's word sits at octets 29–32, both as the raw 32-bit parameter NCDD05J1 TC Decoder A.PdecCLCW and split into the CLCW fields NCD0Z021 (Type, bit 0) to NCD0Z02D (RepValue, octet 32), including NCD0Z029 LkOt, NCD0Z02A Wait and NCD0Z02B ReTx. Decoder B's word (NCDD05N1) sits at octets 153–156. The bit offsets reproduce the CLCW layout exactly; the 1-bit spare before the Report Value has no parameter. The 3-bit Status Field (NCD0Z023 PDEC_CLCW.A.Status, and NYGD0657 CLCW Status Field on the ground) carries no textual calibration, so the MIB gives it no mission-specific meaning; whether Solar Orbiter uses the field, as ECSS-E-ST-50-04C allowed, is not stated in the available sources.116100101
    • On the ground, the "Good", "Bad" and "Idle mini-transfer frame" packets (SPIDs 66980, 66981 and 66982, APID 1966, type 161, subtypes 5, 4 and 3) each decode a TM frame primary header (octets 0–5), the frame secondary header (octets 6–9), the OCF (octets 10–13) split into CLCW fields, and the FECF (octets 14–15); the Good packet adds the earth reception time. Each packet has its own parameter set: in the Good packet the OCF is NYGG0670 with CLCW fields NYGD0655 to NYGD0668, in the Bad packet NYGG0570 with NYGD0555 to NYGD0568, and in the Idle packet NYGG0770 with NYGD0755 to NYGD0768. Only the Good packet also carries per-VC copies, such as NYGDA663 VC1 Lockout and NYGDB663 VC2 Lockout, which are valid only when the CLCW VC Id parameter NYGD0659 equals 1 or 2; their textual calibrations read, for example, 0 = NO LOCKOUT, 1 = LOCKOUT. The Solar Orbiter data delivery ICD lists these packets as internally generated by the mission control system, to be filtered out by external users.101102

    Inference

    The mini-transfer-frame packets appear to be how the Solar Orbiter control system turns each received TM frame header and its CLCW into monitoring parameters, so that FOP-1 status and Lockout or Retransmit conditions can be displayed per TC virtual channel. Which ground element runs FOP-1 for Solar Orbiter (the SCOS-2000 telecommand chain or the station interface) is not stated in the available sources. The textual calibration of the on-board NoRF and NoBL fields maps raw 0 to "Asserted" and 1 to "Not_Asserted", which this wiki reads as "RF available asserted" in line with the CCSDS meaning of 0. The ground-side calibrations of the same flags support that reading: they map 0 to "RF" and 1 to "NO RF", and 0 to "BIT LOCK" and 1 to "NO BIT LOCK".100101

    EGSE heritage. In the SCOS-2000-based EGSE described by the EMCS user manual, each TC packet sent to the TC front end carries the virtual channel number, the MAP ID and the service (AD = 0, BD = 2). For an AD command the uplink acknowledgement (UL_Ack) reports whether the packet was confirmed through the processing of the CLCW; for a BD command it only reports whether the packet was completely sent. The NCTRS simulator of that EGSE includes a CLCW simulator.105104
