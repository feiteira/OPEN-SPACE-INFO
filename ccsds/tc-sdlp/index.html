    TC Space Data Link Protocol (CCSDS 232.0-B-4)¶

    The TC Space Data Link Protocol (TC-SDLP) is the CCSDS data link layer protocol for the forward link: it carries telecommands and other data from a ground station (or another spacecraft) to a spacecraft. Its protocol data unit is the variable-length TC Transfer Frame. In the uplink chain it sits below the network-layer Space Packet Protocol and above TC synchronization and channel coding, which wraps each frame into a CLTU for radiation. Its retransmission engine, COP-1, turns a noisy radio link into an in-order, gap-free and duplicate-free command channel, and its optional SDLS interface adds authentication and encryption.12

    Where TC-SDLP sits¶

    CCSDS divides the data link layer into two sublayers. TC-SDLP is the Data Link Protocol Sublayer and provides framing, multiplexing, segmentation and retransmission. The Synchronization and Channel Coding Sublayer below it provides error-correcting coding, delimiting of codewords and optional bit transition generation; for TC-SDLP that sublayer must be CCSDS 231.0 (TC coding and the CLTU).2 TC frames have variable length so that short messages can be received with little delay, which is the opposite choice from the fixed-length TM and AOS frames used on the return link.9

    The protocol has three duties: segmentation and blocking of user data units, transmission control (the retransmission performed by the Communications Operation Procedure) and sharing of one physical channel among many users through virtual channels and MAPs. Splitting large data units into small pieces improves throughput on a noisy link because only small pieces have to be resent; blocking does the opposite for very small units.12 The protocol does not establish or release connections, and it does not manage or configure SDLS.13

    Addressing: master, virtual and MAP channels¶

    Three identifiers in the frame header address a frame: the Transfer Frame Version Number (TFVN), the Spacecraft Identifier (SCID) and the Virtual Channel Identifier (VCID). Their concatenations define nested channels:14

    Identifier Composition Identifies Notes
    MCID (Master Channel Identifier) TFVN + SCID A Master Channel Usually one master channel per physical channel
    GVCID (Global Virtual Channel Identifier) MCID + VCID A Virtual Channel A VC is the set of frames with the same GVCID
    GMAP ID (Global MAP Identifier) GVCID + MAP ID A MAP Channel Only if the optional Segment Header is used
    Physical Channel Name Set by management A physical channel Not carried in any header

    All frames with the same MCID on a physical channel form a Master Channel. A physical channel may carry several master channels if they share the same TFVN.14 The Multiplexer Access Point Identifier (MAP ID) in the optional Segment Header subdivides one virtual channel into up to 64 MAP channels.15 The CCSDS overview report explains why two levels exist: virtual channels let one physical channel carry streams with different priority and latency, and MAPs do the same inside one virtual channel and also provide segmentation of data units that are longer than a frame.1617

    Service types: Type-A and Type-B¶

    Every data transfer service (except the two frame services) offers two service types, chosen per service data unit in the request primitive:19

    • Sequence-Controlled Service (Type-A). An Automatic Repeat reQuest (ARQ) procedure of the go-back-n type, with sequence control at both ends and a standard report (the CLCW) returned by the receiver. With high probability no data unit is lost, duplicated or delivered out of order. The guarantee holds per virtual channel and per MAP: data units sent on different virtual channels, or on different MAPs of one virtual channel, can arrive in a different order from the one in which they were submitted.20
    • Expedited Service (Type-B). Each data unit is sent once, without retransmission, and delivery is not guaranteed. It is meant for exceptional situations such as spacecraft recovery, or for use under a higher-layer protocol that retransmits by itself. Despite its name it is neither a faster nor a required way to send urgent data; if a reliable Type-A service is available it should be used.21

    The CCSDS overview report adds the operational view: COP-1 works well near Earth, where the round trip is short, but in deep space the sender waits a long time with an idle uplink before any automatic retransmission; systematic retransmission in the coding sublayer, a shorter COP-1 timer, or a higher-layer protocol can help.2224 The Type-B service is also the tool for blind commanding when no telemetry is available.23 ECSS-E-ST-50C requires a service that guarantees in-sequence delivery of telecommands, commanding in the blind, and a probability of accepting an erroneous telecommand below 10⁻² divided by the number of telecommands expected in the mission.25

    Mixing Type-A and Type-B on one MAP

    Some receivers do not distinguish Type-A from Type-B data at the receiving end. If both are used at the same time on one MAP channel, frames of a Type-B data unit can interleave with the segments of a Type-A data unit and prevent its reassembly. For such implementations the sending end should end any Type-A transfer before starting a Type-B transfer on the same virtual channel.26

    Services and primitives¶

    TC-SDLP provides six data transfer services and one management service. Two work on a MAP channel, three on a virtual channel, one on a master channel; the COP Management Service controls COP-1 of one virtual channel.27

    Service Service data unit Service types SAP address SDLS Primitives
    MAP Packet (MAPP) Packet with a CCSDS-authorised Packet Version Number A and B GMAP ID + PVN All features MAPP.request, MAPP_Notify.indication, MAPP.indication
    Virtual Channel Packet (VCP) Packet A and B GVCID + PVN All VCP.request, VCP_Notify.indication, VCP.indication
    MAP Access (MAPA) MAP_SDU (private format, any length) A and B GMAP ID All MAPA.request, MAPA_Notify.indication, MAPA.indication
    Virtual Channel Access (VCA) VCA_SDU (private format, fits one frame) A and B GVCID All VCA.request, VCA_Notify.indication, VCA.indication
    Virtual Channel Frame (VCF) Partially formatted TC Transfer Frame Not applicable GVCID None VCF.request, VCF.indication
    Master Channel Frame (MCF) Partially formatted TC Transfer Frame Not applicable MCID None MCF.request, MCF.indication
    COP Management Directives Not applicable GVCID Not applicable Directive.request, Directive_Notify.indication, Async_Notify.indication

    Table restated from table 2-1 and the primitive lists of §3.3 to §3.9.2728

    • MAPP and VCP carry packets. A user is identified by its PVN plus GMAP ID (or GVCID); packets of different versions can share a channel and are multiplexed into one stream. If the provider blocks several packets into one frame, it must know where the length field of each packet is, so that the receiver can cut them apart again.2930
    • MAPA carries privately formatted data units whose length is not limited by the frame size, because the MAP generation function segments them. VCA carries privately formatted units that must each fit into one frame data field. Only one user may use either service on a channel.3132
    • VCF and MCF let an independent, certified entity hand over frames that it built itself; the provider fills in what is missing. The Frame Error Control Field of such frames is empty when submitted, and the provider does not distinguish service types: the user has to provide Type-A or Type-B behaviour itself.3334
    • COP Management lets an authorised user drive FOP-1 with directives. Most directives only change the internal state of FOP-1; two of them generate Type-BC frames carrying the control commands Unlock and Set V(R).3536

    The request primitives carry the data unit, its address, a user-supplied SDU ID (echoed in later notifications) and the Service Type. Notifications report a Notification Type whose values are defined in COP-1. At the receiving end, packet services may add a Packet Quality Indicator (complete or partial packet), and, with SDLS, a Verification Status Code where a non-zero value means the security protocol detected an error in a frame addressed to the channel.37

    The Blue Book restricts which services may coexist:38

    1. If the MCF service exists on a master channel, no other data transfer service may exist on it.
    2. If the VCF, VCA or VCP service exists on a virtual channel, no other data transfer service may exist on that virtual channel.
    3. On one MAP channel, the MAPA and MAPP services are mutually exclusive.
    4. The COP Management Service may not coexist with the VCF service on the same virtual channel, nor with the MCF service.

    The TC Transfer Frame¶

    A TC Transfer Frame consists of a mandatory 5-octet primary header, a mandatory data field of up to 1019 octets (1017 if the Frame Error Control Field is present) and an optional 2-octet Frame Error Control Field (FECF). An implementation may support a lower maximum on a particular virtual channel.6 Because the frame length is variable, the header has to carry it; on the fixed-length TM frame this is not needed.39

    Transfer Frame Primary Header¶

    The primary header has eight fields in a fixed order and length:7

    Field Bits (position) Values Meaning and rationale
    Transfer Frame Version Number 2 (0–1) 0b00 Identifies the TC Version 1 asynchronous frame defined by this standard.40
    Bypass Flag 1 (2) 0, 1 0: Type-A frame, subject to the normal Frame Acceptance Checks of the FARM. 1: Type-B frame, acceptance checks bypassed. Frame Validation Checks apply in both cases.41
    Control Command Flag 1 (3) 0, 1 0: the data field holds a Frame Data Unit (Type-D, "data"). 1: it holds control information used to configure the FARM (Type-C).42
    Reserved Spare 2 (4–5) 0b00 Reserved for future use.43
    Spacecraft Identifier 10 (6–15) 0–1023 Assigned by the CCSDS Secretariat; identifies the spacecraft the data belongs to and does not change between mission phases.44
    Virtual Channel Identifier 6 (16–21) 0–63 Identifies the virtual channel. No numbering rule: VCs need not be consecutive.45
    Frame Length 10 (22–31) 0–1023 Length count C = total octets in the frame − 1, from the first header bit to the last bit of the FECF (or of the data field if there is no FECF). Caps a frame at 1024 octets.46
    Frame Sequence Number N(S) 8 (32–39) 0–255 Assigned by COP-1; lets the FARM check the order of Type-A frames. Maintained separately per virtual channel. COP-1 sets it to all zeros in Type-B frames.47

    The two flags combine into the three frame types that COP-1 knows:48

    Bypass Control Command Frame type Data field Use
    0 0 Type-AD Frame Data Unit, Frame Acceptance Checks applied Sequence-Controlled (AD) Service
    0 1 — — Reserved for future application
    1 0 Type-BD Frame Data Unit, acceptance checks bypassed Expedited (BD) Service
    1 1 Type-BC Control command, acceptance checks bypassed Controls the Sequence-Controlled Service

    Reading a header: Green Book example 1 (real bytes from the source)

    The CCSDS TC coding Green Book gives the Unlock frame 30 1B 00 07 00 00 4C A9 for spacecraft 0x1B, virtual channel 0.49 The first five octets decode as:

    Octets Bits Field Value
    30 00 1 1 00 00 Version, Bypass, Ctrl Cmd, Spare, SCID bits 6–7 Version 0, Type-BC frame
    30 1B ..00 0001 1011 Spacecraft ID (10 bits) 0x01B = 27
    00 07 000000 0000000111 VCID (6 bits), Frame Length (10 bits) VC 0, C = 7, so 8 octets
    00 00000000 Frame Sequence Number 0, as for every Type-B frame

    The remaining octets are the data field 00 (the Unlock command) and the FECF 4C A9. The field split is this wiki's reading of the published bytes.

    Transfer Frame Data Field and Frame Data Units¶

    The data field follows the header without a gap, contains a whole number of octets, and holds either one Frame Data Unit (FDU, Type-D frames) or control command information (Type-C frames).53 An FDU is either plain user data or a Segment Header followed by user data; an FDU with a Segment Header is called a Segment.5455

    Virtual channel configuration The user data of one FDU may be
    With Segment Header (MAPs in use) one complete packet, several packets, part of a packet, one complete MAP_SDU, part of a MAP_SDU
    Without Segment Header one complete packet, several packets, one complete VCA_SDU

    The Segment Header is required on any virtual channel that has more than one MAP, or that carries data units longer than one frame can hold. Otherwise it is optional, but once used on a virtual channel it must appear in every frame carrying an FDU on that channel. Its presence is a managed parameter of the virtual channel, and it never appears in frames carrying control commands.5556

    Segment Header and MAP channels¶

    Sequence Flags (bit 0, bit 1) Meaning
    0b01 First portion of a service data unit on one MAP
    0b00 Continuing portion of a service data unit on one MAP
    0b10 Last portion of a service data unit on one MAP
    0b11 No segmentation: one complete service data unit, or several complete packets

    The Sequence Flags give the position of the segment's user data inside the original data unit. The 6-bit MAP ID (bits 2–7) names the MAP channel; if a virtual channel uses the Segment Header but not several MAPs, the MAP ID is set to a constant. There is no numbering rule for MAP IDs.57 The ECSS handbook stresses that the flags carry no sequence count, so reassembly assumes that segments arrive in order and without gaps, and recommends the sequence-controlled service for any MAP that uses segmentation.58

    A segment carrying one packet (real bytes from the source)

    Green Book example 12 is a Type-AD frame (SCID 0x1B, VC 0, N(S) = 0) with the 11-octet data field C0 10 00 C0 00 00 03 2E AF 8A 06.51 In this wiki's reading, C0 = 0b11 000000 is a Segment Header (no segmentation, MAP 0) and the following ten octets are a Space Packet: primary header 10 00 C0 00 00 03 (version 0, telecommand, APID 0, standalone, data length field 3 so four data octets) and data 2E AF 8A 06.

    Control commands: Unlock and Set V(R)¶

    Type-BC frames carry one of two control commands. Their effect on the FARM is specified by COP-1:59

    • Unlock (0x00) takes the FARM of a virtual channel out of Lockout and clears its Wait and Retransmit flags; it does not change V(R).
    • Set V(R) (0x82 0x00 nn) sets the FARM's expected sequence number V(R) to nn. The value should be the N(S) that the sender will put into its next Type-A frame on that virtual channel.

    All other bit patterns are reserved by CCSDS.59136 The full FARM behaviour on each command, including the rule that Set V(R) is ignored (but counted) while the FARM is locked out, is on the COP-1 page.

    The control commands in the real Solar Orbiter MIB

    The Solar Orbiter MIB defines both control frames as commands with CCF_CTYPE = F ("control frame", a BC frame) and the special header NO_HDR, so their cdf entries describe the frame data field instead of a packet:6063

    Command Description (CCF_DESCR) Elements (cdf) Resulting data field
    UNLOCK FARM UNLOCK directive fixed area, 8 bits, value 0 00
    SETVR SETV( R ) Directive fixed area, 16 bits, value 8200; editable parameter VR, 8 bits, default 0 82 00 nn

    Fixed-area values in CDF_VALUE are hexadecimal, so 8200 is exactly the Set V(R) code.62 Both commands are flagged CCF_HIPRI = Y with no MAP ID. The SCOS-2000 ICD strongly recommends attaching BC-frame commands to a global interlock on at least the second uplink verification stage, so that no further commands leave the ground before AD mode is set up; in this release both have CCF_ILSCOPE = N (no interlock), and CCF_ILSTAGE = N, which is not one of the stage codes (R, U, O, A, C) that issue 7.0 of the ICD lists. Whether interlocking is handled elsewhere in the Solar Orbiter control system is not stated in the available sources.606163 See Commanding in the MIB for the full ccf and cdf description.

    Frame Error Control Field¶

    The optional FECF occupies the two octets after the data field. Its presence is set by management for the whole physical channel: if present, it is in every frame of that physical channel throughout a mission phase. It detects errors introduced during transmission and data handling; whether to use it depends on the required data quality and on the coding options chosen below.64

    The field is a systematic (n, n−16) cyclic redundancy code computed over the whole frame except the FECF itself:65

    \[\text{FECF} = \left[X^{16}\,M(X) + X^{(n-16)}\,L(X)\right] \bmod G(X), \qquad G(X) = X^{16} + X^{12} + X^{5} + 1, \qquad L(X) = \sum_{i=0}^{15} X^i\]

    M(X) is the frame without the FECF, most significant (first transmitted) bit first, and the L(X) term presets the shift register to all ones before encoding. At the receiver the syndrome \(S(X) = [X^{16}C^*(X) + X^{n}L(X)] \bmod G(X)\) over the whole received frame is zero when no error is detected.6566 The TC coding Green Book notes that the same CRC code is used in other CCSDS frames.67

    Implementation in a few lines (illustrative)

    A byte-wise implementation is: start with crc = 0xFFFF; for each octet b, crc ^= b << 8, then eight times shift left and XOR with 0x1021 whenever the bit shifted out was 1; keep 16 bits. This wiki checked that this gives the published FECF values of the Green Book examples, for example 4C A9 for 30 1B 00 07 00 00 and F6 F0 for 30 1B 00 09 00 82 00 00.4950

    The CCSDS overview report recommends the FECF whenever the error detection of the coding sublayer alone is not enough.68 The TC coding Green Book quantifies it: with the BCH code decoded in single-error-correction mode and no CRC, the probability of an undetected error in a 10-codeword frame is about 3.9 × 10⁻¹⁰ at a channel bit error rate of 10⁻⁵, while with the CRC it drops to about 1.2 × 10⁻²⁴.69 The ECSS handbook gives the same reasoning for making the field mandatory in the European standards, which always use SEC decoding (see ECSS adoption).8

    ECSS-E-ST-50-04C, which already made the FECF part of every TC frame, states what the code guarantees on an encoded block shorter than 32,768 bits (4096 octets, so any TC frame): every error pattern with an odd number of bit errors and every pattern of two bit errors is detected, every single burst of 16 bits or less is detected if no other error occurs in the block, and a random pattern with an even number of errors (four or more) escapes with a probability of about 2⁻¹⁵, roughly 3 × 10⁻⁵. It also forbids using the field for error correction, and its informative annex A draws the shift-register encoder and decoder with all register bits preset to one.154155

    The CLCW: the report returned to the sender¶

    The second protocol data unit of TC-SDLP is the Communications Link Control Word (CLCW), a 32-bit report from the FARM to the FOP. It is usually carried in the Operational Control Field (OCF) of TM or AOS frames on the return link; TC-SDLP does not specify how it is delivered. Each virtual channel in use has its own CLCW, and some minimum reporting rate is needed for COP-1 to work.70

    Every field, the meaning of each flag, how the FOP reacts to it and how Solar Orbiter exposes it in its telemetry are explained on the COP-1 page.70

    Blocking and segmentation rules in ECSS-E-ST-50-04C. The superseded ECSS standard spelled out a few blocking and segmentation rules in detail. All segments of one user data unit share the MAP and the service type, and the segmentation sublayer turns COP-1's per-frame confirmations into one result per user data unit: Positive Confirm only when every segment was positively confirmed, Negative Confirm when COP-1 signalled a Negative Confirm for one or more segments.151152153

    Systematic retransmissions¶

    The interface to the coding sublayer, ChannelAccess.request, has an optional Repetitions parameter: the coding sublayer sends the same data unit that many times. Management sets one value for frames carrying Type-A data and one for frames carrying COP control commands (Type-BC) on each virtual channel, and an upper limit per physical channel. Frames carrying Type-B data (Type-BD) are always sent with Repetitions = 1.7978 The mechanism targets deep-space links with long light times; its use and trade-offs are discussed on the CLTU page. The reception probability improves most when each data unit holds a single frame.78

    All Frames Reception: delimiting and fill removal¶

    The coding sublayer delivers the decoded octets of one CLTU, declared clean, together with a Data Start signal that stays true while it transfers octets and goes false (Data Stop) when decoding fails or the channel drops. The first octet after Data Start is the first octet of the first frame, so the receiver can delimit each frame by reading successive Frame Length fields.81 Then:82

    • if the octets received before Data Stop exactly match the Frame Length values, each frame goes on to validation;
    • if fewer octets arrived than the Frame Length announces, the incomplete frame is discarded;
    • if more octets arrived, the surplus is taken as fill added by the coding sublayer to complete the last codeword, and is discarded.

    The receiving coding sublayer cannot distinguish fill from data, so this protocol must strip it. With BCH coding there are at most six fill octets. Fewer than five cannot look like a frame header; five or six could, but the fill pattern 0x55 in a Frame Length position announces a frame longer than the octets received, so the validation checks reject it.82

    Frame Validation Checks¶

    Every reconstituted frame, Type-A or Type-B, must pass all of these tests or it is discarded:83

    1. an expected Transfer Frame Version Number;
    2. one of the expected MCIDs (version number and spacecraft ID);
    3. no header values inconsistent with the features implemented on that spacecraft;
    4. a Frame Length consistent with the number of octets present;
    5. if the FECF is present, a recomputed CRC equal to the received FECF.

    The SCID check matters because several spacecraft with identical RF characteristics may all decode the same uplink; only the addressed one accepts the frame. Since a corrupted frame can carry a corrupted SCID, the undetected error rate must be low enough to protect against accepting foreign data.84

    ECSS-E-ST-50-04C split the same work into three procedures that run in a fixed order on each candidate frame: frame delimiting and fill removal (discard if shorter than the 8-octet minimum or than its Frame Length, strip any surplus as fill), then the frame error control procedure (discard on a CRC error), then frame header validation (version 0b00, a valid Bypass/Control Command combination, the receiving spacecraft's SCID, a valid VCID, no values inconsistent with the implemented features). Virtual channel demultiplexing comes after delimiting and before FARM-1, its position relative to the other two being left to the implementation, and the VCID check may be done there.156157158 It adds a practical example: when virtual channels serve several telecommand units, demultiplexing can simply mean that each unit discards the frames not addressed to it.159

    Demultiplexing, FARM and delivery¶

    The master channel demultiplexer routes by MCID, the virtual channel demultiplexer by VCID (frames with an invalid VCID are discarded). The Virtual Channel Reception function runs the FARM, which performs the Frame Acceptance Checks on Type-AD frames, executes control commands from Type-BC frames and produces the values for the CLCW. FDUs from accepted Type-AD frames are delivered only after passing the acceptance checks; FDUs from Type-BD frames are delivered immediately.8586 The MAP demultiplexer routes FDUs by MAP ID and discards invalid ones. The MAP Packet Extraction function rebuilds packets using the Sequence Flags and, when blocking is allowed, the packet length fields, and delivers them by PVN; incomplete packets need not be delivered in cross support. The MAP Reception function rebuilds MAP_SDUs, and VC Packet Extraction splits blocked packets with their length fields.878889

    The SDLS option¶

    A TC-SDLP entity may optionally support the Space Data Link Security protocol, which provides authentication and confidentiality at the data link layer. The choice is made per virtual channel, or per MAP when Segment Headers are used, through managed parameters; a channel without SDLS uses exactly the frame format above.9697

    • The primary header and the Segment Header are unchanged; the Segment Header stays outside the security envelope, and the Security Header follows it (or the primary header if there is no Segment Header).98
    • The maximum data field length becomes 1024 octets minus the primary header, Security Header, and, when present, Segment Header, Security Trailer and FECF.99
    • Type-C frames (Unlock, Set V(R)) never carry SDLS fields.98
    • The FECF follows the Security Trailer, or the data field if there is no trailer.100

    Order of processing. At the sending end the Virtual Channel Generation function runs Frame Initialisation (leaving room for the security fields), then the SDLS ApplySecurity function, then FOP-1, then Frame Finalisation, which writes the values from ApplySecurity into the header and trailer.101 At the receiving end FARM-1 runs first, then the SDLS ProcessSecurity function (verify the MAC, decrypt), then delivery. A frame rejected by ProcessSecurity is discarded, and the Verification Status Code may inform the user; SDLS errors are reported back in a Frame Security Report carried in the return-link OCF.10211103

    Anti-replay and mixed AD/BD traffic

    With authentication, a retransmitted Type-AD frame has a lower anti-replay sequence number than a Type-BD frame sent in between, so the receiver's anti-replay check rejects the retransmission and reports it, wrongly, as a security failure. Mixing Type-AD and Type-BD frames on one SDLS-protected virtual channel is therefore not advised, unless BD frames are sent only after all AD frames have been accepted. Several virtual channels sharing one SDLS Security Association is not supported.102104

    The additional managed parameters are, per virtual channel (without Segment Headers) or per MAP: presence of the Security Header, presence of the Security Trailer, and the length of each in octets. If the Security Header is present, SDLS is in use for that channel.105

    The PSS-04-107 roots. Annex B of ECSS-E-ST-50-04C compares it with ESA's Packet Telecommand Standard PSS-04-107 (issue 2, April 1992). Within the scope of this page it lists:149

    • PSS-04-107 used TC Segments on every virtual channel, had no packet blocking, and assumed a transfer layer below its Segmentation Layer.
    • It defined telecommand authentication with an optional Segment Trailer; ECSS-E-ST-50-04C left authentication out of scope and dropped the trailer (CCSDS now offers SDLS).
    • Its frames were at most 256 octets: the Frame Length occupied bits 24–31 and bits 22–23 were a reserved field. ECSS-E-ST-50-04C widened the field to bits 22–31 and notes that frames built to the earlier definition remain valid.150
    • It specified the older COP-1A; ECSS-E-ST-50-04C specifies COP-1B, which differs only at the sending end (see COP-1).
    • Field names changed: Frame Header became Transfer Frame Primary Header, Version Number the Transfer Frame Version Number, Reserved Field A the Reserved Spare, Reserved Field B part of the Frame Length, and Frame Data Field the Transfer Frame Data Field; "Command" became "Communications" in COP-1, CLCW and CLTU.

    Packet Assembly Controller and MAP Reset¶

    The PAC, inherited from an older ESA PSS standard, reassembles packets or MAP_SDUs and handles exceptions.119 Each PAC instance uses a pair of MAP IDs: the data MAP has its most significant bit at 0 (0 to 31) and the control MAP has the same low five bits with the MSB at 1, so control MAP = data MAP + 32.113114 The PAC keeps a reassembly status flag and a lockout flag, reports both (with the data MAP ID) to the sending end in a format the standard does not fix, and enters lockout when it sees an invalid control segment or one of these illegal Sequence Flag successions:115116

    Previous segment Followed by Result
    First 01 First 01 or Unsegmented 11 Lockout
    Continuing 00 First 01 or Unsegmented 11 Lockout
    Last 10 Continuing 00 or Last 10 Lockout
    Unsegmented 11 Continuing 00 or Last 10 Lockout

    In lockout the PAC delivers nothing until it receives a MAP Reset command: a one-octet control segment consisting only of a Segment Header with Sequence Flags 0b11 and the control MAP ID. On a MAP Reset the PAC discards any partial data unit, clears the reassembly flag and leaves lockout. It is used, for example, to recover after link breaks or aborted transfers.117118 The ECSS handbook explains the consequences: the minimum segment length becomes one octet instead of two, each PAC uses up two MAP IDs, European hardware implements the PAC, European missions generally do not use segmentation, and the one-octet control segment can affect interoperability, for example with the SLE Forward Space Packet service.119120

    The adoption notice re-inserts into the CCSDS book what ECSS-E-ST-50-04C §5.5.4 already specified, with the same MAP pairing, flags, lockout successions, status report and MAP Reset; both texts note that the name "packet" assembly controller is inherited from earlier standards and that the function serves any data unit carried in segments. The 2008 text adds a few clarifications that the notice does not repeat: it reassembles from the Sequence Flags and the segment lengths alone, without reading any length field inside the user data; its lockout has nothing to do with the FARM-1 Lockout state; it is not used at all when segmentation is off; and no service type (sequence-controlled or expedited) is prescribed for sending a control segment.160152113

    MAP Reset in the real Solar Orbiter MIB

    The MIB defines the command RESET "PAC RESET directive" with CCF_CTYPE = R (control segment, "Reset Map Command") and three elements: a 2-bit fixed area 3, a 1-bit fixed area 1 and an editable 5-bit parameter RESETMAP with default 1.121 That is exactly a Segment Header 0b11 + 1 + 00001, the octet 0xE1: Sequence Flags "no segmentation" and control MAP 33, paired with data MAP 1, the MAP of normal Solar Orbiter commands. Two other R commands, REIN_TTR "Reinit TTR" and TC_ONLY "CPDU TC_Only", are one-octet segments with MSB 0 and MAP IDs 5 and 6 (octets 0xC5 and 0xC6).121

    Which VCIDs? A wording inconsistency in the ICD

    The ICD requirement on the TC Virtual Channel ID still says that "the suggested values are Zero and One" but then lists VC1 = 0b000001 and VC2 = 0b000010. Its change record (in which the extracted text runs deleted and inserted words together) appears to show that the values were changed from VC0/VC1 to VC1/VC2 without updating that sentence; it also contains a note, not present in the current requirement text, that called the values provisional until RUAG provided definitive ones.122130 This reading of the change record is this wiki's. This page uses 1 and 2, which is also what the MIB expects: its per-VC CLCW monitoring parameters (for example NYGDA663 VC1 Lockout) are valid only when the CLCW VC Id equals 1 or 2.131 Avoiding the all-zeros VCID also follows the ECSS handbook, which advises against all-zeros and all-ones TC VCIDs because a failed or unpowered decoder can produce such CLCWs.132

    Giving each decoder its own virtual channel matches the example that ECSS-E-ST-50-04C gives of virtual channel demultiplexing, in which each telecommand unit discards the frames not addressed to it; the Solar Orbiter ICD says only that the two VCIDs address the two decoders.159122

    The CPDU in the on-board computer can generate command pulses directly from ground telecommands received on MAP 0 (HPC-1 commands), without the central software, so that vital units can be switched on or off even when the software is not running.124125 This is the data-link half of the ECSS requirement that essential telecommands be decodable and distributable when all other systems, including the CDMU, are non-operational.126 In the MIB the 125 CPDU commands (for example ZBC04001 "Select PM A EEPROM Image 1") carry CCF_HIPRI = Y and CCF_MAPID = 0 on APID 44. In the ICD a telecommand APID is a 7-bit process ID followed by a 4-bit packet category fixed to 12, so 44 is process ID 2, which the APID plan assigns to the on-board computer hardware for "High Priority TC Functions to CPDU (MAP ID = 0)".127129128 In the SCOS-2000 database, CCF_HIPRI = Y means that the MAP ID is forced to the value in CCF_MAPID, that the command cannot be time-tagged on board and that it cannot be blocked with other commands; CCF_MAPID is ignored for all other commands.133 The same five frame-level commands and 125 CPDU commands are present in the April 2020 release.134

    Inference

    Solar Orbiter's maximum TC packet is 6 + 242 = 248 octets.135 A 256-octet frame holds 256 − 5 (header) − 2 (FECF) − 1 (Segment Header) = 248 octets of segment data, so one maximum-size packet fills one maximum-size frame exactly. The arithmetic is this wiki's and assumes the FECF is present, as ECSS requires; the ICD pages read for this page do not state the FECF use explicitly.

    Relationship to other standards¶

    • COP-1 (CCSDS 232.1-B-2) is the normative specification of FOP-1 and FARM-1; where the TC-SDLP text and COP-1 differ, COP-1 prevails.137
    • TC synchronization and channel coding (CCSDS 231.0) must be used below TC-SDLP; all frames of a physical channel use the same coding options, chosen so that the probability of misidentifying MCID, VCID or MAP ID, and of rejecting frames, stays below mission-specified values. One request to that sublayer hands over one or more TC frames, which become one CLTU; in ECSS it is always exactly one frame.138139161 The 2026 corrigendum of CCSDS 231.0-B-4 lists changes only to the optional LDPC (128,64) tail sequence (§5.2.4.2), so this interface is unchanged.162
    • TM and AOS frames carry the CLCW back in their OCF. A Type-1 report (type flag 0) in the OCF is a CLCW; a Type-2 report may carry an SDLS Frame Security Report.103
    • USLP can also run COP-1 and uses the same coding sublayer.140
    • SLE Forward CLTU delivers the CLTUs built from these frames to the ground station; the CCSDS services described here may be extended on the ground by SLE services.141
    • PUS telecommand packets are the usual content of TC frames; see ST[02] Device access for software-distributed CPDU commands.
    • HDLC is the obvious terrestrial comparison. The CCSDS overview report explains the difference: space data link protocols assume strong coding and synchronization underneath and keep frame formats compatible with traditional receiving equipment, while HDLC was designed for nearly error-free wire links.142
