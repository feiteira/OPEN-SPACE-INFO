    TC synchronization and channel coding: the CLTU (CCSDS 231.0-B-4)¶

    Before a TC Transfer Frame is radiated it passes through the Synchronization and Channel Coding Sublayer. This sublayer adds error-control coding, makes the start of the data recognisable in a continuous bit stream, keeps enough bit transitions for the receiver's bit synchroniser, and optionally repeats the transmission. Its data unit is the Communications Link Transmission Unit (CLTU): a Start Sequence, an integer number of codewords, and a Tail Sequence. The same Recommended Standard also defines the Physical Layer Operations Procedures (PLOP-1 and PLOP-2) that the transmitter follows to switch the carrier, the acquisition and idle patterns and the CLTUs on and off.123

    This page follows CCSDS 231.0-B-4 (Blue Book, July 2021) with its Technical Corrigendum 1 (July 2026), which replaces the optional LDPC tail sequence, and the companion Green Book CCSDS 230.1-G-3 (October 2021), which explains the rationale and gives performance data and worked examples. For the European side it uses the superseded standard ECSS-E-ST-50-04C (31 July 2008), the adoption notice ECSS-E-AS-50-24C Rev.1 (13 January 2023) that replaced it, the ECSS communications handbook, and the Solar Orbiter documentation and MIB.41295135154

    Architecture and functions¶

    The sublayer sits between the data link protocol sublayer (TC-SDLP or USLP) and the physical layer, whose main specification is the CCSDS radio frequency and modulation standard (see Radio frequency, modulation and ranging).2 It provides four functions:1314

    • error-control coding with either the modified BCH code or one of two LDPC codes; the BCH code can be decoded in an error-detecting or an error-correcting mode, while the LDPC codes are typically decoded from soft symbols and work at a lower signal-to-noise ratio;
    • synchronization through the CLTU, whose Start Sequence can also resolve the ambiguity between 0 and 1 when the modulation does not; plus the PLOP for activating and deactivating the physical channel;
    • pseudo-randomizing (optional with BCH) to raise the bit transition density;
    • repeated transmissions (optional), requested through the service interface.

    The Green Book lists the purposes behind these functions: protect the data against corruption on the link, mark its start and end so the receiver can find it, let the receiver resolve the sense of 1 and 0, let it acquire bit synchronization with an acquisition pattern and keep it during data and between data units. One instance of the sublayer serves one physical channel.15

    Service interface¶

    The sublayer offers one unidirectional service per physical channel, with a single user; frames from different users are not multiplexed at this level.19 Two primitives exist:20

    • ChannelAccess.request (Frame(s), Repetitions) at the sending end. Frames is one or more TC Transfer Frames, or a single USLP frame. Repetitions is optional; when supported it is an integer ≥ 1 giving the total number of times the CLTU is transferred (3 means three transfers, not four). With Repetitions > 1 the frames should not include Type-BD frames, and the option should be limited to links with long light time.2122 In ECSS the Frames parameter is narrowed to one TC Transfer Frame or a single USLP frame; ECSS-E-ST-50-04C had neither a formal service interface nor the Repetitions parameter.157162
    • ChannelAccess.indication (Frames) at the receiving end. The delivered Frames may contain an incomplete frame or trailing fill, which the data link protocol discards.2123

    One request produces one CLTU, and the sublayer does not look at frame boundaries or length fields: to it, the Frames parameter is one block of data.24 The Green Book describes an equivalent interface at the receiving end in terms of a Data Start signal, true while octets of a CLTU are being delivered and false (Data Stop) after a decoder failure or loss of the channel.25

    The BCH code¶

    Codeword format¶

    A BCH codeword is 64 bits long: 56 information bits (randomized if the randomizer is used), the complements of 7 parity bits, and one filler bit that is always 0, so that the codeword is a whole number of octets.6

    The parity bits are complemented to help maintain bit synchronization and to detect bit slippage.6 The ECSS handbook gives the reason this matters: an all-zero frame encoded without randomization produces codewords of 56 zeros, 7 ones and a zero, a square-wave-like pattern with long runs that transponders can fail to track.26

    Encoding¶

    The code is a systematic (63,56) modified Bose-Chaudhuri-Hocquenghem code with generator polynomial27

    \[g(x) = x^7 + x^6 + x^2 + 1\]

    The encoder shift register starts at zero; the 56 information bits pass straight through while the register computes the remainder, then the 7 parity bits are shifted out, complemented, and the filler bit is appended.27 The Green Book explains the choice. A basic Hamming code with 6 check bits has 63-bit codewords, 57 information bits, minimum distance 3 and generator \(g_1(x) = x^6 + x + 1\); keeping only its even-parity codewords gives the expurgated (63,56) code with \(g(x) = g_1(x)\,(x + 1) = x^7 + x^6 + x^2 + 1\) and minimum distance 4. Used for detection it detects up to three errors and every odd number of errors; used for correction it corrects one error and detects two.11

    Earlier CCSDS recommendations also allowed 40, 48 and 56-bit codewords with the same 8-bit error control field; they were dropped in June 2000 because the 64-bit codeword is the most efficient:28

    Codeword length Data bits Bandwidth overhead
    64 bits 56 14 %
    56 bits (obsolete) 48 17 %
    48 bits (obsolete) 40 20 %
    40 bits (obsolete) 32 25 %

    Fill data¶

    The frames are cut into 7-octet pieces, ignoring frame boundaries. If the last piece is short, fill completes the last codeword: alternating bits starting with 0, so each fill octet is 0x55. Only the last codeword of a CLTU can contain fill, at most six octets. Fill is not removed by the decoder; the data link layer removes it when it delimits the frames. With randomization, fill may be added before or after randomizing; either way the receiver derandomizes it, so unrandomized fill does not come out as 0x55.293031

    Decoding modes: TED and SEC¶

    The receiver decodes BCH codewords in one of two modes, chosen per physical channel:3233

    • Triple Error Detection (TED), the error-detecting mode: any detected error rejects the codeword. One, two or three errors are always detected. No error is accepted in the Start Sequence.
    • Single Error Correction (SEC), in full Single Error Correction and Double Error Detection: one error is corrected, two are detected. One error is accepted in the Start Sequence.

    ECSS uses only the second mode: ECSS-E-ST-50-04C mentions TED but specifies SEC, and ECSS-E-AS-50-24C Rev.1 rewrites §3.5 of the Blue Book so that BCH codewords shall be decoded in SEC mode.146158

    In both modes the received filler bit is ignored.3435 A TED decoder can simply recompute the parity from the first 56 bits and compare it with the inverted next 7 bits. A SEC decoder computes the 6-bit Hamming syndrome (with \(x^6 + x + 1\)) and an overall parity bit (the \(x + 1\) factor) and decides as follows:3436

    Parity of errors (EOD output P) Syndrome non-zero (SB) Decision
    even (0) no (0) No error detected: accept
    even (0) yes (1) Even number of errors: reject the codeword
    odd (1) no (0) Odd number of errors in an apparently correct codeword: reject
    odd (1) yes (1) Single error: correct it at the position found by the syndrome, accept

    Correction lowers the rejection rate but increases undetected errors: in SEC mode a codeword with three errors can be "corrected" into one with four, a case TED mode would have detected. The Green Book's exhaustive simulation shows all 63 single errors corrected, all 1953 double errors detected, and of the 39,711 triple errors none undetected in TED but 39,060 undetected in SEC; four errors escape both modes in 9,765 of 595,665 cases.3738 This is why the Frame Error Control Field is particularly advisable with SEC.39

    An obsolete Filler Bit Augmentation algorithm once used the filler bit (always 0 in a codeword but 1 at the end of the tail) to inhibit correction and so recognise the old tail pattern more reliably. The current tail pattern is one bit further from the nearest codewords, so the algorithm is no longer part of the standard.40

    The LDPC codes¶

    LDPC codes give more coding gain than the BCH code. Two systematic, rate-½ binary codes are defined, (n = 128, k = 64) and (n = 512, k = 256). Both are transparent, so phase ambiguity can be resolved from the Start Sequence or after decoding, and their undetected error rates lie orders of magnitude below their detected error rates, especially with the FECF. Because LDPC coding alone does not guarantee enough bit transitions, the pseudo-randomizer is mandatory with it.7

    Structure. Each code is defined by an m × n parity-check matrix H built from M × M blocks, with M = k/4 = n/8 (16 for the short code, 64 for the long one): identity, zero and powers of Φ, the first right circular shift of the identity, added modulo 2. An encoder maps k information bits to an n-bit codeword satisfying all m = n − k parity checks. Codewords may be generated either by multiplying with a block-circulant generator matrix derived from H, or from the hexadecimal rows of the dense matrix W given in the standard, with the other rows obtained by circular shifts.4142 For the (128,64) code the four defining rows of W are:42

    W row Hexadecimal value
    1 0E69 166B EF4C 0BC2
    17 7766 137E BB24 8418
    33 C480 FEB9 CD53 A713
    49 4EAA 22FA 465E EA11

    Design rationale. Uplinks now carry far more than short commands: software and FPGA reloads, file uploads, even crew video. The Green Book sorts the uses into four modes and states that the TC codes target the first two; for the others some missions have used the TM LDPC codes:43

    Mode Purpose Block length (kb) Throughput (kb/s)
    A Emergency 0.1 0.01
    B Command / ARQ 0.1–1 1–4
    C File upload 1–4 1000
    D Human support > 4 20000

    Rate ½ balanced complexity, gain and the number of parity bits to store and send. Binary codes were chosen over non-binary GF(256) codes, which are 1.0 to 1.3 dB better, because the decoder is on board where complexity counts. A protograph-plus-circulant construction allows fast, simple encoders and well-structured decoders, with circulants chosen by a variant of Progressive Edge Growth. The minimum weight of the (128,64) code is 14 (16 codewords of that weight) and of the (512,256) code about 40.4445 The LDPC codes work at a lower SNR than BCH because of the lower rate (½ instead of 0.89), soft-decision decoding (a rule of thumb of about 2 dB) and longer codewords; the spacecraft receiver then has to hold symbol synchronization at a lower SNR.12

    Fill and randomization. Fill (0x55 pattern) is added before encoding and is encoded and randomized with the frame.46 The randomizer is placed after the encoder because the codes are quasi-cyclic: a codeword shifted by one symbol, as after a slip of the receiver's tracking loop, can look like another valid codeword and be mis-corrected; randomizing the codeword prevents this. Unlike TM, there are no synchronization markers between codewords, since synchronization is established at the start of each CLTU.17

    Inference: how much LDPC fill?

    A (128,64) codeword carries 8 octets of information, so at most 7 octets of fill are needed. A note in the Green Book says there may be "up to 7 octets or 15 octets" of fill depending on the code.47 For the (512,256) code, whose information block is 32 octets, the maximum should be 31 octets, and the Green Book's own annex F2 example 2 adds 26 fill octets to a 70-octet frame to fill three (512,256) codewords.83 This wiki therefore reads "15 octets" as an error in that note; the sources do not say so explicitly.

    Decoding. Soft symbols are recommended (about 2 dB better), but belief-propagation decoders also work on hard symbols; the Green Book discusses flooding, layered and Most Reliable Basis decoders.4849

    The CLTU¶

    The CLTU carries the codewords as one contiguous series. Its contents are the frame or frames from the layer above, plus any fill.50

    Start Sequence¶

    The Start Sequence delimits the start of the encoded data.8

    Coding Pattern Hexadecimal Inverse (for ambiguity resolution)
    BCH 1110 1011 1001 0000 (16 bits) 0xEB90 0x146F
    LDPC 64 bits 0x0347 76C7 2728 95B0 0xFCB8 8938 D8D7 6A4F

    Patterns from §5.2.2; inverses from the Green Book.851 Both patterns have low autocorrelation side lobes, so a shifted or partial match is unlikely, and they are clearly distinct from the acquisition and idle patterns: six bit errors (five if one error is tolerated) would be needed to turn part of an idle sequence into the BCH Start Sequence.5253 The LDPC sequence is longer for better detection at low SNR.17 If the physical layer cannot tell 1 from 0 (with some modulations), the receiver searches for both the pattern and its inverse, and on finding the inverse it inverts all following bits until it next returns to the search.5451

    Tail Sequence¶

    With BCH coding, the 64-bit Tail Sequence 0xC5C5C5C5C5C5C579 (seven octets 0xC5 and one 0x79) is built to be an uncorrectable pattern, so that it stops the decoder.9 It has the length of a codeword. Without errors it has odd parity and a zero syndrome, and with one error even parity and a non-zero syndrome, so it is rejected in both modes; it is missed only when channel errors turn it into an acceptable codeword: 651 of the 39,711 three-error patterns (both modes), and in SEC mode all 1953 two-error patterns.5556 The resulting probabilities of missing it are, at a channel bit error rate of 10⁻⁵, about 6.5 × 10⁻¹³ in TED mode and 1.95 × 10⁻⁷ in SEC mode.57

    History: before November 1995 the tail was alternating 0x55 octets, which was easier to miss; the shorter tails of the obsolete codeword lengths disappeared in June 2000.58 ECSS-E-ST-50-04C specified the current pattern (seven 0xC5 octets and a final 0x79, the length of one codeblock), and its annex B lists a different tail bit pattern among the changes from ESA PSS-04-107.142138

    With LDPC coding a conventional decoder reliably fails when it runs past the end of a CLTU, which ends the CLTU without a tail. For the (128,64) code an optional 128-bit tail exists for decoders that do not have that property; it can be found by decoder failure or by pattern matching before derandomization. The (512,256) code never uses a tail.959130

    Technical Corrigendum 1 to CCSDS 231.0-B-4 (July 2026) lists changes to §5.2.4.2 only. It replaces the first 64 bits of the optional (128,64) tail, puts a number on how reliably the tail and a decoder over-run stop decoding, and adds a note that gives the tail as the decoder sees it:129130134

    Note 3 makes explicit how the tail meets the randomizer. The sending end never randomizes the Start or Tail Sequence, but a receiver that treats the 128 symbols after the last codeword as one more codeword derandomizes them first, with the BTG reset to all ones as at every codeword.6667 The value in note 3 is exactly the tail XORed with the first 128 bits of the BTG sequence (FF 39 9E 5A 68 E9 06 F5 6C 89 2F A1 31 5E 08 C0): 63 ⊕ FF = 9C, A1 ⊕ 39 = 98, and so on, and the unchanged second half 55 … 55 becomes 39 DC 7A F4 64 0B 5D 95 in both issues. This wiki generated the BTG octets from the polynomial of the randomizer section and reproduced all 16 octets of note 3.13064 The corrigendum does not say why the old pattern was replaced.

    Inference: what the corrigendum changes in practice

    A receiver that relies on its LDPC decoder failing at the tail is affected only through the stated probabilities. A receiver that detects the tail by correlation before derandomization (allowed by note 2 of §5.3, which also asks for the 1/0 ambiguity to be handled) must look for the new pattern, while equipment built to the 2021 text, or tested against Green Book annex F2 example 1 (see below), uses the old one. The managed parameter "Tail Sequence: Used, Not used" and the reception logic with event E5 are unchanged, so nothing in the managed parameters identifies which pattern a link uses; the two ends of a cross-support link have to agree on the issue. ECSS-E-AS-50-24C Rev.1 (January 2023) applies CCSDS 231.0-B-4 of July 2021, before the corrigendum; whether ECSS will adopt it is not stated in the available sources. BCH links and the (512,256) code are untouched.13333154

    One frame per CLTU in ECSS practice

    CCSDS allows several TC frames in one CLTU. ECSS-E-ST-50-04C (2008) required exactly one: when the sublayer above is the transfer sublayer, the codeblocks of a CLTU carry a single TC Transfer Frame.141139 The handbook gives the reasons: more codewords per CLTU raise the rejection probability, and European on-board hardware did not support several frames per CLTU in its frame delimiting procedure.62 For systematic retransmissions the Blue Book also advises a single frame per CLTU: losing one frame loses all following frames of the same CLTU.22 The rule survives in the current adoption notice: ECSS-E-AS-50-24C Rev.1 rewrites note 2 of the Transfer Frame definition and the Frames parameter of annex A3, so that the service data unit is one TC Transfer Frame or a single USLP Transfer Frame.157 ECSS-E-ST-50C Rev.1 (March 2021) lists ECSS-E-AS-50-24 as based on CCSDS 231.0-B-3 and as superseding clauses 8 and 9 of ECSS-E-ST-50-04C; that was true of the notice's first issue of 1 March 2021, while Rev.1 of 13 January 2023 applies 231.0-B-4.81155 The other ECSS choices are compared below.

    The pseudo-randomizer¶

    To keep bit synchronization the receiver needs a minimum bit transition density, so the data must be "sufficiently random". The pseudo-randomizer is the preferred way to achieve this for every CCSDS-recommended combination of modulation and coding. With BCH it is required unless the designer verifies correct operation without it; its use is fixed and known in advance for a physical channel (a managed parameter, never signalled). With LDPC it is always applied.63

    The random sequence comes from the Bit Transition Generator (BTG), an 8-stage shift register preset to all ones, with polynomial64

    \[h(x) = x^8 + x^6 + x^4 + x^3 + x^2 + x + 1\]

    The sequence repeats every 255 bits (2⁸ − 1, the maximum for an 8-bit register) and starts 1111 1111 0011 1001 1001 1110 0101 1010 0110 1000, that is FF 39 9E 5A 68. Randomizing is an exclusive OR, so derandomizing is the same operation.6465

    Fill Randomized or not, as the implementation chooses Randomized with the frame
    Receiving end XOR the 56 information bits of each successfully decoded codeword; BTG held at all ones until the Start Sequence is found and reset after any decoding failure XOR (or sign-flip of soft symbols) on each noisy codeword before decoding; reset after each codeword

    After a rejection without a tail in use, the search must restart at the beginning of the rejected codeword (it may hold the next Start Sequence); with a tail it may restart after it.     ECSS-E-ST-50-04C described the same machine for BCH only, as the "channel logic" with three states and four events (no E5), and added two exits from DECODE: a CLTU whose number of codeblocks exceeds an implementation-dependent upper limit is abandoned and the receiver returns to SEARCH, and if the channel stays active but no data arrive because the symbol clock is lost, the CLTU is abandoned and the receiver goes to INACTIVE.145 The CCSDS state tables have no such exits; the book only makes the Maximum CLTU Length a managed parameter of the physical channel, which limits what the sending end may put into one CLTU.733324

    What the data link layer receives is not yet clean frames: fill has not been removed, the last frame may be truncated, nothing has been validated, and the Spacecraft ID has not been checked.     Probability of losing a CLTU¶

    The Green Book defines the target service as at most one rejected frame in 10³ (the command threshold) and at most one undetected erroneous frame in 10⁹.84 At system level, ECSS-E-ST-50C requires the probability of accepting an erroneous telecommand to stay below 10⁻² divided by the number of telecommands expected in the mission.79 Some of its figures, at a channel bit error rate of 10⁻⁵:8586878288

    The trade-off is plain: SEC rejects thousands of times fewer CLTUs, at the cost of an undetected error rate that only the CRC brings back to negligible levels. ECSS-E-ST-50-04C therefore always used SEC, always accepted one error in the Start Sequence, and made the FECF mandatory; its annex E lists these, with the randomizer and the single frame per CLTU, as physical channel parameters "fixed by the requirements" of the standard.899091153

With BCH coding and frame error control the probability of an undetected frame error can be kept below 10⁻¹⁸, and below 10⁻⁸ without it.80

    Synchronization lockout with PLOP-2

    If the receiver misses a Start Sequence (or a codeword fails) it searches while the rest of the CLTU is still arriving. A chance Start Sequence pattern across the last bits of the last codeword and the first bits of the tail then sends it into DECODE at the wrong place; the next 64 bits it tries to decode are the rest of the tail and, when no idle sequence follows, the beginning of the next Start Sequence, so the following CLTU is lost. A minimum one-octet Idle Sequence between CLTUs removes the risk, and the SLE Forward CLTU service has a parameter for the idle duration after a CLTU. The risk is higher when one Start Sequence error is accepted or when the inverse pattern is also searched.99102

    The Green Book adds that the PLOP has no formal service interface in the standard, and points to the SLE Forward CLTU service as a useful model, citing as an example its minimum delay between one CLTU and the next.103 The configuration parameters of that service include plop-in-effect, acquisition-sequence-length, plop-1-idle-sequence-length, minimum-delay-time, maximum-cltu-length and the CLCW-based rf-available-required and bit-lock-required checks.104

    For ECSS missions, ECSS-E-ST-50-04C fixed several of these options: PLOP-2 should be used in preference to PLOP-1 (which it kept for completeness, for ground systems and for cross support), an idle sequence of at least 8 bits between CLTUs, an acquisition sequence of at least 128 bits, and a mandatory No Bit Lock flag.105106107108147149 The adoption notice ECSS-E-AS-50-24C Rev.1 carries the length rules over as requirements on CCSDS 231.0-B-4: §7.2.2 gets a minimum Acquisition Sequence of 16 octets instead of a preferred minimum, §7.2.4 an Idle Sequence of at least 8 bits, and §7.5.2 turns the recommended one-octet Idle Sequence between PLOP-2 CLTUs into a "shall". It does not modify §7.1, so the CCSDS rule of PLOP-2 for missions planned after September 2010 applies unchanged; the No Bit Lock rule now sits in the TC-SDLP adoption notice.16010163

    Repeated transmissions¶

    Systematic retransmission, added in 2010, is an optional feature of the sending end only; the receiving sublayer is unaffected. The standard does not say how it is implemented (generate once and send N times, or regenerate each time).109110 It complements the automatic go-back-n retransmission of COP-1, which is efficient near Earth but leaves the uplink idle for most of a deep-space round trip.111112

    Option Pattern for frames A to F Strength Weakness
    Systematic retransmission, Repetitions = 3 AAABBBCCCDDDEEEFFF Sporadic losses rarely hit all copies of one frame A burst can wipe out all copies of one frame
    Early COP-1 retransmission (short T1) ABCDEF ABCDEF ABCDEF Resists bursts An early loss in a cycle causes the rest of that cycle to be rejected

    After §10.3.3 of the Green Book.113114 Neither is universal; mission designers may combine them and optimise patterns and repetition factors by simulation.     Reading the first codeword: seven frame octets, then A4 = 1010010 0, that is the complemented parity 1010010 (true parity 0101101) and the filler bit 0. The 8-octet frame needs ⌊(8 + 6)/7⌋ = 2 codewords, the second holding the last frame octet A9 and six fill octets, for a 26-octet CLTU. In the randomized CLTU the first octet CF is 30 XOR FF and the second 22 is 1B XOR 39, the first two octets of the BTG sequence; the parity octet is recomputed over the randomized data, and the fill keeps its 0x55 value.12064

    Reproducing the examples

    This wiki implemented the CRC-16 FECF, the BCH encoder (register preset to zero, parity complemented, filler 0) and the BTG, using the recurrence \(s_{n+8} = s_{n+6} \oplus s_{n+4} \oplus s_{n+3} \oplus s_{n+2} \oplus s_{n+1} \oplus s_n\) from an all-ones start, which reproduces FF 39 9E 5A 68, and checked them against Green Book examples 1, 2, 6, 12 and 15, both unrandomized and randomized: all codewords match.120121122123124

    Real LDPC CLTUs from the Green Book¶

    Annex F2 of the Green Book gives sending-end test vectors for the LDPC codes. Because only the sending end is standardized, and an error-correcting decoder can hide implementation errors, it recommends testing interoperability by checking that two encoders produce identical output symbol by symbol. Example 1 uses a 70-octet ASCII text string as a stand-in for a Transfer Frame and the (128,64) code: two fill octets are added, the 72 octets become nine codewords, each codeword is randomized with the BTG reset to all ones, and the 64-bit Start Sequence and the optional 128-bit tail are added, giving a 1344-bit (168-octet) CLTU. Its real bytes begin 03 47 76 C7 27 28 95 B0 (the Start Sequence), then AC 51 F1 28 1C C9 44 99 … (the first randomized codeword), and end with the tail 55 55 55 56 AA AA AA AA 55 55 55 55 55 55 55 55. A receiver decodes the text followed by UU, the two fill octets 0x55, which this sublayer does not remove. Example 2 encodes the same string with the (512,256) code: 26 fill octets and three 512-bit codewords.83 The CLTU length matches the formula above: 16 × 9 + 24 = 168 octets.

    These bytes predate the 2026 corrigendum and end with the old tail. Under Cor. 1 the same CLTU would end 63 A1 ED 72 C6 AC 79 E2 55 55 55 55 55 55 55 55; the Start Sequence and the nine codewords do not change.83130

    Reproducing the LDPC example

    This wiki also implemented the (128,64) encoder from the four defining rows of table 4-1 (codeword = the 64 information bits followed by their product with W, modulo 2) and the randomizer reset at each codeword, and reproduced all 1344 bits of table F-2. Only one reading of the "right circular shifts" of §4.3.3 works: the rows below each defining row are obtained by shifting each 16-bit (M-bit) block of it separately, as the block-circulant structure of W in §4.3.2 implies; shifting the whole 64-bit row does not reproduce the table.4283

    A Solar Orbiter Unlock CLTU (illustrative)¶

    Solar Orbiter uses spacecraft ID 0x28A, TC virtual channels 1 and 2 (one per on-board decoder) and frames of at most 256 octets.125 With the UNLOCK data field defined in the MIB (one octet 00), the frame on VC1 and its CLTU are:126

    Inference

    These bytes are computed by this wiki with the implementation checked above; they are not captured spacecraft data. Whether Solar Orbiter uses the randomizer, which BCH decoding mode its decoders use, and which PLOP the ground stations apply are not stated in the Solar Orbiter documents read for this page. A maximum-size 256-octet frame needs ⌊(256 + 6)/7⌋ = 37 codewords and a 306-octet CLTU, the 37-codeword row of the Green Book rejection tables above.86

    What the Solar Orbiter decoders report¶

    The Solar Orbiter MIB decodes two status words of each packet telecommand decoder (PDEC) that relate to this sublayer:127

    • PDEC_MON (for decoder A at octets 22–24 of SPID 19500 "DMS OBC Status Fast" and at octets 38–40 of SPID 19541): NCD0Z037 Lock with textual calibration 0 = No_Start_Seq, 1 = Start_Seq, and six inputs TC0 to TC5, each with a Dis flag (No_Dis, Dis) and a Status (Inactive, Active, Timed_out).
    • PDEC_FARCP (SPID 36997): besides the frame analysis described on the TC-SDLP page, a 6-bit CbCnt, a 3-bit ErrCnt, a Channel field calibrated TcA (DST-1), TcB (DST-2), TcAux (Test), and the outcome ABANDONED_CLTU.

    Inference

    Lock = Start_Seq presumably reports that the CLTU reception logic has found a Start Sequence (DECODE state); CbCnt and ErrCnt look like codeblock and corrected-error counts of the last CLTU; DST-1 and DST-2 presumably name the two deep-space transponders feeding decoder inputs. ABANDONED_CLTU uses the wording of ECSS-E-ST-50-04C, whose channel logic abandons a CLTU when the number of codeblocks exceeds an upper limit or the symbol clock is lost; the standard does not say how, or whether, that event is reported.145 CbCnt is a 6-bit unsigned parameter (PTC 3, PFC 2), so it could count up to 63 codeblocks, more than the 37 of a maximum-size 256-octet Solar Orbiter frame.127 The decoder documentation that would confirm these meanings is not among the available sources.
