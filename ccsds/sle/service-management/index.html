    SLE cross support reference model and service management¶

    Every SLE transfer service runs inside an agreed framework. A mission (the user) and a ground network operator (the provider) agree which services exist, when they exist and how they are configured. Only then can a mission user entity bind to a RAF, FCLTU or FSP instance. This page covers that framework. It starts with the CCSDS Cross Support Reference Model, which defines the vocabulary every SLE book uses. It then follows the service management standards built on that model, from the original SLE service management concept to the extensible Space Communication Cross Support (SCCS) service management suite. It ends with the Monitored Data transfer service used to watch a pass in progress, and with ESA's operational experience at ESTRACK.

    Part 1: the Cross Support Reference Model (910.4-B-2)¶

    Scope and the three kinds of cross support¶

    Cross support means one agency uses part of another agency's resources to complement its own when operating a spacecraft.7 The reference model names three kinds of cross support service on the ground and planned one part of the reference model for each:7

    Kind Content Reference model part
    SLE services Extend the CCSDS space link services onto the ground Part 1 (this document)
    Ground communications services Ground communications support, for example relaying operational data Part 2
    Ground domain services Services on spacecraft-operations data that does not map onto space link data structures, for example tracking, database exchange and mission planning Part 3

    Part 1 makes four assumptions: a single mission, a single spacecraft, CCSDS-compliant TM and TC, and all ground users affiliated with one mission management entity. It does not model the sharing of ground systems between missions, though it does not forbid it. It excludes the processing of packet contents, and it does not model the ground communications that SLE relies on.8 The model is a guideline for agency standards, not the design of a real system.8

    The environment¶

    Term Definition in the reference model
    Space element Source of return data and sink of forward data; one spacecraft with its platform and payloads. Each spacecraft of a multi-spacecraft mission is a separate space element.
    Physical channel The capability to carry one stream of bits in one direction
    Space link One or both of a forward and a return RF carrier channel, each giving one or more physical channels
    Space link session A continuous period in which the SLE system makes one or more physical channels of a space link usable
    Ground element The Mission Data Operation System (MDOS) plus the SLE system (plus components out of scope)
    SLE system Extends transfer and delivery between the space link ground termination and the MDOS, to specifications issued by the MDOS
    MDOS Source of forward and sink of return data. It contains one SLE Utilization Management and one or more Mission User Entities (MUEs), and may work with several SLE systems.
    SLE Utilization Management (SLE-UM) Negotiates the provision of transfer services with the SLE system, and controls and monitors it

    Source: SLE system environment.9

    SLE services are of two types. Transfer services move SLE data channels between the space element and the MDOS. The management service controls the scheduling and provision of transfer service instances.10 Within one mission, the model speaks of instances of services, and many instances of both types can exist at once.10

    Data units and data channels¶

    The SLE system exchanges Space Link Data Units (SL-DUs) with the space element. Inside the SLE system and towards the MDOS, it carries SLE Service Data Units (SLE-SDUs). An SLE-SDU wraps an SL-DU with annotation, control information, or both. A control-only SLE-SDU may produce an SL-DU, for example a COP directive that sends an Unlock to the spacecraft, or may matter only on the ground.11 Annotation examples are ground reception time and quality for return data, and requested transmission time and uplink path for forward data.11 A data channel is a uniquely identified stream of data units of one type. SL data channels and SLE data channels have the same types and identifiers, and SLE channels add the annotation.1112

    The forward channels that matter for telecommand, from annex A:

    The baseline transfer services and delivery modes¶

    The reference model lists 20 baseline transfer services. Each one delivers one type of SLE data channel.16

    Group Services
    Return (10) Return All Frames; Return Insert (AOS); Return Master Channel Frames; Return MC-OCF; Return MC-FSH (Packet Telemetry); Return VC Frames; Return VC-OCF; Return VC-FSH (Packet Telemetry); Return Bitstream (AOS); Return Space Packet
    Forward AOS (6) Forward Bitstream; Forward VCA; Forward Space Packet; Forward Proto Transfer Frame; Forward Insert; Forward Coded Transfer Frame
    Forward Telecommand (4) TC-VCA; Forward Space Packet; Telecommand Frame; CLTU

    Only some of these have their own Recommended Standards. The SLE overview lists the published ones.

    Mode Behaviour
    Forward online During the forward space link session only. Two qualities: complete and in-sequence (follows the routing control instructions, such as the multiplexing scheme, with sequence kept and no ground-induced errors, omissions or duplicates) and expedited (in sequence received, no ground errors, but data may be lost). Cannot extend past the end of the session.
    Return online, complete In sequence, no ground errors, no omissions, even if data arrives faster than it can be delivered (needs reserved buffering). May extend past the session.
    Return online, timely Two mechanisms: notification when delivery delay exceeds Tdelay-notify (and again on recovery); deletion of the queue when it exceeds Tdelete. The user can disable both.
    Forward offline The whole data set must reach the SLE system before it is transmitted to the space element during the session. It is transmitted complete and in sequence at a time set by SLE management.
    Return offline Delivered during or after the session, as a stored data set. Storage is either user data storage (everything received, with selection later) or user service data storage (only the service data chosen up front).

    Source: delivery modes.17 Offline delivery is arranged, like online delivery, through the service package.17

    Provision, production and ports¶

    Two definitions run through every SLE book:

    • Provision: an SLE system provides a transfer service when it exposes the operations needed to obtain it. Provision is characterised by which data channels are transferred, when, and with what quality of service.18
    • Production: the transformations between the RF carrier and the transferred SLE data channels.18

    An SLE system has transfer ports and management ports. A transfer port is either a user port (T-U) or a provider port (T-P), never both. Ports are asymmetric, and each service runs between exactly one pair of ports.18 The ports are named consumer or supplier by the direction of data flow. For return services the provider is the supplier. For forward services the provider is the consumer, because the user supplies the data.19

    The model defines four kinds of transfer-port operations. These are the abstract ancestors of the concrete SLE operations:2019

    Operation type Invoked by Purpose Concrete examples in the SLE books
    Transfer_Data The supplier (provider for return, user for forward) Carries an SLE-SDU RAF-TRANSFER-DATA, FSP-TRANSFER-DATA
    Transfer_Set The user Initialises or updates attributes of the user's instance START parameters, INVOKE-DIRECTIVE
    Transfer_Get The user Reads status and configuration of the instance GET-PARAMETER
    Transfer_Notification The provider Status and accounting reports STATUS-REPORT, ASYNC-NOTIFY

    The cross support view: complexes, packages and agreements¶

    Real SLE systems are built from physical systems run by different agencies or organisations. The cross support view models each of them as an SLE Complex: a set of SLE-FGs under one management authority.27

    Concept Definition
    SLE Complex A set of SLE-FGs under a single management authority, with one established relationship to the MDOS during cross support
    SLE Utilization Management The single MDOS entity that every complex talks to. It arranges data transfer with the complexes and monitors it, and is part of the Mission Management Entity.
    SLE Complex Management Negotiates service packages with UM. It also controls and monitors production and provision by the complex's SLE-FGs, distributes set-up parameters to them, and consolidates their reports for UM.
    SLE transfer service instance The provision by a complex of the capability to transfer one or more SLE data channels of one type, all related to the same space link session
    SLE Service Package The set of transfer service instances, with the characteristics of their production, that one complex provides to one or more users. Its online services are restricted to one space link session.
    SLE Service Agreement The transfer and management services a complex provides to an MDOS, and the conditions. Only one is in effect between a given complex and mission at a time.

    Sources: cross support view definitions.2728293031

    A complex exposes at least one user and one provider transfer port, and exactly one Complex Management port. A real system that serves several missions offers one such port per mission.32 A package only describes the part of production done by the complex that provides it. When a chain of complexes supports a mission, each complex has its own package with UM.29

    Time spans and phases¶

    The reference model defines three nested periods:34

    • Service agreement period: when a complex lets UM create packages and provides their services. It often covers the whole operational life (several packages a day, hundreds or thousands in total). It can also be short, for example launch support, a manoeuvre or an emergency.
    • Service package lifetime: when the complex provides the services of one package. Its instances exist only during this time.
    • Service instance provision period: when the capability to transfer the instance's channels is provided. Online instances belong to one space link session, but may start before it and end after it. Offline instances can be anywhere in the agreement period.

    Security in the reference model¶

    Issue 2 added a cross support security section covering six areas:37

    Area SLE transfer services SLE service management
    Data privacy Not provided; to be ensured above or below SLE (for example by encrypting the PDU) XML encryption may be considered
    Data integrity In-sequence, complete, flow-controlled transfer; strict operation sequence; credentials over the whole PDU can be agreed Sequence numbers
    Authentication Credentials in the PDUs (procedure in the cross support concept); algorithms out of scope; secure key distribution needed Digital signatures recommended
    Access control Initiator and responder identifiers Unique identification parameters created by UM and carried in each message to CM
    Availability Not provided; depends on the underlying network CM may reject requests; denial of service left to routers and firewalls
    Auditing Not specified; the SLE API logs access attempts Not specified; agencies expected to keep audit trails

    Service-specific threats and consequences are left to each service book. For FSP, see the FSP security section. For the wider picture, see security in CCSDS space links.37

    Part 2: SLE service management in the Cross Support Concept (910.3-G-3)¶

    The Cross Support Concept explains what SLE service management was meant to cover. Of the five OSI management functional areas, it includes four:38

    OSI area In SLE service management
    Configuration The largest part: UM and CM define service packages (input and output channels, processing parameters, storage)
    Accounting Per-package reports of data received, sent and processed by the complex
    Fault Notification of faults affecting services; detection and repair inside the complex stay hidden
    Security Credentials, access control to cross support interfaces, authentication of requests
    Performance Excluded: an internal matter for the complex's operator

    The guiding considerations were these. Mission needs drive the concept. The user is isolated from the provider's internals. Services are presented the same way whatever the provider offers. Reporting gives enough accountability. Automation and low operating cost are design aims. Adoption can be incremental.3839 The SLE overview summarises the services (service agreement, configuration profile, trajectory prediction, service package) and the nominal timeline. The nominal use case runs as follows:

    Part 3: from SLE service management to SCCS service management¶

    The first standard for this management interface, the SCCS Service Management Service Specification (CCSDS 910.11-B-1, August 2009), and its operations concept (910.14-G-1) are not in this library.42 The 2006 cross support concept cites the same number as a draft, the SLE Service Management Service Specification 910.11-R-1 (Red Book, March 2006).130 The name changed from SLE to SCCS service management with the version-1 specification.45 The extensible concept explains what version 1 covered and why it is being replaced. Version 1 offered the Service Package, Trajectory Prediction, Configuration Profile and Service Agreement management services, using Version-1 information entities.4243 ESTRACK used 910.11-B-1 "whenever possible" for its interfaces.44

    Annex B of the extensible concept maps the old terms to the new ones:45

    Cross Support Reference Model / SCCS SM version 1 Extensible SCCS SM enterprise model Note
    Space element (one spacecraft) Space User Node The Space User CSSS may contain several nodes
    MDOS Earth User CSSS MDOS is only the functional view; the new model adds a physical view of Earth User Nodes

    Part 4: the extensible SCCS service management concept (902.0-G-1)¶

    Why a new suite¶

    The concept names two groups of shortcomings in version 1. Its scope covered only requesting and scheduling services, not the other management activities over a mission's relationship with a provider. Its structure could not absorb new space communication technologies or new service management techniques.47 SCCS SM covers the physical and data link layer aspects of space link services. In the near term it is focused on single-hop Earth–space links, which the SCCS architecture calls the ABA configuration (Mission A supported by provider B) and which match IOAG Service Catalog 1. The SSI (Solar System Internetwork) configuration adds space–space and space–planet links with internetworking, and matches Service Catalog 2.48 In SSI, data is routed through the provider by internetwork address. The concept says it logically includes SSI, but many SSI details were still undefined, so the SSI configuration is outside the scope of this version and the first standards focus on Service Catalog 1.4849

    The enterprise model splits service management between two functions. Utilization Management belongs to the Earth User CSSS, and Provision Management to the Provider CSSS. Each takes part in service catalog consultation, mission telecom analysis, service agreement negotiation and adoption, service planning and scheduling, service package execution, and service accounting.50 The model adds two management functions to the Earth User CSSS. Mission Planning relies on UM to acquire and configure the provider's services, and on Space User Management to configure and control the spacecraft side.51

    Service packages and scheduling¶

    There are three kinds of service package. The SLS package covers services that need an active space link. The Retrieval package covers delivery of stored return data, with or without an SLS running. The Forward Offline package covers upload of forward data to the provider before the SLS that will carry it. Version 1 had no Forward Offline package.72 Providers schedule in two ways:73

    • Specific-period scheduling. The mission asks for SLSes at or around given times. The request can be made flexible with a preferred start time plus start-time lead and lag, a preferred and minimum duration, and the relative timing of carriers (for example, the forward carrier for at least n minutes inside the return carrier). Process options are waitlisting (keep trying until a waitlist period expires), improvement after scheduling up to a freeze interval, and service scenarios (nominal plus contingency configurations reserved together, for example for LEOP).
    • Rule-based scheduling, also called generic or standing order scheduling. Mission and provider agree rules, such as "6 return carriers per week, 15–30 min each, 6–30 h apart". PM then generates tentative packages, which UM may delete. The concept names this as the primary mode of the NASA Near Earth Network and ESTRACK. The Recurrent Service Package Request combines the two: rules for a stated horizon, optionally with allowed and forbidden windows.

    The extensible SLS Service Package Request keeps what is requested separate from how it may be scheduled. A Space Communication Service Set holds one or more Space Communication Service Requests, each pointing to one configuration profile. A Flexibilities and Constraints component holds rules, each pointing to the requests it applies to. Every provider that adopts the format must support the minimal rule, a fixed start and stop time per request. Providers may add their own rules at this extension point. Trajectory references are another likely extension point, because deep-space packages may need the trajectories of both the spacecraft and a celestial body.74

    The planning IEs (Provisional Plan, Communications Geometry, Sustainable Data Rates, RFI, Resource Conflicts, Cost Estimates), the Space Link Event Sequence and the Accounting Report all follow an Event Timeline stereotype. This is a time-ordered series of events. Each event has an identifier unique within the service agreement and an event time. The time is instantaneous or has a duration, carries an uncertainty window, and is absolute or relative. Each event also has an extension point for type-specific data, such as the aperture of a visibility event.75

    Naming monitored items¶

    Parameters and events are named by OIDs. A Parameter Name combines a Parameter Identifier (a published OID for the parameter type) with a Functional Resource Name (FR Type OID plus FR Instance Number). Event Names work the same way. FR instance numbers come from scheduling, so they are not fixed in advance.100 The book writes these as text, for example [[{Antenna}: 1]: {antPointingMode}] for the pointing mode of antenna instance 1.101

    A cyclic-report START (or a GET, or a Notification START) can select by individual names, by labels (a parameter type for all instances), by a named or default label list agreed by service management, by FR Name (all parameters of one instance) or by FR Type (all instances of a type). Optionally, it can also select procedure configuration parameters. Any unknown item makes the START fail, and the unknown items are returned.102 Several cyclic report instances can run at once with different lists and cycles.102

    On-change option. Each START of the cyclic report carries on-change-option. With FALSE, every report contains every subscribed value. With TRUE, the first report is complete, and later reports contain only parameters whose value or qualifier changed since they were last reported. A value that changes and changes back between two reports is not sent.103104

    Part 7: ESTRACK in practice (SpaceOps 2025)¶

    The ESOC paper describes the service management interfaces of the ESTRACK Scheduling Office (ESO). The number of ESA spacecraft flying has tripled in twenty years, while ESTRACK capacity stayed stable. Deep-space demand now exceeds the network's capacity at peak periods. ESTRACK therefore acts both as a user of six external providers and as a provider (and broker) to five external partners.644

    Planning. The ESTRACK Planning System (EPS) solves all users' standing orders together. Standing orders are planning requirements and constraints from each mission agreement, translated into EPS configuration. The result is a baseline booking covering typically 4 weeks for the LEO network and up to 12 months for deep space. Users then add, modify or delete bookings.112 This is the rule-based scheduling that the extensible concept attributes to ESTRACK.73 Every change request is checked for validity (format, ID, privilege), conflict, technical feasibility (service available on that terminal, visibility) and, for external providers, availability. Valid requests then follow the EMSP request state machine.112 The ESTRACK Management System web Portal (EMSP) handles all external interfaces, both as user and as provider, through the web or system-to-system, using REST or files.112113

    Closing the loop. Providers change bookings without warning (LEOP, maintenance, failures), and negotiations for deep space can last months. Immediate per-request confirmation therefore cannot keep two databases consistent. ESTRACK uses the provider's Simple Schedule Format list of everything it has agreed to support.114115 Building inter-network synchronisation correctly took two years for each of two generations of software.116

It shields its core from partners' variants with XML plus XSL transforms, one independent translator per interface.118119 There are two request styles. The legacy one is replace all: a time range plus a list of supports, which deletes everything else in the range. SMURF's add/modify/delete handles single requests, which suits a yearly deep-space plan where under 1 % changes, but makes the booking system more complex.120

    Service definition is the least standardised part. Interfaces use agreed keywords (such as XBand, SBand, Mode1, Mode2), with extra parameters for DDOR, MSPA or complex links. A network operator must still be able to set up the service from instructions read over a voice loop.121 Each ESTRACK service type has a scheduling template of automated tasks. A published catalogue of user scheduled events (absolute-time actions such as starting or stopping the uplink or a recording) has become a de facto standard for occultations and link changes.122

    Inference

    These user scheduled events play much the same role as the Space Link Event Sequence entity of the extensible concept, which lists planned link changes at absolute or relative times.60 The paper does not make this comparison.

    Lessons. Exchange the minimum, and leave complex configuration to documents. Expose only tested configurations. Keep file exchange next to REST, because firewall changes can break live protocols.123 A catalogue of every possible service field proved hard to maintain. The CCSDS functional service levels (online telemetry, uplink, ranging and so on) were awkward, and a single agreed "TTC" service name worked better.123 Individual request confirmation (SPDF) was rated essential when the EPS was designed, but was never used, and only one of ESTRACK's providers supports it.115 The paper expects request formats (format, basic parameters, service-definition parameters) to be standardisable now. Services themselves will stay bilateral, and standing orders are best kept proprietary. The SMURF flexible-request fields (earliest start, latest end, minimum and maximum duration) are not yet implemented anywhere.124 The conclusion names SMAC, SACP and SMASH as the next topics.125

    Service agreement and package identifiers in the Solar Orbiter MIB¶

    The public Solar Orbiter MIB carries one direct trace of this machinery. The NIS command EGENRTCO "GENERIC OPEN TC LINK" stores the SLE service instance identifier in three fixed-value elements. They join up as sagr=144.spack=NN11-PERM.fsl-fg=1.cltu=cltu01. The TM link commands EGENRTMO and EGENRTMC carry sagr=144.spack=NN11-PERM.rsl-fg=1.rcf=onlc0001. The forward CLTU instance and the return RCF instance therefore name the same agreement and the same package. The values are identical in the 2025-09-16 and 2020-04-16 releases.126127 The first two attributes name the service agreement (sagr) and the service package (spack) defined by the reference model. They are followed by the forward or return functional group and the service instance, using the syntax of the SLE service books.12829 The SLE overview explains the syntax. The FSP page covers the TC link command, and the return services page the RCF instance.

    Inference

    The -PERM suffix suggests a standing (permanent) package used for every pass, rather than one package per pass. Neither the MIB nor the library documents state this.
