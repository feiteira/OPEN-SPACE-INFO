    SLE return services: RAF, RCF and ROCF¶

    The SLE return services carry what a ground station receives from a spacecraft to the users who need it. Return All Frames (RAF) delivers every telemetry frame of one physical channel, including frames that failed decoding if the user asks for them.1 Return Channel Frames (RCF) delivers only the good frames of one Master Channel or one Virtual Channel.2 Return Operational Control Fields (ROCF) delivers only the 4-octet Operational Control Fields (OCFs) of those frames, typically the CLCWs that the spacecraft uses to report the state of its telecommand receiver.3 The three services share the same operations, delivery modes, buffering rules and state machine. They differ in what they select and what they annotate.

    This page assumes the concepts on the SLE overview: providers and users, service instances, BIND/UNBIND/PEER-ABORT, and access control. The architecture behind them is on the cross support reference model and service management, and the software side on ISP1 and the SLE API. The frames themselves are described on TM Space Data Link Protocol, AOS and USLP, and the coding that the station undoes on TM synchronization and channel coding.

    Where the services sit in the ground station¶

    All three services start from the same processing chain. The Return Space Link Processing functional group (RSLP-FG) receives the RF signal and produces the RAF data channel: it demodulates the carrier and subcarrier, recovers symbols, synchronises frames, decodes them, and annotates each frame with its earth receive time (ERT), antenna, quality and continuity. The Return Frame Processing functional group (RFP-FG) consumes that RAF data channel. It discards every frame whose quality is not 'good', demultiplexes the rest into Master Channels and Virtual Channels, and, for ROCF, decommutates the OCF from each frame.101112

    The services assume a stable physical channel. At any one time all frames on a channel must use the same coding options and, for TM, the same frame length, and the station learns these through service management rather than from the data.1314 The reference model gives the sharpest example: Reed-Solomon coding must be present on all frames of a physical channel or on none, even where the space link standards would allow a mix.100 The concept report puts it from the other side: to offer channel frames, a provider must implement both the frame processing and the space link processing functional groups.15

    What "good" means¶

    The RSLP-FG annotates a frame as good if, after decoding, it consists only of valid Reed-Solomon or LDPC codewords, or, for a frame that uses neither code, if its Frame Error Control Field checks correctly. A USLP frame is good if it passes the USLP frame validation checks (except for the checks of §4.3.10.3.4 c) of the USLP standard). If Reed-Solomon is the outer code of a concatenated scheme, the same rule applies.1617 Erred means that at least one codeword is invalid or the FECF fails. Undetermined means the coding scheme is unknown or unsupported, or the result is not provided, and the exact meaning is implementation dependent.16 The optional Header Error Control field of AOS frames is disregarded when the RAF service reports frame quality.14

    The RAF specification defines precisely how a frame is trimmed before delivery. RCF and ROCF only ever deliver good frames, so only the first case applies to them.1819

    Earth receive time¶

    The ERT of a frame is the UTC time at which the leading edge of the first bit of the Attached Sync Marker (or, for USLP and other codes delimited that way, of the start sequence) that immediately precedes the frame reached the phase centre of the receiving antenna. The antenna-ID exists precisely to identify that reference point.27 With punctured convolutional codes the number of symbols per information bit varies, so missions must allow for jitter in the ERT.27 The ERT must be accurate to within 1 millisecond of true UTC; this is a mandatory conformance requirement.28

    ESA's SCOS-2000 time correlation technical note relies on this definition. It takes its definition of frame reception time from SLE and states that for SLE providers the frame reception time is the ERT, so the ground delay term in the correlation is zero by definition.29 See time correlation.

    Data link continuity¶

    data-link-continuity tells the user whether frames were lost before this one. The encoding is an integer from −1 to 16,777,215.24

    • RAF: −1 means the first frame after production started, 0 means the frame directly follows the last frame acquired, and a positive value is an estimate of the number of frames missed (1 if no better estimate exists). RAF production does not read frame headers to compute it, so this reflects frame synchronisation, not counters.32
    • RCF and ROCF compute it from the frame counters of the selected channel:3334
    Selected channel Value
    First frame after production start, or an AOS or USLP Master Channel (no MC counter) −1
    TM Master Channel (MCFCn − MCFCn−1 − 1) mod 256
    TM Virtual Channel (VCFCn − VCFCn−1 − 1) mod 256
    AOS Virtual Channel (VCFCn − VCFCn−1 − 1) mod 16,777,216
    USLP VC, non-truncated header (VCFCn − VCFCn−1 − 1) mod 28 × VC count length
    USLP VC, truncated header −1

    For TM the count is only correct for gaps under 256 frames. Longer gaps must be resolved using the ERT and the nominal frame rate. The AOS VC Frame Count Cycle field is ignored.33

    Worked example (illustrative values, real Solar Orbiter frame format). Solar Orbiter TM frames are TFVN 0 frames with 8-bit MC and VC frame counts, modulo 256.35 Suppose the previous VC0 frame delivered by an RCF instance had VCFC 0xFE and the next one has 0x02. The provider reports (2 − 254 − 1) mod 256 = 3, meaning frames 0xFF, 0x00 and 0x01 were lost. Solar Orbiter also extends the VC count by 24 bits in its frame secondary header,36 but RCF does not use that extension: the TM rule above is modulo 256.

    Inference

    Because RCF ignores the secondary-header extension, a control centre that needs an exact gap count longer than 255 frames for Solar Orbiter would have to compare the 24-bit secondary-header counts itself. The standard's own suggestion is to use the ERT and the nominal frame rate.33 Whether ESA's ground software does this is not stated in the available sources.

    Delivery modes and buffering¶

    Each return service instance is configured, by service management, for exactly one delivery mode.7 The three modes behave very differently when the ground network cannot keep up. The reference model describes the same three modes in more abstract terms. Its timely online mode uses two user-settable delay thresholds, one for a warning and one for deletion, instead of the single latency limit described below; the two are compared on the overview.102

    The transfer buffer and the release timer¶

    In all modes, TRANSFER-DATA and SYNC-NOTIFY invocations are collected in a transfer buffer and sent together as one TransferBuffer PDU, which is a SEQUENCE OF annotated frames and synchronous notifications in insertion order.3724 When the first record goes into an empty buffer, the provider starts the release timer, whose duration is the latency-limit. The buffer is sent when it holds transfer-buffer-size records, when the release timer expires (online modes), or when an 'end of data' notification is inserted.37 Every other operation (returns, status reports) bypasses the buffer and is sent as soon as possible.40 A conforming transfer buffer must hold at least 200 TRANSFER-DATA invocations.28

    Timely online¶

    Timely online mode trades completeness for latency. If the communications service applies backpressure (it will not accept the PDU, or would block the provider), the provider discards the whole TransferBuffer PDU, clears the buffer, inserts a 'data discarded due to excessive backlog' notification, and restarts the release timer. While that notification is in the buffer, the buffer size is temporarily increased by one, so that a buffer of size one still lets some telemetry through instead of carrying only discard notices.40 On RAF-STOP the buffer is flushed immediately. On abort it is cleared.40

    Complete online¶

    Complete online mode attempts to deliver every frame, in order, with the minimum delay the network allows.38 Frames first go into a large online frame buffer that starts filling as soon as both the provision period and the space link session have started. Filling continues for the whole provision period whether or not a user is bound, and stops only if the association is released with UNBIND 'end'.41 Records move from the online frame buffer to the transfer buffer while the instance is 'active'. A full transfer buffer is retried until the network accepts it.41

    Two consequences follow:

    • After a STOP or a lost association, the user can re-bind and issue a new START with a start time in the past to retrieve what was buffered. Frames older than that start time are removed.41
    • A record taken from the online frame buffer cannot be taken again, so data in a transfer buffer that was lost in an abort are gone. The standard deliberately chose this over an application-level acknowledgement, which would hurt throughput, and expects such gaps to be filled offline.41

    If the online frame buffer itself overflows (for example during a long outage), the oldest records are discarded (how many is set by service management) and a 'data discarded' notification is queued. A conforming online frame buffer must hold at least 100,000 TRANSFER-DATA invocations. The buffer is emptied at the end of the provision period.4228

    Offline¶

    Offline mode delivers frames acquired earlier, for an ERT window the user chooses. Frames are kept in an offline frame buffer, ideally one per service agreement, so deleting data affects all offline instances of that agreement and no others.39 Each provider must document the delay before a frame becomes available offline. At START the provider extracts records from the earliest ERT ≥ start-time in original order. Delivery continues until the buffer is full, a frame with ERT > stop-time is found (which generates 'end of data'), the user stops, or the association aborts. Full transfer buffers are retried until accepted.3943 Offline START requires both times to be non-null. stop-time plus the offline processing latency must already be in the past. SYNC-NOTIFY in offline mode only ever reports 'end of data', and SCHEDULE-STATUS-REPORT is rejected.444546 A conforming offline buffer must hold at least 1,000,000 TRANSFER-DATA invocations.28

    The reference model explains the storage choice behind offline delivery. An SLE system can store the full user data of a session, so that the MDOS chooses what to retrieve only when it retrieves it, or only the user service data that the MDOS named in advance. The first is more flexible for the user, but its cost grows as the share of data actually retrieved falls, so real systems may restrict or not offer it. The frame processing group's description makes the same choice concrete: storage relative to the source RAF channel needs no advance selection, storage relative to each product channel (MC, VC, OCF or FSH) does, and some implementations can afford only the second. What matters for cross support is what the MDOS and the SLE system agree, not how the system stores internally.102100

    Worked example (illustrative numbers). A timely online RAF instance has latency-limit = 1 s and transfer-buffer-size = 200. The spacecraft sends 1115-octet Solar Orbiter frames35 at about 8 frames per second. The release timer, not the size limit, triggers transmission: each TransferBuffer PDU carries about 8 frames and leaves the station about 1 s after its first frame was acquired. If the wide area link stalls for 10 s, roughly ten PDUs are discarded. The user sees one 'data discarded due to excessive backlog' notification at the point of the gap (repeated discards without an intervening delivery produce only one notification45), followed by fresh frames, and data-link-continuity on the first frame after the gap shows the frame-sync view of continuity. The same outage in complete online mode would delay the frames but deliver them all, as long as the online frame buffer did not overflow.

    ROCF and the CLCW¶

    What the OCF carries¶

    A TM, AOS or USLP frame may end with a 32-bit Operational Control Field. Its first bit is the control word type: 0 means the field holds a Communications Link Control Word (CLCW), the report of the spacecraft's COP-1 receiving end (FARM). 1 means some other report. ROCF's 'not clcw' type is the one to use to obtain Frame Security Reports.818283

    Field layout from CCSDS 232.0-B-4.84 The semantics of each flag for the FOP-1 machine are explained on the COP-1 page.

    Selecting OCFs¶

    ROCF START adds three criteria to the GVCID.8185

    • control-word-type: 'all control word types' delivers every OCF. 'clcw' delivers only OCFs with type bit 0. 'not clcw' delivers only those with type bit 1. In ASN.1, ControlWordType is a CHOICE of allControlWords [0] NULL, clcw [1] TcVcid and notClcw [2] NULL. The CLCW choice carries the TC VC selection inside it.58
    • tc-vcid: present only for 'clcw'. It selects CLCWs that report on one telecommand VC, or all of them if 'null' (noTcVC [0] NULL).8586
    • update-mode: 'continuous' delivers every OCF that matches. 'change-based' delivers an OCF only if its content differs from the last one with the same tc-vcid put into the transfer buffer, or if none has been delivered since the last START.85

    If filtering suppresses some OCFs, data-link-continuity still reports a discontinuity only when the frame was the first after a gap on the channel. In USLP the OCF may be absent from some frames, so counters can falsely suggest a gap.34

    How CLCWs reach the control centre¶

    A ground segment can see CLCWs by three routes, and the SLE documents describe all three:

    1. Inside frames delivered by RAF or RCF. The OCF is part of every delivered frame, so the control centre can extract the CLCW itself. Solar Orbiter sets the OCF flag in every frame and always puts a CLCW in it.87
    2. Through ROCF. A user that only needs the command link status, such as a separate commanding facility, can subscribe to the CLCWs of one TC VC without receiving the frames. Change-based mode then delivers a CLCW only when something changes.85
    3. Inside the station. The concept report describes ROCF supplying the CLCW to the forward providers: the CLTU provider needs it to know whether the physical uplink is available, and the VC or packet provider needs it to decide on COP-1 retransmissions.88 The reference model formalises this: the users of its MC-OCF and VC-OCF transfer ports are the Forward TC VC Data Insertion and Forward TC Space Link Processing functional groups as well as MUEs, and the production of Forward CLTU includes a consumer OCF port.103104 The FCLTU production process itself can consume CLCWs from a configured GVCID and physical channel; see FCLTU. With FSP the provider also runs FOP-1, so the station's VC Data Insertion function uses the CLCW to retransmit frames.105

    Checks split between the API and the application¶

    On the provider side the service element checks a RAF-START before passing it on, and answers it negatively itself if a check fails:123

    • offline mode: the start time must not be null, the stop time must not be null, and the stop time must be earlier than the current time;
    • online mode: a start time, if given, must lie within the scheduled provision period, and a stop time, if given, must not be later than its end;
    • the operation object itself checks that the start time is earlier than the stop time.

    The service element does not check production status, because it can change before the application sees the PDU. The offline processing latency check is left to the application too.123 For SYNC-NOTIFY it refuses, in offline mode, the 'loss of frame synchronization', 'production status change' and 'data discarded' types, and in timely online mode the 'data discarded' type.124

    Offsets are counted from the end of the SCOS-2000 TM header, as for every PLF entry;92 PTC/PFC meanings are on parameter types. See also monitoring in the MIB.

    Inference

    Octets 0 to 15 are exactly a Solar Orbiter frame (6 + 4 + 1099 + 4 + 2 = 1115 octets35) with its 1099-octet data field removed. "Mini-transfer frame" therefore seems to mean the frame without its data field, plus the reception time. The split into good, bad and idle mirrors the RAF delivered-frame-quality values and the VC7 idle frames. The ERT fields have the same resolution as SLE's picosecond time code. None of this is stated in the available sources, which do not document how the NCTRS builds these packets.

    Opening an RCF link from SCOS-2000¶

    The NIS throw event EGENRTMO ("GENERIC OPEN TM LINK") opens a return link on ESA's network interface system. Its fields mirror RCF-START: a service type, a TFVN, an SCID and a VCID, a channel type that chooses between a virtual channel and a master channel, start and stop times each preceded by a "used" flag, and the service instance identifier.9193

    The two 32-bit words after "End Time Used" are labelled "Start time" in the MIB's CDF descriptions, like the two words after "Start Time Used". This page labels them as end time words from their position; the MIB itself does not say so.91

    After bit 224 come three ASCII fields, "sagr=144.spack=", "NN11-PERM.rsl-f" (two 15-character fields) and a variable-length "g=1.rcf=onlc0001". Together they spell the RCF service instance identifier sagr=144.spack=NN11-PERM.rsl-fg=1.rcf=onlc0001, valid in the 911.2 Annex A syntax; the onlc prefix presumably denotes a complete online instance (see the overview).9194 The companion command EGENRTMC ("GENERIC CLOSE TM LINK") carries only the event ID CLOSE_LINK (21), the service type and the same identifier. The April 2020 release holds identical definitions.95

    Inference

    The TFVN, SCID, VCID and channel-type fields correspond one-to-one to the RCF GvcId (with 'MASTER' playing the role of masterChannel). The two "used" flags followed by two 32-bit words look like the two ConditionalTime values of RCF-START. This suggests that the NIS turns this event into an RCF-BIND and RCF-START towards the station. The NIS Throw Events ICD that defines these fields (EGOS-NIS-NIS-ICD-0003, referenced by the SCOS-2000 import ICD96) is not in this library. The meaning of "Mode" and "Link priority" is not stated in the available sources.

    SLE service identifiers in ESA data products¶

    Telemetry that reaches users through ESA's data distribution still records the SLE channel. The Rosetta and Mars Express data delivery ICD defines an 8-bit "SLE Type" at octet 16 of its DDS packet header:97

    SLE Type Real-Time (RT) Real-Time Flow Control (RTFC) Off-Line
    SLC 0 4 8
    MC 1 5 9
    VC 2 6 10
    Bad Frames 3 7 11

    The EDDS raw TM header keeps an 8-bit SleServiceID (field 17) "for backward compatibility with the GDDS", and the GDDS binary packet header carries a one-octet "SLE Service".98 See EDDS formats and GDDS and DDIDs.

    Inference

    The three columns plausibly correspond to SLE's timely online, complete online ("flow control", meaning no discarding) and offline delivery modes. "MC", "VC" and "Bad Frames" fit RCF master channel, RCF virtual channel and RAF erred frames. "SLC" may mean the whole space link channel (RAF). The ICD does not define these terms.

    Security¶

    The return services use the common access control and authentication rules of the overview. Their specific risk is confidentiality and integrity of the data. The RAF specification relies on unspecified mechanisms above the service (between the spacecraft application and its ground peer), in the underlying communications service, or in bilaterally agreed extras such as encryption of the data parameter. Without them, telemetry crossing the wide area network could be read or substituted without detection. The stated consequences of not applying security are degraded or lost telemetry reception, or altered telemetry.99 SDLS is one such mechanism, applied within the frames themselves.20
