    SLE over TCP/IP (ISP1) and the SLE API¶

    The SLE transfer service specifications define what is exchanged: operations, parameters and ASN.1 types. They deliberately say nothing about the network. They require only an underlying service that delivers PDUs in sequence, completely and with integrity, without duplication, with flow control, and with notice of disruption.1 Two further CCSDS documents close that gap. The Internet SLE Protocol One (ISP1, CCSDS 913.1-B-2) is a Recommended Standard that maps SLE associations onto TCP connections.2 The SLE Application Program Interface (CCSDS 914.0-M-2) is a Recommended Practice that defines a C++ component architecture, so that SLE user and provider software can be built from interchangeable packages.3 The 2006 concept report already described the API in the same layered way: an API Proxy for the communications technology beneath an API Service Element for the service logic.69

    The SLE concepts used here (associations, BIND, PEER-ABORT, credentials) are introduced on the SLE overview. The services carried are described on return services, FCLTU and FSP. Where these documents sit in the SLE documentation tree is shown on the overview.

    ISP1 architecture¶

    ISP1 sits between the "higher layers" and TCP/IP. The higher layers are the SLE transfer service logic: they build and analyse PDUs and run the state tables. ISP1 itself has three sublayers:7

    Diagram based on figure 2-1 and the interface descriptions of CCSDS 913.1-B-2.712

    Two design rules shape the whole protocol:

    • One SLE association uses exactly one TCP connection. Association establishment and release involve only the TML. Once established, every PDU passes through the DEL and the AL.713
    • PEER-ABORT bypasses encoding. The PEER-ABORT invocation is never BER-encoded. The TML sends its one-octet diagnostic as TCP urgent data.1415

    ISP1 leaves open how its configuration parameters are defined, agreed, stored and made available to an implementation.7

    Authentication Layer¶

    The AL adds credentials to outgoing PDUs and checks them on incoming ones, according to the instance's authentication level: 'all' (every invocation and return except the PEER-ABORT invocation), 'bind' (BIND invocation and return only) or 'none'.16 It uses the "Protected 1" simple authentication procedure, with these inputs:10

    • a user name of 3 to 16 characters, identical to the authority identifier in the BIND (initiator-identifier for the initiator, responder-identifier for the responder);
    • a password of 6 to 16 octets;
    • the current time, as an 8-octet CCSDS Day Segmented code without P-field;
    • a random number from 0 to 2,147,483,647.

    These four values are DER-encoded as a HashInput and hashed with SHA-256. The result is called "the protected". The credentials carry the time, the random number and the digest, but not the user name, which is already in the BIND.10

    HashInput ::= SEQUENCE              -- DER-encoded, then hashed with SHA-256
{ time          OCTET STRING (SIZE(8))      -- CDS, no P-field
, randomNumber  INTEGER (0 .. 2147483647)
, userName      VisibleString
, passWord      OCTET STRING
}

ISP1Credentials ::= SEQUENCE        -- carried inside Credentials 'used' [1] OCTET STRING
{ time          OCTET STRING (SIZE (8))
, randomNumber  INTEGER (0 .. 2147483647)
, theProtected  OCTET STRING (SIZE (20..32))  -- 32 for SHA-256; 20 allowed for SHA-1 peers
}

    ASN.1 quoted from figures 3-1 and 3-2 of CCSDS 913.1-B-2.109

    The receiver first checks that the credential time is within an acceptable delay of its own clock. This maximum delay is a configuration parameter. It then recomputes the digest using the peer's user name and password, and compares the two.1016 The 20-octet option exists so that implementations can stay compatible with peers built to the SHA-1 based 913.1-B-1.9 If authentication fails, the higher layers apply the transfer service rule: the PDU is ignored, as if it had never arrived.17

    Worked example (illustrative values, real algorithm). Take user name MCS-USER, password 01 23 45 67 89 AB CD EF, time 62 40 02 93 2E 7B 01 C8 (2026-11-12 12:00:00.123456 UTC; see return services) and random number 0x12345678. The DER HashInput is:

    30 24                                    SEQUENCE, 36 octets
   04 08 62 40 02 93 2E 7B 01 C8         time
   02 04 12 34 56 78                     randomNumber
   1A 08 4D 43 53 2D 55 53 45 52         userName "MCS-USER" (VisibleString)
   04 08 01 23 45 67 89 AB CD EF         passWord

    Its SHA-256 digest is C69510D1403E0E97C55A59F4D741C97DE919020E9CE006AC2303046B944C3020. The ISP1Credentials value is 30 32 04 08 62 40 02 93 2E 7B 01 C8 02 04 12 34 56 78 04 20 followed by the 32 digest octets, 52 octets in all. Inside an SLE PDU this becomes Credentials → used [1], encoded 81 34 followed by those 52 octets. This wiki computed these bytes from the ASN.1 definitions. The credentials are invented and are not from any real system.

    Inference

    The final step assumes the IMPLICIT TAGS encoding of the Credentials CHOICE alternative used [1] OCTET STRING (context-specific primitive tag 1 = 0x81). This follows from the RAF common types module,18 but ISP1 does not print a complete encoded example.

    ISP1 is frank about the limits of this scheme. It provides authentication and access control only. Confidentiality, integrity beyond what TCP gives, and strong authentication must come from a secure channel through which ISP1 traffic is tunnelled, or from end-to-end protection of the mission data.1920

    Data Encoding Layer¶

    The DEL encodes and decodes every SLE PDU except the PEER-ABORT invocation. It uses the ASN.1 types of the applicable service specification and the Basic Encoding Rules.149 The first PDU on a new association must be a BIND invocation. Its service-type and version-number tell the DEL which ASN.1 modules to use for everything that follows on the same association. An unsupported service type or version is reported to the higher layers, which then apply the BIND rules (for example 'service type not supported').149

    The top-level CHOICE tags of each service's user-to-provider and provider-to-user PDUs tell the receiver which operation a PDU carries. These tags are listed on the return services and FCLTU pages.

    Worked example (illustrative, constructed from the ASN.1). A RAF user sends STOP with invoke-ID 5 and no credentials. rafStopInvocation [2] is a SleStopInvocation, which is a SEQUENCE of invokerCredentials and invokeId.21 With IMPLICIT TAGS, the alternative tag replaces the SEQUENCE tag. Credentials 'unused' is [0] NULL, and the invoke-ID is an INTEGER:

    A2 05          [2] constructed (rafStopInvocation), length 5
   80 00       invokerCredentials = unused [0] NULL
   02 01 05    invokeId = 5

    Inference

    This encoding follows from the RAF ASN.1 modules (tag [2], IMPLICIT TAGS, Credentials CHOICE, InvokeId ::= IntUnsignedShort).211822 The common PDUs module, also under IMPLICIT TAGS, defines SleStopInvocation as a SEQUENCE of invokerCredentials and invokeId only.23 The library has no SLE capture to confirm the bytes.

    Transport Mapping Layer¶

    TML messages¶

    TCP carries a byte stream, so the TML frames everything in TML messages: an 8-octet header followed by a body of any length (not necessarily a multiple of four). All integers are big endian.2425

    Type ID Message Body
    1 SLE PDU message One BER-encoded SLE PDU (never a PEER-ABORT)
    2 TML context message 12 octets: protocol ID, version, heartbeat parameters
    3 TML heartbeat message Empty (length 0)

    Sources: table 3-1 and §3.3.2.2426

    Field layout from figure 3-4.24

    Worked examples (byte layouts from the standard, parameter values illustrative):

    Message Bytes
    Context, heartbeat 30 s, dead factor 5 02 00 00 00 00 00 00 0C 49 53 50 31 00 00 00 01 00 1E 00 05
    Heartbeat 03 00 00 00 00 00 00 00
    SLE PDU carrying the RAF STOP above 01 00 00 00 00 00 00 07 A2 05 80 00 02 01 05
    PEER-ABORT 'return timeout' one byte 06 sent as TCP urgent data (no TML header)

    The PEER-ABORT code 6 is the 'return timeout' value of PeerAbortDiagnostic.2728

    Heartbeat¶

    TCP cannot tell an idle connection from a dead one. Some TCP implementations offer keep-alive probes, but the Internet host requirements (STD 3, ISP1 reference [E7]) require their default interval to be at least two hours, so ISP1 defines its own heartbeat.29 Two parameters control it. The heartbeat-interval is the longest a TML may stay silent, in seconds. The dead-factor is the number of intervals without any incoming message after which the connection is declared dead. Two timers implement it:30

    • HBT (heartbeat transmit) runs for the heartbeat interval and is restarted on every message sent. When it expires, the TML sends a heartbeat message.
    • HBR (heartbeat receive) runs for the interval × dead factor and is restarted on every message received. When it expires, the TML aborts TCP and reports a protocol abort with diagnostic 'heartbeat receive timeout' (132).

    With the illustrative values above, an idle TML sends a heartbeat every 30 s and gives up after 150 s of silence. A heartbeat interval of 0 disables the mechanism.30 The heartbeat is how ISP1 meets the transfer services' requirement to detect communications failure, which they then treat as a 'protocol abort'.31

    Sequence based on §2.5.3–2.5.4 and §3.3.4 of CCSDS 913.1-B-2.3233

    On the responding side, any failed check on the first message ends the connection silently with TCP-ABORT and no TML diagnostic. This happens for a header that does not parse, a first message that is not a context message, the wrong protocol ID or version, or a TMS timeout before the context message and the first SLE PDU arrive.33 If the heartbeat parameters are out of range, §2.5.3 describes a PEER-ABORT with the TML diagnostic 'heartbeat unacceptable' (Annex A code 130, 'heartbeat parameters not acceptable'). The detailed §3.3.4 instead only says that the TML starts its timer "if the values are acceptable", and §2.5.4.2 says it aborts with TCP-ABORT.293233 The start-up timer is ISP1's only defence against unauthenticated users holding resources open.20 If the TMS timer expires after the context message but before a valid SLE PDU, the TML also informs the higher layers with a protocol abort.33

    Redundant hosts. A responder port identifier may map to several sockets. The initiator then connects to all of them at once, keeps the first that succeeds, and aborts the others. This relies on only one responding host listening at any time, and the standard leaves open how that is ensured.3435

    Release and abort¶

    Procedure Trigger What the TML does
    Orderly release (initiator) TML-DISCONNECT-request after UNBIND Closes the TCP connection36
    Orderly release (responder) TML-DISCONNECT-request after UNBIND return Stops HBT, restarts HBR, and waits for the peer to close. Aborts if data arrive or HBR expires36
    Peer abort TML-PEER-ABORT-request Sends the diagnostic as one urgent byte, stops HBT and HBR, starts CPA (close after peer abort). Discards incoming data, closes when the peer closes, and aborts TCP if CPA expires28
    Receiving an abort TCP urgent data indication Discards data up to the urgent byte and reads it. Codes 0–127 give PEER-ABORT-indication; TML codes give PROTOCOL-ABORT-indication. Then closes28
    Simultaneous aborts Urgent data after sending one's own Discards up to and including the urgent byte, closes, and does not report the peer's diagnostic28
    Silent abort TML-RESET-request (for example on return timeout) TCP-ABORT, nothing sent28
    Protocol abort TCP error, send timeout, or peer close before DISCONNECT or urgent data PROTOCOL-ABORT-indication37

    If the TCP API does not support ABORT, ISP1 allows TCP-ABORT to have the same effect as a normal disconnect.28

    Diagnostic code ranges and TML codes¶

    PEER-ABORT diagnostics are a single octet. Codes 0 to 127 belong to the transfer service specifications, 128 to 199 to ISP1, and 200 to 255 to implementations.38

    Code TML diagnostic
    128 TML protocol error (for example a context message received after start-up)
    129 Badly formatted TML message
    130 Heartbeat parameters not acceptable
    131 Association establishment timeout
    132 Heartbeat receive timeout
    133 Unexpected disconnect by peer
    134 Premature disconnect during peer abort
    135 Timeout during peer abort
    199 Other reason

    Sources: Annex A and §3.3.7.3940

    ISP1 and its ESA precursor¶

    ISP1 grew out of ESA work. Its precursor was ESA's Specification of an SLE API Proxy for TCP/IP and ASN.1 (SLES-SW-API-0002-TOS-GCI, issue 1.1, February 2001), which took its authentication scheme and service instance identifier from ESA's SLE C++ Application Program Interface for Transfer Services (SLES-SW-API-0001-TOS-GCI, December 2000).4445 When ISP1 was published, all known SLE implementations were based on the ESA proxy specification. Two differences remain:44

    • That generation used draft service specifications with BIND version 1 (RAF 911.1-R-1.7, RCF 911.2-R-1.7, CLTU 912.1-R-1.99h), whose ASN.1 differs. An initiator talking to such a responder must send version 1 and use the old types. The BIND encoding itself did not change.
    • Old service instance identifiers distinguished vcf= and mcf=. The standard uses rcf=, so a timely online RCF instance was vcf=onlt1 or mcf=onlt1 and is now rcf=onlt1.

    The SLE API (CCSDS 914.0-M-2)¶

    Purpose and scope¶

    The SLE API is a C++ API, independent of the communications technology, for applications that implement SLE services in either the user or the provider role. It also aims to simplify gateways between different technologies. Its goal is that an API package for a platform can be supplied to a new SLE user and integrated with little investment.3 It defines components, their functions, their interfaces and their externally visible behaviour, but not implementations, internal design or the communications technology.46 Service-specific API books complement the core:4647

    Book Service In this library
    CCSDS 915.1-M-2 RAF API yes (library; see RAF with the SLE API)
    CCSDS 915.2-M-2 RCF API no
    CCSDS 915.5-M-2 ROCF API no
    CCSDS 916.1-M-2 FCLTU API no
    CCSDS 916.3-M-2 FSP API yes (library; see the FSP API)

    Two companion Reports belong to the same family: Summary of Concept and Rationale (914.1-G-1, January 2006) and Application Programmer's Guide (914.2-G-2, October 2008), the latter with guidance and source code examples for developers. Neither is in this library.7273

    Two optional features of the service standards are deliberately left out. BIND version negotiation is not supported: an unsupported version is simply rejected. Provider-initiated binding is not supported either, although the management parameters for it exist.48

    • API Proxy. All technology-specific functions live here, hidden from clients. The Proxy also enforces system-level access control and authenticates peers. ISLE_ProxyAdmin configures it. ISLE_AssocFactory creates Associations, which exchange PDUs through ISLE_SrvProxyInitiate and the client-supplied ISLE_SrvProxyInform. The PDU Translator converts between API operation objects and the transfer encoding; it is the only part of the Proxy that depends on the service type. A Proxy declares its technology with a Protocol ID, and the service element can use several proxies.1150
    • API Service Element. It holds the service instances. A service instance checks that PDUs fit its role, service type and version. For return services, a SI User unpacks each TRANSFER-BUFFER into individual TRANSFER-DATA and SYNC-NOTIFY operations. A SI Provider fills the transfer buffer, runs the release timer, performs the timely online discard, and answers GET-PARAMETER and status reporting itself.5152
    • SLE Operations. These are operation objects for each SLE operation, such as ISLE_Bind, ISLE_Unbind, ISLE_PeerAbort, ISLE_Stop, ISLE_ScheduleStatusReport, ISLE_TransferBuffer and IRAF_TransferData, all derived from ISLE_Operation or ISLE_ConfirmedOperation.53
    • SLE Utilities. Helper objects for time, service instance identifiers, credentials, security attributes and memory (IMalloc, a subset of the COM memory manager).5455
    • SLE Application. Supplied by the user of the API, not part of it. It must provide ISLE_ServiceInform, logging (ISLE_Reporter), optional tracing (ISLE_Trace) and a time source.5657

    All interfaces derive from a COM-style IUnknown, so objects are navigated with QueryInterface(). Each interface has a GUID. Compatibility between applications built against different API issues is guaranteed only for interfaces with the same GUID.5859

    Service-specific extensions: the RAF and FSP books¶

    The core uses placeholders such as I<SRV>_SI User, I<SRV>_SI Provider, I<SRV>_SIAdmin and I<SRV>_SIUpdate. Each service book fills them in. Both books in this library follow the same pattern: the API Service Element and SLE Operations components are extended, and the API Proxy must in addition encode and decode the service's PDUs.7980

    Flow control and buffering¶

    The API pushes the SLE buffering rules down into the service element and the Proxy, so that applications see only operations:515260

    • Inbound limits. An Association stops reading from the network when more than N1 received PDUs, or N2 ≤ N1 TRANSFER-DATA or TRANSFER-BUFFER PDUs, are waiting for the client. This builds back-pressure on TCP.
    • Outbound queue. A positive transmission request means only "queued". On request, the Association reports actual transmission. It can also remove TRANSFER-BUFFER PDUs that have not started transmission. This is how the timely online discard is implemented: if the previous buffer has not been sent, it is discarded and the next buffer starts with a 'data discarded due to excessive backlog' notification.
    • Application back-pressure. In complete online and offline modes, and for forward services, the service instance returns a code telling the application to suspend data transfer. It calls ResumeDataTransfer() on ISLE_ServiceInform when transfer can continue.

    Sequential and concurrent behaviour¶

    Every component exposes one of two threading models, through ISLE_Sequential or ISLE_Concurrent. Sequential means only one flow of control passes an interface at a time. The application then has to provide an event loop and timers (ISLE_EventMonitor, ISLE_TimerHandler). Concurrent means several threads may call in at once; the term maps to UML's "concurrent or guarded". A service element can use different models towards the application and towards the proxy. An implementation must support at least one model, and an application must handle the control interface of the model it uses.616257

    Pass-through mode for gateways¶

    As an option, the Proxy supports a pass-through mode for gateways. In this mode it does not insert its own application identifier into BIND invocations and returns, but forwards the identifiers in the operation objects. This keeps end-to-end identification and authentication between the real user and the real provider.63

    States¶

    The Proxy's association state table uses five states: S1 UNBOUND, S2 BIND PEND, S3 BOUND, S4 LOC UNBIND PEND and S5 REM UNBIND PEND.64 The service instance state tables reuse the transfer services' main states ('unbound', 'ready', 'active') and add sub-states that track pending returns between the application and the proxy.65

    Inference

    The 100 KB PDU minimum matters for return services. A transfer buffer of 200 RAF TRANSFER-DATA invocations (the RAF conformance minimum67) of 1,115-octet Solar Orbiter frames already holds 223,000 octets of frame data, more than twice the 100 KB minimum, before any annotation or encoding overhead. An implementation built to the minimum would therefore need a smaller transfer-buffer-size for that mission. Real products are expected to support higher limits.66

    ESA and the SLE API¶

    Both documents record ESA's early role. The ISP1 precursor and the original C++ API specification were ESA documents (SLES-SW-API-0002-TOS-GCI and SLES-SW-API-0001-TOS-GCI). Generation 1 of the CCSDS API keeps interoperability with peers that follow the ESOC TML specification.444549 The ECSS communications handbook points to the ESA ground operations software portal, which includes "the ESA SLE Gateway".68 SCOS-2000 reaches SLE providers through the NCTRS and NIS rather than by embedding an SLE API directly, as described on the SLE overview.

    The reference model adds one point about auditing: although the transfer service specifications define no security auditing, logging attempts at access is a standard feature of the SLE API, on top of what firewall logs provide.91
