    Architecture CCSDS Data link layer Overview

    CCSDS: overview of the protocol stack¶

    The Consultative Committee for Space Data Systems (CCSDS) is a committee set up by the space agencies to solve data-system problems they share. Its member agencies include ESA, NASA, CNES, DLR, ASI, JAXA and others.1 Its results are "Recommended Standards". Endorsing one is voluntary, and a Recommended Standard is reviewed no later than five years after it is issued, as the Space Packet Protocol's statement of intent puts it.2 Together the CCSDS standards define the chain that spacecraft data follows. Telemetry packets are framed by the TM Space Data Link Protocol, protected by channel coding, received by a ground station and, in cross support, delivered to the user over Space Link Extension. Telecommands make the reverse trip as CLTUs, with COP-1 providing retransmission.293948

    This page explains how the protocols fit together. It follows two CCSDS reports: the Overview of Space Communications Protocols (CCSDS 130.0-G-4, April 2023) and the Space Data Link Protocols: Summary of Concept and Rationale (CCSDS 130.2-G-3, September 2015).1032 It ends with a map of every layer, the standard that defines it, the copy in this wiki's reference catalogue and the page that explains it.

    CCSDS document colours

    The protocol itself is specified in a Blue Book (Recommended Standard). Its rationale is explained in a Green Book (Informational Report).10 The reference lists also show Magenta Books (Recommended Practices, such as the SCID code assignment procedures), Yellow Books (CCSDS Records, such as A02.1-Y-4 on CCSDS organization) and retired standards marked "Historical" with an "-S" suffix (for example the SCPS protocols).12

    From fixed TDM formats to a layered stack¶

    Traditional telemetry used Time Division Multiplexing (TDM). Data items sat in a continuous stream of fixed-length frames according to a fixed multiplexing rule, so every project built its own data system.13 When on-board processors arrived, CCSDS standardized a series of protocols. The timeline shows the sequence described in the 2023 overview:13 ESA's own path, from the PSS-04-106 and PSS-04-107 packet standards to the ECSS adoption notices, is told on From ESA PSS to CCSDS and ECSS.

    timeline

    The 2023 overview expects USLP to become the data link protocol for all future robotic and crewed missions.13 Solar Orbiter, which uses the TC and TM Space Data Link Protocols, is an example of the established configuration (see below).7477

    The reference model¶

    CCSDS places its protocols in five layers of the OSI model: Physical, Data Link, Network, Transport and Application. Session and Presentation layers are rarely used over space links.14 CCSDS does not define programming interfaces. It describes services as abstract primitives (.request, .indication), which can serve as a reference for building an API.14

    The physical layer¶

    CCSDS 401.0-B, Radio Frequency and Modulation Systems, is an omnibus standard. It covers the RF signal between spacecraft and ground stations that carries the frames. Proximity-1 has its own physical layer standard.15 ECSS uses ECSS-E-ST-50-05 for the same role, and notes that CCSDS 401.0-B has extra options.61 The library holds CCSDS 401.0-B-32 (October 2021) and ECSS-E-ST-50-05C Rev. 2 (4 October 2011), together with ECSS-E-ST-50-02C on ranging and Doppler tracking; all three are summarised on Radio frequency, modulation and ranging.6768

    The data link layer¶

    CCSDS divides the OSI data link layer into two sublayers:1634

    • The Data Link Protocol Sublayer moves higher-layer data units over one point-to-point space link inside Transfer Frames. Its protocols are TM, TC, AOS, Proximity-1 and USLP, together called the Space Data Link Protocols. TM, TC, AOS and USLP can carry secured user data through the optional Space Data Link Security (SDLS) protocol. No security requirement exists yet for Proximity-1.16 The wider CCSDS security family (threats, the choice of layer, algorithms and key management) is on Security in CCSDS space links.
    • The Synchronization and Channel Coding Sublayer gets frames across a noisy link. It delimits and synchronizes frames, applies error-correcting coding, and generates and removes bit transitions (pseudo-randomization).2534

    The pairing is fixed.1625

    The two link directions use quite different sync-and-coding data units:

    • On the return link (TM), the unit on the channel is the Channel Access Data Unit (CADU): an Attached Sync Marker followed by a frame, a Reed-Solomon codeblock or a codeword, depending on the coding.53 The 32-bit ASM for uncoded, convolutional, Reed-Solomon and concatenated data is 0x1ACFFC1D.54 The service is for fixed-length frames delivered periodically, and it always delivers validated frames.25
    • On the forward link (TC), the unit is the Communications Link Transmission Unit (CLTU): a Start Sequence, BCH or LDPC codewords, and a Tail Sequence (optional for LDPC).58 The 16-bit BCH Start Sequence is 0b1110101110010000, which is 0xEB90.59 The service is for variable-length frames sent intermittently, and the TC coding delivers non-validated frames to the layer above.25 The TC coding standard also defines the Physical Layer Operations Procedure (PLOP) that switches the channel on and off.58

    Between the data link and network layers¶

    LTP (Licklider Transmission Protocol) adds optional reliability over one link. It usually carries each segment in an Encapsulation Packet. IP over CCSDS is a shim that carries CCSDS-recognized IP datagrams over the Space Data Link Protocols.17

    The network layer¶

    CCSDS recognizes two network-layer interfaces: CCSDS-recognized IP datagrams and the Bundle Protocol of Delay Tolerant Networking (DTN). The Bundle Protocol builds a store-and-forward "overlay" network that reaches each link through convergence layer adapters (CLAs). DTN is designed for intermittent connectivity, long and variable delays, high error rates and asymmetric or simplex links.18

    Between the data link protocols and these network protocols sits the shim position, held by either the Space Packet Protocol or the Encapsulation Packet Protocol.143 The Space Packet itself does forwarding: data moves along a path configured in advance by management, labelled only by its APID. It does not do routing, which the overview defines as choosing paths from origins to destinations in a network.112627

    Transport and application layers¶

    • Transport: SCPS-TP, which extends TCP and includes UDP by reference. Internet TCP and UDP can run over IP over CCSDS.19
    • Application: AMS, CFDP, lossless, image and multispectral or hyperspectral data compression, the Space Packet Protocol, and the MO MAL Space Packet binding.20 CFDP is a file transfer protocol that also provides transport functions (complete, in-order delivery without duplicates). It can run over SPP (with mission-assigned APIDs), over EPP, over IP or BP, or directly over a Virtual Channel, MAP or Port.21
    • Mission-specific protocols may also run on top. For ESA missions the most important is the ECSS Packet Utilization Standard (PUS). ECSS-E-ST-50C names it as an example of an "application specific source/sink".2061

    Time stamps in packets use the CCSDS Time Code Formats (CCSDS 301.0-B), which the Space Packet Protocol cites for its secondary-header time field.4 For describing packet formats, the Space Packet Protocol prefers a CCSDS notation such as XTCE.5

    Packets and Transfer Frames¶

    Two kinds of data unit run through the whole stack, and keeping them apart is the key to understanding it:

    Packet Transfer Frame
    Defined by Packet protocols: SPP, EPP, others with an authorized PVN Space Data Link Protocols (TM, TC, AOS, USLP, Proximity-1)
    Scope End to end. Created and used by application processes on board or on the ground. One space link, point to point
    Length Variable TM, AOS and USLP fixed; TC, Proximity-1 and USLP variable
    Identified by APID (SPP) or Protocol ID (EPP), with the Packet Version Number Transfer Frame Version Number, Spacecraft ID, Virtual Channel ID (and MAP ID)

    Compiled from CCSDS 130.0-G-4 §2.2.7, §3.2.1 and §3.5 and CCSDS 130.2-G-3 §4.1.222040

    Fixed-length TM and AOS frames allow simple, robust synchronization on weak, noisy links. Their length must stay constant on a Physical Channel for a Mission Phase and be known to the receiver in advance. Variable-length TC frames let short commands arrive quickly.4022

    Every packet that a data link protocol carries directly must have a Packet Version Number (PVN) recognized by CCSDS and recorded by SANA. Other data units travel inside Encapsulation Packets.22 The protocols put packets into frames in different ways:49

    • TM and AOS concatenate packets into the fixed-length data field, split a packet that does not fit across consecutive frames of the same Virtual Channel, and point to the first packet header with the First Header Pointer. Idle Packets fill frames when there is not enough data.
    • TC carries one or more complete packets per frame. It segments long packets only when MAP channels are in use.
    • In both cases the receiver separates packets using each packet's length field, so the data link service provider must know where that field is and what it means.

    Channels and identifiers¶

    A key idea in every Space Data Link Protocol is the Virtual Channel (VC). One Physical Channel, a stream of bits in one direction, is shared among several logical streams, each possibly with different service requirements.22 The identifiers form a hierarchy:2342

    flowchart TB
  PC["Physical Channel<br/>Physical Channel Name (management only, not in frame headers)"]
  MC["Master Channel (MC)<br/>MCID = TFVN + SCID"]
  VC["Virtual Channel (VC)<br/>VCID; GVCID = MCID + VCID"]
  MAP["MAP Channel (TC and USLP, optional)<br/>MAP ID"]
  PC -->|"one or more"| MC -->|"one or more"| VC -->|"zero or more"| MAP
    • Transfer Frame Version Number (TFVN) separates frame formats. Frames of different Space Data Link Protocols must never be mixed on one Physical Channel.2342 The binary values in the header are 00 for both TC and TM frames (version 1, told apart by management) and 01 for AOS (version 2).43
    • Spacecraft Identifier (SCID) identifies the spacecraft. It is unique only together with the TFVN, which makes the Master Channel Identifier (MCID). TC and TM use 10-bit SCIDs and AOS uses 8-bit ones, so a spacecraft with a TC uplink and an AOS downlink needs two SCIDs. SCIDs are requested through SANA by an agency representative and must be given up for re-use when a spacecraft retires.4445 A Magenta Book (CCSDS 320.0) governs the code assignment, and SANA has replaced the old Space Link Identifiers Blue Book.23 Both documents, and the Solar Orbiter values of every identifier, are described on Space link identifiers.
    • Master Channel (MC): all frames with the same MCID on a Physical Channel. Usually the Physical Channel carries a single MC. When it carries several (for example when one spacecraft relays another, as in an orbiter and lander mission), TM and AOS frames of all of them must have the same length.457
    • Virtual Channel (VC): identified by the VCID within an MC. MCID plus VCID gives the Global Virtual Channel Identifier (GVCID).45
    • MAP channel: TC and USLP can split a VC into MAP channels with a MAP ID. TC uses MAPs to segment packets longer than one frame.4723

    The identifiers sit at the very start of every frame header. A receiver can therefore sort frames into Master and Virtual Channels before it looks at anything else. The two layouts used by most ESA missions are shown below. Both headers continue beyond the fields shown, and the full layouts are on the TM and TC pages.

    Why Virtual Channels? A long, low-priority packet, such as a memory dump, may take several frames on VC 1. If an urgent event report arrives meanwhile, the provider can insert a VC 0 frame between the VC 1 frames, provided it has the buffers for this.41 CCSDS does not standardize the VC multiplexing algorithm, and each project must make sure its own scheme meets its priority and latency needs. The one exception is the SLE Forward Space Packet service, which prescribes the algorithm when it is used.37

    What the data link protocols offer¶

    Packets VC Packet MAP Packet, VC Packet VC Packet MAP Packet

    Variable-length private data (none) MAP Access, VC Access (none) MAP Access

    After CCSDS 130.0-G-4 table 3-2. FSH is the Frame Secondary Header and OCF the Operational Control Field. Proximity-1 has no formal service definition.24 USLP issue 3 (June 2024), the issue in the library, adds VC Packet and VC Access services to the USLP column; see USLP.72

    The services differ in reliability and timing:

    • TC offers each SDU either the Sequence-Controlled (Type-A) service, a go-back-n ARQ run by COP-1 with reports in the CLCW, or the Expedited (Type-B) service, sent once and used for recovery operations or when a higher layer retransmits.35 COP-1 guarantees complete delivery only over the space link (including SLE), not end to end.48
    • TM and AOS have no retransmission. They keep order on each SAP, may signal gaps, and leave retransmission to higher layers such as LTP.3648
    • TM and AOS services are asynchronous (a queue, every SDU sent once), synchronous (a one-SDU buffer released with frames, so an SDU may be sent several times or not at all) or periodic (synchronous at a constant rate).38

    Three combinations are common. Most missions use TC forward with TM return. Missions that need AOS features on the return link use TC with AOS. Missions that need two-way high-rate or audio and video links use AOS in both directions.33

    Managed parameters¶

    The CCSDS protocols keep long-lived settings out of the data stream. Such managed parameters change rarely, a change usually means a major reconfiguration, and keeping them out of the protocol saves bandwidth. A management system that CCSDS does not specify conveys them to the protocol entities.8 Each data link Blue Book has a section listing its managed parameters. Their settings depend on the mission, the deployment and any SLE provider, and SLE parameters are usually set through CCSDS Service Management. SANA keeps one registry per data-link parameter, giving its format, value range, reserved values and the protocols that use it.51

    Typical examples:

    Layer Example managed parameters
    Space Packet Maximum packet length, multiplexing scheme, service type per APID, secondary header contents8
    Encapsulation Minimum and maximum data unit length, valid Protocol IDs and extended IDs9
    TM packet transfer Valid PVNs, maximum packet length, whether incomplete packets must be delivered57
    Data link generally Physical Channel Name, a character string that is also the SAP address of the AOS Insert service46

    Cross support: Space Link Extension¶

    Space Link Extension (SLE) services give users far from the station access to the space link, in a controlled way. They extend the TM, TC and AOS space link services between ground stations and control centres.39 When Space Packets are forwarded end to end, the ground part of the path is usually an SLE service.29

    Direction SLE service Delivers
    Return Return All Frames (RAF) All TM frames from one space link bit stream
    Return Return Channel Frames (RCF) One Master Channel or selected Virtual Channels
    Return Return Operational Control Field (ROCF) MC or VC Operational Control Fields, such as CLCWs
    Forward Forward CLTU (FCLTU) CLTUs (encoded TC frames) for uplink
    Forward Forward Space Packet (FSP) Packets from one user, without coordination with other users
    Forward Enhanced FCLTU (EFCLTU) Uncoded AOS (or TC) frames for uplink

    After CCSDS 130.2-G-3 §3.5.39 In the 2023 overview, the FSP specification is listed as "Historical" (CCSDS 912.3-B-3-S).12 See SLE concept, return services, FCLTU, FSP, ISP1 and the SLE API and the cross support reference model and service management.

    Typical end-to-end configurations¶

    The examples in the 2023 overview show three ways to move user data from an on-board end system through an on-board relay (the spacecraft data handling system) and a ground relay (the station) to a ground end system. Its §4.1 announces five examples, but issue 4 contains only the three in §4.2 to §4.4.28

    1. Space Packets (or Encapsulation Packets) end to end. At each relay, a mechanism that SPP does not specify reads the APID and forwards the packet as instructed. There is no end-point address, and the scheme works by management and agreement.29 PUS telemetry and telecommands, which ECSS-E-ST-70-41C carries in Space Packets, follow this pattern.6
    2. IP over CCSDS. IP datagrams in Encapsulation Packets, routed at each hop by destination address. It suits missions that need Internet integration, where connectivity and round-trip light time allow it.30
    3. Bundle Protocol. Store-and-forward routing of bundles through CLAs, for example over LTP on a CCSDS data link.31

    TC MAP channels MAP 0 for CPDU (high-priority, HPC-1) commands, MAP 1 for normal commands. No segmentation (segment flags 11). Several packets may be aggregated in one segment.73
    TM frames Fixed 1115 octets (8920 bits). Data field 1099 octets. Secondary header with a 24-bit VC frame count extension. CLCW in the OCF of every frame. Frame Error Control in every frame.777678
    TM Virtual Channels VC4 real-time high priority; VC5 critical event log playback; VC0 real-time; VC1 playback from OBC mass memory; VC2 and VC3 playback from the SSMM; VC7 idle frames only. Priority in that order. VC6 is marked "Not Required".77
    Packets Space Packets with PUS version 1 (PUS-A) data field headers; see Space Packet: Solar Orbiter case study75

    In the MIB, all 125 commands that use the CPDU header HPC1_TC are flagged high priority (CCF_HIPRI = 'Y') and carry CCF_MAPID = 0, which matches the MAP 0 rule above.79 The SCOS-2000 import ICD uses CCF_MAPID only for high-priority commands and calls it irrelevant otherwise.80 Of the 5318 nominal (NOM_TC) commands, none is high priority. 5113 leave CCF_MAPID blank, 128 set it to 1 and 77 (all on APID 876) set it to 54. By the ICD's rule these values have no effect.7980

    Inference

    The TM frame length adds up: 6 octets of primary header, 4 of secondary header (1-octet ID plus 3 octets of frame count), 1099 of data field, 4 of OCF and 2 of frame error control give 1115 octets. The ICD gives each component separately and does not show the sum. The TC Virtual Channel identifiers are unclear in the ICD. It calls the suggested values "Zero and One" but then lists them in binary as 000001 and 000010.7478

    Frequently asked questions¶

    How do the Space Data Link Protocols differ from HDLC? They assume powerful coding, modulation and synchronization below them, and their frames are designed for efficient synchronization and decoding. HDLC was designed for nearly noise-free wire links. The CCSDS frames are also upward-compatible with older TDM frame formats, so existing baseband equipment could be reused.50

    Are they secure? TM, TC, AOS and USLP can carry SDLS-protected data (authentication, encryption, or both), but SDLS is optional.5016 See SDLS.

    Does COP-1 work for deep space or blind commanding? Yes. For long round-trip times, a shorter retransmission timer or repeated transmission in the coding sublayer keeps the uplink busy. For blind commanding without telemetry, the Expedited service needs no feedback loop.52 See COP-1.
