    Unified Space Data Link Protocol (CCSDS 732.1-B-3)¶

    The Unified Space Data Link Protocol (USLP) is the newest CCSDS protocol for the Data Link Protocol Sublayer. It is a single protocol for space-to-ground, ground-to-space and space-to-space links.2 CCSDS released it in 2018 and envisions it as the data link protocol of future robotic and crewed missions, in place of TM, TC, AOS and Proximity-1.121122 In this wiki's reading (see the comparison below, flagged as inference), it combines features of its predecessors. From TM and AOS it takes fixed-length frames, idle frames, the First Header Pointer and the Insert Zone. From TC it takes variable-length frames, Multiplexer Access Points and COP-1. From Proximity-1 it takes the source-or-destination addressing and COP-P. The standard itself names as additions a larger maximum frame (up to 65 536 octets), a larger spacecraft address space (16-bit SCIDs), a frame counter whose length can be configured, and a small header at the start of each data field that says how the data is organized.8750

    This page follows CCSDS 732.1-B-3 (June 2024, with Editorial Change 1 of October 2024), held in the library. Issue 3 adds the Virtual Channel Packet and Virtual Channel Access services and allows more than one frame per CLTU, as in the TC specification. It also adds a table, a diagram and text on the processing order of COP and SDLS to the security section, as TC has.1

    Why a unified protocol¶

    The rationale is set out in §2.1.2 of the standard:89

    • Bigger frames. The maximum frame is larger than in earlier protocols. High-rate missions then handle fewer frames.
    • More spacecraft. A larger address space identifies more spacecraft. The SCID grows to 16 bits so that future SCID requests can be met.109
    • A counter that scales. Frame sizes now range much more widely, so the frame sequence counter has a configurable size.
    • Segmentation and blocking. Large SDUs can be cut into smaller pieces. On a noisy link each piece is then less likely to be lost, and a retransmission resends only a small piece. Small SDUs can be grouped into one frame for efficiency.
    • Optional reliability and security. COP-1 or COP-P provide reliable delivery and SDLS provides security. Both are selectable per Virtual Channel.1012

    The same frame format runs over every CCSDS synchronization and coding standard. Over the TM standards (131.0, 131.2, 131.3) the Physical Channel carries fixed-length frames as a continuous bit stream. Over TC (231.0) and Proximity-1 (211.2) coding it carries variable-length frames in bursts. Even then, fixed-length frames can be sent asynchronously by setting the Master or Virtual Channel frame type to "Fixed Length".33

    How a received frame is validated depends on the coding below it:33

    • TM coding: the sublayer delivers fully validated frames, with or without the optional FECF.
    • TC coding: the sublayer delivers decoded octets that may be incomplete or include fill data. USLP itself must delimit the frames and validate them (see receiving end).
    • Proximity-1 coding: the mandatory CRC-32 of the PLTU gives fully validated frames.

    Channels and addressing¶

    A USLP frame carries four identifiers: TFVN, SCID, VCID and MAP ID. They nest as follows:13

    \[\begin{aligned} \text{MCID} &= \text{TFVN} + \text{SCID}\\ \text{GVCID} &= \text{MCID} + \text{VCID}\\ \text{GMAP ID} &= \text{GVCID} + \text{MAP ID} \end{aligned}\]

    All frames with the same MCID on a Physical Channel form a Master Channel, those with the same GVCID a Virtual Channel, and those with the same GVCID and MAP ID a MAP Channel. A VC therefore consists of one or more MAP Channels. As in TM and AOS, the Physical Channel Name is set by management and never appears in the frame.13 The SANA entries (see Space link identifiers) created or changed by USLP fix the ranges. SCIDs run from 0x0000 to 0xFFFF. The 20-bit "global" SCID (TFVN.SCID, the same thing as the MCID) runs from 0xC0000 to 0xCFFFF. MAP IDs are limited to 0000 to 1111, and the full 6-bit VCID range applies.119

    The overview report compares identifier ranges across protocols. USLP allows 0 to 65 535 for the SCID, 0 to 63 for the VCID and 0 to 15 for the MAP ID. TC allows 0 to 1023, 0 to 63 and 0 to 63, and AOS allows 0 to 255 and 0 to 63, with no MAP ID.124

    The USLP Transfer Frame¶

    A USLP Transfer Frame contains these fields, in this order and with no gaps:43

    # Field Length Presence
    1 Transfer Frame Primary Header 4 to 14 octets Mandatory
    2 Transfer Frame Insert Zone Integral number of octets Optional (fixed-length Physical Channels only)
    3 Transfer Frame Data Field (TFDF) = TFDF Header (1 to 3 octets) + Transfer Frame Data Zone (TFDZ) Varies Mandatory
    4 Operational Control Field (OCF) 4 octets Optional, flagged in the header
    5 Frame Error Control Field (FECF) 2 octets Optional (per Physical Channel)

    The TFDF may be up to 65 529 octets long.58 On its own, "Transfer Frame" in the standard means the non-truncated frame. The truncated frame, with only a 4-octet header, is a special short form for brief commands; see Truncated Transfer Frames.3 Bit numbering follows the usual CCSDS convention: bit 0 is transmitted first and is the most significant bit, and spare bits are zero.5

    Transfer Frame Primary Header¶

    The non-truncated Primary Header has 13 fields:44

    Field Bits Values Meaning and rationale
    Transfer Frame Version Number 0–3 0b1100 Identifies the USLP Version-4 frame.45 Proximity-1 used the last free 2-bit value, 11; USLP appends 00 to make a 4-bit field with room for future versions.106
    Spacecraft Identifier 4–19 0 to 65 535 Assigned by SANA. With the TFVN it forms the 20-bit MCID.45119
    Source-or-Destination Identifier 20 0 = source, 1 = destination Says whether the SCID names the sender or the intended receiver of the frame. The Proximity-1 green book discusses when to use which, but the field is not limited to proximity links.46
    Virtual Channel Identifier 21–26 0 to 62; 63 reserved VCs need not be numbered consecutively. VCID 63 is used only for OID frames.4759
    MAP ID 27–30 0 to 15 Identifies up to 16 MAP Channels in a VC. With one MAP the value is constant. With several MAPs, an SDU belongs to one MAP only, and it must be complete before an SDU of another MAP goes out on that VC. MAPs are SAPs and may be designated for sequence-controlled or expedited SDUs.48
    End of Frame Primary Header Flag 31 0 = full header, 1 = truncated Set to 1, the header ends after bit 31.49
    Frame Length 32–47 0 to 65 535 Count C = total frame octets − 1, measured from the first header octet to the last octet of the FECF, OCF or TFDF, whichever comes last. This caps a frame at 65 536 octets. On fixed-length channels the TM coding options may limit the allowed values.50
    Bypass/Sequence Control Flag 48 0 = sequence-controlled, 1 = expedited Decides whether the FARM's Frame Acceptance Checks apply. It is equivalent to the Proximity-1 QoS Indicator.51
    Protocol Control Command Flag 49 0 = user data, 1 = control information Says whether the TFDF carries protocol control commands. It is equivalent to the Proximity-1 PDU Type.52
    Reserve Spares 50–51 0b00 Reserved for future CCSDS use.53
    OCF Flag 52 0 = absent, 1 = present Flags the OCF in each frame, so the OCF can be included frame by frame.54
    VCF Count Length 53–55 0 to 7 Length in octets of the VCF Count field that follows. Fixed for a given VC.55
    VCF Count 56 onward 0 to 56 bits The frame sequence counter of this VC. Absent when the length is 000.56

    Header length

    The fixed part of the non-truncated header is 56 bits (7 octets). Adding a VCF Count of \(n\) octets gives a header of \(7+n\) octets, from 7 to 14. That is the "4 to 14 octets" of the frame layout, with the 4-octet case being the truncated header. This arithmetic follows from the field sizes in §4.1.2.4443

    Bypass and Protocol Control Command flags together¶

    The FOP sets these two flags. Read together, they say what kind of frame it is:5379

    Bypass Protocol Control Command Meaning COP-1 name / COP-P name
    0 0 User data, subject to the FARM's acceptance checks (sequence-controlled service) Type-AD frame / Sequence-Controlled U-frame
    0 1 Reserved for future use —
    1 0 User data, acceptance checks bypassed (expedited service) Type-BD frame
    1 1 Protocol Control Commands, acceptance checks bypassed Type-BC frame / SPDU

    On a TC-coded link, every received frame first passes the basic USLP Frame Validation Checks, whatever the Bypass Flag says.51

    Virtual Channel Frame Count¶

    The VCF Count Length field (3 bits) picks the counter size. Each VC keeps its own counter, and the length of a given VC never changes:55

    VCF Count Length Count field Maximum count
    000 absent not applicable
    001 1 octet 255
    010 2 octets 65 535
    011 3 octets 16 777 215
    100 4 octets 4 294 967 295
    101 5 octets 1 099 511 627 775
    110 6 octets 281 474 976 710 655
    111 7 octets about 7.2 × 10^16

    The count increments by one for each frame sent on the VC, modulo the maximum plus one. A VC may keep two counters: a Sequence-Controlled Counter for frames with Bypass = 0, and a FARM-B (Expedited Frame) Counter for frames with Bypass = 1. This mirrors TC and Proximity-1, which both need a sequence count and an expedited count on the same VC.56 The managed parameters set the count length separately for each QoS.95 That sits uneasily with §4.1.2.11.4, which says the VCF Count Length of a VC is invariant; the standard does not reconcile the two.55 For COP-1 the FOP supplies the Frame Sequence Number that goes into the count.79 The counter should not be reset before it reaches its maximum. After an unavoidable reset, completeness cannot be judged and SDUs spanning frames may not be reassembled.56 For Proximity-1 operation the length is set to 001, one octet.110

    Truncated Transfer Frames¶

    Annex D defines a truncated Transfer Frame for short forward-link or direct-from-Earth telecommands. CCSDS does not currently expect it to be used for cross-support on direct-to-Earth links.116 Its header keeps only the first six fields, with the End of Frame Primary Header Flag set to 1:117

    The rules for truncated frames are:116117118

    • They are allowed only on VCs whose "VC Transfer Frame Type" is "Variable Length". Every truncated frame of a VC has the same length, set by the VC parameter "Truncated Transfer Frame Length". The frame has no length field of its own.
    • The length is at least 6 octets (4-octet header, 1-octet TFDF header and one data octet). It is at most 32 octets, so that the whole frame fits in one LDPC (512,256) codeword of the TC coding standard.
    • There is no Insert Zone, no OCF and no FECF. The TFDF header is one octet: construction rule 111 (no segmentation) and the UPID "Mission Specific Information-1". The TFDZ holds at most 27 octets.
    • There is no Bypass or Protocol Control Command flag, so the frames are handled as expedited user data (COP-1 BD service).
    • With SDLS the frame carries a 6-octet Security Header and a 16-octet Security Trailer, both mandatory. SDLS is allowed only if the truncated length is at least 28 octets. A different Security Association should be used than for VCs with non-truncated frames.
    • Truncated and non-truncated frames are never mixed in the same CLTU.

    The header length of 4 octets plus the 1-octet TFDF header gives 5 octets. That matches the 5-octet primary headers of TC and Proximity-1, which keeps backward compatibility.117

    Inference

    The 28-octet minimum for SDLS on truncated frames is exactly 4 (header) + 6 (Security Header) + 1 (TFDF header) + 1 (one TFDZ octet) + 16 (Security Trailer). With the 32-octet maximum, a secured truncated frame can therefore carry at most 5 octets of user data. The standard states the 28-octet rule but does not show this sum.

    Transfer Frame Insert Zone¶

    The Insert Zone is optional and serves the periodic Insert Service. Physical Channel parameters control whether it is present and how long it is. When present, it is in every frame of a Physical Channel whose frame type is "Fixed Length", OID frames included. It holds exactly one IN_SDU and its length stays fixed for the Mission Phase.57 It may be present only when the Physical Channel frame type is "Fixed Length".93 It is not allowed in proximity operations or in truncated frames.111

    Transfer Frame Data Field and its header¶

    The TFDF follows the Primary Header, or the Insert Zone if present. It is an integral number of octets: the frame length minus the header, Insert Zone, OCF and FECF. It consists of a TFDF Header and a Transfer Frame Data Zone (TFDZ).58 The TFDF Header is what lets one frame format carry packets, private SDUs, streams and control commands. It states how the zone is organized and which protocol the data belongs to.7

    TFDZ Construction Rules¶

    Bits 0–2 of the TFDF Header hold one of eight construction rules. Rules 000 to 010 apply to fixed-length TFDZs and rules 011 to 111 to variable-length ones. The VC parameter "VC Transfer Frame Type" decides which kind a VC uses.62

    Rule TFDZ Name Content
    000 Fixed Packets Spanning Multiple Frames CCSDS packets concatenated across frame boundaries. The First Header Pointer is required.63
    001 Fixed Start of MAPA_SDU or VCA_SDU All or the start of a MAPA_SDU or VCA_SDU, beginning at the first TFDZ octet. The Last Valid Octet Pointer marks its end, or is all ones if it continues.63
    010 Fixed Continuing Portion of MAPA_SDU or VCA_SDU The continuation of an SDU begun earlier. The pointer marks its end, or is all ones.63
    011 Variable Octet Stream An octet-aligned stream with no start or end, for example video.63
    100 Variable Starting Segment Only the first segment of an SDU (MAPA_SDU, VCA_SDU or packet) that is longer than the maximum transmission unit of the SAP.63
    101 Variable Continuing Segment A middle segment of that SDU.63
    110 Variable Last Segment The last segment of that SDU.63
    111 Variable No Segmentation One MAPA_SDU, one VCA_SDU, one or more complete packets, one or more control commands (COP-1, COP-P or SDLS), or one or more Proximity-1 SPDUs.64

    The placement rules are as follows. A MAPA_SDU or VCA_SDU always starts at the first octet of the TFDZ of its first frame. The first packet in a variable-length TFDZ also starts at the first octet. The remaining segments of an SDU travel in frames with the same SAP (GMAP ID or GVCID) and contiguous VCF Counts. Completeness can therefore be checked from the counter.6273 Several complete packets may be blocked into one variable-length TFDZ, provided they fit within the VC's maximum frame and share the same QoS.64

    USLP Protocol Identifier (UPID)¶

    Bits 3–7 hold the UPID. It identifies the CCSDS-recognized protocol, procedure or type of data in the TFDZ, and it must be a value from the SANA UPID registry.65 SANA manages the full range 00000 to 11111.119 The standard names some entries but does not list the numbers. Those named are "Only Idle Data" (used by OID frames) and "Mission Specific Information-1" (used by truncated frames). It also notes that values 00001 and 11111 do not apply to Proximity-1 operations.59118112 The numeric UPID assignments are not stated in the available sources. Check the SANA registry.

    First Header Pointer / Last Valid Octet Pointer¶

    The optional 16-bit pointer is used only with rules 000, 001 and 010, the fixed-length rules. It gives an offset within the TFDZ, counting the first octet as 0.66

    • Rule 000, the First Header Pointer (FHP). It points to the first octet of the first packet header that starts in the TFDZ. That lets packet extraction restart after a lost frame. If no packet starts or ends in the TFDZ, the FHP is all ones (0xFFFF). Packet locations after the first are found from the packets' own length fields. If frame M+1 is lost, the FHP of the next frame received skips the leftover part of the split packet.66
    • Rules 001 and 010, the Last Valid Octet Pointer. It points to the last octet of the MAPA_SDU or VCA_SDU, after which the TFDZ is project-specified idle data. It is all ones if the SDU does not end in this TFDZ.67

    Variable-length TFDZs never contain idle data and need no pointer. When a fixed-length TFDZ holding packets must be released before it is full, an Encapsulation Idle Packet completes it. The data in one TFDZ always belongs to a single GMAP ID or GVCID, a single QoS and a single UPID.6872

    Inference

    For packets in fixed-length frames, the USLP TFDF header is 3 octets (rule, UPID and FHP). The AOS M_PDU header is 2 octets (5 spare bits and an 11-bit FHP).127 The extra octet buys a protocol identifier and a pointer wide enough for 65 536-octet frames.

    Only Idle Data frames¶

    On fixed-length Physical Channels, a frame with an idle TFDZ is sent when no VC has a valid TFDF ready at release time. Such an OID Transfer Frame has VCID 63, the only VC used for OID frames, and MAP ID 0. Its TFDF header has rule 001, the UPID "Only Idle Data" and a Last Valid Octet Pointer set to the last octet of the TFDZ. In effect it is one complete MAPA_SDU of idle data. The TFDZ is filled with the same pseudo-noise sequence as in AOS: the 32-cell LFSR \(D^0+D^1+D^2+D^{22}+D^{32}\), all-ones seed in the Fibonacci form, initialized at start-up and never restarted.5960120 OID frames carry no valid user or control data. They may contain an Insert Zone and an FECF, and keeping a VCF Count for them is optional. On variable-length channels the Master Channel Multiplexing Function does not create OID frames at all.6082

    Operational Control Field¶

    The OCF Flag in each frame's header signals whether that frame has an OCF. When present, the OCF is the 4 octets after the TFDF.69 Bit 0 is the Type Flag:69

    • 0: Type-1 Report, containing a CLCW (COP-1) or a PLCW (COP-P);
    • 1: Type-2 Report. Bit 1 is then 0 for project-specific content or 1 for an SDLS Frame Security Report.

    On fixed-length channels, the MC parameter "Inclusion of OCF Required" can force an OCF into every frame of the Master Channel. On variable-length VCs, the parameter "Inclusion of OCF Allowed" lets mission rules decide when to include one. A mission might, for example, include each new OCF_SDU only once, or repeat it until a new one arrives.6994 As with AOS, VCs that carry OCFs must be sent often enough that the COP in use does not time out.70 For Proximity-1 operation, a PLCW or FSR may go in the OCF, even in a frame without a TFDF, or as an SPDU in a separate frame.114

    Frame Error Control Field¶

    The FECF is optional. The Physical Channel parameter "Presence of Frame Error Control" decides whether it is present, and if so it fills the last 16 bits of every frame on that channel for the Mission Phase. It is the same CRC-16 as in TC and the other data link protocols: generator \(X^{16}+X^{12}+X^5+1\), register preset to all ones, MSB first, and a zero syndrome when the frame is good.71104 Depending on the coding layer it may be mandatory.71 Over Proximity-1 coding it is not strictly needed, because the PLTU already carries a CRC-32.115 The AOS page has a worked CRC example.

    Common features and the SDU ID¶

    All the services are unidirectional, asynchronous (no predefined timing rules), unconfirmed, incomplete and sequence-preserving. Gaps and duplicates are possible only on the expedited service. With COP the services gain in-order delivery without error, omission or duplication. With SDLS they gain authentication and encryption on selected VCs.15

    USLP adds an SDU ID to each .request. When reliable delivery is selected, the provider returns a Notify.indication with the same SDU ID once that SDU has actually been transferred. It may also report a failed transfer or other events. The SDU ID is used only for bookkeeping between user and provider at the sending end. It is never sent over the link, and the receiving end sees only .indication.14

    Service attributes¶

    • Sequence-controlled ("reliable delivery"). COP-1 or COP-P use a "Go-Back-n" ARQ with a standard report from the receiving end. They ensure, with high probability, that no SDU is lost, duplicated or delivered out of order.16
    • Expedited ("best effort"). For use when no data link ARQ is needed, or when a higher layer retransmits. An SDU may be sent one or more times (see systematic retransmission below) with no guarantee of delivery. Despite the name, expedited is neither required nor faster for urgent data.17
    • Security. SDLS covers the TFDZ of MAPP, MAP Octet Stream, MAPA, VCP and VCA. It authenticates, but does not encrypt, some header fields. It protects neither COP control frames, nor USLP_MC_OCF and Insert data, nor frames supplied by VCF or MCF users.18
    • Asynchronous, synchronous, periodic. These timing attributes come from the frame multiplexing rules the mission defines. Synchronous transfer is effectively time-division multiplexing. Periodic transfer occurs when a Master Channel's frames are sent back to back.19

    The services one by one¶

    • MAPP carries packets with a CCSDS-authorized PVN, such as Space Packets and Encapsulation Packets, on a MAP Channel. Several users, each identified by GMAP ID and PVN, may share a MAP. Packets from different MAP IDs may be multiplexed on one VC only between complete packets: a new MAP ID cannot appear until the current packet is finished. Without a COP, only best-effort delivery is offered.2235 Primitives: MAPP.request(Packet, GMAP ID, PVN, SDU ID, QoS), MAPP_Notify.indication(GMAP ID, PVN, SDU ID, QoS, Notification Type) and MAPP.indication(Packet, GMAP ID, PVN, QoS, Packet Quality Indicator, Verification Status Code), with the last three optional.40
    • VCP (new in issue 3) does the same per Virtual Channel, without MAPs. The user picks Type-A or Type-B per packet.231
    • MAPA carries private variable-length SDUs. Unlike the fixed-length VCA_SDUs of TM and AOS,135 their length is not limited by the data field, because USLP segments them. The length is not contained in the SDU itself.2436
    • VCA (new in issue 3) carries private variable-length SDUs per VC, one user per VC.2537
    • MAP Octet Stream carries a continuous string of octets with no structure known to the provider. It uses only variable-length frames, because those insert no idle data, and several streams can share a VC on different MAPs.26 It is the USLP counterpart of the AOS Bitstream service in the CCSDS service summary.125
    • USLP_MC_OCF carries 4-octet OCF_SDUs in the OCF. Each frame's OCF Flag signals inclusion. Several users, identified by GVCID, can share it on one Master Channel, and the receiving user demultiplexes by GVCID.2787
    • VCF and MCF pass in fixed- or variable-length frames built by an independent entity. They are offered to trusted users certified during design, so that outside frames cannot harm the link. The submitted frames must leave the OCF and OCF Flag (if USLP_MC_OCF exists), the Insert Zone (if Insert exists) and the FECF empty.282938
    • Insert carries fixed-length IN_SDUs in fixed-length frames, periodically, one user per Physical Channel.3039
    • COPs Management lets one authorized user per VC (or per Port ID for COP-P) run the FOP with Directives. Its primitives are Directive.request(GVCID/Port ID, Directive ID, Directive Type, Directive Qualifier), Directive_Notify.indication(...) and Async_Notify.indication(GVCID/Port ID, Notification Type, Notification Qualifier). The values of Directive Type and Notification Type come from COP-1 (CCSDS 232.1) or Proximity-1 (CCSDS 211.0).3141

    The full primitive definitions are in §3.3 to §3.12 of the standard.42

    Restrictions¶

    • On a MAP Channel with fixed-length frames, MAPA and MAPP cannot coexist.
    • On a VC with fixed-length frames, VCA and VCP cannot coexist.
    • COPs Management cannot coexist with VCF on the same VC, or with MCF.
    • If MCF exists on a Master Channel, no other data transfer service may exist there.
    • Only one USLP_MC_OCF service may exist per Master Channel.
    • MAP Octet Stream cannot exist with fixed-length frames.
    • If VCF, VCA or VCP exists on a VC, no other data transfer service may exist on that VC.32

    Sending end¶

    • MAP Packet Processing (one per MAP Channel that carries packets). In fixed-length TFDZs (rule 000) it concatenates and splits packets, sets the FHP and fills the remainder at release time with an Encapsulation Idle Packet, which can be as short as one octet.72 In variable-length TFDZs it segments an oversized packet (100, 101, 110), or blocks several complete packets (111) if the MAP allows it. The segments of one packet go in consecutive frames of the VC with the same QoS, not interleaved with other packets of that QoS.73
    • MAPA_SDU Generation works the same way with rules 001/010 (fixed length, idle fill and Last Valid Octet Pointer) and 100/101/110/111 (variable length).74
    • MAP Octet Stream Processing places octets unchanged into variable-length TFDFs with rule 011. Release can be bounded by the VC parameter "Maximum delay … for a TFDF to be completed, once started".75
    • MAP Multiplexing (up to 16 instances per VC) queues TFDFs from different MAPs in a management-defined order. CCSDS does not specify the algorithm.76
    • VC Packet Processing is the per-VC counterpart of MAP Packet Processing.77
    • Virtual Channel Generation runs three procedures in order. Frame Initialization takes a TFDF and builds a partial frame with the static header fields. The FOP (COP-1 or COP-P) controls transmission and retransmission from CLCW/PLCW reports and Directives. Frame Finalization completes the header, writing in the Bypass and Control Command flags and the Frame Sequence Number supplied by the FOP.7879
    • VC Multiplexing and MC Multiplexing order frames from VCs and from VCF and MCF users, using algorithms the project defines from priority, release rate and isochronous timing. "Maximum delay … between releases of USLP Frames of the same VC" bounds the latency. MC Multiplexing creates OID frames only when the Physical Channel frame type is fixed length.808279
    • Master Channel Generation puts OCF_SDUs into the OCF of a VC's frames according to management settings. USLP has no Master Channel frame count.81
    • All Frames Generation inserts IN_SDUs, computes the FECF, and passes data units of one or more frames to the coding sublayer, up to a managed maximum per data unit. External VCF and MCF frames bypass the error-control encoding.83

    Systematic retransmission over TC coding¶

    Over TC Synchronization and Channel Coding, USLP may ask the sublayer to send a data unit several times. It does so through the optional Repetitions parameter of ChannelAccess.request. This helps deep-space links, where the long round-trip delay makes COP-1's go-back-n retransmission slow. Management sets one Repetitions value for sequence-controlled data frames (Type-AD) and one for COP control commands (Type-BC) on each VC, with an upper limit per Physical Channel. Repetitions are not allowed for expedited data (Type-BD).3483 The TC coding standard in the library (issue 4, July 2021) still describes one request as carrying "one or more TC Transfer Frames" or "a single USLP Transfer Frame".134 USLP issue 3 (2024) allows more than one USLP frame per CLTU, to match TC.1

    Receiving end¶

    • All Frames Reception comes first (see below).
    • MC Demultiplexing routes frames by MCID and discards those with an invalid MCID. MC Reception extracts any OCF into an OCF_SDU for the USLP_MC_OCF user, then passes every frame on unchanged.8887
    • VC Demultiplexing routes frames by VCID. It discards OID frames once their Insert Zone has been read, and frames with an invalid VCID, and it may flag gaps in the VCF Count.86
    • VC Reception runs the FARM (FARM-1 or FARM-P) when a COP applies, which accepts or discards frames and generates CLCWs or PLCWs. It then decommutes the TFDZ, together with its MAP ID or VCID, for MAP Demultiplexing, VC Packet Extraction or the VCA user.85
    • MAP Demultiplexing and the extraction functions rebuild packets (using the FHP or the segment rules), MAPA_SDUs (removing idle data with the Last Valid Octet Pointer) and octet streams. They discard anything with an invalid MAP ID or VCID, and incomplete SDUs need not be delivered in cross-support.84

    All Frames Reception: delimiting and validation¶

    Over TM or Proximity-1 coding, the sublayer below delivers validated frames. USLP may discard those it flags as received with errors, rechecks the FECF if present, and extracts IN_SDUs. Frames with a detected error may be discarded in cross-support.89 Over TC coding USLP itself must delimit and validate the frames. It applies two procedures in order:90

    The fill-data rule has a subtle side. If fewer than five fill octets remain, they cannot form a frame header and are dropped at once. Up to 6 fill octets are possible with BCH, 7 with LDPC (128,64) and 31 with LDPC (512,256). The 01010101 fill pattern normally fails validation, for example by implying a frame length longer than the octets received. The exception is BCH with randomization when the fill is added after randomizing: the receiver derandomizes octets that were never randomized, and validation may then not catch them.91 The Frame Validation Checks are: an expected TFVN, one of the expected MCIDs, no header values inconsistent with the spacecraft's implemented features, an octet count consistent with the Frame Length (or with the managed truncated length), and a matching FECF if present. A frame that fails any check is discarded.92

    USLP with COP-1 and COP-P¶

    The COP is optional, chosen per VC by the parameter "COP in Effect" (COP-1, COP-P or none). USLP uses the generic terms FOP and FARM for both COPs. Their reports (CLCW for COP-1, PLCW for COP-P) differ but are transparent to USLP.10495 Expedited frames only increment the FARM's expedited counter. In COP-1, Type-BC frames carry the Control Commands "Unlock" and Set V(R). In COP-P a Type-1 SPDU carries Set V(R). Only the COPs Management user may send control commands.114 Over TC coding, the FECF and the Frame Validation Checks guarantee correctness. Over Proximity-1 coding, that is done by the coding sublayer's own CRC.11 The COP-1 page describes the FOP-1 and FARM-1 state machines.

    Solar Orbiter uses the TC Space Data Link Protocol rather than USLP, but its MIB shows the same COP-1 control commands. The commands UNLOCK ("FARM UNLOCK directive") and SETVR are defined in the ccf table with the high-priority flag set and no APID, unlike packet telecommands.145

    USLP with SDLS¶

    SDLS can be enabled per VC or per MAP. When the Security Header is present, SDLS is in use there, and it applies to all frames of that GVCID, truncated frames included.97103 The Security Header follows the Insert Zone (or the Primary Header). An optional Security Trailer follows the TFDF, then the OCF and FECF. The TFDF shrinks by the lengths of these fields, and the Primary Header is unchanged.98 Frames with the Protocol Control Command Flag = 1 carry no Security Header or Trailer and are not protected.97

    The processing order is fixed. At the sending end the Virtual Channel Generation Function runs: Frame Initialization, which reserves empty security fields; SDLS ApplySecurity; the FOP; and Frame Finalization, which writes in the security values. At the receiving end the VC Reception Function runs the FARM, then SDLS ProcessSecurity, then the rest of VC reception.99102

    Several points need care:

    • Security Associations. Several Virtual Channels cannot share an SDLS Security Association.100 SDLS itself also requires one SA per VC when COPs are used.137 Note that §6.4.1 still describes, as in TM and AOS, an option to place the ApplySecurity interface in the VC Multiplexing Function and to have SAs that cover more than one VC or MAP.101 This page follows the explicit "not supported" rule of §6.4.8.1.
    • Retransmission and anti-replay. If Type-AD frames must be retransmitted after Type-BD frames on the same authenticated VC, the anti-replay check rejects the retransmitted frames. Their sequence numbers are lower than those of the BD frames, so they are wrongly reported as security failures. Mixing the two frame types on an SDLS-secured VC is therefore generally not advised, unless BD frames are sent only after all AD frames have been accepted.102
    • Error reporting. A ProcessSecurity error makes VC Reception discard the frame. The optional Verification Status Code tells the service user.102
    • Baseline. The informative SDLS baseline for USLP is AES-GCM authenticated encryption. It has a 14-octet Security Header (2-octet SPI and 96-bit IV) and a 128-bit MAC, the same as for TM and AOS.139

    A Solar Orbiter perspective¶

    Solar Orbiter uses the classic TM and TC protocols, not USLP. Its data still shows how the USLP fields would scale.

    • SCID. The mission's spacecraft ID is 0x28A (650).142 It fits in USLP's 16-bit SCID, as it does in the 10-bit TM/TC field.
    • Frame length. Its 1115-octet TM frames142 match one of the Reed-Solomon lengths that TM coding allows. The frame-length rules of TM coding apply to USLP as well, with a 65 536-octet upper bound instead of 2048 for uncoded frames.136
    • MAP IDs. Solar Orbiter's TC Segment Header uses MAP ID 0 for CPDU (high-priority hardware) commands and 1 for all other commands.143 In the MIB, the ccf field CCF_MAPID matters only for high-priority commands (CCF_HIPRI = 'Y'), and the MIB ICD allows values 0 to 63.144 The release of 16 September 2025 has 5454 commands. Of these, 130 are flagged high priority. 125 of them carry MAP ID 0 (for example ZBC04001, on APID 44). The other five have no MAP ID: UNLOCK, SETVR, RESET, TC_ONLY and REIN_TTR. Values 1 and 54 also appear, but only on non-high-priority commands (128 and 77 rows), where the ICD says the field is irrelevant.145144

    If Solar Orbiter's commanding were carried over USLP, MAP IDs 0 and 1 would fit in the 4-bit USLP MAP ID. The value 54 found in non-high-priority rows would not, but per the ICD it is not used. Nothing in the sources says Solar Orbiter considered USLP. This only illustrates the field widths.
