    Proximity-1 Space Link Protocol (CCSDS 211.0-B-6)¶

    Proximity-1 is the CCSDS link protocol for proximity space links: short-range, two-way radio links, fixed or mobile, between probes, landers, rovers, orbiting constellations and orbiting relays. Such links have short delays, moderate (not weak) signals and short, independent sessions.1 The ECSS handbook calls it a departure from earlier CCSDS link protocols such as TM and TC: contacts are brief and mission control is remote, with long delays, so the two spacecraft set up the link locally by a handshake (hailing), without precise scheduling, and can renegotiate data rates during the contact.194 Proximity-1 then exchanges data reliably and ends the session itself.6 The Blue Book specifies the data link layer. It covers the Frame, Medium Access Control (MAC), Data Services and Input/Output (I/O) sublayers, the protocol data units, the sequence-controlled and expedited transfer, timing services and the procedures that start and end a session between a caller and a responder.2

    This page follows issue 6 of the Blue Book (July 2020, with Editorial Change 1 of September 2024). It adds the USLP annex that maps Proximity-1 onto Version-4 frames, the CCSDS overview Green Book, the ECSS communications handbook and the CCSDS security report.3183193

    Item Value
    Layer Data link layer, in five sublayers: Coding and Synchronization (C&S), Frame, MAC, Data Services, I/O
    Companion standards CCSDS 211.2 (C&S sublayer) and CCSDS 211.1 (physical layer). Neither is in this wiki's library
    Protocol data units Version-3 Transfer Frame (or the USLP Version-4 frame), carried in a PLTU

    Where Proximity-1 sits¶

    The Proximity-1 model has a physical layer and a data link layer. Work is split into a send side, which radiates the transmitted physical channel and acquires the received one, and a receive side, which processes the received bit stream. The transmitter is driven by states. The receiver, once it is on, has no modes: it accepts every valid local and remote directive and delivers the received data units to the users.10 The physical layer takes control variables and PLTUs from the layers above and performs the requested channel coding. On reception it reports two status signals, CARRIER_ACQUIRED and SYMBOL_INLOCK_STATUS, and outputs the coded symbol stream.11

    flowchart TB
    VC["Vehicle controller<br/>(e.g. spacecraft C&DH)"] -- "local directives,<br/>notifications" --- MAC
    U["User data (SDUs)<br/>+ QoS, Port ID, PCID"] --> IO["I/O Sublayer<br/>queues, segmentation,<br/>reassembly, delivery per Port ID"]
    IO --> DS["Data Services Sublayer<br/>COP-P = FOP-P + FARM-P"]
    DS --> FR["Frame Sublayer<br/>build and validate Version-3 frames,<br/>choose next frame to send"]
    MAC["MAC Sublayer<br/>session set-up and end, persistence,<br/>directive decoder, MIB"] --> FR

    CS --> PL["Physical Layer (CCSDS 211.1)<br/>transceiver"]

    Sublayers and their main jobs, after section 2.1.4 and figure 2-1 of the Blue Book.1210

    The five sublayers divide the work as follows:12

    Sublayer Send side Receive side
    Coding and Synchronization (C&S), CCSDS 211.2 Builds a PLTU around each Version-3 or Version-4 frame, inserts idle data, codes the bit stream Delimits PLTUs, checks them (including decoding), passes valid frames up; time-tags data on request
    Frame Builds frames and fills in header fields, decides the order of transmission Checks the version, SCID and source-or-destination flag, routes U-frames to Data Services and P-frames to MAC
    Medium Access Control (MAC) Starts, maintains and ends sessions; changes data rates and other link settings; holds the MIB parameters Accepts directives from the local controller and across the link; sets MODE, TRANSMIT and DUPLEX
    Data Services Runs FOP-P for Sequence Controlled and Expedited service Runs FARM-P
    Input/Output (I/O) Accepts SDUs and routing information from on-board users Delivers SDUs to users through the Port ID given in the frame

    The CCSDS overview counts Proximity-1 among the Space Data Link Protocols. It notes that Proximity-1, like TC and USLP, uses variable-length frames to suit variable-length messages with different latency needs. Like TC, it has a retransmission procedure, COP-P, which the Green Book calls similar to COP-1.189 The Green Book also expects that future missions may use USLP instead of TM, TC, AOS and Proximity-1. Both Proximity-1 and USLP can run over the Proximity-1 C&S sublayer and physical layer.189190 ECSS-E-ST-50C shows the Proximity-1 suite in its protocol architecture figure, but describes it as only one possible choice for proximity links.207 The Space Packet Protocol Blue Book likewise draws Prox-1 beside USLP, TM, TC and AOS as a data link protocol that can carry Space Packets or Encapsulation Packets.206

    Terms used throughout¶

    Term Meaning in Proximity-1
    Caller / responder The caller starts link establishment and manages any negotiation. The responder usually receives the link parameters from the caller. The caller calls on a prearranged channel with predefined parameters.4
    Forward / return link The forward link carries data from caller to responder (typically commands). The return link carries data from responder to caller (typically telemetry).46
    Hailing The persistent activity that a caller uses to set up a link to a responder, in full or half duplex. It does not apply to simplex.4
    Hailing channel The pair of forward and return frequencies used to set up physical communication.4
    Session A dialogue in three phases: establishment, data services (which may include resynchronization and reconnect) and termination. Termination is either coordinated, by exchanging "no more data" directives, or each side decides on its own after communication is lost.6
    Reconnect The caller hails the responder again during a session because no progress is being made. FOP-P and FARM-P variables, including the frame counters, are kept.6
    Resynchronization The caller sees a sequence count anomaly and forces the responder's counter with the SET V(R) activity.6
    U-frame / P-frame A frame carrying user data, or a frame carrying only supervisory protocol data units (SPDUs).57
    Vehicle controller The on-board entity (e.g. the spacecraft computer) that receives the notifications of annex D.7
    Asynchronous data link A sequence of variable-length PLTUs that are not necessarily back to back. Proximity-1 is currently defined only for asynchronous links.477

    Rates have their own names. Rd is the data rate of the PLTU-plus-idle bit stream at the encoder input. Rcs is the coded symbol rate between the C&S sublayer and the physical layer. Rchs is the channel symbol rate at the transmitter output, after optional Bi-Phase-L encoding.9 Bits are numbered as in all CCSDS standards: bit 0 is transmitted first and is the most significant bit, and all spare bits are zero.8

    Addressing: SCID, PCID and Port ID¶

    Proximity-1 uses a triad of identifiers:15191

    • Spacecraft Identifier (SCID). The SCID names the spacecraft that is either the source or the destination of the frame. A separate bit, the Source-or-Destination Identifier, says which.
    • Physical Channel Identifier (PCID). The PCID can select one of two redundant receivers at the receiving end. Either receiver supports both services.
    • Port ID. The Port ID routes user data inside the receiving spacecraft. A port can be logical, such as an application or a transport process. It can also be physical, such as an on-board bus or a hardware command decoder.

    SCIDs for Version-3 frames are assigned by the procedures of CCSDS 320.0. These procedures keep a separate SCID table for each Transfer Frame Version Number. Version 3 ('10') has a 10-bit SCID range of 0 to 1023.28201 See space link identifiers for how SANA assigns them. CCSDS has registered three Port ID uses (bitstream, hardware commands, packets). They are listed on that page.200

    The Proximity Link Transmission Unit (PLTU)¶

    The PLTU is the data unit of the C&S sublayer. It is sized to fit what it carries: a variable-length frame that holds variable-length packets.14 It consists of:22182

    Part Size Content
    Attached Synchronization Marker (ASM) 3 octets 0xFAF320. The 24-bit marker suits short-delay, moderate-signal links and sets the bit error tolerance for synchronization
    Transfer Frame up to 2048 octets Version-3 frame (5-octet header + up to 2043 octets of data field) or a Version-4 frame
    CRC 4 octets CRC-32 for detecting transmission errors

    An idle sequence between PLTUs keeps symbol synchronization. PLTUs are inserted only after a physical connection exists.14 The PLTU itself is specified in CCSDS 211.2, which is not in this wiki's library. Because the CRC-32 is outside the frame, frame validation for COP-P is done by the C&S sublayer, not by a frame error control field.14188

    The Version-3 Transfer Frame¶

    A Version-3 Transfer Frame is a mandatory 5-octet header followed by a data field of up to 2043 octets. A particular implementation may allow less on a given physical channel.23

    Field Bits Values Meaning
    Transfer Frame Version Number 2 (0–1) 0b10 Marks a Version-3 frame. Other values belong to other CCSDS frames.24
    Quality of Service (QoS) Indicator 1 (2) 0 / 1 0 = Sequence Controlled service, 1 = Expedited service. At the receiver, COP-P checks the sequence number of Sequence Controlled frames only. Expedited frames bypass the check.2425
    PDU Type ID 1 (3) 0 / 1 0 = U-frame with user data, 1 = P-frame with SPDUs.26
    Data Field Construction ID (DFC ID) 2 (4–5) 00–11 Says how user data is arranged in a U-frame (table below). Not used in P-frames, where it must be 00.27
    Spacecraft Identifier (SCID) 10 (6–15) 0–1023 Spacecraft that is the source or the destination of the data in the frame.28
    Physical Channel Identifier (PCID) 1 (16) 0 / 1 Selects which of two concurrently operating receivers processes the frame.29
    Port ID 3 (17–19) 0–7 Output port to which the I/O sublayer delivers the SDUs. Must be 0 in P-frames.30
    Source-or-Destination Identifier 1 (20) 0 / 1 0: the SCID is the sender (Local_Spacecraft_ID). 1: the SCID is the intended receiver (Remote_Spacecraft_ID).31
    Frame Length 11 (21–31) 4–2047 Total octets in the frame minus one, from the first header octet to the last data field octet. The maximum frame is 2048 octets.33
    Frame Sequence Number (FSN) 8 (32–39) 0–255 Counts Sequence Controlled frames (SEQ_CTRL_FSN) or Expedited frames (EXP_FSN) separately, per PCID.34

    Ranges as listed in the PICS requirements list.134

    Notes on the header fields¶

    PCID. The PCID is meant for a receiving system with two transceivers working at the same time, for example a primary and a backup. An implementation may also ignore the PCID and accept both values with one set of MIB parameters and one set of state machines, including COP-P. If it does distinguish the two values, each PCID must have its own complete set of MIB parameters and state machines. If only one transponder is powered at a time, the standard advises against using the PCID to select it.29

    Port ID. There are eight ports. They are independent of the physical channel, so all SDUs for the same Port ID reach the same port whatever PCID carried them. CCSDS-reserved values are kept in the SANA registries.30

    Source-or-Destination and SCID checking. The sender fills the SCID field from its MIB: with Local_Spacecraft_ID when the flag is 0 (source), and with Remote_Spacecraft_ID when it is 1 (destination).31 The receiver validates frames as follows:32118

    S/D flag Test_Source SCID compared with Behaviour
    1 (destination) true or false Local_Spacecraft_ID A mismatch rejects the frame
    0 (source) true RECEIVING_SCID_BUFFER (the remote SCID) A mismatch is a session violation and the vehicle controller is notified. If the buffer is still zero, it is loaded from the first source-flagged frame and used for the rest of the session
    0 (source) false (no test) Accepted

    Frame Sequence Number. The FSN increases monotonically and separately for the Sequence Controlled and the Expedited frames of each PCID. The SET INITIALIZE MODE directive resets both counters to 0. SEQ_CTRL_FSN drives the sequence check. EXP_FSN plays no part in frame validation but is needed to correlate time tags in the timing services.34

    Frame Data Field¶

    The data field follows the header without a gap. It holds from zero octets up to the lesser of 2043 octets and Maximum_Frame_Length minus 5.35 In a U-frame the DFC ID says what it holds:27

    DFC ID Content of a U-frame data field Rules
    00 An integer number of complete, unsegmented packets All for the same Port ID and PCID. The first bit of the data field is the first bit of a packet header.36
    01 One segment data unit: an 8-bit segment header and a piece of one packet See below.37
    10 Reserved for future CCSDS definition Must not be used.39
    11 User-defined data (an octet stream) The user may even send frames with an empty data field.39

    In a P-frame the data field holds only SPDUs.39 The packets carried must have a Packet Version Number authorised by CCSDS, such as Space Packets or Encapsulation Packets.18 For the Proximity-1 packet service, the Encapsulation Packet Protocol identifies its channel by TFVN, SCID, PCID, DFC ID and Port ID.202

    The segment header holds two Sequence Flags (01 first, 00 continuing, 10 last, 11 whole packet) and a 6-bit pseudo packet identifier. The pseudo packet ID is a temporary label that the protocol assigns to a user packet during segmentation. Segments of one packet must travel in frames with the same PCID and Port ID. Segments of another packet may be interleaved only in frames with a different PCID or Port ID.376 The receiver reassembles by Routing ID, the combination of PCID, Port ID and pseudo packet ID, and delivers only complete packets. It discards the packet being assembled, and logs the event in the session accountability report, in three cases: the packet length field disagrees with the octets received; the first segment for a Routing ID is not a start segment; or a new packet starts before the last segment of the previous one has arrived.38

    Same flags as TC

    The four sequence flag values are the same as those of the TC segment header (01 first, 00 continuing, 10 last, 11 no segmentation).38203

    Worked example: a U-frame header¶

    The bytes below are illustrative, built for this page from the field definitions. They are not taken from a real link. Take a Sequence Controlled U-frame that carries whole packets to Port ID 2, which the CCSDS port assignment reserves for packets.200 It is addressed (S/D = 1) to an illustrative spacecraft with SCID 42 on PCID 0. The frame is 205 octets long, so C = 204, and its sequence number is 7:2433

    Octet Bits Hex Fields
    0–1 10 0 0 00 0000101010 80 2A TFVN 10, QoS 0, PDU Type 0, DFC 00, SCID 42
    2–3 0 010 1 00011001100 28 CC PCID 0, Port ID 2, S/D 1, Frame Length 204
    4 00000111 07 FSN 7 (a SEQ_CTRL_FSN, because QoS = 0)

    The receiver checks that the first two bits are 10, a Version-3 frame (11 would mean Version-4, and 00 or 01 are rejected). With S/D = 1 it compares SCID 42 with its own Local_Spacecraft_ID. It then hands the U-frame to FARM-P, which accepts it only if 7 equals its V(R).118129

    Supervisory protocol data units (SPDUs)¶

    SPDUs carry protocol directives and reports. Directives configure and control the protocol processor at the receiving node, set up, maintain and end sessions, and carry time correlation and synchronization data. Reports describe the configuration and status of the sending node.13 An SPDU is either fixed-length or variable-length, depending on its SPDU Format ID bit. SPDUs identify and delimit themselves, and they are sent only with Expedited QoS.40

    Fixed-length SPDU: the Proximity Link Control Word (PLCW)¶

    A 1 in the Format ID marks a 16-bit fixed-length SPDU: a 2-bit SPDU header and 14 bits of data. Type 0 is the PLCW. Type 1 is reserved for future CCSDS use.4142 The PLCW reports the progress of the Sequence Controlled service from the receiver back to the sender. It is sent with Expedited QoS.4243

    Field Bits Values Meaning
    SPDU Format ID 1 (0) 1 Fixed-length SPDU.42
    SPDU Type Identifier 1 (1) 0 PLCW (1 reserved).42
    PLCW Retransmit Flag 1 (2) 0 / 1 0: no outstanding rejections, nothing to resend. 1: a received frame left a gap in the sequence numbers and the expected frame must be retransmitted.46
    PCID 1 (3) 0 / 1 The physical channel the report belongs to (from RECEIVING_PCID_BUFFER). Each PCID in use has its own PLCW reporting.45
    Reserved Spare 1 (4) 0 Always 0.44
    Expedited Frame Counter 3 (5–7) 0–7 Modulo-8 counter showing that Expedited frames have arrived.44
    Report Value 8 (8–15) 0–255 The FARM-P variable V(R), reported separately for each physical channel and independently of the I/O port.44

    For comparison, the TC CLCW of COP-1 is a 32-bit report carried in the 4-octet Operational Control Field of TM frames.204205 The PLCW fits in 16 bits and is sent inside a P-frame.42

    Illustrative example. A responder has accepted frames 0 to 7 (V(R) = 8) on PCID 0 and has counted three Expedited frames. Its PLCW is 1 0 0 0 0 011 00001000 = 0x8308.     Services and qualities of service¶

    When a user, for example the vehicle controller, hands over an SDU, it also gives the PCID, the quality of service and the destination Port ID.16 There are two data transfer services and a timing service:1718

    • Packet delivery service. Carries packets whose Packet Version Number is authorised by CCSDS. A packet larger than the frame data field is segmented and reassembled. Smaller packets can share a frame. The Port ID selects the output port.
    • User-defined data delivery service. Carries one user's octet-aligned data unit, whose format the service does not know or use. A large SDU is spread over several frames and delivered frame by frame, without reassembly.
    • Timing services. Time-tag frames for time correlation, and transfer time to a remote asset (see timing services).

    Each transfer has one of two qualities of service, controlled by COP-P:192021

    Inside the data link layer¶

    Frame Sublayer: building, validating and choosing frames¶

    At the sending end the Frame Sublayer takes frames from Data Services and MAC, adjusts field values, builds PLCWs and status reports into P-frames, decides the order of transmission and passes frames to C&S. At the receiving end it checks that a frame is Version-3 or Version-4 and that the SCID and S/D flag allow local acceptance. It routes valid U-frames to Data Services, the SPDUs of valid P-frames to MAC, and PLCWs to Data Services.52 Frames are sent only while TRANSMIT is on. When NEED_PLCW or NEED_STATUS_REPORT is true, the report goes into a P-frame.53

    Each time a frame is needed, the source is chosen by a fixed priority:54

    1. a frame from the MAC queue;
    2. a PLCW or status report, if the last frame sent was a U-frame (U-frame_last_sent true);
    3. an Expedited frame from the I/O sublayer's Expedited queue;
    4. a Sequence Controlled frame, first from the Sent queue if a retransmission is needed, then from the Sequence Controlled queue;
    5. a PLCW or status report, if U-frame_last_sent is false.

    U-frame_last_sent is set true at session start and after any frame other than a report, and false after a PLCW or status report. Steps 2 and 5 therefore alternate reports with user data. While PERSISTENCE is true, only supervisory frames from the MAC queue are sent.54

    MAC Sublayer: persistence¶

    The MAC Sublayer sets up and ends each session and makes any physical-layer change during data services. Many of these operations are a handshake based on the physical-layer signals. Because a control message may be corrupted on the link, each MAC activity uses a persistence process: the expected result must be confirmed before the next activity starts.5556 A persistent activity uses Expedited QoS and the MAC queue. It consists of one or more actions, such as sending directives, followed by a waiting period for a response. Only one activity runs at a time, but activities can be chained. Three are defined: hailing, COMM_CHANGE and resynchronization (SET V(R)).56

    Persistence parameter Meaning
    ACTIVITY Name of the activity
    WAITING_PERIOD Time allowed for the RESPONSE before the activity is repeated or aborted
    RESPONSE The responder's acknowledgement that the activity was accepted
    NOTIFICATION Success or failure message to the local vehicle controller
    LIFETIME How long, or how many times, the activity is repeated before it is aborted

    Per-activity values are MIB parameters (for hailing: Hail_Wait_Duration, Hail_Response, Hail_Notification, Hail_Lifetime).5790 When an activity starts, PERSISTENCE is set true and the Frame Sublayer sends only from the MAC queue. The activity succeeds if the RESPONSE arrives within the LIFETIME and fails otherwise. In both cases the vehicle controller is notified and PERSISTENCE returns to false.58 MAC_FRAME_PENDING tells the Frame Sublayer that a whole frame is in the MAC queue. A Directive Decoder applies received directives to the configuration of both layers. Two buffers hold the egress and ingress clock times, sequence numbers and QoS for the timing service.5960

    Data Services Sublayer and I/O Sublayer¶

    Data Services orders the transfer of user data within the session and provides both qualities of service. On the send side it runs FOP-P, processes received PLCWs, confirms complete SDUs to the I/O Sublayer and accepts frames from it. On the receive side it runs FARM-P on received U-frames.6162 FOP-P reports frame-level accounting, V(S) and VE(S), to the I/O Sublayer for every frame it numbers.65

    The I/O Sublayer is the interface to on-board data systems. For a Version-3 frame its I/O Port ID is the PCID followed by the Port ID. For a Version-4 frame it is the VCID followed by the MAP ID.66 At the sending end the user gives, for each data unit, the QoS, output Port ID, PDU type, DFC ID, Remote_Spacecraft_ID, PCID and S/D flag. The I/O Sublayer then builds the frame data unit and the header (with the FSN still empty) within Maximum_Packet_Size and Maximum_Frame_Length, segmenting packets if needed.67 All data units in one frame must have the same destination, PDU type, PCID, Port ID, QoS and DFC ID.132 The user is told when an Expedited SDU has been radiated, and when a Sequence Controlled SDU has been acknowledged. For the latter, the I/O Sublayer associates each SDU with the FSN of the frame that holds its last octet and checks it against NN(R).6768 Two queues, Expedited and Sequence Controlled, raise EXPEDITED_FRAME_AVAILABLE and SEQUENCE_CONTROLLED_FRAME_AVAILABLE while they hold frames. A frame taken by Data Services leaves its queue for good. The local directive CLEAR QUEUE can empty a queue.6869 At the receiving end the I/O Sublayer reassembles segments and delivers only complete data units to the port named in the frame. With Version-4 frames these functions pass to the USLP service users.133132

    Half duplex and token passing¶

    In half duplex only one side transmits at a time, and the right to transmit passes back and forth as a token in SET CONTROL PARAMETERS.80151 The sender stays in S50 for at most Send_Duration. When that runs out (E38) it sets PERSISTENCE so that only MAC frames are sent. Once nothing is pending and no PLCW is needed (E39), it puts the token into the MAC queue (S56), sends the tail (E42, S58) and turns around to receive (E43, S62, wait for carrier).10891 The receiver expects transmissions for up to Receive_Duration.     Timers, the output FIFO and what gets transmitted¶

    All timers count down at the MIB frequency Interval_Clock, for example 100 Hz. The event fires when a timer reaches 1, and a timer at 0 is inactive. The wait timer (WT) is loaded from whichever MIB duration the state tables call for. The CARRIER_LOSS_TIMER is loaded with Carrier_Loss_Timer_Duration when carrier is lost in mode active (in full duplex, or in half duplex while receiving), and is cleared when carrier returns. A zero interval means "never".939592 When the output FIFO is empty, the next content is chosen by sub-state and flags:115

    Local and remote directives¶

    Local directives come from the local controller and never cross the link: SET MODE, SET INITIALIZE MODE, LOCAL COMM_CHANGE (LCCD), LOAD COMMUNICATIONS VALUE BUFFER, LOCAL_NO_MORE_DATA, SET DUPLEX, SET RECEIVING SCID BUFFER and READ STATUS. In the PICS, LNMD and READ STATUS are optional.99100137 Remote directives are sent to the partner. SET TRANSMITTER and SET RECEIVER PARAMETERS put the recipient's MODE into active. Together with SET PL EXTENSIONS they serve both for hailing and for COMM_CHANGE. SET CONTROL PARAMETERS swaps transmit and receive in half duplex, ends the session, changes duplex and sets up the timing service.102103

    Frame reception and validation¶

    Receiving is set up by SET MODE (connecting-L) or (connecting-T). The Frame Sublayer gets its frames from the C&S ChannelAccess.indication primitive. C&S has already delimited them using the frame length field and rejected any with a CRC-32 error.117 Validation then checks the version (10 for Version-3, 11 for Version-4, 00 or 01 rejected) and the SCID rules shown earlier. Each validated Expedited frame increments the Expedited Frame Counter.118 Validated U-frames go to COP-P. In validated P-frames the SPDUs are delimited, PLCWs go to COP-P and all other directives and reports are executed.119

    COP-P: the Communication Operations Procedure for Proximity links¶

    COP-P works between one sender and one receiver on a direct link. The receiver accepts every valid Expedited frame, and valid Sequence Controlled frames only if they arrive in sequence. It reports its state in PLCWs, and the sender uses them to retransmit Sequence Controlled frames. Expedited frames are never retransmitted. Data can flow both ways at once, so each node runs both a FOP-P (sending) and a FARM-P (receiving).6364

    Modulo-256 arithmetic¶

    All COP-P counters are single octets that count modulo 256. A − B is the number of increments that take B to A. B < A means that A − B is between 1 and 127, B > A that it is between 128 and 255, and B = A that it is 0.120

    FOP-P procedures and state table¶

    The procedures used by the state table:124125

    • Initialize: V(S) = VE(S) = VV(S) = NN(R) = N(R) = 0; R(R) = RR(R) = RESYNC = false; NEED_PLCW = NEED_STATUS_REPORT = true; clear the Sent and SEQ queues.
    • Remove acknowledged frames: drop N(R) − NN(R) frames from the Sent queue.
    • Start / Clear SYNCH_TIMER: load Synch_Timeout if the timer is 0, or set it to 0 (clearing does not trigger a resynchronization).
    • Store this PLCW: NN(R) = N(R), RR(R) = R(R).
    • Send EXP frame: take a frame from the EXP queue, number it VE(S), increment VE(S), report VE(S) to I/O and pass the frame down.
    • Resend SEQ frame: copy frame VV(S) from the Sent queue, increment VV(S), pass it down.
    • Send new SEQ frame: take a frame from the SEQ queue, number it V(S), append a copy to the Sent queue, increment V(S) and VV(S), report V(S) to I/O and pass it down.

    FARM-P¶

    The receiver keeps four variables: V(R), the last acknowledged Sequence Controlled frame + 1; R(S), the retransmit flag copied into the PLCW; N(S), the FSN of the arriving frame; and the 3-bit Expedited Frame Counter.130 Its state table has one state:129

    Event Action
    RE0 session start R(S) = false, V(R) = 0, Expedited Frame Counter = 0, NEED_PLCW and NEED_STATUS_REPORT = true
    RE1 invalid frame Discard
    RE2 valid SET V(R) R(S) = false, V(R) = the FSN in the directive, NEED_PLCW = true
    RE3 valid Expedited frame Pass to I/O, increment the Expedited Frame Counter
    RE4 valid Sequence Controlled frame, N(S) = V(R) Pass to I/O, R(S) = false, increment V(R), NEED_PLCW = true
    RE5 N(S) > V(R) (gap) Discard, R(S) = true, NEED_PLCW = true
    RE6 N(S) < V(R) (already received) Discard
    RE7 Frame Sublayer asks for PLCW content Report R(S), V(R) and the Expedited Frame Counter

    FARM-P passes valid Expedited and in-sequence U-frames to the I/O Sublayer, which buffers and reassembles them and delivers the result through the output port.131

    Timing services¶

    Proximity-1 defines two timing services for Version-3 or Version-4 frames. They provide information for a time correlation function that is outside the standard. Implementations may offer further parameters.70

    Time tag recording. When time tagging is active, a transceiver records the time at which the trailing edge of the last ASM bit of every incoming and outgoing frame crosses its clock capture point. All tags must be correlatable to the enterprise-defined time reference point. MODE must be active, in full or half duplex or in simplex, and tagging may run alongside data transfer. The vehicle controller asks its initiator to send SET CONTROL PARAMETERS with a Time Sample value n. Both MAC sublayers then capture local time, frame sequence number, direction and QoS for n frames and package them for time correlation.7172 The correlation process needs both data sets, the relation of one clock to UTC, all path delays (the spacecraft builder measures those from antenna to radio port, the radio builder those inside the radio, which depend on coding, symbol rate and mode) and the time code formats. Collecting tags in both directions at once improves accuracy.73

    Time transfer to a remote asset. Every transceiver must be able to distribute time. The initiator's vehicle controller may first add the one-way light time to the enterprise time at the planned instant, formatted as a CCSDS Unsegmented Time Code. It then commands a TIME DISTRIBUTION directive with that time, the sender path delay and the OWLT, if used. The responder sets its clock and may add the delays according to its accuracy needs. Accuracy depends on the initiator's own time error, the latency up to transmission, the OWLT accuracy and the delay until the remote master clock is loaded.7475 The ECSS handbook adds that timing services provide time correlation data among units and time-derived ranging measurements.196

    Security¶

    The Proximity-1 data link layer has no security services. Annex E assumes that a layer above or below provides them as needed: authentication where commands must be authentic, integrity against altered commands, software or telemetry, and confidentiality against eavesdropping. It lists the consequences of leaving any of these out.174 The CCSDS security report states that SDLS cannot be used with the Proximity-1 data link protocol. It recommends applying security above the I/O sublayer, to the user data, with all Proximity-1 handling unchanged, which it compares to Transport Layer Security.198 The SDLS Blue Book itself excludes Proximity-1, and the overview Green Book notes that no Proximity-1 security requirements have been set so far.199192 With Version-4 frames, SDLS can be used through the USLP Security Header and Trailer, chosen per VCID.187 See SDLS and security in CCSDS space links. The current issue required no SANA action, and the existing Proximity-1 registries continue.175

    Where Proximity-1 is used: Mars relay¶

    Proximity-1 was partly a response to the need for interoperable Mars spacecraft. The ECSS handbook gives typical scenarios: a base station and a roving vehicle, such as Pathfinder, or an orbiter and a lander, such as NASA's Mars Reconnaissance Orbiter (MRO) talking to ESA's ExoMars rover or NASA's MER rovers.193 It explains the design choices. Contacts are short because of orbiter motion and planetary rotation, and mission control is far away. Proximity-1 therefore sets up links locally by handshake, without precise scheduling, and can renegotiate data rates during a contact as the link budget changes. Frequency-agile transceivers can use a separate hailing channel and working channel, which reduces interference when several landed and orbiting elements are in view.194 The protocol is symmetric, so the same equipment can serve both ends. In practice, however, return rates are often much higher than forward rates: often 256 to 1, and up to 2000 to 1. Overflight geometry, signal strength and light time also vary, so session parameters must be tuned.195

    NASA Mars Odyssey (annex F)¶

    Annex F records capabilities of the Mars Odyssey orbiter (Mars Surveyor Project 2001). They are given for information only:176177178

    • Tone Beacon Mode. A CW tone that tells microprobes to send their data. Four orbiter beacon frequencies (437.1000, 440.7425, 444.3850 and 448.0275 MHz) address several microprobes, and the lander beacon frequency is 401.585625 MHz. A 437.1 MHz tone coherently transponded at 401.585625 MHz supports Doppler measurements.
    • Transmit Standby Mode. This is the default when several landed elements are in view of a hailing orbiter. It stops them all answering at once.
    • Convolutional code. Odyssey's rate ½, constraint-length 7 code does not invert G2, so the encoding field must be set to match.
    • Directive values. Channel 000 is 401.585625 MHz for the responder's return transmissions and 437.1 MHz for its forward reception. The coding options are scrambler, convolutional (no G2 inversion, CRC-32 attached) and bypass. Only 8, 32, 128 and 256 kb/s are available. The mode values are standby, sequence controlled, expedited, unreliable bitstream, tone beacon and (transmitter only) canister.
    • PLCW. Odyssey sets the Expedited Frame Counter to zero (unused), always uses PCID 0, and never sets the Retransmit Flag. A Report Value that fails to increase signals a rejected frame. Odyssey called the PCID field "VCID".
