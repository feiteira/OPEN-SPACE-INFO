    Encapsulation Packet Protocol (CCSDS 133.1-B-3)¶

    The CCSDS Space Data Link Protocols carry only packets whose Packet Version Number (PVN) CCSDS has authorized. The Encapsulation Packet Protocol (EPP) is how anything else reaches a space link, such as an IP datagram, an LTP segment or a private protocol data unit. EPP wraps each such data unit, unchanged, in an Encapsulation Packet. This packet is "Version 8 CCSDS Packet", PVN 0b111. Its header is 1, 2, 4 or 8 octets long, so the overhead can be as small as the data unit allows.411 The 2023 Overview of Space Communications Protocols calls EPP a "shim". It is also the standard carrier of CCSDS-recognized IP datagrams over a space link, through IP over CCSDS.30

    This page follows CCSDS 133.1-B-3 (May 2020, with Editorial Change 1 of November 2020), the issue in the library.1 For the fixed-header alternative, see the Space Packet Protocol.

    At a glance

    Property Value
    Packet Version Number 0b111 (Version 8 CCSDS Packet)11
    Header length 1, 2, 4 or 8 octets, chosen by the Length of Length field10
    Packet length 1 to 4 294 967 295 octets9
    Encapsulated data 0 to 4 294 967 287 octets, one data unit per packet95
    Addressing Encapsulation Protocol ID (3 bits), with a 4-bit extension when the ID is 0b11012
    Idle packet Protocol ID 0b000. The shortest is one octet, 0xE0.1213
    Length field meaning Total packet length including the header (unlike the Space Packet)17
    Security None in EPP; use SDLS or the Bundle Security Protocol23

    Why it exists¶

    CCSDS first designed the Space Data Link Protocols to carry application-layer data put straight into their data fields. EPP is the shim that defines, without ambiguity, how they can also carry other protocol data units, such as internetworking, file transfer or message transfer protocols.2 A data unit that the data link protocols can carry directly has a CCSDS-authorized PVN, listed in a SANA registry. EPP exists mainly to move data units that have no such PVN.4 The overview of the data link protocols puts it this way. Packets with authorized PVNs go straight through the packet services, and packets without one can be carried by the encapsulation service.36

    In 2008, the ECSS communications handbook gave a concrete reason. IPv4 datagrams could be carried directly as packets. The layout of the IPv6 version number, however, required an encapsulation service with low overhead. At that time the authorized PVNs included the Space Packet, the Encapsulation Packet and the IPv4 datagram.4847 The current content of the SANA PVN registry is not in the library, so this page does not list it.

    Space Packet or Encapsulation Packet?

    Earlier issues of this standard ("Encapsulation Service", 133.1-B-1 and B-2) could wrap a data unit in either a Space Packet or an Encapsulation Packet.3647 Issue 3 removes the Space Packet from the available formats and renames the standard.1 At the same time, Editorial Change 1 of CCSDS 133.0-B-2 made the reference-model figure show that the shim position holds either EPP or SPP.26 Carrying another protocol inside Space Packets is still possible, but it is now a mission-specific use of APIDs and no longer part of EPP.27

    Redrawn after CCSDS 133.1-B-3 figure 2-1.4

    EPP is used together with one of the Space Data Link Protocols (TM, TC, AOS, Proximity-1 or USLP). It relies on their Virtual Channel Packet, MAP Packet or Proximity-1 Packet services, and management decides which data link protocol is used.4

    Service features¶

    • A user of EPP is a protocol entity that sends or receives data units with no authorized PVN.5
    • Each data unit is wrapped unchanged in exactly one Encapsulation Packet. It may be any whole number of octets up to 4 294 967 287, within project limits.5
    • Data units given to one Service Access Point are processed in order. No order is kept between different SAPs. CCSDS recommends no flow-control scheme.5
    • Transfer is one-way, with no timing relationship to the data link mechanisms, and the sender gets no confirmation. The provider may signal gaps, and the sequence is kept, although it may have gaps.5

    Inference

    Clause 2.2 says an Encapsulation.indication "acknowledges the receipt of the Encapsulation.request". Clause 3 defines the indication as the primitive that delivers a data unit at the receiving end. That earlier sentence looks like a leftover from an earlier issue.58

    Addressing and service primitives¶

    The user is identified by its Encapsulation Protocol ID (EPI), a value registered in SANA as a "defined Protocol ID". A SAP is identified by three things together: the PVN, the EPI and the SDLP channel that carries the data.6 The SDLP_Channel parameter depends on the underlying service:7

    Underlying service SDLP_Channel contains
    Virtual Channel Packet (VCP) service of TM, TC or AOS Global Virtual Channel Identifier (GVCID)
    MAP Packet (MAPP) service of TC or USLP Global MAP ID (GMAP ID)
    Packet service of Proximity-1 Transfer Frame Version Number, SCID, Physical Channel ID, Data Field Construction ID and Port ID
    Primitive Parameters Generated
    ENCAPSULATION.request Data Unit, SDLP_Channel, EPI By the sending user, to have a data unit transferred through the data link protocol
    ENCAPSULATION.indication Data Unit, SDLP_Channel, EPI By the provider, to deliver a data unit to the receiving user. The effect on the user is undefined.

    After CCSDS 133.1-B-3 clauses 3.2 and 3.3.78

    Two expansions of EPI

    The header specification (clause 4.1.2.3) and clause 3.2.3 call the 3-bit field the "Encapsulation Protocol ID" or "Encapsulation Protocol Identifier". The addressing clause 2.3 and Annex B expand the abbreviation EPI as "Encapsulated Protocol Identifier". Both refer to the same field.671225

    The Encapsulation Packet¶

    An Encapsulation Packet is a Packet Header of 1 to 8 octets followed by an optional Encapsulated Data Field of 0 to 4 294 967 287 octets. The whole packet is 1 to 4 294 967 295 octets.9 The header has three, four, six or seven fields, depending on its length:10

    Field Bits Present in header of Values and meaning
    Packet Version Number 3 (bits 0 to 2) all 0b111, the Encapsulation Packet (Version 8 CCSDS Packet)11
    Encapsulation Protocol ID 3 (bits 3 to 5) all The protocol inside. 0b000 is idle, 0b110 means "see the extension", 0b111 is mission-specific private data. Other values are registered in SANA.12
    Length of Length 2 (bits 6 and 7) all Length of the Packet Length field: 00 none, 01 1 octet, 10 2 octets, 11 4 octets13
    User Defined Field 4 4- and 8-octet headers Mission-specific, privately defined header data14
    Encapsulation Protocol ID Extension 4 4- and 8-octet headers Identifies the protocol when the EPI is 0b110; otherwise all zeros. Values are registered in SANA.15
    CCSDS Defined Field 16 8-octet header Reserved for future CCSDS use, set to all zeros by convention16
    Packet Length 8, 16 or 32 2-, 4- and 8-octet headers Total packet length in octets, header included17

    The four header formats, as bit-field diagrams:10

    Packet Version Number¶

    Bits 0 to 2 are 0b111. Like the Space Packet's PVN, the field leaves room for other packet structures. This value identifies the Encapsulation Packet, which the standard calls "Version 8 CCSDS Packet".11 A receiver can therefore tell an Encapsulation Packet from a Space Packet (PVN 0b000) by the first three bits, even when both share one Virtual Channel.1138

    Encapsulation Protocol ID (EPI)¶

    Bits 3 to 5 name the protocol whose data unit the packet carries. The values CCSDS recognizes are registered with SANA. The standard itself fixes three:12

    EPI Meaning
    0b000 Encapsulation Idle Packet. It may fill space in a fixed-length TM, AOS or USLP Transfer Frame.
    0b110 The 4-bit Encapsulation Protocol ID Extension identifies the protocol.
    0b111 Mission-specific, privately defined data
    others Registered in the SANA "Protocol Identifier" registry

    The 2008 ECSS handbook says the registered values then included IPv6, IPv4 and CFDP.47 The present registry content is not in the library.

    Inference

    The extension field exists only in 4- and 8-octet headers. An EPI of 0b110 is therefore meaningful only with Length of Length 10 or 11. The standard does not state this restriction in so many words.1015

    Length of Length¶

    Bits 6 and 7 give the size of the Packet Length field:13

    Length of Length Packet Length field Header length
    00 absent 1 octet
    01 1 octet 2 octets
    10 2 octets 4 octets
    11 4 octets 8 octets

    When the value is 00, the EPI must be 0b000. Such a packet is an Encapsulation Idle Packet of exactly one octet, with neither a length nor a data field.13 Receivers must accept both fixed and variable header lengths. A sender may keep one header size, or change the size packet by packet to match the payload and reduce overhead.10

    User Defined Field, Protocol ID Extension and CCSDS Defined Field¶

    These fields exist only in the longer headers. The User Defined Field (4 bits) carries mission-specific header data.14 The Encapsulation Protocol ID Extension (4 bits) identifies the protocol when the EPI is 0b110. Otherwise it is all zeros, and its values are registered in a separate SANA registry.15 The CCSDS Defined Field (2 octets, 8-octet header only) is reserved and set to zeros by convention.16

    Packet Length¶

    When present, the Packet Length is the last header field. It holds the total length of the packet in octets, header included.17 This differs from the Space Packet, whose length field counts only the data field and subtracts one.29 A 4-octet length field can represent IPv6 "jumbograms" of up to 4 294 967 287 octets (\(2^{32}-5\)), although that use is unlikely in space.17

    Header length Packet Length field Packet length Encapsulated Data Field
    1 octet absent 1 absent
    2 octets 1 octet 2 to 255 0 to 253
    4 octets 2 octets 4 to 65 535 0 to 65 531
    8 octets 4 octets 8 to 4 294 967 295 0 to 4 294 967 287

    All lengths in octets, after CCSDS 133.1-B-3 table 4-2. An implementation may set a lower maximum for the data field.17

    Encapsulated Data Field¶

    The data field follows the Packet Length field with no gap. It is a whole number of octets and contains the data of the protocol named by the EPI (and the extension, if used). With EPI 0b000 it contains idle data. It is absent when the Length of Length is 00, or when the Packet Length equals the header length. Whenever it is absent, the EPI must be 0b000.18 So an Encapsulation Packet with no data is always an idle packet.

    Encapsulation Idle Packets¶

    An Encapsulation Idle Packet has EPI 0b000 and holds idle data. CCSDS does not specify the idle bit pattern.318 Its value lies in the one-octet minimum. The TM and AOS protocols may fill a frame that must go out at its release time with either an SPP Idle Packet or an Encapsulation Idle Packet. An SPP Idle Packet is at least 7 octets, so in a gap of fewer than 7 octets it spills into the next frame. An Encapsulation Idle Packet can fill a gap of a single octet.3942 USLP goes further. When there are not enough packets at release time, it shall insert one Encapsulation Idle Packet of the right length to complete the frame's data zone.43

  B -->|"1 octet"| D["Insert 0xE0<br/>(1-octet idle)"]
  B -->|"2 to 255 octets"| E["Insert 2-octet-header idle:<br/>0xE1, total length"]

    ECSS took up the option early. ECSS-E-ST-50-03C (2008) already allowed a TM idle packet to be either an idle Space Packet or a "fill encapsulation packet" of 133.1-B-1, and noted that this second option was still being evaluated.45 The 2008 handbook explained that the Fill Encapsulation Packet (the old name) can be one octet long. It also warned that implementations would probably be few for some time.49

    Procedures¶

    At the sending end, the Encapsulation Function takes data units from users and rejects any that break the size limits. It wraps each valid unit in an Encapsulation Packet and passes it to the packet service of the data link protocol underneath.19 At the receiving end, the De-encapsulation Function takes Encapsulation Packets from that packet service, strips the headers, and delivers each data unit to the user named by the EPI or extended EPI.20

    sequenceDiagram
  participant U as Protocol user (sender)
  participant E as Encapsulation Function
  participant L as SDLP Packet Service (VC or MAP)
  participant D as De-encapsulation Function
  participant R as Protocol user (receiver)
  U->>E: ENCAPSULATION.request(Data Unit, SDLP_Channel, EPI)
  alt size outside min/max managed limits
    E-->>U: rejected
  else valid
    E->>L: Encapsulation Packet (PVN 111, EPI, length)
    L->>D: Encapsulation Packet (extracted from Transfer Frames)
    D->>R: ENCAPSULATION.indication(Data Unit, SDLP_Channel, EPI)
  end

    Sequence drawn by this wiki from clauses 3.3, 4.2 and 4.3.81920

    A data link receiver extracting packets from a frame needs to know where each packet ends. The rule below follows directly from the header definition. It is not a numbered CCSDS procedure.

    Parsing an Encapsulation Packet (derived from clause 4.1)

    1. Read octet 0. Bits 0 to 2 must be 111, otherwise the packet is not an Encapsulation Packet. Take the EPI from bits 3 to 5 and the Length of Length (LoL) from bits 6 and 7.
    2. If LoL = 00, the packet is a 1-octet idle packet, so continue at the next octet.
    3. Otherwise the header is 2, 4 or 8 octets for LoL 01, 10 or 11. Read the Packet Length from the last 1, 2 or 4 octets of the header.
    4. The packet occupies Packet Length octets from octet 0. The data unit is Packet Length − header length octets. If the EPI is 000, discard the packet as idle. If the EPI is 110, read the extension from the low 4 bits of octet 1.

    This procedure is this wiki's summary of clauses 4.1.2 to 4.1.3.10131718

    Header size and overhead

    For a data unit of n octets, the smallest legal header is 2 octets when \(n \le 253\), 4 octets when \(n \le 65\,531\), and 8 octets beyond that.17 Wrapping the same unit in a Space Packet costs 6 octets of header, and SPP data fields stop at 65 536 octets.28 The 2023 overview gives this lower overhead as the reason the Encapsulation Packet is the more bandwidth-efficient carrier for LTP segments.31

    EPP as the carrier for network protocols¶

    IP over CCSDS¶

    CCSDS recognizes two network-layer standards: CCSDS-recognized IP datagrams and the DTN Bundle Protocol.32 Over a space link, the data link protocols can carry IP data units, multiplexed or not, inside Encapsulation Packets. The separate standard IP over CCSDS Space Links (CCSDS 702.1-B-1) specifies how this is done. That standard is not in the library.30 The overview of the data link protocols states it directly: IP over CCSDS uses the Encapsulation Packet as the data structure that holds the IP datagram.37

    flowchart TB
  APP["Application-specific protocols"] --> TCPUDP["TCP / UDP"]
  TCPUDP --> IPOC["IP over CCSDS (CCSDS 702.1-B)"]
  IPOC --> EP["Encapsulation Packet (CCSDS 133.1-B)"]
  EP --> SDLP["CCSDS Space Data Link Protocols"]
  SDLP --> RF["RF and Modulation Systems"]

    Redrawn after CCSDS 130.0-G-4 figure 4-4.35

    In that configuration the Internet is extended into the space segment. Each IP router makes its routing decisions from the destination address, and EPP provides the shim that puts the datagrams into the CCSDS link and takes them out at the other end.35 The overview says this suits missions that need their space segment integrated into the Internet, where connectivity and round-trip light time allow it.35

    LTP, the Bundle Protocol and CFDP¶

    • LTP usually carries each segment in one link-layer data unit, an Encapsulation Packet. Space Packets are also possible. The overview prefers EPP because its overhead is lower.31
    • The Bundle Protocol reaches links through convergence layer adapters, one of which runs over EPP or SPP (ENCAPCLA in the reference model).33
    • CFDP needs only a simple unitdata service from below. One option given in CCSDS 727.0-B-5 is the Encapsulation service, with the CFDP PDU as the data field of an Encapsulation Packet. The CFDP standard also refers to a Magenta Book, Operation of CFDP over Encapsulation Service (CCSDS 722.1-M-1), which is not in the library.44 See CFDP.

    Where an ESA ground-segment engineer may meet it¶

    Inference

    This section joins sourced facts to show where EPP appears in practice. The assessment is this wiki's own.

    • Telemetry frames from newer spacecraft. A TM or AOS on-board encoder may fill frames with Encapsulation Idle Packets, and a USLP encoder must.394243 Ground packet extraction (in the station, in NCTRS/NIS or in the control system) then has to recognize PVN 0b111 and discard idle packets, as TM receiving ends already do with SPP idle packets.40
    • Not on Solar Orbiter. The Solar Orbiter packet ICD fills frames with idle Space Packets (APID all ones, random data), not Encapsulation Idle Packets.52 Its TM and TC traffic is PUS packets, which are Space Packets (see Space Packet: Solar Orbiter case study).
    • SCOS-2000 and the MIB. The SCOS-2000 import ICD identifies telemetry packets by APID, type, subtype and extra identification fields in the pid table. It has no key for packet version.51 So the MIB has nowhere to describe Encapsulation Packets, and the library sources do not say how SCOS-2000 would handle them.
    • IP, DTN and file-transfer experiments. EPP is the standard way to carry IP datagrams, LTP segments, bundles or CFDP PDUs that should not be wrapped in mission APIDs.303144
    • ECSS context. ECSS-E-ST-50C Rev.1 (2021) shows the "Encapsulation Service" and the "Encapsulation Packet" (CCSDS 133.1-B) under IP over CCSDS in its protocol figure.46 The 2008 handbook listed CCSDS 133.1-B as "support to IPv6 for all ECSS space links". It recommended the Space Packet as the encapsulating packet unless very long data units had to be carried, because few implementations then supported Encapsulation Packets.5047

    Edition history¶

    Edition Date Main points
    CCSDS 133.1-B-1 June 2006 "Encapsulation Service", Issue 1, superseded1
    CCSDS 133.1-B-2 October 2009 "Encapsulation Service", Issue 2, superseded1
    CCSDS 133.1-B-3 May 2020 Removes the Space Packet from the encapsulation formats, renames the standard "Encapsulation Packet Protocol" and adds USLP to the supported data link protocols1
    EC 1 November 2020 Updates obsolete page-header text1

    Issue 3 also asked SANA to rename two registries, without changing their contents. They are now "Protocol Identifier for Encapsulation Packet Protocol" and "Extended Protocol Identifier for Encapsulation Packet Protocol". The old names referred to the "Encapsulation Service".24 EPP offers no security functions of its own. Authentication, confidentiality and integrity come from SDLS at the data link layer or from the Bundle Security Protocol at the network layer.23
