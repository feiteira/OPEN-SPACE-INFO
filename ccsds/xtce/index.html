    XTCE: XML Telemetric and Command Exchange (CCSDS 660)¶

    Every mission control system needs a mission database. This is the description, item by item, of every telemetry parameter, packet, calibration, limit, command and verification check that the ground must handle. ESA's SCOS-2000 keeps it in the MIB, a set of ASCII tables. Other control systems have their own formats. Every hand-over between organisations, for example from spacecraft manufacturer to operator or from test system to control centre, has therefore needed a custom translation, more testing and more risk of error.3 XTCE, the XML Telemetric and Command Exchange format, is an open, standard XML Schema for describing such a database. The aim is that TM/TC definitions can be exchanged "without the need for customized import/export, re-validation, or even re-implementation".6

    XTCE is an Object Management Group (OMG) specification. CCSDS publishes the OMG text of XTCE 1.2, inside CCSDS front matter, as the Recommended Standard CCSDS 660.0-B-2.21 The CCSDS Informational Report 660.1-G-2 explains every element.26 A second, shorter Informational Report, 660.2-G-2, introduces the concepts and use cases.132 In March 2026 the OMG published XTCE 1.3 (formal/26-06-09) with a new schema. Its specification text differs from 1.2 mostly in wording, as shown below.157 Whether CCSDS will re-issue 660.0 for 1.3 is not stated in the available sources. This page summarises these documents and a NASA tutorial on XTCE 1.1 (2008 or 2009), and records which parts two open implementations, Yamcs and OpenC3 COSMOS, support. It then maps XTCE concepts onto the SCOS-2000 MIB tables, a mapping that the standards themselves do not provide. Each mapping judgement on this page is this wiki's own analysis.

    Purpose and scope¶

    XTCE covers the metadata needed to:6

    • define the structure and sequence of CCSDS packets and TDM frames;
    • define how individual data items are packed and unpacked;
    • describe commands: identification, arguments and validation criteria;
    • define parameter and command encoding;
    • define data properties such as default values, validity criteria and dependencies.

    It explicitly excludes data distribution mechanisms, command and data protocols, RF and analogue streams, data grouping and coherent data sets, visualisation, scheduling, orbital properties, displays and flight software. It is "a meta-data specification, not a data specification".6

    Philosophy: neither packets nor frames¶

    The industry is split between packet telemetry and TDM (time-division multiplexed) telemetry, and much of the apparent divide is vocabulary. XTCE therefore avoids words such as "minor frame", "major frame" and even "packet" except in examples, and builds in no packet or frame standard. Instead, users build libraries of containers that represent those standards.4 The processing that XTCE metadata supports runs in two directions. Stream processing covers decryption, decoding, frame synchronisation and so on. Parameter processing covers decommutation, de-packetisation, calibration and custom processing. On the command side the corresponding steps are formatting, constraint checking, authentication and verification.5

    This wiki's summary of 660.0-B-2 §6.1 and 660.1-G-2 §3.2.9111928

    The root is called SpaceSystem rather than "Spacecraft", because an operations centre also controls antennas, recorders, ground equipment and RF hardware. Each of these is a SpaceSystem.9 A SpaceSystem can contain sub-SpaceSystems. The standard gives four reasons: fewer name collisions (a dozen identical transponders can each live in their own sub-SpaceSystem), better organisation of databases with thousands of commands and tens of thousands of parameters, the ability to nest spacecraft inside a constellation, and a natural fit to systems of systems.9 The optional Header records the source, version, revision history, notes and classification.10 660.2-G-2 lists its content as date, version, classification and validation status (validated, tested or draft), an author set, a note set and a history set for configuration management.140

    660.2-G-2 treats SpaceSystems as namespaces addressed by paths such as /MyMission/SubSystem1/Power/Battery1. A SpaceSystem has no fixed meaning: it can be an instrument, a spacecraft bus, a whole spacecraft, a constellation or a ground station. XTCE 1.2's XInclude support lets each instrument and the spacecraft bus have its own SpaceSystem database, assembled into one large database such as the satellite database.138139 Some organisations keep a single SpaceSystem, others use many.139

    Names may contain digits, letters, underscores, hyphens and backslashes, and are case sensitive. The characters / (SpaceSystem path separator), . (member of an aggregate), [ ] (array index) and : are reserved. In 1.2 the : is held for a future selector of data in other SpaceSystems; in 1.3 implementations may use it to separate a name from an alias namespace.9161 Collections are named …Set when unordered and …List when ordered. Meta marks a description (a MetaCommand is a command description), and Ref marks a by-name reference.8

    References and instances¶

    Items refer to each other by NameReference, which is the item's name with an optional Unix-style path through the SpaceSystem hierarchy.29 The NASA tutorial lists absolute, relative and path-less forms. A path-less name is not global: it is looked up in the local SpaceSystem first and then up the tree. Because an XML parser does not resolve these references, every implementation must, and the tutorial counts them among the hardest parts of XTCE to implement.167178 During processing, a ParameterInstanceRef points at a parameter's value. Instance 0 (the default) is the last recorded value, and negative instances go back in time. useCalibratedValue (default true) selects the engineering or raw value.33 Conditions throughout the schema use MatchCriteria: a simple Comparison, a ComparisonList, an arbitrarily complex BooleanExpression, or an escape to a custom algorithm.23 A ContextMatch is a MatchCriteria that selects which calibrator, alarm or significance applies. The Green Book gives mission phases as an example of a context.30

    Telemetry¶

    Parameter types¶

    A ParameterType is a description of something that can have a value. A Parameter is an instance of it ("a Parameter is not the value itself").1213 The type carries most of the information: data type, description, units, alarm limits, string conversion and, through one of four DataEncodings, the on-the-link form.12 The Green Book describes the processing order. The encoded link value is checked against a valid range and calibrated into the host data type. Alarm checks are then applied to the result.35

    XTCE type Typical encoding Notes
    StringParameterType StringDataEncoding restriction pattern, character width, string alarms5455
    EnumeratedParameterType IntegerDataEncoding EnumerationList of label/value pairs. maxValue turns a value into a range. EnumerationAlarm56
    BinaryParameterType BinaryDataEncoding data with no type54
    BooleanParameterType IntegerDataEncoding, 1 bit oneStringValue / zeroStringValue57
    IntegerParameterType IntegerDataEncoding signed, sizeInBits, ValidRange, numeric alarms54
    FloatParameterType Float or IntegerDataEncoding (with calibrator) numeric alarms54

    The Green Book counts ten ParameterTypes in two groups: the scalar types and the complex Array and Aggregate types. Its list of scalar names repeats "String" and leaves out the two time types.54 660.2-G-2 lists all ten with one-line roles (Boolean as "a special case of" enumerated types, Binary as a "blob" catch-all) and distinguishes two forms of ParameterType: one with a DataEncoding, describing a value from the spacecraft, and one without, describing a ground-side value whose Parameter sets dataSource to local.141 It names three common combinations: a FloatParameterType with an IntegerDataEncoding and (typically) a PolynomialCalibrator for a calibrated count, an IntegerParameterType with IntegerDataEncoding, and a FloatParameterType with FloatDataEncoding. For calibrations too complex for the three calibrator kinds it suggests a BinaryDataEncoding with a FromBinaryTransformAlgorithm.142

    Encodings¶

    • IntegerDataEncoding: encoding is one of unsigned (default), twosComplement, onesComplement, BCD or packedBCD. The default sizeInBits is 8. It can carry calibrators and a changeThreshold.39 The specification body of both 1.2 and 1.3 also lists signMagnitude and spells the complements "twosCompliment" and "onesCompliment".12162 A later Green Book table names "signedMagnitude", and the NASA tutorial warns that the 1.1 schema used the "Compliment" spelling.131168 The GovSat example of 660.2-G-2, which the report states is valid against the 1.2 schema, uses twosComplement.154153 The full list of enumeration strings is that of the schema, which is not in this wiki's library.
    • FloatDataEncoding: IEEE754_1985, IEEE754, MILSTD_1750A, DEC, IBM or TI. The listed sizes are 16, 32, 40, 48, 64, 80 and 128 bits. Not every format supports every size, and a later paragraph of the Green Book mentions only 32, 64 and 128 bits.40 The specification text names only IEEE754_1985 and MILSTD_1750A.12
    • StringDataEncoding: US-ASCII, ISO-8859-1, Windows-1252, UTF-8, UTF-16 (LE/BE) or UTF-32 (LE/BE). The size is either fixed (SizeInBits, optionally ended by a termination character or given by a leading size field, 16 bits by default) or Variable.38
    • BinaryDataEncoding: a size plus optional From/ToBinaryTransformAlgorithms. It is used for data with no type and for exotic formats.41

    Every encoding shares a bitOrder (MSB first by default), an optional byte order list for non-big-endian items, and ErrorDetectCorrect (parity, CRC, and a checksum added in 1.2).37 A ParameterType with no encoding describes a local, ground, constant or derived value that never comes from telemetry. Its Parameter should then declare a non-telemetered dataSource.42

    Calibrators¶

    Integer and float encodings can hold a DefaultCalibrator and any number of ContextCalibrators, each selected by a ContextMatch.43

    • SplineCalibrator: a list of raw-to-calibrated SplinePoints. order 0 gives a step function, 1 linear (the default), 2 quadratic and 3 cubic. extrapolate controls values beyond the end points.44
    • PolynomialCalibrator: Term elements with coefficient and a non-negative integer exponent, for example \(y = 0.5 + 1.5x - 0.045x^2 + 1.25x^3 + 0.0025x^4\).45
    • MathOperationCalibrator: an expression built from MathOperationType, written in postfix (reverse Polish) form.4575

    Alarms¶

    Every scalar type except AbsoluteTime has a DefaultAlarm and a ContextAlarmList. The first context alarm whose ContextMatch is true is used. Otherwise the default applies, like an if-then chain.4648 All alarms share minViolations (successive violations before the alarm state) and minConformance (successive good samples to leave it).47 The levels are normal, watch, warning, distress, critical and severe.49 The alarm forms are:

    Form Applies to Meaning
    StaticAlarmRanges Integer, Float (and time) nested bands for watch, warning, distress, critical and severe. rangeForm is outside (default: normal in the middle) or inside (normal at the outside)51
    ChangeAlarmRanges Integer, Float changePerSample (delta) or changePerSecond (rate), on an absolute or percentage basis, over a span of samples or seconds52
    MultiRange Integer, Float any number of ranges (new in 1.2)52
    EnumerationAlarm Enumerated alarm level per enumeration label49
    StringAlarm String level per matching pattern, with a default level55
    AlarmConditions most types a MatchCriteria per level. The most severe true level wins50
    CustomAlarm most types algorithm-based47

    Boundary semantics

    In the Green Book's outside-alarm example, WarningRange minInclusive="-5" maxInclusive="5" makes -5 and 5 themselves warnings: the normal range is -5 < x < 5.51 The "inclusive" values belong to the alarm band. This matters when mapping MIB limits (see below). The NASA tutorial reads its own example the same way. With WatchRange −2000 to 5000 and SevereRange −5000 to 6000, values x ≤ −2000 or x ≥ 5000 are at watch level and x ≤ −5000 or x ≥ 6000 are severe. More severe ranges clip less severe ones, and the colours used for the levels are not part of XTCE.170 The Yamcs manual reads its own example the same way: a value of 40 against a warning range of 10 to 30 raises a warning, which it calls "perhaps a bit counter intuitive". It does not discuss the boundary values themselves.184

    For AlarmConditions, the NASA tutorial adds that the condition of each of up to five levels can be a single comparison, several conditions, a Boolean expression or a custom algorithm.171

    A ValidRange check applies only to Integer and Float types. It is separate from alarms: an out-of-range value is invalid rather than alarmed.3553 On the telemetry side the tutorial says to ignore the attribute validRangeAppliesToCalibrated. For commands it chooses where the check happens: on the engineering value before calibration (true, the default) or on the encoded value after it (false), but not both.169 Yamcs marks a parameter outside its ValidRange as invalid and skips its limit checks, while a command argument outside its range makes Yamcs reject the command.183190

    Type inheritance¶

    String, Enumerated, Binary, Integer, Float and Boolean types can extend another type of the same kind through @baseType. Loops are illegal. A child can override calibrators, units, the default alarm and ranges, and can prefix context alarms and enumerations. It cannot change the encoding, sizeInBits or signedness.36

    Parameters¶

    A Parameter is usually just a name and a parameterTypeRef.61 Its ParameterProperties add:62

    • dataSource: telemetered (the default), derived (computed by an algorithm), constant or local (for example a session variable).
    • readOnly and persistance (spelled this way in XTCE).
    • ValidityCondition: a MatchCriteria that must hold for the value to be valid. The standard's example is a value that is invalid while its subsystem is off.
    • PhysicalAddressSet: hardware addresses, for example on a MIL-STD-1553 bus.
    • TimeAssociation: the offset of the sample from a reference time parameter. In XTCE 1.2 it can also be set per container entry.
    • SystemName: a subsystem name for flat, single-SpaceSystem databases.

    One type per parameter? A ParameterType can in theory serve many Parameters. 660.2-G-2 says that this is "not common practice". Most databases give every Parameter its own type, so that a change to an alarm or calibrator cannot spread by accident to other parameters, at the price of a larger file. The same holds for ArgumentTypes.143148 The Yamcs manual makes the same observation from the other side. Many control systems do not separate a parameter from its type, and shared types are mostly generic ones such as uint8 or uint16, or types for a family of identical sensors.182 660.2-G-2 also warns that the dataSource attribute, which defaults to telemetered, "is often overlooked".143

    Containers¶

    A SequenceContainer describes "a packet, frame, a subframe, or any other grouping". Its EntryList is an ordered list of items.1463 By default the entries are packed back to back, and the container's size is the sum of their encoded sizes.66

    Entry Purpose
    ParameterRefEntry a parameter. Its width comes from the type's encoding66
    ParameterSegmentRefEntry part of a parameter (for example a 1 024-bit binary split into 116-bit segments)66
    ContainerRefEntry another container, resolved as a unit. Referencing an abstract container triggers dynamic container matching67
    ContainerSegmentRefEntry, StreamSegmentEntry parts of containers or streams spread over several containers67

    Each entry can be modified by three elements:69

    • LocationInContainerInBits sets the position relative to containerStart, containerEnd, the previous entry (the default) or the next entry. The Green Book's XML examples spell the previous-entry value previousEntry.6970

    Algorithms¶

    The AlgorithmSet holds processing that cannot be stated declaratively. A MathAlgorithm is a formula in postfix notation. A CustomAlgorithm (also called SimpleAlgorithm) holds algorithm text and references to external implementations such as Java classes, DLLs or scripts. Input, Input-Output and Input-Output-Trigger algorithms add named inputs, outputs, and periodic or event-driven triggers.1875

    Commanding¶

    CommandMetaData has the telemetry sets plus an ArgumentTypeSet, a MetaCommandSet and a CommandContainerSet. Parameters are scoped per SpaceSystem, so a telemetry parameter can be used in a command and the other way round.1976 The Green Book draws the line this way. An argument is something an operator (or automation) supplies. A command parameter is part of the command that the system supplies, or that RestrictionCriteria fix.77 On the command side, data flows the other way. The host value is range-checked, then (de)calibrated into the encoding for uplink, and can be range-checked again.78

    ArgumentTypes mirror the ParameterTypes but have no alarms. Float and integer argument types carry a ValidRangeSet.2079

    660.2-G-2 adds three practical points. Arguments are local to their MetaCommand and cannot be reused by another command, although commands can inherit them through BaseMetaCommand.146 The line between argument and command parameter is not always clear to users. Some see the whole command "load", others only their own arguments, but XTCE has the syntax to separate the two when needed.147 And the CommandContainerSet holds the "pieces/parts" of command containers that several commands share.149 The NASA tutorial describes those shared pieces as "has a" building blocks, for example an optional secondary header included only when the secondary header flag is 1.174 It also lists how a MetaCommand's own CommandContainer differs from a telemetry container. It can hold a FixedValueEntry, for example an opcode, and ArgumentRefEntries, which must cover every argument but need not follow the ArgumentList order. It can extend the parent command's container only through an explicit BaseContainer, its RestrictionCriteria are optional, and it has no abstract attribute of its own. The tutorial encourages simple "parameter == value" restrictions, because they can be processed automatically to tell the system which values it must supply in the named parameters.172173

    ServiceSet¶

    A Service is a named grouping of containers or messages, such as a "memory dump service". Referencing an abstract container includes all its children. The meaning of a grouping is left to the implementation, and services are optional.2294 660.2-G-2 explains that services were introduced "for the European space organizations that deal with services", that is, users of the PUS, and calls the area under-used.150 The NASA tutorial's example groups the containers of each CCSDS virtual channel into one service.176

    Too big and too small: profiles and extensions¶

    660.2-G-2 admits that for many users XTCE has "far more features than are needed". The answer is a trimmed profile, colloquially GovSat, published by the OMG as the XTCE US Govt Satellite Conformance Profile (XUSP). XUSP is not a new schema but a set of executable rules, applied after schema validation. The rules allow only one SpaceSystem, limit the number of polynomial coefficients and the length of mnemonics, and define a standard CCSDS header with its parameters. Organisations may relax rules, for example to allow several SpaceSystems, at a cost in compatibility.136

    The same report admits that XTCE can also be too small, when a local "must have" feature is missing, and lists six ways to handle it:137

    Option How Trade-off
    a) AncillaryData name/value pairs, available in many places of the schema easiest; files stay schema-valid
    b) Modify the schema locally edit the XTCE schema "breaking the standard"
    c) Modify via an external schema extensions in their own namespace, included at the modification point easier to separate standard and local parts
    d) External schema and file keep extra information in a second file files stay valid, but two files to manage and software must merge them
    e) Overload elements reuse an element or attribute for another purpose may break software; "least preferred"
    f) Change request to the OMG propose a change to the specification "very lengthy", worthwhile for features of broad value

    The NASA tutorial approaches the same problem from the exchange side. A full exchange works only between parties that agree in advance on which XTCE features to use. Even partners with different packet formats can exchange part of their data: NASA CCSDS and ESA PUS missions exchanged "the majority of telemetry metadata", with some work.180 Its list of points to agree goes below the CCSDS header: polynomial coefficients, alarm levels, floating-point sizes and formats, and bit and byte order. It suggests writing such constraints in machine-processable form, to configure validators and "builder" tools. 660.2-G-2 later describes the XUSP rules as executable rules for a validation program, which is a similar idea.181136 The tutorial names the GSFC JWST translator, the CNES "Best" suite and ESA CryoSat as exchange implementations, and says that several others exist, mostly on the customer side.180

    Inference

    For a MIB converter, option a) is the natural home for MIB fields with no XTCE element, such as PCF_DARC, CCF_PLAN or the display tables. Option c) would suit features such as status consistency checks that need structure. Neither 660.2-G-2 nor the tutorial mentions the MIB.

    Implementing XTCE¶

    The tutorial describes four ways to implement XTCE: XSLT and XPath, a DOM or SAX parser, a data-binding "autogenerator" that maps schema types to classes (it used JAXB for the GSFC prototypes, and also mentions Eclipse EMF and XMLSpy), or a mix.177 The order of elements matters and must survive the mapping. A native implementation can configure itself from any valid file, but at the time GSFC's prototype had never decommutated real packet data. A University of Bremen implementation had been demonstrated doing so.179 The hardest parts were name references and their instance syntax, container inheritance with include conditions, type inheritance, and dynamic container matching with NextContainer. Of the last, the authors wrote that it had "never been implemented yet that we are aware of".178

    XTCE and ECSS-E-ST-70-31C¶

    ECSS-E-ST-70-31C, the European monitoring and control data definition standard, defines what data a supplier must deliver with a product so that the customer can integrate, test and operate it. It leaves out how the data is provided: "spreadsheet data or XML" are both outside its scope.97 It organises the data as a space system model: a hierarchy of system elements, each with activities (telecommands, procedures and other commands), reporting data (parameters and compound parameters with raw and engineering representations) and events.9899 It requires interpretation functions (linear interpolation with an extrapolate/invalid choice, or IFL scripts) selected by ordered conditions. Compound parameters can be records, arrays (fixed or variable) or deduced structures. Limit checks have danger and warning limits, each optionally tied to a corrective activity.100101102

    Inference

    XTCE could serve as a delivery format for 70-31C data: the SpaceSystem hierarchy for system elements, Parameters and Aggregate/Array types for reporting data, MetaCommands for telecommand activities, ContextCalibrators for ordered interpretation functions, and ContextAlarms for limit sets. Neither document says so. 70-31C does not mention XTCE, and the 70-31C requirements for corrective actions, procedures and events have no direct XTCE element.

    Inference: limit boundaries differ

    In SCOS-2000, "In case the telemetry value matches exactly one of the limit values, this is not considered as an OOL condition."115 In XTCE's outside ranges, the minInclusive and maxInclusive values are themselves in the alarm band.51 A literal copy of OCP_LVALU and OCP_HVALU into minInclusive and maxInclusive would therefore raise alarms at the exact limit values, which SCOS-2000 does not. A converter would need exclusive bounds or adjusted values. The Green Book's StaticAlarmRanges examples use only minInclusive/maxInclusive, but its description of the XTCE 1.2 MultiRange alarm lists both inclusive and exclusive interval forms, so a MultiRange alarm is the likelier way to express SCOS-2000's semantics.32 The attribute names for exclusive bounds are not legible in the available text. SCOS-2000 also stops at the first applicable check (or soft/hard pair) unless configured otherwise, and limit checks always come in low/high pairs.115

    Telemetry packets (pid, pic, tpcf, plf, vpd)¶

    SCOS-2000 identifies a packet by APID, type and subtype, plus up to two extra identification fields whose position comes from PIC, giving an SPID.116117 In XTCE this is naturally a hierarchy. An abstract CCSDS header container restricts on APID. An abstract PUS header container restricts on service type and subtype. Each concrete SPID container restricts on PI1/PI2 values. The ICD warns that type, subtype and PI fields must sit at the same position in every packet of a given type and subtype.116 XTCE does not impose that constraint, so the mapping from MIB to XTCE is safe, while the reverse may not be.

    • PLF_OFFBY, PLF_OFFBI (octet and bit of the first occurrence, from the start of the source packet header) become LocationInContainerInBits referenceLocation="containerStart" with value 8 × OFFBY + OFFBI.11869
    • PLF_NBOCC, PLF_LGOCC (super-commutation) become RepeatEntry with Count = NBOCC − 1 and offset LGOCC − width. XTCE counts extra copies and measures the gap between them.11869
    • PLF_TIME, PLF_TDOCC (millisecond offsets) become TimeAssociation/@offset (in seconds by default). XTCE has no per-occurrence delta.11862
    • PID_INTER (period of periodic packets, used for expiry) becomes DefaultRateInStream. TPCF_SIZE becomes BinaryEncoding/SizeInBits.11665
    • VPD (variable packets): VPD_GRPSIZE counters become RepeatEntry with a DynamicValue count. VPD_FIXREP becomes a fixed count. VPD_CHOICE becomes dynamic container matching. VPD_PIDREF (deduced parameters by on-board ID) becomes IndirectParameterRefEntry, matching PCF_PID through an alias namespace.1196834

    What has no XTCE counterpart¶

    • Displays (alphanumeric, graphic and scrolling displays: tables dpf/dpc, gpf/gpc, spf/spc, and printouts ppf/ppc). XTCE excludes displays. SCOS-2000 itself has kept display definitions outside the MIB database since R5.0.6120
    • Command sequences with formal parameters, timing and nesting. From SCOS-2000 R5.0 these are kept as XML files in the FARC. That XML is not XTCE.124 BlockMetaCommand covers only fixed groups.93
    • Parameter sets (PST/PSV/CPS/PVS/PSM), command routing (DST), status consistency checking, event-generating checks, dynamic defaults, and SCOS-2000 configuration hooks such as PCF_DARC or PID_EVENT.
    • Time correlation. The MIB says whether to correlate and with which OBT clock (PCF_CORR, PCF_OBTID). Correlation coefficients are run-time data. See Time correlation in SCOS-2000.

    NIH0K31T ("ccT") is defined in the 2025 Solar Orbiter MIB as follows:130

    Inference

    RestrictionCriteria is a MatchCriteria, and the Green Book combines several conditions in it with a ComparisonList, in which every Comparison must be true.7131 The example above follows that form. The schema is the normative reference and was not checked. Because containerStart is measured from the start of the concrete container, the container hierarchy must cover the whole packet from the primary header onwards, which matches the MIB's convention that PLF offsets count from the start of the source packet header.118 The soft-to-Warning and hard-to-Severe choice follows the Green Book's tri-colour recommendation. The boundary caveat above also applies: SCOS-2000 does not flag exactly −40 or 40.
