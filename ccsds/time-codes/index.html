    Time code formats (CCSDS 301.0-B-4)¶

    Every telemetry packet that reaches a control centre carries a time stamp, and many telecommands carry a time at which something must happen on board. CCSDS 301.0-B-4 defines the small set of time codes used to put those times on the wire. A time code is a digital representation of time that uses the SI second as its basic unit.1 The standard defines one unsegmented code, the CCSDS Unsegmented time Code (CUC), which is a pure binary count from an epoch. It also defines three segmented codes, in which the count is spread over cascaded counters with different moduli: the CCSDS Day Segmented code (CDS), the CCSDS Calendar Segmented code (CCS) and the ASCII calendar codes.1 Agency-defined codes can also be identified through the same preamble mechanism.18

    This page explains each code bit by bit. It then follows the codes into the rest of the chain: the Space Packet secondary header, the PUS absolute and relative time parameter types (PTC 9 and PTC 10), the ST[09] time management time reports, the SCOS-2000 MIB, and SCOS-2000 time correlation, which turns on-board time into UTC. Solar Orbiter is the running example throughout.

    At a glance

    Property Value
    Document CCSDS 301.0-B-4, Blue Book, Issue 4, November 2010 (Editorial Change 1, February 2014)5
    Structure of every binary code optional P-field (preamble) + T-field (time), each an integral number of octets7
    CUC binary count of seconds and binary fractions; recommended epoch 1958-01-01 TAI; no leap seconds9
    CDS day count + milliseconds of day (+ optional µs or ps); UTC based11
    CCS BCD calendar segments (year, month/day or day of year, h, m, s, decimal fractions); UTC based12
    ASCII YYYY-MM-DDThh:mm:ss.d…dZ (A) or YYYY-DDDThh:mm:ss.d…dZ (B); no P-field1415
    Interpretation levels Level 1 (fully self-defined) to Level 4 (length only)2
    PUS use PTC 9 absolute time, PTC 10 relative time, CUC or CDS3335
    Solar Orbiter on-board time CUC, 4 coarse + 2 fine octets, P-field 0x2E, zero reference 2000-01-01 00:007680

    Document history¶

    CCSDS first issued the time code formats in January 1987, with Issue 2 in April 1990 and Issue 3 in January 2002. Issue 4 (November 2010) added a second P-field octet for CUC and a new section on security. Editorial Change 1 (February 2014) corrected an error on page v.5 Older ESA documents still cite earlier issues: ECSS-E-70-41A (PUS-A, 2003) refers to CCSDS 301.0-B-2.51 ECSS-E-ST-70-41C (PUS-C, 2016) refers to 301.0-B-4.33

    Concepts¶

    Preamble field and time field¶

    Every binary CCSDS time code is a P-field (time code preamble field) followed by a T-field (time specification field). The P-field identifies the code and its options. The standard advises including it whenever the receiver may not know which code is in use. Both fields are always an integral number of octets.7

    The P-field can be explicit (sent with the T-field) or implicit (not sent). When it is implicit, the code does not identify itself and the receiver must learn the format "by other means".8 In practice those means are a mission constant or a database definition. PUS calls this the implicit P-field value, which must be declared for the mission.46 In the SCOS-2000 MIB it is the parameter's PTC/PFC pair.58

    Interpretation levels¶

    CCSDS 301.0-B-4 grades codes by how much a receiver can understand without outside help:2

    Level Name What is self-defined
    1 Complete unambiguous interpretation structure and a CCSDS-recommended epoch, so absolute time can be compared between sources
    2 Partial interpretation structure only; the epoch comes from an external source, so only relative times can be interpreted
    3 Recognition of increasing time value only the length; the value increases monotonically except at rollover
    4 No interpretation only the length

    Table B-2 of the standard summarises which services each level supports: absolute time interpretation, relative time interpretation and ordering of events from one source.22

    Code Absolute time Relative time Ordering
    CUC Level 1, CDS Level 1, CCS Level 1, ASCII yes yes yes
    CUC Level 2, CDS Level 2 no yes yes
    Level 3 (agency-defined) no no yes
    Level 4 (agency-defined) no no no

    Bit numbering¶

    As in all CCSDS standards, bit 0 is the first bit transmitted and the most significant bit of any counter. An 8-bit group is called an octet.4 The bit-field diagrams on this page follow that convention.

    The P-field: first octet¶

    When the P-field is explicit, its mandatory first octet has the same overall layout for every binary code:8

    The extension flag (bit 0) shows whether another P-field octet follows. Every extension octet starts with its own extension flag, so the P-field can be chained: 0 marks the last octet and 1 means another octet follows.8 Bits 1 to 3 hold the time code identification. The values 0b000, 0b011 and 0b111 are reserved for future use.8 The full allocation is in table B-3:23

    Bits 1-3 Code Category
    000 reserved -
    001 CUC, 1958-01-01 epoch Level 1
    010 CUC, agency-defined epoch Level 2
    011 reserved -
    100 CDS Level 1 or 2 (epoch bit)
    101 CCS Level 1
    110 agency-defined code Level 3 or 4
    111 reserved -
    none ASCII Level 1 (table B-3 lists "Level 1 or 3")

    The ASCII codes have no P-field at all, because the format can be recognised by parsing the characters.817

    CCSDS Unsegmented time Code (CUC)¶

    T-field¶

    The CUC T-field is a run of contiguous octets that counts whole basic time units from an epoch. It can be followed by octets that count the elapsed binary fraction of the basic unit. Each octet is 8 bits of one long binary counter that rolls over modulo 256 into its neighbour, and the code increases monotonically without reversion.9 The integer part is usually called coarse time and the fractional part fine time. PUS uses these names.33

    The basic unit intended for correlation with Earth clocks is the second. The unit, the epoch and the number of coarse and fine octets are metadata. They come from the P-field if the code identifies itself, and from outside otherwise.9 For a Level 1 code, CCSDS recommends the epoch 1958 January 1 (TAI) with the TAI second as unit. Such a code is not UTC based, and leap-second corrections do not apply.9

    With \(C_1 \ldots C_n\) the coarse octets (most significant first) and \(F_1 \ldots F_m\) the fine octets, the time since the epoch is:

    \[ t = \sum_{i=1}^{n} C_i \cdot 256^{\,n-i} + \sum_{j=1}^{m} F_j \cdot 256^{-j} \]

    PUS gives exactly this formula for the full 4+3 octet case (PFC 18).34

    P-field¶

    Octet 1 alone describes 1 to 4 coarse octets and 0 to 3 fine octets. Issue 4 added octet 2, which adds up to 3 more coarse octets and up to 7 more fine octets.105 The combined range is therefore 1 to 7 coarse octets and 0 to 10 fine octets. PUS-C quotes a similar range: it says CCSDS "offers means" for 1 to 7 coarse and 1 to 10 fine octets, and that PUS itself implements 1 to 4 coarse and 1 to 10 fine octets.33

    Reading CUC P-fields (constructed examples)

    P-field Bits Meaning
    0x1E 0 001 11 10 CUC Level 1 (1958 TAI epoch), 4 coarse + 2 fine octets
    0x2E 0 010 11 10 CUC Level 2 (agency epoch), 4 coarse + 2 fine octets. Solar Orbiter uses this value (see below).
    0x2F 0 010 11 11 CUC Level 2, 4 coarse + 3 fine octets (the PUS "full CUC")
    0x9E 0x20 1 001 11 10, 0 01 000 00 CUC Level 1 with octet 2: 4+1 = 5 coarse, 2+0 = 2 fine

    The bit patterns follow from clause 3.2.2.10 Only 0x2E is a value documented for a real mission.80

    Resolution and ambiguity period¶

    The ambiguity period is the time between two recurrences of the same code value.28 For CUC it is set by the number of coarse octets. The resolution is set by the number of fine octets. The figures below are this wiki's arithmetic from the counter widths:

    Coarse octets Rolls over after Fine octets Resolution
    1 256 s 1 \(2^{-8}\) s ≈ 3.9 ms
    2 65 536 s ≈ 18.2 h 2 \(2^{-16}\) s ≈ 15.3 µs
    3 \(2^{24}\) s ≈ 194 days 3 \(2^{-24}\) s ≈ 59.6 ns
    4 \(2^{32}\) s ≈ 136 years 4 \(2^{-32}\) s ≈ 0.23 ns

    PUS-A annex C, transcribed from ESA PSS-04-106 (see From ESA PSS to CCSDS and ECSS), describes the classic ESA spacecraft elapsed time in these terms. It is a CUC with 1 to 4 coarse octets and a resolution of \(2^0\), \(2^{-8}\), \(2^{-16}\) or \(2^{-24}\) s. Its P-field always starts 0b0010 (agency epoch), the unit is the TAI second, and the epoch is arbitrary because the ground correlates the count to UTC.53

    Why CUC exists¶

    Because CUC is the state of one binary counter with no discontinuities, time differences can be computed by direct arithmetic. That makes it the natural choice for spacecraft clock measurement.24 Its main limitation is the converse: it cannot represent UTC, because UTC jumps at each leap second.25

    CCSDS Day Segmented time code (CDS)¶

    T-field¶

    CDS splits time into right-adjusted binary counters:11

    Segment Width Range
    Day 16 or 24 bits 0 to \(2^{16}-1\) or 0 to \(2^{24}-1\)
    Milliseconds of day 32 bits 0 to 86 399 999; 0 to 86 400 999 or 86 398 999 on a leap-second day
    Submilliseconds (optional) 16 bits (µs of ms) or 32 bits (ps) µs of ms: 0 to 999

    The ranges are those of annex A.19 The day counter counts from 1958 January 1, starting at 0. An agency-defined epoch is allowed as a Level 2 code. Because CDS is UTC based, leap seconds must be handled: a positive leap second makes that day 86 401 seconds long, so the millisecond counter reaches 86 400 999.1119

    P-field¶

    The submillisecond bits set the resolution: millisecond, microsecond or picosecond.11 Typical values are 0x40 (16-bit day, no submilliseconds, 1958 epoch) and 0x41 (the same with microseconds). These two values are constructed from the clause.

    Rationale¶

    Most terrestrial measurements are in UTC, so events on board usually end up time-tagged in UTC. CDS in its simplest form is just two binary counters. That keeps it convenient for computers, and the millisecond unit fills 28 of the 32 bits of its segment. CCSDS calls CDS the most "machine friendly" of the UTC codes. The recommended epoch 1958 January 1 is Julian date 2436203.5, the epoch of TAI. A 1950 January 1 epoch differs from it by exactly 2922.0 days. The 24-bit day segment is meant for special uses such as astronomy.25

    CDS worked example (illustrative bytes)

    Encode 2025-09-16T12:00:00.123456 UTC with P-field 0x41 (16-bit day, µs, 1958 epoch):

    Segment Value Octets
    Day since 1958-01-01 24 730 60 9A
    ms of day 43 200 123 02 93 2E 7B
    µs of ms 456 01 C8

    T-field: 60 9A 02 93 2E 7B 01 C8 (8 octets). This is the layout PUS calls PTC 9 PFC 2.34 The values were computed by this wiki for illustration.

    CCSDS Calendar Segmented time code (CCS)¶

    T-field¶

    CCS uses binary coded decimal (BCD): each 8-bit segment holds two decimal digits. There are two variations, both Level 1 and both UTC based with leap-second correction:12

    Variation Segments (bits)
    Month of year / day of month YR (16), MO (8), DOM (8), h (8), m (8), s (8), then optional \(10^{-2}\) s … \(10^{-12}\) s (8 each)
    Day of year YR (16), DOY (16), h, m, s (8 each), then optional subsecond segments (8 each)

    The year A.D. needs 16 bits (four BCD digits). In the day-of-year variation, the DOY segment is 16 bits because all segments are whole octets, and its four most significant bits are always zero.12

    P-field¶

    The resolution field gives the number of decimal subsecond segments, from none (1 s) to six (\(10^{-12}\) s).13 CCS suits applications in which people often read the code, for example when time is converted to characters for display. It is less efficient than CDS for arithmetic.26

    CCS worked example (illustrative bytes)

    2025-09-16T12:00:00.123456 UTC, month/day variation, microsecond resolution: P-field 0b0_101_0_011 = 0x53, T-field 20 25 09 16 12 00 00 12 34 56. Each octet reads directly as two decimal digits. Constructed by this wiki from clause 3.4.1213

    ASCII calendar segmented time codes¶

    The ASCII codes are strings of one-octet ASCII characters. They are UTC based, intended to match civil time, and use the Gregorian calendar epoch of 1 A.D. on the prime meridian.14

    Code Format Example from the standard
    ASCII Time Code A (month/day) YYYY-MM-DDThh:mm:ss.d…dZ 1988-01-18T17:20:43.123456Z
    ASCII Time Code B (day of year) YYYY-DDDThh:mm:ss.d…dZ 1988-018T17:20:43.123456Z

    Subfield ranges are: year 0001 to 9999, month 01 to 12, day of month 01 to 28/29/30/31, day of year 001 to 365 or 366, hour 00 to 23, minute 00 to 59, second 00 to 59 (58 or 60 during leap seconds). Any number of decimal fraction digits may follow the period. The Z terminator is optional, and every subfield keeps its leading zeros.1415 Both variations are subsets of ISO 8601.27

    The standard also sets rules for subsets, so that a calendar-only or time-only string can be used:16

    1. The calendar part (left of T) and the time part (right of T) may be used on their own if the context makes the meaning clear. The T is then dropped.
    2. A subset may be shortened. If subfields are removed on the left, their separators stay. If they are removed on the right, their separators go.
    3. A subset may not contain a partial subfield. In particular the year is always four digits. Each fractional digit counts as a complete subfield.
    4. When a calendar subset and a time subset are joined with T, the calendar part must not be truncated on the right and the time part must not be truncated on the left.
    5. Using these formats for anything other than instants in UTC, for example as counters, is outside the standard.

    For the example date above, code A gives 2025-09-16T12:00:00.123456Z and code B gives 2025-259T12:00:00.123456Z (day 259). These strings were constructed by this wiki. Ground software uses the ASCII codes wherever a human or a text file is involved. The rationale cites text editors, exchange of text files between unlike systems, and direct printing.27

    Agency-defined codes (Levels 3 and 4)¶

    A code that is not CCSDS-recommended can still carry a P-field with time code identification 110. The T-field is then any number of octets, read as one binary number. It is Level 3 if the number increases monotonically (except at recycle) and Level 4 otherwise.18

    Annex E gives the NASA PB-5J code as an example. It has a 16-bit truncated Julian day, a 24-bit second of day and optional 16-bit ms, µs and ns segments, followed by an 8-bit ID code. Fill bits pad each segment to an octet boundary. Its P-field values are 0b0110 followed by the length codes 0101, 0111, 1001 and 1011 for the 6, 8, 10 and 12 octet forms.32 The Truncated Julian Date counts from 1968-05-24.0 (JD 2440000.5).30

    Choosing a code¶

    CCSDS compares the four recommended codes against three criteria: whether they can represent leap seconds without ambiguity (UTC compatible), whether they are efficient for computers, and whether people can read them:21

    Code Segmented? UTC compatible Computer efficient Human readable
    CUC no no yes no
    CDS yes yes yes no
    CCS yes yes no yes
    ASCII yes yes no yes

    The standard deliberately does not prescribe a code for each application, and it leaves timing accuracy to the responsible authority.3 Annex B explains why time matters so much: time is usually the only link between instrument data and independently produced ancillary data such as orbit and attitude.20

    Time scales and leap seconds¶

    The informative glossary (annex C) takes its definitions from ITU-R TF.686-2.28

    • TAI (International Atomic Time) is kept by the BIPM from atomic clocks. Its epoch was set to agree approximately with UT1 on 1 January 1958, and its rate follows the SI second.29
    • UTC runs at the same rate as TAI but differs from it by a whole number of seconds. It is adjusted by positive or negative leap seconds to stay close to UT1.28
    • DTAI = TAI − UTC is the correction to add to UTC to obtain TAI.29
    • The Modified Julian Date is JD − 2 400 000.5. The constant 2 436 203.5 gives 1958 January 1, the origin of TAI and the epoch of both CUC and CDS.30

    Annex D gives the conversion \(T_i = U_i + L_i\). Here \(T_i\) is TAI, \(U_i\) is UTC in seconds and \(L_i\) is the accumulated leap seconds since 1972. Its table runs from \(L\) = 10 s (from 1972-01-01) to \(L\) = 34 s (from 2009-01-01).31 Later leap seconds are not listed in the available sources. Differencing two UTC times therefore needs a leap-second table, while differencing two TAI-based CUC values does not.31

    SCOS-2000 time correlation meets the same issue from another side. GPS time does not include leap seconds, so a GPS-disciplined on-board clock keeps a known, growing offset from UTC. The ground monitors that offset as a "synchronisation" status.66

    Security considerations¶

    Issue 4 added a security section. Time values can be operationally critical, for example the time of a manoeuvre burn, and an unauthenticated or corrupted time code uploaded to a spacecraft could change its time basis. The standard places integrity, authentication and confidentiality outside its scope and expects them from the application, network or data link layers.6 On the data link, SDLS is the CCSDS answer.

    Time codes inside packets¶

    In the Space Packet secondary header¶

    CCSDS 133.0-B-2 allows the Packet Secondary Header to hold a Time Code Field, an Ancillary Data Field, or both in that order. The Time Code Field must be one of the CCSDS segmented or unsegmented binary codes, an integral number of octets, and fixed for a managed data path throughout the mission. The P-field may be omitted if the code's characteristics never change. If it is present, it immediately precedes the T-field.56 The Packet Sequence Count can be combined with the time code to order packets over a long mission. The time code then needs enough resolution to change at least once per sequence-count cycle.57

    PUS absolute time (PTC 9)¶

    In PUS-C, every packet field that carries an absolute time is of PTC 9. Its value is a positive number of seconds and fractions from an epoch. With CUC, the epoch is either the CCSDS 1958 epoch or an agency epoch. With an agency epoch the field is in effect a free-running counter that the ground converts using time correlation coefficients. With CDS, the 1958 epoch is mandatory.33 The format codes are:34

    PFC Format Length
    0 explicit P-field followed by CUC or CDS variable
    1 CDS, 2-octet day, no µs 6 octets
    2 CDS, 2-octet day, with µs (day, ms of day, µs of ms) 8 octets
    3 to 18 CUC, coarse = ⌊(PFC + 1) / 4⌋ octets, fine = (PFC + 1) mod 4 octets; implicit P-field 1 to 7 octets
    19 to 46 CUC, coarse = ⌊(PFC − 12) / 7⌋ octets, fine = 4 + (PFC − 12) mod 7 octets; implicit P-field 5 to 14 octets

    The formula for PFC 3 to 18 gives 3 → 1+0, 6 → 1+3, 7 → 2+0, 11 → 3+0, 15 → 4+0, 17 → 4+2 and 18 → 4+3 (coarse+fine octets). The formula for PFC 19 to 46 gives 19 → 1+4, 25 → 1+10, 26 → 2+4 and 46 → 4+10.34 PUS-A (2003) defined only PFC 0 to 18 for absolute time, with the same formula. Its CUC and CDS references point to CCSDS 301.0-B-2.51

    PUS relative time (PTC 10)¶

    A relative time (PTC 10) is a signed offset in seconds. It is measured either from an event that other fields in the packet identify, or between two absolute times. Negative offsets are the two's complement of the positive value, so the first coarse octet of a positive offset is at most 127.35 PUS-C allows PFC 2 (8-octet CDS layout) and PFC 3 to 18, with the same CUC formula as for absolute time.36

    PUS-A and PUS-C number relative-time PFCs differently

    In PUS-A, relative time uses PFC 0 (explicit P-field) and PFC 1 to 16, with coarse = ⌊(PFC + 3) / 4⌋ and fine = (PFC + 3) mod 4.51 In PUS-C it uses PFC 3 to 18 with coarse = ⌊(PFC + 1) / 4⌋.36 The SCOS-2000 ICD 7.0 lists PTC 10 with PFC 3 and up, each with the same coarse/fine split as the PTC 9 entry of the same PFC.59 A database that mixes both conventions would decode relative times wrongly. For example, the Solar Orbiter MIB uses PTC 10 PFC 6, which SCOS-2000 reads as 1 coarse + 3 fine octets (4 octets), while the PUS-A formula would give 2 coarse + 1 fine octets (3 octets).595183

    The time field of the PUS TM secondary header¶

    In PUS-C every TM packet except the spacecraft time packets has a secondary header. Its time field is an absolute time whose PFC is declared with the mission's time service. Each application process sets it to the time tag of the report, using the on-board reference time.3837 Each process also declares whether it time-tags a report before or after collecting the parameter values.37 If supported, the 4-bit spacecraft time reference status reports the state of the on-board time reference used for the tag. It is 0 when not supported.39 The TC secondary header has no time field.40 Telecommand times appear in the application data instead, for example release times in ST[11] time-based scheduling.41 Full header layouts are on PUS packet structures.

    ST[09] time reports: how the ground learns the on-board time¶

    The time management service exists so that the ground can correlate the spacecraft time reference with UTC. With that correlation the ground can reconstruct the on-board time of every other event the spacecraft reports.42 A time reporting subservice supports exactly one format: CUC (suited to counter-style clocks) or CDS (suited to clocks synchronised to TAI or UTC).4245

    Sampling rule¶

    The time reports are generated by the application process with APID 0. Each report travels in a space packet without a secondary header, so APID 0 can carry nothing else.4349

    sequenceDiagram
  participant TFG as On-board frame generator (VC 0)
  participant OBT as Spacecraft time reference
  participant APID0 as Time reporting (APID 0)
  participant GS as Ground station / SCOS-2000
  TFG->>OBT: Frame with VC frame count mod rate = 0 starts
  Note over TFG,OBT: OBT is sampled at the leading edge of the first bit of the frame's ASM
  OBT->>APID0: Sampled value
  APID0->>GS: Time report in a later frame (TM[9,2] or TM[9,3])
  GS->>GS: Earth reception time of the sampled frame + delays gives the time couple

    The subservice samples the time reference for each TM transfer frame on virtual channel 0 whose virtual channel frame count, modulo the generation rate, is 0. The sample is taken at the leading edge of the first bit of that frame's attached synchronisation marker. The report's T-field is set to the sampled value. A rate change applies immediately to the next qualifying frame. PUS-C does not require the time packet to go down in the frame that triggered it.4744 The rate is \(2^n\) frames with \(n\) = 0 to 8 (1 to 256 frames). The rate exponential value is changed by TC[9,1].4448

    Report layouts¶

    TM[9,2] CUC time report and TM[9,3] CDS time report have the same source data field: an optional rate exponential value (unsigned integer), the spacecraft time (absolute time, formatted as CUC or CDS, with or without P-field as declared), and an optional spacecraft time reference status (deduced).5046

    The time report (9,2) contains an optional 1-octet Rate, the Satellite Time in CUC with implicit or explicit P-field, and an optional Status. The implicit P-field is the mission constant <MISSION_TIME_CODE>.52 Annex C describes the standard time source packet in more detail. The first data octet carries the sampling rate in bits 4 to 7, as codes 0000 (1 frame) to 1000 (256 frames). It is followed by the P-field and T-field, then any mission-defined time-system octets.54 The ground station must time-tag the reception of the same attached-sync-marker bit in CDS-coded UTC.55

    Solar Orbiter's time packet¶

    Solar Orbiter's time packet has the same S-field, P-field and T-field layout as the PUS-A annex C standard time source packet.5480 Its On-Board Computer keeps the OBT, the spacecraft's zero time reference is 00:00 on 1 January 2000, and the OBT is CUC with 4 coarse and 2 fine octets.76 At power-up the OBT starts from 0. It is then set to real time by TC(9,128) Set OBT, which can load an absolute value or add or subtract a delta.7678 The time packet has APID 0 and no data field header. Its data field is 8 octets long (packet length field C = 7).80

    Annex 4 relates the T-field to the leading edge of the first ASM bit of the VC 0 frame "with a virtual channel frame count of 0".80 This is the same wording as PUS-A annex C. PUS-A clause 13.2 extends it to every later VC 0 frame whose frame count modulo the generation rate is 0.5552 The Solar Orbiter MIB describes the same packet as SPID 9999 "Time Report": type 9, subtype 2, APID 0, PID_TIME = Y, PID_DFHSIZE = 6. Its plf entries place three pcf parameters at octets 6, 7 and 8:83

    Offset (octets) Parameter Description PTC/PFC Calibration
    6 NCD09021 OBCHP_Time Rep S-Field 2/8 textual CCDT0043TX: 0 = EVERY_TMFR … 8 = EVERY_256_TMFR
    7 NCD09022 OBCHP_Time Rep P-Field ¾ none
    8 NCD09023 OBCHP_OBT 9/17 none (PCF_CORR blank, so the ICD default Y applies)

    The rate is changed by ZCD00901 "Change Time Report Generation Rate" (TC(9,1)). Its single editable parameter PCD09011 is an 8-bit value (PTC 2, PFC 8).8377 Solar Orbiter also uses private subtypes: TC(9,129) "Accept Time Synchronisation" and TC(9,130) "Start Time Synchronisation to User". With these, the central software distributes the OBT of the next synchronisation signal (PPS, MIL-STD-1553 major frame or SpaceWire time code) to other packet terminals.79

    Decoding a Solar Orbiter time packet data field (illustrative bytes)

    Data field 05 2E 30 5C 0D C0 80 00:

    1. S-field 0x05. Bits 4-7 = 5, so the rate is \(2^5\) = 32 frames. NCD09021 calibrates it as EVERY_32_TMFR.83
    2. P-field 0x2E = 0 010 11 10: CUC, agency epoch, 4 coarse and 2 fine octets.80
    3. Coarse 0x305C0DC0 = 811 339 200 s. Fine 0x8000 = 0.5 s.
    4. Counted from the 2000-01-01 00:00 zero reference, that is nominally 2025-09-16 12:00:00.5. This is not yet UTC. The OBT is a free-running count set by TC(9,128), so SCOS-2000 must apply its time correlation coefficients to obtain UTC.7633

    The bytes were chosen by this wiki and are not taken from a real downlink.

    Time codes in the SCOS-2000 MIB¶

    The MIB gives every time parameter a PTC/PFC pair from Appendix A of the Database Import ICD. The time types are:5859

    PTC PFC SCOS-2000 meaning Length
    9 0 absolute time with explicit P-field. Not supported by SCOS-2000 variable
    9 1 CDS without µs (supported from R5.0) 6 octets
    9 2 CDS with µs. Command parameters only, not monitoring parameters 8 octets
    9 3 to 18 CUC, as in PUS (for example 15 = 4 coarse, 17 = 4+2, 18 = 4+3) 1 to 7 octets
    9 30 Unix time: 4 octets of seconds since 1970-01-01 00:00:00 and 4 octets of microseconds. Not defined in PUS 8 octets
    10 3 to 18 relative time, CUC 1 to 7 octets

    Two pcf fields control how times are interpreted.6061

    • PCF_CORR: Y (default) applies time correlation to an absolute time parameter. N extracts it without correlation. Relative times must be N.
    • PCF_OBTID: which on-board clock's format and correlation to use. Clocks are numbered 1 to N. If the field is blank, the MISCconfig variable TCO_DEFAULT_OBT_ID applies. If there is no OBT ID and PCF_CORR = N, the epoch comes from the MISC variable TCO_ESA_EPOCH.

    The cpc table has the same pair of fields for command parameters (CPC_CORR, CPC_OBTID), and display formats T (absolute) and D (relative).62

    What the Solar Orbiter MIB actually uses¶

    The counts are from this wiki's queries.83 Every absolute CUC time on Solar Orbiter has 4 coarse octets, which matches the single 4+2 OBT format of the spacecraft ICD.76 Relative times are not all 4-coarse: the 6 parameters of PTC 10 PFC 6 (for example NIM00093 "FIB DataRdy Assert Time") use 1 coarse and 3 fine octets.8359

    Inference

    The ICD says that CDS with microseconds (PTC 9 PFC 2) is supported only for command parameters.58 The one Solar Orbiter monitoring parameter of that type, NYG02204, sits in SPID 66850 "TM Packet used by the Releaser G/S response". Its NYG prefix and APID 1966 suggest a ground-generated packet rather than spacecraft telemetry. Neither the ICD nor the Solar Orbiter documents describe these packets. The same applies to the Unix-time (PFC 30) fields.

    From OBT to UTC: SCOS-2000 time correlation¶

    Time correlation links the On-Board Time (OBT) of an event with the time SCOS-2000 assigns to it. The packetiser needs it to time-stamp packets, and the releaser needs it to encode time-tagged telecommands.63 The full mechanism is on Time correlation in SCOS-2000. This section gives the parts that depend on time codes.

    The delay chain¶

    The on-board time in a time packet is latched when a qualifying frame starts. The ground station stamps that frame with its Earth Reception Time (ERT). SCOS-2000 works back to the Frame Transmission Time (FTT) and then to the OBT Latching Time (OLT):6471

    \[ \mathrm{FTT} = \mathrm{ERT} - d_{\mathrm{ground}} - d_{\mathrm{propagation}} - d_{\mathrm{on\text{-}board\ radiation}} $$ $$ \mathrm{OLT} = \mathrm{FTT} + d_{\mathrm{latching}} \]

    The pair (OBT from the time packet, OLT in UTC) is a time couple.64 For SLE service providers the ground delay is zero by definition, because ERT already equals the frame reception time at the antenna.71 The propagation delay is the one-way light time.71

    flowchart LR
  FTT["Frame Transmission Time<br/>(OBT latch requested)"] -->|"on-board frame radiation delay"| FRT["Frame Radiation Time"]
  FRT -->|"propagation delay (OWLT)"| FRX["Frame Reception Time"]
  FRX -->|"ground delay"| ERT["Earth Reception Time<br/>(frame time stamp)"]
  FTT -->|"OBT latching delay"| OLT["OBT Latching Time<br/>(paired with OBT)"]

    Redrawn after TN-1030 figure 5.71

    Because the time packet arrives in a later frame than the one it describes, the packetiser remembers frames whose counter is a multiple of N. It accepts a time packet only if the stored FTT lies within a configurable window (MISC variables TCO_FAR_FTT_PLAUSIBILITY_LIMIT and TCO_CLOSE_FTT_PLAUSIBILITY_LIMIT) before the FTT of the frame carrying the report. Otherwise no time couple is made.73 The OBT is extracted in its configured format. The library supports CUC (parameterised by PFC) and CDS, and missions can subclass TCOtimeFormat for others.75

    Coefficients¶

    Two algorithms produce the conversion coefficients:67

    • Free running clock: a least-squares fit over a buffer of time couples, \(\mathrm{UTC}(\mathrm{OBT}) = \mathrm{UTC}_N + \mathrm{Gradient}\cdot(\mathrm{OBT}-\mathrm{OBT}_N) + \mathrm{Offset}\).
    • Synchronised on-board clock (for example GPS disciplined): the gradient is fixed at 1 and only the offset is computed from the last time couple, \(\mathrm{UTC}(\mathrm{OBT}) = \mathrm{UTC}_N + \mathrm{OBT} - \mathrm{OBT}_N - \mathrm{Offset}\).

    Both are evaluated relative to the last time couple used, (\(\mathrm{OBT}_N\), \(\mathrm{UTC}_N\)), to keep time resolution.67 Each new time couple gives a deviation: the couple's UTC minus the UTC computed from its OBT with the current coefficients. The deviation is compared with an accuracy limit and a looser validity limit:65

    stateDiagram-v2
  [*] --> ValidAccurate
  ValidAccurate --> ValidInaccurate: deviation exceeds accuracy limit
  ValidAccurate --> InvalidInaccurate: deviation exceeds validity limit, or reset
  ValidInaccurate --> InvalidInaccurate: deviation exceeds validity limit, or reset
  ValidInaccurate --> ValidAccurate: new coefficients committed
  InvalidInaccurate --> ValidAccurate: new coefficients committed

    Redrawn after TN-1030 figure 6.72

    In automatic mode the coefficients are recomputed without operator action. TN-1030 describes the trigger inconsistently. Sections 4 and 6.2, and the summary that closes §6.3.2.1.1, say it fires when the deviation exceeds half the accuracy limit.657274 Step 6 of the engine's step list gives the condition as a deviation above the accuracy interval but not above the validity interval.74 The overview in §3.1 speaks of the deviation exceeding "the specified thresholds for the validity".63 The available sources do not say which wording matches the software. While deviations exceed the validity interval, time couples are still processed but are kept out of the recalculation buffer. After TCO_AUTORESET_INVALID_DEVIATIONS consecutive invalid couples, the buffer is cleared, validity checking is suspended, and a new correlation starts once two new time couples have arrived.74 For synchronised clocks, a separate synchronisation status compares the computed offset with the expected offset, for example the GPS-UTC difference, within the accuracy limit. It is assessed only when new coefficients are generated.6672

    The packets SCOS-2000 stores¶

    The time correlation server files two internal packet types. TN-1030 gives their layouts. Times in these packets use SCOS-2000's internal Unix-style TDSsunTime (seconds and microseconds, plus picoseconds for TDSsunTime_pico), counted from the MISC variable TCO_ESA_EPOCH. If that variable cannot be read, the fallback is DEFAULT_ESA_EPOCH, which is hard-coded in the software:70

    Time couple packet field Bits Position Coefficient packet field Bits Position
    OBT (TDSsunTime) 64 0 Version (= 1) 8 0
    OLT (TDSsunTime_pico) 96 8 Algorithm (1 difference, 2 least squares) 32 1
    FTT 96 20 Synchronisation check flag 8 5
    ERT 96 32 Validity (0/1) 8 6
    Light time delay (double) 64 44 Accuracy (0/1) 8 7
    On-board frame radiation delay 64 52 Synchronisation (0/1) 8 8
    OBT latching delay 64 60 Spare 24 9
    Ground station delay 64 68 Gradient (IEEE double) 64 12
    Ground station ID 32 76 Offset (obsolete) 64 20
    Deviation (double) 64 80 OBT_N, UTC_N (doubles) 64 each 28, 36
    Display offset 64 44

    TN-1030 also lists the SPIDs used for testing: 1000005 (time report), 1000098 (time couple) and 1000099 (coefficients).69 The Solar Orbiter MIB defines its own versions under APID 1966, type 164. SPID 66841 "TCO Time_Couples OBT" holds OBT (8-octet string), OLT, FTT and ERT (12-octet strings), light time, on-board frame radiation delay, ground station delay, station ID, deviation, two frame counters, the OBT size and a raw OBT of PTC 9 PFC 17. SPID 66842 "TCO_Coefficients OBT" holds validity, accuracy, gradient, offset, OBT_N, UTC_N and two statistics (STD, STE).83

    Inference

    The Solar Orbiter time-couple layout (offsets 16 to 99) matches TN-1030 table 1 shifted by a 16-octet header, except that there is no separate "OBT Latching Delay" field and there are extra frame-counter and raw-OBT fields. Its coefficient layout differs from TN-1030 table 2 more noticeably: it has no version, algorithm, synchronisation-check or synchronisation fields, it has one "offset" field where TN-1030 has both an obsolete offset and a display offset, and it adds STD and STE. This may reflect an older SCOS-2000 release or a mission extension. The available sources do not say which.

    Time stamps on archived packets¶

    The packetiser can time-stamp each filed packet in one of three ways: by filing time (useful for replay tests), by the FTT of the frame carrying the packet header, or by the packet's own on-board time converted to UTC through the time correlation API.68 Downstream systems receive these times in their own formats. For example, the EDDS binary format lists a TM header field 8 "Generation Time" (time-correlated on-board generation time), typed "CCSDS CUC" in the field table.81 In the EUICD's GDDS binary file example, that field is 8 octets: seconds since 1970-01-01 followed by microseconds, the same split as MIB PTC 9 PFC 30.8258
