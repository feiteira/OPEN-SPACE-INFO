    AOS Space Data Link Protocol (CCSDS 732.0-B-4)¶

    The AOS Space Data Link Protocol (AOS-SDLP) is one of the CCSDS protocols of the Data Link Protocol Sublayer. It carries user data over a space link in fixed-length AOS Transfer Frames. These can travel space-to-ground, ground-to-space or space-to-space.12 AOS stands for Advanced Orbiting Systems. The protocol was created for the International Space Station and similar systems. They needed to send many classes of data at once, audio and video included, at high combined rates and in both directions.105 The ECSS communications handbook (2008) reports that in practice it was adopted for high-rate downlinks,110 where the conventional TM sequence counters would roll over during a contact.112 AOS has a 24-bit Virtual Channel Frame Count, while the TM Space Data Link Protocol has 8-bit frame counters.37118

    The AOS frame is a close relative of the TM frame. Both are fixed-length, both run over TM Synchronization and Channel Coding, both carry Space Packets using a First Header Pointer, and both can carry the CLCW of the uplink in an Operational Control Field. The differences are a wider Virtual Channel ID (6 bits instead of 3) but, up to Issue 4, a narrower Spacecraft ID (8 bits instead of 10; Issue 5 widens it to 10136), longer counters, an optional Reed-Solomon-protected header, an Insert Zone for small periodic data and a Bitstream Service.107108 This page follows the October 2021 issue, CCSDS 732.0-B-4, held in the library. Issue 4 adds support for the SDLS Extended Procedures, a conformance proforma (annex A) and options for randomizing idle frames (annex D).3 Issue 5 (October 2025) widens the Spacecraft Identifier to 10 bits and the First Header Pointer to 16 bits, so that frames can be up to 65,536 octets long; it is described in Newer issue at the end of this page.131

    History and context¶

    CCSDS began extending its Packet Telemetry and Telecommand standards for Advanced Orbiting Systems in the late 1980s.101 The resulting AOS Recommendation, CCSDS 701.0-B, emerged in the early 1990s. It went well beyond a link protocol: it defined a "CCSDS Principal Network" of ground network, on-board network and space links, with Path and Internet services running end to end.105 CCSDS later restructured the Packet Telemetry, Telecommand and AOS standards into a cleaner set: the Space Packet Protocol, the TM, TC and AOS Space Data Link Protocols, and the TM and TC synchronization and coding standards.101 For AOS the replacement, CCSDS 732.0-B, came in 2003. It covers only data transfer over a single space link.106 It has had five issues: September 2003, July 2006, September 2015, October 2021 and October 2025.3131

    The ECSS communications handbook describes what happened next. The demand for a high-rate uplink largely vanished once projects were realistic about it, and the symmetric reliability features failed for lack of firm requirements. What was left is a protocol that suits high-rate downlinks.112 CCSDS now expects the Unified Space Data Link Protocol to be used by future missions in place of TM, TC, AOS and Proximity-1.102

    Where AOS sits in the protocol stack¶

    CCSDS divides the OSI Data Link Layer into two sublayers. AOS-SDLP belongs to the upper one, the Data Link Protocol Sublayer, together with the optional Space Data Link Security protocol. Below it, the Synchronization and Channel Coding Sublayer delimits frames, adds error-correcting codes and ensures enough bit transitions. For AOS this sublayer must be one of the TM synchronization and coding standards: CCSDS 131.0-B, 131.2-B (flexible advanced coding and modulation) or 131.3-B (DVB-S2).222

    The coding options and the RF link performance must keep two error probabilities below mission-specified values: misidentifying the MCID or VCID, and failing to extract packets using the First Header Pointer and the packet length field. All frames of a Physical Channel use the same coding options.23

    Every CCSDS data link protocol works one way only. A link with commands going up and telemetry coming down uses two Physical Channels, one in each direction. Only one Space Data Link Protocol may be used on a given Physical Channel.89 Three pairings are common:90

    Forward link (ground to space) Return link (space to ground) Typical use
    TC-SDLP TM-SDLP Most missions
    TC-SDLP AOS-SDLP Missions that need the extended AOS features on the return link
    AOS-SDLP AOS-SDLP Crewed missions, or missions that need two-way on-line or high-rate links (audio, video)

    Channels and addressing¶

    An AOS frame carries three identifiers: the Transfer Frame Version Number (TFVN), the Spacecraft Identifier (SCID) and the Virtual Channel Identifier (VCID). They combine as follows:6

    \[\text{MCID} = \text{TFVN} + \text{SCID}, \qquad \text{GVCID} = \text{MCID} + \text{VCID}\]

    All frames with the same MCID on a Physical Channel form a Master Channel, and all frames with the same GVCID form a Virtual Channel. Usually a Physical Channel carries one Master Channel. It may carry several, provided they share the same TFVN. The Physical Channel Name is set by management and does not appear in the frame.6

    Because the TFVN is part of the MCID, AOS spacecraft identifiers form a separate number space from the 10-bit SCIDs used with TM and TC. A spacecraft that uses TC on the uplink and AOS on the downlink therefore needs two SCIDs from the SANA registry, one for each TFVN.91 The CCSDS overview compares the identifier ranges of all the data link protocols:103

    Identifier TM TC AOS Proximity-1 USLP
    TFVN Version 1 Version 1 Version 2 Version 3 Version 4
    SCID 0 to 1023 0 to 1023 0 to 255 0 to 1023 0 to 65535
    VCID 0 to 7 0 to 63 0 to 63 not used 0 to 63
    MAP ID not used 0 to 63 not used not used 0 to 15

    The overview predates AOS Issue 5, which widens the AOS SCID to 10 bits (0 to 1023) while keeping the TFVN 01 in the MCID; the MCID thus grows from 10 to 12 bits.103136

    Inference

    Solar Orbiter's TM frames carry the global spacecraft ID 650 (0x28A).129 That value does not fit in the 8-bit AOS SCID field of Issue 4. If the mission had used AOS frames under Issue 4, it would have needed a separate AOS SCID. This illustrates the separate number spaces; it is not a statement about any real assignment. The 10-bit SCID of Issue 5 could hold the value 650, but the TFVN still distinguishes an AOS MCID from a TM or TC one, and the available sources do not say whether SANA would assign the same number in both spaces.13691

    The AOS Transfer Frame¶

    An AOS Transfer Frame consists of these fields, in this order and with no gaps:33

    # Field Length Presence
    1 Transfer Frame Primary Header 6 or 8 octets Mandatory
    2 Transfer Frame Insert Zone Integral number of octets Optional (per Physical Channel)
    3 Transfer Frame Data Field Integral number of octets Mandatory
    4 Operational Control Field (OCF) 4 octets Optional (per Virtual Channel)
    5 Frame Error Control Field (FECF) 2 octets Optional (per Physical Channel)

    Together the OCF and FECF are called the Transfer Frame Trailer. The frame length is constant for every Virtual and Master Channel of a Physical Channel throughout a Mission Phase. Changing it can cost the receiver its synchronization. The start of a frame is signalled by the coding sublayer below, through the attached sync marker.33

    AOS-SDLP itself does not fix the frame length. The coding option decides which lengths are allowed. Uncoded or convolutional-only links may use any integer number of octets up to 2048. With the Reed-Solomon code, the length follows from the code parameters as \(L = (255 - 2E - q)\,I\), where \(E\) is the error-correction capability, \(q\) the number of virtual fill symbols and \(I\) the interleaving depth.113114 For example, \(E = 16\), \(q = 0\) and \(I = 5\) give \(L = 1115\) octets. That is exactly the frame length Solar Orbiter uses for its TM frames.129

    All bit numbering follows the CCSDS convention. Bit 0 is the first bit transmitted and the most significant bit of any number, and spare bits are always set to zero.4

    Transfer Frame Primary Header¶

    The Primary Header has five fields. The first four are mandatory and the last, the Frame Header Error Control, is optional.34

    Field Bits Values Meaning and rationale
    Transfer Frame Version Number 0–1 0b01 Identifies the AOS Version 2 Transfer Frame.35
    Spacecraft Identifier 2–9 0 to 255 Identifies the spacecraft; assigned by SANA under CCSDS 320.0-M.35 Together with the TFVN it forms the 10-bit MCID.
    Virtual Channel Identifier 10–15 0 to 62; 63 reserved Identifies the Virtual Channel. All zeros when only one VC is used. All ones (63) marks the Only Idle Data (OID) channel. VCIDs need not be consecutive.36
    Virtual Channel Frame Count 16–39 0 to 16 777 215 Sequential count, modulo 16 777 216, of the frames of one Virtual Channel. It gives each VC its own accounting, mainly so packets can be extracted systematically. It is not reset unless that is unavoidable; after a reset, completeness cannot be judged.37
    Replay Flag 40 0 = realtime, 1 = replay Separates frames played back from on-board storage from realtime frames, when both use the same VC.39
    VC Frame Count Cycle Use Flag 41 0 = not used, 1 = used Says whether the receiver must interpret bits 44–47.40
    Reserved Spare 42–43 0b00 Reserved for future CCSDS definition.40
    Virtual Channel Frame Count Cycle 44–47 0 to 15 When used, it increments each time the VC Frame Count returns to zero, which in effect extends the counter from 24 to 28 bits. When unused it is all zeros.40
    Frame Header Error Control 48–63 RS check symbols Optional. Protects the key header fields with an error-correcting code (see below).41

    Bits 40–47 form the Signaling Field. It warns the receiver about things that change faster than management can handle, and it gives a cross-check against manual or automated setups for fault detection.38 Issue 5 shrinks the Signaling Field to bits 40–41, puts the two most significant SCID bits in the former spare bits 42–43 and lists the cycle count as a field of its own; see the Issue 5 header.135138

    The Replay Flag is deliberately loosely specified. On-board storage technologies vary widely, so projects and cross-support organizations must agree on what it means exactly. For example, it may mean that the frame count on the replayed VC runs downwards because the data is played back in reverse. If frames were stored after channel coding, they must be re-encoded when the flag changes on retrieval.39 The ECSS handbook contrasts this with TM. With TM, recorded frames are nested inside the data field of realtime frames ("asynchronous insertion"), whereas AOS simply flags the replayed frame.111 The ECSS adoption notice ECSS-E-AS-50-23C Rev.1 removes the choice: under ECSS the Replay Flag shall be 0, the interpretation requirement and its two notes are deleted, and a new note explains that other means of replaying frames exist and that replay frames would add processing complexity at the receiving end.147

    Why 24 bits matter (illustrative calculation by this wiki)

    Take 1115-octet frames (8920 bits) on a 1 Mbit/s return link, about 112 frames per second. An 8-bit TM Virtual Channel frame count118 wraps every 256 frames, so in under 3 s if one VC takes all the frames. The 24-bit AOS count wraps after 16 777 216 frames, about 41.6 hours. With the 4-bit cycle extension in use it wraps after 2^28 frames, about 27.7 days. A ground system can therefore detect gaps and order frames across a whole pass, without guessing how many times the counter has wrapped.

    Frame Header Error Control¶

    The optional Frame Header Error Control is a shortened Reed-Solomon (10,6) code. This page abbreviates it "FHEC", an abbreviation the standard itself does not use. The code works over 4-bit symbols. It protects the 10-bit MCID, the 6-bit VCID and the 8-bit Signaling Field. Management decides whether it is present. If present, it appears in every frame of the Physical Channel, and its presence stays fixed for the Mission Phase.41 The code is defined as follows:42

    • symbol size \(J = 4\) bits, correcting up to \(E = 2\) symbol errors per codeword;
    • field generator polynomial \(F(x) = x^4 + x + 1\) over GF(2);
    • code generator \(g(x) = (x+\alpha^6)(x+\alpha^7)(x+\alpha^8)(x+\alpha^9) = x^4 + \alpha^3x^3 + \alpha x^2 + \alpha^3x + 1\) over GF(2^4);
    • each symbol is transmitted left bit first (for example \(\alpha^3\) = 1000 is sent as a 1 then three 0s).

    The ten symbols are mapped onto header bits as follows. Symbols 0 to 3 cover bits 0–15, symbols 4 and 5 cover bits 40–47, and symbols 6 to 9 are the check bits 48–63.43 The frame count (bits 16–39) is not protected. Correcting up to two symbol errors is enough for fewer than \(10^{-7}\) missing data fields at a channel bit error rate of \(10^{-5}\), with random errors. On convolutionally coded channels, especially interleaved ones, the burst errors typical of the decoders give a data field loss rate of \(2\times10^{-5}\) at an equivalent operating point.43 The receiving All Frames Reception Function uses the field to try to correct the key header elements. A frame with an uncorrectable header error need not be delivered in cross-support situations.73 ECSS adds a note when adopting Issue 4: the Frame Header Error Control may be restricted to physical channels whose frames are not protected by an error-correcting code in the coding sublayer; when the frames are, for example, Reed-Solomon coded, the field brings no benefit and is strongly discouraged.147 Issue 5 restates the code as a Reed-Solomon (15,11) code shortened by five symbols (see below).139

    Transfer Frame Insert Zone¶

    The Insert Zone is an optional, fixed-length area directly after the Primary Header. Management decides whether it is present. If the Physical Channel supports the Insert Service, the zone is in every frame of that channel, OID frames included. Its presence and length stay fixed for the Mission Phase. The zone holds exactly one octet-aligned IN_SDU, and the space it takes is lost to the data field.44 Because the zone appears in every frame at the constant frame rate, it gives a periodic, low-overhead path for small fixed-size data (see Insert Service). If a Virtual Channel Frame or Master Channel Frame service exists on the Physical Channel, no frame may carry an Insert Zone.28

    Transfer Frame Data Field¶

    The Transfer Frame Data Field follows the Primary Header, or the Insert Zone when present. It is an integral number of octets. Its length is the frame length minus the Primary Header, the Insert Zone and the Trailer.45 It holds exactly one of the following:45

    • one Multiplexing Protocol Data Unit (M_PDU), which carries packets;
    • one Bitstream Protocol Data Unit (B_PDU), which carries a bit stream;
    • one VCA_SDU, a private fixed-length block;
    • Idle Data.

    These types are never mixed on one Virtual Channel. Management assigns the type of each VC, and the assignment stays fixed for a Mission Phase.45

    Only Idle Data frames¶

    When no valid data field is ready at release time, an OID Transfer Frame is sent. Its VCID is all ones (63). Its data field is filled with a mandatory pseudo-noise sequence from a 32-cell linear feedback shift register with polynomial \(D^0 + D^1 + D^2 + D^{22} + D^{32}\).46 In the Fibonacci form the register starts with an all-ones seed. In the Galois form it starts with 00000000001111111111111111111101. In both forms it is initialized once at device start-up and never restarted. Both produce the same output, which begins FF FF FF FF 6D B6 D8 61 45 1F 11 F1 97 16 72 3C BE 7E 00 B1.4748 A random pattern is used to avoid frame-reception problems that insufficient randomization would cause. OID frames keep the receiver synchronized, and they still carry the Insert Zone when there is nothing else to send. Idle Data in an OID frame is not the same thing as the CCSDS Idle Packet.47

    Multiplexing Protocol Data Unit (M_PDU)¶

    On a VC that carries packets, the data field holds one M_PDU. It has a 2-octet header followed by the M_PDU Packet Zone. Its length is fixed by management so that it fits the data field exactly, after allowing for an Insert Zone if there is one.49

    Field Bits Values Meaning
    Reserved Spare 0–4 0b00000 Currently undefined by CCSDS.50
    First Header Pointer (FHP) 5–15 0 to 2045 Position of the first octet of the first packet that starts in the Packet Zone. The first octet of the zone is position 0.50
    2047 (0x7FF, all ones) No packet starts in this Packet Zone (a long packet spans the whole frame).50
    2046 (all ones minus one) The Packet Zone contains only Idle Data.51

    The FHP exists so that variable-length packets can be found inside fixed-length frames. A receiver reads the first packet header at the FHP, takes its length field to locate the next packet, and so on. If the last packet of frame N carries on into frame M of the same VC, the FHP of frame M skips the leftover part and points to the next packet that starts there.50 This is what lets the receiver resynchronize after a lost frame. Issue 5 drops the five spare bits and makes the pointer 16 bits wide, with 0xFFFF and 0xFFFE as the special values (see the Issue 5 M_PDU).140

    Packets go into the Packet Zone one after another, in forward order. So the first and last packets in an M_PDU may be incomplete.51 If not enough packets are ready at release time, the sender may build Idle Packets of a suitable length. These are either CCSDS Space Packet Idle Packets (APID all ones, at least 7 octets) or Encapsulation Idle Packets (as short as 1 octet). A 7-octet Idle Packet that does not fit spills into the next M_PDU.59121122 Otherwise the sender sends an "idle" M_PDU with FHP = 2046. It may do so even in the middle of a packet that is split across frames.5160 An idle M_PDU is not an OID frame. The frame still belongs to its own VC, so it can keep the frame rate up and still carry an OCF for that VC.51

    Worked example: delimiting packets across frames (illustrative)

    Consider a VC with an 1103-octet Packet Zone. That is a 1115-octet frame minus the 6-octet header, a 4-octet OCF and the 2-octet M_PDU header, with no Insert Zone or FECF.

    Frame FHP Packet Zone content
    N 40 Octets 0–39: tail of a packet begun in frame N−1. Octets 40–539: a complete 500-octet packet. Octets 540–1102: the first 563 octets of an 800-octet packet.
    N+1 237 Octets 0–236: the last 237 octets of the 800-octet packet. A new packet starts at octet 237.
    N+2 2047 A 3000-octet packet that started in N+1 fills the whole zone. No packet starts here.

    Suppose frame N+1 is lost. The receiver notices a jump in the VC Frame Count. Frame N+2 has no packet start, so extraction restarts at the FHP of frame N+3, the next frame that has one. It does not have to deliver the incomplete packet. If the location it worked out from packet lengths disagrees with the FHP, the standard tells it to trust the FHP.68

    Pointer width and frame length

    An 11-bit FHP can address octet offsets up to 2045. That matches the 2048-octet maximum frame length that TM Synchronization and Channel Coding Issue 5 allows for AOS.113 The AOS standard of 2021 does not link the two, but later documents do: Issue 5 of the AOS standard widens the pointer to 16 bits "to accommodate frames up to 65,536 octets", and Issue 6 of the coding standard states that the maximum frame length is constrained by the number of FHP bits (11 for TM, 16 for AOS and USLP).131144

    Bitstream Protocol Data Unit (B_PDU)¶

    On a VC that carries a bit stream, the data field holds one B_PDU. It has a 2-octet header and a Bitstream Data Zone, and its length is fixed so that it fills the data field.52

    Field Bits Values Meaning
    Reserved Spare 0–1 0b00 Currently undefined by CCSDS.52
    Bitstream Data Pointer 2–15 0 to 16381 Bit position (counting from 0) of the last valid user data bit in the zone. Everything after it is idle fill.53
    16383 (all ones) The zone contains only valid user data.53
    16382 (all ones minus one) The zone contains only idle data.53

    The pointer counts bits, whereas the FHP counts octets. Bitstream Data are undelimited strings of bits whose format the provider does not know.2553 When a frame must be released before the zone is full, the provider pads it with a locally specified idle pattern and marks the boundary with the pointer.61 At the receiving end the Bitstream Extraction Function removes the idle data. It may also raise a Bitstream Data Loss Flag, derived from gaps in the VC Frame Count. That flag tells the user that an unknown amount of data may have been lost. It stays set through discarded idle-only B_PDUs until valid data is delivered again.6931 The B_PDU header is unchanged in Issue 5, which adds a note that the 14-bit pointer limits frames used with the Bitstream Service to 16384 bits.141

    Operational Control Field¶

    The OCF is an optional 4-octet field directly after the data field. Management decides per Virtual Channel whether it is present. If it is present on a VC, it is in every frame of that VC for the whole Mission Phase.54 Bit 0 is a Type Flag:55

    • 0: Type-1 Report, a Communications Link Control Word (CLCW). This is the FARM-1 report of COP-1, which closes the retransmission loop of the TC uplink.
    • 1: Type-2 Report. Bit 1 then tells the two uses apart: 0 means the content is project-specific, and 1 means it is an SDLS Frame Security Report (FSR) as defined in the SDLS Extended Procedures (see The Frame Security Report).

    The Type Flag, and bit 1 in Type-2 reports, can change from frame to frame on the same VC. The spacecraft designer must make sure that VCs carrying OCFs are sent often enough. Otherwise the COP-1 sender on the ground may time out.55 The OCF is filled by the VC_OCF Service.15

    Solar Orbiter uses TM rather than AOS frames, but its CLCW is laid out the same way. The Solar Orbiter MIB decodes the CLCW reported by each of the two on-board TC decoders field by field. Examples are NCD0Z021 "PDEC_CLCW.A.Type" (a 1-bit parameter, PTC 1 and PFC 0) and NCD0Z025 "PDEC_CLCW.A.VCID". The whole word also exists as a 32-bit unsigned parameter, NCDD05J1 "TC Decoder A.PdecCLCW" (PTC 3, PFC 14).130 These definitions are in the pcf table.

    Frame Error Control Field¶

    The optional FECF fills the last 16 bits of the frame. Management decides whether it is present. If present, it is in every frame of the Physical Channel for the Mission Phase. It detects errors introduced in transmission and data handling. Whether it is needed depends on the mission's data quality requirements and on the coding options, and some coding options make it mandatory.56 For example, TM Synchronization and Channel Coding requires the FECF for frame validation when the convolutional code is used without an outer Reed-Solomon code.115

    The FECF is a systematic cyclic redundancy check:57

    \[\text{FECF} = \left[X^{16}\,M(X) + X^{(n-16)}\,L(X)\right] \bmod G(X), \quad G(X) = X^{16}+X^{12}+X^5+1,\quad L(X)=\sum_{i=0}^{15}X^i\]

    Here \(M(X)\) is the frame without the FECF, sent most significant bit first, and \(n\) is the frame length in bits. The \(L(X)\) term amounts to presetting the shift register to all ones. At the receiver, the syndrome \(S(X) = [X^{16}C^*(X) + X^nL(X)] \bmod G(X)\) over the received frame \(C^*\) is zero when no error is detected.5758

    Worked example: FECF (computed by this wiki, illustrative frame)

    The register is preset to 0xFFFF, the generator is 0x1021, data is processed MSB first and no final inversion is applied. This is the same CRC that is often called "CRC-16/CCITT-FALSE". Over the ASCII string 123456789 it gives 0x29B1, a handy test vector. Now take a toy uncoded frame of 18 octets. Before the FECF it holds 16 octets: the header 56 83 00 01 2C 42, an M_PDU header 07 FF (FHP = 2047) and eight zero octets. The FECF over those 16 octets is 0xFBBA. Running the decoder equation over all 18 octets gives a syndrome of zero. The header bytes decode as TFVN 01, SCID 0x5A, VCID 3, VC Frame Count 300, Replay Flag 0, Cycle Use Flag 1, VC Frame Count Cycle 2.

    Inference: FHEC of the example header

    For the same header, this wiki computed the RS(10,6) Frame Header Error Control as 0x4D5C. The information symbols are 5 6 8 3 4 2 and the check symbols are 4 D 5 C. The calculation takes symbol 0 as the coefficient of the highest power of x. The standard gives the symbol-to-bit mapping, but it does not state the polynomial ordering in these words. The codeword was checked to vanish at α^6 to α^9, and the generator expands to the coefficients printed in the standard. A second, independent recomputation during review, using the same convention, gave the same check symbols; taking symbol 0 as the lowest power of x instead gives different ones. Check this against a validated implementation before relying on it. The Issue 5 formulation, five leading zero symbols of virtual fill followed by the six header symbols, gives the same check symbols when computed the same way.139

    Services¶

    AOS-SDLP offers seven services. Five work on a Virtual Channel, one on a Master Channel and one on the whole Physical Channel.11

    Service Service type SDU SAP address SDLS protection
    Virtual Channel Packet (VCP), the "Packet Service" Asynchronous Packet GVCID + Packet Version Number All features
    Bitstream Asynchronous or periodic Bitstream Data GVCID All features
    Virtual Channel Access (VCA) Asynchronous or periodic VCA_SDU GVCID All features
    Virtual Channel Operational Control Field (VC_OCF) Synchronous or periodic OCF_SDU (4 octets) GVCID None

    All the services are unidirectional, unconfirmed, incomplete (no guarantee that every SDU arrives, although some services signal gaps) and sequence-preserving within one SAP. SDUs at one SAP are processed in the order received. No order is kept between different SAPs. CCSDS does not define any flow control between user and provider.7 The services may be extended on the ground with SLE services.7

    Service types¶

    • Asynchronous: each SDU goes into a queue and is sent exactly once, in order. The provider picks the timing according to mission rules.8
    • Synchronous: the SDU sits in a one-slot buffer that is read every time a frame of the associated VC, MC or Physical Channel is sent. This is effectively time-division multiplexing. A value may go out once, several times, or not at all if it is overwritten first.9
    • Periodic: a synchronous service at constant rate, with a specified maximum delay and jitter. This is the case when the associated VC or MC produces frames at a constant rate, or when the service belongs to the only Master Channel of the Physical Channel.10

    Virtual Channel Packet Service¶

    The VCP service carries variable-length, delimited, octet-aligned packets whose Packet Version Number (PVN) is authorized by CCSDS. The SANA registry lists the PVNs, and examples are the Space Packet and the Encapsulation Packet. A user is one protocol entity with one PVN on one GVCID. Packets of several PVNs may share a VC, and the provider multiplexes them into one stream.1299 The provider must know where the packet length field is and how long it is, because it delimits packets with it.24 Primitives: VCP.request(Packet, GVCID, Packet Version Number) and VCP.indication(Packet, GVCID, Packet Version Number, Packet Quality Indicator, Verification Status Code). The last two parameters are optional. The Packet Quality Indicator says whether the packet is complete or partial, and the Verification Status Code reports SDLS errors.3032 Packets without an authorized PVN, such as IP datagrams, can travel inside an Encapsulation Packet.95

    Bitstream Service¶

    The Bitstream Service carries a serial string of bits whose structure the provider does not know. The length of each request is not preserved, because data may be split across frames or combined in one. One user per VC; bitstreams are never multiplexed on a VC.1325 Primitives: BITSTREAM.request(Bitstream Data, GVCID) and BITSTREAM.indication(Bitstream Data, GVCID, Bitstream Data Loss Flag, Verification Status Code), with the last two optional.32 Among TM, TC and AOS, only AOS has a stream service. In the same row of the CCSDS service summary, USLP offers an Octet Stream service.104

    Virtual Channel Access Service¶

    The VCA Service carries private, fixed-length SDUs whose format the provider does not know. Management sets their length so that one VCA_SDU fills a data field. One user per VC; the service may signal gaps.1426 The CCSDS green book illustrates the VCA Service with a TM-SDLP example: a stream of encrypted data, cut into fixed-length chunks and sent on its own VC.96

    VC_OCF Service¶

    The VC_OCF Service puts a 4-octet OCF_SDU into the OCF of every frame of one Virtual Channel. Its typical uses are the COP-1 CLCW and the SDLS FSR. Sending is synchronized to the release of frames on the VC. When the user creates each OCF_SDU, however, need not be synchronized; that is a mission design choice.1527 Note that AOS has no Master Channel OCF service and no frame secondary header services. TM has both; AOS has the Insert Service instead.9711 The schematic figure B-5 of the same green book nevertheless draws an "MC OCF Service" box for AOS.99 This conflicts with the seven services of CCSDS 732.0-B-4 and with table 3-1 of the green book itself, so this page follows the Recommended Standard.

    Virtual Channel Frame and Master Channel Frame Services¶

    The VCF and MCF services pass in complete frames built by another, independent protocol entity, identified by GVCID or MCID. The provider multiplexes these with its own frames. The outside frames must have the same length as the provider's frames, and each VCF or MCF instance needs its own unique GVCID or MCID.1617 These frames bypass the provider's error control encoding. The user must therefore supply frames whose FHEC and FECF options match the Physical Channel.67 Unlike TM frames, frames supplied through these services are complete AOS frames. That is why the Insert Service cannot be used together with VCF or MCF on the same Physical Channel.28

    Insert Service¶

    The Insert Service carries private, fixed-length, octet-aligned IN_SDUs in the Insert Zone of every frame of the Physical Channel. It is periodic and makes efficient use of the link at relatively low data rates.18 An IN_SDU may be any whole number of octets, from 1 up to the full data-carrying space of the frame. Its length is the same at both ends.29 On the ground the Insert Zone is read from all incoming frames, whatever their GVCID. If the IN_SDUs do not need error protection, they may even be read before the FECF check.73 The ECSS handbook notes the trade-off with TM's secondary-header services. Those are more flexible because they are not tied to the Physical Channel, but they allow a shorter maximum length.108 The CCSDS Green Book on the packet protocols names the Insert Zone of AOS (and of USLP) as one way to carry isochronous data such as voice or launch-vehicle telemetry, since neither the Space Packet nor the Encapsulation Packet guarantees a minimum delay.149

    Restrictions on combining services¶

    • On one Physical Channel, the Insert Service cannot coexist with the VCF or MCF services.
    • If the MCF Service exists on a Master Channel, no other service may exist on that Master Channel.
    • If the VCF Service exists on a VC, no other service may exist on that VC.
    • On any other VC, only one of VCP, Bitstream or VCA may exist.19

    Sending end¶

    • Packet Processing (one per packet-carrying VC) concatenates packets until the M_PDU is full. A packet that does not fit is split, and the rest starts the next M_PDU of the same VC. Packets of different PVNs are merged into one stream first. The function sets the FHP, inserts Idle Packets when it runs short at release time, or issues an idle M_PDU with FHP = 2046.5960
    • Bitstream Processing (one per bitstream VC) places the user's bits into B_PDUs one after another, unchanged. It pads with idle data at release time and sets the Bitstream Data Pointer, or issues an idle-only B_PDU. Each B_PDU is exactly as long as the data field.61
    • Virtual Channel Generation (one per VC) places one M_PDU, B_PDU or VCA_SDU unchanged into the data field. It builds the Primary Header, keeps a separate VC Frame Count for each VC, and puts the VC_OCF user's OCF_SDU into the OCF. It leaves the Insert Zone and FECF empty.62
    • Virtual Channel Multiplexing (one per Master Channel with several VCs) interleaves frames of the VCs and of VCF users in an order that management sets. CCSDS does not specify the algorithm; projects define it from priority, release rate and isochronous timing. With a single Master Channel, this function also creates OID frames (VCID 63) when nothing valid is ready. OID frames need no VC Frame Count.6364
    • Master Channel Multiplexing (one per Physical Channel with several MCs) interleaves Master Channels and MCF users in the same way. It creates OID frames with an allowed MCID when nothing is ready.65
    • All Frames Generation (one per Physical Channel) puts the IN_SDU, which arrives at a constant interval matching the frame release rate, into the Insert Zone. It then computes the FHEC and the FECF. Frames from VCF and MCF users bypass this encoding.6667

    Multiplexing is the mission's job

    Virtual Channels are the quality-of-service tool of every CCSDS data link protocol. Urgent traffic goes on one VC and bulk traffic on another, and the multiplexer can slip a frame of the urgent VC between two frames of a long packet on the bulk VC. CCSDS deliberately leaves the multiplexing algorithm to the project, which must check that it meets its own latency and priority needs.94 For an example, Solar Orbiter's ICD gives a fixed priority order among its TM Virtual Channels, with VC 7 reserved for idle frames.129

    Receiving end¶

    • All Frames Reception uses the FHEC to correct the header, if present. It recomputes the CRC and compares it with the FECF, and it extracts IN_SDUs from all frames. Frames with detected errors need not be delivered in cross-support situations.73
    • Master Channel Demultiplexing routes frames by MCID and discards frames whose SCID or TFVN is not in the managed list. A loss signal from the coding sublayer cannot be tied to one Master Channel, so it may be passed to all users.72
    • Virtual Channel Demultiplexing routes frames by VCID. It discards OID frames and frames with an invalid VCID, and it may raise a Loss Flag when the VC Frame Count jumps.71
    • Virtual Channel Reception takes the data field and the OCF apart and hands them to their users, again with an optional Loss Flag.70
    • Packet Extraction uses the FHP and each packet's length field. It joins packets split across frames, trusts the FHP over its own calculation when the two disagree, discards Idle Packets and idle M_PDUs, and delivers packets by PVN. Incomplete packets need not be delivered in cross-support.68
    • Bitstream Extraction removes the idle data using the pointer and passes on the loss flag.69

    AOS-SDLP does not set up or release connections, does not control flow, never retransmits, and does not manage SDLS.20 Neither TM nor AOS has a retransmission mechanism. Missions that need complete delivery must leave retransmission to a higher layer, for example LTP.93 For files, CFDP gives reliable transfer over an unreliable protocol.100

    AOS with the SDLS option¶

    When a link needs security, AOS can use the Space Data Link Security protocol on selected Virtual Channels. Using SDLS changes nothing in the requirements for VCs without it, and different VCs may use different kinds of security.5 On a VC with SDLS, a Security Header follows the Insert Zone (or the Primary Header when there is no Insert Zone). An optional Security Trailer follows the data field, so the OCF and FECF move along. The data field shrinks to match. The header, Insert Zone and trailer fields keep their meaning.7981

  PH["Primary Header<br/>6 or 8 octets"] --> IZ["Insert Zone<br/>(optional)"] --> SH["Security Header<br/>(managed length)"] --> DF["Transfer Frame Data Field<br/>(M_PDU / B_PDU / VCA_SDU, may be encrypted)"] --> ST["Security Trailer<br/>(optional, MAC)"] --> OCF["OCF<br/>(optional)"] --> FECF["FECF<br/>(optional)"]
    • Where security is applied. The SDLS ApplySecurity call may sit in Virtual Channel Generation or in Virtual Channel Multiplexing. In VC Generation, each Security Association can cover one VC and the processing can happen in different places for different VCs, which is the most flexible option. In VC Multiplexing, several VCs can share one Security Association, because security is applied to the multiplexed stream.82
    • Order of processing. The function first assembles the frame, leaving the security fields empty, and then calls ApplySecurity. SDLS fills in the security fields and may encrypt the data field.83 SDLS has no interface with All Frames Generation, which guarantees that the FECF is computed after SDLS has processed the frame.84
    • Receiving end. ProcessSecurity is called in VC Demultiplexing or in VC Reception, matching the choice made at the sending end. If it reports an error, the frame is discarded and the optional Verification Status Code tells the service user.85
    • What is protected. SDLS fully protects the VCP, Bitstream and VCA services. It authenticates some Primary Header fields but does not encrypt them. It gives no protection to the VC_OCF and Insert services, nor to frames supplied through VCF or MCF.123 The Insert Zone and the FHEC are always masked out of authentication.124
    • Replay frames. How SDLS treats frames with the Replay Flag set is mission-specific.80

    When do missions choose AOS?¶

    The sources give the following reasons and patterns:

    • High data rates. The ECSS handbook (2008) names the long frame counter as one reason: AOS "is sometimes applied for its suitability to high rate downlinks" where TM counters would roll over during a contact.112
    • A hybrid configuration. TC on the uplink and AOS on the downlink, with the CLCW in the AOS OCF. According to the same 2008 handbook, AOS had been adopted for high-rate downlinks on Envisat and the International Space Station, and some mission scenarios use two downlinks: AOS frames for high-rate payload data and TM frames for housekeeping.110 No newer source in the library reports on current AOS usage.
    • Two-way high-rate or on-line links. For example audio and video on crewed missions, using AOS in both directions.90
    • Isochronous side data. The Insert Service gives a slot for small periodic data units in every frame, without the cost of a Virtual Channel.18

    Inference

    With the Replay Flag fixed at 0, an ECSS AOS link uses only realtime frames, so recorded data must come back by other means, for example as packets played back from on-board storage on dedicated Virtual Channels, which is how the TM frames of Solar Orbiter handle playback. The notice says only that "alternative means" exist; it does not name them. The FHEC note matches the arithmetic of the coding layer: a Reed-Solomon decoder that has corrected the whole frame leaves nothing for the header code to correct.14741

    Solar Orbiter uses TM frames, not AOS

    The Solar Orbiter TM/TC ICD requires all telemetry transfer frames to follow ECSS-E-ST-50-03C, the TM frame standard. The frames are 1115 octets long, with version number 00 and spacecraft ID 0x28A.129 So the AOS-specific fields described on this page do not appear in Solar Orbiter telemetry. The TM Space Data Link Protocol page covers the frames the mission actually uses.

    AOS on the ground: Space Link Extension¶

    Ground stations deliver AOS frames to control centres through the same SLE return services as TM frames. The SLE Return All Frames specification defines a "telemetry frame" as a TM, AOS or USLP Transfer Frame.126 Return Channel Frames delivers selected Master or Virtual Channels, and Return Operational Control Field delivers OCFs. In the forward direction, Enhanced FCLTU lets users supply uncoded AOS or TC frames for uplink.98

    Conformance¶

    Issue 4 adds a normative Protocol Implementation Conformance Statement (PICS) proforma in annex A. Implementers complete its requirements list, marked M (mandatory), O (optional) or C (conditional), to state which features they support. SDLS items, for example, become mandatory only if the SDLS option is claimed.8788

    Worked example: SCID 650 in an Issue 5 header (illustrative, computed by this wiki)

    Take SCID 650 = 0x28A = 0b10 1000 1010, so SCID (MSB) = 0b10 and SCID (LSB) = 0x8A, with VCID 3, VC Frame Count 300, Replay Flag 0, Cycle Use Flag 1 and cycle count 2. The header is 62 83 00 01 2C 62: 01 + 10001010 + 000011 gives 0x6283, the count gives 00 01 2C, and 0 1 10 0010 gives 0x62. The Issue 4 example header used above, 56 83 00 01 2C 42, has 00 in bits 42–43 and so decodes under Issue 5 to the same SCID 0x5A.

    Inference: compatibility of the two layouts

    An Issue 4 frame always reads correctly under Issue 5, because its spare bits 42–43 are 00. The reverse holds only for SCIDs below 256: equipment built to Issue 4 that ignores the spare bits would read SCID 650 as 0x8A = 138. The PICS item "SCID Length" lets an implementation state which layout it supports. These consequences are this wiki's reading of the field definitions; the standard states only that older missions set bits 42–43 to 00.138143

    Frame Header Error Control in Issue 5¶

    Issue 5 (Editorial Change 1) describes the Frame Header Error Control as a Reed-Solomon (15,11) code over GF(2⁴), shortened by 5 symbols and converted to GF(2) to form a binary (40,24) code. Its parameters are those of Issue 4: \(J = 4\), \(E = 2\), \(F(x) = x^4 + x + 1\) and \(g(x) = (x+\alpha^6)(x+\alpha^7)(x+\alpha^8)(x+\alpha^9) = x^4 + \alpha^3x^3 + \alpha x^2 + \alpha^3 x + 1\), with \(\alpha^6\) = 1100, \(\alpha^7\) = 1011, \(\alpha^8\) = 0101 and \(\alpha^9\) = 1010 as before. Two items are new: five symbols of all-zero virtual fill, not transmitted and inserted only at the beginning of the codeword, complete it, and the code is declared systematic; the symbols are now numbered 1 to 15 instead of 0 to 9.1394243

    Symbol Header bits Function
    1–5 none Virtual fill
    6, 7, 8, 9 0–3, 4–7, 8–11, 12–15 Systematic: TFVN, SCID (LSB), VCID
    10, 11 40–43, 44–47 Systematic: Signaling Field, SCID (MSB), VC Frame Count Cycle
    12, 13, 14, 15 48–51, 52–55, 56–59, 60–63 Parity

    (After §4.1.2.6.5 h.)139 The 24 protected bits are the 12-bit MCID, the 6-bit VCID, the 2-bit Signaling Field and the 4-bit cycle count; the VC Frame Count is still unprotected, and the performance note (fewer than 10⁻⁷ lost data fields at a 10⁻⁵ random bit error rate, 2 × 10⁻⁵ on interleaved convolutional channels) is unchanged.139

    Inference

    Prefixing a systematic Reed-Solomon codeword with zero symbols changes neither its check symbols nor the header bits it covers, so the Issue 5 code produces exactly the same 16 bits as the Issue 4 (10,6) code. This wiki checked this for the example header above: both formulations give 0x4D5C for 56 83 00 01 2C 42, and 0xE47F for the Issue 5 header 62 83 00 01 2C 62, with the symbol-ordering convention discussed earlier on this page. Bits 42–43 were already inside symbol 10 (symbol 4 in Issue 4), so the new SCID bits are protected without any change to the encoder.13943

    The Issue 5 M_PDU header¶

    Field Bits Values Meaning
    First Header Pointer 0–15 offset Position of the first octet of the first packet that starts in the M_PDU Packet Zone, counting from 0.140
    0xFFFF (all ones) No packet starts in the Packet Zone.140

    Inference: pointer values in the two issues

    For real offsets the two headers carry the same octets, because the Issue 4 spare bits are zero: the pointers 40 and 237 of the worked example above are 00 28 and 00 ED in both issues. The special values differ: "no packet starts" is 07 FF in Issue 4 and FF FF in Issue 5. Sender and receiver must therefore agree on the issue; the standard does not discuss mixed configurations.14050

    Frame length and the coding layer¶

    Issue 5 still requires the frame length to be consistent with the coding standards it references: CCSDS 131.0-B-5, 131.2-B-2 and 131.3-B-2. Of these, the library holds only 131.0-B-5, whose §11 limits uncoded and convolutionally coded AOS frames to 2048 octets; the limits of the other two are not stated in the available sources.134133113 Within the 131.0 series, the 65,536-octet AOS maximum appears in Issue 6 (2026), which references AOS Issue 5, allows that length for uncoded, convolutional and sliced block-coded links, and ties it to the 16-bit FHP; without slicing, Reed-Solomon, turbo and LDPC codes still dictate the frame lengths given on the coding page.144 The Bitstream Service keeps its 14-bit bit pointer, hence the 16384-bit limit on frames that carry B_PDUs.141 The services, procedures, managed parameters and SDLS provisions show no Issue 5 change marks, and the managed-parameter tables list the same parameters and values as those above, with only editorial rewording.14275
