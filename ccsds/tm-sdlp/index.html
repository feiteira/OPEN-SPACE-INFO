    TM Space Data Link Protocol (CCSDS 132.0-B-3)¶

    The TM Space Data Link Protocol (TM SDLP) is the CCSDS Data Link Layer protocol that carries telemetry from a spacecraft to the ground (or between spacecraft) inside fixed-length TM Transfer Frames.1 It takes variable-length Space Packets (and a few other kinds of data), packs them back to back into a constant stream of identical-length frames, labels each frame with a spacecraft and virtual channel identity, and optionally appends a 4-octet status word for the uplink (the CLCW) and a 16-bit CRC. Below it, the TM synchronization and channel coding sublayer adds the sync marker, the pseudo-randomizer and the error-correcting code; above it sit the Space Packet Protocol and the PUS.4 Solar Orbiter, whose MIB and SCOS-2000 ground system are used as examples throughout this wiki, downlinks TM Transfer Frames as described here.9089

    At a glance

    Item Value
    Current issue CCSDS 132.0-B-3, October 2021 (B-1 2003, B-2 2015); still the issue cited by the April 2026 coding standard2113
    Frame length Fixed per Physical Channel and Mission Phase; at most 2048 octets for TM80
    Primary header 6 octets, mandatory21
    Optional fields Secondary header (2 to 64 octets), Operational Control Field (4 octets), Frame Error Control Field (2 octets)21
    Identifiers TFVN 0b00 (2 bits), SCID (10 bits), VCID (3 bits, up to 8 VCs)22
    Frame counters 8-bit Master Channel and 8-bit Virtual Channel counts, modulo 25625
    Special First Header Pointer values 0x7FF (no packet starts here), 0x7FE (only idle data)28
    Services VCP, VCA, VC_FSH, VC_OCF, VCF, MC_FSH, MC_OCF, MCF9
    ECSS equivalent ECSS-E-ST-50-03C (2008), superseded by the adoption notice ECSS-E-AS-50-22; Rev.1 (13 January 2023) adopts 132.0-B-3 with one amendment, the extended VC frame count86109110

    Where the protocol sits¶

    CCSDS splits the OSI Data Link Layer into two sublayers. The TM SDLP is the upper one, the Data Link Protocol Sublayer; it can optionally host the Space Data Link Security (SDLS) protocol. The lower one, the Synchronization and Channel Coding Sublayer, delimits frames, adds error-correction coding and guarantees bit transitions; for TM it is always specified by the TM synchronization and channel coding standards.453

    flowchart TB
    A["Application data<br/>(PUS services, housekeeping, science)"] --> B["Space Packets / Encapsulation Packets<br/>CCSDS 133.0 / 133.1"]
    B --> C["TM Space Data Link Protocol<br/>CCSDS 132.0 (this page)<br/>+ optional SDLS (CCSDS 355.0)"]
    C --> D["TM Synchronization and Channel Coding<br/>CCSDS 131.0: ASM, randomizer, RS / convolutional / turbo / LDPC"]
    D --> E["RF and modulation<br/>Physical Layer"]
    C -. "fixed-length TM Transfer Frames" .-> D

    A space link normally pairs one forward physical channel with one or more return physical channels. The usual combination is the TC SDLP on the uplink and the TM SDLP on the downlink; the AOS SDLP is the alternative for the return link when its extra features are needed, and only one Space Data Link Protocol may be used on a given physical channel.52 The TC protocol relies on the TM link in the other direction for its feedback: the CLCW of COP-1 normally travels in the TM frame's Operational Control Field.5284

    The TM SDLP provides unidirectional, unconfirmed, sequence-preserving and incomplete services: it never retransmits, has no flow control and no connection set-up.713 Lost frames are simply lost; some services can tell the receiver that a gap occurred. If complete delivery is required, a higher layer must retransmit.59

    Design principles¶

    • Fixed-length frames at a constant rate. Fixed-length protocol data units make synchronization simple and robust on weak, noisy links. The length is set by management for a Physical Channel and a Mission Phase, and frames must be transmitted at a constant rate.513 Changing the frame length can make the receiver lose lock.21
    • Virtual channels. One Physical Channel is shared by up to eight logical streams per spacecraft, each with its own sequence counter and possibly its own service options.557
    • Upward compatibility with time-division telemetry. CCSDS designed the frame structure so that conventional base-band receiving equipment could support it, and to be decodable efficiently after strong channel coding (unlike HDLC, which assumes nearly error-free links).61
    • Management instead of in-line signalling. Parameters that rarely change (frame length, which optional fields exist, which VCIDs are valid) are not transmitted; both ends know them from a management system (see Managed parameters).45

    Channels and addressing¶

    Three identifier fields appear in every frame header: the Transfer Frame Version Number (TFVN), the Spacecraft Identifier (SCID) and the Virtual Channel Identifier (VCID). Their concatenations define the channel hierarchy (the standard writes the concatenation as "+"):6

    \[\text{MCID} = \text{TFVN} + \text{SCID} \qquad \text{GVCID} = \text{MCID} + \text{VCID} = \text{TFVN} + \text{SCID} + \text{VCID}\]
    flowchart TB
    PC["Physical Channel<br/>named by management (not in the header)"] --> MC1["Master Channel<br/>MCID = TFVN + SCID"]
    PC --> MC2["Further Master Channels<br/>(other SCIDs, same TFVN)"]
    MC1 --> VC0["Virtual Channel 0<br/>GVCID = MCID + VCID"]
    MC1 --> VC1["Virtual Channel 1"]
    MC1 --> VCn["... up to VCID 7"]
    • A Virtual Channel is the set of frames with the same GVCID; a Master Channel is the set of frames with the same MCID on a Physical Channel. Most missions have a single Master Channel, which is then identical to the Physical Channel, but several spacecraft (same TFVN, different SCIDs) can share one Physical Channel.6 ECSS gives a probe carried by another spacecraft as an example.63
    • The Physical Channel Name is a character string set by management and never transmitted.658
    • TC and TM frames both use TFVN 0b00 (version 1); AOS frames use 0b01. TC and TM frames are told apart by the sync pattern (ASM versus TC start sequence) or by management.2258
    • SCIDs are assigned by the Space Assigned Numbers Authority (SANA); the procedure is on Space link identifiers. A SCID is unique only within a frequency band, so the same value can belong to a different spacecraft in another band. The 10-bit SCID space is shared by TC and TM; AOS has its own space, 8 bits wide until AOS Issue 5 (2025) made it 10 bits, so a spacecraft using TC up and AOS down needs two SCIDs.2258121

    Solar Orbiter

    The CCSDS spacecraft identifier of Solar Orbiter is 0x28A (650 decimal), and the same SCID is used for the flight model, the "ETB" and the "OBC-DM" (abbreviations not expanded in the ICD).8995 The ECSS standard notes that projects may instead obtain separate SCIDs for development vehicles and simulated data streams.64

    The TM Transfer Frame¶

    Overall structure¶

    A TM Transfer Frame contains up to five fields, always in this order and without gaps:21

    Field Length Presence Controlled by
    Transfer Frame Primary Header 6 octets Mandatory Always present
    Transfer Frame Secondary Header 2 to 64 octets Optional Secondary Header Flag; static per MC or VC
    Transfer Frame Data Field Remainder of the frame Mandatory Contains packets, one VCA_SDU, or idle data
    Operational Control Field (OCF) 4 octets Optional OCF Flag; static per MC or VC
    Frame Error Control Field (FECF) 2 octets Optional Management; static per Physical Channel

    The OCF and FECF together form the Transfer Frame Trailer. The start of each frame is signalled by the coding sublayer (the Attached Sync Marker), which is not part of the frame.2175 The data field length is the fixed frame length minus the primary header and whichever of secondary header and trailer are present:30

    \[L_{\text{data}} = L_{\text{frame}} - 6 - L_{\text{FSH}} - 4\,[\text{OCF}] - 2\,[\text{FECF}]\]

    The TM SDLP Blue Book itself defers the allowed lengths to the coding standards; the coding standard allows any whole number of octets up to 2048 for uncoded or convolutionally coded TM, and specific lengths for Reed-Solomon, turbo and LDPC codes (see allowed frame lengths).2180 ECSS-E-ST-50-03C states the 2048-octet maximum explicitly.62 Issue 6 of the coding standard (2026) explains that this limit comes from the 11-bit First Header Pointer and adds slicing, which lets Reed-Solomon, turbo and LDPC codes carry TM frames of any length up to 2048 octets (see below).114115

    Primary header¶

    As in all CCSDS documents, bit 0 is the first bit transmitted and, for numeric fields, the most significant bit; octets are numbered from 0 and spare bits are always 0.3

    Field Bits Values Meaning
    Transfer Frame Version Number 0–1 0b00 Identifies a version 1 TM frame.22
    Spacecraft Identifier 2–11 0–1023 Spacecraft associated with the data; static throughout all Mission Phases.22
    Virtual Channel Identifier 12–14 0–7 Virtual Channel of the frame. VCIDs need not be consecutive.23
    Operational Control Field Flag 15 0, 1 1 if the OCF is present; static within the associated MC or VC for a Mission Phase.24
    Master Channel Frame Count 16–23 0–255 Sequential count, modulo 256, of frames on the Master Channel.25
    Virtual Channel Frame Count 24–31 0–255 Sequential count, modulo 256, of frames on the Virtual Channel.26
    Transfer Frame Secondary Header Flag 32 0, 1 1 if a secondary header is present; static within the associated MC or VC.27
    Synchronization Flag 33 0, 1 0: octet-synchronized, forward-ordered packets or idle data; 1: a VCA_SDU. Static per VC.27
    Packet Order Flag 34 0 Reserved by CCSDS and set to 0 when Sync = 0; undefined when Sync = 1.27
    Segment Length Identifier 35–36 0b11 Set to 11 when Sync = 0; undefined when Sync = 1.27
    First Header Pointer 37–47 0–2045, 0x7FE, 0x7FF Position of the first octet of the first packet that starts in the data field.28

    Master Channel Identifier. The first 12 bits are read as one unit, the MCID, by the receiving end's master channel demultiplexer; frames whose SCID or TFVN is not in the managed list of valid values are discarded.2243

    Frame counts. Both counters increment by one per frame on their channel and must not be reset before reaching 255 unless that is unavoidable; after an unavoidable reset the receiver can no longer tell whether the sequence is complete.2526 The Master Channel count lets the receiver check the whole Master Channel; the Virtual Channel count gives each VC its own accountability and is the basis for systematic packet extraction and for the optional loss flags of the services.2641 ECSS phrases the reset rule as "not reset before reaching 255 unless there is a major system reset"; the adoption notice lists this wording difference among those with CCSDS.65111 The Virtual Channel Frame Count is generated by the VC Generation Function, while the Master Channel Frame Count is filled in later by the MC Generation Function, after virtual channel multiplexing.3537

    Inference

    An 8-bit counter cannot reveal the loss of a multiple of 256 consecutive frames on one channel. On a Master Channel shared by several VCs, the MC count still detects losses when the VC count of a rarely used VC would not, which is one practical reason for having both counters. The ECSS extended VC frame count (below) removes most of this ambiguity. This reasoning is the wiki's own, built on the field definitions.2567

    Transfer Frame Data Field Status. The last two octets describe the content of the data field.

    The Segment Length Identifier is a fossil: earlier issues allowed Source Packet Segments, which are no longer defined, and the value 11 is the one that meant "no segments".27 The Synchronization Flag tells the receiver whether the First Header Pointer is meaningful at all: with Sync = 1 the data field carries a privately formatted VCA_SDU and the pointer, Packet Order Flag and Segment Length Identifier are undefined by CCSDS (they are passed to the user as the "VCA Status Fields").272818

    First Header Pointer (FHP). Octets of the data field are numbered from 0. The FHP holds the binary position of the first octet of the first packet that starts in this frame, so the receiver can find a packet header even if it missed the previous frame. Subsequent packets are located through each packet's own length field.28

    FHP value Binary Meaning
    0 to 2045 (at most 2041 in practice, see below) — Offset of the first packet header starting in this data field. Octets before it belong to a packet continued from an earlier frame of the same VC.28
    0x7FF (2047) 11111111111 No packet starts in this data field (a long packet continues through it).28
    0x7FE (2046) 11111111110 The data field contains only idle data: an OID Transfer Frame.2831

    Inference

    The standard reserves the two values 0x7FE and 0x7FF but states no maximum offset. Because a TM frame is at most 2048 octets, its data field is at most 2042 octets (2048 minus the 6-octet primary header), so a real offset never exceeds 2041 and can never collide with the reserved values. This calculation is the wiki's own.8028 The 2026 coding standard states the same link from the other side: the 11-bit pointer is what limits TM frames to 2048 octets.114

    Secondary header¶

    The optional Transfer Frame Secondary Header (FSH) follows the primary header. It is associated either with the Master Channel (then present, with the same length, in every frame of the MC) or with one Virtual Channel (then present in every frame of that VC). Its length is fixed for the associated channel for a Mission Phase.2966

    Subfield Bits Values Meaning
    Secondary Header Version Number 0–1 0b00 Version 1, the only version defined.29
    Secondary Header Length 2–7 1–63 Total secondary header length in octets minus one; static.29
    Secondary Header Data Field 8 … 1 to 63 octets Mission data; CCSDS defines no content.2915

    The secondary header is the vehicle of the VC_FSH and MC_FSH services, whose SDUs are 2 to 64 octets long.15 ECSS-E-ST-50-03C adds one standardized use, inherited from the ESA Packet Telemetry Standard: the extended virtual channel frame count. The secondary header is then 4 octets long (length field = 3) and its 24-bit data field counts the roll-overs of the 8-bit VC frame count, giving a 32-bit count with the most significant 24 bits in the secondary header.67 The ECSS handbook explains that ESA missions used it to sequence frames reliably, in particular when recorded frames are played back, and to detect losses without reference to ground receive time; it is not defined by CCSDS.7673

    ECSS-E-ST-50-03C has since been replaced by the adoption notice ECSS-E-AS-50-22, and this count is the only normative amendment that Rev.1 of the notice (13 January 2023) makes to CCSDS 132.0-B-3. Its Table 4-1 adds a new requirement 4.1.3.1.7 and a new section 4.1.3.4, whose five requirements restate requirements a to e of ECSS-E-ST-50-03C §5.3.4:11067

    New clause Requirement (paraphrased)
    4.1.3.1.7 The secondary header may be used to provide an extended virtual channel frame count as specified in 4.1.3.4
    4.1.3.4.2.1 The secondary header is then 32 bits long (length field = 3)
    4.1.3.4.2.2 Its data field holds the 24-bit extension of the VC frame count
    4.1.3.4.2.3 The extension is a binary count of the roll-overs of the 8-bit VC Frame Count; together they form a 32-bit count, the 24 most significant bits in the secondary header
    4.1.3.4.2.4 The extended count is associated with either a Master Channel or a Virtual Channel. With a Master Channel, every frame of the MC carries it, but each frame carries the value of its own VC; with a Virtual Channel, the secondary headers of the other VCs may be absent or used for other purposes
    4.1.3.4.2.5 Its use is static for the associated channel throughout a mission phase

    Reading the extended count (illustrative)

    A frame whose secondary header data field holds 0x000123 and whose primary header VC Frame Count is 0x45 has the 32-bit count 0x00012345 = 74,565. The 32-bit count wraps after 2³² frames, against 256 for the primary header alone.110

    Inference

    Solar Orbiter puts the extension in the secondary header of every frame (below), which is consistent with the Master Channel association of clause 4.1.3.4.2.4, each frame carrying the count of its own VC (a separate association on every VC would look the same on the link). The ICD cites ECSS-E-ST-50-03C, not the adoption notice, so it does not use this wording.9390110

    Solar Orbiter puts a secondary header in every frame, with identification octet 0b00000011 and a 3-octet extension of the VC frame counter. This is the layout of the ECSS extended count; the ICD requires its frames to follow ECSS-E-ST-50-03C.9390

    Transfer Frame Data Field¶

    The data field holds either packets, exactly one VCA_SDU, or idle data. Packets and VCA_SDUs are never mixed on one VC; which of the two a VC carries is fixed by management for a Mission Phase, and idle data may appear on a VC that carries packets.30 Packets are inserted contiguously and in forward order, so the first and the last packet of a data field are often fragments of packets that started in an earlier frame or continue in a later frame of the same VC.30

    The packets must have a CCSDS-authorized Packet Version Number, and the service provider must know where each version keeps its length field, because that is how packets are delimited.1560 In practice these are Space Packets and Encapsulation Packets; the TM Blue Book points to the SANA registry for the list of authorized version numbers.15

    OID frames. When a frame must be released and there is not enough data for it, the protocol sends an Only Idle Data (OID) Transfer Frame: its FHP is 0x7FE and its data field is filled with a pseudo-noise (PN) sequence. Issue 3 makes the PN content mandatory: a 32-cell Linear Feedback Shift Register with polynomial \(D^0 + D^1 + D^2 + D^{22} + D^{32}\), initialized once at device start-up (all ones in the Fibonacci form, 00000000001111111111111111111101 in the Galois form) and never restarted, so consecutive OID frames continue the same sequence.3151 The pattern starts FF FF FF FF 6D B6 D8 61 45 1F 11 F1 97 16 72 3C BE 7E 00 B1.51

    • The OID frame's VCID must be that of a VC that carries packets; CCSDS prefers a VC dedicated to idle frames, unless the secondary header or OCF content of a particular VC must be sent.31
    • The secondary header and OCF of an OID frame can still carry valid data, and an OID frame can be inserted even in the middle of a packet that is split across frames.31
    • The idle data of an OID frame is not the same thing as an Idle Packet. The random pattern is there to avoid reception problems caused by insufficient randomization.31

    Inference

    The CCSDS coding Green Book (2020) describes how OID frames filled with zeros, after the short 255-bit randomizer, produced periodic transmitted sequences and spectral lines that could violate ITU power-flux-density limits, and proposes filling OID data fields with a long, free-running PN sequence such as a 32-cell LFSR. The Green Book suggests doing this inside the coding sublayer, so that the data link layer could keep filling OID data fields with zeros.82 The 2021 TM SDLP issue instead mandates such a free-running 32-cell LFSR in the data link layer itself (§4.1.4.6, with example generators in the new Annex D). That the second is a response to the first is this wiki's reading; the TM SDLP itself only says the random pattern avoids problems from insufficient randomization.312 ECSS-E-ST-50-03C (2008) still left the idle pattern as a mission configuration parameter.74

    The ECSS adoption notice lists the OID randomization among its differences from ECSS-E-ST-50-03, which had no such specification, and points to the two generator forms of Annex D.111 Since Issue 6 of the coding standard (2026) the coding-layer pseudo-randomizer is mandatory as well, so an OID frame's PN fill is now always randomized again, with the rest of the frame, below the data link layer.117

    Operational Control Field¶

    The optional 4-octet OCF follows the data field. Like the secondary header, it is associated either with the Master Channel or with one Virtual Channel and is then present in every frame of that channel.32 Bit 0 is the Type Flag:32

    • 0: Type-1-Report, a Communications Link Control Word (CLCW) reporting the state of the on-board telecommand receiver (FARM) to the ground (FOP).
    • 1: Type-2-Report. In CCSDS 132.0-B-3, bit 1 then distinguishes project-specific content (0) from an SDLS Frame Security Report (1). In ECSS-E-ST-50-03C, written before the SDLS extended procedures, bit 1 = 1 is reserved for future application.3270

    The Type Flag, and bit 1 of a Type-2 report, may change from frame to frame on the same channel.32 CCSDS warns that the VCs carrying the OCF must be sent often enough for the COP to work, because the COP can time out if CLCWs do not arrive in time.32 The ECSS handbook recommends using the OCF only for Type-1 reports, and ECSS notes that some ground equipment can only retrieve an OCF associated with the Master Channel.7770

    The CLCW layout is defined by the TC Space Data Link Protocol, and each TC VC in use has its own CLCW reporting.84 Its semantics (lockout, wait, retransmit, FARM-B counter, N(R)) are explained on the COP-1 page.

    Frame Error Control Field¶

    The optional 16-bit FECF is the last field. Its presence is a management decision for the whole Physical Channel and Mission Phase.33 It is a cyclic redundancy check over the whole frame except the FECF itself, computed with the generator polynomial \(G(X) = X^{16} + X^{12} + X^5 + 1\) and a shift register preset to all ones:33

    \[\text{FECF} = \left[ X^{16}\, M(X) + X^{(n-16)}\, L(X) \right] \bmod G(X), \qquad L(X) = \sum_{i=0}^{15} X^i\]

    where \(M(X)\) is the \((n-16)\)-bit frame content with the first transmitted bit as the highest-order coefficient. The \(X^{(n-16)} L(X)\) term is what presets the register to all ones. At the receiver the syndrome \(S(X) = [X^{16} C^*(X) + X^n L(X)] \bmod G(X)\) over the received frame, FECF included, is zero for an error-free frame.33

    • Error detection only. ECSS states that the FECF shall not be used for error correction.71
    • Capabilities. For blocks shorter than 32,768 bits it detects every odd number of bit errors, every pattern of up to two bit errors (the Green Book says three), every single burst of 16 bits or less, and misses a random even-weight error pattern with probability of about \(2^{-15}\) (≈ 3 × 10⁻⁵).7183
    • When it is mandatory. It must be present when neither Reed-Solomon nor LDPC coding is used; with Reed-Solomon or LDPC it is optional.81 ECSS-E-ST-50-03C (2008) exempts only Reed-Solomon-encoded frames, and its companion coding standard ECSS-E-ST-50-01C reminds that frames on uncoded or turbo-coded channels therefore carry the CRC.71120 Issue 6 of the coding standard (2026) keeps the rule and spells it out: the FECF is mandatory with no coding, convolutional or turbo coding, optional with Reed-Solomon, concatenated or LDPC coding, and with slicing a frame is invalid if any part of it lies in an invalid information block.116 The Green Book explains why: uncoded and convolutionally coded data have no error-detection capability of their own, and a turbo decoder has only a limited one, whereas the (255,223) Reed-Solomon decoder (\(E\) = 16) already detects errors far better than the CRC. The \(E\) = 8 code detects errors only about as well as the CRC, so the Green Book still requires the CRC in that case.83

    Inference

    The definition above is the CRC-16 variant often called "CCITT-FALSE" (polynomial 0x1021, initial value 0xFFFF, no bit reflection, no final XOR). This wiki computed its check value on the ASCII string 123456789 as 0x29B1, which can serve as an implementation test. The name and the test vector are not given in the CCSDS or ECSS documents.33

    Service types¶

    The three service types describe how SDU submission relates to frame release:854

    • Asynchronous: SDUs are queued and each is sent exactly once, in order, when the provider decides (for example according to the multiplexing rules).
    • Synchronous: the SDU is placed in a one-deep buffer whose content is copied into every frame released on the associated channel. A value may therefore be sent several times, or overwritten before it is sent. It is essentially time-division multiplexing.
    • Periodic: a synchronous (or VCA/VCF/MCF) service whose channel releases frames at a constant rate, with a specified maximum delay and jitter.

    Rules that keep the services consistent¶

    • An MCF service on a Master Channel excludes every other service on it; a VCF service excludes every other service on its VC.12
    • VC_FSH and MC_FSH cannot coexist on one Master Channel; nor can VC_OCF and MC_OCF.12
    • VCP and VCA cannot coexist on one VC.12
    • Frames given to the VCF or MCF services are partially formatted: they must have the same length as the provider's own frames, and the fields that the provider will fill later (MC frame count; MC secondary header and OCF if those MC services exist; FECF) are left empty.1611

    The Green Book's example shows the services working together: urgent and non-urgent packets on VC 0 and VC 1, an on-board clock-calibration value sent with VC_OCF on VC 0, and an encrypted stream cut into fixed-length chunks and sent with VCA on VC 2.55

    Protocol procedures¶

    Sending end¶

    Data flow down a fixed chain of functions, which CCSDS draws as the channel tree. Multiplexing mixes streams with different identifiers; commutation places data from different services into the same frame.14

The function sets the FHP to the first packet start, or to 0x7FF if none.     2. Virtual Channel Generation (one per VC) builds the frame: puts the data field or VCA_SDU in place, generates the primary header and the VC frame count, inserts VC_FSH and VC_OCF SDUs, and leaves the MC frame count, MC secondary header, MC OCF and FECF empty.35

If there is a single Master Channel and nothing is ready at a release time, this function generates an OID frame to keep the stream continuous.36
    4. Master Channel Generation (one per MC) inserts MC_FSH and MC_OCF SDUs and the MC frame count.37
    5. Master Channel Multiplexing (one per Physical Channel with several MCs) orders the MCs' frames and those of MCF users and, again, creates an OID frame if nothing is available.38

    Receiving end¶

    The receiving functions mirror the sending ones, from the bottom up:4443424140

    1. All Frames Reception recomputes the CRC; a frame with a detected error does not have to be delivered in cross-support situations.
    2. Master Channel Demultiplexing routes frames by MCID and discards frames whose MCID is not valid.
    3. Master Channel Reception extracts MC_FSH and MC_OCF SDUs and can flag gaps in the MC count.
    4. Virtual Channel Demultiplexing routes frames by VCID and discards frames with an invalid VCID.
    5. Virtual Channel Reception extracts the data field (to the packet extraction function or the VCA user) and the VC_FSH and VC_OCF SDUs, and can flag gaps in the VC count.
    6. Packet Extraction uses the FHP and the packet length fields to delimit packets, completes a packet split across frames with the beginning of the next data field of the same VC, delivers packets to users by PVN, discards Idle Packets and idle data fields, and need not deliver incomplete packets.

    One rule is worth stressing: if the position at which the extractor expects the next packet header disagrees with the FHP, the FHP wins and extraction continues from the FHP.40 This is what makes the stream self-healing after a lost or corrupted frame.

    ECSS adds recommended practice: data fields of frames with uncorrectable errors should not be used by packet extraction, and every missing or erroneous frame detected through the counters should be signalled as a gap.77

    Virtual channel multiplexing and quality of service¶

    Virtual channels are the protocol's only tool for quality of service. A long, low-priority packet (a memory dump, say) occupies its VC frame after frame; if a short urgent packet appears, a frame of another, high-priority VC can be inserted between two frames of the long packet, because each VC keeps its own packet assembly. The service provider needs buffer memory to do this, and the project must design the multiplexing algorithm to meet its QoS needs; CCSDS recommends no standard algorithm.57 The ECSS handbook suggests giving an instrument with very long packets its own VC, and choosing the maximum packet length per VC with the waiting time of other sources in mind.77

    The SDLS option¶

    With the optional Space Data Link Security protocol, each VC can individually be protected by authentication, encryption or authenticated encryption. A Security Header follows the primary (or secondary) header and an optional Security Trailer follows the data field, both shrinking the data field; the primary and secondary headers themselves are unchanged.465

    Primary header · Secondary header · Data field · OCF · FECF Primary header · Secondary header · Security Header · Data field · Security Trailer · OCF · FECF

    7.0 NYGG0653 TF Secondary Header Data 3/13 24 bits
    10.0 NYGG0670 Operational Cntrl Field (whole word) 3/14 32 bits
    10.0–13.0 NYGD0655 … NYGD0668 CLCW subfields (type, version, status, COP, VC Id, flags, FARM-B, report value) various 1–8 bits
    14.0 NYGG0669 Frame Error Cntrl Field 3/12 16 bits
    16.0, 20.0, 24.0 NYG00538/539/540 ERT sec / msec / psec 3/14 32 bits each

    The widths come from the SCOS-2000 parameter type table (PTC 3, PFC 4 = 8-bit unsigned, PFC 6 = 10 bits, PFC 7 = 11 bits, PFC 12 = 16 bits, PFC 13 = 24 bits, PFC 14 = 32 bits; PTC 2 = enumerated with PFC bits; PTC 1 PFC 0 = 1-bit Boolean), and offsets are counted from the end of the SCOS-2000 packet header with bit 0 as the leftmost bit of the octet.100101

    Inference

    The offsets show that a "mini-transfer frame" is the TM frame with its data field removed: 6 octets of primary header, 4 of secondary header, 4 of OCF and 2 of FECF make exactly the 16 octets of MTFBAD and MTFIDLE; MTFGOOD adds 12 octets of Earth Reception Time. The ICD does not define these internal packets; this is deduced from the MIB rows.98

    The CLCW subfields are defined twice more with a validity parameter: parameters NYGDA6xx are valid only when the CLCW VC Id (NYGD0659) equals 1, and NYGDB6xx only when it equals 2, so the reports of Solar Orbiter's two telecommand VCs (one per on-board TC decoder) are kept apart.9810295 The "VC1/VC2 Lockout" and "VC1/VC2 Retransmit" parameters carry textual calibrations (CYGT0663TM: 0 = NO LOCKOUT, 1 = LOCKOUT; CYGT0665TM: 0 = NO RETRANSMIT, 1 = RETRANSMIT) and monitoring checks (hard-severity status checks, OCP OCP_TYPE = H) that expect NO LOCKOUT and NO RETRANSMIT, applicable only when the ground variable NYG01923 "CMD VC ID" has the matching value 1 or 2.98103 NYG01923 is placed in SPID 66832, described as the "MISC_PACKET: Config variables packet MISCdynamic server".98

    Inference

    Read together, these rows mean that the control system alarms on FARM lockout or a retransmit request only for the TC virtual channel it is currently commanding on, and ignores the CLCW of the other decoder. The MIB does not state this intent; it is deduced from the applicability criteria.

    On the spacecraft side, the MIB's decoding of the TM encoder configuration register includes a 2-bit field "SCW" whose textual calibration CCDX9326TM offers ClcwD0, ClcwD1, ClcwD0 and D1 and round robin.98

    Inference

    "SCW" plausibly selects which TC decoder's CLCW the encoder places in the OCF: decoder 0, decoder 1, both, or the two in turn. A round-robin setting would explain why the ground needs per-VC copies of the CLCW parameters, distinguished by the VC Id field. Neither the ICD nor the MIB documents the field; see TM coding for the whole register.9895

    Frames, time correlation and the ground segment¶

    The frame is also the time reference of the downlink. In the ESA Packet Telemetry scheme quoted in the Rosetta and Mars Express interface document, the on-board clock is sampled at the leading edge of the first bit of the sync marker of the VC 0 frame whose VC frame count is 0 (or every 128, 64 … 1 frames of VC 0), the sample is sent in the spacecraft time packet before VC 0 has counted 255 more frames, and the ground station time-tags the same marker bit.105 SCOS-2000's time correlation defines frame radiation, reception and Earth Reception Time against that same marker edge.106 See time correlation in SCOS-2000.

    On the ground, the SLE return services deliver TM frames to the control centre: Return All Frames (RAF) delivers every frame of a physical channel, Return Channel Frames (RCF) a Master Channel or selected VCs, and Return Operational Control Field (ROCF) just the OCFs.56 RAF annotates each frame with its Earth Reception Time, the antenna, a good/erred quality flag and a data-link-continuity value, and removes Reed-Solomon check symbols from frames that decoded correctly.107 How ESOC's ground station interface hands frames to SCOS-2000 is described on the NCTRS and NIS page, and how packets are then interpreted with the MIB on the MIB monitoring page. The end-to-end path is described in Downlink: from on-board parameter to operator display.
